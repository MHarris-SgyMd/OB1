## Changelog

The writable-projection spike, prototyped on a throwaway Postgres at 053: the write functions can append the event first and project the row in the same transaction with an empty contributor delta, the existing lock-order behaviours held, read-your-writes held and the log rebuilding every row through the same projector — while a view named `thoughts` breaks the community schemas' `ADD COLUMN`, `CREATE INDEX`, `REFERENCES` and row triggers; the event-sourcing ADR's second gate opens on option 2 (SMD-1999).

## FORK

The writable projection prototyped — the three write functions append the event and project the row with nothing a vendored caller has to change, a view in the table's name breaks the community schemas; the event-sourcing ADR's second gate opens on the dual-write (SMD-1999)

**What changed.** `evals/eval-writable-projection.ts` resets a throwaway Postgres to migration 053 four times and runs one scripted set of writes against each schema: 053 as it stands; **option 2** — `thoughts` stays a table and `upsert_thought` (2- and 3-argument), `update_thought` and `delete_thought` append the `thought_audit` row first and call one projector that writes the row in the same transaction, while the audit trigger, which today derives the event from the row after the write, becomes the CHECK that the projected row matches its event (SQLSTATE `OB002` when it does not) and stays the writer for a raw write; **option 1** with 053's functions unchanged — the table renamed to `thought_rows`, a view named `thoughts` over it, INSTEAD OF triggers that append and project; and option 1 with option 2's bodies. The writes are the callers' own shapes: the 3-argument capture as `integrations/readwise-capture` sends it, the 2-argument form the recipes use, the 4-argument form with chunks, the server's 9-argument and the integrations' 6-argument `update_thought` (a content edit, a metadata patch, `supersedes`, `DUPLICATE_CONTENT`, `STALE_READ`, the re-embed's same-text-new-vector), `delete_thought` plain, refused `CITED` and detaching, a raw `INSERT INTO thoughts`, `db/ingest-records.ts`'s `ON CONFLICT (id) … RETURNING (xmax = 0)`; then the community DDL verbatim from `schemas/` (workflow-status's `ADD COLUMN` and `CREATE INDEX`, agent-memory's `REFERENCES public.thoughts(id)`, entity-extraction's `AFTER … FOR EACH ROW` trigger, a sidecar `UPDATE`), the three behaviours the functions carry (SMD-1043's fingerprint lock, SMD-1323's `FOR NO KEY UPDATE`, SMD-1462's lock order — two sessions each, the waiter read from `pg_locks`), the audit-row and claim counts per write, read-your-writes in one session with the drop-the-projector control, and the replay: the rows copied, the projection wiped, every event replayed in `(created_at, seq)` order through the same projector the live write used. The prototype's SQL is in `evals/writable-projection/` — `common.sql` (one diff rule lifted out of 046's trigger, the append as a function, the projector, an embedding snapshot keyed by `(content_fingerprint, embedding_model)` — SMD-1998's key made a table — the checking trigger, 050's stamp as callable functions, 001's `updated_at` trigger yielding to the projector's stamp), `option2-functions.sql`, `option1-view.sql`, `option1-undo.sql`; it lives where check 7 does not look, deliberately — the functions are redefined for the measurement, not shipped. `evals/writable-projection.ts` holds the rules pure: the four options, the fourteen pre-registered criteria and their gating, the judgement of probes, the verdict, the recommendation's tie-break, the differential's normalisation, the replay rule with its one tolerated difference, the recorded matrix and the drift from it, the report. `--self-check` (54 probes) runs in the portable-server job; `--check` (the run, held to the recorded matrix) in the data-layer job after SMD-1998's fixture.

**Why.** SMD-1997 moves the write-side truth to the event log and makes the `thoughts` row a projection — and the entire community surface writes to that row. The ticket named three shapes and asked which keeps the contract with the least surface, with read-your-writes non-negotiable (an agent that captures then searches must see its own write). The criteria, the bar (GO when C1–C6 and C10–C12 all PASS and C7–C9 hold; NO-GO on any contract FAIL) and the expected outcome were posted on the ticket before the prototype ran.

**Held.** The self-check: the contract's shape; `judge` (no probe → N/A, one failure → FAIL naming it); `verdict` (a contract FAIL, a behaviour that does not hold, an unmeasured contract criterion each → NO-GO; informative criteria never enter); `recommend` (the shorter delta, fewer moved objects on a tie, none when none is GO, never the baseline); the normalisation (a capture's content and an update's key move set aside, copies not mutations, a length difference one mismatch); the replay rule (a NULL key the projector filled is the one tolerated difference, a key lost is not, presence both ways, `updated_at` and the vector compared); the cost line; the recorded matrix's cells and the drift's wording; the report's parts; the arguments; the prototype SQL substituted with no placeholder left and no destructive statement in it (check 21 reads it). `--check` on a real Postgres: no cell moved, option 2 GO and option 1 NO-GO, the replay only tolerated differences, the differential identical, option 2's delta empty.

**Measured after** (Postgres 16.15, pgvector 0.8.6, width 8, no provider; the report is in `evals/README.md`, verbatim). **Option 2 is GO** with an empty contributor delta: every scripted write returns what 046 returns, the log and the rows are byte-identical to the baseline's for the same writes once the prototype's two additions (content on a capture, the key's move on an update) are set aside, the three behaviours hold, one audit row and one extraction claim per logical write, a capture is visible to a `SELECT` and to `search_thoughts_keyword` in the same session with no delay, the event appended without the projector leaves no row and the search misses until the projector runs, and the replay rebuilds every row equal to its copy — content, key, metadata, provenance, `created_at`, `updated_at`, the vector from the snapshot and its label — the one difference the raw row's key, NULL before and filled after. A capture costs the same (574 → 570 µs medians over 200) and an edit some more (568 → 635 µs; ×1.12 to ×1.4 across the review's runs, the round trip dominating). **Option 1 is NO-GO twice**: with 053's functions, every capture fails (`INSERT … ON CONFLICT` has no unique constraint on a view) while `update_thought` and `delete_thought` through the INSTEAD OF triggers work; with option 2's functions, C6 fails whole — `ADD COLUMN` "not supported for views", `CREATE INDEX` likewise, `REFERENCES` "not a table", the row trigger "is a view" — and ingest-records' `xmax` "does not exist". Row locks do work through the simple view; a raw insert through it gains 003's key. **053 as it stands** fails C1's last clause alone — the capture event carries no content — and C12 is not measurable: the log cannot rebuild the rows.

**What it says for the ADR.** The extension contract survives the move by option 2 and by nothing else prototyped: the projector belongs in the write functions, the trigger becomes the check, and a vendored contributor changes nothing. Two consequences the run found that the design must own: a projected write CASCADES — a tombstone's `ON DELETE SET NULL` writes every successor's pointer and 042's guard bumps a citing thought's stamp under the delete's projection, so the check needs a rule for the rows an event moves that it does not name (live: the successor's move is appended as its own event, as 046 does; replay: it is skipped, since the log holds it); and a write that changes nothing leaves no event and so no write — an identical re-capture no longer bumps `updated_at` (053's `ON CONFLICT DO UPDATE` does), and a vector arriving on a row that has one is a projection refresh whose stamp the log cannot replay, so it leaves `updated_at` alone (053's re-embed bumps it, and reads as a change to a caller's `if_unchanged_since`). The migration path the ticket asked for: (1) the capture event carries content and the diff rule, the append and the stamp become functions (046-shaped, additive); (2) the three write functions append then project, the trigger checks under `ob1.projecting` and appends otherwise — dual-write, the log complete from that day; (3) the projector is the only writer of the row for the in-tree paths, a raw write still trigger-audited; a replay (`ob1_project_thought_event(id, NULL, NULL, true)` over the log) is the rebuild. `thought_changes` (052) can then read a capture's head from the event rather than the row.

**Not taken.** Option 3 (a projection table beside a compat view) has option 1's writer surface and is judged from its rows. The production projector, a migration, `thought_changes` reading the event, the raw in-tree writers (`review_supersession_proposal`, the backfills, the guard's bump — trigger-audited as today), the chunk rows (a recipe 022 does not record; SMD-1998 E). The prototype redefines `update_updated_at`, `thoughts_write_audit` and the three functions; preflight's recognisers and test-schema's sentinel reads pin those bodies, and the real build moves them with the bodies.
