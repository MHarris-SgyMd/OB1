## Changelog

Both workflows name their runner image, `ubuntu-24.04`, where they had `ubuntu-latest`, which GitHub moves to Ubuntu 26 from 2026-10-19. Every action is pinned to a full commit SHA with its tag in a trailing comment, where it had a tag its owner could move (the release job runs its actions with `packages: write`), and at its latest release, all on Node 24. The two images the release job's actions start, QEMU's binfmt and the BuildKit builder that pushes to GHCR, are pinned by digest, and no checkout leaves the job token in the workspace (`persist-credentials: false`). `.github/dependabot.yml` moves the pins weekly, a week after a release, and check 23 refuses a tag, a SHA with no tag comment, or a `-latest` runner (SMD-2093).

## FORK

The workflows name their runner image and pin every action to a commit; Dependabot moves the pins and check 23 holds them (SMD-2093)

**What changed.** Every `runs-on: ubuntu-latest` (ten in `fork-checks.yml`, one in `release.yml`) is `ubuntu-24.04`, the image `ubuntu-latest` resolves to today, so nothing about the runner moves in this PR. Every `uses:` is a full commit SHA with its tag in a trailing comment, each at its action's latest release. `actions/checkout` goes from v4 to v7.0.1, `actions/upload-artifact` from v4 to v7.0.1, the three `docker/setup-*`/`login` actions from v3 to v4, and `docker/build-push-action` from v6 to v7.4.0. `oven-sh/setup-bun` stays v2 (v2.2.0, the commit `v2` pointed at). Every one runs on Node 24, so the "Node.js 20 is deprecated" warning goes. The ticket named checkout v5, but v7 is current, and Dependabot would open that PR on its first run. None of the majors crossed changes an input or behaviour these workflows use; every `with:` key they pass is declared in the pinned action.yml. The changes were checkout v6's credentials file, checkout v7's refusal of fork checkouts under `pull_request_target` and `workflow_run`, build-push v7's removal of two env knobs this job never set (`DOCKER_BUILD_RECORD_UPLOAD`, the one it sets, stays), and setup-buildx v4's removal of deprecated inputs it never passed.

`.github/dependabot.yml` has one `github-actions` update over `/`, weekly, with a seven-day cooldown on version updates (a security update does not wait), minor and patch releases grouped into one PR, and each major sent alone. Dependabot rewrites the SHA and the comment together. Its commit-message prefix is `"[fork] "`, with the trailing space. dependabot-core appends a colon to a prefix that ends in a letter, a digit, `)` or `]`, and `[fork]: Bump …` would fail commitlint's header rule, an error. The space gives `[fork] Bump …`, which passes, with only the ticket-suffix warning.

Check 23 in `scripts/check-fork-consistency.ts` holds every workflow under `.github/workflows/` to three rules:
- every job's `runs-on` names an image: no `-latest` label in any case or size (`macos-latest-large` moves too), and no expression it cannot read; a runner group alone names none and passes;
- every `uses:` (a step's, or a job's reusable workflow) is a 40-hex SHA with a `# vX.Y.Z` comment (`# X.Y.Z` for an action whose tags carry no `v`), a local `./` path, or a `docker://` image by digest;
- `.github/dependabot.yml` is a `version: 2` file, every entry on a schedule Dependabot accepts (a known interval, a `cronjob` for `cron`, or its multi-ecosystem group's), with a `github-actions` entry over `/` that can open a PR (not limited to 0, not ignoring `*` at every version; ignoring every action's majors is fine). It is a heuristic for the ways a file stops the pins moving, not a validator of Dependabot's schema.

The structure is read with Bun.YAML. The comment, which a parser drops, is read from the value's line: the first unclaimed line carrying it, with block scalars (`run: |`, a `- |` item, an anchored `&a |`) skipped. A SHA-pinned step in flow style is refused, since its tag cannot be read. And every SHA-pinned `uses:` line the reader finds must carry its tag, whether a step's tag was read from it or not, so text the reader cannot tell from a step (a quoted scalar across lines, an input named `uses`) cannot lend its tag to a bare step below it. Lines end in LF or CRLF. Steps reused by YAML alias have no line of their own and are refused, as actionlint 1.7.7 refuses them. The check holds a pin's shape, not its truth: a comment naming another tag, or a commit only a fork of the action holds, is what zizmor finds, and zizmor ran once and is not in CI.

The release job's actions start two images by default, and those moved by tag too: setup-qemu runs `tonistiigi/binfmt:latest` with `--privileged`, and setup-buildx starts `moby/buildkit:buildx-stable-1`, the daemon that pushes to GHCR with the job's login. Both are now pinned by digest through the actions' inputs (`qemu-v10.2.3`, BuildKit `v0.32.2`, the versions the moving tags named on 2026-09-24; a builder on that pin bootstraps and reports v0.32.2). Neither check 23 nor Dependabot reads an action's inputs, so these move by hand, as the workflow comment says.

zizmor (1.30.1, run once as the ticket asked, online audits included) reported three kinds of finding, all fixed. `artipacked` covered all eleven checkouts, which left the job token in the workspace. They now set `persist-credentials: false`: no step talks to the remote after checkout (a job that reads history takes it at checkout, and the repository is public). `cache-poisoning` flagged the release job's `setup-bun`, which now sets `no-cache: true`, so the Bun it publishes with is downloaded fresh. `dependabot-cooldown` flagged the new `dependabot.yml`, which now waits seven days. FORK.md's "Checking CI on this fork" says all of this in one paragraph, and "Files we own" lists `dependabot.yml`.

**Why.** On 2026-10-19 `ubuntu-latest` becomes Ubuntu 26 on GitHub's schedule, not ours. The Docker, compose, python3, jq and shellcheck steps all depend on what the image ships, so the switch would have landed as an unrelated red on whichever PR ran first after it. Now the move is a PR of its own, with the stack job's lines rerun. A tag is a pointer its owner, or anyone holding its owner's credentials, can move, and the release job runs five third-party actions holding `contents: write` and `packages: write`. SMD-1808 set SHA pinning aside, and a pin that nothing checks drifts back the first time someone copies a step from a README.

**Held.** Check 23's probes run on in-memory workflows. It accepts twenty: a SHA pin with its tag, one quoted, one on the line after the step's name, one after a folded `name: >-`, a `uses:` key with an anchor, a docker image by digest, a label list with no `-latest`, a `uses:` line inside a `run:` body, two steps on one pin, a bare copy of the pin in an earlier run body (after a blank line too, and in a `run: |-`, a `run: | # note` and a tagged `!!str |` body), an earlier `- |` item and an earlier nested `- - |` item (none takes the commented step's line), a tag comment with no `v`, a runner group alone, a group with a named image, and a workflow with CRLF line ends. It refuses twenty-nine mutants with exactly one problem each, naming what broke: `ubuntu-latest`, a `-latest` label in a list, with a size, in another case, and as a group's label; a runner by expression; a non-string label; a major tag, a branch, a short SHA, a 41-character ref, no ref; no comment, a comment naming no tag, a date for a comment, and either of two steps on one pin left bare; a bare step under a commented pin in a run body, a `- |` item, an anchored run body, a quoted run across lines, and an input named `uses`; flow style; steps reused by alias; a docker image by tag, and a digest with text after it; a reusable workflow by tag; a `uses:` that is not a string; and no `jobs:`. It holds `dependabot.yml` to seven accepted forms (`directory: /`, `directories: [/]`, an ignore of every action's majors, and of every action at some versions, a cron schedule with its cronjob, an entry scheduled by its multi-ecosystem group, and one whose own schedule stands where its group names none) and eleven refused ones, each by its own message: a missing file, an npm-only entry, another directory, a limit of 0, an ignore of `*`, `version: 1`, no schedule, an unknown interval, cron with no cronjob, a second entry with no schedule, and multi-ecosystem groups written as a list. Deleting any one of the rules the five review passes added, tightened or gave a probe fails one: thirty-five code mutants, one per rule. On the live tree, four mutants each fail the check, and the restored tree passes: build-push put back on `@v6`, one runner put back on `ubuntu-latest`, setup-bun's tag comment deleted, and `dependabot.yml` removed.

**Measured after.** Both of the ticket's greps come back empty: `grep -n runs-on` finds no `-latest`, and `grep -nE 'uses: [^#]+@v[0-9]'` finds no match. actionlint 1.7.7 (CI's pin, with shellcheck) passes on both workflows. zizmor's default persona reports nothing on `.github/workflows/` or `.github/dependabot.yml`, online audits included (impostor commits, known-vulnerable actions, a tag comment that does not match its SHA). The scripts typecheck and check-fork pass.

**Not taken.**
- Reading `runs-on: ${{ matrix.os }}` against the job's matrix values. A matrix of named images (native arm64 runners in place of QEMU, say) is refused today, and the contributor who wants one edits check 23 to read `strategy.matrix`.
- Giving the Release rehearsal a read-only token (SMD-2111). It runs on a PR touching `release.yml` with the job's `contents: write` / `packages: write`, so a Dependabot bump of a docker action runs the new action with those rights before review. A maintainer's PR already did; Dependabot adds an automated route. The fix splits the 350-line job, which is its own change.
- Holding in check 23 the images an action starts by default (release.yml's two, pinned here by hand through the actions' inputs) or a local action's own steps (`.github/actions/`, none today). Each is an action's own schema, not a `uses:`, and the check says in its docblock what it does not read.
- Pinning the three `pgvector/pgvector:0.8.6-pg16` service images by digest. zizmor's pedantic persona asks for it. They are pinned by version tag, compose pulls the same tag, and moving that pin is a stack change (SMD-1860 pinned Ollama the same way), not a workflow one.
- Holding `persist-credentials: false` in check 23, or running zizmor in CI. Both findings are fixed once, as the ticket asked. The repository setting that makes GitHub itself refuse an unpinned action (`sha_pinning_required`) is outside the tree, and is the maintainer's call.
- Moving to `ubuntu-26.04`. That is its own PR, as the ticket says, and it moves actionlint's pin too.
