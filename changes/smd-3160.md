## Changelog

A migration that changes which ticket status types the brain knows can now rebuild only the rows that change: `ob1_rebuild_source_gate_for_types(text[])`, added by migration 106, reconciles the dependency gate's rows for the status types given, where the full `ob1_rebuild_source_gate()` reconciles every source row and holds writes for the whole table while it does (SMD-3160, migration 106).

## FORK

A keyed rebuild of 071's gate mirror for a status-set change — the cost follows the moved rows, not the table (SMD-3160)

**What changed** (migration 106).
- **`ob1_rebuild_source_gate_for_types(text[])`**, beside the full rebuild:
  - refuses outside READ COMMITTED and takes SHARE on `thoughts`, then `thought_sources`, as the full rebuild does (a writer working from the old set could otherwise move a status after the scan);
  - finds the sourced thoughts whose `status_type` is one of the types given, one probe of 001's GIN index on `thoughts.metadata` per type (`metadata @> {"status_type": <type>}`);
  - reconciles those alone with 071's `ob1_source_gate_reconcile(ids)` and returns what it wrote and deleted;
  - takes no advisory lock: SHARE holds off every writer whose triggers could touch the mirror, as the full rebuild relies on;
  - an empty or NULL array touches nothing.
- **The full rebuild stays**, for repair after a write made with the tables' triggers disabled. Its comment now names the keyed form for a set change; 071's header is not edited (append-only), and 106's supersedes that note.
- **For the next set change:** `SELECT * FROM ob1_rebuild_source_gate_for_types('{<each type it adds or drops>}')` after redefining the set.
- **Refuses by name** without 071; a re-apply is a no-op. No table, column or grant.

**Why.** 071 asked a migration that changes `node_lifecycle_types()` to run the full rebuild, which joins every source row to its thought under SHARE locks held to the migration's commit. 105 (SMD-2935) did. Measured in SMD-2935's review pass 5 on PG 16 at compose defaults, writes waited 26 ms at 10,000 source rows, 221 ms at 100,000 and 3.3–4.4 s at a million (2M thoughts), and the cost grows with the thoughts table, heading for minutes at the 1B horizon (SMD-2754, SMD-2758). A set change moves only the rows of the types it adds or drops; stable had 16.

**Held.**
- **test-schema [95]:**
  - a set change that adds a type: the keyed form reconciles that type's rows and no other, so a wrong gate row it was not asked about stays wrong and drift() names it, which the full rebuild then fixes;
  - a set change that drops the type: the same call takes the rows back;
  - an empty or NULL array touches nothing, and on an exact mirror the call writes nothing;
  - refused under REPEATABLE READ, naming the level;
  - a re-apply is a no-op, and both functions' comments say what each is for.
- **Measured** (PG 16 at compose defaults, 2M thoughts and 1M source rows, 70% Linear tickets; each call in a migrate.ts-shaped transaction, a capture issued as it took its locks; warm medians):

  | source rows | rows of the moved type | full rebuild: call / capture waits | keyed: call / capture waits |
  |---|---|---|---|
  | 10k | 212 | 32 / 35 ms | 14 / 20 ms |
  | 100k | 2,122 | 388 / 393 ms | 76 / 82 ms |
  | 1M | 21,212 | 8.8 / 8.9 s | 1.39 / 1.39 s |
  | 1M | 16 (stable's count) | 6.2 / 6.2 s | 14 / 29 ms |

  After every run (20) a full reconcile wrote and deleted nothing and drift() was empty. The keyed scan is a bitmap scan of `thoughts_metadata_idx` into `thought_sources_pkey`. The host was busy, so the full rebuild ran 1.5–2.5× pass 5's times; the ratio is what holds. At tens of thousands of moved rows most of the keyed cost is 071's reconcile itself, whose delete arm then scans the whole mirror rather than its key (16 rows take the key) — a cost for a set change that moves a large share of a 1B brain, not for this one.
- **test-upgrade [20ax]:** refused without 071; onto a populated brain at 105, no thought, audit or gate row moved; a status write waits for the keyed form's locks to its transaction's end (55P03 at a 1 s lock timeout) and goes through after; a re-apply is a no-op. The window guard (seventy-seven) and both enumerations name 106.
