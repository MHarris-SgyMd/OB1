## Changelog

The agent-registry lookup no longer waits on a lock without limit: on the SQL store each of `resolve_agent`'s lock waits is capped at 250 ms (a ceiling — a stricter setting is kept) and a lookup that times out is retried for up to 2 s with no connection held, so a brief migration lock is still waited out while a long one no longer holds pool connections until it clears. A key the lookup still cannot confirm is refused with a retry (JSON-RPC error `-32003`; `/health` answers `ok`) rather than served, since the registry could still say revoked, and a revocation the server has already read stands through any failure until the registry answers otherwise (SMD-2072).

## FORK

The registry lookup's lock waits are capped and a timed-out lookup is retried briefly, a key it still cannot confirm is refused with a retry, and a revocation the server has read stands through any failure — a lock on `ob1_agent_keys` no longer empties the pool or lifts a revocation the server has read (SMD-2072)

**What changed.** `server-portable/store-sql.ts`'s `resolveAgent` is one
statement: a materialised CTE over a one-row scalar subquery sets
`lock_timeout` to `RESOLVE_LOCK_TIMEOUT_MS` (250 ms, `agents.ts`) as a
ceiling — 0, unset or a looser setting lowered, a stricter one kept, local to
the statement's implicit transaction — and `resolve_agent` (volatile, so
evaluated per row of it) runs from it; `lock_timeout` is read as each wait
begins. No `BEGIN`, so a pooler in statement mode passes it (one that carries
Bun's prepared statements: PgBouncer 1.21+ with `max_prepared_statements`
set). `AgentResolver` retries a lookup that times out on a lock — SQLSTATE
55P03, 57014 or 40P01 on `errno` — up to five attempts within 2 s, 250 ms
apart (`BUSY_RETRY`, real time); past that the outcome is the new `busy`,
reused for a second. A key whose revocation this process has read stays
`revoked` through any failure and any reply that is not an answer (no retry),
until the registry answers that it is not. Any other failure (no connection,
no `resolve_agent`) is served by name, as before. The MCP route refuses `busy`
with JSON-RPC error `-32003` for the request's id, "Temporarily unavailable:
the agent registry is busy and could not confirm this key. Retry in a few
seconds."; `/health` answers it `ok`. The PostgREST store (Workers) sets no
cap but copies PostgREST's SQLSTATE onto `errno`; the store interface states
that contract. Warn-once dedupes on the key and its outcome, reset by an
answer.

**Why.** SMD-2041's third run-it review held a key's row and watched ten keyed
`/health` probes empty the pool of 10, every tool call timing out at 8 s. Its
fourth pass left one lookup per key in flight, so K distinct cold keys held K
connections for as long as the lock lasted. Capping the wait alone opens a
worse hole: the header's case for serving an unanswered lookup by name —
"with the registry unreachable, every tool is unreachable too" — is false when
only `ob1_agent_keys` is locked, and a revoked key (still in
`MCP_ACCESS_KEYS`, refused only by the registry) that the process had not
seen would capture under the lock. Before the cap it waited out the lock and
was refused. The retry keeps what that wait gave a good key through a brief
lock — service, a second or two late — and `busy` keeps what it gave every
key through a long one, no service, without the connection held. Keeping an
earlier ok answer does neither: a lookup runs only once the cached ok has
expired, so it is at least a TTL old, the revocation delay the operator
accepted.

Verified in pass 2 (run-it): the 250 ms `lock_timeout` never reached another
query on the connection — Bun gives each query its own implicit transaction
(20/20 pipelined pairs distinct txids; 0/40 readers saw it) — and through
PgBouncer 1.25.2 in statement and transaction mode the lookup capped at
252 ms with every server connection clean after; 50/50 lookups capped, a
generic plan included.

**Not taken.** The caps as a `SET` clause on the function (a migration): it
overrides a stricter caller, and `db/consolidate.ts` and
`db/extract-entities.ts`, batch runs that should wait out a migration, would
fail on its lock. A statement cap: a lookup's waits are its lock waits, each
capped. Letting `initialize` through on `busy`: an unread revoked key would
learn the server's info; the retry covers a brief lock.

**Left as it is.** A DDL lock on `ob1_agents` still stalls captures (046's
audit trigger reads a writer's kind there), as a lock on `thoughts` does, and
046's backfill holds `ob1_agents` FOR SHARE per batch, so a renamed key is
`busy` while a pass runs. More cold keys than the pool holds queue for it, in
rounds of the cap. A lookup overlapping an uncommitted revocation of the same
key still answers ok (older than this change; the cap narrows it to 250 ms).

**Follow-ups.** SMD-2090: `resolve_agent` writes `last_used_at` only when it
is stale or the scope changed, and refuses a key whose revocation committed
while its UPDATE waited. SMD-2091: registry lookups bounded apart from the
tools' pool — measure first. SMD-2106: a refused notification gets 202 or a
4xx, not a 200 with a JSON-RPC error body. SMD-2063 (statement-mode poolers)
no longer carries this lookup.
