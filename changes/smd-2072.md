## Changelog

The agent-registry lookup no longer waits on a lock without limit: on the SQL store each of `resolve_agent`'s lock waits is capped at 250 ms (a ceiling — a stricter setting is kept), so while a migration or an open transaction holds `ob1_agent_keys` a request no longer holds a pool connection until the lock clears. A key the lookup could not confirm is refused with a retry (JSON-RPC error `-32003`; `/health` answers `ok`) rather than served, since the registry could still say revoked, and a revocation the server has already read stands through any failure until the registry answers otherwise (SMD-2072).

## FORK

The registry lookup's lock waits are capped, a key the capped lookup cannot confirm is refused with a retry, and a revocation the server has read stands through any failure — a lock on `ob1_agent_keys` no longer empties the pool, and neither a lock nor an outage lifts a revocation (SMD-2072)

**What changed.** `server-portable/store-sql.ts`'s `resolveAgent` is one
statement: a materialised CTE sets `lock_timeout` to
`RESOLVE_LOCK_TIMEOUT_MS` (250 ms, `agents.ts`) as a ceiling — 0 or a looser
setting lowered, a stricter one kept, local to the statement's implicit
transaction — and `resolve_agent` (volatile, so evaluated per row of it) runs
from it; `lock_timeout` is read as each wait begins. No `BEGIN`, so a
statement-mode pooler still passes the lookup. `AgentResolver` answers a
failed lookup in three ways: a key whose revocation this process has read
stays `revoked` whatever the failure, until the registry answers that it is
not; a timeout on a lock — SQLSTATE 55P03, 57014 or 40P01 on `errno` — is the
new `busy` outcome, not cached; any other failure (no connection, no
`resolve_agent`) is served by name, as before. The MCP route refuses `busy`
with JSON-RPC error `-32003`, "Temporarily unavailable: the agent registry is
busy and could not confirm this key. Retry in a few seconds."; `/health`
answers it `ok`. The PostgREST store (Workers) sets no cap but now copies
PostgREST's SQLSTATE onto `errno`, so a role's `statement_timeout` there is
`busy` too. Warn-once dedupes on the key and its outcome, so a change of
outcome is logged.

**Why.** SMD-2041's third run-it review held a key's row and watched ten keyed
`/health` probes empty the pool of 10, every tool call timing out at 8 s. Its
fourth pass left one lookup per key in flight, so K distinct cold keys held K
connections for as long as the lock lasted. Capping the wait alone opened a
worse hole, which this change's first draft shipped and review pass 1 found
three ways: the header's case for serving by name — "with the registry
unreachable, every tool is unreachable too" — is false when only
`ob1_agent_keys` is locked. A revoked key (still in `MCP_ACCESS_KEYS`, refused
only by the registry) that this process had not seen captured a thought under
the lock, and one it had answered ok before the revocation kept its agent id
past the cache TTL. Before the cap both waited out the lock and were refused.
`busy` is that outcome without the wait. Keeping an ok answer was dropped: a
lookup runs only once a key's cached ok has expired, so it is at least a TTL
old, the revocation delay the operator accepted.

**Held.** test-agents [16]: an ok-answered key and a never-seen one are `busy`
on 55P03, 57014 and 40P01; a lost connection is served by name; a revocation
stands through a lock, a lost connection and a missing `resolve_agent`, by
digest, and the registry's next ok answer clears it; one warning per key and
outcome (busy → unreachable → revoked → busy); a kept revocation is cached for
the failure TTL and `busy` not at all (a fake clock). test-store-sql [15]:
55P03 at the cap (253 ms), a connection's stricter 80 ms kept (83 ms), the
connection's `lock_timeout` its own after each lookup. test-store-postgrest
[15]: PostgREST's 57014 arrives as `errno`. test-e2e-sql [14], real server:
with both registry tables locked, the revoked key `ok` at `/health` in 252 ms
(not the 2.5 s deadline) and refused as revoked at the MCP route, the other
key `ok` and asked to retry with `-32003`, ten probes one lookup at a time,
none left waiting; with `ob1_agent_keys` locked, twelve cold keys — the pool
pinned at 10 — each asked to retry (slowest 510 ms), none captured, including
one revoked through the registry before the server saw it, which is refused
as revoked once the lock clears, while a cold key then captures under its
registered id; with the keys' rows held FOR UPDATE, the revoked key refused
as revoked in 2 ms and a good key busy at the cap (256 ms). Thirteen
mutants, thirteen killed, each e2e case under a guard of its own so none
hangs: the cap dropped, the ceiling set non-local, a timeout served by name
(e2e and unit), the revocation not kept, kept on a timeout only, `busy`
cached, 40P01 not busy, `/health` showing a busy key the record, the
revocation not cleared by an ok answer, PostgREST's SQLSTATE dropped, the
warning deduped by key alone, the MCP route serving a busy key.

**Not taken.** The caps as a `SET` clause on the function (a migration): it
overrides a stricter caller, and `db/consolidate.ts` and
`db/extract-entities.ts` — batch runs that should wait out a migration —
would fail on its lock. A statement cap: a lookup's waits are its lock waits,
each capped. An `unresolved: "stale"` marker: no ok answer is kept.

**Left as it is.** Every write reads a writer's kind from `ob1_agents` (046's
audit trigger), so a DDL lock on `ob1_agents` still stalls captures, as a
lock on `thoughts` does. More cold keys than the pool holds still queue for
it, in rounds of about the cap. Writing `last_used_at` only when it is stale
would let a known key's lookup take no row lock at all; it is a change to
`resolve_agent` (SMD-2090).

**Follow-ups.** SMD-2090: `resolve_agent` writes `last_used_at` only when it
is stale or the scope changed, so a known key's lookup takes no row lock.
SMD-2091: registry lookups bounded apart from the tools' pool — measure
first how many cold keys at the 250 ms cap delay a cached key's call. SMD-2063
(statement-mode poolers) no longer carries this lookup: it is one statement.

**Upstream status:** not sent — the fork dropped parity (SMD-1924).
