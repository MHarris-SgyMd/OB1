## Changelog

The agent-registry lookup no longer waits on a lock without limit: on the SQL store `resolve_agent` runs in a transaction of its own whose statement is capped at 2 s and whose lock wait at 1 s (as ceilings — a stricter role setting is kept), so while a migration or an open transaction holds the registry, a cold key's request is served as when the database cannot be reached instead of holding a pool connection until the lock clears; a key the server already had an answer for keeps it while the lookup times out — its agent id, or its revocation (SMD-2072).

## FORK

The registry lookup's lock wait is capped, and a timed-out lookup keeps the registry's last answer for the key, so a lock can neither empty the pool nor lift a revocation (SMD-2072)

**What changed.** `server-portable/store-sql.ts`'s `resolveAgent` runs
`resolve_agent` inside `sql.begin`, after `setTimeoutCeilings(tx, 2000, 1000)`
— the ceiling statement `readDatabaseFacts` used, moved out of it into an
exported helper in `brain-info.ts` so the two share one rule: 0 or a looser
setting is lowered to the cap, a stricter one kept, local to the transaction.
The caps are `RESOLVE_STATEMENT_TIMEOUT_MS` and `RESOLVE_LOCK_TIMEOUT_MS` in
`agents.ts`. A timeout raises into `AgentResolver`'s existing catch — the
"registry cannot answer, serve by name, warn once" path. `AgentResolver` now
also keeps the registry's last answer per digest (`lastAnswer`, beside the
cache and independent of its TTL, 0 included): when a lookup fails with
SQLSTATE 55P03 or 57014 (`errno` on Bun's error), a key with a last answer
gets that answer — its agent id, or `revoked` — and one without is served by
name. Every other failure (no connection, `resolve_agent` missing) is served
by name as before, whatever came earlier. The warning names the answer kept.
`/health`'s comment and the README's `/health` paragraph say what a locked
registry now answers.

**Why.** SMD-2041's third run-it review held a key's row and watched ten keyed
`/health` probes empty the pool of 10, every tool call timing out at 8 s while
`/health` said `ok`. Its fourth pass made concurrent requests of one key share
one lookup, which left K distinct cold keys holding K connections for as long
as the lock lasted, through the MCP route and `/health` alike. Capping the
wait alone opens a hole the header's argument did not cover: "with the
registry unreachable, every tool is unreachable too" is false when only the
registry's tables are locked. A revoked key — still listed in
`MCP_ACCESS_KEYS`, refused only by the registry — would have been served by
name for as long as the lock lasted. So a timeout, the one failure that means
"there but busy", keeps the last answer. A row lock never reaches a revoked
key at all: `resolve_agent` reads `revoked_at` with a plain SELECT, before the
UPDATE that waits.

**Held.** test-agents [16]: a timed-out lookup keeps an agent id (by digest,
so across a rename), keeps a revocation lookup after lookup, serves a
never-answered key by name, gives way to serving by name on a lost
connection or a missing `resolve_agent` ([11b]'s database at 009 — the first
draft kept the old id there, and that suite caught it), treats 57014 as 55P03
does, and warns once per failure run. test-e2e-sql [14] against real Postgres:
with `ob1_agents` and `ob1_agent_keys` locked ACCESS EXCLUSIVE, the revoked key
is still refused at the MCP route and shown `ok` at `/health` — in 1005 ms
rather than at the 2.5 s deadline — and the good key gets the record; ten probes of one key
share one waiting lookup and none waits after. With `ob1_agent_keys` locked,
twelve cold write keys — more than the pool's ten connections — each capture
(slowest 2.0 s), each attributed by name with no agent id, none left waiting,
and a cold key registers once the lock clears. With the keys' rows held FOR
UPDATE, the revoked key is refused in 3 ms and the good key waits out the 1 s
cap and keeps its id. Seven mutants, seven killed: the caps dropped (nine
e2e assertions fail, each in its own guard — none hangs), the last answer
dropped (e2e: the revoked key is served during the lock; unit: five), kept on
every failure ([11b] and two), a revocation not kept, 57014 not read as a
timeout, and the warning's dedupe cleared by a kept answer.

**Not taken.** Writing `last_used_at` only when stale (the ticket's third
bullet): the cache already bounds a key to one lookup per TTL (60 s) per
process, so a once-a-minute rule would skip almost no writes, and the UPDATE
also records the key's presented scope. The caps as a `SET` clause on the
function (a migration): it would reach Workers too, but it overrides a
stricter caller, cannot cap the statement (statement_timeout is armed before
the function is entered), and would make `db/consolidate.ts` and
`db/extract-entities.ts` — batch runs that resolve once and should wait —
fail on a migration's lock.

**Left as it is.** The PostgREST store (Workers) sets no caps: its lookup runs
under the role PostgREST connects as, in PostgREST's own pool. Every write
reads a writer's kind from `ob1_agents` (046's audit trigger), so a DDL lock on
`ob1_agents` itself still stalls captures, as a lock on `thoughts` does; the
write path has no lock cap, and a migration's locks are expected to be brief.
The lookup now needs a transaction, where it was one statement: a pooler in
statement mode (PgBouncer `pool_mode = statement`), which refuses `BEGIN`,
would fail every lookup, so every key is served by name there and a revocation
is not enforced — preflight's facts read already warns on such a pooler, and
the server starts. Unmeasured against a real one; SMD-2063 carries it.
