## Changelog

`db/graph-centrality.ts` ranks the entity graph by attention — top entities by mentions and degree, the thoughts that build the graph, and around one subject its neighbours by co-mentions plus edge support with the thoughts that tie them — resolving the subject by 016's own rule, printing the graph's caveats with the run's numbers, and offering `--no-edges` as the drop-the-graph control; no MCP tool yet, by decision (SMD-1938).

## FORK

The entity graph answers "what is central about X" from one command — `db/graph-centrality.ts`, with the subject resolved by 016's rule, the caveats printed with the run's numbers and edges-off as the control; promotion to a core MCP tool decided against for now (SMD-1938)

**What changed.** `db/graph-centrality.ts` is a read-only Bun script over
migration 016's three tables. With no subject it prints the whole graph: the
top entities by **mentions** (distinct thoughts mentioning one), the hubs by
**degree** (distinct entities an edge joins one to, either end) with
**support** (distinct thoughts evidencing any edge touching it), and the top
thoughts by in-scope entities mentioned plus in-scope edges evidenced. With a
subject it resolves it one rung at a time — exact `normalized_name` through
`normalize_entity_name`, then a `merged_from` name or an alias, then the five
nearest by trigram similarity at pg_trgm's default threshold, named as guesses,
a uuid taken as an id — and ranks the neighbourhood by **co_mentions** plus
**support** (thoughts evidencing an edge between the two, any relation, either
direction, the per-relation counts beside it), then the thoughts mentioning the
subject by ranked neighbours mentioned plus subject edges evidenced. Entity
ties break on mentions, normalised name, type — never a uuid or a timestamp;
thought ties on the thought id, stable on one database, no recency. `--no-edges`
drops every edge term and column, so two runs say what the edges add over
co-occurrence. `--types` and the numeric-name rule define which entities exist
for the run — the scope is the graph, an entity outside it is in no list and no
count — with the subject the one exception. `--json` emits the same report as
data. The SQL is built by exported functions over a `Runner`, so the CLI's text
is the text `db/test-schema.ts` [43] runs under PGlite.

**Why.** The graph shipped with SMD-947 and nothing read it for importance;
"what matters most about X" was answered twice in one session by hand-written
SQL through `podman exec psql`. Run on the dogfood brain (296 thoughts, 262
extracted, 1,278 entities, 2,375 edges) the whole-graph report reproduces the
hand analysis captured there: Open Brain 179 mentions / degree 231, Linear 122 /
101, the PostgreSQL 78 / Postgres 19 split, `uses` the dominant relation,
support at most 5. The caveats are printed rather than assumed because the
graph's defects are measured: 2,375 of 2,375 edges at confidence 1.00
(SMD-1925), 28 entities named only by digits (SMD-1935).

**Held.** `test-schema.ts` [43], 104 assertions over a graph whose every count is
known by construction: a subject, three neighbours that separate under each
ranking (PostgreSQL 3+3, Anita 2+2, Bun 3+0), a numeric-named `person` with an
edge to the subject, a merged entity. The counts as defined, with the numeric
entity out of degree, support and every list by default and in all of them
when kept; the four rungs; the neighbourhood's order with edges on
(PostgreSQL, Anita, Bun) differing from the order without (Bun, PostgreSQL,
Anita) at every position, so a build ranking on co-mentions and calling it the
graph fails; two runs byte-identical; the rendered caveats carrying the run's
counts; the flags refused as documented. Mutants, run against the suite: the
support term dropped from the neighbourhood's ORDER BY fails 5, the numeric
predicate dropped from the scope fails 13, the far-end scope dropped from the
subject-edge count fails 1 (t5's edge to 021 counted).

The third pass's top findings were seams between rules the first two passes
added — the numeric `excluded` probe, the ladder's order and the subject
grouping read each other — which is the stop signal, with the one more look
the house rule asks for when new rules read each other: a cold read of the
third pass's own additions (the probe before the guesses, the grouping, the
catch, the marked cut) against every rung × scope × subject shape found no
further seam, and the live brain agrees ("11434" stops at the flag, a
connection refused exits 2, the tool-scope caveat counts 10 not 28).

**Not taken.** *Guarding `similarity()` against pg_trgm off the search path*
(a reviewer's finding): 011's trigram index already needs `gin_trgm_ops` to
resolve unqualified, so a brain where the fuzzy rung would raise is one 011
did not apply to; nothing new is exposed. *Rewriting `topThoughts` as one
GROUP BY*: its three index probes per extracted thought are the shape of a
diagnostic over thousands of rows, not millions; revisit if the query ever
serves a tool. *Refusing digits-only names at `record_thought_entities`*: the
right depth for SMD-1935's noise, and that ticket's to take; a read-side rule
here is what a reader can do without a migration. *A core MCP tool now.* The ticket's second item asks for the
decision; it is no, for three reasons that are each measurable and may change.
The graph is empty until `db/extract-entities.ts` has run, so on most brains
the tool would answer nothing and a client could not tell "no extraction" from
"nothing central". Its numbers are attention over a graph with two measured
defects (SMD-1925, SMD-1935) and a synonym split (SMD-1913); the caveats are a
paragraph, and a tool result that needs a paragraph of caveats is a diagnostic,
not a memory read. And the dev-facing script already answers the repeated
question. Promote when a client asks the question twice — the signal that
filed this ticket — once the extractor emits a weight (SMD-1925) or the
resolver merges synonyms (SMD-1913); the SQL is the exported functions, the
manifest entry is `server-portable/tools.ts`, and the render is one function.
*A weighted centrality* (PageRank, eigenvector): with support at most 5 and
every confidence 1.00 there is nothing to weight by that a count does not
already say. *Ticket status in the ranking*: the graph does not hold it; the
output says so.
