## Changelog

The MCP route no longer answers a refused JSON-RPC **notification** with an HTTP 200 error envelope — a shape the MCP TS SDK silently drops, so `notifications/initialized` and `notifications/cancelled` looked delivered when they were refused. A notification-only body now gets no JSON-RPC body: `202` for a refusal that cannot change on retry (no, wrong or revoked key), `503` with `Retry-After` for one that can (the agent registry busy). A request still gets its 200 envelope, and the busy request now carries `Retry-After` too (SMD-2106).

## FORK

The MCP route answers a refused notification per spec: 202/503 with no body, not a dropped 200 envelope (SMD-2106)

**What changed.** `server-portable/index.ts`: the two pre-transport auth
refusals (no/wrong key at the `!principal` site; revoked/busy at the
`resolve()` site) now branch on whether the body expects a reply. A new
`refusalTarget(bodyText)` returns `expectsReply` false only when the body is
positively notification-only — every message a plain object with a string
`method` and no `id` member (the `id`'s presence, not its value, marks a
request: `id: null` is still a request). A request, a response, a malformed
body, a mixed or empty batch all keep the 200 envelope, so a reply is suppressed
only where JSON-RPC forbids one. `notificationRefusedResponse({ retryAfter? })`
returns a bodyless `202` (no retry) or `503` + `Retry-After` (busy);
`unauthorizedResponse` gains a `retryAfter` option so the busy REQUEST envelope
carries the header too. `RETRY_AFTER_SECONDS = 2`.

**Why.** JSON-RPC 2.0 says the server MUST NOT reply to a notification; MCP
streamable HTTP says a notification the server accepts is `202` with no body, one
it cannot accept an HTTP error. The route answered `200` with a
`{error, id: null}` envelope for every refusal, inherited from the `-32001`
path. The MCP TS SDK (1.30, `client/streamableHttp.js`) cancels the body of a
`200` that held no request, so during a registry lock `notifications/initialized`
and `notifications/cancelled` were dropped and the client believed them
delivered (SMD-2072 review pass 2 measured a 252 ms `200` carrying
`{"error":{"code":-32003},"id":null}`). Harmless on this sessionless server
today, but wrong on the wire.

**Held.** `bun server-portable/test-server.ts`, 292 assertions (from 285): a
refused notification (missing key, wrong key), an all-notifications batch, and a
mixed batch and an `id: null` request are each answered correctly — 202 no body
for the notifications, the 200 envelope for anything holding a request.
`bun server-portable/test-e2e-sql.ts` against real Postgres, 229 assertions (from
226): during a registry lock a revoked key's notification is `202` no body, a
busy key's is `503` no body with `Retry-After`, and the busy request keeps its
200 envelope now carrying `Retry-After`. Server typecheck clean.

## Not taken

A distinct HTTP status for a malformed or mixed-batch refusal: the route keeps
the 200 envelope for anything not positively a notification, so a request is
never answered with a bodyless status by mistake — the conservative choice, and
the transport still 400s a malformed body it is handed. `Retry-After` as an
HTTP-date rather than delta-seconds: the value is advisory and "a few seconds"
is what BUSY_MESSAGE promises.
