## Changelog

Both servers write one JSON line per request, on every route but the keyless liveness probe's — the method, the tool, the key's name, the status, how a tool call ended, an error's code, the time and the bytes — from an allow-list that never lets the URL, a key, a tool's arguments or a thought's text into it; each request and each tool call is also an OpenTelemetry span with those values alone, each request a point on a request-duration histogram and a log record of the line's fields, each provider call and store operation a span and a point of its own and a job's body a trace of its own, sent only where an operator names a collector (`OTEL_EXPORTER_OTLP_ENDPOINT`, or a signal's own variable). The image's health check is a keyless `GET /health`, so it no longer writes a refusal every 30 seconds, and every service in `deploy/`'s compose files has a bounded log: 10 MB × 3 files on Docker, one file truncated at 10 MB on Podman (SMD-1849).

## FORK

Each request to either server but the keyless liveness probe leaves one JSON line, from an allow-list, and a span, a metric point and a log record where a collector is named, and no container's log grows without bound (SMD-1849)

**What changed.**
- **`server-portable/telemetry.ts`** (new): `requestLine(record)` writes `{ts, door, method, route, rpc, tool, agent, status, outcome, code, ms, bytes}` in that order, each value held to its rule as the line is written:
  - a method, a JSON-RPC method, a tool and an outcome to their known sets (MCP's client methods; the manifest's tools), anything else `?` (`other` for a JSON-RPC method);
  - a route template and a code to their spellings;
  - the agent's name to `labelPart`'s printable ASCII of 64 characters;
  - numbers to non-negative integers.
  A field the record does not declare is not written. `logRequest` sends the line to stdout; `useRequestLog` swaps the sink for a suite.
- **The MCP server** (`index.ts`): one line per request on its MCP endpoint, written once, when the request ends:
  - at the stream's end, with the bytes it carried (`sse.ts`'s `withSseKeepalive` now counts them, its own keepalive frames apart, and hands them to `onEnd`);
  - at a refusal at the key (`UNAUTHORIZED`, `REVOKED`, `BUSY`, `AUTH_UNREACHABLE`);
  - when the client leaves (`abandoned`), at the stop (`cut`), at the keepalive's ceiling (`stalled`, and the call's own end then writes nothing), or at a throw or no answer (`error`, 500).

  `registerOp` counts the calls that end and keeps the worst (`CallRecord`, `worseOutcome`): `ok`, `refused` (a refusal as a value) or `error` (the fault), with the code its reply's `structuredContent` carries. A call asked for that never ended is `unrun`. `partsOf` reads the method and, for a tool call alone, the tool, from the body (`parsedBody`); the label in words is `sse.ts`'s `requestLabel`, shared with the vendored servers (SMD-2001). A body of several messages is `batch`, naming no tool, with its worst call's outcome. The agent is named once the key authenticates, before the registry answers. `requestLabel` says what it said before. `useKeepaliveTiming` sets the keepalive's interval and ceiling for a suite.
  The MCP server's other routes (its keyed `/health`, the worker mirrors, `/jobs/`, 405s, `/.well-known/`) wrote no line in PR 1; PR 2a gives each one (below).
- **The REST core** (`rest/app.ts`): its `api <METHOD> <route> <status> <ms>ms` line is now the same JSON record. It adds the operation the route runs, the name of the key that authenticated, and a 4xx or 5xx answer's code, read from a copy of the answer's JSON (`errorCode`). It is written when the answer is sent (PR 2a times a job stream to its end). The liveness probe's 200 is still not logged.
- **One outcome on every line.** `telemetry.ts`'s `outcomeOf` gives any line that is not a tool call its answer's outcome: `error` for a fault (a 5xx `FAILED` or `STORE_UNAVAILABLE`, or one with no code), `refused` for any other 4xx or 5xx, else `ok`. That covers an MCP `initialize` or `tools/list` and every REST request. A 503 `BUSY` is then `refused` on both doors, as the MCP server always said it. A REST client gone before its answer, which includes a body read it cut off (otherwise onError's 500 `FAILED`), is `abandoned` with no code, measured against `bun api.ts`. A tool's code is read from an error reply alone.
- **The image's `HEALTHCHECK`** is a keyless `GET /health`, not a POST to the MCP endpoint, which the new line would have written as a refusal every 30 seconds. The REST core's services keep their own check, the same GET, for an image built before this.
- **Log rotation.** `deploy/compose.yaml`'s `x-logging` is the json-file driver at 10 MB × 3 files, and every service there and in `compose.tiers.yaml` names it. It replaces an engine-wide default driver, which the README says, with how to keep one. Check 29 of `scripts/check-fork-consistency.ts` refuses a compose.yaml service without it (eight probes). Check 27 holds the tiers file to compose.yaml, so a tier service without it fails there; its probe "the proxy waiting on stable" is re-anchored past the new line. Check 25 admits `telemetry.ts` in `index.ts` and `rest/app.ts`: an allow-list and a sink, no store and no provider.
- **`deploy/README.md`**: "What the servers log", with which requests write a line, the keys and what each holds, what a line never holds, and the bound. Its REST core paragraph and `server-portable/README.md`'s two passages on the log say the JSON line.

**Why.** After a capture and a search, the server's log still ended at `Started server`: no request line, no status, no duration, so the only per-tool numbers the fork had came from benches on synthetic corpora. The brain is personal data and a connector carries its key in `?key=`, so the line is an allow-list rather than a scrubbed request: what is not named cannot reach it. Search text already has a home behind its own switch, the query log (034), and gets no second copy here. The proxy's access log (SMD-1846) already has the path and the status; this line adds what only the server knows — the tool, whose key, and how the call ended inside a 200. Docker's default json-file log is one file that grows until the disk is full, and every request now writes to it.

**Measured.** On podman 6.0.2 (podman machine, macOS), `--log-driver json-file --log-opt max-size=2k --log-opt max-file=2` is accepted and enforced as its k8s-file driver: 400 lines written, 10 kept. It keeps one file, truncated at the bound, and `max-file` has no effect there.

**PR 2a: one record per request.** `telemetry.ts`'s `RequestTrace` is made by each server's first middleware for every request it is handed but the probe (notFound makes it for a path that middleware never sees), filled in by the handler that serves it, and ended exactly once:
- **Every route of both servers has a line**: the MCP server's keyed `/health`, `/worker-status`, worker actions and `/jobs/` mirrors (each with its route as a template, its tool and its key's name), its 405s, preflights and `/.well-known/` answers, beside the MCP endpoint, which now ends the record the middleware made instead of building its own. A mirror's 200 that shows a caller nothing is `refused`: with no key named for a wrong or out-of-scope key, and by the key's name where the registry did not clear it, REVOKED or BUSY where it said which. A path the `*` middleware never matches (an encoded line break) gets its line from notFound. The liveness probe alone gets no record: on the MCP server a GET or HEAD at a health path that presents no key (a wrong or out-of-scope key there is a logged `refused`), on the REST core a GET or HEAD of `/health` — decided as it arrives, so PR 2b's span never starts for it.
- **A stream is timed to its end**: both servers' job streams write their line when the stream ends (`ok` with its bytes, `abandoned`, `stalled`), not when it opens, through `endsWithStream`, which also ends the record `abandoned` when the client is gone before the route listens or lets go of the body with no abort — `sse.ts`'s new `onCancel` (measured on Bun 1.4.0; other runtimes unmeasured), which the MCP endpoint's stream takes too (the shared copies synced).
- **The stop writes what it cuts**: `cutOpenRequests` ends every record still open as `cut` from the stop's `onCut` (`abandoned` for one whose client already left), keeping the status its answer had, before the process exits (check 25 admits it among `api.ts`'s imports); before, a REST request the stop cut off left no line.
- The REST core's request-keyed map and `errorCode` move into the record and `telemetry.ts`; the REST core makes the record before it seeds the environment, so an init that throws is a line (`FAILED`, as its answer says); each REST operation route, whoami and the job stream included, names its route template (and the stream its operation) as it starts, so a refusal or a `cut` line carries it.

**PR 2b: traces.** Each request's record is an OpenTelemetry span (`@opentelemetry/api`), and each tool call a span under it:
- **The request's span** starts with the record — its own trace, an incoming W3C `traceparent` a link on it (continued only with `OB1_OTEL_TRUST_TRACEPARENT=1`, for a proxy that sets it — declared in `root.ts`'s `Env`, and held by check 14's `NOT_FORWARDED` out of every deploy/ compose file's `server` service; nothing of a `tracestate`) — and ends in its one `end()`: named for its MCP method (`tools/call <tool>`) or `<METHOD> <route>`, it holds the line's checked values (`checked`, split out of `requestLine`) under the HTTP, MCP and `ob1.*` names — no status for an answer the client never received (`abandoned`, `cut`), ERROR for a 5xx it answered or an `error`, `stalled` or `cut` request, `error.type` its code, else its outcome. The line gains `trace`: the span's trace id, or with no collector a trusted incoming `traceparent`'s. `RequestTrace` keeps its name: it is the request's trace now, and `telemetry.ts` reaches OpenTelemetry's `trace` only as `otel.trace`.
- **A tool call's span** (`withToolSpan`: `execute_tool <tool>`, the gen_ai names, its outcome and code) wraps the MCP server's `registerOp` and its plugin tools and the REST core's operation and plugin routes; each middleware runs its handlers under the request's span (`run`). The MCP server's plugin tools now tell the record how they ended: their line read `unrun`.
- **The SDK** (`otel-setup.ts`: OTLP/HTTP JSON, batched; the AsyncLocalStorage context manager; the W3C propagator; the SDK's resource with `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES`) is loaded by `startTelemetry` once, only on Bun, only for an http(s) endpoint and with neither `OTEL_SDK_DISABLED` nor `OTEL_TRACES_EXPORTER=none`; it says where spans go by origin alone, spans not sent — a failed export, the queue's drops — by count, origin and kind (`watchExporter`, `failureKind`; at the stop, what is unsaid, the queue's drops counted as queued less handed, `countingProcessor`), and each server's stop flushes what is batched and waits for what is on its way beside closing its pool, under its bound, said in a clause of its own (`shutdown.ts`'s `flush`; check 25 admits both names in `api.ts`). The stop's cut ends a running tool call's span with its request's. Six exact pins, all Apache-2.0; the image's production install grows about 20 MB (28 MB on disk). `wrangler.toml` aliases `otel-setup.ts` to `shims/otel-unavailable.ts`, so the Worker bundles the API alone, as a new CI step holds; CI's two line regexes take a closing `trace`.
- Measured: with no provider a request's record and spans cost about 0.2 µs more than before; unaliased, the Worker bundled the SDK (about +330 KB, `async_hooks` and `events` at start-up) and CI's build passed. A collector down, hung or failing adds no latency to a request: over 200 mixed requests, p50 1.8–2.4 ms against 2.0 ms with none.

**PR 2c: metrics and the log record.**
- **One setup for three signals** (`otel-setup.ts`'s `setUpTelemetry`, was `setUpTracing`). `telemetry.ts`'s `planTelemetry` gives each signal its URL — its own endpoint variable, else `OTEL_EXPORTER_OTLP_ENDPOINT` with its path — and says by the variable's name each that goes nowhere (`OTEL_SDK_DISABLED`, its exporter's `none`, no http(s) URL, a query string on the shared endpoint) and each setting it does not read (another exporter, another protocol); `startTelemetry` hands the setup those URLs, so a suite runs the SDK's success path in-process. `watchExporter` takes any signal, by its noun and its count (spans, metric exports, log records); the log batch's drops are read from its own meter as it drops them (`logDrops`); each batch's sizes, delay and timeout, and the metric reader's interval and timeout, are read and held here (`batchOptions`, `metricTimes`): the SDK reads none for log records and metrics, and the span batch's timers unbounded. One flush covers the three (`flushesResult`), and the stop's clause says `telemetry`.
- **The request-duration histogram** `http.server.request.duration`, in seconds on bounds to 600 s, recorded in the record's `end()` through the API and labelled with nine of the span's attributes (`labelsOf`), each from a set the server's own words bound: no key's name, an `error.type` that is a fault's code or else the outcome, never a refusal's code, and no tool for a request refused at its key on either door (`refusedAtKey`: the MCP route's, a mirror's, the REST core's `refuse` of a key).
- **The log record**, one per request, emitted in `end()` whatever the line's sink (`Telemetry.emit`: the Worker's bundle keeps the API alone, so `telemetry.ts` imports no logs API): the line's checked fields as its body, `ob1.request`, INFO, WARN or ERROR, under its span's context. An emit that throws loses the record, not the request.
- **A fault's kind and code** (`faultOf`) as an `exception` event — `exception.type`, `ob1.fault.code`, never the message — on a tool call's span for what it throws (`ToolSpan.fault`), and on the request's for a webhook's fault, a worker mirror's and onError's (`RequestTrace.fault`). The webhook's message stays on stderr.
- **The stop ends every record still open before its flush** (`shutdown.ts`'s `endOpen`, on a drained stop too): on Bun 1.4.3, which counts a request done once its client has left, a mirror whose client left while it waited on the registry had no line and no telemetry at all (since PR 2a); the image's and CI's 1.4.0 still counts it, and drains it.
- **Refusals set their code as they answer**: the REST core's `answerError` (every `refuse`, a refusal as a value, a fault, the hook route's answers, onError) and a hook handler's own refusal read from its checked JSON; the MCP server's worker actions. `errorCode`, and its clone of every error answer, is gone.
- Five more exact pins, Apache-2.0: `sdk-logs`, `api-logs` and `sdk-metrics`, already in the tree under the trace exporter, and the logs and metrics OTLP exporters, which add 0.7 MB on disk. With no collector a request's record, span and point cost about 0.27 µs, measured.

**PR 2d: child spans.**
- **`spans.ts`** (new, importing nothing): `withSpan`, `withProviderSpan`, `withStoreSpan`, `faultOf` (from `telemetry.ts`) and `useTracing`. `embed.ts` and `store.ts` are imported by `db/`'s workers and `evals/`, which install none of `server-portable/`'s packages, so a span there is nothing until `telemetry.ts` installs `tracing.ts`'s, as a server, or preflight under `--deep`, loads it. `tracing.ts` (new) makes them on the OpenTelemetry API: it keeps the open ones for the stop's cut (once the tool calls' set alone), the histograms by name and `markFault`, and its every SDK call is guarded, as `RequestTrace`'s now are. `withToolSpan` is built on it.
- **A provider call** past the egress gate (`providerCall`) is a client span, `embeddings <model>` or `chat <model>` under the GenAI conventions (model, host and port, token counts held to safe integers; `error.type` the status — 300 to 599, else `_OTHER` — `timeout`, `invalid_body` or the runtime's code), and a point on `gen_ai.client.operation.duration`: the ticket's `ob1.provider.duration` under the conventions' name, its kind the operation.
- **A store operation**: `createStore`'s store is wrapped (`tracedStore`), each operation the core calls a client span named for it — `db.operation.name`, `ob1.store`, a SQLSTATE as `error.type` and `db.response.status_code` — and a point on `db.client.operation.duration`, on finer bounds than the conventions' and on to 60 s; `STORE_OPERATIONS` names every member, so a new one fails the typecheck until decided. One span per operation, not per query: no query's text is read, and PR 3's `pg_stat_statements` times each SQL function. A plugin's transaction is an internal span with `ob1.plugin` and no point: its time is the plugin's code and SQL.
- **A job's body** (`startJob`) starts a trace of its own, `job <kind>`, linked to the tool call that started it; its calls are its children, and a job its timer fails ends it then, `JOB_TIMEOUT`; each is a point on `ob1.job.duration` by its kind and how it failed. A webhook's deferred work (`runHook`'s `ctx.defer`, run after the answer) is a trace of its own the same way, `defer <plugin>`; a failed delivery's discard, run before its 500, stays its request's child.
- **`preflight --deep`** makes each provider probe a span and a point, marked `ob1.probe`, sends them before its report as `open-brain-preflight` under one 5 s bound, and says how in a `telemetry` row: `ok`, a warning for what the server would share (an export not sent, an endpoint that is no URL, an SDK that would not start), a skip for what goes nowhere on purpose, or when no probe ran, counted as each runs (`telemetry.ts`'s `telemetryRow`). A plain preflight, each container start's, loads no telemetry. The pool's connections in use (the ticket's `ob1.pg.pool.in_use`) are not counted: Bun's client does not say them, and PR 3's Postgres exporter reads them from the database.
- **`service.instance.id`**, a UUID per start, on each process's resource (`otel-setup.ts`), so two doors or two tiers under one name are two series; each start so begins new series, and `OTEL_RESOURCE_ATTRIBUTES` pins one.
- **Measured:** with no collector a store operation costs about 0.5 µs more and a provider call under 1 µs, a request with three such calls about 3 µs; with a healthy collector at 2,000 requests a second, about 40 µs of CPU a request, memory flat, and a collector down or hung adds no latency.

**Not here.** SMD-2902: the stop gives the three flushes at most a second, while the exporters retry for ten, and a collector that trickles its answer or rejects part of an export is not counted. SMD-2907: a job's timeout names `OB1_JOB_MAX_MS`, which nothing reads, so a real server's job runs to the 30-minute default. SMD-2908: a provider's redirect carries the text past the egress gate (from before this PR). SMD-2909: the `telemetry` row reads its verdict from other modules' sentences. SMD-2910: `db/`'s workers make no spans or points.

PR 3 brings the `observability` profile (LGTM, `pg_stat_statements` and its exporter, Grafana at `/grafana`, the dashboard), and with it the tier from the container's label. Uptime Kuma is left out: Grafana's alerting covers a `/health` probe.
