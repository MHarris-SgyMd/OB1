## Changelog

A user and password in a provider, jev or Telegram base URL (`https://user:pass@host/v1`) are that endpoint's credential, sent as `Authorization: Basic` on every Bun unless a key is set, whose Bearer takes their place; preflight counts them as a credential, warns when a key overrides them, and its `--deep` probes send them (SMD-2885).

## FORK

A base URL's user and password are its endpoint's Basic credential, on every Bun — never left in the URL for fetch to decide (SMD-2885)

**What changed.**
- `server-portable/embed.ts`: `providerEndpoint` takes userinfo out of the base (`splitUserinfo`: the URL parser's reading, percent-escapes decoded, the pair UTF-8, the base as written with the userinfo cut out where the parser reads that as the same URL, else rebuilt from the parse, so the host dialled is the one the parser read) and records `userinfo: true`. Its one header rule is now the key's `Bearer`, else the userinfo's `Basic`, else none. `base` carries no userinfo, so every request dials a clean URL and every message that prints a base (`ProviderError`, the workers' logs) prints none.
  - `shownBase(at)` prints a base for a row: `***@` where userinfo was, maskUrl's shape; a base the parser refuses keeps its userinfo (fetch refuses it too) and is masked as maskUrl masked it.
  - `resolveProviderEndpoints`: a chat base's own userinfo is its own credential, like `OB1_CHAT_API_KEY` — it stands alone rather than inheriting the embeddings key — unless it is the embeddings base's own: the same spelling in both knobs, or the chat base without the userinfo, is one endpoint and shares the key.
- jev (`OB1_JEV_BASE_URL`) goes through `providerEndpoint` already, with no key, so its userinfo is now always Basic. `db/weekly-digest.ts`'s `telegramEndpoint` is built by `providerEndpoint` too, and `deliverTelegram` sends its headers.
- `server-portable/preflight.ts`:
  - The credential row counts userinfo as the credential ("the user and password in OB1_LLM_BASE_URL, sent as Basic") instead of failing a hosted base with no key, and warns, naming the key that is set, when a key overrides it.
  - `--deep`'s embeddings and chat probes test a base with userinfo instead of skipping "no credential to test with", and a 401 names the credential that was sent (`rejectedRemedy`): the key, the base's user and password, or none — by the embeddings knobs for a chat endpoint that is the embeddings one. The jev row's 401 names its user and password, not its path.
  - The default reachability probe still sends no credential. Its comment said fetch never sends userinfo; it now says why the probe does not (the userinfo is out of the base).
  - Every row prints a base through `shownBase` and a host through `egress.ts`'s `hostOf`, whose fallback for a base the parser refuses now masks its userinfo (the gate's records read it too). Rows print `shownBase`; the unshared-key aside compares endpoints, not bases; a chat endpoint that is the embeddings one says so on its credential row instead of naming `OB1_CHAT_*` knobs that are not set.
- `recipes/session-capture-hook/session-capture.mjs`, which reads the same knobs for its opt-in model summary (or its own `model_url`) and runs alone, carries a copy of the split: `loadConfig` takes userinfo out of the model url into `modelBasic`, sent when no model key is. Which key goes with the url stays the hook's own pairing (SMD-2897).
- `SETUP.md`, `deploy/.env.example`, `server-portable/README.md` and the hook's README say the rule beside the key rule.

**Why.** Bun 1.4.3's fetch sends a URL's userinfo as Basic; 1.4.0, which CI and every image pin, dropped it silently, and a user-only URL (`http://user@host`) failed to resolve. Run locally under 1.4.3, test-preflight's "fetch sent no Authorization" assertion failed: the probe sent `Basic …`. The paths also disagreed with each other there: with a key set, the server sent Bearer while the probe sent the userinfo; a hosted base with userinfo and no key was authenticated by the server and failed by preflight's credential row. On a deployed brain (1.4.0) userinfo was never sent, so a Basic-auth front before a provider could not be used. The maintainer's choice: send it, on purpose. Done in the endpoint's own header, it is the same on 1.4.0 and 1.4.3: a probe found both versions keep an explicit Authorization header across a same-origin redirect and drop it across origins.

**Not taken.**
- Stripping userinfo and never sending it, or refusing it at start: offered; the maintainer chose to send it.
- Bumping CI's and the images' Bun pin: the contract no longer depends on it. The ticket's "every suite under the new version first" belongs to the bump.
- A base the URL parser refuses keeps its userinfo in `base`, so a `ProviderError` in the server's or a worker's log names it whole, as before this change: fetch refuses the URL before any request, and preflight, which says why on start, masks it — unless the password holds an unescaped `/`, which ends the authority for every mask, as for maskUrl's DATABASE_URL row before this change. Cutting it by regex was declined, since a cut can turn a refused URL into one that parses and dials elsewhere.
- The hook's key pairing: with the server's `OB1_CHAT_BASE_URL` it falls back to `OB1_LLM_API_KEY`, which SMD-1902's rule does not, and that key wins over a chat url's own user and password. The fallback predates this change, and copying the server's whole sharing rule into the hook is a second mechanism: SMD-2897.
- brain-compare, the n8n provisioner and the openclaw client also fetch an operator URL with no Authorization of their own; on 1.4.3 Bun sends their userinfo itself. None of them is a provider endpoint, and each sends its own key header.
