## Changelog

A capture-only key's pointers are no longer cleared above a supersedes link that moved while the clearing ran, and no longer missed above a link that moved onto a thought being taken (SMD-3046). Before, any write that took such a thought — another key re-capturing or editing its text, board-sync filing it, a page render — could race a link being moved and leave the wrong pointers lapsed or standing.

## FORK

The lapse locks its own tree: the walk records the links it went on through, the lapse trigger locks them FOR SHARE from the taken row up and reads each again before it clears above it, and a pointer's lapse locks its target's chain first (SMD-3046)

**What changed** (migration 101).
- **`ob1_lapse_tree(row, onto)`**: 097's walk, unchanged, also listing `{id, onto, "stays": true}` for each link it went on through (row `id`'s pointer names `onto`), after that row's clears and before anything above it; never the event's own row.
- **`ob1_lapse_walk(row, onto)`**: the tree's clears, in their order — byte for byte 097's `[{id, onto}]`, which `ob1_accept_lapses`, the listing and `consolidate --accept` read unchanged. Still one walk: the trigger reads the tree, the listing the walk derived from it.
- **`ob1_lapse_capture_pointers()`** keeps 097's gates and pointer, then:
  - locks the event's row (every write function holds it already; the order rests on it);
  - **moved in:** for a pointer onto a thought, locks that thought's chain (it and 1,000 below) FOR SHARE from its deepest row up, before the walk — a taking in flight below holds its row, so the pointer's lapse waits for it, and its walk, a statement of its own, then reads the row taken;
  - runs the tree;
  - **moved out:** before any clear, locks each clear's links — from its pointer's target down to the taken row (or to a row an earlier clear names, where the walk went on whatever that row's pointer, or to a link already held) — FOR SHARE from the lowest up, each where its pointer still names the row below, then that clear's own row by its id; a link moved since the walk is broken, and the clears above it are left. Every row the lapse waits on is waited on here, before any clear, holding nothing above it:
    - a clear projects its pointer and takes 068's node-state bucket locks, held to the commit, and a lapse that waited on a row while holding one deadlocked against a re-point out of the tree, which needs the same bucket when its own event projects (the race table's first live run: every taker, five of five);
    - a lapse that held a link and then waited on the cleared row above it crossed a delete of that row (its cascade needs the link) and a transaction that edited the row and then moved the link (review pass 2: every taker, where 097 deadlocked only an accept);
  - then 097's clears, unchanged, those whose links held.

**Why.** The lapse (097) reads the tree above a taken row in one snapshot, then locks and clears. 099 (SMD-3045) closed the window under an accept, which holds the review lock every pointer write waits on. Any other taking held none, and SMD-3045's Verify measured both races open: a link moved out between the walk and the clears still had the hook's pointer above it cleared, and a link moved in missed its own.

**Not writer-side.** A first attempt had the takers take the review lock before their row lock (review pass 1, never shipped). Pass 1 sank it twice:
- a page render already holds its row when it writes, so page writes deadlocked against a delete or a pointer write of the page — 154 of 400 races, none under 099;
- a capture's merge gaining an `issue` with no agent was a taker it had not listed.

Every taking passes through the lapse trigger, so the locks are taken there: no writer changes, no global lock.

**Lock order.** A taker holds its row FOR NO KEY UPDATE and no review lock; inside its lapse it locks only rows of its own tree, bottom-up — each clear's links FOR SHARE, then its row FOR NO KEY UPDATE — before any clear, and takes 068's buckets only in its clears, waiting on nothing after. A pointer writer holds the review lock and its row, and its lapse locks its target's chain FOR SHARE bottom-up. No cycle for: an unlink; delete's cascade (top-down path locks, or a cleared row locked after the links above it, deadlock here); an accept (onto a NULL pointer, in no tree); 092's capture check (bottom-up, waits at the taken row); two takers on one tree; a page render; a link moved in (a target the taker clears is reached only after the taker's row — top-down would deadlock); a transaction that edits a row the lapse clears and then moves a link under it.

**The named residual.** A pointer write whose new target's chain (to 1,000 rows) reaches the taken row, while the row it moves is one the taking will lock — a link of the tree or a row it clears, re-pointed onto the taken row, onto a row above it, or onto a row outside the tree whose chain runs through a cleared row the walk did not go on from. The writer's chain lock waits on the taker, the taker's lock on the writer's row; Postgres breaks it with 40P01, one side rolls back whole. It is not narrow: an overlap of such a write with a taking nearly always meets it (review pass 2: 395 of 400 overlapping races, the pointer writer the usual victim), and nothing in the server retries it — the caller gets the error, and a retry of the call succeeds. An unlink and an accept cannot meet it. 099's multi-call class (a transaction that holds a row, then asks for the review lock) stands outside the order as before, and now meets an accept too, whose lapse waits on its links: the race table's accept against a metadata edit of X then an unlink in one transaction.

**Cost.** A lapse that clears: one FOR SHARE per distinct path link and one row lock per clear, at most 1,001 each; each FOR SHARE writes the row's header. Measured against 097 (review pass 2, before the membership sets): a lapse over 200 rows about +8%, over 1,000 about +22–60% (the sets since remove the quadratic scans that gave the top of that range); a pointer onto the end of a 1,000-row chain about +17%, onto a short chain +0.3 ms. A pointer onto a thought locks its chain even when nothing lapses — usually one to three rows — so it waits for a plain edit of a chain row while it holds the review lock, which every other pointer write, delete and accept waits behind.

**Not here.** A raw write, which locks nothing of anyone's. 097's and 099's NOT HERE name this residual; they stand as written (append-only) and db/README says what holds.
