## Changelog

An opt-in `orchestration` compose profile runs n8n beside the brain: pinned by digest, its store its own (SQLite, measured against a Postgres 17), loopback only, a 24-hour run-history window, refusing to start without its encryption key; `deploy/orchestration/provision.ts` sets the owner up, keeps an expiring API key in `deploy/.env` that a re-mint revokes, loads credentials and templates, and refuses a brain key at write scope; the eval kit now runs its checks against the profile as it ships, with key, pruning and egress-probe checks (SMD-2210).

## FORK

n8n as an opt-in `orchestration` profile — pinned, its own store, expiring and separate keys, a short run-history window, and the eval kit re-run against what ships (SMD-2210)

**What changed.** `deploy/compose.yaml` gains an `n8n` service under
`profiles: ["orchestration"]`, beside `board-sync` and `jev`. It runs
`n8nio/n8n:2.40.6` by its multi-arch index digest, on n8n's default SQLite
in the `n8n-data` volume. Its one port is `${N8N_BIND:-127.0.0.1}:${N8N_PORT:-5678}`,
check 13's form, and PUBLISHES now lists it. It sets the telemetry switches
and `N8N_BLOCK_ENV_ACCESS_IN_NODE`, and a window of 24 hours or 1,000 runs
(`N8N_EXECUTIONS_MAX_AGE`, `N8N_EXECUTIONS_MAX_COUNT`; n8n's defaults are 336
and 10,000). Its entrypoint refuses to start without `N8N_ENCRYPTION_KEY`,
since n8n would otherwise generate one inside the volume. Compose's `:?`
cannot do that job: it would fail every `up` without the profile.

`deploy/orchestration/provision.ts` is the provisioning step. An operator
runs it from a checkout; the kit imports it. Owner setup and sign-in go
through the internal `/rest` endpoints. The API key carries ten scopes and
expires after `N8N_API_KEY_DAYS` (90), and it is kept in `deploy/.env` as
`N8N_API_KEY`. A new key is minted when the stored one is refused, has less
than a week left, or on `--rotate`. The new key is written before any old one
is deleted, and each earlier `ob1-provision` key is then deleted (revoked).
Credentials are created or patched from `credentials.template.json`, and
templates created or replaced, through `/api/v1`. A brain key that
`MCP_ACCESS_KEYS` does not list, or lists at write scope, is refused. The
inbound keys are two: `N8N_MCP_KEY` (header `x-n8n-key`) for the MCP
endpoint, `N8N_WEBHOOK_KEY` (`x-n8n-run-key`) for on-demand runs. `--self-check`
runs the pure rules, and CI runs it in the portable-server job.

The kit's n8n (`evals/orchestration/`) is now the profile: the driver passes
`--profile orchestration`, and `compose.n8n.yaml` changes only the pruning
cadence. `--with postgres` gives it a Postgres 17 of its own, and `--with
sealed` is the egress probe. That probe puts n8n on an `internal: true`
network, in the network namespace of a tcpdump watcher that starts before
it, with a Bun HTTP front for the host. It runs a probe workflow of ten fixed
captures, and C3 requires the act tool to FAIL. Beyond C1–C3 and C1s,
`--verify` adds three checks:
- **K**: each inbound key refused on the other's path; after `--rotate` the
  replaced key answers 401, the new one expires on time, and exactly one
  provisioned key is left.
- **P**: two saved runs moved to 25 h and 23 h back in the store; the first
  is gone from the API and the store, the second kept.
- **E**: the watcher's DNS names and outbound SYNs.

**Decided here.** The store is SQLite (below). The import recipes' pipeline
runs from a workflow through a keyed HTTP runner in the profile, built with
SMD-2212's first import template (`docs/orchestration-tool.md`, "Running a
pipeline from a workflow"). The declined alternatives are an n8n image with
Bun and python3, which OB1 would then distribute, and a compose one-off,
which needs the engine's socket.

**Why.** The ADR (SMD-1863) left the store to measurement and the profile to
this ticket. The POC's shape ran n8n on the brain's Postgres 16, which n8n
calls "compatibility support only". Its key did not expire and stayed valid
after a re-mint, one key served two paths, and nothing probed what n8n dials.

**Held.** CI's "Every published port binds loopback" step holds three things:
n8n's port on loopback, its image to a digest, and a plain `config` to
`migrate postgres server`. `provision.ts --self-check` covers the brain-key
refusals, the renderer, the expiry reader, the env writer and the template
ids. The kit (`--verify n8n`) holds the rest against a live profile.

**Measured after.** On the dogfood Mac (2026-09-25, podman, the host's
Ollama), one cycle each. SQLite and `--with postgres` ran with
`--wait-schedule`, and passed C1–C3, C1s, K and P. `--with sealed` passed
C1–C3 on the brain-side paths (the act tool refused), K, P and E. Ten
captures, then none more, in 20.4 s, 22.8 s and 12.1 s. The schedule was
seen after 811 s and 752 s. The run past the window was gone after 40–101 s.

The store is SQLite:

| store | n8n | its own server | extra image | on disk |
| --- | --- | --- | --- | --- |
| SQLite | 369 MiB | none | none | 6.4 MiB |
| Postgres 17 | 404 MiB | 52 MiB | 280 MiB | 15.5 MiB |

A hot copy (`VACUUM INTO`) restored into a fresh volume brought back the
workflows and credentials, and the stored key still answered. The sealed
n8n first asked for `api.n8n.io` at boot, from its MCP registry module, so
`N8N_DISABLED_MODULES=mcp-registry` is set. After that it asked only for
`api.linear.app` (the act tool's) and the brain, over a four-minute window.
Found on the way: the kit's `--up --build` had been starting a day-old
`localhost/` brain image on podman. `--up` now stamps the build and refuses
a brain that does not report the stamp.
