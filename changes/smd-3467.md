## Changelog

`scripts/ci-step-times.ts --shift` names each Fork Checks job or step on main whose last 3 runs all went over its line, the median of the 10 before them plus max(30 s, 20%), with the pull requests merged where it landed. A new workflow, `.github/workflows/ci-shift.yml`, runs it after each Fork Checks run on main and shows each one made at that run as a warning and a table in its summary; it blocks nothing (SMD-3467).

## FORK

A warning when a job or step on main got slower (SMD-3467)

**What changed.**
- **`scripts/ci-step-times.ts --shift`** reads every job and step of main's push runs, each a series over the runs where its job succeeded, a step named `job › step`:
  - a shift is all of a series' last 3 runs over its line, the median of the 10 before them plus max(30 s, 20%);
  - it is named once, at the run that makes it, and again only after 3 runs back under the line;
  - it says where it landed, from the run before the first of those 13 runs over the line to the first of the 3, with the pull requests merged there, read from GitHub's compare of the two commits;
  - those made at the newest run read, or at `--through <run id>`'s, are `::warning`s and a table in `$GITHUB_STEP_SUMMARY` when that is set; the earlier ones in the window are listed.
- **New options:** `--last <n>` (the newest n completed runs, for the per-job report too; with `--shift` the default, 40, and at least 13), `--shift` and `--through`. `--shift` lists push runs alone, since a fork's pull request from a branch it named main lists as main too. The refused combinations exit 2, as the others do.
- **`.github/workflows/ci-shift.yml`** (new) runs `--shift --last 40 --through <the run>` on `workflow_run` after each Fork Checks run on main whose event is push, or by hand (`workflow_dispatch`, a run named or the newest). Its token reads actions and contents and nothing else; it runs main's copy of the script, since `workflow_run` reads the workflow from the default branch.
- **The self-check** holds the shifts to two of main's real series, from the 2026-10-28 review's data, and to made-up ones. It also holds the series' reading, the merge subjects' parsing and the warning's escaping.
  - **The real series:** SMD-2679 PR 4b's sleep cell is named once at its third run over, landing in 8a0f40e7..2b46a488. SMD-3155's canary step is named at 211aaa6f, its range f3267523..b7e784c7.
  - **The made-up series:**
    - a one-run and a two-run spike that name nothing;
    - the line at 10 s and at 200 s, each side of it;
    - a series that shifts twice after going back under its line;
    - 12 runs, which name nothing.

**Why.** Two slowdowns reached main and nobody saw them for days: SMD-3155's canary case, 113 → 155 s, and SMD-2679 PR 4b's sleep cell, 196 → 269 s. Earlier PRs of SMD-2679 had each added time too. The report needed someone to run it on a job they already suspected.

**Departures from the ticket.**
- **The range.** The ticket said "since the last run under the line". SMD-3155's canary step after its merge (330f9ad5) ran 155, 121, 150, 123, then 153, 155 and 164: slow only some of the time. The last run under the line before the 3 is b3f50fdd, so that range would hold only PR 550 and miss PR 546. Reaching back to the run before the first of the 13 over the line gives f3267523..b7e784c7, PRs 546–550.
- **Step size.** The ticket said "any step of at least 5 s". Every step is read: a step under 5 s can't clear a 30 s floor without taking 30 s more, so the 5 s cut would only have changed which runs make up a series' median.
- **Which runs count.** A run counts for a job where the job succeeded, not only where the whole run did. Of the review's 120 main push runs, 117 were green; a run that failed in one job still has the others' times.
- **Where it runs.** It is a workflow of its own on `workflow_run`, not a job in Fork Checks. A job inside Fork Checks would read only the runs before its own, so each warning would show up one run late. It would also need `fork-checks-passed`'s `needs:` (check 20) and would cost every PR a runner. SMD-2095's scheduled runs don't exist yet; if they replace the push runs, `--shift`'s push-only listing and this trigger change with them.

**Held.**
- **The ticket's backtest,** the 117 green main push runs of 10-20 → 10-28, read through `gh` (`--shift --runs <the 117>`): 17 shifts at 9 runs, not the ~13 the ticket expected. The review's prototype cut job names to 22 characters, which put the four db-live cells' "Run the live suite's shard" steps into one series. Read per series, each sleep and extract shift shows on both the job and its shard step. The 17:
  - Five pairs: the sleep cell at fbedb39c (#463), af6abc28 (#487) and 2b46a488 (#542); the extract cell at 43845850 (#517); the long cell at b7e784c7 (#550), which SMD-3392 moved [38r] into on purpose.
  - Full stack at 3a6686aa (#472).
  - The canary step, range f3267523..b7e784c7 (#546–#550).
  - Schema migrations: the job and its step at af6abc28, each over a 12-PR range; the step again at 32424f81, an 8-PR range.
  - Schema's live suite at f403293d (5 PRs).
  - The data layer's upgrade step at 4c1fa373 (#445).
  - Both of the ticket's cases are there: 2b46a488 named at its merge, alone in its range, and the canary within 3 runs of the first of its 3 (6 runs after 330f9ad5 itself), with 330f9ad5 in its range. No one-run spike made a shift.
- **Live on main,** as the workflow runs it (`--shift`, the newest 40 push runs, a summary file set): 17 s for 40 runs, 299 series, no shift at main's newest run (730d0cd8, run 40901815151), and the summary's one line saying so. `--through 40597324540`, the canary's run, gives three warnings (the canary step, and the long cell and its step) and the table with compare links.
- **Mutants,** each killed by the self-check:
  - the once-only rule dropped;
  - the range from the last run under the line instead;
  - a run on the line counted as over (killed once a case put 3 runs exactly on a 240 s line);
  - the 30 s floor dropped.
- **The rest:**
  - the refused option combinations each exit 2;
  - a `--through` run that isn't one of main's push runs exits 1;
  - the per-job report with `--last 3` reads as before;
  - the scripts' typecheck, the checker and actionlint 1.7.7 (its image, which runs shellcheck on `run:` bodies; a positive control with an unquoted `$THROUGH` fails) all pass.
  - The checker reads the new file: a `-latest` runner in it is refused.
- **Not run before the merge:** the workflow itself. `workflow_run` takes its definition from the default branch, so its first run is the first Fork Checks run on main after this merges.

**Verify** (the ticket's, as held above, and after the merge):
- CI shift runs after each Fork Checks run on main and finishes green, in under a minute of runner time.
- A `workflow_dispatch` with run 40597324540 shows the canary step's warning and the table.
- Over the following week, every warning it raises names a slowdown the step times show, or its noise is recorded here for the line to be revisited.
