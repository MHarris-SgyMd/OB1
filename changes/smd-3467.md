## Changelog

`scripts/ci-step-times.ts --shift` names each Fork Checks job or step on main whose last 3 runs all went over its line, the median of the 10 before them plus max(30 s, 20%), with the pull requests merged where it landed. A new workflow, `.github/workflows/ci-shift.yml`, runs it after each Fork Checks run on main and shows each one made at that run as a warning and a table in its summary; it blocks nothing (SMD-3467).

## FORK

A warning when a job or step on main got slower (SMD-3467)

**What changed.**
- **`scripts/ci-step-times.ts --shift`** reads every job and step of main's push runs, each a series over the runs where its job succeeded, a step named `job › step`:
  - a shift is all of a series' last 3 runs over its line, the median of the 10 before them plus max(30 s, 20%);
  - **once only:** a series is armed by 3 runs in a row under its line and disarmed by a shift, so a shift is named once, at the run that makes it, and again only after 3 runs back under. A series starts armed only if 3 runs in a row among its first 10 are under the line its first check draws. So a window that opens on a step slow every other run names nothing for it, while a new job slowed at its first check is named;
  - **where it landed:** from the run before the first of the 10 that is over the line with at least half the runs from it on over it too, to the first of the 3, with the pull requests merged there (from GitHub's compare of the two commits, which lists 250 commits at most; a longer range says so);
  - **the report:** those made at the newest run read, or at `--through <run id>`'s, are `::warning`s, and a table in `$GITHUB_STEP_SUMMARY` when that is set. GitHub shows 10 warnings a step, so past 10 it gives nine and a tenth counting the rest. The earlier ones in the window are listed.
- **New options:** `--last <n>` (the newest n completed runs, for the per-job report too; with `--shift` the default, 40, and at least 13), `--shift` and `--through`. `--shift` lists push runs alone, since a fork's pull request from a branch it named main lists as main too (with `--runs`, the runs named are read whatever their event). The refused combinations exit 2, as the others do; `--days` and `--last` take digits alone.
- **When `--shift` exits 1:** fewer than 13 runs are left to read after the cut, or a run in the window could not be read after three tries 3 s apart. In the second case the report still prints, then a `::error`: a missing run takes a point out of its series and can move a shift off the run that makes it.
- **`.github/workflows/ci-shift.yml`** (new) runs `--shift --last 40 --through <the run>`:
  - **when:** on `workflow_run` after each Fork Checks run on main whose event is push, or by hand (`workflow_dispatch`, a run named or the newest);
  - **its token** reads actions and contents and nothing else;
  - **its code** is main's copy of the script, since `workflow_run` reads the workflow from the default branch;
  - **re-runs:** a re-run of a main run triggers it again through that run, so a warning made there can show twice.
- **The self-check** holds the shifts to three of main's real series, from the 2026-10-28 review's data, and to made-up ones:
  - **the real series:**
    - SMD-2679 PR 4b's sleep cell, named once at its third run over, landing in 8a0f40e7..2b46a488;
    - SMD-3155's canary step, named at 211aaa6f, its range f3267523..b7e784c7;
    - the sleep cell as a new job, slowed by SMD-2679 PR 2 at its eleventh run and named at its first check, landing in b40c4d12..fbedb39c;
  - **the made-up series:**
    - spikes of one and two runs, which name nothing;
    - the line at 10 s and at 200 s, each side of it and on it;
    - a series that shifts twice after going back under its line;
    - one or two runs back under, which don't re-arm it;
    - a window opening on a step slow every other run, which names nothing;
    - a lone spike among the 10, or a slow stretch before the 13, neither of which stretches the range;
    - 12 runs, which name nothing;
  - **the plumbing:**
    - the window's cut at `--through` and `--last`;
    - runs given out of order, put in creation order;
    - the series' reading;
    - the merge subjects' parsing (a revert of a merge left out);
    - the warning's escaping.

**Why.** Two slowdowns reached main and nobody saw them for days: SMD-3155's canary case, 113 → 155 s, and SMD-2679 PR 4b's sleep cell, 196 → 269 s. Earlier PRs of SMD-2679 had each added time too. The report needed someone to run it on a job they already suspected.

**Departures from the ticket.**
- **The range.**
  - The ticket said "since the last run under the line". SMD-3155's canary step after its merge (330f9ad5) ran 155, 121, 150, 123, then 153, 155 and 164: slow only some of the time. The last run under the line before the 3 is b3f50fdd, so that range would hold only PR 550 and miss PR 546.
  - Reaching back to the first run over the line from which at least half are over gives f3267523..b7e784c7, PRs 546–550, and keeps a lone spike earlier among the 10 from stretching it.
- **Step size.** The ticket said "any step of at least 5 s". Every step is read: a step under 5 s can't clear a 30 s floor without taking 30 s more, so the 5 s cut would only have changed which runs make up a series' median.
- **Which runs count.** A run counts for a job where the job succeeded, not only where the whole run did. Of the review's 120 main push runs, 117 were green; a run that failed in one job still has the others' times.
- **Where it runs.**
  - It is a workflow of its own on `workflow_run`, not a job in Fork Checks. A job inside Fork Checks would read only the runs before its own, so each warning would show up one run late. It would also need `fork-checks-passed`'s `needs:` (check 20) and would cost every PR a runner.
  - SMD-2095's scheduled runs don't exist yet; if they replace the push runs, `--shift`'s push-only listing and this trigger change with them.

**Held.**
- **The ticket's backtest,** the 117 green main push runs of 10-20 → 10-28, read through `gh` (`--shift --runs <the 117>`): 17 shifts made at 9 runs, not the ~13 the ticket expected.
  - **Why 17:** the review's prototype cut job names to 22 characters, which put the four db-live cells' "Run the live suite's shard" steps into one series. Read per series, each sleep and extract shift shows on both the job and its shard step.
  - **The 17, each by the commit its range ends at, where it landed;** 14 of the 17 ranges name one pull request:
    - five pairs, a job and its shard step: the sleep cell at fbedb39c (#463), af6abc28 (#487) and 2b46a488 (#542); the extract cell at 43845850 (#517); the long cell at b7e784c7 (#550), which SMD-3392 moved [38r] into on purpose;
    - Full stack at 3a6686aa (#472);
    - the canary step, f3267523..b7e784c7 (#546–#550);
    - Schema migrations, the job and its step, at af6abc28 (8 PRs), and the step again at 32424f81 (#553);
    - Schema's live suite at f403293d (#443);
    - the data layer's upgrade step at 4c1fa373 (#445).
  - **Both of the ticket's cases are there:**
    - 2b46a488 alone in its range, named two runs after its merge;
    - the canary named at the third of its 3 runs over (6 runs after 330f9ad5 itself), with 330f9ad5 in its range.
  - No one-run spike made a shift.
- **As the workflow reads them** (review pass 1's run-it, with the script's own functions over cached runs): for each of main's last 161 push runs, the 40-run window through it warns of the same shifts a full history makes at that run, 21 in all.
- **Live on main,** as the workflow runs it (`--shift --through <the run>`, the newest 40 push runs, a summary file set):
  - **main's newest run:** 15–22 s, 299 series, no shift, and the summary's one line saying so;
  - **an older run:** 28–36 s, since the whole 500-run list is read to reach it. `--through 40597324540`, the canary's run, gives three warnings (the canary step, and the long cell and its step) and the table with compare links; `--through 39608575828` gives the live suite's one.
- **Mutants,** each killed by the self-check, 20 in all:
  - **the rule:** the once-only rule dropped; starting armed; starting disarmed; one run under enough to arm it first; re-arming on any 3 not all over, or on one run under; never re-arming; the loop starting one run late; a run on the line counted as over; the floor at 29 s; the floor dropped;
  - **the range:** no majority rule; searched from the series' start; from the last run under the line;
  - **the plumbing:** `--through`'s cut dropped, or one run past it; the runs not sorted; a failed job's run counted; the merge regex unanchored; `%` not escaped.
- **The rest:**
  - the refused option combinations each exit 2, `--last 0x10` and `--days " 3"` among them;
  - a `--through` run that isn't one of main's push runs exits 1, as do 5 runs left by `--days 2 --through`;
  - one run `gh` won't give (a stand-in `gh` failing it) prints the report and a `::error`, exit 1, after 6 s of retries;
  - a summary path in a missing directory is said on stderr and the run exits 0;
  - the per-job report with `--last 3` reads as before;
  - the scripts' typecheck, the checker and actionlint 1.7.7 all pass. That actionlint image runs shellcheck on `run:` bodies: a positive control with an unquoted `$THROUGH` fails.
  - The checker reads the new file: a `-latest` runner in it is refused.
- **Not run before the merge:** the workflow itself. `workflow_run` takes its definition from the default branch, so its first run is the first Fork Checks run on main after this merges.

**Verify** (the ticket's, as held above, and after the merge):

- A `workflow_dispatch` with run 40597324540 shows the canary step's warning and the table.

## Review pass 1

A cold read and a run-it. The run-it reran the backtest (byte-identical), checked the canary and sleep shifts by hand from raw `gh run view` data, ran the workflow's step under `bash --noprofile --norc -eo pipefail` with `THROUGH` empty and set, and ran 32 mutants of its own.

- **Fixed (run-it):** one run `gh` failed to read (a 502, twice in ~400 calls during the review) dropped a point from its series, and could move a shift off the run that makes it. The extract cell's shift moved from 40257181318 to 40258485407 that way, so neither run's CI shift would have warned. `gh` is now tried three times 3 s apart, and with `--shift` a run still unread fails the job with a `::error` after the report.
- **Fixed (cold read, run-it):**
  - **The problem:** each window started a series armed, so the once-only rule held only within the window. A step slow every other run, already named before the window opened, could be warned of again.
  - **What happens now:** a series starts armed only if 3 runs in a row among its first 10 are under the line its first check draws.
  - **Starting disarmed outright was tried first** and lost 3 of the 17. Those were SMD-2679 PR 2's sleep shift, which came at the sleep cell's first check since the job had been split out the day before, and the live suite's at the window's start.
- **Fixed (cold read):**
  - **The problem:** the range reached back to the first run over the line anywhere in the 13, so a lone spike among the 10 stretched it.
  - **The fix:** it now starts at the first run over the line from which at least half are over. The canary keeps PR 546.
  - **The effect:** Schema migrations' range went from 12 PRs to 8 and its step's at 32424f81 from 8 to 1; the live suite's from 5 to 1.
- **Fixed (cold read, run-it):** the self-check missed four things, each shown by a mutant that survived: re-arming too early, the range's lower bound, the first check's index, and a run exactly on the 10 s line. Each now has a case. The window cut and the run ordering moved into exported functions (`windowOf`, `collectShifts`) with cases of their own.
- **Fixed (run-it):**
  - **Too few runs:** `--through` an old run, or `--days 2 --through`, could leave fewer than 13 runs and still say "None made". Now it exits 1 and says why.
  - **Listing cost:** `--through` read the whole 500-run list every time (28–32 s); it now lists 50 first and widens only when fewer than 40 runs end at the named one.
  - **Unwritable summary:** a summary path that can't be written is said rather than thrown.
  - **Number parsing:** `--last` and `--days` refuse anything but digits (`0x10` read as 16).
- **Fixed (cold read, run-it):** GitHub shows 10 warning annotations a step; past 10 it now gives nine and one counting the rest.
- **Fixed (run-it):** a range over GitHub's 250-commit compare limit says it read only the first 250.
- **Fixed (cold read), the docs:**
  - this record said 2b46a488 was named at its merge; it is named two runs after;
  - the header said `--shift` reads push runs only, which isn't true with `--runs`;
  - the workflow said main's runs were done when it starts, where only the run it reads through is;
  - "outside the window" was the reason given for a range with no start, which is also a new job's first run;
  - the header's "A re-run shows its latest attempt, marked" is the per-job report's.
- **Recorded, not changed (cold read, run-it):** a re-run of a main run triggers CI shift again through it, so a warning made there can show twice. The workflow's header says so; skipping attempts after the first would also skip a shift that only the re-run's passing job makes.
- **Caught by this pass's own checks:** with `--through` naming a run inside the short list but with fewer than 40 runs before it, the first form of the shorter listing left a 31-run window. It widens on that too now.
