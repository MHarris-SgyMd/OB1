## Changelog

`scripts/ci-step-times.ts --shift` names each Fork Checks job or step on main whose last 3 runs all went over its line, the median of the 10 before them plus max(30 s, 20%), with the pull requests merged where it landed. A new workflow, `.github/workflows/ci-shift.yml`, runs it after each Fork Checks run on main and shows each one made at that run as a warning and a table in its summary; it blocks nothing (SMD-3467).

## FORK

A warning when a job or step on main got slower (SMD-3467)

**What changed.**
- **`scripts/ci-step-times.ts --shift`** reads every job and step of main's push runs, each a series over the runs where its job succeeded, a step named `job › step`:
  - a shift is all of a series' last 3 runs over its line, the median of the 10 before them plus max(30 s, 20%);
  - **once only:** a series is armed by 3 runs in a row under its line and disarmed by a shift, so a shift is named once, at the run that makes it, and again only after 3 runs back under.
    - **Where it starts:** a series starts armed only if 3 runs in a row among its first 10 are under the line its first check draws. So a window that opens on a step slow every other run names nothing for it, while a new job slowed at its first check is named.
    - **The cost:** such a step stays unarmed, so a slowdown on top of it goes unnamed.
    - **A series that opens the window** (its job or step is in the window's first run, in any state, or for a step, its job is there with no steps listed; all series when that run lists no jobs; a step added to a job later is new) names nothing at its first check, since its 13 runs can hold a shift named before the window opened. So `--shift` wants a window of at least 20 runs.
  - **where it landed:** from the run before the first of the 10 that is over the line with at least half the runs from it on over it too, to the first of the 3, with the pull requests merged there. A lone spike stretches it only from the last two of the 10. The pull requests come from GitHub's compare of the two commits, which lists the newest 250; a longer range says an older pull request may be missing;
  - **the report:** those made at the newest run read, or at `--through <run id>`'s, are `::warning`s, and a table in `$GITHUB_STEP_SUMMARY` when that is set. GitHub shows 10 warnings a step, so past 10 it gives nine and a tenth counting the rest. The earlier ones are listed as the window reads them, which is none in its first 13 runs.
- **New options:** `--last <n>` (for the per-job report the newest n completed runs; with `--shift` the newest n up to the newest completed, a run being re-run among them as a gap, the default 40 and at least 20), `--shift` and `--through`. `--runs` reads a run named twice once. `--shift` lists push runs alone, since a fork's pull request from a branch it named main lists as main too (with `--runs`, the runs named are read whatever their event). The refused combinations exit 2, as the others do; `--days` and `--last` take digits alone.
- **When `--shift` exits 1:**
  - fewer than 20 runs are left to read after the cut;
  - the run reported on (`--through`'s, or a listed window's newest) could not be read: no report;
  - one of the window's newest 26 (all of a shorter window) could not be read after three tries 3 s apart, or is being re-run. A missing run takes a point out of its series and can move a shift off the run that makes it, so the report prints, then a `::error`, and the summary says so. An older one is a `::warning`, exit 0. With `--runs` the report is at the newest run read, and a gap at the newest named is one of these.
- **Runs are listed whatever their state,** so a run being re-run stays in the window, as a gap, as does one re-run between the list and its read (or a view that gives no state). When `--through`'s run is the one being re-run, in the list or at its read, nothing is read, exit 0, and the re-run's end runs it again (the window's newest, without `--through`, likewise at its read; in the list it is a push not done, and the report is at the run before). Every `--shift` failure once the options are read gives a `::error` and its line in the summary. The per-job report passes over a run not completed when read (main's script read its partial jobs) and its totals say so. `--runs` ids are read oldest first by id, whatever order they were named in, compared as digit strings so a long one isn't rounded.
- **`.github/workflows/ci-shift.yml`** (new) runs `--shift --last 40 --through <the run>`:
  - **when:** on `workflow_run` after each Fork Checks run on main whose event is push, or by hand (`workflow_dispatch`, a run named or the newest);
  - **its token** reads actions and contents and nothing else; the repository is named (`--repo "$GITHUB_REPOSITORY"`), not found from the checkout's remote;
  - **its code** is main's copy of the script, since `workflow_run` reads the workflow from the default branch;
  - **re-runs:** a re-run of a main run triggers it again through that run, so a warning made there can show twice.
- **The self-check** holds the shifts to four of main's real series, from the 2026-10-28 review's data, and to made-up ones:
  - **the real series:**
    - SMD-2679 PR 4b's sleep cell, named once at its third run over, landing in 8a0f40e7..2b46a488;
    - SMD-3155's canary step, named at 211aaa6f, its range f3267523..b7e784c7;
    - the sleep cell as a new job, slowed by SMD-2679 PR 2 at its eleventh run and named at its first check, landing in b40c4d12..fbedb39c;
    - Schema's live suite opening the backtest, armed by its first 10 and named at its third check, landing in 78899cb9..f403293d;
  - **the made-up series:**
    - spikes of one and two runs, which name nothing;
    - the line at 10 s and at 200 s, each side of it and on it;
    - a series that shifts twice after going back under its line;
    - one or two runs back under, which don't re-arm it;
    - a window opening on a step slow every other run, which names nothing;
    - a series opening the window, not named at its first check, and a job added later, which is;
    - the first arm's terms: the last 3 of the 10 counted, 2 in a row not enough, the line's margin, a run on it under;
    - a lone spike among the 10 (third from its end or earlier) or a slow stretch before the 13, neither of which stretches the range, a spike second from the end, which does, and a run on the line, which is not over it;
    - 12 runs, which name nothing;
  - **the plumbing:**
    - the window's cut at `--through` and `--last` over runs in any state, and when the whole list is read;
    - which gaps, unread or being re-run, fail the job;
    - a job cancelled in the window's first run, still opening it, a step listed there as skipped too, and a first run with no jobs opening all; a step added later to a job that succeeded or failed there, and a job first in the second run, new; a job's name not opening a longer one's;
    - the per-job window over completed runs alone; the run reported on (none with `--runs`) not read, or re-run since the list; ids and same-second runs in order;
    - the 10-warning cap, the compare's 250-commit note, a table cell's `|` and line break, and digits-only numbers;
    - runs given out of order, put in creation order;
    - the series' reading;
    - the merge subjects' parsing (a revert of a merge left out);
    - the warning's escaping.

**Why.** Two slowdowns reached main and nobody saw them for days: SMD-3155's canary case, 113 → 155 s, and SMD-2679 PR 4b's sleep cell, 196 → 269 s. Earlier PRs of SMD-2679 had each added time too. The report needed someone to run it on a job they already suspected.

**Departures from the ticket.**
- **The range.**
  - The ticket said "since the last run under the line". SMD-3155's canary step after its merge (330f9ad5) ran 155, 121, 150, 123, then 153, 155 and 164: slow only some of the time. The last run under the line before the 3 is b3f50fdd, so that range would hold only PR 550 and miss PR 546.
  - Reaching back to the first run over the line from which at least half are over gives f3267523..b7e784c7, PRs 546–550, and keeps a lone spike earlier among the 10 from stretching it.
- **Step size.** The ticket said "any step of at least 5 s". Every step is read: a step under 5 s can't clear a 30 s floor without taking 30 s more, so the 5 s cut would only have changed which runs make up a series' median.
- **Which runs count.** A run counts for a job where the job succeeded, not only where the whole run did. Of the review's 120 main push runs, 117 were green; a run that failed in one job still has the others' times.
- **Where it runs.**
  - It is a workflow of its own on `workflow_run`, not a job in Fork Checks. A job inside Fork Checks would read only the runs before its own, so each warning would show up one run late. It would also need `fork-checks-passed`'s `needs:` (check 20) and would cost every PR a runner.
  - SMD-2095's scheduled runs don't exist yet; if they replace the push runs, `--shift`'s push-only listing and this trigger change with them.

**Held.**

  - **The 17, each by the commit its range ends at, where it landed;** 14 of the 17 ranges name one pull request:

  - **Three of the 17 are noise:** the Schema migrations job and its step at af6abc28, and the step at 32424f81 (#553, a docs sweep). That step has two modes over main's last 80 runs, 32 runs at 90–139 s and 45 at 150–179 s, and flips between them; each of these shifts is three slow-mode runs against a median of mostly fast ones. Over the 500 push runs to 10-29 the job and the step make 7 of the 38 shifts (the step 4), about one a week.

A 40-run window gives 37 warnings over 461 windows. 15 runs misses 1, 14 misses 4, and 13 names nothing. No window of 20 or 40 lists a shift the full history doesn't make.
