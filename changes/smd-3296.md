## Changelog

Every suite that starts a server child now starts it at PORT 0 and reads the port it bound from Bun's start line, where six suites picked a free port and freed it for the child. Children started together no longer race for a port, so a case can't read another child's answers (SMD-3296).

## FORK

Server children bind their own ports (SMD-3296)

**What changed.** `db/test-support.ts` exports `startedPort`, which reads a child's port from Bun's start line. SMD-3263 gave `serveChild` that read, and now `serveChild` uses `startedPort` too. These sites started their children on a port picked by binding port 0 and freeing it, and now start them at PORT 0:
- **test-server [13d]:** its eight children start at once, and `start()` is async. The seven independent children start together, then the calling MCP server, which needs its REST core's port.
- **test-server [13c]:** its two REST cores.
- **extensions/test-auth.ts:** each vendored server on the SQL shim. Its comment allowed a rerun when another process took the port; that comment and `freePort` are gone.
- **mcp-server/test-mcp.ts:** its three entry children.
- **test-egress [10] and [11]:** the REST cores and the MCP server's entry, the entry started once its core has said its port.
- **test-e2e-sql and test-rest-sql:** their one `api.ts` child each.

A child's stdout is drained as it comes, and read to its end where a row reads it.

Three picked ports stay, deliberately. Each is a port with no listener, not a child's:
- test-egress [10]'s and [11]'s provider port must refuse until the stub binds it, so nothing can hold it in between.
- test-server [13c]'s refusing database is the same kind of port.

**Why.** SMD-3263 measured the race on Linux, where bind(0) picks a random port: a freed port went to another server before the child bound it in about 1% of runs with nine children at once. When a port is taken, the child exits ("Is port N in use?"). Or worse, the server that took it answers the child's `/health` and the case reads someone else's answers. On macOS ports are handed out in sequence, so no local run shows it.

A probe of test-server [13d]'s start pattern (eight `api.ts` children in one tick beside a silent listener) ran on Linux, `oven/bun:1.4.3` at 4 CPUs:
- main's pick: 1 round of 400 had two children on one port, the loser exiting with its port in use and no start line;
- PORT 0: none in 400.

That loser's `/health` would have been the winner's. So a [13d] case could signal one child while its request went to another, which fits SMD-2576's flake (a stop expected to cut a call exits 0 in about 300 ms). The probe doesn't prove it was the cause.
