## Changelog

`capture_thought` now says what a re-capture did to a capture-only key's label: that the text landed on an existing thought, whether its label moved to the caller's key or was kept, whether the thought is now settled against other keys, and, unless the label is the caller's own or was not weighed, that the operator's `reset_capture_stamp` puts a moved label back or reopens a kept one. Before, only `thought_changes` said so. REST's capture body carries the same as `label` (SMD-2898).

## FORK

A re-capture says what it did to a capture-only key's label (SMD-2898)

**What changed.**
- **The weighing that answers** (migration 089, `ob1_weigh_recapture(id, fingerprint, actor, declared)`). It holds 086's `ob1_restamp_recapture` body unchanged — its guards, row lock, reads, events and sentinels — and answers what each branch found, from inside the call with the row locked:
  - `moved`: the label moved to the caller; `stamp` is the caller's, `before` the capture-only key's.
  - `kept`: weighed now and not higher; the decline is recorded (or the caller's own was already there). `weighed` is the trust the caller was weighed at, and `own` whether the caller has an agent id — 085 weighs a key's own later landing again only by its id, so a name-only key's decline settles the row for it too.
  - `settled`: an earlier re-capture settled the row since the latest reset — `by: "restamp"` (with `mine` when the stamp is the caller's own) or `by: "decline"` (another key's decline, or a name-only key's own), with `decliner` its key's name and `decliner_weighed` whether it names an agent id, by which 085 still weighs that key's own later re-capture.
  - `unweighed`: the caller's key has no kind, so nothing was weighed and this call recorded nothing.
  - `none`: not a capture-only key's label to weigh — a capture-scoped caller, the row gone or its metadata not an object, the text moved since the capture, no scope mark, or a change of text since.
  - `stamp` is the row's `actor_kind`, `actor_name` and `trust` after the call.
- **A settled row's text changed since.** 086 refuses a settled row before the text-change read, which hashes every edit (085's review pass 5). So a settled row reads `none` when any update moved its `content_fingerprint` — the diff records it (055). 085 settles only an unchanged text and 086's reset refuses a changed one, so such a move came after the settle, and the label is the editor's, the settling key's own edit included. A whitespace edit moves no fingerprint and the row stays settled. Nothing is hashed.
- **085's function stays.** `ob1_restamp_recapture` keeps its signature and boolean answer as a call of `ob1_weigh_recapture`. A return type cannot change in place, and 085's and 086's files re-applied (test-schema [2], `migrate.ts --reapply`) over a jsonb form would fail. A server before this one calls it and moves the label as before.
- **The stores.** Both call `ob1_weigh_recapture` where they called `ob1_restamp_recapture`, and read its answer as `label`. On a database at 085–088 they fall back to `ob1_restamp_recapture` (the label moves; no label), and before 085 to neither. `none`, an outcome the server does not know and 085's boolean are no label.
- **The reply.** `capture_thought` adds one note, for a key that can read and a re-capture: "this re-capture landed on <id>, which already held the text", then what happened —
  - moved to your key (out of `ingested`, the outside-text notice goes and min_trust searches include it; into it, the notice shows and searches find it at `ingested` and leave it out above), no later re-capture moves it, and the reset puts the capture-only key's label back;
  - kept and settled — against every other key, your own key's later re-capture still weighed, for a key with an agent id; against every key, yours included, for one without — and the reset reopens it;
  - already your key's — a label moves once — and the reset as the way to weigh it afresh;
  - moved by another key's earlier re-capture, and the reset puts it back; or settled by an earlier decline, leaving the capture-only key's label — naming the decliner whose own later re-capture is still weighed, where its decline carries its agent id — and the reset reopens it;
  - not weighed, because your key has no kind (classified in SQL with `set_agent_kind`).

  Stamp values are cleaned as every reply cleans them. Structured content carries `label` as the outcome and, after a restamp, `labelMine`; REST's body carries the whole label. A new text, a key that cannot read, `none` and a database before 089 reply exactly as before.
- **The skill.** `ob1-local-http` (0.4.0) says what to report from `label`.

**Why.** SMD-2744's review passes all ran into this: a client that re-captured a text had no way to tell from the reply whether it now held the label, and so could not see the outcome the reset (086) exists to fix. The answer is read inside the call: SMD-2744's second PR first read its row back after the write, and each of four review passes found a new seam in that read.

**Not here.**
- **A plain re-capture** of a row no capture-only key captured: `none`, and the reply says what it said.
- **A raw content edit that leaves the fingerprint stale.** 055 records no move for it, so a settled row reads `settled` where the reset, which hashes, refuses. Telling it from a whitespace edit — both a content diff and no fingerprint move — would hash each edit under the row lock, the cost 085's review pass 5 removed. A raw writer's row only.
- **The converse,** a raw `SET content_fingerprint = NULL` then a refill: a fingerprint move with no change of text, so a settled row reads `none` — the note silenced, never false.
- **The fingerprint read** detoasts each update's diff since the latest reset (it hashes nothing).
- **086's reset reply** still says "your own key's later plain re-capture still moves it" whatever the operator key's agent id — the overclaim this change's review pass 1 fixed here (SMD-2914).
- **Identity by name, and the decliner as it stands now.** `mine` and the decliner's naming go by the name as the stamp and the log hold it: a renamed restamper reads its own label as another key's; a decliner arriving without its agent id is told its own decline settled the row with no word on why this landing was not weighed; a decliner renamed since is named by its old name, which a new key may now hold; and "still weighed" is 085's rule for that agent, which an agent unclassified or revoked since cannot use until it is classified or its key rotated (SMD-2915).
- **One name on two keys.** `mine` compares the stamp's name with the caller's, as the stamp holds it (the reply names whose the label is). A key given a renamed key's old name reads that key's label as its own — SMD-2746's family.
- **The reset addressed to the operator itself.** The reply does not know the caller's kind, so an operator key is told of "an operator key's" reset too.

**Tests.** test-schema [80], test-upgrade [20ak], test-store-sql and test-store-postgrest [8d] (the answer, the fallback at 085–088 and before 085, a weighing's own fault thrown), test-e2e-sql [13h] (each Verify case through the real server, a database before 089 included), test-rest-sql [3], test-server [26]. 60 mutants: 56 killed, 4 equivalent (an ORDER BY on the capture row in the first build, of which a thought has one — that read is gone; the empty append on a move, whose diff always moves the trust; the decliner read's order, there being one decline since a reset, since a later key finds the row settled and writes none; the notice clause's `before` on a move into `ingested`, which always comes from below it).
