## Changelog

Preflight's `schema` row, for a role whose `public.thoughts` exists but does not resolve, now prints the exact search-path fix: the login role's own path parsed as its server's Postgres parses it, every name quoted, `public` added. Where the connection sets the path, the row says to replace that setting with the connection string's `options` value instead; with no USAGE on `public` as well it names both causes; it acts only when thoughts itself does not resolve (SMD-2242).

## FORK

Preflight's `schema` row prints the exact search-path statement — the login role's path parsed as its Postgres parses it, rebuilt quoted, public added (SMD-2242)

**What changed.** SMD-2062 left the `schema` row a template: `ALTER ROLE r IN DATABASE d SET search_path = <the schemas it has>, public`. With no USAGE on `public`, it offered the path fix only "if public is not on the role's search_path". Now:

- **`server-portable/search-path.ts`** (new) parses a search_path setting as Postgres's `SplitIdentifierString` does:
  - names separated by commas;
  - around them, whitespace as `scanner_isspace` sees it: space, tab, newline, CR and FF, and from PostgreSQL 17 vertical tab;
  - a quoted name is kept as written, `""` inside it a quote;
  - an unquoted name is folded A–Z only;
  - the empty name a `''` path reads back as is dropped.

  `withPublic()` rebuilds the path with every name quoted and `public` last. `withPublicInOptions()` gives the same path as a connection string's `options=-c search_path=…`, the form both Bun and libpq (psql, pg_dump) read. It has no space between names, a space or backslash inside a name backslash-escaped, and is percent-encoded, the characters a shell reads included.
- **The probe** runs only when thoughts itself does not resolve: the count failed with an undefined table (SQLSTATE 42P01, in any `lc_messages`), and the probe's own `to_regclass('thoughts')` is NULL. It reads `current_setting('search_path')`, `server_version_num`, `session_user`, and in its own try the setting's `pg_settings.source`, then names each cause that holds, each with its statement:
  - no USAGE: `GRANT USAGE ON SCHEMA public TO <current_user>;`.
  - `public` off the path: `ALTER ROLE <session_user> IN DATABASE <db> SET search_path = <its schemas, quoted>, public;`. It names the login role, whose settings load, not a role that SET ROLE made current. Where the two differ, the statement starts `SET ROLE NONE;`, for the login role itself or a superuser to run; the role it becomes may not alter it, and neither may the database's owner.
  - Source `client`: the connection string sets the path (a `search_path=` parameter, or `-c search_path=` in `options=`) and outranks every `ALTER ROLE`. The row says to replace that setting with `-csearch_path%3D…` in `options=`, beside any other `-c` setting. Appending a second one is not the same: Bun joins two `options` with a comma, libpq keeps only the last, and a `search_path=` parameter outranks both.
  - Source `session`: the path was SET after login, by a pooler replaying it or a login trigger, and the row says the statement is outranked there.
  - A role barred from `pg_settings` gets the statement, with the caveat that a connection-string path outranks it.
  - With USAGE held, thoughts not resolving means off the path whatever the parse says.

**Why.** The template made the operator work out the role's path and quote it. SMD-2062's review passes 2–4 built the exact statement, then split it out of that PR for size. They also found what an exact statement has to get right:
- echoing the setting printed invalid SQL for an empty path (`""`) and for a raw `$user`;
- worse, it pasted a raw path a role had stored (`set_config`, then `SET search_path FROM CURRENT`) into the remedy. A reviewer stored `x;drop/**/table/**/…;--`, and piping the printed line into psql as postgres ran the DROP.
- A parser using `/\s/` read an NBSP before `public` as whitespace, bringing "Apply the migrations" back on a migrated brain.
- `toLowerCase()` folded `Ü`, naming a different schema.

**Held.** test-preflight, 463 → 491:

- **[4b]:** fifteen settings read as the named server version reads them:
  - quotes, doubled quotes and `""`;
  - case, including `Ü`;
  - a quoted comma;
  - tab, newline, CR and FF;
  - an NBSP, which is no whitespace;
  - `\v` as 16 and as 17 read it;
  - an injection-shaped name.

  Plus `withPublic`'s order and quoting, and `withPublicInOptions`'s spacing, escaping and encoding.
- **The ticket's role** gets `ALTER ROLE pf_reader IN DATABASE … SET search_path = "nowhere", public;`.
- **An empty path:** the row says so and sets `public` alone. Run as printed, it makes `thoughts` resolve.
- **A raw path stored `FROM CURRENT`:** `"$user", "Odd ""x", NoWhere,<NBSP>public, x;drop/**/table/**/pf_sentinel;--` becomes `"$user", "Odd ""x", "nowhere", "<NBSP>public", "x;drop/**/table/**/pf_sentinel;--", public`. Run as printed, as a superuser, it makes `thoughts` resolve for the role, and the sentinel table stands.
- **A path from the connection string,** in `options` or as Bun's `search_path=`, gets `-csearch_path%3D%22nowhere%22%2Cpublic` for `options=`. With the setting replaced as printed, beside another `-c` setting, `thoughts` resolves and the other setting holds. Checked by hand through Bun and psql as well, with names holding a space, a quote, a comma, a backslash and a shell's characters.
- **A login role whose settings SET ROLE** gets `SET ROLE NONE; ALTER ROLE pf_reader …`. Run as printed over the login role's own connection, it takes.
- **With `pg_settings` revoked** in the database, the role still gets the statement, with the connection-string caveat.
- **An RLS policy calling a missing table** fails the same count with 42P01 while thoughts resolves, and the row does not call it off the path.
- **No USAGE with the path at `nowhere`:** both statements.
- **No USAGE with `PUBLIC` in the connection string:** the GRANT alone.

**Measured after.** A fuzz of random raw settings through `set_config`, mixing quoted and unquoted names with odd cases, commas, quotes, `Ü`, NBSP, BOM, U+2028, U+3000 and `\v`. For each accepted setting:
- the parse, at that server's version, matched `current_schemas(false)`;
- `SET search_path = <withPublic(parse)>` resolved to the old path with `public` last.

Results: PG16.15, 0 divergences in 3,089 accepted; PG17.11, 0 in 3,011; no round-trip failures. On PG16 the same fuzz with `/\s/` gave 822 divergences in 1,223, and with `toLowerCase()` 91 in 1,275.

Nineteen mutants against test-preflight, all run on the final tree: seventeen killed, two equivalent.

  - `\v` never whitespace;

- **Killed, the probe:**

- **Equivalent:**

In behaviour `to_regclass('thoughts')` still keeps any failure where thoughts resolves off the path statement; the gate spares the second connection.
  - "USAGE held is taken as off the path": with thoughts confirmed unresolved, it acts only where the parse disagrees with Postgres, and the fuzz found no such setting.

**Not taken.**

- **Aligning the `vector extension` row,** which on the same screen gives a plain `ALTER ROLE` (outranked by a setting in the database), names `current_user`, and ignores a connection-string path. SMD-2238 owns that row's remedy and now lists all three.
- **Terminal escapes:** a quoted schema name carrying ESC sequences reaches the screen raw, as role names, database names and Postgres error text already do. That belongs to preflight's printer, not to this row.
- **Truncating a name over 63 bytes:** Postgres truncates the rebuilt statement's names the same way, and no truncation can yield `public`.
- **Single-byte encodings** (LATIN1 and similar), where Postgres also folds high-bit uppercase by the locale. The parse is UTF-8's; the `public` judgement is unaffected, only such a name's spelling in the statement.
- **Testing the `session` source,** which a fresh connection only shows behind a pooler or a PG17 login trigger, and the SQLSTATE gate under a localised `lc_messages` (the test image has no other locale).
- **The remedy for a count failing 42P01 on another relation** (an RLS function's missing table): this row no longer calls it off the path, but still falls through to the migrate remedy. SMD-2238 now lists it with the other misread remedies.
- **A killed run leaving `pg_settings` revoked** in a reused local database, as SMD-2062's `PUBLIC` USAGE leg can. CI's databases are fresh.
- **Reading the connection string's own path** when `pg_settings` is unreadable: the row gives the ALTER ROLE with the caveat that a connection-string path outranks it, not the `options=` value.
- **Moving the "(as <login>, or a superuser)" note off the statement's line:** it follows the file's `statement;  (note)` style, which pastes as one line into psql only up to the statement.

**Follow-ups.** SMD-2247: `db/migrate.ts`'s own search-path splitter trims an NBSP and takes a quoted `"PG_TEMP"` for `pg_temp`; it could reuse this parser.
