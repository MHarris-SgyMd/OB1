## Changelog

`db/with-postgres.sh` no longer fails a run before its first test because another process took the database's host port between the pick and the container's start. The port is now picked below the kernels' ranges for port 0, and a start that loses it anyway is retried on another (SMD-3592).

## FORK

with-postgres.sh picks its host port below the port-0 ranges and retries a start that loses it — a busy machine no longer fails a run before its first test (SMD-3592)

**What changed.** `db/with-postgres.sh`:
- **The pick:** at random in 20000–29999, as the suites' `quietPort` picks (SMD-3296), below the kernels' default ranges for port 0 (Linux 32768–60999, macOS 49152–65535). It was 49152–64151, inside macOS's. The test is unchanged: a port is free when a connect to 127.0.0.1 at it is refused.
- **The retry:** a start that fails with the port in use (podman's "address already in use", docker's "port is already allocated") discards its container by ID, picks again and starts again, up to five starts. Any other failure, or a start on a port `OB1_PG_PORT` named, fails as before, with the runtime's status. The runtime's message is printed either way.
- The header comment and `db/README.md` say the range and the retry.

**Why.**
- The runtime binds the host port only at `start`. Until then any process binding port 0 could be handed it, and macOS hands port 0 out from one cursor every process shares (SMD-3323). The start then failed with `listen tcp :P: bind: address already in use`, and the whole run with it.
- While working SMD-2475 on 2026-10-29, running test-live `[32]` alone in a loop: 1 of 51 starts failed this way unloaded, 5 of 20 under load.

**Held.** Through a `podman` shim on `PATH` that holds the requested port on `::` before the real `create`:
- held once: the start fails, the loser is removed, the second start on a new port runs the command, which reads `SELECT 1`;
- held on every start: five starts, then the runtime's status (125), no container left;
- held under `OB1_PG_PORT`: one start, status 125, no retry;
- an unrelated start failure: one start, its message and status;
- held once under `OB1_PG_KEEP`: the retry reuses the name, and the volume and exit hint are kept as before;
- main's script, held once: status 125, as in the measurement.

**Measured on macOS.**
- **Which holders fail podman's start:** podman's forwarder binds `:P`, every address. A holder on `::` fails it with the measured message. A holder on 127.0.0.1, 0.0.0.0 or `::1` does not; the start succeeds beside it. A 127.0.0.1 or 0.0.0.0 holder then takes DATABASE_URL's connections: the command's connect timed out on each. So the pick still tests a port by a connect to 127.0.0.1, which such a holder answers.
- **`quietPort` beside a container's port:** its 0.0.0.0 bind is refused, so a suite run under with-postgres.sh cannot be handed the database's port now that the two share a range. A 127.0.0.1 or `::1` bind succeeds beside it.
- **Under load:** 20 pairs, each starting the branch's script and main's at once, running `true`. Beside them: eight CPU burners, a process holding 2,000 listeners at port 0 on `::` and rotating them, and three other sessions' with-postgres.sh containers.
  - **The branch:** 20 of 20 ran the command, none needing a retry.
  - **Main:** 15 of 20 ran it; 5 failed `address already in use`, as in the measurement above.
