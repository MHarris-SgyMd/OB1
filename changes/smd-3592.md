## Changelog

`db/with-postgres.sh` no longer fails a run before its first test because another process took the database's host port between the pick and the container's start. The port is now picked below the kernels' default ranges for port 0, and a start that loses it anyway is retried on another (SMD-3592).

## FORK

with-postgres.sh picks its host port below the port-0 ranges and retries a start that loses it — a busy machine no longer fails a run before its first test (SMD-3592)

**What changed.** `db/with-postgres.sh`:
- **The pick:** at random in 10000–19999, below the kernels' default ranges for port 0 (Linux 32768–60999, macOS 49152–65535) and apart from the suites' `quietPort` (20000–29999, SMD-3296), whose ports must refuse while a suite runs. It was 49152–64151, inside macOS's. The number comes from `/dev/urandom`, not `$RANDOM`. The test is unchanged: a port is free when a connect to 127.0.0.1 at it is refused.
- **The retry:** a start that fails with the port in use ("address already in use", or docker's "port is already allocated") discards its container by ID, picks again and starts again, up to five starts. Any other failure, or a start on a port `OB1_PG_PORT` named, fails as before, with the runtime's status. What a start prints on stderr is printed, whether it fails or not.
- **The exit status under `OB1_PG_KEEP`:** a run that exits before its container starts now exits with the status it was given. Cleanup's last command was `[ "$STARTED" = 1 ] && echo …`, and its false test made the EXIT trap exit 1 under `set -e`, in place of a failed start's 125 or an interrupt's 130 or 143. That line dates from SMD-1493.
- The header comment and `db/README.md` say the range and the retry.

**Why.**
- The runtime binds the host port only at `start`. Until then any process binding port 0 could be handed it, and macOS hands port 0 out from one cursor every process shares (SMD-3323). The start then failed with `listen tcp :P: bind: address already in use`, and the whole run with it.
- While working SMD-2475 on 2026-10-29, running test-live `[32]` alone in a loop: 1 of 51 starts failed this way unloaded, 5 of 20 under load.

**Held.** Through a `podman` shim on `PATH` that holds the requested port on `::` before the real `create`, or fails a `start` with words of its own; each count is of the shim's `start`s, since two of the mutants below exit 125 as well:
- held once: the start fails, the loser is removed, the second start on a new port runs the command, which reads `SELECT 1`; the command's own status (7) is the script's;
- held on every start: five starts, then the runtime's status (125), no container left;
- held under `OB1_PG_PORT`: one start, status 125;
- an unrelated start failure: one start, its message and status;
- docker's words for a lost port, once: two starts, and the command runs;
- held once under `OB1_PG_KEEP`: the retry reuses the name, and the volume and exit hint are kept as before; held on every start, or an unrelated failure: status 125; SIGTERM between starts: 143, the container gone;
- main's script, held once: status 125, as in the measurement.
- Mutants, each killed by one of these: no `discard` of the loser; a retry on any failure (five starts, not one); no new pick; a retry under `OB1_PG_PORT`; four or six starts; `exit 1` for the runtime's status; the `&&` back in cleanup (status 1 under `OB1_PG_KEEP`). Dropping `CID=""` survived every scenario, interrupts included: the next `create`'s substitution sets `CID` whatever it ends in. It stays, so no path reads a removed container's ID.

**Measured on macOS.**
- **Which holders fail podman's start:** podman's forwarder binds `:P`, every address. A holder on `::` fails it with the measured message. A holder on 127.0.0.1, 0.0.0.0 or `::1` does not; the start succeeds beside it. A 127.0.0.1 or 0.0.0.0 holder then takes DATABASE_URL's connections: the command's connect timed out on each. So the pick still tests a port by a connect to 127.0.0.1, which such a holder answers.
- **`quietPort` beside a container's port:** its 0.0.0.0 bind is refused, but a 127.0.0.1 or `::1` bind succeeds beside it. A container started on a port a suite had picked and not yet bound would then answer the port the suite needs refused, and a stub bound after it would take the other run's DATABASE_URL. So the two ranges are apart.
- **Under load:** 20 pairs, each starting the branch's script and main's at once, running `true`. Beside them: eight CPU burners, a process holding 2,000 listeners at port 0 on `::` and rotating them, and other sessions' with-postgres.sh containers. The retry would rescue a start that lost its port in either range, so what shows the range is the count of retries.
  - **The branch, its pick in 20000–29999 (0d1bd134):** 20 of 20 ran the command, none needing a retry. **Main:** 15 of 20; 5 failed `address already in use`.
  - **The branch, its pick in 10000–19999:** 20 of 20, none needing a retry, every port in the range. **Main:** 14 of 20; 6 failed `address already in use`.
- **Two runs launched at once, 20 pairs, no load:** with `$RANDOM`, as 0d1bd134 picked, both runs picked the same port first in 3 pairs, each saved by the retry; bash 3.2 seeds `$RANDOM` from the time and the pid. From `/dev/urandom`: in none.

**Not taken.** A check that DATABASE_URL reaches the container. A listener on 127.0.0.1 or 0.0.0.0 bound after the pick and before the start lets the start succeed and takes the command's connections; readiness, asked inside the container, still passes (reproduced: the command's `SELECT 1` timed out). Below the port-0 ranges only a bind of that port by number can do it, as only one can take a port from the start.
