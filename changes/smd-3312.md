## Changelog

`deploy/canary.sh` runs the canary's own board-sync, so a canary upgraded in place keeps its own copy of the board. It reads Linear with a `LINEAR_API_KEY` of the canary's own, never stable's. That key is a Linear personal API key made with Read access alone, put in the canary's env file. Every `up` clears stable's key, and any other Linear key, from that file, each one said. `up` stops a running board-sync with the other writers, and (re)starts it on the new build once the smoke passes whenever the file holds a key of the canary's own. The canary never posts a finding: `LINEAR_COMMENT_API_KEY` is cleared from its file and held empty for every compose call `canary.sh` makes. **Upgrading an existing canary:** make a read-only Linear key for it, add it to its env file as `LINEAR_API_KEY`, and re-run `up --no-refresh` (a canary holding rows of its own; a plain `up` refreshes from stable) (SMD-3312).

## FORK

The canary runs its own board-sync, on a read-only key of its own (SMD-3312)

**What changed.**
- **`env_file own-fix`** clears, from the canary's env file, a `LINEAR_API_KEY` that is one of stable's Linear keys, its comment key included (by value, spaces aside), and every other `LINEAR_*` name in any letter case (the comment key pasted in, say). Each is said, as it already clears stable's `OB1_WORKER_KEY`. A `LINEAR_API_KEY` set on more than one line is refused, named, since compose reads only the last.
  - **Why the canary's own key:** a Linear personal key can write unless it was made read-only, and board-sync runs the checkout's `db/`, which on the canary is an unreleased build's. The canary is its own deployment, with its own keys (SMD-2872).
  - The exact name alone is a read key, since compose reads `${LINEAR_API_KEY}` by its case.
  - `CANARY_DROPPED` keeps SMD-2882's whole `LINEAR_*` prefix, so a newly made file holds no Linear key.
- **The shell.** canary.sh unsets every `LINEAR_*` (and `OB1_WORKER_KEY`) from its own environment, beside stable's other keys, since compose reads a shell value over the env file. `canary_compose` also sets `LINEAR_COMMENT_API_KEY=""`, a second layer beside the clearing.
- **`up`, the writers.** A running board-sync is stopped by name within its 60 s grace, beside the servers and the sleep worker, before the canary's Postgres is touched. Before, it was refused ("stop it first"). The workers profile is still refused.
- **`up`, step 6.** After the smoke, whenever the canary has a key of its own (read once before the stop, as compose reads the file, spaces aside; a failed read stops the run), board-sync is (re)created on this checkout with `--profile board-sync up -d --no-deps --force-recreate`, every board-sync container of the project removed first. The message names the checkout, whose `db/` it runs.
  - A start that fails says so itself, naming the removed container.
  - One stopped by this run with no key of the canary's own since is turned off, its container removed, said, so it stays off past a reboot.
  - With no key, the run says the canary runs no board-sync and how to give it one.
- **A failed run says board-sync is stopped:** in the four messages that advise (an in-place canary with no relations, the refresh, the in-place migrate, the `/health` wait), as each names the sleep worker, and in the EXIT trap's message otherwise. It promises a restart only when the canary has a key of its own, and otherwise says how to give it one.
- **`down`** names the board-sync profile, so its container goes with the rest.
- **`deploy/README.md`**: the writers paragraph, the left-out list, and board-sync as step 5, before the connector, the order the code runs them, with the key's line, turning it on with `up --no-refresh`, checking it syncs, and turning it off.
