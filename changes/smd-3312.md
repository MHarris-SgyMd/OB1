## Changelog

`deploy/canary.sh` runs the canary's own board-sync, so a canary upgraded in place keeps its own copy of the board. The canary's env file now carries `LINEAR_API_KEY`, board-sync's read key, and every other Linear key is still left out. `up` stops a running board-sync with the other writers and (re)starts it on the new build once the smoke passes, whenever the file holds the key. The canary never posts a finding: `LINEAR_COMMENT_API_KEY` is held empty for every compose call. **Upgrading an existing canary:** add a `LINEAR_API_KEY` to its env file, stable's or a read-only key of its own, and re-run `up` (SMD-3312).

## FORK

The canary runs its own board-sync, read-only (SMD-3312)

**What changed.**
- **`CANARY_DROPPED`** leaves out `LINEAR_(?!API_KEY\Z)[A-Z0-9_]*`, not every `LINEAR_*`. `LINEAR_API_KEY` is carried into a newly made canary env file. `LINEAR_COMMENT_API_KEY`, and any Linear key added later, stays out: the prefix rule SMD-2882 asked for still holds.
- **`canary_compose`** sets `LINEAR_COMMENT_API_KEY=""` in the shell, which compose reads over the env file. A comment key an operator pastes into the canary's file never reaches its board-sync, so `db/board-findings.ts` never posts from a canary.
- **`up`, the writers.** A running board-sync is stopped by name, within its 60 s grace, beside the servers and the sleep worker, before the canary's Postgres is touched. Before, it was refused ("stop it first"). The workers profile is still refused.
- **`up`, step 7.** After the smoke, whenever the canary's env file holds a `LINEAR_API_KEY`, board-sync is (re)created on this checkout with `--profile board-sync up -d --no-deps --force-recreate`. A container compose did not make is removed first.
  - One stopped by this run whose key has since gone from the file is left stopped, said.
  - With no key, the run says the canary runs no board-sync and how to start it.
- **The drift note** names `LINEAR_API_KEY` when the canary's file lacks it. A read key of the canary's own, which can differ from stable's, is no drift.
- **`down`** names the board-sync profile, so its container goes with the rest.
- **The EXIT trap** names a board-sync left stopped by a failed run.
- **`deploy/README.md`**: the env file's left-out list and a step 6 for board-sync.

**Why.** The canary is upgraded in place with `up --no-refresh` (SMD-3154) and never refreshed, because it holds rows of its own. The refresh was what copied stable's board rows, so on 2026-10-25 the canary's board-sync watermark was still 2026-10-13T13:35:32Z:
- its SMD-2288 row read Backlog (the ticket went Done that day);
- SMD-3309, filed that day, was not there;
- its "what next" named SMD-2287, whose PRs had all merged.

A canary soaking a release on a stale board can't show what the build does with the board's current state. Under SMD-2872, the canary is its own deployment and takes its inputs from the sources themselves.

**Held.** CI's "A canary stands beside the stack from deploy/canary.sh":
- stable's `.env` carries dummy `LINEAR_API_KEY`, `LINEAR_COMMENT_API_KEY` and `LINEAR_OTHER_KEY`. The canary's file holds the first alone, and the first `up` starts board-sync on it with `LINEAR_COMMENT_API_KEY` empty;
- the first `up --no-refresh`, with the key taken out of the canary's file, stops board-sync for the migration, leaves it stopped, said, and its drift note names the key;
- the second, with a read key of the canary's own and a pasted comment key, brings board-sync back as a new container on the canary's key, the comment key empty. Its drift note doesn't name the read key.

`bash -n`, shellcheck (`-S warning`) and the pinned actionlint pass.
