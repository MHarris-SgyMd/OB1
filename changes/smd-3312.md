## Changelog

`deploy/canary.sh` runs the canary's own board-sync, so a canary upgraded in place keeps its own copy of the board. It reads Linear with a `LINEAR_API_KEY` of the canary's own, never stable's. That key is a Linear personal API key made with Read access alone, put in the canary's env file. Every `up` clears stable's key, and any other Linear key, from that file, each one said. `up` stops a running board-sync with the other writers, and (re)starts it on the new build once the smoke passes whenever the file holds a key of the canary's own. The canary never posts a finding: `LINEAR_COMMENT_API_KEY` is cleared from its file and held empty for every compose call `canary.sh` makes. **Upgrading an existing canary:** make a read-only Linear key for it, add it to its env file as `LINEAR_API_KEY`, and re-run `up` (SMD-3312).

## FORK

The canary runs its own board-sync, on a read-only key of its own (SMD-3312)

**What changed.**
- **`env_file own-fix`** clears, from the canary's env file, a `LINEAR_API_KEY` that is stable's (its value, spaces aside) and every other `LINEAR_*` name in any letter case (the comment key pasted in, say). Each is said, as it already clears stable's `OB1_WORKER_KEY`.
  - **Why the canary's own key:** a Linear personal key can write unless it was made read-only, and board-sync runs the checkout's `db/`, which on the canary is an unreleased build's. The canary is its own deployment, with its own keys (SMD-2872).
  - The exact name alone is a read key, since compose reads `${LINEAR_API_KEY}` by its case.
  - `CANARY_DROPPED` keeps SMD-2882's whole `LINEAR_*` prefix, so a newly made file holds no Linear key.
- **`canary_compose`** sets `LINEAR_COMMENT_API_KEY=""` in the shell, which compose reads over the env file. This is a second layer, beside the clearing.
- **`up`, the writers.** A running board-sync is stopped by name within its 60 s grace, beside the servers and the sleep worker, before the canary's Postgres is touched. Before, it was refused ("stop it first"). The workers profile is still refused.
- **`up`, step 6.** After the smoke, whenever the file holds a `LINEAR_API_KEY` (after step 2's clearing, the canary's own), board-sync is (re)created on this checkout with `--profile board-sync up -d --no-deps --force-recreate`. A container compose did not make is removed first.
  - A start that fails says so itself, naming the removed container.
  - One stopped by this run with no key of the canary's own since is left stopped, said.
  - With no key, the run says the canary runs no board-sync and how to give it one.
- **A failed run says board-sync is stopped:** in the four messages that advise (an in-place canary with no relations, the refresh, the in-place migrate, the `/health` wait), as each names the sleep worker, and in the EXIT trap's message otherwise.
- **`down`** names the board-sync profile, so its container goes with the rest.
- **`deploy/README.md`**: the writers paragraph, the left-out list, and board-sync as step 5, before the connector, the order the code runs them.

**Why.** The canary is upgraded in place with `up --no-refresh` (SMD-3154) and never refreshed, because it holds rows of its own. The refresh was what copied stable's board rows, so on 2026-10-25 the canary's board-sync watermark was still 2026-10-13T13:35:32Z:
- its SMD-2288 row read Backlog (the ticket went Done that day);
- SMD-3309, filed that day, was not there;
- its "what next" named SMD-2287, whose PRs had all merged.

Turning that around also settled the case-folding leak of `linear_api_key`, the untested `\Z` anchor, a stable key built from the shell blocking the first `up`, both brains on one key's rate limit, and a stale copy of a rotated key (caught: cold-read)
- A comment key pasted into the canary's file reached a board-sync started by hand with that file. Every `up` now clears it (caught: cold-read)

- The README still said board-sync was refused, and the header listed Linear's keys among those of profiles the canary never runs. The docs listed board-sync after the connector, against the code's order (caught: cold-read)

**Held.** The new `own-fix` code was run on dummy files through `podman compose config`:
- stable's key (spaces aside), a pasted comment key and a lower-case Linear key are each cleared, said;
- the canary's own key and empty values are left alone;
- applied through `env-file.ts` and read back, nothing is named;

CI's "A canary stands beside the stack from deploy/canary.sh":
- **the first `up`:** stable's dummy `LINEAR_API_KEY`, `LINEAR_COMMENT_API_KEY` and `LINEAR_OTHER_KEY` are none of them carried, and the run says the canary runs no board-sync;
- **the root-URL `up`,** with the canary's own key plus a pasted comment key and `linear_other_key`: clears the two, said, keeps the own key, and starts board-sync on it with the comment key empty;
- **the first `up --no-refresh`,** with stable's key in the canary's file: clears it, said, stops board-sync for the migration and leaves it stopped, said;
- **the second,** with the canary's key back: brings board-sync back as a new container on it.

`canary_compose`'s empty comment key is now a second layer behind the clearing, held by review: CI can't paste a key after an `up` has cleared it.
