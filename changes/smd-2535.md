## Changelog

A request whose `Host` the URL parser refuses (`x:99999`, `[::1`, `brain.example.test:abc`), or that comes with no `Host` at all, now gets the answer a request at any `Host` but the public origin's gets: the -32001 refusal at `/mcp`, `ok` at `/health`, the REST core's 401. Before this fix it got a 500, through the stack's proxy too, which forwards those three as sent; a request with no `Host`, which reaches the server only off the proxy, was also routed wrong (a 405 at `/health`) (SMD-2535).

## FORK

A `Host` the URL parser refuses, or none — answered as at any `Host` but the public origin's, not a 500 or a wrong route (SMD-2535)

**What changed.**
- **`auth.ts` `queryOf(url)`** reads the query string without parsing the rest of the URL. For any URL Bun builds, it gives the same parameters as `searchParams` (`??key=` is a `?key` parameter in both). It is used by:
  - `presentedKeys`. The five `_shared/auth.ts` copies are synced, so three vendored servers' keyless refusal stops throwing too (see "Not here").
  - `oauth-edge.ts` `presentedKind`, so the edge and `auth.ts` agree on whether a `?key=` is there.
  - `rest/app.ts`'s query read.
- **`root.ts` `routable(req)`** (moved to `auth.ts` by SMD-2595). Both entries (`index.ts` and `api.ts`) hand their app this instead of the raw request.
  - A request whose URL will not parse is rebuilt at `REBUILD_ORIGIN`, `http://unparsable-host.invalid` (RFC 6761). Its path is joined to that origin as a string, so `//x` stays a path, and Bun normalises it as at a `Host` that parses.
  - The rebuild keeps the query, method, headers (the `Host` too), body and abort signal.
  - Any other request passes as it came.
  - Past the entry, every `new URL(req.url)` parses, `rawPath` included, and Hono routes on the real path.
- **`check-fork-consistency.ts` check 25** lets both entries import `routable`.
- **The edge (`atOrigin`)** judges by the `Host` header when there is one, as before, so such a request gets no challenge and no document. One change: a `Host` the URL parser cleans up to the origin's name (a Latin-1 spelling of a punycode name, a tab, a trailing `\`) now matches, where the parse used to throw. Both are public, so this opens nothing.

**Why.** Bun builds `req.url` from the `Host` header without checking it, which leaves one of two broken URLs:
- **One that will not parse.** This comes from a `Host` such as `x:99999`, `[::1`, `brain.example.test:abc` or `::1:8000`.
- **The bare request target** (`/mcp?key=…`). This comes from HTTP/1.0 with no `Host`, or a `Host` with userinfo, a path or a non-ASCII name.

`presentedKeys`, REST's query read and `rawPath` each threw, giving a 500. Hono also read a bare target's path wrong, giving a 405 at `/health` and `NO_ROUTE` at the REST core.

The proxy does not stop the first kind. Measured on Traefik v3.7.13, the stack's version:
- the four `Host` values above are forwarded as sent;
- userinfo, a path, a non-ASCII name and two `Host` headers each get Traefik's own 400;
- a missing `Host` is filled in.

**Not here.**
- **The vendored servers (SMD-2595, since fixed).** Seven called `new URL(req.url)` themselves:
  - `agent-memory-api` and `open-brain-rest` called it before their key check, so they still gave a 500.
  - `bio`, `metadata-norm` and `entity-extraction-worker` called it after the key check, so only their keyless refusal was fixed here.
  - `rest-api` and `smart-ingest` read keys from headers alone, so a keyed request there still gave a 500.

  `jev/serve.ts` and `deploy/orchestration/runner.ts`, both internal, parse `req.url` the same way.
- **A 400.** RFC 9112 §3.2 wants a 400 for an invalid `Host`, and for two `Host` headers. Such a request is answered as any other instead, as the ticket's Verify asks. HTTP/1.1 with no `Host` already gets Bun's own 400. Two `Host` headers are answered as the first, and the edge refuses the joined value, unchanged.

**Held by**
- **test-server [20]** (57 new, 685 in all). Raw-socket requests go to the real `index.ts` and `api.ts` entries at seven bad Hosts: the four above, no `Host`, userinfo, and a path. At each one:
  - the keyless refusal arrives, with no challenge;
  - a `?key=` call gets the tools;
  - `/health` answers `ok`;
  - the document is a 404;
  - the REST core gives a 401 keyless, and a 400 naming `limit` for a keyed `?limit=x`.

  The section also checks:
  - a hang-up mid-upload leaves no request pending on either server;
  - an abandoned tool call is logged;
  - `/x\..\health` is normalised;
  - `routable`'s own rules.
- **test-auth [13]** (24 new, 165 in all): `queryOf` against `searchParams` over 15 URLs that parse, the query of 7 that do not, and `presentedKeys` on two that do not.
- **test-rest [9]** (3 new, 271 in all): `createRestApp`, reached without the entry, reads the query of a URL that will not parse.
- **Through a real store** (test-e2e-sql 466 and test-rest-sql 149 unchanged): a 60 KB REST capture at a bad `Host` is stored byte for byte, and MCP search finds it.
- **Mutants**, each caught:
