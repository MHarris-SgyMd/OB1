## Changelog

The canary is a brain of its own on a port of its own: `deploy/canary.sh` no longer stands it at `/canary/mcp` on stable's origin with its servers on stable's mesh, and `deploy/compose.canary.yaml` is gone. `up` takes the canary's port from `--port` the first time and from the canary's env file after, which now holds the canary's own port, loopback address, tier and profiles; a `--port` that differs is written there, as are the canary's own settings into a file made before this, and stable's port is refused. A canary standing on stable's origin moves to its port at its next `up --port N`, on the same volume. Its access keys are its own: `up` mints a write key, its hash alone in `MCP_ACCESS_KEYS`, smokes and registers the connector with it, and leaves stable's keys, webhook secrets and plugin role password out, giving the plugin role a password of its own (SMD-2874, SMD-3032).

## FORK

The canary is a brain on a port of its own with keys of its own — path mode and `compose.canary.yaml` retired, stable's keys left out (SMD-2874 / 3032)

**What changed.**
- `deploy/canary.sh`:
  - one mode: the canary's own proxy and forwarder on `127.0.0.1:<port>`, at `/mcp`. Gone: the mode switch, `compose.canary.yaml`, `CANARY_STABLE_MESH`, the checks of stable's proxy (its `/canary` route, its mesh, its forwarder's port), the notes on stable's bind address and public origin reaching the canary, and the step that removed a canary's own proxy once it answered on stable's origin;
  - the port is `--port`, else the canary's env file's `SERVER_PORT`, read only from a file holding the canary's own tier, which `up` writes with the port: a file made before this holds stable's tier and the port stable had then. With neither, or with a file naming stable's port, `up` refuses with exit 2, naming `--port`. So it does when the port is stable's (its env file's `SERVER_PORT`, else 8000, or the port its forwarder publishes). Where the file holds another port, address, tier or profiles than the canary's own (a `--port` that differs, or a file made before this, which holds stable's), `up` writes the canary's own to a copy of the file (in place since PR 2, `deploy/env-file.ts`), reads the copy back through compose, and puts it in the file's place, written mode 600, the rest of the file unchanged; it says what it wrote;
  - the canary's env file, when `up` makes it, holds the canary's own `SERVER_PORT`, `SERVER_BIND="127.0.0.1"`, `OB1_TIER="canary"` and `COMPOSE_PROFILES=""`, not stable's, so compose given that file alone is the canary. canary.sh still hands compose these four in the shell. The file is checked as it is made, these four included;
  - a connector counts as the canary's on one of its ports: `--port`, the file's, the one its forwarder published when the run began and the one it publishes now, never stable's (its env file's port or the one its forwarder publishes) (a file made in path mode names stable's port: review pass 1). One left at `/canary/mcp` on stable's origin, or at stable's `/mcp`, is stable's URL. `up` names one at `/canary/mcp`, `up --connect` refuses it with the command that removes it, and `down` leaves both. One left at a port the canary moved off is named with the command that removes it, since from the next run that port is not the canary's;
  - the telemetry note (stable's collector, `lgtm.ob1.internal`, unreachable from the canary) is said whenever the endpoint names it, since no canary is on stable's mesh;
  - `bound_ip` and `host_of`, which read stable's bound address for path mode, are gone. Check 30's hint now points at `deploy/instance.ts`'s `portsFromBindings` for reading a binding's address from its JSON.
- `scripts/check-fork-consistency.ts`, check 28: `compose.canary.yaml`'s `OVERLAYS`, `FILE_NETWORKS` and `SERVICE_NETWORKS` entries are gone. Its eight probes are kept against `compose.grafana-port.yaml`, so each rule they caught keeps its catch: U+2029, a verbatim `!<…binary>` key, a `%TAG` directive, two `!!binary` flow keys, a second network key external by another's name with a shadow answering as `mcp.ob1.internal`, a second key alone, and a `!override` on a service's networks.
- `.github/workflows/fork-checks.yml`:
  - "Every published port binds loopback" renders the canary as canary.sh runs it, `compose.yaml` alone under `open-brain-canary`: every network its own and none external, one port, its forwarder's, on `127.0.0.1:8011`. With every profile, nothing is on a default network, and every network is the canary's;
  - "The proxy loads only the held route tables" renders `compose.yaml` under the canary's project with no overlay;
  - the refusals step drops the old-stable-proxy and proxy-off-mesh refusals. It adds no port, stable's port, and a canary file naming stable's port. It refuses a connector left at `/canary/mcp`, naming it, with no canary file and with one naming stable's port, and a `down` on that file leaves connectors at stable's `/canary/mcp` and `/mcp` alone. Its other refusals pass `--port 8011`;
  - the canary's life:
    - `--port 8011 up --connect`: the file holds the canary's own four settings. The connector is at `127.0.0.1:8011/mcp`. Every canary container is on `open-brain-canary_*` networks alone, and stable's mesh holds no canary container;
    - an `up` with no `--port` runs on the file's port;
    - the root connector's note says `--connect`;
    - a fourth `up`, on `--port 8012`: the port is written to the file (mode 600, compose reading 8012), the forwarder moves, 8011 is freed, and a connector left there is named. Then 8013 is edited into the file by hand, and an `up` with no `--port` moves there and names the connector left at 8012;
    - teardown leaves a connector at `/canary/mcp` alone, and its last `down` finds the canary's connector by the file's port.
- `deploy/compose.yaml`: Postgres's and the networks' comments no longer name the overlay.
- `deploy/README.md`:

**What changed in PR 2 (the canary's own keys; SMD-3032).**
- `deploy/canary.sh`:
  - left out of the canary's file with the other profiles' secrets: `MCP_ACCESS_KEYS`, `MCP_ACCESS_KEY`, `OB1_FORWARDER_KEY`, `OB1_HOOK_SECRETS`, `OB1_PLUGIN_DB_PASSWORD`, `OB1_CANARY_KEY`;
  - `env_file own-fix` says what a file needs to be the canary's own, and `apply_own` writes it, both on the file being made and on a standing one at every `up`:
    - its port, address, tier and profiles (PR 1);
    - none of stable's access key hashes in `MCP_ACCESS_KEYS` (read as `parseKeyRecords` reads them), and a write key of its own, minted (`<canary>:write:<sha256>`), the raw key in `OB1_CANARY_KEY`;
    - no raw key of stable's (`MCP_ACCESS_KEY`, `OB1_WORKER_KEY`, `OB1_FORWARDER_KEY`) and no webhook secret of stable's;
    - a plugin role password of its own wherever stable sets one;
  - written with `deploy/env-file.ts`'s `setEnvValues`, one line a setting, replaced in place, through a symlink. The values reach it on stdin, never argv. A copy is read back through compose, which must find nothing left to fix, before it takes the file's place. `up` says each fix, by name, never a secret's value;
  - `up` smokes and registers the connector with `OB1_CANARY_KEY`; `OB1_SMOKE_KEY` is not read, and `--connect` no longer needs the smoke. `up` needs `bun` on PATH;
  - every `up` also sets the plugins' login role (`ob1_plugins`) to the file's `OB1_PLUGIN_DB_PASSWORD` where the canary's Postgres has one, beside the `postgres` password: migrate.ts makes that role once and never changes its password;
  - stable's keys and their secrets set in the shell are unset for the run, as `POSTGRES_PASSWORD` is; a key setting spanning lines is refused; of `OB1_HOOK_SECRETS` (space-separated `plugin=secret` pairs) stable's pairs go and the canary's own stay; a connector at the canary's URL is told to re-run with `--connect` when this `up` gave the canary keys of its own.
- `deploy/env-file.ts`: a CLI, `bun --no-env-file deploy/env-file.ts set FILE`, the values as one JSON object on stdin.
- CI, the canary's life:
  - stable's `.env` gains a dummy plugin role password and webhook secret, taken out after the first `up`;
  - the canary's file must hold its own minted key alone (no key hash of stable's), a plugin role password of its own, and no webhook secret of stable's;
  - stable's smoke key must list nothing at the canary, and the canary's nothing at stable, each listing at its own;
  - `tier.ts --diff` replays with each brain's own key;
  - the hand-edited `up` also has stable's keys added back to `MCP_ACCESS_KEYS`, and must take them out by count, keeping the canary's key and one `MCP_ACCESS_KEYS` line;
  - neither key nor password is printed.
- `deploy/README.md` ("Its own keys"), `db/README.md` (`--compare` with a key for each) and `docs/one-brain-per-stack.md` follow.

**Why.** SMD-2872's ADR: each brain is self-contained, and brains never join each other's networks. In path mode, names resolved across the two brains: `mcp.ob1.internal`, `api.ob1.internal` and `auth.ob1.internal` reached stable from the canary. Stable's proxy carried the canary's route. The canary was reached wherever stable was, and check 28 spent eight probes and three tables policing the join. Port mode already ran the canary behind its own proxy. Stable's tier routes (PR 3) and the canary's own keys (PR 2) follow.

**Not taken.**
- Naming a connector that still holds stable's key after a failed upgrade `up` (the next `up` has nothing left to fix): it would hash the connector's header from `claude mcp get`. The dogfood's connector sits at `/canary/mcp`, which has its own note.
- Minting the canary a `forward`-scope key: its `OB1_FORWARDER_KEY` is cleared and none minted, as no compose service reads one yet; SMD-2287 PR 5, which wires the MCP server's forwarder into compose, gives the canary one.
- `canary.sh`'s own port-free check, which lists running containers alone: it predates this change, and `deploy/instance.ts check` reads stopped containers' bindings too.
- A MAJOR bump: no released URL stops answering. After PR 2's next `up`, stable's keys open the canary no more, so a canary connector or `db/bench-live.ts` default holding stable's key is refused there: operator tooling on an unreleased tier, not a released surface. Stable's proxy still routes `/canary/mcp` (PR 3 is where that question is argued), a standing path-mode canary keeps answering until its operator runs `up --port N`, and its connector at `/canary/mcp` moves when the operator removes it (`claude mcp remove --scope user open-brain-canary`) and runs `up --connect`, which refuses to replace it until then. An `https://` connector at `/canary/mcp` gets the generic refusal without that note (accepted: canary.sh registers `http://` alone).
