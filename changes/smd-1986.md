## Changelog

enhanced-mcp's three search tools find thoughts on this fork: `brain_search_thoughts` (both modes) and `search_thoughts_text` hand `match_thoughts` and `search_thoughts_text` the caller's `metadata_filter` alone — the `exclude_restricted` and date keys they folded into it were read as a metadata containment no thought satisfies, so every search answered no matches — and apply the restricted tier (by the column, looked up by id in semantic mode, where `match_thoughts` returns none) and the date bounds to the rows (SMD-1986).

## FORK

enhanced-mcp's search tools stop sending the tier and the dates as containment keys — every search on this fork answered no matches, and the client-side tier filter in semantic mode compared a column the function never returned (SMD-1986)

**What changed.** `integrations/enhanced-mcp/index.ts`: `brain_search_thoughts`
in text mode passes `p_filter: metadataFilter` to the sidecar's
`search_thoughts_text`, in semantic mode `filter: metadataFilter` to this
fork's `match_thoughts`, and the `search_thoughts_text` tool passes `{}` —
the caller's `metadata_filter` is the one containment the argument is for.
The restricted tier is dropped from the rows by the `sensitivity_tier`
COLUMN: the text function returns it; `match_thoughts` returns id, content,
metadata, similarity, created_at and score (041's `RETURNS TABLE`), so
`tiersOf(ids)` reads the column for the returned ids in one `.in()` query
before the filter. The date bounds are `dateWindow` — each an ISO 8601 date or
date-time held to that shape, read as UTC unless it carries an offset, a
date-only value that day's midnight UTC — and `withinDates`, one comparison
of instants, applied in both modes; text mode had none before. Both tools on
`search_thoughts_text` render a page through `textPage`: the function ranks
and pages before the filters apply, so `total` is the function's count with
the hidden rows, `has_more` is `offset + page.length < total`, a line's
number is the row's place in the page, and a page the filters emptied says
"No matches on this page; more follow." rather than a false end. The README's
known-limitations note describes this behaviour and names `count_thoughts`
for an exact count under a window.

**Why.** SMD-1798's drive of the server on the SQL shim found all three
tools answering "No matches found." on a brain holding the thought the suite
had just captured through `brain_capture_thought`. The tools built a `filter`
of `exclude_restricted: true` plus `start_date` / `end_date` when given —
"ignored by older RPC versions but used by versions that support them", the
comment said — and both functions here read that argument as
`t.metadata @> filter` (014; the sidecar's `coalesce(p_filter, '{}')`). No
metadata holds `exclude_restricted`, so nothing matched. Removing the keys
alone would have leaked restricted rows: the client-side filter the tools
kept, `row.sensitivity_tier !== "restricted"`, compared `undefined` in
semantic mode — `match_thoughts` returns no such column — and text mode had
no client-side filter at all; the sidecar's `search_thoughts_text` has no
tier argument. The README promises "all tools that expose thought content
skip `sensitivity_tier = 'restricted'` rows"; the column, not the metadata a
capture's caller can set, is what that means.

**Held.** `extensions/test-writes.ts`, the enhanced-mcp block: the three
pins that expected zero results are thirteen assertions that expect the
captured thought. A restricted twin is planted at the captured thought's own
vector with text the query matches, so every search that finds the capture
must also drop the twin — the mutant that removes the three tier filters
fails three assertions by name. `metadata_filter: { nothing_has_this: true }`
answers nothing in both modes (the containment kept); an `end_date` in the
past hides the capture and a `start_date` in the past shows it, in both
modes; a date-only bound is its midnight UTC, held against a Postgres cast
of the same instant; an offset-bearing bound is the instant it names (the
string comparison dropped the capture), a zone-less one is UTC; `yesterday`,
`Dec 25, 2025` and an inverted window are refused by name; with `limit: 1`
the later-planted twin is the whole page in both tools, which say more
follow with `has_more: true`, and the next page holds the capture numbered
`2.`; text mode's `total` counts the hidden row. 323 assertions on a
throwaway Postgres.

**Not taken.** Reserved keys the SQL reads out of `p_filter`: a mixed bag
in one JSON argument, and this fork's `match_thoughts` is frozen with 1.1.0
(001..051, check 17c) — a tier argument there is a migration, not a patch.
Over-fetching in text mode: offsets shift under a page's hidden rows; the
exact answer is a SQL argument (below).

**Follow-ups.** SMD-2054 (High): `integrations/rest-api`'s `POST /search`
LEAKS restricted thoughts in semantic mode — its row filter compares the
`sensitivity_tier` that `match_thoughts` never returns, the no-op this ticket
found — and in text mode sends `exclude_restricted: true` inside `p_filter`
the same way and answers no matches. SMD-2055:
`search_thoughts_text` takes `p_exclude_restricted`, `p_start` and `p_end`
so text mode's page and total are exact, with the three callers moved.

**Upstream status:** not sent — the call-site change is honest on
upstream's schema too, but the fork dropped parity (SMD-1924).
