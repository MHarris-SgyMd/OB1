## Changelog

Effective priority's default weights live in one function, `ob1_priority_defaults()` (SMD-4194, migration 128), so a retune replaces that function alone. Search's `priority_weight` divides by the brain's own `ob1_priority_span()`, the largest effective priority the defaults allow, read with each ranked search, in place of a constant in the server. No effective number changes.

## Record

`effective_priority` reads its default weights from `ob1_priority_defaults()`, and search's blend reads its scale from the brain's `ob1_priority_span()`, so a retune is one function and the server keeps no copy (SMD-4194)

**Why.** `effective_priority`'s default weights were a constant inside its plpgsql body.
- Migrations 122, 125 and 127 each copied the whole body, and SMD-4177 changed only the constant.
- The server kept their largest sum as `PRIORITY_SPAN` (5.8) to scale search's `priority_weight` blend. A server could divide by a scale its brain doesn't use, and each retune touched the body plus six hand-kept copies.

**What changed.** The maintainer chose on 2026-11-09: an IMMUTABLE defaults function changed only by a migration, and the scale read per ranked search.
- **Migration 128** adds:
  - `ob1_priority_defaults()`: 127's weights as jsonb;
  - `ob1_priority_span()`: a critical level plus the largest urgency and unblocks terms, 5.8.

  It replaces `effective_priority` one last time, its defaults read from the function in place of the literal. Every rule, term, refusal, column and effective number is 127's.
- **The ranked search** reads the span with its window read, through the store's `prioritySpan()`, and only when a weight blends: a floor alone at weight 0 never divides. `PRIORITY_SPAN` is gone. A brain before 128 fails a ranked search with a hint naming the migration, as one before 122 does.
- **The docs and the search tool's description** name the two functions. They keep the numbers where a reader needs them.
- **The eval's `plannedNoteReads`** keeps its tenths: it states the expected answer independently, and the seeded run compares it with the database.

**Held.**
