## Changelog

The stack serves an operator GUI at `/dashboard`: `dashboard/`, a SvelteKit server and a client of the REST core, run as compose's `app` service from the server image. Sign in with a read or write access key to see the brain's counts and newest thoughts, its status and any thought; the key stays on the server (SMD-2280).

## FORK

The operator GUI at /dashboard — a SvelteKit client of the REST core, key sign-in held server-side, its first read views (SMD-2280)

**What changed in PR 1.**
- **`dashboard/`** (new), the GUI SMD-2282's decision 2 names: SvelteKit with `paths.base` `/dashboard` (absolute paths), built by adapter-node into one server with every package bundled.
  - `serve.ts` starts it on 8000. It sets the origin SvelteKit judges a form's post and the cookie's Secure by: `OB1_PUBLIC_ORIGIN` when it is sound (`server-portable/oauth-edge.ts`'s rule; an unsound one is warned of), else each request's `Host` with the proxy's `X-Forwarded-Proto`. A bad `OB1_REST_URL` exits 2.
  - Every page is a server-side load through `rest-client/` under the visitor's own key, with no forwarder key and no browser-side API or proxy:
    - `/` reads `thought_stats` and `list_thoughts` (the ten newest);
    - `/status` reads `brain_info` (version, commit, migrations, ledger, sizes, counts, heartbeats, the proposal queue, unread fields);
    - `/thoughts/<id>` reads `fetch`;
    - `/health` asks nothing.
  - A 401 from the core ends the session; any other refusal is the page's error with the core's status and code.
  - **Sign-in** is by key: `GET /v1/whoami` must name `thought_stats`, so a capture-only key gets a 403. Key sign-in is off while `COMPOSE_PROFILES` names `auth` (ADR decision 16).
  - **The session is server-side** (`session.ts`): the cookie (`Path=/dashboard`, httpOnly, Lax, a day, Secure on https) carries 32 random bytes. The key and its scope live in a map capped at 1,000 sessions. Sign-out deletes the entry.
  - `hooks.server.ts` walls every path but `/signin` and `/health`. Pages are `no-store`, `DENY`-framed and `no-referrer`, with a CSP of `self` plus SvelteKit's hashed inline script, and no web font.
  - The nav links to Grafana where an overlay reaches it (`GRAFANA_LINK`).
  - Also `smoke.ts` and `README.md`.
- **`server-portable/Dockerfile`:** a `dashboard-build` stage (the REST client's and the GUI's installs, `vite build`); the image gets `dashboard/build`, `serve.ts` and `package.json`. `.dockerignore` keeps the GUI's build output and smoke out.
- **`deploy/compose.yaml`:**
  - the `app` service: the server image, `bun --no-install ../dashboard/serve.ts`, mesh alone as `app.ob1.internal`, read-only with a tmpfs `/tmp`, no capability, `no-new-privileges`, a healthcheck on `/dashboard/health`;
  - the `dashboard` router (priority 30, path kept);
  - the proxy waits on `app`.
- **The Grafana overlays** each set `GRAFANA_LINK` on `app`: `/grafana/`, or `/grafana/` on the loopback origin.
- **`scripts/release-artifacts.ts`:** the release overlay pins `app` to the release's server image; `release.yml` holds it.
- **`scripts/check-fork-consistency.ts`:**
  - check 28's `PROXY_ROUTE_TABLE`, `PROXY_SERVICE` (the wait), `CONFINEMENT`, `SERVICE_NETWORKS` and `OVERLAYS` learn `app`, and `GRAFANA_APP_ENV` holds the overlays' one key by value;
  - check 32's `RESTART_POLICIES` holds `unless-stopped`.
- **`rest-client/index.ts`** exports `DEFAULT_REST_URL`, which `mcp-server/index.ts` defined; both servers read it.
- **`.github/workflows/fork-checks.yml`:**
  - the portable-server job installs and svelte-checks `dashboard/`;
  - the full-stack job drives `smoke.ts` through the proxy, and its mesh membership, pinned-Bun and daemon-restart checks name `app`;
  - `declared()` names the overlays' `GRAFANA_LINK`.
- **Docs:** `SETUP.md` (eight services, step 5 "Open the dashboard"), `deploy/README.md` (the service, its reach, the `/dashboard` route) and the ADR's As built line.

**Why.** SMD-2282 made the REST core the contract and the GUI one of its clients. No dashboard on this fork served from the stack. The SvelteKit one scraped the MCP server's prose. `-next` and `-pro` sit on a gateway SMD-1931 retired. None showed the operator's own reads.

**Held.**
- `bun scripts/check-fork-consistency.ts` passes.
- `bun run check` (svelte-check) reports 0 errors. `rest-client` and `mcp-server` typecheck, and `bun test-client.ts` passes.
- Scratch stack `ob1-2280` on podman 6.1.4, built from this tree: `smoke.ts` 31 of 31, from the host through the forwarder and from inside `front` through the proxy. That covers the wall, the refused keys, a forged cookie, a cross-site sign-in, the cookie's attributes, the three pages and a 404. It also checks that the key is in no page, header, `__data.json` or any of 21 script modules, and that the old cookie is no session after sign-out.
- Probed by hand:
  - a client's `X-Forwarded-Proto: https` is replaced by Traefik (an https form origin is refused);
  - `COMPOSE_PROFILES=auth` gives no key field and a 403 with no cookie;
  - `OB1_PUBLIC_ORIGIN=https://brain.example` gives a Secure cookie and refuses an http origin;
  - an http LAN origin is warned of, and the GUI is served;
  - `OB1_REST_URL=ftp://x` exits 2;
  - `docker stop` takes 0.26 s.
- CI's "Every published port binds loopback" and "The proxy loads only the held route tables" were rehearsed on the scratch tree, plain `docker compose` with CI's env: both reach their ends.

**Not taken.**
- **The sealed-cookie session** of the SvelteKit dashboard: the ADR keeps tokens server-side, and the Verify line asks that no cookie hold a key. The cost is that a restart signs everyone out.
- **An image of its own:** a release install has no checkout to build one from. The server image already carries the MCP server the same way.
- **A browser-side API route** (the old `/api/mcp` proxy): every page loads on the server, so the analysis's open question (an open proxy or a per-screen allow-list) does not arise.
- **`dashboard/` in check 18's tsc list:** it is checked by svelte-check, which loads SvelteKit's generated types.
