## Changelog

A capture-only key can no longer alter another key's thought by re-capturing its text. Before, the re-capture merged the key's metadata and `source` into the existing row, appended an update event in its name and moved `updated_at`, so a key that could guess a thought's text could relabel it. Migration 080 adds `p_payload.recapture` to all three `upsert_thought` forms, and the server sends `"keep"` for a capture-only key: a capture that lands on an existing row writes nothing to it, except a vector onto a row that has none (one update event, the metadata untouched, and the windows such a row may hold dropped unless its label is the vector's). A write key's re-capture still merges, as before. The reply still carries the id the session hook supersedes its own summary with; four of its notes no longer tell a capture key that a re-capture regenerates or merges anything, since its re-capture does neither. The fix needs the server and the migration both, in either order: until both are in, a capture key's re-capture still merges (SMD-2539).

## FORK

A capture-only key's re-capture leaves the row it lands on (SMD-2539)

**What changed.**
- **Migration 080.** `p_payload.recapture` on all three `upsert_thought` forms:
  - `'keep'`: a capture that lands on an existing row writes nothing to it — no metadata merge, no event, no `updated_at`, no vector refresh, no window written or dropped, no lineage row. The provenance stays 035's, not written, and the return's `supersedes` is the row's.
  - The one exception is a vector onto a row that has none: an update event carrying the vector's presence alone (the row's metadata on both sides, nothing the payload declares), projected with the caller's vector and label. So `updated_at` moves, the audit row names the capture key, and `thoughts_record_vector_lineage` (061) records the vector as for any vector. No windows are written; windows such a row holds go by 022's rule unless its label is the arriving vector's.
  - Absent, a JSON null or `'merge'` is the merge as before; anything else is refused before the write.
  - A fresh text is captured as before, `'keep'` or not, windows included. Each form's return keeps its keys: the 2-argument form's `{id, fingerprint}`, the 3-argument form's `{id, fingerprint, existed, supersedes}`, and the 4-argument form's with `chunks` added, 0 under `'keep'` on an existing row.
  - 080 carries 073's 2- and 3-argument bodies and 061's 4-argument one, each with `ob1:recapture-keep-leaves-the-row`. It refuses to apply without 060, 061 or 073.
- **The server.** `core/writes.ts` `capture` sends `recapture: "keep"` for a key that cannot read (the capture scope) and nothing for a write key, through `captureEnvelope` on both stores.
- **The reply.** A capture key is told nothing new: `existed` and the pointer were already withheld from it (SMD-1298), so a re-capture's reply is a fresh capture's, ids aside — its chunk count and notes speak of what the capture computed, not of what landed. Four notes change for it:
  - the head-window note says what a new thought was stored with, and that text already captured keeps its own vector (or takes this one if it had none) and gets none of the windows; it names the re-embed pass alone for a head window's vector;
  - the situating-context note says a new thought stores its windows so and text already captured gets none of them, and names the model alone;
  - the tagging-refused note says text already captured keeps its tags, with no marker merged in;
  - the tagging-failed note says this capture's tagging failed, not that a thought was saved, and that the placeholders are a new thought's.
- **Preflight.** `atomic capture` reads the sentinel in all three forms and warns naming 080 when the 3-argument body is 073's (080 not applied, or 073 re-applied by hand), when the 2-argument body lacks it, and when the 4-argument body lacks it (007, 013 or 061 re-applied by hand).
  - 080 is now `upsert_thought`'s last definer, so a remedy that names 073 names 080 after it, and one that names 060 or 061 names both — unless the ledger shows the migrator will apply them anyway.
  - Where 080's guard would refuse, the remedy is another file: a ledger before 073 is told 073 (or 061 before that), with the migrator applying the rest; a brain whose ledger cannot say, with a body from before 073, is told 073 then 080.
  - A cause names only the files the ledger does not record (a brain at 079 was told 061 and 073 were unapplied).
- **Before upgrading.** Upgrade both halves; either order is safe, and until both are in a capture key's re-capture merges as it did before.
  - Migration first: a server from before this change sends no word, so 080 changes nothing for it. Its preflight says only that the ledger reaches past its tree.
  - Server first: it sends `"keep"`, which the older bodies ignore. Its preflight warns on `atomic capture` that 080 is not yet applied, and the image's entrypoint starts the server anyway (exit 0).
  - A session-capture hook user loses one thing: the hook's re-capture of its own summary no longer repairs that row (tags after a failed extraction, a head-window vector, windows and their blurbs). A write key's re-capture repairs all of them; a re-embed pass the vector, windows and blurbs; `update_thought` what an edit sets.

**Why.** The capture scope promises a key it cannot alter a thought it did not write. A re-capture of text that is already a thought lands on that row (003's fingerprint, 035's existing-row path), and that path merged the payload's metadata over the row's. SMD-2473's first review pass showed it against the real server: a capture key re-sent a writer key's text with `source: "codex"` and a key of its own, and the writer's row took both. That label is what a `source:` egress term gates the passes on (SMD-1941) and what SMD-1297's planned per-source weight would read. A vector under another model also replaced the row's and dropped its windows (022), and the 4-argument form replaced the windows outright.

**Decisions** (the maintainer's, at the plan stage):
- **Where:** in the write function, under the fingerprint lock it already takes, not as a read in the server before the write. A pre-read leaves a window in which another key's first capture of the same text lands and the merge happens anyway.
- **A write key keeps the merge,** the behaviour before 080. It holds `update_thought`, so the merge grants it nothing.
- **A capture key's own text is left too:** one rule, no ownership read. The cost: its re-capture no longer repairs its own row either — tags after a failed extraction, a head-window vector, windows and their blurbs — which is why the four notes change.
- **A vectorless row takes the vector.** Under 060's log that is an event credited to the capture key, with `updated_at` moving; the maintainer chose it over leaving the row out of semantic search until a re-embed pass. A long text attached this way has no windows until a re-embed pass writes them.

**Not taken.**
- **The id a re-capture returns** still tells a capture key that holds an earlier id whether the text stands there (SMD-2554).
- **A fresh capture's own metadata** can still change how other keys' thoughts read: a capture key's row carrying `source: "linear"` and a ticket's head facets becomes that ticket's head (SMD-2617, High). Its text also feeds the shared entity graph (SMD-2618). Neither is the re-capture path this change closes.
- **Timing.** A `'keep'` re-capture does less work than a fresh capture. SMD-2473 left timing out of the oracle rule, and so does this.
- **The halves out of step.** While this server runs against a brain without 080, the older bodies merge, so a capture key's notes can overstate: a failed extraction's placeholders do reach an existing thought. Preflight warns in that state.
- **A brain whose ledger cannot say and whose bodies predate 061** is told 073 then 080, which 073's guard refuses (it needs 061). The remedy before this change had the same gap, and the guard's hint names `bun migrate.ts --reapply`.
- **The PostgREST two-step fallback** runs when the form the store called is missing — the 3-argument one (before 004, which preflight fails) or the 4-argument one (whose presence preflight does not check). Its plain UPDATE writes the vector onto an existing row whatever the word: SMD-2605.

**The version.** MINOR: a migration. Type security: it closes an alteration the capture scope rules out. A write key's capture and its replies are unchanged; a capture key's reply differs only in the four notes above.
