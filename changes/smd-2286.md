## Changelog

With the `auth` profile on, the REST core accepts the authorization server's access tokens beside access keys. A token must be issued for the REST core itself (`<origin>/api`); a token for `/mcp` is refused there. Its scopes act as the access key that holds the same: `brain:write` as a write key, `brain:read` as a read key, `brain:capture` as a capture key. The caller is `oauth:operator` for a sign-in, or `oauth:<id>` for a service client, and that is the name egress terms, the actor filter and the audit row see. A token holding none of the brain's scopes, or `brain:read` with `brain:capture` and no `brain:write` (which no access key holds), is answered 403 `insufficient_scope`. With the authorization server down, the signing keys the REST core read last go on serving for ten minutes, so a token issued before the outage is served to its end; a token it has no keys for gets a 503, never a pass. Refresh tokens now rotate on every use and last 14 days unused within their 30-day grant. A spent one presented again within 10 s is honoured each time, since MCP clients refresh several times at once; later, it revokes the grant. A stolen token replayed inside those 10 s forks the chain undetected, the price of the window. The authorization server refuses `brain:read` with `brain:capture` and no `brain:write` where a request asks for it, and its consent page says what each scope allows. A service client may not be named `operator`, and names its scope in each token request. **Upgrading:** a service in `OB1_AUTH_SERVICES` with `brain:read+brain:capture` and no `brain:write`, or named `operator`, now stops the authorization server starting; change it first (SMD-2286).

## FORK

**What changed.**
- **`server-portable/oauth-token.ts`** (new). `auth.ts` is untouched: its copies are byte-synced into the vendored servers.
  - `tokenSettings(env)`: on a configured stack with a sound origin (`oauth-edge.ts` `edgeSettings`), the issuer `<origin>/auth` and the audience `<origin>/api`; else null, and no token is accepted.
  - `checkerOver(settings, keys)` checks issuer, ES256, `typ: at+jwt`, `sub` and `exp` with jose, and the audience as exactly `<origin>/api` (jose alone accepts a list holding it). A key reader that fails for any reason but a missing or doubled `kid` answers `unavailable`, not `invalid`.
  - `keyScopeOf(scope)`: `brain:write` is write, `brain:read` alone is read, `brain:capture` alone is capture, and anything else is null: the outcome `scope`.
  - The principal: `oauth:<sub>`, a `keyHash` that is sha256 of `oauth\n<issuer>\n<sub>` (the agent registry's 64-hex key and job ownership's), and `act = oauth:<act.sub>` from an exchanged token. A `sub` or `act.sub` outside `[A-Za-z0-9._~-]{1,128}` is refused, so a log line, an egress term and the audit row carry it as it is.
  - `cachedKeys(read, now)`, the key set kept (jose's remote set reloads on every request once stale and never falls back, review pass 1; restated as one read gate in pass 2), on a monotonic clock:
    - a read is needed with no set, a stale one (600 s, the access tokens' lifetime) or one lacking the `kid`; a request that needs one joins any in flight, else one is made unless one was tried within 30 s;
    - once the set is stale and reads fail, the outage counts from the first moment both hold, and the set serves 600 s from then: every token issued before the outage, to its end, however long the set sat idle and whatever failed while it was fresh;
    - a missing `kid` after a successful read is the token's fault (`invalid`); one with no read made is `unavailable`, so a new signing key never sends a client to sign in.
  - `jwksOver(url)` reads the set (a 200 with a `keys` array, no redirect, 2 s), and `remoteChecker(settings)` is `checkerOver` over `cachedKeys(jwksOver("http://auth.ob1.internal.:3000/auth/jwks"))`.
- **`server-portable/rest/app.ts`** `caller()`: no key matched and a bearer of a JWT's shape (`oauth-edge.ts` `JWT_SHAPE`, now exported): the deps' `tokens()` check.
  - Invalid: 401 `UNAUTHORIZED`, `credential: "token"`, `WWW-Authenticate: Bearer error="invalid_token"`.
  - No key scope: 403 `FORBIDDEN`, `credential: "token"`, `insufficient_scope` (RFC 6750 §3.1, the proof of concept's A8).
  - Unavailable: 503 `BUSY`, `credential: "token"`, `Retry-After: 30` (the MCP server's wait for a token while the authorization server is down).
  - Then the registry's word, as for a key. A token's own `act` stands beside the forwarder slot, whose key is still checked.
  - Keys come first, and a bearer that is not a JWT's shape is never handed to the check.
- **`server-portable/api.ts`**: `tokens()` builds one remote checker per issuer and audience, read from the environment per request as the keys are. `server-portable/package.json` pins `jose` 6.2.12, `deploy/auth`'s pin.
- **`server-portable/rest/openapi.ts`**: the 401, the 403 (whoami's and the plugins' included), the 503 and the bearer scheme describe tokens. `rest-client/` is regenerated.
- **`deploy/auth/layout.ts`**:
  - `keyScopeOf` and `noKeysScope`, the same rule as the REST core's; `test-rest.ts` holds the two equal over all 32 sets of the server's scopes.
  - `OB1_AUTH_SERVICES` refuses `brain:read+brain:capture` without `brain:write`, and the id `operator`, since a client-credentials token's `sub` is its client id.
  - `GRANT_TTL_S` (30 days), `REFRESH_IDLE_S` (14 days) and `refreshTtl(iiat, now)`: 14 days, cut to what is left of 30 since the chain's first token (`iiat`, which oidc-provider carries across rotations), never under a second.
  - `REFRESH_REUSE_GRACE_S` (10 s, the maintainer's choice in pass 2, down from 60) with its price stated, and `chainRotates(iiat, now)`: a chain 30 days old rotates no more.
- **`deploy/auth/store.ts`**: a refresh token spent less than 10 s ago is found unspent, each time it is presented, so the library rotates it again instead of revoking the grant, and a later `consume` keeps the first spend's time, so the grace never extends. The library's revoke-on-replay branch is hard-coded (`refresh_token.js`), so the store is where the grace can live.
- **`deploy/auth/server.ts`**:
  - `ttl.RefreshToken` is `refreshTtl`, and `rotateRefreshToken` is `chainRotates`, so `refreshTtl`'s 1 s floor never stretches a chain past 30 days.
  - The interaction handler sends a request whose scopes no key holds back with `invalid_scope` before a sign-in or a consent, and the exchange refuses such a narrowing. A set the library narrows from what a client holds (a refresh, client credentials, a grant built over two consents) still reaches the REST core, which answers it 403.
  - `OPERATOR` comes from layout.ts; the break-glass mentions here and in `limits.ts` name SMD-2280.
- **`deploy/auth/pages.ts`**: the consent page lists each brain scope it asks for in an access key's words (`SCOPE_MEANS`).
- **`deploy/auth/restart-check.ts --tokens <scope>`**: inside the `auth` container, a public client, the operator's sign-in, the consent, the code for an `/mcp` token, and its exchange as `mcp` for a REST-core token; prints `{ mcp, api }`.
