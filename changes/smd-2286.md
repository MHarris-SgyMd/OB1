## Changelog

With the `auth` profile on, the REST core accepts the authorization server's access tokens beside access keys. A token must be issued for the REST core itself (`<origin>/api`); a token for `/mcp` is refused there. Its scopes act as the access key that holds the same: `brain:write` as a write key, `brain:read` as a read key, `brain:capture` as a capture key. The caller is `oauth:operator` for a sign-in, or `oauth:<id>` for a service client, and that is the name egress terms, the actor filter and the audit row see. With the authorization server down, a token issued before the outage is served to its end, and one the REST core has no keys for gets a 503, never a pass. Refresh tokens now rotate on every use and last 14 days unused within their 30-day grant; a spent one presented again revokes the grant. The authorization server refuses `brain:read` with `brain:capture` and no `brain:write`, which no access key holds, and its consent page says what each scope allows. A service client may not be named `operator` (SMD-2286).

**What changed.**
- **`server-portable/oauth-token.ts`** (new). `auth.ts` is untouched: its copies are byte-synced into the vendored servers.
  - `tokenSettings(env)`: on a configured stack with a sound origin (`oauth-edge.ts` `edgeSettings`), the issuer `<origin>/auth` and the audience `<origin>/api`; else null, and no token is accepted.
  - `checkerOver(settings, keys)` checks issuer, audience, ES256, `typ: at+jwt`, `sub` and `exp` with jose. A key reader that fails for any reason but a missing or doubled `kid` answers `unavailable`, not `invalid`.
  - `keyScopeOf(scope)`: `brain:write` is write, `brain:read` alone is read, `brain:capture` alone is capture, and anything else is null and refused.
  - The principal: `oauth:<sub>`, a `keyHash` that is sha256 of `oauth\n<issuer>\n<sub>` (the agent registry's 64-hex key and job ownership's), and `act = oauth:<act.sub>` from an exchanged token. A `sub` or `act.sub` outside `[A-Za-z0-9._~-]{1,128}` is refused, so a log line, an egress term and the audit row carry it as it is.
  - `remoteChecker(settings)`: jose's remote key set at `http://auth.ob1.internal.:3000/auth/jwks`, kept 600 s (the access tokens' lifetime), read again at most every 30 s, with a 2 s timeout.
- **`server-portable/rest/app.ts`** `caller()`: no key matched and a bearer of a JWT's shape (`oauth-edge.ts` `JWT_SHAPE`, now exported): the deps' `tokens()` check.
  - Invalid: 401 `UNAUTHORIZED`, `credential: "token"`, `WWW-Authenticate: Bearer error="invalid_token"`.
  - Unavailable: 503 `BUSY`, `credential: "token"`, `Retry-After: 30` (the MCP server's wait for a token while the authorization server is down).
  - Then the registry's word, as for a key. A token's own `act` stands beside the forwarder slot, whose key is still checked.
  - Keys come first, and a bearer that is not a JWT's shape is never handed to the check.
- **`server-portable/api.ts`**: `tokens()` builds one remote checker per issuer and audience, read from the environment per request as the keys are. `server-portable/package.json` pins `jose` 6.2.12, `deploy/auth`'s pin.
- **`server-portable/rest/openapi.ts`**: the 401, the 503 and the bearer scheme describe tokens. `rest-client/` is regenerated.
- **`deploy/auth/layout.ts`**:
  - `keyScopeOf` and `noKeysScope`, the same rule as the REST core's; `test-rest.ts` holds the two equal over all 32 sets of the server's scopes.
  - `OB1_AUTH_SERVICES` refuses `brain:read+brain:capture` without `brain:write`, and the id `operator`, since a client-credentials token's `sub` is its client id.
  - `GRANT_TTL_S` (30 days), `REFRESH_IDLE_S` (14 days) and `refreshTtl(iiat, now)`: 14 days, cut to what is left of 30 since the chain's first token (`iiat`, which oidc-provider carries across rotations), never under a second.
- **`deploy/auth/server.ts`**:
  - `ttl.RefreshToken` is `refreshTtl`, and `rotateRefreshToken: true`. The library revokes the grant when a spent token is presented again.
  - The interaction handler sends a request whose scopes no key holds back with `invalid_scope` before a sign-in or a consent, and the exchange refuses such a narrowing.
  - `OPERATOR` comes from layout.ts.
