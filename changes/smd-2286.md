## Changelog

The MCP server built on the REST core (`mcp-server/`) accepts the authorization server's tokens at `/mcp`, at a scan's job links and at the worker mirrors. It trades each one at the authorization server (RFC 8693) for a token the REST core accepts, and never sends a client's token on. It needs `OB1_AUTH_SECRET_MCP` beside `COMPOSE_PROFILES` naming `auth` and the REST core's `OB1_PUBLIC_ORIGIN`, and warns at the start when they disagree. A refused token is 401 `invalid_token`, or 503 while the authorization server is down, so a client is never sent to a sign-in that cannot finish; scopes that reach no operation are 403 `insufficient_scope`. It serves `/mcp` once its compose service lands; until then the `/mcp` that serves still refuses tokens. **Upgrading:** on a stack with the `auth` profile, a raw access key with dots sent as `Authorization: Bearer` reads as a token here; send it as `x-brain-key` or `?key=` (SMD-2286).

## FORK

The MCP server trades each OAuth token at the hop for the REST core's — a client's token is never sent on, and its refusals are OAuth's (SMD-2286)

**What changed.** The second half of SMD-2286; change 337 made the REST core accept the authorization server's tokens.
- **`mcp-server/exchange.ts`** (new):
  - An OAuth token is traded (RFC 8693) at the authorization server's token endpoint on the mesh, `http://auth.ob1.internal.:3000/auth/token`, as the `mcp` client (`OB1_AUTH_SECRET_MCP`), for `<origin>/api`.
  - Its claims are read first, refusing only: another issuer, any audience but exactly `<origin>/mcp`, expired or exp-less.
  - A trade is cached by the token's sha256, never its subject, until 5 s before the exchanged token expires: one trade at a time per token, at most 1,024.
  - The authorization server's exchange checks the token, not its grant, so a grant revoked there is refused once the client's access token expires (at most 600 s).
  - Unavailable: the authorization server away, limiting (429), stalling, or answering a 200 with no token. Each is logged at most once a minute, its reason in this server's words. This server's client refused is a fault with its fix.
  - Only an error code's letters and underscores reach a log line.
- **`mcp-server/app.ts`**:
  - On a stack with a public origin, a JWT-shaped bearer that no key form also carries is never sent to the REST core as a key (`keysToSend`).
  - A dotted value in a key form stays a key. With no origin there is no OAuth, and every bearer is a key, as before.
  - The token is traded at `/mcp` and at the keyed routes at the origin's `Host` (job links, mirrors). The exchanged token rides every call as a bearer (`credOf`); `/health`'s record stays a key's, as the REST core's is.
  - Answers, at `/mcp` and the keyed routes alike (`tokenRefusal`):
    - refused: 401 `invalid_token`, or 503 while the authorization server fails its health check;
    - no key scope: 403 `insufficient_scope`, `scope="brain:read"`;
    - unavailable, the REST core keyless, or a keyed route's 2.5 s deadline passed: 503, `Retry-After: 30`;
    - a revoked subject: the revoked key's refusal;
    - any 401 from the REST core for a token traded for it a moment ago (it checks none, or another origin's): this stack's misconfiguration, a fault with its fix.
  - Elsewhere on a stack with an origin, a token is no caller and gets the edge's answer; before, it was also sent to the REST core as a key.
- **`mcp-server/index.ts`** builds the exchange on a configured stack with the secret. It warns at the start when the secret is missing there, and when the secret is set but the stack is not configured or its origin is unsound.
- **`rest-client`**: a per-call `token`, sent as `Authorization: Bearer` (a key beside it wins).
- **Docs:**
  - `mcp-server/README.md`;
  - the ADR's "As built (SMD-2286 PR 2)" and its amendment line;
  - the preview's end, now SMD-2287 PR 5, in `deploy/README.md`, `docs/one-brain-per-stack.md`, `FORK.md`, `server-portable/index.ts` and `oauth-edge.ts`;

**Why.** Before this, the MCP server sent a client's OAuth token to the REST core's whoami as a key: the passthrough the MCP authorization spec forbids. No OAuth client could use it.

**Not taken.**
- A limit on trades: one per request with a token, as the key's whoami was; the authorization server's 429 is a retry.
- Tokens on `/health`: the REST core's record is a key's.
- An OAuth user revoked in the registry is told to request a new key: the wording follows per-connector identity (SMD-3064).
- A read-only grant sees no write tool rather than a step-up: the design.
- A 4xx whose body fails to read for a reason other than a timeout stays this server's misconfiguration, since a retry would hide a wrong URL.
- The health probe behind a 503 can run past a keyed route's deadline once per its 30 s cache.
