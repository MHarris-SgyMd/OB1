## Changelog

With the `auth` profile on, the REST core accepts the authorization server's access tokens beside access keys. A token must be issued for the REST core itself (`<origin>/api`); a token for `/mcp` is refused there. Its scopes act as the access key that holds the same: `brain:write` as a write key, `brain:read` as a read key, `brain:capture` as a capture key. The caller is `oauth:operator` for a sign-in, or `oauth:<id>` for a service client, and that is the name egress terms, the actor filter and the audit row see. A token holding none of the brain's scopes, or `brain:read` with `brain:capture` and no `brain:write` (which no access key holds), is answered 403 `insufficient_scope`. With the authorization server down, the signing keys the REST core read last go on serving for ten minutes, so a token issued before the outage is served to its end; a token it has no keys for gets a 503, never a pass. Refresh tokens now rotate on every use and last 14 days unused within their 30-day grant. A spent one presented again within 10 s is honoured each time, since MCP clients refresh several times at once; later, it revokes the grant. A stolen token replayed inside those 10 s forks the chain undetected, the price of the window. The authorization server refuses `brain:read` with `brain:capture` and no `brain:write` where a request asks for it, and its consent page says what each scope allows. A service client may not be named `operator`, and names its scope in each token request. Revoking `oauth:operator` in the agent registry bans it until the public origin changes, since no sign-in changes its identity; a leaked token is answered at the authorization server. The MCP server built on the REST core (`mcp-server/`) trades each OAuth token sent to `/mcp` for one the REST core accepts, cached per token, with `OB1_AUTH_SECRET_MCP`; it serves `/mcp` once its compose service lands, and until then the `/mcp` that serves still refuses tokens. **Upgrading:** a service in `OB1_AUTH_SERVICES` with `brain:read+brain:capture` and no `brain:write`, or named `operator`, now stops the authorization server starting; change it first (SMD-2286).

## FORK

The REST core accepts the authorization server's tokens — a sign-in's or a service's token acts as the access key scope it names, refresh tokens rotate within a 10 s reuse grace, and `mcp-server/` trades a client's token for one at the hop (SMD-2286)

**What changed.**
- **`server-portable/oauth-token.ts`** (new; `auth.ts`, byte-synced into the vendored servers, is untouched):
  - `tokenSettings(env)`: on a configured stack with a sound origin, the issuer `<origin>/auth` and the audience `<origin>/api`; else null, and no token is accepted.
  - `checkerOver(settings, keys)`:
    - First, on the claims read unverified (refusing only), it refuses another issuer, any audience but exactly `<origin>/api`, and an expired or exp-less token, so each is 401 even with no keys to be had.
    - Then jose checks the ES256 signature, `typ: at+jwt`, issuer, `sub` and `exp`.
    - A key reader's failure, other than a missing or doubled `kid`, is `unavailable`.
  - `keyScopeOf`: `brain:write` is write, `brain:read` alone read, `brain:capture` alone capture; anything else is the outcome `scope`.
  - The principal: `oauth:<sub>`, a `keyHash` of sha256 `oauth\n<issuer>\n<sub>` (the registry's key and job ownership's), and `act = oauth:<act.sub>` from an exchanged token. A `sub` or `act.sub` outside `[A-Za-z0-9._~-]{1,128}` is refused.
  - `cachedKeys(read, now)`, the key set kept on a monotonic clock:
    - A read is needed with no set, a stale one (600 s, the access tokens' lifetime) or one lacking the `kid`. A request that needs one joins any in flight, else reads unless one was tried within 30 s.
    - Once the set is stale and reads fail, the set serves 600 s from then, so every token issued before the outage lives to its end.
    - A missing `kid` after a successful read is `invalid`; with no read made it is `unavailable`.
  - `jwksOver(url)` (a 200 with a non-empty `keys` array, no redirect, 2 s) and `remoteChecker(settings)` over `http://auth.ob1.internal.:3000/auth/jwks`.
- **`server-portable/rest/app.ts` `caller()`**: when no key matched and the bearer has a JWT's shape (`oauth-edge.ts` `JWT_SHAPE`, exported), the token check runs; keys still come first.
  - Answers, each with `credential: "token"`: 401 `UNAUTHORIZED` `invalid_token`; 403 `FORBIDDEN` `insufficient_scope` (RFC 6750 §3.1, the POC's A8); 503 `BUSY` `Retry-After: 30`; a revoked subject's 401 `REVOKED`.
  - A token's own `act` stands beside the forwarder slot, whose key is still checked.
- **`server-portable/api.ts`**: `tokens()` builds one remote checker per issuer and audience, read per request from the environment as the keys are. `restApp()` takes an optional token check for a suite. `jose` 6.2.12 is pinned (deploy/auth's pin).
- **`server-portable/agents.ts`**: `recordedScope` sends an `oauth:` subject's scope as none, so tokens of two scopes from one subject never rewrite its row in turn.
- **`rest/openapi.ts`** describes the token answers (401, 403 at whoami and the plugins too, 503, the bearer scheme); `rest-client/` is regenerated.
- **`deploy/auth/layout.ts`**:
  - `keyScopeOf` and `noKeysScope` follow the REST core's rule; `test-rest.ts` holds the two equal over all 32 sets.
  - `OB1_AUTH_SERVICES` refuses read+capture without write, and the id `operator` (a client-credentials token's `sub` is its id).
  - `refreshTtl` is 14 days, cut to what is left of 30 since the chain's `iiat`.
  - `chainRotates` stops rotation at 30 days.
  - `REFRESH_REUSE_GRACE_S` is 10 (the maintainer's choice), with its price stated.
- **`deploy/auth/store.ts`**: a refresh token spent less than 10 s ago (never a negative age) reads as unspent, so the library rotates it again rather than revoking the grant; a later `consume` keeps the first spend's time. The library's revoke-on-replay branch is hard-coded, so the store is where the grace can live.

**What changed in PR 2: the exchange at the hop.**
- **`mcp-server/exchange.ts`** (new): an OAuth token traded (RFC 8693) at the authorization server's token endpoint on the mesh as the `mcp` client (`OB1_AUTH_SECRET_MCP`) for `<origin>/api`. Its claims are read first, refusing only: another issuer, any audience but exactly `<origin>/mcp`, expired or exp-less. A trade is cached by the token's sha256 (never its subject) until 5 s before the exchanged token expires, one trade at a time per token, at most 1,024; a grant revoked at the authorization server is refused once the client's access token expires (at most 600 s), since its exchange checks the token, not the grant.
- **`mcp-server/app.ts` `standingOf`**: on a stack with an origin, a JWT-shaped bearer is never sent to the REST core as a key, a key form beside it or not; a dotted value in a key form stays a key, and with no public origin (no OAuth) so does any bearer. On a stack with an origin, a raw key with dots sent as a bearer reads as a token: send it as `x-brain-key` or `?key=`. At the public resource of a configured stack it is traded and the exchanged token rides every call (`credOf`); so it is at the keyed routes at the origin's `Host` (job links, mirrors), while `/health`'s record stays a key's. Refused, there and at `/mcp`: 401 `invalid_token`, or 503 while the authorization server is away (and at a keyed route not checked within its deadline); no key scope: 403 `insufficient_scope`, `scope="brain:read"`; the authorization server away, limiting, stalling or cut short, or the REST core keyless: 503, `Retry-After: 30`; a revoked subject: the revoked key's refusal; this server's client refused, or the REST core refusing a token traded for it (checking none, or another origin's): a fault, logged with its fix; an unanswered trade is logged once a minute. Elsewhere on a stack with an origin a token is no caller and gets the edge's answer (before, it was also sent as a key). The start warns when the secret is set but the stack trades nothing.
- **`rest-client`**: a per-call `token`, sent as `Authorization: Bearer` (a key beside it wins).
- **`mcp-server/index.ts`** builds the exchange on a configured stack with the secret, and warns when the secret is missing. Docs: `mcp-server/README.md`, the ADR's MCP server as built, `deploy/README.md`'s preview (now until SMD-2287 PR 5), `oauth-edge.ts`'s header.

**Why.** Before this, the REST core checked no token at all, refresh tokens ran on the library's defaults, and scopes like read+capture had no key meaning; the MCP server sent a client's token to the REST core as a key. Step 3 (the GUI's sign-in, break-glass, the revocation page) moved to SMD-2280, since nothing serves `/dashboard`; `mcp-server/` serves `/mcp` with SMD-2287 PR 5.

**Not taken.**
- The refusal reason in the request line: it holds no free text (SMD-3110).
- `insufficient_scope` headers on per-operation 403s: REST clients are not step-up MCP clients, and PR 2 words its own.
- An `agentId` on a token's `act`, and tokens on `/health`.
- Closing the library's narrowing paths to read+capture: they fail closed at the REST core.
- Refusing an exchange to an empty scope: harmless, and A8's expectations ride on it.
- A limit on trades: one per request with a token, as the key's whoami was; the authorization server's 429 is a retry.
