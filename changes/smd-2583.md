## Changelog

The stack's services leave compose's default network for networks of their own. Postgres is on an internal `data` network, beside only what connects to it, so a container on `egress` cannot reach it, by name or by address. The proxy and the authorization server each have an outward network nothing else joins. A command that ran a container on `open-brain_default` now names `open-brain_data`, plus `open-brain_egress` when it calls a model, and `deploy/tier.sh` defaults to both. `deploy/canary.sh` runs the canary on an env file of its own, `.env.canary.local`, which its first `up` writes from stable's as compose reads it. It has a database password of its own, which every `up` sets on the canary's database, and leaves out the other profiles' secrets. That is one way: once it has run, a canary.sh from before this change cannot log in to the canary's database, and `/canary/mcp` stays down until this one runs again. An upgraded stack keeps its old `open-brain_default` network, unused; `docker network rm open-brain_default` removes it (SMD-2583).

## FORK

The network move — Postgres on an internal network of its own, every service on the networks it needs, nothing on compose's default network, and the canary on a database password of its own (SMD-2583)

**What changed.**
- **`deploy/compose.yaml`** names every service's networks, so compose makes no default network and nothing joins one:
  - `mesh` (internal, as before): the proxy, the MCP server, the REST core and the authorization server.
  - `data` (internal, new): Postgres, and only what connects to it — the migrator, the two servers, board-sync, the workers, the import runner and its role's one-shot. It is Postgres's only network.
  - `egress` (outward): the provider callers (the two servers, board-sync, the workers, the import runner, n8n), and the stack's Ollama and Jev, which fetch their weights there and are called there by name.
  - `auth-egress` (outward, new): the authorization server's alone. It was on `egress` alone before; on the shared one it would reach Ollama, Jev, n8n and the runner.
  - `edge` (outward, new): the proxy's alone, where its port is published.
- **`deploy/compose.host-ports.yaml`** gives Postgres a lone outward network, `postgres-port`, since a container on internal networks alone publishes no port (measured on podman 6).
- **`deploy/compose.tiers.yaml`** follows, as check 27 generates it from compose.yaml (`tierStack()` now carries the networks its services join, and `tierHazards()` refuses a fixed name on any of them).
- **`deploy/canary.sh`** refreshes on each project's database network, read off its Postgres container: `data`, or `default` for a stable from before this change, so a new canary still refreshes from an old stable. It refuses before changing anything when stable's Postgres is on neither.
- **The canary's own env file.** `deploy/canary.sh` runs the canary on `.env.canary.local`, beside stable's unless `--canary-env-file` names another (never stable's own file, by any path). The root `.gitignore`'s `.env.*.local`, older than this change, ignores it in any checkout, a release checkout of stable's included; check 13 refuses a tracked one.
  - **Written at the first `up`** from stable's file as compose reads it, mode 600, by value: every setting's value is rendered through a service's environment, read back as JSON with compose on a bare environment (so the shell's variables play no part), and written `NAME="…"` with `\\ \" \$ \n` escaped, which compose reads back exactly (measured). Left out: the database password, which is a fresh one, and the secrets of the profiles the canary never runs (`OB1_AUTH_*`, `N8N_*`, `OB1_RUNNER_*`, `OB1_WORKER_KEY`, `LINEAR_API_KEY`), in any letter case. Stable's comments are not carried. It is kept only if compose reads every value in it as stable's, no left-out setting is set, the password is its own, and no value carries stable's database password (a `DATABASE_URL` holding it, say); a refusal names the setting, never the value. It is made in a temporary `.env.canary-<pid>-<n>.local` beside it, created with noclobber, which the EXIT trap removes however the run ends.
  - **The password, at every `up`.** The canary's database takes the file's password, through psql on the container's socket, from the exec's environment, never a command line. So a canary made before this change on stable's password takes its own.
  - **Stable's changes.** A change to stable's file no longer reaches the canary, and `up` names each setting that differs (names, never values), from the same reading.
  - **`down`** also removes a pre-move canary's `open-brain-canary_default`, which compose no longer names, when compose made it for that project and nothing is on it.
  - **The refresh** takes stable's password from stable's file through tier.sh's new `--from-env-file`, and the canary's from its own.
  - **The shell's `POSTGRES_PASSWORD` is unset** in canary.sh, since compose would let it win over the canary's file.
- **`deploy/tier.sh`** defaults `--network` to `open-brain_data,open-brain_egress`: Postgres, and the model a replay embeds with. Its `--from-env-file` refuses an empty value, and refuses while the shell sets `POSTGRES_PASSWORD`, which would win over both files.
- **`deploy/auth/provision.ts --self-check`** holds the authorization server to `mesh` and `auth-egress`, and no other service to `auth-egress`.
- **The orchestration eval kit's overlays** put their services on `data` and `egress`, and the sealed variant resets n8n's networks beside its `network_mode`.
- **Docs:** deploy/README.md's reachability tables, its tier and canary sections and "Adding a service"; the ADR's "as built" notes (`docs/operator-surface-tiers.md`); the evals' and the dashboard's run commands.

**Why.** The ADR's "Two networks" puts every service on an internal mesh, and gives outward reach only to the services that call a provider. As built, Postgres, Ollama, Jev, board-sync, n8n and the runner were on compose's default network alone. The REST core, the MCP server and the proxy were there too, beside them. So every container in the stack could dial `postgres:5432`, and "being on the mesh is not trust" had no second network to hold it.

**Where the build departs from the ADR**, each in its "as built" notes:
- **Postgres is not on the mesh.** A canary of another project joins stable's mesh (SMD-2294). Compose names every container by its service name on each network it joins, so on the mesh stable's Postgres would answer the canary's `postgres:5432`. Until this change the canary also ran on stable's env file, with stable's database password. `data` is per project, and canary.sh's canary never joins stable's. (The three-brain stack, compose.tiers.yaml, is one project: its tiers share one `data`, as they share one password.)
- **The MCP server is on `data` and `egress`.** It still embeds and writes for itself; it can be mesh-only once it calls the REST core (SMD-2287).
- **n8n is on `egress`, not the mesh.** It reaches `server:8000` and `orchestration-runner:8090` there, where no tier's `server` answers. Its calls by mesh name wait for it to join the mesh.

**Held.**
- **Check 28** (`scripts/check-fork-consistency.ts`) holds each file's networks and each service's exactly (`FILE_NETWORKS`, `SERVICE_NETWORKS`), now naming every compose.yaml service; a compose.yaml service it does not name fails, since one that names no network lands on `default`. Its `OVERLAYS` entry lets compose.host-ports.yaml set Postgres's `networks`, and `PROXY_SERVICE` has `edge` and `mesh`. New probes, each caught by the `networks` rule:
  - `data` given a route out;
  - Postgres on the mesh too;
  - the authorization server on the shared `egress`;
  - n8n back on `default`;
  - a new service under a profile of its own that names no network;
  - compose.host-ports.yaml putting Postgres on `egress`, or naming `postgres-port` as another project's network.
- **Check 27** gains a probe with `data` given a fixed name, which every tier would share.
- **CI's "Every published port binds loopback"** renders each stack with every profile its file defines (read with `config --profiles`), as compose makes it:
  - no service on `default`;
  - Postgres on `data` alone;
  - each network's members exactly, the authorization server's and the proxy's outward networks each holding that one service;
  - the same of the host-ports overlay, the three-brain stack and the canary.
- **CI's new "Postgres answers on the data network alone"**, on the running stack. A container on `open-brain_egress` alone cannot open a connection to Postgres, by name or by its `data` address. One on `open-brain_data` can, both ways, so the refusal has teeth.
- **CI's "The proxy loads only the held route tables"** declares the host-ports overlay's new paths.
- **CI's canary step** stands its first canary over a canary Postgres made the old way, on stable's password. It then holds:
  - `.env.canary.local` made, mode 600, gitignored, with a password of its own, stable's keys, and none of the auth step's `OB1_AUTH_*` lines;
  - the canary's password opening the canary's database, and stable's no longer opening it;
  - the canary's password not opening stable's database;
  - no stable password in the canary server's environment;
  - a setting added to stable's file named on the next `up`;
  - the canary's password in neither run's output.

**Measured after** (podman 6, a scratch project from compose.yaml, probes beside its Postgres):
- From `egress` alone, `postgres` does not resolve, and Postgres's `data` address times out. From `data`, both connect.
- With compose.host-ports.yaml:
  - the loopback port answers;
  - from `egress`, Postgres's `postgres-port` address and that network's gateway time out;
  - the host alias reaches the published port, which is the host's own, as it reaches any port the overlay publishes. The overlay's comment says so.
- A container on an internal network alone publishes no port, and its lookup of a name nothing holds fails rather than reaching the host's resolvers.
- With an internal network first (compose attaches in name order, so `data` before `egress`), a container's outward names resolve (api.linear.app, openrouter.ai, under Bun and musl) and an HTTPS call to api.linear.app gets through.
- The canary's env-file functions, lifted from canary.sh, on sample stable files:
  - kept, whole, with no secret left in them: plain quoted and `export`ed lines; `NAME: value` for the password and an auth secret; a lower-case left-out name; a BOM; a left-out value spanning into a kept-looking line, or ending in a comment-shaped line; a kept multi-line value holding left-out-looking lines; the names `null` and `TRUE`; values with `"`, `\\`, `$`, `$$` and a newline;
  - names set in the shell as well: the file's values are written, not the shell's;
  - refused, naming the setting: a `DATABASE_URL` holding stable's password, and a `PG` that `POSTGRES_PASSWORD=${PG}` reads; with the read-back made to pass, both are kept;
  - a file compose cannot read is refused, saying so;
  - the drift note names exactly the setting stable gained, and neither a left-out one nor `SERVER_PORT`, which canary.sh sets itself;
  - a HUP or a TERM while the file is made, at 0.05, 0.3 and 0.8 s, leaves neither the temporary file nor a half-made one.
- After review pass 3, on sample stable files: a value built from a shell variable, one holding a line that sets `POSTGRES_PASSWORD`, and a byte that is not UTF-8 are refused by name; a 5-character password inside `OB1_PUBLIC_ORIGIN` is not; the per-`up` guard refuses a file carrying stable's password, a value holding it, or no password; the password is read exactly past an injected line; `write` never creates the file it writes, so the EXIT trap's removal stands.
- After review pass 4: the guard refuses a canary password holding stable's, spanning lines or built from the shell, and finds stable's password in a value when stable builds it from the shell; a non-UTF-8 variable in the shell no longer fails a good file. Under bash 5.3 (a container), canary.sh's trap block removes the temporary file on a HUP or a TERM to the whole process group at 0.2, 0.7 and 1.2 s.
- `db_network_of`, lifted from canary.sh, on scratch containers: one on `<p>_data` and `<p>_postgres-port` gives `<p>_data`; one on `<p>_default` alone, as a stable from before this change, gives `<p>_default`; one on neither gives nothing, and `up` refuses.
- `.env.canary.local` and `.env.canary-1-2.local` are ignored by the root `.gitignore`'s `.env.*.local`, the rule a v1.7.0 checkout already has, and refused by check 13 when force-added.

After the passes, one tidy commit of what they cut for space, behaviour unchanged: the egress probe reads the server's image from compose as the later CI steps do, the evals' run note names the networks since the move, and two canary.sh comments match the code (the bare environment's variables; step 2's order since pass 5).

**Not taken.**
- **This Mac's podman and fresh networks.** The move creates networks the stack never had (the canary's `data` and `egress` at its next `up`, stable's `edge` at its upgrade), and fresh networks here have twice lost outward reach or port forwarding. That is the host's, not the change's; the dogfood's upgrade checks egress and the published port first, with the recovery recipe at hand.
- **CI running a canary Postgres moved from `default` to `data`.** CI's old-way canary is made with this compose.yaml, so on `data`; the move itself is compose recreating a container on new networks, and `db_network_of`'s `default` branch is measured above.
- **Docker's isolation of an internal network from another bridge**, which the cold reader doubted. On podman it holds (measured above); CI's new step is the first run on Docker, and fails if it does not.
- **The proxy on internal networks alone.** It needs an outward network to publish its port, so a name it dials that nothing holds still reaches the host's resolvers through `edge`. The fix is a forwarder holding the published port, which dials only addresses on its own front network. A forwarder that looked the proxy up by name would itself fall through while the proxy is down. That is this ticket's second PR.
- **n8n and the import runner on the mesh under mesh names.** n8n reaches both on `egress` with no collision, so moving them waits on the MCP server leaving `egress` (SMD-2287).
