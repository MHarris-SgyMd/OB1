## Changelog

A server that holds listen streams says how many are open: the MCP server's keyed `/health` gains `listen` (the streams open, the two bounds, and each caller's count), and the server sends the total as a metric, `ob1.mcp.listen_streams` (SMD-4458). No server holds a stream yet, so nothing the brain serves or sends changes.

## Record

A count of the listen streams a running MCP server holds, on keyed /health and as a metric: PR 1 (SMD-4458)

**What changed.**

- `mcp-server/app.ts`: on an app that holds streams, keyed `/health` answers `listen` beside the REST core's record and `oauth`: `open`, `max`, `perCaller`, and `callers`, one `{ name, open }` for each caller that holds a stream, the most first and equal shares in name order. It is read as the route answers, from the count the route already keeps for its two bounds. An app that holds none has no such field, whether it was given the streams' settings (as the entry is) or none.
- `server-portable/tracing.ts`: `observeListenStreams(read)` makes `ob1.mcp.listen_streams`, an up-down counter read when asked, unit `{stream}`, on the meter provider the API has, and answers false where making it threw. It is in `server-portable/` and not beside the server that uses it because that module holds the OpenTelemetry API, which `mcp-server/` has no dependency of its own on; and check 37 reads the instruments a dashboard may name from that directory's code alone.
- `mcp-server/index.ts` asks for it once the SDK is set up, and only where the server holds streams: before the SDK is set up the API's provider is its no-op, and an instrument made on it is never sent. It reads the app's count, and 0 once the stop's drain has ended, so that a stopped server's series ends on 0.
- `deploy/README.md` is the operator's account: what counts as open, what the metric and the field read and when, who is shown callers' names and what a name is, how a refusal's line is read against the field and what gives a place back, and when a stopped server's last point is not 0. Its account of a line's `code` names the two refusals, and its account of `outcome` says such a line is `refused`. `mcp-server/README.md` names the field and the metric and points there. `docs/mcp-listen-streams.md` says the count is built, and its list for SMD-4347's PR 2b carries what this change wrote that goes false the day streams are on.

**Why.** SMD-4347's PR 2a built what the MCP server needs to hold 2026-07-28 `subscriptions/listen` streams, with the capability off, and left two things an operator would want the day it is on. This is the first: only the stop's two lines counted the open streams, so a listen refused at a bound (`LISTEN_SERVER_FULL`, `LISTEN_CALLER_FULL`) had nothing to be read against. The maintainer set this ticket to come before that capability is turned on, and decided on 2026-11-19 where the count shows: on keyed `/health`, as a metric, and on a panel of the observability profile's dashboard (PR 2); with the per-caller table on keyed `/health` alone, shown to any key that may read the brain's record there, a read key included. The metric is the total, with no label for a caller: such a label would have no bound.

**Not taken.**

- Nothing was built around a stop whose flush cannot get its last export out. The 0 is the series' last point only where it can: where the collector does not answer, or is still answering the export before it when the flush's bound runs out, or the process is killed, the count before it stands for Prometheus's five minutes. And the 0 comes at the drain's end, the streams' close after the flush, 5 s later at most. PR 2's panel says so rather than queries around it.
- A stream is counted until its connection ends: a client that goes quiet without closing, and a key revoked since, keep their places, and at a bound those places refuse clients that are there. That is how SMD-4347 built the hold. The operator's page says it; no bound on a quiet stream was added (SMD-4493).
- A log line's `agent` is a caller's name cut to 64 characters, and `callers` has it whole, so a long name (a token's, with a client's URL) is matched by its start. The page says so; the field was not cut to match, which would have put two callers on one name (SMD-4494).
- No row holds: the entry's warning's words; that after a cut the 0 at the flush is the flag's and not the streams' own, already closed; that the field is read as the route answers and not as the request arrived. Keyed `/health`'s CORS headers were held by no row before this change, and are not now.
- `listen.open` is the shared count and `callers` the app's own map, which agree in the one app an entry builds; two apps given one count would not. A read that failed at an export would be said by no one, the SDK keeping its own errors; this one reads a flag and a number.
- Check 37 reads no up-down counter from the code yet, and reads the unit of no instrument where it is braced: PR 2's, which is what needs both.
