## Changelog

A server that holds listen streams says how many are open: the MCP server's keyed `/health` gains `listen` (the streams open, the two bounds, and each caller's count), and the server sends the total as a metric, `ob1.mcp.listen_streams` (SMD-4458). No server holds a stream yet, so nothing the brain serves or sends changes.

## Record

A count of the listen streams a running MCP server holds, on keyed /health and as a metric: PR 1 (SMD-4458)

**Why.** SMD-4347's PR 2a built what the MCP server needs to hold 2026-07-28 `subscriptions/listen` streams, with the capability off, and left one thing an operator would want the day it is on: only the stop's two lines counted the open streams, so a listen refused at a bound (`LISTEN_SERVER_FULL`, `LISTEN_CALLER_FULL`) had nothing to be read against. The maintainer set this ticket to come before that capability is turned on.

**Decided, by the maintainer, 2026-11-19.**

- Where the count shows: on keyed `/health`, as a metric, and on a panel of the observability profile's dashboard. This PR is the first two; the panel is PR 2.
- By caller: the per-caller table is on keyed `/health` alone, and any key that may read the brain's record there, a read key included, sees every caller's name. The metric is the total, with no label for a caller: such a label would have no bound.

**What changed.**

- `mcp-server/app.ts`: on an app that holds streams, keyed `/health` answers `listen` beside the REST core's record and `oauth`: `open`, `max`, `perCaller`, and `callers`, one `{ name, open }` for each caller that holds a stream, the most first and equal shares in name order. It is read as the route answers, from the count the route already keeps for its two bounds. An app that holds none has no such field, whether it was given the streams' settings (as the entry is) or none.
- `server-portable/tracing.ts`: `observeListenStreams(read)` makes `ob1.mcp.listen_streams`, an up-down counter read when asked, unit `{stream}`, on the meter provider the API has, and answers false where making it threw. It is in `server-portable/` and not beside the server that uses it because that module holds the OpenTelemetry API, which `mcp-server/` has no dependency of its own on; and check 37 reads the instruments a dashboard may name from that directory's code alone.
- `mcp-server/index.ts` asks for it once the SDK is set up, and only where the server holds streams: before the SDK is set up the API's provider is its no-op, and an instrument made on it is never sent. It reads the app's count, and 0 once the stop's drain has ended.
- `deploy/README.md` and `mcp-server/README.md` say what the field and the metric are, who is shown callers' names and what a name is, and when there is no count; `deploy/README.md`'s account of a line's `code` names the two refusals, and its account of `outcome` says such a line is `refused`. `docs/mcp-listen-streams.md` says the count is built.

**Found by the first review.** Two independent readers, each with a copy of the commit: one set against the count on a real process, one on every claim and on the rows' teeth. Neither found anything that reaches a running server: the entry as shipped matched its parent's keyed `/health`, metric names, lines and exit codes, and on a holding entry the count never disagreed with itself or with the streams open, through 900 churned listens, 256 at once and every abort they tried.

- **A throw as the count was made would have ended a holding server at its start.** It was asked for in a continuation of the SDK's start with no guard, where that start is written to lose its signals and not the server. Shown by a planted throw; nothing natural was found to make one. The function answers false where making it threw, and the entry says so. (caught: run-it; held: test-server [22])
- **The last point of a stopped server was the count still open.** After a drain that finished the streams are closed after the flush, which reads the count a last time: a stop with two open sent 2, on a series that never reports again, and a panel that sums the servers would have counted those two beside the next server's until the series went stale. It reads 0 once the drain has ended. (caught: run-it; held: test-mcp [8h])
- **A gauge, where the conventions give a count of open things to an up-down counter.** A gauge is their instrument for what is not summed over servers, and this is. Prometheus shows either as a gauge, and the name is unchanged. Check 37 reads no up-down counter from the code yet, and reads the unit of neither kind where it is braced: both are PR 2's, which is what needs them. (caught: cold-read; held: test-server [22])
- **The entry's count was seen only at 1 and 0,** so one that read 1 for any number of streams passed every row. The cut's row reads its 24 from an export before the stop. (caught: mutant; held: test-mcp [8h])
- **The operator's page said less than an operator needs, and one thing against itself:** a refused listen is `refused`, where the page's account of `outcome` says a JSON-RPC error inside a 200 is `ok`; a read key sees every caller's name, and a token is never shown the record; a token's name may hold a client's https URL, and a service's has no client; `callers` holds a name and its count and leaves out a caller with none; with the REST core away the route answers `ok` and there is no count; the metric is a sample each minute, and the field is the count when asked, not at the refusal. (caught: cold-read)
- **This record said "so it is 0" of a cut's flush,** which was so only where every stream closed inside its bound, and said thirteen mutants without saying what became of them. (caught: cold-read)
- **A row that would have thrown out of its section** on a `/health` that answered liveness: it fails its row. (caught: cold-read)

**Found by the second review.** Two more readers: one set against the first review's fixes on a real process, one reading the whole pull request as its merger. Nothing reaches a running server. The count is a cumulative sum that is not monotonic under every temporality preference, an unchanged value is sent at every export, and the 0 was on the wire before the exit in each. The merger's verdict was to merge after named changes, all of them words.

- **No row held that the count is still the count during a stop's drain:** one that read 0 from the signal passed every row, where a drain serves its streams for up to 8 s. The cut's row has a drain of 2 s and reads the exports that arrive in it. (caught: mutant; held: test-mcp [8h])
- **"That point is the last the server sends" was flatter than what happens.** The 0 is the last point only where the stop's flush gets that export out: with the collector gone, or still answering the export before it, the last point was the count still open. And the 0 comes at the drain's end, the streams' close after the flush, up to 5 s later. The operator's page says both; nothing was built around either. (caught: run-it)
- **The page's list for PR 2b was made untrue and left short:** it said the two codes were named nowhere else, and it did not carry the three "none yet" this change wrote, which go false the day the capability is on. (caught: cold-read)
- **The two bounds were written into the operator's page as numbers,** a second copy of two constants the design page calls a first guess. The field says them. (caught: cold-read)
- **The reason given for the function's home was the weaker one:** check 37 cannot read this instrument yet. The one that stands is that `mcp-server/` has no dependency of its own on the OpenTelemetry API. (caught: cold-read)
- **Smaller:** "answers whether it was made", of a function that answers true on the API's no-op provider; a refused notification is a 202, not a 200; names in the rows that still said gauge; a comment on what the app's count is for. (caught: cold-read)

**Left as it is.** The entry's warning for a count that could not be made is held by no row: a real meter gave nothing to make it throw. `listen.open` is the shared count and `callers` the app's own map, which agree in the one app an entry builds; two apps given one count would not. A caller's name is whatever the REST core's whoami says; a core that named none would leave its row with no name, and every such caller on that one row. The 0 at a stop's flush is the series' last point only where the flush gets that export out: where the collector does not answer, or is still answering the export before it when the flush's bound runs out, or the process is killed, the count before it stands until the series goes stale, and a sum over servers counts it beside the next server's. The 0 comes at the drain's end and the streams' close after the flush, 5 s later at most. A read that failed at an export would be said by no one, the SDK keeping its own errors; this one reads a flag and a number.
