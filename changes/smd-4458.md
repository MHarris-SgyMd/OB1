## Changelog

A server that holds listen streams says how many are open: the MCP server's keyed `/health` gains `listen` (the streams open, the two bounds, and each caller's count), and the server sends the total as a gauge, `ob1.mcp.listen_streams` (SMD-4458). No server holds a stream yet, so nothing the brain serves or sends changes.

## Record

A count of the listen streams a running MCP server holds, on keyed /health and as a gauge: PR 1 (SMD-4458)

**Why.** SMD-4347's PR 2a built what the MCP server needs to hold 2026-07-28 `subscriptions/listen` streams, with the capability off, and left one thing an operator would want the day it is on: only the stop's two lines counted the open streams, so a listen refused at a bound (`LISTEN_SERVER_FULL`, `LISTEN_CALLER_FULL`) had nothing to be read against. The maintainer set this ticket to come before that capability is turned on.

**Decided, by the maintainer, 2026-11-19.**

- Where the count shows: on keyed `/health`, as a gauge, and on a panel of the observability profile's dashboard. This PR is the first two; the panel is PR 2.
- By caller: the per-caller table is on keyed `/health` alone, and whoever may read the brain's record there sees every caller's name. A key's caller name is the key's; a token's is its subject and its client together. The gauge is the total, with no label for a caller: such a label would have no bound.

**What changed.**

- `mcp-server/app.ts`: on an app that holds streams, keyed `/health` answers `listen` beside the REST core's record and `oauth`: `open`, `max`, `perCaller`, and `callers`, each `{ name, open }`, the most first and equal shares in name order. It is read as the route answers, from the count the route already keeps for its two bounds. An app that holds none has no such field, whether it was given the streams' settings (as the entry is) or none.
- `server-portable/tracing.ts`: `observeListenStreams(read)` makes the gauge `ob1.mcp.listen_streams`, unit `{stream}`, on the meter provider the API has, and reads the count at each export. It is in `server-portable/` and not beside the server that uses it because check 37 reads the instruments a dashboard may name from that directory's code, which PR 2's panel needs.
- `mcp-server/index.ts` asks for the gauge once the SDK is set up, and only where the server holds streams: before the SDK is set up the API's provider is its no-op, and a gauge made on it is never sent.
- `deploy/README.md` and `mcp-server/README.md` say what the field and the gauge are, and `deploy/README.md`'s account of a line's `code` names the two refusals, which no operator's page did. `docs/mcp-listen-streams.md` says the count is built.

**What the gauge reads at a stop.** The stop's flush reads it once more. After a drain that finished, the streams are closed after the flush, so that last point is the count still open. After a cut they are closed at the bound, before the flush, so it is 0. Neither was designed here: it is the order SMD-4347 gave the stop, and a row holds each.
