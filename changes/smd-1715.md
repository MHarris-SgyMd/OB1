## Changelog

The brain records deliverables (SMD-1715 PR 1, migration 133). A deliverable is a piece of agent output tied to the spec it was meant to meet, with a checkpoint (a commit hash or a content fingerprint) and a status: unverified, verified or corrected. The status moves only unverified to verified or corrected, verified to corrected, and corrected to verified. The database refuses any other move, a direct write included. A deliverable isn't verified by the key that captured it. Each change is an event that names the key that made it. The `deliverable` facet on the thought is the events' projection, so it can't be edited directly. A new grant group, `deliverables`, covers the calls. The operations over REST and MCP, `capture_deliverable` and `verify_deliverable`, follow in PR 2.

## Record

The brain records deliverables: one output tied to a spec, with a checkpoint and a status that moves only through the allowed transitions, PR 1 (SMD-1715)

A deliverable is what gets verified. Nothing in the brain held one, so whether an agent's run did what it was asked lived only in the PR and the session. `plan_context`'s specs section has said "not available here" since it shipped, and SMD-2683's spec reads "met" from a verified deliverable. This is the store. The operations over REST and MCP are PR 2.

**The maintainer's three choices (2026-11-11), made before the migration was written:**
- **The events have a table of their own,** `deliverable_events`, as 116's priorities and 117's open items do. They are not an op on `thought_audit`.
- **The ticket's Work 5 is dropped.** It would have recorded "who is working this deliverable" on 015's `thought_work_claims`. That table is a worker's batch pool: the database picks the batch, and no caller can claim one named thought. Each event stamps its maker from the key instead.
- **The key that captured a deliverable doesn't verify it** (`VERIFY_NOT_YOURS`, by its name or its agent id). Any write key may mark it corrected, its maker included.

**What changed (migration 133):**
- **The events** are a capture, then each verification. Each carries the deliverable's whole state after it, and a verification carries its method and outcome. No event is ever changed: an UPDATE, DELETE or TRUNCATE is refused for the owner too.
- **The transitions** are checked by a trigger on every insert, a raw one included, under a lock on the deliverable. A capture comes first, of a thought and a spec that both exist. Every later event keeps the capture's spec and checkpoint, and moves the status by one of the four allowed moves.
- **The `deliverable` facet** is the events' projection, one per thought. The facet validator (120's, carried with a fifth kind) admits it only as `ob1_deliverable_payload`'s projection of the newest event. So a direct UPDATE of its status is refused whether the move is allowed or not, and so is a facet with no events. It is deleted only with its thought; the events stay as history.
- **The writers** are `record_deliverable` and `verify_deliverable`. Their refusals are values: `READ_ONLY_KEY`, `SPEC_NOT_FOUND`, `SPEC_IS_SELF`, `THOUGHT_NOT_FOUND`, `ALREADY_A_DELIVERABLE`, `NOT_A_DELIVERABLE`, `ILLEGAL_TRANSITION` (naming from and to) and `VERIFY_NOT_YOURS`. `deliverable_history` reads a deliverable. A drift check and a rebuild follow 068's pattern.
- **The `deliverables` grant group** gives `SELECT, INSERT` on the events and `SELECT, INSERT, UPDATE` on `thought_facets`.

**Not done:**
- The operations over REST and MCP (PR 2).
- A spec record (SMD-2683): `spec_ref` is any thought's id.
- Deleting the spec isn't refused, as deleting a cited source is (042).
- Forgetting a deliverable's events (SMD-1723).
