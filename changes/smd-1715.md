## Changelog

The brain records deliverables (SMD-1715 PR 1, migration 134). A deliverable is a piece of agent output tied to the spec it was meant to meet, with a checkpoint (a commit hash or a content fingerprint) and a status: unverified, verified or corrected. The status moves only unverified to verified or corrected, verified to corrected, and corrected to verified. The database refuses any other move, a direct write included. A verification vouches for the output at its checkpoint, not for the thought's text, which stays editable. `corrected` means a verification found that output wanting; reworked output is a new deliverable. Through `verify_deliverable`, neither the key that recorded a deliverable nor a key the brain records as writing its thought can verify it. Each change is an event that names the key that made it. The `deliverable` facet on the thought is the events' projection, kept current as each event lands, so it can't be edited directly. A new grant group, `deliverables`, covers the calls. 

Agents capture, verify and read deliverables over REST and MCP (SMD-1715 PR 2). `capture_deliverable` (`POST /v1/deliverables`) captures the output as a thought, derived from the spec, its text closing with a `Checkpoint: …` line, and records it unverified. `verify_deliverable` (`POST /v1/deliverables/{id}/verifications`) records a check: its method, its finding, and the status it moves to. `deliverable_history` (`GET /v1/deliverables/{id}`) reads one. The two writers are a write key's alone; the read is any key's. A server role needs the `deliverables` grant group, and preflight checks it.

## Record

The brain records deliverables — one output tied to a spec, with a checkpoint and a status that moves only through the allowed transitions — and agents capture, verify and read them over REST and MCP (SMD-1715)

A deliverable is what gets verified. Nothing in the brain held one, so whether an agent's run did what it was asked lived only in the PR and the session. `plan_context`'s specs section has said "not available here" since it shipped, and SMD-2683's spec reads "met" from a verified deliverable. This is the store. The operations over REST and MCP are PR 2.

**The maintainer's three choices (2026-11-11), made before the migration was written:**
- **The events have a table of their own,** `deliverable_events`, as 116's priorities and 117's open items do. They are not an op on `thought_audit`.
- **The ticket's Work 5 is dropped.** It would have recorded "who is working this deliverable" on 015's `thought_work_claims`. That table is a worker's batch pool: the database picks the batch, and no caller can claim one named thought. Each event stamps its maker from the key instead.
- **The key that captured a deliverable doesn't verify it** (`VERIFY_NOT_YOURS`, by its name or its agent id). Since review pass 2 (the maintainer's choice), neither does a key that wrote its thought. Any write key may mark it corrected, its maker included.

**Two definitions, the maintainer's (2026-11-12, review pass 3):**
- **A verification vouches for the output at the checkpoint,** not the thought's text. The thought stays editable, and the events don't follow an edit. A reader comparing a content-fingerprint checkpoint with the thought's own fingerprint says when they differ (PR 2, `plan_context`).
- **`corrected` is a finding on the same output:** a verification found the output at its checkpoint wanting. Corrected to verified is a later verification overturning that finding, at the same checkpoint. Reworked output is a new deliverable: a new thought at its new checkpoint.

**What changed (migration 134):**
- **The events** are a capture, then each verification. Each carries the deliverable's whole state after it, and a verification carries its method and outcome. No event is ever changed: an UPDATE, DELETE or TRUNCATE is refused for the owner too.
- **The transitions** are checked by a trigger on every insert, a raw one included, under a lock on the deliverable. A capture comes first, of a thought and a spec that both exist. Every later event keeps the capture's spec and checkpoint, and moves the status by one of the four allowed moves.
- **The `deliverable` facet** is the events' projection, one per thought, written by a trigger as each event lands, a raw one's too. The facet validator (120's, carried with a fifth kind) admits it only as `ob1_deliverable_payload`'s projection of the newest event. So a direct UPDATE of its status is refused whether the move is allowed or not, and so is a facet with no events. It is deleted only with its thought; the events stay as history.
- **The writers** are `record_deliverable` and `verify_deliverable`. Their refusals are values: `WRITE_SCOPE_REQUIRED`, `SPEC_NOT_FOUND`, `SPEC_IS_SELF`, `THOUGHT_NOT_FOUND`, `ALREADY_A_DELIVERABLE`, `NOT_A_DELIVERABLE`, `ILLEGAL_TRANSITION` (naming from and to) and `VERIFY_NOT_YOURS`. `deliverable_history` reads a deliverable. A drift check and a rebuild follow 068's pattern.
- **The `deliverables` grant group** gives `SELECT, INSERT` on the events, `USAGE` on their `seq`'s sequence, and `SELECT, INSERT, UPDATE` on `thought_facets`. A thought's author is read from `thought_audit`, which the capture group already reads.

**Review pass 1.** An independent cold read ran each suspicion on a scratch Postgres; four findings were confirmed. Fixed:
- **A raw event could sort under a newer one.** The identity `seq` is drawn before the trigger takes the lock. So a raw insert that waited while a writer wrote got a lower `seq`, and the last move read as older than the one it followed; no drift showed it. Such an insert is now refused 40001, to be made again. The writers lock first and never meet it. (caught: cold-read)
- **A raw event above READ COMMITTED skipped the status rule.** Its read of the newest event was the transaction's old snapshot, so a forbidden move was written for good. The event trigger and the facet's validator now refuse a transaction above READ COMMITTED, as the writers do. (caught: cold-read)
- **The rebuild beside a delete of the thought failed whole.** The projector saw the thought, the facet went by the cascade under it, and its INSERT failed the foreign key, undoing every repair in the call. It now locks the thought `FOR KEY SHARE`, so the delete is waited out. (caught: cold-read)
- **No test held concurrency or isolation.** test-schema [121] now holds the four refusals above READ COMMITTED. A new test-live [49] uses real sessions: a second verification waits for the first, a raw event that waited is refused 40001, and the rebuild runs beside a delete. (caught: cold-read)
- **The words claimed more than the code holds.** A role with INSERT on the events writes any maker it names, as on 117's events. So the maker, and the rule that it doesn't verify its own, hold through the writers. The changelog, header, table comment and README now say so. The group's INSERT on `thought_facets` lets a role write any facet kind, as the structure group does; the README and `db/config.mjs` now say that too. (caught: cold-read)

**Review pass 2.** A second independent cold read, with its own scratch Postgres. Fixed:
- **A raw insert could choose its own `seq` and block a deliverable for good.** `OVERRIDING SYSTEM VALUE` needs only INSERT. A huge `seq` made pass 1's 40001 refusal refuse every later verification, so a caller retrying as told looped forever. The trigger now draws each event's `seq` itself, under the deliverable's lock, whatever the insert brought, so every insert is numbered in lock order. The 40001 refusal is gone, and the group gains `USAGE` on the sequence. (caught: cold-read)
- **The key that wrote a deliverable's thought could verify it.** `record_deliverable` takes any thought, so the key that recorded it need not be its author. The maintainer chose that both are refused: `VERIFY_NOT_YOURS` now also matches the thought's first capture in `thought_audit`, and the group gains `SELECT` there. (caught: cold-read)
- **The rebuild counted a thought deleted while it waited,** and took the deliverables in no set order. Two rebuilds could deadlock. It now counts only what it wrote, takes the deliverables in id order, and test-live [49] asserts the exact count. (caught: cold-read)

**Review pass 3,** a definitions pass: does each stored or reported value mean what the words say? Fixed:
- **"The key that wrote its thought" meant only its first capture.** A key that rewrote the text after another captured it could verify its own text, though the row's own writer stamp named it. `VERIFY_NOT_YOURS` now matches every key that wrote the text: the capture, an edit of its content, and 082's re-capture. Pass 2's `SELECT` grant on `thought_audit` is dropped, since the capture group holds it already. (caught: cold-read)
- **A raw event left the facet stale until someone ran the rebuild, which nothing runs, and its `at` was taken as given.** One dated 1999 was admitted. A trigger now projects every event as it lands, and the event trigger stamps `at` as it draws `seq`. (caught: cold-read)
- **The rebuild counted a facet that another rebuild or a writer had made current.** Two concurrent rebuilds both counted one. It now reads the facet again under the lock, and test-live [49] runs the two at once. (caught: cold-read)
- **Another key recording the same deliverable was told `unchanged`,** read it as its own, and could then verify it; a capture deduplicated onto an existing thought lands there. Now it is refused `ALREADY_A_DELIVERABLE`, naming the key that recorded it. Its verification is still admitted, as review pass 4 found (SMD-4242). (caught: cold-read)
- **A capture key was told `READ_ONLY_KEY`,** which means a read key in 116 and 117. Now it is `WRITE_SCOPE_REQUIRED`. (caught: cold-read)
- **Two meanings were open, and the maintainer chose:** a verification vouches for the checkpoint, not the thought's text, and `corrected` is a finding on the same output. Now said in the header, the README and here. (caught: cold-read)
- **The words:** the README said the identity `seq` needs no grant, beside the `USAGE` row; `seq` is not a cursor across deliverables; and a key with no agent id that was renamed since isn't matched by `VERIFY_NOT_YOURS`. Each is now said. (caught: cold-read)

**PR 2: the operations over REST and MCP.**
- **`capture_deliverable`** captures the output as `capture_thought` captures any thought, with the spec as its `derived_from`. Its text closes with a `Checkpoint: …` line, so a new checkpoint is a new thought, as the maintainer's definition of `corrected` needs. It then records the deliverable, its key's scope stated. Three of pass 4's notes for PR 2 are taken here:
  - a key without write scope is refused before anything is captured;
  - the spec is checked by the capture, and a spec naming nothing is `SPEC_NOT_FOUND` (422), with nothing written;
  - since PR 2's review pass 1, the text is looked for first too, and a record that fails after a fresh capture deletes the thought.
- **`verify_deliverable`** records a check: its method, its finding and the status it moves to.
- **`deliverable_history`** reads a deliverable and its events, for any key. The ticket's Work named only the two writers, but its Problem is that nothing *produces or reads* a deliverable, and `deliverable_history` is that read.
- **The finding is named `finding`,** apart from every call's `outcome` (pass 4's third note). 134 stores it as `outcome`.
- **The refusals** are values, each with its HTTP status: `SPEC_NOT_FOUND` 422; `SPEC_IS_SELF`, `ALREADY_A_DELIVERABLE` and `ILLEGAL_TRANSITION` 409; `NOT_A_DELIVERABLE` 404; `VERIFY_NOT_YOURS` and `WRITE_SCOPE_REQUIRED` 403.
- **Preflight's `deliverables` row** checks 134's functions and the server role's grant group, its sequence's `USAGE` included.
- **`plan_context`'s specs section** said the brain records no deliverables, which is now false. It now waits on the spec record alone (SMD-2683), and names `deliverable_history` as the read.
- **Tested** in test-rest-sql [21], over both doors:
  - the capture, the same again, and another key's repeat;
  - the maker and the author refused verification, another key verifying, a move not allowed, the maker correcting;
  - the history, read by a read key;
  - a read key's `tools/list` holding neither writer, as the ticket's Verify asks;
  - each refusal.

  test-preflight holds the new row, and test-mcp the tools' order.

**PR 2, review pass 1.** An independent reader drove the operations against real servers and confirmed five findings. Fixed:
- **A spec given by its `client_key` left an orphan thought, every retry the same.** The capture resolved the key to the thought's id, but the record was given the raw key and refused it. The spec is now resolved once, before the capture, and the id passed to both. (caught: run-it)
- **Another key's repeat rewrote the deliverable's thought before it was refused.** The capture ran first: it merged its tags, moved `updated_at` and wrote an audit row, and the record then refused it. The text is now looked for before any capture. A deliverable is answered from the record with nothing captured; any other thought is refused. (caught: run-it)
- **Text that was already an ordinary thought was recorded onto.** Its `derived_from` stayed unset, and the caller became the recorder of a thought another key may have written. The maintainer chose (2026-11-12) to refuse it: `OUTPUT_EXISTS` (409). (caught: run-it)
- **The capture and the record are two statements, and 134's header says one transaction.** A record that failed after a fresh capture left the thought behind: a server role without the group, a spec deleted between them, a race. The thought is now deleted when nothing has recorded it since. test-rest-sql [21] renames the record away for one call and finds no thought left. (caught: cold-read)
- **Checkpoints differing only in letter case or white space name one thought,** by 016's fingerprint. Now said in the tool's description, the refusal and the README. (caught: run-it)
- **The answer carried the raw capture:** the provider's address, the egress policy's words, the extractor's tags. `capture` is now capture_thought's safe fields alone. (caught: run-it)
- **Blank output was accepted;** the schema refuses it. (caught: run-it)

**PR 2, review pass 2.** A second independent reader, with a provider stub that held an embedding call open, found three races in pass 1's own additions. All three came from one cause: the text check, the capture, the record and the undo were four statements. The maintainer chose (2026-11-12) to simplify now and ticket one transaction (SMD-4248). Fixed:
- **Pass 1's undo could delete a thought another key had just been told was stored:** that key's capture landed on it while this call's record waited. Nothing is deleted now. A record refused after a fresh capture leaves the thought, and `SPEC_NOT_FOUND` names it (`left`). (caught: run-it)
- **A capture that landed on a thought written meanwhile was recorded onto,** another key's ordinary thought among them, which `OUTPUT_EXISTS` exists to refuse. The thought a capture lands on is now answered as one found before would be. (caught: run-it)
- **Without the undo, a key's own leftover would block its retry.** So a thought this key captured from this spec, with no deliverable naming it, is recorded onto. Any other ordinary thought is still `OUTPUT_EXISTS`, the key's own capture from no spec among them. (caught: cold-read)
- **An undone capture left its proposed open items behind,** naming a thought that was gone. With nothing deleted, they name a thought that stays. (caught: run-it)
- **The smaller ones:**
  - `ALREADY_A_DELIVERABLE` read the deliverable again after 134 answered, and threw if the thought was deleted between them; it reads the capture event now, which outlives its thought;
  - the `unchanged` reply said "nothing was written" where this call's capture had landed on the thought.

  (caught: cold-read)
- **SMD-4248 remains:** a raced capture still merges into the other key's row before it is refused, and a left thought keeps its side effects. (caught: run-it)
