## Changelog

The authorization server's proof-of-concept kit now runs the runner-up too: Better Auth 1.7.6 with its OAuth-provider and CIMD plugins, through the same stack and verifier as oidc-provider and in the same CI job, passes all 32 checks, with one noted departure from RFC 7636 (a wrong PKCE verifier gets `invalid_request`) — after an allowlist, an Origin check and three hooks of ours, since its handler also serves sign-up and session routes, its signed interaction query is not bound to the browser (a consent was forged cross-page until the Origin check), it lets a token carry several audiences, and it offers DPoP with no switch.
The winner's sign-in and consent pages now forbid framing (`X-Frame-Options: DENY`, `frame-ancestors 'none'`): a framed consent page would have let one click post it from the brain's own origin. The verifier gains four checks for both candidates (off-protocol routes 404, a DPoP proof binds nothing, a cross-origin consent issues nothing, no page may be framed), for 32 in all (SMD-2285).
The winning server leaves the kit for `deploy/auth/`, with its own exactly pinned package and its own image, and reads its tiers and service clients from two settings, `OB1_AUTH_TIERS` (`stable` when unset) and `OB1_AUTH_SERVICES`; the proof of concept now builds and checks that image, 32/32. It is not in `deploy/compose.yaml` yet (SMD-2285).

## FORK

The authorization server's proof of concept, second leg: the runner-up, Better Auth 1.7.6, through the same 32 checks as oidc-provider, the winner's pages made unframeable, and the winning server moved to `deploy/auth/` (SMD-2285)

This follows the winner's kit, released in 1.4.0 (`changes/242-the-authorization-server-s-proof-of-concept-oidc.md`); the ticket asks for criteria 1–5 proved "with the winner and one runner-up". The runner-up is eval-only; the winner's move to `deploy/auth/` is below.

**The runner-up.** `evals/auth/better-auth.ts` runs Better Auth 1.7.6, `@better-auth/oauth-provider` and `@better-auth/cimd` (pinned exactly) as its own Bun service beside the same stack, and `bun eval-auth.ts --verify better-auth` runs the same checks: 32/32 twice.
- **What it needs of ours.**
  - An allowlist, because its handler also answers sign-up, profile, session, consent- and client-management routes; POST on the authorization route is a 405, since the library reads a POST's body there.
  - An Origin check on every sign-in and consent POST: they are called in-process with our Origin, so the library's CSRF check sees ours, and its signed query is not bound to the browser. Review pass 1 forged a consent from another same-site page and got a `/mcp` token.
  - A before-hook holding every token to one resource: none issued for no resource, none naming more than one (counted in the raw token-request form, since the parsed body keeps the last of a repeated field and the library grants a client-credentials token every resource the client is linked to), no `openid`, and no request naming no scope or an empty one. With scope left out, the library filled in `openid`, saved a consent, and gave the next request a two-audience token. Pass 1 read the client's registered scopes instead, and pass 2 found that a metadata-document client has no row until after the hook. Any other method than GET and POST on the interaction routes is a 405.
  - The third-party rule for DCR in that hook, and for metadata documents in the fetch wrapper (the CIMD plugin's `onClientCreated` only notifies), refusing `backchannel_logout_uri` too.
  - The `DPoP` header stripped, and the metadata trimmed of everything the allowlist blocks.
  - Token exchange through `extendOAuthProvider`: the library strips a contributed `exp`, so the REST cores' tokens live 60 s (the GUI's included) and a subject token with less left is refused.
  - Static clients seeded as database rows.
- **Where it is stronger.** It refuses `com.evilapp://localhost:8020/mcp` at registration (RFC 8252 §7.1). Its CIMD plugin refuses private `client_id`s before any fetch, and its own `@better-auth/cimd/node` fetcher is SSRF-safe: with it in place of our guard the bait saw no connection, though the reply names no cause.
- **The verifier, made candidate-neutral.**
  - The pages moved to `evals/auth/pages.ts`, rendered by both servers; the MCP stand-in reads the token endpoint's path from the metadata.
  - `EXPECT` holds each candidate to what it actually answers; `KNOWN` notes a departure from a standard beside its row without excusing it (its first version excused whole rows, hiding G3's replay half).
  - New for both: D7 (a sample of the routes outside the protocol answers 404), D8 (a DPoP proof binds nothing), G7 (a consent posted from another origin issues nothing; the winner refuses one too), G8 (neither the sign-in nor the consent page may be framed: `X-Frame-Options: DENY` and `frame-ancestors 'none'`, on both, the winner's merged pages included; and a live sign-in page takes only GET and POST), D1 asserting introspection, back-channel logout, the claims parameter and `prompt=create` are not advertised.
  - R3 and A6 read a cause from the reply or the guard's log line; A4 asks a signed-in, consented operator twice with no scope and pins each candidate's refusal; A7 posts an authorization request from a signed-in, consented browser and pins each candidate's answer (POST is off on both); G6's custom scheme is `com.evilapp://` so the naming authority is the only fault; A8 and G6 hold each candidate to the scope-less tokens and consent pages it produces; a `null` reply body no longer crashes the report.
- **A test client.** `runner-tiers` in `evals/auth/policy.ts` is a service linked to both tiers' REST cores, so A4 can ask client credentials for both at once; both candidates refuse it. `ensureEnv` appends a new client's secret to an existing `evals/auth/.env`.
- **Held by.** Nineteen mutants on its server (the two third-party rules and the back-channel refusal, the three resource rules, the raw-form resource count, the no-scope and empty-scope refusals, the POST refusal, the Origin check, the method rule, the frame headers, the DPoP strip, the metadata trim, the allowlist, the guard, the exchange's audience and `act`), each turning its checks red; the winner's 28 still do, re-run against the changed verifier.

**Tidied after the runner-up's three review passes, while the files were open** (no behaviour change): the token-exchange handler is typed by the library's own `OAuthExtensionGrantHandler` (checked with `satisfies`) instead of a hand-written shape that disagreed with it; `html()` spreads the page headers last, so no caller can override the framing rule; and `Browser.pageUrls`, recorded and never read, is gone.

**The winner moves to `deploy/auth/`** (Work step 3's first cut; no change in what the server does). The deploy's server is the file the proof of concept passed, so the checks keep holding it:
- `evals/auth/oidc-provider.ts` is `deploy/auth/server.ts`; the fetch guard and the pages move beside it. Its own `package.json` pins `oidc-provider` 9.12.2 and `jose`; the kit's package drops `oidc-provider` and keeps `jose`, which the runner-up and the stand-ins use. Its own Dockerfile builds from `deploy/auth/` alone.
- **The layout is the deploy's.** `deploy/auth/layout.ts` builds the resources and static clients from the origin and two settings: `OB1_AUTH_TIERS` (comma-separated tier names; `stable` when unset or blank, since compose passes an unset `${X:-}` as the empty string, and `stable` must be among them) gives each tier its `/mcp` and `/api` audiences and an exchange client, `mcp` or `mcp-<tier>`; `OB1_AUTH_SERVICES` (whitespace-separated `<id>=<scope>[+<scope>]@<tier>[,<tier>]`) adds client-credentials identities. An unknown tier or scope, a service naming a tier `OB1_AUTH_TIERS` does not list, an empty or repeated part, a malformed entry, an id that is not lowercase letters, digits and inner hyphens within 64 characters, the server's own ids (`gui`, `mcp`, `mcp-*`) or a repeated id stops the server starting, each with its own message. The URL helpers take only the three tier prefixes. `evals/auth/policy.ts` is now the deploy's layout read with the POC's settings (two tiers, `runner` and `runner-tiers`); `stack.ts` sets them in `evals/auth/.env` on every `--up`, replacing whatever the file held, and the winner's overlay passes them to the container, so the server and the verifier cannot read different layouts.
- **The kit's image builds from the repo root**, so the stand-ins and the runner-up import the deploy's layout, pages and guard from where they live; the root `.dockerignore` lets `evals/auth/`'s sources in, and the kit's own `.dockerignore` goes.
- **Held by.** 32/32 twice on the deploy's image, and the runner-up 32/32 twice on the root-built kit image. The winner's 28 mutants (24 in `deploy/auth/`, four in the kit's proxy, its stand-ins and the winner's overlay) each still turn their checks red. The self-check's 26 probes of the deploy's settings (the two, and a missing origin) match each refusal by its message, report a wrongly refused setting by name, and hold the id rule's accepted edges; 19 mutants of `layout.ts` (every refusal dropped, plus blank tiers read as set, untrimmed parts, space-only splitting, `gui` and `mcp` unreserved, and the id rule loosened, tightened or without digits) each turn it red.

**Review passes** of the move (the prose is in the commit body):

| Pass | Finding | Caught | Fix |
