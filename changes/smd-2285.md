## Changelog

The authorization server's proof-of-concept kit now runs the runner-up too: Better Auth 1.7.6 with its OAuth-provider and CIMD plugins, through the same stack and verifier as oidc-provider and in the same CI job, passes all 32 checks, with one noted departure from RFC 7636 (a wrong PKCE verifier gets `invalid_request`) — after an allowlist, an Origin check and three hooks of ours, since its handler also serves sign-up and session routes, its signed interaction query is not bound to the browser (a consent was forged cross-page until the Origin check), it lets a token carry several audiences, and it offers DPoP with no switch.
The winner's sign-in and consent pages now forbid framing (`X-Frame-Options: DENY`, `frame-ancestors 'none'`): a framed consent page would have let one click post it from the brain's own origin. The verifier gains four checks for both candidates (off-protocol routes 404, a DPoP proof binds nothing, a cross-origin consent issues nothing, no page may be framed), for 32 in all (SMD-2285).
The winning server leaves the kit for `deploy/auth/` and runs as `deploy/compose.yaml`'s `auth` profile: its own exactly pinned image, its tiers and service clients read from `OB1_AUTH_TIERS` (`stable` when unset) and `OB1_AUTH_SERVICES`, its state in SQLite in its own volume (it holds no Postgres credential), its secrets written by `bun deploy/auth/provision.ts --init`, and every setting checked at start, the problems named all at once. Nothing routes to it until the proxy; the proof of concept checks its image, 32/32 (SMD-2285).

## FORK

The authorization server's proof of concept, second leg: the runner-up, Better Auth 1.7.6, through the same 32 checks as oidc-provider, the winner's pages made unframeable, and the winning server moved to `deploy/auth/` and deployed as the `auth` compose profile with a SQLite store (SMD-2285)

This follows the winner's kit, released in 1.4.0 (`changes/242-the-authorization-server-s-proof-of-concept-oidc.md`); the ticket asks for criteria 1–5 proved "with the winner and one runner-up". The runner-up is eval-only; the winner's move to `deploy/auth/` is below.

**The runner-up.** `evals/auth/better-auth.ts` runs Better Auth 1.7.6, `@better-auth/oauth-provider` and `@better-auth/cimd` (pinned exactly) as its own Bun service beside the same stack, and `bun eval-auth.ts --verify better-auth` runs the same checks: 32/32 twice.
- **What it needs of ours.**
  - An allowlist, because its handler also answers sign-up, profile, session, consent- and client-management routes; POST on the authorization route is a 405, since the library reads a POST's body there.
  - An Origin check on every sign-in and consent POST: they are called in-process with our Origin, so the library's CSRF check sees ours, and its signed query is not bound to the browser. Review pass 1 forged a consent from another same-site page and got a `/mcp` token.
  - A before-hook holding every token to one resource: none issued for no resource, none naming more than one (counted in the raw token-request form, since the parsed body keeps the last of a repeated field and the library grants a client-credentials token every resource the client is linked to), no `openid`, and no request naming no scope or an empty one. With scope left out, the library filled in `openid`, saved a consent, and gave the next request a two-audience token. Pass 1 read the client's registered scopes instead, and pass 2 found that a metadata-document client has no row until after the hook. Any other method than GET and POST on the interaction routes is a 405.
  - The third-party rule for DCR in that hook, and for metadata documents in the fetch wrapper (the CIMD plugin's `onClientCreated` only notifies), refusing `backchannel_logout_uri` too.
  - The `DPoP` header stripped, and the metadata trimmed of everything the allowlist blocks.
  - Token exchange through `extendOAuthProvider`: the library strips a contributed `exp`, so the REST cores' tokens live 60 s (the GUI's included) and a subject token with less left is refused.
  - Static clients seeded as database rows.
- **Where it is stronger.** It refuses `com.evilapp://localhost:8020/mcp` at registration (RFC 8252 §7.1). Its CIMD plugin refuses private `client_id`s before any fetch, and its own `@better-auth/cimd/node` fetcher is SSRF-safe: with it in place of our guard the bait saw no connection, though the reply names no cause.
- **The verifier, made candidate-neutral.**
  - The pages moved to `evals/auth/pages.ts`, rendered by both servers; the MCP stand-in reads the token endpoint's path from the metadata.
  - `EXPECT` holds each candidate to what it actually answers; `KNOWN` notes a departure from a standard beside its row without excusing it (its first version excused whole rows, hiding G3's replay half).
  - New for both: D7 (a sample of the routes outside the protocol answers 404), D8 (a DPoP proof binds nothing), G7 (a consent posted from another origin issues nothing; the winner refuses one too), G8 (neither the sign-in nor the consent page may be framed: `X-Frame-Options: DENY` and `frame-ancestors 'none'`, on both, the winner's merged pages included; and a live sign-in page takes only GET and POST), D1 asserting introspection, back-channel logout, the claims parameter and `prompt=create` are not advertised.
  - R3 and A6 read a cause from the reply or the guard's log line; A4 asks a signed-in, consented operator twice with no scope and pins each candidate's refusal; A7 posts an authorization request from a signed-in, consented browser and pins each candidate's answer (POST is off on both); G6's custom scheme is `com.evilapp://` so the naming authority is the only fault; A8 and G6 hold each candidate to the scope-less tokens and consent pages it produces; a `null` reply body no longer crashes the report.
- **A test client.** `runner-tiers` in `evals/auth/policy.ts` is a service linked to both tiers' REST cores, so A4 can ask client credentials for both at once; both candidates refuse it. `ensureEnv` appends a new client's secret to an existing `evals/auth/.env`.
- **Held by.** Nineteen mutants on its server (the two third-party rules and the back-channel refusal, the three resource rules, the raw-form resource count, the no-scope and empty-scope refusals, the POST refusal, the Origin check, the method rule, the frame headers, the DPoP strip, the metadata trim, the allowlist, the guard, the exchange's audience and `act`), each turning its checks red; the winner's 28 still do, re-run against the changed verifier.

**The `auth` profile** (Work step 3's second cut, on the maintainer's three decisions of 2026-10-01: the service now and the route later, SQLite in a volume, password sign-in now):
- **The service.** `deploy/compose.yaml`'s `auth` service runs the image under the `auth` profile. It publishes no port and joins two networks of its own, not the default one: `mesh` (internal, as `auth.ob1.internal`) and `egress` (for client metadata documents, through the fetch guard). So it cannot reach Postgres until SMD-1846 moves the stack onto the mesh, holds no Postgres credential either way, and nothing routes to it until that proxy. Its environment names exactly the layout, the keys, the hash and the GUI's and each tier's MCP secrets, each `${X:-}`, with no `env_file`, so the container never sees the Postgres password, the brain's keys, the operator's plain password or the POC's switch; `deploy/tier.sh`, which hands `OB1_*` lines to its own container, now skips `OB1_AUTH_*`. Its files are read-only, it keeps no capability, the store's directory is its user's alone, and a stop (SIGTERM, through `init`) finishes what is in flight, closes the store and exits 0, where Bun alone ignored the signal until the grace period's SIGKILL.
- **The store.** `deploy/auth/store.ts` is an oidc-provider adapter on `bun:sqlite`: one table keyed by model and id, with the grant id, session uid and user code beside the payload, and the expiry the library gives. It behaves as the memory adapter the proof of concept passed against: an expired row is never returned, `consume` stamps the payload, and a grant's revocation removes every grantable row of it. WAL mode, so `VACUUM INTO` backs it up beside the running server (`deploy/README.md`, "Authorization server", measured both ways). A file that will not open as the store stops the server with exit 2 and the remedy, by its cause: a corrupt file or one of another shape is restored or dropped, a permissions failure is the directory's owner. Rows are kept 15 s past their expiry, the library's clock tolerance, which the server sets from the store's one constant. A store failure while serving (a full volume, a held lock) answers `server_error` with nothing internal in it and is logged with its stack; a sign-in page shows the library's own refusals and nothing of any other error. The proof of concept's image now runs it too, 32/32 twice.
- **Start-up checks.** `deploy/auth/config.ts` reads every setting at once and the server exits 2 naming every problem: `OB1_PUBLIC_ORIGIN` must be an origin alone (`https://`, or `http://` on a loopback host; no path, query, fragment, credentials or default port, and a value with an `@` is refused without being echoed, since it may hold credentials), the JWKS must be JSON holding P-256 private keys (a parse error names the variable), the cookie keys and client secrets at least 32 characters, the hash a whole argon2id hash as Bun writes it (version 19, a 43-character salt and digest, so a cut at any length is refused; a cost of at most 256 MiB, 10 passes and 16 lanes, refused before any verify, since every sign-in pays it; and a verify that does not throw, for a character the decoder refuses), and every static client's secret set. The POC's error-detail switch is read there, logs a warning when on, and is not passed by compose.
- **Provisioning.** `bun deploy/auth/provision.ts --init` writes the signing key, the cookie keys, the operator's password and its argon2id hash, and every static client's secret, where `deploy/.env` has none, in one write. It derives the hash again when it does not verify against the password or is not a whole argon2id hash, holding a password it must hash to 12 characters, and reads the hash trimmed, as the server does; with the password's line removed it keeps the hash (quoting it if bare) and makes no new password; a hash in place that verifies is kept, its line quoted if bare, whatever the password's length; it refuses a password holding `'` (compose cannot read one inside a single-quoted line, and then reads none of the file) and a password line that holds `#` or `$` and is not single-quoted (the hashing script would keep a ` # note`, and compose reads every `$` in the file as a variable), as the check does; and it warns when anyone but its owner may read or write the file. Without a flag it reads `deploy/.env` as the server would, and also reports a mismatched hash, a service secret compose does not pass (with the line to add), and whether the profile is configured (`COMPOSE_PROFILES`). The env-file writer moved from `deploy/orchestration/provision.ts` to `deploy/env-file.ts`, shared by both.
- **Typechecked.** `deploy/auth/` has a tsconfig and the type-checked directories' pins plus `@types/oidc-provider` 9.12.1, and check 18 holds it with the others. The types found four loose spots in `server.ts`, none a behaviour change: the static clients' and resource servers' literal types, the token endpoint's client, and the exchange's token, which the library takes with no grant.
- **Check 14's `FILE_ONLY`.** `.env.example` documents `OB1_AUTH_OPERATOR_PASSWORD`, which no compose service forwards; check 14 now names such settings with the reason and refuses one that compose forwards.
- **Held by.** In CI: `store.ts --self-check` (25 probes) and `provision.ts --self-check` (88: the refusals, all at once and one by one, 18 origins, `--init` and the file check on scratch files, `tier.sh`'s own filter run on sample lines, and compose's `auth` block as written, held to its exact keys, mount, build, healthcheck, networks and volume, its hardening included); the full-stack job renders the profile (no port, the two networks, no Postgres, password or POC variable) and runs it: a blanked setting and an origin with a path refused together with exit 2; a client registered by DCR read back with its registration token after a restart (two starts in the log) and after a recreate; `/data` mode 700; an interaction with no session answered by the library's 400; a write to a store held locked answering 500, logged; and a stop that exits 0 inside 5 s with the server's own line. 90 mutants of the store, the checks, `--init`, the file check, the compose block and `tier.sh`'s filter each turn their self-check red: 36 were the author's own, two of them caught only once a probe was added (a uid another model holds; a P-384 key), and review passes 1–5 added the rest with the probes that catch them. The server on the memory adapter fails the restart check with a 401, without its SIGTERM handler the stop check, and without its `server_error` handler the locked-store check.
