## Changelog

readwise-capture becomes the `readwise` plugin (SMD-2690). The REST core serves its webhook at `/hooks/readwise/highlight` behind the brain's own webhook gate, and it captures each Readwise highlight once by its id, through the core as the hook's capture-only caller. What Readwise sends beside the text is kept in the plugin's own table, and `readwise_list_highlights` lists it. Its standalone server and its `READWISE_*` settings go. A highlight no longer carries its book's title and author, since a plugin makes no outbound call.
**Upgrading:** stop a running `bun integrations/readwise-capture/index.ts`, turn the plugin and its webhook on as `plugins/readwise/README.md` says (`OB1_PLUGINS`, `OB1_HOOKS`, `OB1_HOOK_SECRETS`, `compose.hooks-public.yaml`), and point the Readwise webhook at `https://<host>/hooks/readwise/highlight`. With a model provider that is not local, add `actor:hook:readwise` to `OB1_EGRESS_ALLOW`, or the default policy saves each highlight with no vector or extracted metadata. Its README's copy block copies the old server's highlights into the plugin's table. Don't run the old server beside the plugin.

## Record

readwise-capture becomes the `readwise` plugin, its webhook served by the brain (SMD-2690)

**What changed.** SMD-2690 is four PRs (decided 2026-11-05): PR 1, readwise; PR 2, agent-memory with its clients; PR 3, the core services smart-ingest needs (a model call on the plugin context, through the egress gate, and an evidence-append operation); PR 4, smart-ingest.
- **The plugin.** `plugins/readwise/`, registered in `plugins/registry.ts`, has one hook and one operation.
  - **The hook**, `highlight`. An empty body (Readwise's Test Endpoint) is answered 200, and so is any event but `readwise.highlight.created` that carries the secret; neither changes anything. The secret Readwise echoes in the body is compared with `OB1_HOOK_SECRETS`'s, digest to digest. A body over 512 KiB is refused before it is parsed. The highlight is held to the fields it reads: text with no NUL or lone surrogate, each field within a bound in characters as Readwise counts them (the passage 16,384, the note 8,192, the url 4,096, up to 100 tags of 128), positive whole ids. A time it cannot read as an ISO 8601 string is stored as none, never a reason to lose the passage. It is captured through `onceById`, keyed by the highlight id and kept for good (Readwise signs no time):
    - its content is the passage, with the note after it as the old server wrote it;
    - it is captured with `source: readwise`, `trust: ingested`, and the highlight's and book's ids as its only metadata;
    - the plugin's `highlights` row keeps the note, location, colour, url, tags and times, but not the text, which is the thought's alone; a row a later capture replaces takes its time of capture.
  - **Resends and failures.** A resend is answered with the first's thought, and one whose capture is still running is told 409; a claim whose capture never finished holds its id for an hour (the SDK's default lease, a capture's model calls and a minute, lets a stalled capture be captured twice). A core refusal is a 503 when retryable, else a 422. A row that fails to write gives the id back.
  - **`list_highlights`** (read): newest highlighted first, optionally by book, truncated past `limit`, each highlight marked `trust: ingested`, its fields being what the sender posted.
- **What it no longer does.**
  - **No book lookup.** A plugin makes no outbound call, so the Readwise API lookup goes (decided 2026-11-05): a highlight carries the book id alone. A books table the plugin can read is SMD-3878.
  - **No column writes.** A capture-only caller cannot set `source_type` or `type`, so the raw updates go.
  - **No metadata merge on known text.** A capture-only re-capture keeps the existing thought as it is.
  - **The old metadata.** The 13 metadata keys become two, the rest the plugin's row (decided 2026-11-05: detail past `capture_thought`'s 8 flat keys lives in the plugin's tables).
  - **Cost.** Each capture now runs the core's metadata extraction too.
- **`schemas/readwise-books` stays**, with its `community` grant: `recipes/readwise-import` (SMD-2149) still writes it. Its README and comments, and the import recipe's, name the plugin. The plugin's highlights are not found by its `get_book_highlights`, which reads `source_type`.
- **The server and its tests go.** `integrations/readwise-capture/` is deleted.
  - **test-auth:** its webhook constant and import, its in-process and under-Bun probes, and its text check go (212 assertions → 201).
  - **test-writes:** its section, the Readwise book stub, the secret settings and its SMD-1524 entry go, and `schemas/readwise-books` leaves the sidecars (150 assertions).
  - **The disposition and the connectors:** `docs/vendored-disposition.md`'s rows say it is a plugin, and `docs/connector-registry.json`'s artifact is `plugins/readwise` (taxonomy tables regenerated).
  - **The docs:** `primitives/deploy-remote-mcp` drops it from its servers. `plugins/README.md` lists it.
- **Which side of the version contract.** A plugin is in the image: a new one is a minor. The vendored server it replaces was outside the contract (MAINTAINING.md, "Versioning").

**Why.** SMD-1931 kept the three surface-bearing vendored integrations as plugins (`docs/vendored-disposition.md`): each was a server of its own with its own key check, reaching core tables with raw SQL. readwise-capture also embedded at a fixed 1536 width the brain's default 1024 refused, and wrote `thoughts` directly.
