## Changelog

agent-memory-api becomes the `agent-memory` plugin (SMD-2690). A runtime's write-back captures each memory as a thought through the core, and its provenance, review, use policy and recall traces live in the plugin's own tables: the old `schemas/agent-memory` tables' columns, in `plugin_agent_memory`. A recall searches through the core. The eight routes are tools on the brain's connector and REST routes under `/v1/plugins/agent-memory/`, the request versions kept and every answer the old memory shape, with the changes its README lists: three routes move, `/health` goes, refusals are codes, and a capture key can write back, never confirming. The standalone server and `schemas/agent-memory` go. A plugin operation may now refuse with a retryable 503, for a service it needs that did not answer. The Hermes and OpenClaw clients call the plugin's routes from their 0.2.0. A plugin's operation can ask the brain's model (`ctx.model.chat`), judged by the egress gate for its caller and plugin: under `deny` only `OB1_EGRESS_ALLOW=plugin:<name>` lets its calls out, not an `actor:` or `marker:` term; under `allow` a row's `source:`, `type:` or `topic:` deny term never holds one (preflight warns). A write key can append an evidence entry to a thought (`append_thought_evidence`), an edit the event log records. smart-ingest becomes the `smart-ingest` plugin: a document's thoughts extracted by the brain's model, matched by meaning through the core's search, and added, skipped, appended as evidence or written as revisions through the core, optionally after a dry run that stores each decision; a job counts what was done, an add or evidence already there as `existed`.
**Upgrading:** stop a running `bun integrations/agent-memory-api/index.ts`, add `agent-memory` to `OB1_PLUGINS`, and copy the old tables' rows across with `plugins/agent-memory/README.md`'s block. Move the Hermes client and the OpenClaw plugin to 0.2.0 at the same time, each endpoint `https://<host>/api/v1/plugins/agent-memory`: link the OpenClaw plugin from the repository until ClawHub has 0.2.0, since 0.1.6's usage, trace and review-queue tools call routes the plugin does not have. With a model provider that is not local, add `actor:<key name>` to `OB1_EGRESS_ALLOW` for each runtime's key. A memory the old server recalled while restricted but never confirmed is left out of a plain recall now: confirm it or mark it `evidence_only` (or recall with `include_unconfirmed`). `--grant`'s `community` group no longer grants the old tables; a grant made before stays until they are dropped. For smart-ingest: stop a running `bun integrations/smart-ingest/index.ts`, add `smart-ingest` to `OB1_PLUGINS` (and, with a chat endpoint that is not local under `deny`, `plugin:smart-ingest` to `OB1_EGRESS_ALLOW`), and copy the old jobs with `plugins/smart-ingest/README.md`'s block before its first ingest; its callers move to the plugin's routes, a write key and its answer (the README's table). `--grant` no longer grants `ingestion_jobs`, `ingestion_items` or `append_thought_evidence(uuid, jsonb)`, and a grant made before stays until they are dropped; `brain-health-monitoring`'s `ops-views.sql` no longer makes `ops_ingestion_summary`. The README gives the order to drop them in.

## Record

agent-memory-api becomes the `agent-memory` plugin, and a plugin's 503 is its one retryable refusal (SMD-2690)

SMD-2690 is four PRs (decided 2026-11-05): PR 1, readwise (released in 2.0.0, change 491); PR 2, agent-memory with its clients, split in two (2a the plugin, this record; 2b the clients, decided 2026-11-06, its section below); PR 3, the core services smart-ingest needs; PR 4, smart-ingest.

**What changed.**
- **A plugin's retryable 503** (SMD-1992's answer, decided 2026-11-05). `PluginRefusal` takes 503. `runOperation` marks a 503 retryable and every other refusal not, whatever the plugin's own facts say, on both transports, and the REST core sends a plugin's 503 with `Retry-After`, as the OpenAPI document's 503 says. The document's plugin answers describe it, and `plugins/README.md`, the template's `AGENT_SPEC.md` and `plugin/index.ts` state the rule.
- **The plugin.** `plugins/agent-memory/`, registered in `plugins/registry.ts`: eight operations over eight tables. `001_memories.sql` keeps the old schema's columns with the `agent_memory_` prefix dropped, and no foreign key into the core. `agent_memory_hash_text` and the `updated_at` trigger go: the hash is computed in the plugin, and the writes set the time.
  - **`writeback`** (capture; the old server took a write key, and refused a capture key outright). Each memory is captured through `capture_thought` with `source: agent-memory`, the runtime's declared trust and six flat `agent_memory_*` keys. The old server wrote `source_type`, `topics`, `people` and a nested object, which a capture through the core does not take. The unsafe check is the old server's, unchanged. The idempotency key is the old one (a colon or percent sign in a part now escaped), so a migrated memory keeps its key, but a workspace's own, indexed by its md5 (the old index was global, so a write-back to one workspace was answered another's memory); a key already holding other text, or losing a race to a write-back of other text, is refused, so a write-back is never answered another memory's text. A key that can only capture writes back but never confirms (its `user_confirmed` or `imported` is recorded as `generated`; a memory already written is confirmed with `review_memory`, never by its write-back sent again) and is answered each memory's id and its write-back's thought alone, as a core capture is (decided 2026-11-07). A write-back holds at most 50 memories. An edit keeps the memory's hash, so the write-back sent again still answers it (to a key that can only capture, its id and the thought its write-back captured, kept in `metadata.written`, which the README's copy block writes for a migrated memory). An `artifact_reference` keeps its own artifact (the old server gave each one every artifact of its write-back). A thought saved with no vector, the provider down or the egress policy keeping the text in, still gets its memory: the vector mender fills it in. A core refusal is a 503 when retryable, else a 422.
  - **`recall`** (read). `search_thoughts` reads four candidates per memory asked for (at least 20, the core's 100 at most), and the hits are joined to the workspace's memories. Scope and ranking are the old server's, but a memory a person never confirmed is left out without `include_unconfirmed` whatever review it had since (the old server's test read `pending` alone). A search that finds nothing answers no memories (the old server answered the workspace's newest). A query the provider did not embed is refused `PROVIDER_UNAVAILABLE`, the plugin's first retryable 503. Only a write key's recall is traced, as before.
  - **The others.** `record_usage` and `review_memory` (write); `review_queue`, `list_memories`, `get_memory` and `get_recall` (read). `/recall/:id/usage`, `/recall-traces/:id` and `/memories/review` become `/recalls/{request_id}/usage`, `/recalls/{request_id}` and `/review-queue`: a route beside `/memories/{memory_id}` may not match its request. Every answer is the old memory shape plus its type, thought, review and lifecycle status. A review records the key's name as its actor (the old server took the body's). `restrict_scope` takes only the five visibilities, and never a wider one than the memory's (the old server took any word, and failed with a 500 on one not of the five). A confirm makes a memory active again and usable as evidence. `record_usage` marks each memory once however often one list names it (one in both lists is left ignored). `review_queue` lists what waits for a person's confirmation, a restricted memory no one confirmed among them, and nothing rejected, stale, disputed or superseded. An edit of the content alone takes the new content's summary when the text changes (the old server kept the old one, so a redacted text stayed in every recall). A merge or supersede checks the other memory exists. An edit's text is held to the write-back's unsafe check and captured as a thought of its own, which the memory then names: the core keeps one thought per text, so the old thought may be another memory's.
  - **Bounds.** A memory is at most 16,384 characters, a recall's query 4,000, an id or label 200, a uri 4,096, a list 50, a record 50 keys; a summary is cut between characters. Every stored text holds no NUL and no lone surrogate. **SMD-3308** (canceled) goes with the server. The plugin's four GETs are the REST core's, which serves with `idleTimeout: 255`.
- **What goes.** `integrations/agent-memory-api/` (its server, README and smoke scripts; PR 2b brings the clients onto the plugin) and `schemas/agent-memory/`. `db/config.mjs`'s `community` group loses the eight tables (`db/README.md`'s row with it). test-live and test-schema count 12 schema files.
  - **test-auth:** it was the last HTTP API behind the shared auth module (smart-ingest, the other, checks its one key itself). The rest kind goes with its route classifier (`RPC_READS`, `LOG_TABLES`), and the auth module's shadowing checks (a gateway's bearer beside `?key=`, a stale header, no Accept header) move to a worker. **test-writes:** its section, its arm of the trust block, and its named-key arm go. The named-key arm was its one witness, and the plugins name their caller through the core. `schemas/agent-memory` leaves the sidecars.
  - **The docs.** The README and `integrations/README.md` indexes drop it, and `plugins/README.md` lists the plugin. `primitives/deploy-remote-mcp`, the shim README's example, `docs/vendored-disposition.md`'s rows, the GPT context, per-agent-identity's README and the screenshots README are updated. The clients' READMEs link the plugin, and say they call the old routes until PR 2b (below). The checker's check 47 and check 54 entries for the deleted files go.

### PR 2b: the clients on the plugin

**What changed.** The repository's two clients of the old server, and the recipes and skill beside them, call the plugin's routes and read its answers. A brain on 2.0.0 or earlier keeps the clients' old versions.
- **Hermes** (`integrations/hermes-agent-memory`, 0.2.0). `endpoint` is the plugin's REST base, `https://<host>/api/v1/plugins/agent-memory`. Usage, the trace and the queue are on the new routes. The queue and listing were `POST /memories/review` and `POST /memories/list`, which the old server never had (it served both as GETs): the provider's review-queue tool always failed. A review sends the reviewer as `actor_label`; the plugin refuses the old `reviewer` field. An edit takes `content` and `summary`; one with neither is refused before it is sent. A refusal raises `OB1RequestError`, with the plugin's code, its status and a 503's `Retry-After`, and so does a 2xx that is no JSON object, an empty one among them. A write-back of more than ten memories goes in parts of ten, each under a write-back timeout of its own (`writeback_timeout`, 60 s): the plugin takes at most 50 at once, a long session's end extracts up to 60 findings, and each memory is a capture with its model calls. Each part has its own key or step (`:part<n>`), so the same text at the same index of two parts is two memories, as in one write-back; the parts' keys are their own, so the same payload sent whole by another client is keyed apart. Exit waits for write-backs at most one `writeback_timeout` (the maintainer's call, 2026-11-08, over waiting for every part or extracting fewer findings): a session end's write-back runs in the background, holding its caller at most the 2 s it gives the write-back before it, and gets that long, its deadline fresh each time, since Hermes ends sessions mid-process too (`/new` on Hermes's background worker, and a compression inside a turn) and serves on; shutdown shares the last session end's deadline while it is ahead, as at exit, and waits for every background write-back, not only the latest; the client starts no part after shutdown's deadline; what the deadline left out is logged at warning, a part never started as not written back and one whose wait it cut as unconfirmed (the plugin finishes it). Hermes's CLI kills its own exit after `HERMES_EXIT_WATCHDOG_S` (30 s), so the README says to set it about 15 s above `writeback_timeout`; shutdown logs what is outstanding before it waits. A session ended twice with the same transcript (the TUI's finalize and close) is written back once. Review pass 6 proposed dropping the deadlines for one request of up to 50 under the 8 s read timeout, the plugin finishing a write-back its caller stops waiting for; the maintainer kept this design and its patches (2026-11-08). Recall context reads a memory's time from `freshness`. The `GET /health` probe at start goes: the plugin has no such route.
- **OpenClaw** (`integrations/openclaw-agent-memory`, 0.2.0, `dist/index.js` rebuilt). It moves to the same routes, sends `content-type` only with a body, and encodes a path's id. It passes on only the fields each route takes (`FIELDS`), so a field a model adds to a tool's arguments is dropped where the plugin would refuse it. A refusal throws `AgentMemoryError` with the code; a body that is not JSON, and a 2xx that is no JSON object (an empty 204 among them), throw one too, never a bare parse error. `openbrain_review_memory` drops `actor_id`, which the plugin refuses, and holds `visibility` to the plugin's five. The memory corpus reads `get_memory`'s `{memory, …}` and a memory's `memory_id` and `freshness`; it read `id` and `updated_at` off the top level, where the old recall answered neither and the old get_memory nested them under `memory`. Its mapping lives in `client.ts` (`corpusHits`, `corpusDocument`), where the suite drives it. `src/index.ts` declared its own copies of the tool schemas beside the import of `src/tool-schemas.js`, and the build kept the copies: the record schemas 0.1.5 replaced were what shipped. They go, so the schemas `schema:check` reads are the ones built. ClawHub still serves 0.1.6 until the package's owner publishes 0.2.0, and its usage, trace and review-queue tools call routes the plugin does not have: the READMEs say to link 0.2.0 until then.
- **The recipes and skill.** `recipes/openclaw-agent-memory` names the plugin's routes. Its recall-response contract allows the plugin's added fields (`thought_id`, `memory_type`, `review_status`, `lifecycle_status`, an artifact's `description`) and a provenance of `disputed` or `superseded`: it allowed no others, so the plugin's answer broke it. Its usage example sent `ignored_memory_ids` and `usage_notes`, which neither server took, and now sends `ignored: [{memory_id, reason}]`. The examples' file entities name the plugin's files, and the three OpenClaw recipes' and the skill's metadata drop Supabase (and Deno). **Not changed:** `docs/assets/agent-memory`'s diagrams say "OB1 Agent Memory API" for the contract, which the plugin still serves (the recall lifecycle's usage route alone moves to the plugin's, in its source and its SVG); their README already says where the tables went.
