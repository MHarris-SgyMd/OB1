## Changelog

Fork Checks' Portable server job no longer runs the same assertions in both of test-server's passes, and its idle-timeout measurements wait once a run, not four times (SMD-3201).

## FORK

Suites stop re-proving what no MCP server under test reaches (SMD-3201)

**What changed.**
- **A new suite, `server-portable/test-entry.ts`, runs once.** It holds test-server's [13a], [13c] and [13d], except [13d]'s counted call, as its [1], [2] and [3]:
  - brain-info.ts's rules;
  - a keyed /health's deadline on child servers;
  - the stop on child servers, the drain's bounds, the call count, and the grace period's parse and where compose and preflight read it.

  None of these read the server under test. They spawn `bun --no-env-file index.ts` or call a module, whatever `OB1_MCP_UNDER_TEST` says, so test-server's REST-client pass ran them a second time. test-server keeps [13d]'s count of a tool call whose client left, which does read the server under test, in both passes. The children get the env test-server's top gave them: one access key, no store, and a local provider stub. The suite has its own step in Portable server and a line in db/ci-parity.sh; checks 34 and 35 refuse it unrun.
- **test-server [17]'s REST-client pass** no longer measures the bare, kept and capped servers. Those test the runtime's premise and sse.ts's ceiling, which the index pass holds. Nor does it wait for a 13 s embedding. It holds the MCP server's own wrap at its timing knob (`useKeepaliveTiming({ intervalMs: 100, maxMs: 2000 })`):
  - frames through a 1 s embedding;
  - the call's envelope;
  - a client that leaves at 300 ms while its call runs, logged once at that moment.

  The index pass is unchanged.
- **extensions/test-auth's mcpReply probe** waits SSE_KEEPALIVE_MS + 600 ms, where it waited 13 s, and asserts one or more `: keepalive` frames. That proves mcpReply wraps. Its sse.ts is a byte-for-byte copy, held by the same suite, of the file whose frames test-server [17]'s index pass carries past the last sweep. Its header no longer says "slower than the idle timeout".
- **test-rest [16]'s two 14 s idle probes** start before section [1], and [16] awaits them. Their wait now overlaps every other section.

**Why.** Fork Checks runs 39707442097 and 39706512002 measured [13a], [13c] and [13d] at 1.2, 2.8 and 12.0 s, the same in both passes. Bun's idle timeout was measured four times a run, each with 13–14 s of waiting. test-rest's probes ran after every other section, with nothing else waiting on them.

**Measured locally**, Bun 1.4.3:

| Suite | Before | After |
|---|---|---|
| test-server, index pass | 1183 assertions, 47.6 s | 1061, 32.0 s |
| test-server, REST-client pass | 1183, 46.9 s | 1055, 19.1 s |
| test-entry (new) | — | 122, 15.8 s |
| test-rest | 480, 56.9 s | 480, 42.9 s |

That comes to about 42 s off Portable server's steps, and about 7 s off the job that runs extensions/test-auth.

**Mutants**, each killed:
- the MCP server's keepalive off (an interval of an hour): [17]'s client pass, frames 0;
- an mcpReply that writes no frames: test-auth's frames row;
- test-rest's held probe served at Bun's default idle timeout: [16]'s "at 255" row;
- test-entry left out of fork-checks.yml: checks 34 and 35.

**At SMD-2287 PR 6** the index pass goes with `OB1_MCP_UNDER_TEST`. Two things live only there now and must move:
- test-server [17]'s runtime premise (bare, kept, capped), to test-entry or the surviving pass;
- the call carried past the last sweep, to the surviving pass at the default timing.

The rest of item 4, deleting the five index-mode steps and folding the index-only sections into the surviving pass, is that PR's.
