## Changelog

Fork Checks' Portable server job no longer runs the same assertions in both of test-server's passes. Of the four waits past Bun's idle timeout a run made, test-server's REST-client pass and extensions/test-auth no longer make theirs, and test-rest's now overlaps its other sections (SMD-3201).

## FORK

Suites stop re-proving what no MCP server under test reaches (SMD-3201)

**What changed.**
- **A new suite, `server-portable/test-entry.ts`, runs once.** It holds test-server's [13a], [13c] and [13d], except [13d]'s counted call, as its [1], [2] and [3]:
  - brain-info.ts's rules;
  - a keyed /health's deadline on child servers;
  - the stop on child servers, the drain's bounds, the call count, and the grace period's parse and where compose and preflight read it.

  [3] adds one child: a tool call whose client has left, still running when SIGTERM lands, holds the stop until it ends. Nothing held index.ts's stop to its count of tool calls before. That count could be dropped from the stop with every suite passing; now [3] fails.

  None of these read the server under test. They spawn `bun --no-env-file index.ts` or call a module, whatever `OB1_MCP_UNDER_TEST` says, so test-server's REST-client pass ran them a second time. test-server keeps [13d]'s count of a tool call whose client left, which does read the server under test, in both passes. The children get what of test-server's env these rows read, one access key and no store, plus a local provider stub that holds [3]'s tool call. test-server's named keys and OAuth settings are read by none of them; a mutant adding them back changed no row. The suite has its own step in Portable server and a line in db/ci-parity.sh; checks 34 and 35 refuse it unrun.
- **test-server [17]'s REST-client pass** no longer measures the bare, kept and capped servers. Those test the runtime's premise and sse.ts's ceiling, which the index pass holds. Nor does it wait for a 13 s embedding. It holds the MCP server's own wrap at its timing knob (`useKeepaliveTiming({ intervalMs: 100, maxMs: 30_000 })`):
  - frames through a 1 s embedding;
  - the call's envelope;
  - a client that leaves at 300 ms while its call runs, logged once at that moment.

  The index pass is unchanged.
- **extensions/test-auth's mcpReply probe** waits SSE_KEEPALIVE_MS + 600 ms, where it waited 13 s, and asserts one or more `: keepalive` frames. That proves mcpReply wraps. Its sse.ts is a byte-for-byte copy, held by the same suite, of the file whose frames test-server [17]'s index pass carries past the last sweep. Its header no longer says "slower than the idle timeout".
- **test-rest [16]'s two 14 s idle probes** start before section [1], and [16] awaits them. Their wait now overlaps every other section.

**Why.** Fork Checks runs 39707442097 and 39706512002 measured [13a], [13c] and [13d] at 1.2, 2.8 and 12.0 s, the same in both passes. Bun's idle timeout was measured four times a run, each with 13–14 s of waiting. test-rest's probes ran after every other section, with nothing else waiting on them.

**Mutants**, each killed:

- an mcpReply that writes no frames: test-auth's frames row;

**At SMD-2287 PR 6** the index pass goes with `OB1_MCP_UNDER_TEST`, and the `server` service with it. Three things must move:
- test-server [17]'s runtime premise (bare, kept, capped), to test-entry or the surviving pass;
- the call carried past the last sweep, to the surviving pass at the default timing. With the index pass gone it is the only row holding SSE_KEEPALIVE_MS against Bun's idle sweep: test-auth's probe waits SSE_KEEPALIVE_MS + 600 ms, so it stretches with the constant;
- test-entry [2] and [3]'s child servers, which spawn `bun index.ts`: to the entries that remain (api.ts, mcp-server/index.ts), or they test an entry nothing runs.

The rest of item 4, deleting the five index-mode steps and folding the index-only sections into the surviving pass, is that PR's.

**Seen, not this change's.** Nothing holds either MCP route's abort listener (mcp-server/app.ts, index.ts): Bun 1.4.3's body cancel calls `onCancel` at the same moment, and every suite passes with the listener removed. It matters only for a client gone before the stream exists, such as during a hung registry lookup.
