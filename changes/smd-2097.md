`db/test-schema.ts` loads its three large match_thoughts fixtures ([8c], [8d], [8e]) with the walk's HNSW index dropped and builds it again afterwards, and drops it for [8e]'s emptied band, so those sections take 14 s of a 23.5 s run where they took 70 s of 79 s (SMD-2097).

## FORK

test-schema.ts loads its match_thoughts fixtures without the HNSW index and builds it after: 70 s of the run down to 14 s (SMD-2097)

**What changed.** The fixture loads in [8c] (1,201 rows), [8d] (1,505 rows, 305 with a vector) and [8e] (1,000 rows) now go through one helper, `loadWithoutWalkIndex`. It reads `thoughts_embedding_idx`'s definition with `pg_get_indexdef`, drops the index, empties `thoughts`, runs the section's own inserts unchanged, and rebuilds the index from that definition, in a `finally`. [8e]'s VACUUM, which compacts the heap before the load, runs inside it. [8e] also drops the index before it deletes its eight-page band, since from there on the section reads only the heap: the pinned probe, its buffer count and the random draws. At the section's end it deletes the rows, which [9] deletes anyway, and builds the index over the empty table. Every row, seed and quoted count is unchanged, and the suite stays at 1625 assertions at each width.

**Why, measured.** The ticket listed three candidates: HNSW maintenance per row, the write triggers, and one statement per row. The loads were already multi-row `INSERT … VALUES` in batches of 100. A probe loaded [8c]'s 1,200 rows at 1024 dims into a migrated PGlite:

| Load | Insert time |
| --- | --- |
| As shipped | 28.6 s |
| Triggers off (`session_replication_role = replica`) | 28.9 s |
| HNSW index dropped | 1.2 s |
| HNSW dropped, triggers off | 1.2 s |
| Index rebuilt over the 1,200 rows | 4.8 s |

Generating the vectors in JS took 0.1 s. A per-statement timer over the whole suite showed two more costs of the growing graph:
- [8d]'s three 100-row inserts took 3.9, 3.8 and 3.6 s. [8c]'s rows were deleted but never vacuumed, so the graph still held 1,201 dead nodes that every insert walked.
- [8e]'s band `VACUUM` took 6.8 s, repairing the graph around 520 deleted rows.

The ticket's fourth load, "the vacuum band", is that VACUUM.

**Held.** Both suites were run side by side on an 18-core Mac, at both widths, four runs at once. The normalised logs (UUIDs, timestamps and xmin values masked) differ only in lines that also differ between two runs of the original:
- [8e]'s random sample draws;
- ties ordered by random UUIDs;
- recency scores read off the clock;
- one audit feed that sorts a shared `created_at` by id;
- the order of three equal-weight board rows.

[8c]'s overlap reads 30/30 in both versions at both widths. Six mutants, run against this tree at 1024:

| Mutant | Result |
| --- | --- |
| The walk drops its metadata filter | "…every one of them matching the filter" fails, and overlap drops to 24 |
| The walk returns 5 candidates in place of `v_fetch` | "the walk returns 10 rows" fails, with 15 returned |
| [8e]'s probe join is INNER, not LEFT | the pinned probe over the emptied band "draws 0 pages" (this runs after the index is dropped) |
| The probe's upper bound is `<=` | the probe "touches 16 buffers", also after the drop |
| The routing collection counts unscoreable rows | only the two source-text checks fail |
| The helper never rebuilds the index | the suite stops at [8d], where the next load finds no `thoughts_embedding_idx` to read |

The routing-collection mutant behaves the same on origin/main. [8d]'s own assertion was never able to catch it, because without `ANALYZE` the planner takes the GIN bitmap and a sort for the walk, so the one-tuple clamp on HNSW never applies. After `ANALYZE thoughts` the same statement plans as `Index Scan using thoughts_embedding_idx`. That gap predates this change and is filed as SMD-2151. This change builds the index before every `match_thoughts` call, so it stands whichever way SMD-2151 goes.

The db typecheck passes.

**Measured after.** On the Mac, with the four runs at once:

| Section | 1024 before | 1024 after | 768 before | 768 after |
| --- | --- | --- | --- | --- |
| [8c] | 29.4 s | 7.1 s | 22.6 s | 5.2 s |
| [8d] | 10.6 s | 1.3 s | 8.6 s | 1.0 s |
| [8e] | 30.3 s | 5.9 s | 22.7 s | 4.4 s |

The CI timings come from the PR's run.

**Not taken.**
- Turning the triggers off does nothing for the time, as measured above.
- Smaller fixtures: the ticket keeps the rows byte for byte, and [8e]'s band needs a heap of at least eleven pages.
