## Changelog

The operator GUI's session cookie carries the origin's port when the origin names one (`ob1_dashboard_session_8010` at `http://127.0.0.1:8010`), so one browser stays signed in to two brains reached on one machine. Before, a browser kept one cookie for both (cookies are per host, not per port), and signing in to one brain's dashboard signed the browser out of the other. An origin on its default port, such as a configured https one, keeps the bare name. The upgrade signs every GUI session out once, as any restart of `app` already does (SMD-3352).

## FORK

The GUI's session cookie carries the origin's port — two brains on one machine no longer sign each other out (SMD-3352)

**What changed.**
- **`dashboard/src/lib/server/listener.ts`:** `sessionCookieName(breakglass, port, url)` names the origin's cookie `ob1_dashboard_session_<port>` when the request's URL names a port, and `ob1_dashboard_session` when it names none (an origin on its scheme's default port). The break-glass name is unchanged (`ob1_dashboard_breakglass_<port>`, SMD-3307). The URL is SvelteKit's: `OB1_PUBLIC_ORIGIN`'s when set, else the Host the request was reached at (`serve.ts`).
- **`hooks.server.ts`** passes `event.url`. Sign-in, the AS callback, sign-out, `signOutHere` and the hook's stale-cookie delete already read `locals.sessionCookie`, so all of them follow.
- **`smoke.ts`, `smoke-oauth.ts`, `smoke-breakglass.ts`** each work out the name from the origin they drive. They write the rule out rather than import it, so a GUI that drops the port fails `smoke.ts` in CI.
- **CI:** the configured GUI's "set no session cookie" grep matches the port-named cookie too.
- **`dashboard/README.md`** says why the name varies.

**Why.** Browsers keep one cookie per host and name, whatever the port (RFC 6265 §8.5). Two unconfigured brains at `http://127.0.0.1:18352` and `:18353` therefore shared `ob1_dashboard_session`. Signing in to B overwrote A's session id. A's hook then found an id it doesn't hold and deleted the cookie, signing the browser out of B as well. Reproduced on two scratch stacks with the mutant below, which is main's behaviour: in Chromium, Firefox and WebKit, after signing in to A then B, A's overview was the sign-in page and B's was too. This Mac's stable (:8010) and canary (:8011) are that case once both serve the GUI.

**Held.**
- **`test-oauth.ts`**, one row: two loopback ports get two names, as do the default ports 443 and 80 with the bare one, `https://…:8443` gets `_8443`, and the break-glass name is its own whatever the origin. Three mutants were killed: the port dropped, the port always named, and the break-glass name taking the origin's port.
- **`smoke.ts`** in the full-stack job reads the cookie at `http://127.0.0.1:8010` under `ob1_dashboard_session_8010`.
- **Live, before merge:** two unconfigured scratch stacks from this branch, with one browser profile in each of Chromium, Firefox and WebKit. Sign in to A, then B, then load A's overview, B's, and A's again: all render signed in, with both cookies held. Under the mutant (the port dropped, both stacks rebuilt), every engine fails.

**Not taken.** The stack's project name in the cookie: the GUI isn't handed it, and the port already tells brains on one host apart. Two stacks can't publish one port. Deleting a leftover bare-named cookie: it names a session no restarted GUI holds, is never read, and expires within its day.

**Not in the version contract.** The cookie's name is the GUI's own, set and read by the GUI alone. No client sends it, so this rename is a `patch`.
