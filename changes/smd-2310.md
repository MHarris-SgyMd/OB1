## Changelog

Plugins in the REST core (SMD-2310): a curated `plugins/<name>/` manifest whose operations, enabled by `OB1_PLUGINS`, join the one contract — REST routes under `/v1/plugins/<name>`, MCP tools named `<name>_<operation>`, the OpenAPI document and whoami — behind the core's scope gate; its tables in a schema and role of its own, applied by the migrator into `plugin_migrations`, and its SQL run on a login role, `ob1_plugins`, that the migrator makes with a new secret, `OB1_PLUGIN_DB_PASSWORD`, and that holds nothing on the core; `GET /v1/plugins` for the GUI's nav; check 31 holds plugin code to its schema and role.

## FORK

Plugins in the REST core — a contribution's operations join the brain's one contract behind its scope gate, enabled by name (SMD-2310)

**What changed** (PR 1 of 4: the contract).
- **The plugin shape.** A plugin is a directory, `plugins/<name>/`, a new curated category (`metadata.json` category `plugins`). Its `index.ts` exports a manifest built with `server-portable/plugin-sdk.ts` (`definePlugin`, `operation`, `ok`, `refuse`, and zod, re-exported so a plugin resolves no package from its own directory). Each operation declares:
  - a title, a description, and the scope a key needs (`read`, `capture` or `write`);
  - its REST method and a path under the plugin's own;
  - an input and an output as zod shapes;
  - a handler `(ctx, input)` that answers `ok(value)` or `refuse(status, CODE, facts)`.
- **Loading.** `plugins/registry.ts` imports every plugin in the tree by name (no `import()` by a name the environment gives). `OB1_PLUGINS` (comma-separated) picks which run; unset, none.
  - `core/plugins.ts` checks every manifest, enabled or not. It refuses:
    - a malformed name, key, path, scope or method;
    - a path field no input names, one named twice, one that is not a string, or one that is optional or defaulted;
    - two operations whose routes one request could match (`/items/{id}` beside `/items/latest`);
    - an output schema that transforms (MCP holds the answer to it a second time);
    - a tool name the core or another plugin holds, or one over 64 characters (the Claude API's limit).
  - A name that is no plugin, or one given twice, refuses to start. Preflight's new `plugins` row fails first, and `serveHere` stops the entry before its first request.
  - The three-tier stack runs none (check 27's `TIER_OMITTED_ENV`).
- **Projection.** An enabled plugin's operation is:
  - an MCP tool `<plugin>_<key>` (a hyphen in the plugin's name read as `_`), registered only where the key's scope reaches it, with its output schema and, for a read operation, the read-only hint;
  - a REST route `/v1/plugins/<name>/<path>`, with the core routes' input rules (the query string or the body, path fields, strict schema, HEAD runs nothing). It answers `FORBIDDEN needs <scope>`, a plugin's refusal at its status (400, 403, 404, 409, 422) with its code and facts, never retryable on either transport, and a fault, or a value its output schema refuses (held twice, as the MCP SDK holds it again), as `FAILED`;
  - an OpenAPI operation under the tag `plugin:<name>`, with `x-ob1-scope`, `x-ob1-plugin` and its output schema as the success schema;
  - an entry in whoami's `operations` for a key whose scope reaches it;
  - in the request line (SMD-1849), its route's template (`{field}` spelled `:field`) and its tool name, which `telemetry.ts`'s `knowTools` adds beside the core's for the enabled plugins, so neither is `?`.
- **One gate.** `tools.ts` gains `unlocks(caller, group)`, the rule `mayCall` applies: a plugin operation of a group is reached by the same keys as a core tool of that group.
- **Core data through the core.** `ctx.call(name, input)` runs a core operation as the caller, through `core/calls.ts`, the one table from a tool name to its core function that `rest/routes.ts` now reads too. It asks `mayCall` first (a read key cannot capture through a read operation: `FORBIDDEN`, and the core never runs) and holds the input to the operation's schema (`REFUSED_INPUT`). A write through it names the caller on its audit row. Its answer is the operation's whole value, so what reaches a plugin's caller is what its output schema declares (`plugins/README.md` says to declare no more than the caller may see).
- **Landing.** A change under `plugins/` asks for a fragment, as one under `server-portable/` does (`scripts/check-landing.ts`, CONTRIBUTING). `release.yml`'s PR paths include `plugins/**`, which the image now copies.
- **check 25.** The plugin host lives in `core/`, and the transport files reach it through `core/index.ts`. `root.ts` gains `plugins()`, the enabled set read once, which `index.ts` and `api.ts` may import, and its own import of `core/plugins.ts` (`loadPlugins`).
- **The image** keeps the checkout's layout under `/app` (`server-portable/`, `db/`, `plugins/`, `releases.json`), so a plugin's `../../server-portable/plugin-sdk.ts` and the server's `../db/` resolve as in a checkout; before, the server sat at `/app` and `db/` at `/db`.
- **The example plugin** (`plugins/example/`): `example_recent`, a read operation that lists the newest thoughts' ids, types and capture times through `ctx.call("list_thoughts")`.

**What changed** (PR 2 of 4: tables).
- **The migrator.** `db/migrate.ts` applies the migrations of the plugins `OB1_PLUGINS` names, after the core's and only when the core's are clean. They are `plugins/<name>/migrations/NNN_name.sql`, under the core's naming rule.
  - **Role and schema.** Each plugin gets a role, `ob1_plugin_<name>` (NOLOGIN), and a schema it owns, `plugin_<name>` (`db/config.mjs`'s `pluginIdents`). Both are made by any run that names the plugin and finds either missing, even with nothing pending, and are never dropped. A schema restored without its owners (`--no-owner`, as a tier's refresh restores, or into a cluster without the role) is handed back to the role with every relation, routine and type in it another role owns (`db/config.mjs`'s `pluginForeignOwned`, which preflight reads too). A run with both in place and nothing pending asks the migrator no privilege. A migrator that is no superuser takes `SET` membership in the role it made (PG 16 gives a CREATEROLE role ADMIN alone). After each file the session's temp tables go.
  - **How a file runs.** Each file runs under `SET LOCAL ROLE` with that schema first on the path. A reference to a core table is refused by Postgres and records nothing.
  - **The ledger.** Files are recorded in `plugin_migrations (plugin, name, sha256, applied_at)`, beside `schema_migrations`, so nothing that reads the core's ledger sees them. An edited file is a drift.
  - **Dry run and refusals.** `--dry-run` lists each plugin's pending files, the sha, and the role and schema each would run as, and makes nothing. `--baseline` and `--reapply` leave plugins to a plain run. A name that is no plugin, or one given twice, is refused before anything runs.
  - **A plugin not named** is not read: its schema, tables and rows stay.
  - **Where it runs.** The compose migrator reads `OB1_PLUGINS`, and its image copies `plugins/`. The tier migrators leave it out, as the tier servers do.
- **`ctx.db.tx(fn)`**, the plugin's own tables at runtime. It goes through `store-sql.ts`'s `pluginTx`: one transaction under the same role and search path, handed a tagged template alone (bound parameters, no `unsafe()`). Each plugin runs on a pool of its own, so a temp table, session setting, advisory lock or held cursor its SQL leaves never meets a core query or another plugin. The PostgREST store has none, and says so.
- **Preflight's `plugin tables` row** fails when an enabled plugin with migrations lacks its role or schema, when the role it reaches the tables as cannot `SET ROLE` to it (the `SET` option on PG 16; the server's role here, `ob1_plugins` from PR 3), when the schema or a table in it is another role's, or when the ledger lacks a file or records it at another sha. The `plugins` row fails a plugin with tables on the PostgREST store.
- **The example plugin** gains `migrations/001_notes.sql` (`notes`, keyed to a thought by id: no foreign key into the core). It also gains `example_add_note` (write; it checks the thought through `ctx.call("fetch")` first, and `written_by` is the caller's key) and `example_list_notes` (read).
- **Limits.** `SET ROLE` holds a plugin's SQL to its tables only while that SQL does not undo the role; PR 3 moves every plugin's SQL onto a login role that holds nothing on the core, so undoing it reaches nothing either. `dropSchema` in the suites drops the plugin schemas and their ledger. Check 12's SQL rules cover `plugins/`.

**What changed** (PR 3 of 4: the boundary, the GUI registry, the docs).
- **The plugin login role.** Every plugin's SQL runs on a connection logged in as `ob1_plugins` (LOGIN, NOINHERIT, no superuser), then `SET LOCAL ROLE` to the plugin's own: the servers' per-plugin pools (`store-sql.ts`'s `pluginTx`) and the migrator's plugin phase alike. It holds `SET` on each plugin's role and nothing on the core, so SQL that undoes the plugin's role (`END;`, `RESET ROLE`, a quoted or escaped `role`) lands where Postgres still refuses the core's tables — the boundary is the database's, not the code's good behaviour. The migrator makes the role once with `OB1_PLUGIN_DB_PASSWORD` (a new secret, forwarded to both servers and the migrator, left out of the tiers) and never alters an existing one's password; a run that would apply a plugin's file, or make the role, without it is refused before anything runs; one with nothing of the plugins' to do asks for it not at all. The login URL refuses a database URL with no host (the parser drops a user set on one) — at the plugin's first transaction, not the server's start, and as a failed preflight row — and percent-encodes the password, and each login — the handle's pool, the migrator's connection, preflight's probe — confirms `session_user`. It grants each plugin's role to it `WITH SET TRUE, INHERIT FALSE` (PG 16) and writes the ledger from its own connection after the file commits. Preflight's `plugin tables` row logs in as it and fails it when it is missing, cannot log in with the server's password, is a superuser, inherits (by the role's flag or a grant's own option), is a member of any role but the plugins', holds `SELECT`, `INSERT`, `UPDATE`, `DELETE` or `TRUNCATE` on a core table or view, or lacks `SET` on a plugin's role. The workers take neither plugin knob: compose.yaml's server block is anchored under an extension key, and the two servers alone merge it with `x-plugin-env` (CI asserts the workers' environments). From `ob1_plugins` SQL could still `SET ROLE` to another plugin's role, and a transaction-level advisory lock on a core key would hold a core write up; the docs say both. The server's own role needs no membership, so `--grant` needs none either (SMD-2728 cancelled). `ctx.db`'s `sql` takes a template's own frozen strings array alone.
- **Check 31**, the accident guard in front of that boundary — not a sandbox: a plugin's TypeScript runs in the server's process, and curation holds hostile code. It reads a plugin's SQL — a migration file, or a *tagged* template literal found by a lexer (`${…}`, nested templates and type arguments included; an untagged one is UI or log text) — for a core table's name anywhere, another schema, a `U&` escape, a role, `session_authorization` or `search_path` change quoted or not, `RESET ALL`, `set_config`, `SET SESSION`, a temp object, a session advisory lock, `WITH HOLD`, `LISTEN`, `DISCARD`, and outside a plpgsql body `BEGIN`, `END`, `ABORT`, `COMMIT`, `ROLLBACK` (not `ROLLBACK TO`), `START TRANSACTION`, `PREPARE`, `EXECUTE`; inside one, `EXECUTE`, `COMMIT`, `ROLLBACK`. Its TypeScript imports the SDK and its own `.ts` files alone (static, re-exported or bare), no test file from code that runs in the server, and names no global past `ctx`, aliased or not. A plugin's directory holds TypeScript, `migrations/*.sql`, a README and metadata.json, nothing else; the registry matches the directories and each manifest's name its directory's. Fifty-four probes hold the rules (sixteen of them code the check must not flag, among them a trigger function's multi-line body, an untagged template, a `temp` column, `ROLLBACK TO`); ten plants in the real tree each fail it by name, the ticket's `FROM thoughts` in a handler and the review's `END;`, aliased `fetch`, `.js` file and imported test file among them.
- **GUI pages.** A manifest declares `gui: { pages: [{ path, label }] }`, checked at load. `GET /v1/plugins` lists each enabled plugin of which the key may call an operation — its name, title, description, pages and those operations — the registry the operator GUI's nav reads (SMD-2280). The example declares a Notes page.
- **Egress.** A plugin is given no outbound call (check 31 refuses `fetch` and its kin); a gated model call as a core service comes with smart-ingest's port, SMD-2690.
- **Docs.** CONTRIBUTING's category table, Plugins requirements, remote-MCP rule and check item 14; the PR template; CLAUDE.md's repo structure and server guard rail; `docs/operator-surface-tiers.md`'s "As built" amendment; `plugins/README.md`; `db/README.md`'s "Plugin migrations"; each says the roles are the boundary, check 31 the accident guard and curation the control.
