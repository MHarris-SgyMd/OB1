## Changelog

`set_priority` and `clear_priority` now name every statement they closed, and the item they were asked about (SMD-4238, migration 138). A ticket and its own board-sync rows are one item to the writers, so one call can close a key's statements on both. Each reply gains `closed`, every statement it closed, newest first, each on its own item, and `item`, the item named. `replaced` and `assertion` stay as the newest of them. A clear on a ticket that closed the key's statement on the ticket's row now says it cleared the ticket and where the statement stood. With nothing to clear, the winner is placed relative to the item named.

## Record

A priority write names every statement it closed and the item it was asked about — `closed` and `item` in both writers' answers; migration 138 (SMD-4238)

**Why.** SMD-4127 (migration 133) made the writers close a key's statements across a ticket and its own rows, but their answers still named one statement: `assert_priority`'s `replaced` and `clear_priority`'s `assertion`, the newest closed. A key holding two open statements in one pool (a thought that became the ticket's row late; a by-name statement beside a by-id one) heard of one. `clear_priority`'s answer also carried no item, so the server read the closed statement's item as the one asked: `clear_priority('ticket', 'PRB-60')` that closed the key's statement on the row answered "Cleared your statement on thought …", and placed the winner relative to the row. SMD-4127's four review passes each raised it.

**What changed.** Migration 138 replaces 133's two writers, their answers gaining two keys, and `assert_priority` changing in two ways (below). `item` is the item named, as `ob1_priority_item` keys it. `closed` is every statement the call's own UPDATE closed, newest first, `[]` when it closed none (a first statement, `unchanged`, `nothing_to_clear`, a refusal). A new STABLE SQL function, `ob1_priority_closed_json(ids)`, renders them. A statement a delete closed between the call's read and its write (136's trigger takes no priority lock) is not listed. Two changes of behaviour in `assert_priority` (review passes 1–3): it locks every one of the key's statements in the pool still open, where 133 locked the newest it had read alone, so a delete can no longer close one between the lock and the UPDATE and `replaced` is always one the call closed; and the `unchanged` test counts the statements locked, so a restatement of the one a racing delete left open is `unchanged` rather than a copy of itself. Both writers re-project only the items whose statements they closed, and render `closed` once, `replaced` and `assertion` its first. 138 refuses by name without any function the carried bodies call (115's, 116's, 117's, 122's and 133's). The server reads both keys (`store.ts`, strictly: any other shape is a fault). On a brain before 138 it reads `item` from the statement written (a set) or from 116's `ob1_priority_item` (a clear), and `closed` as the one statement named. That read follows a clear that has landed, so its failure, the store's included, falls back to the caller's words, the item asked, rather than failing the clear (review passes 1 and 3). `SetPriorityResult` and `ClearPriorityResult` gain `item` and `closed`, so the REST and MCP values carry them. `render.ts` says every statement closed, each where it stood relative to the item named, and the winner placed relative to it, `nothing_to_clear` included. The tools' descriptions, `server-portable/README.md`, `db/README.md` and `docs/priority.md` decision 2 say it; `rest-client/openapi.json` is regenerated for the descriptions.

**Not changed.** A set that checked its item exists before a delete committed still writes its statement on the deleted item, which `ob1_close_orphan_priorities()` closes: 136's choice, which the maintainer kept (review pass 2); a re-check after the lock would narrow the gap, not close it. The rest-client types requests alone, so its types gain nothing: the ticket's Verify bullet on them has nothing to hold. A refusal from `assert_priority` is still keyed by the server's own read (`priorityItem`), as before.
