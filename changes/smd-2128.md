## Changelog

smart-ingest writes a thought through the fork's 3-argument `upsert_thought` — the vector as `p_embedding`, its model's label and the actor in the envelope, the enhanced columns beside it — where it called upstream's 2-argument form with the vector inside the payload, which the fork's function does not read, so every thought the server wrote had no vector, no label and none of the enhanced columns; `schemas/smart-ingest`'s `matched_thought_id` and `result_thought_id` are `uuid`, as `thoughts.id` is here, and `append_thought_evidence` takes one — against `bigint`, no item of a job with a match was ever persisted and no executed item recorded its thought; a revision sets the row's `supersedes` (SMD-2128).

## FORK

smart-ingest's write path is the fork's — the 3-argument `upsert_thought` with the vector as `p_embedding`, the label and the actor in the envelope, and `uuid` thought-id columns on its items, where upstream's 2-argument call dropped every vector on the floor and the fork's UUID failed every item that named a thought (SMD-2128)

**What changed.** `integrations/smart-ingest/index.ts`: `writeThought` is the
one call site of `upsert_thought`, the 3-argument form every other vendored
writer uses (SMD-1228; `db/migrations/004`, last redefined by `046`): the
vector as `p_embedding`, `embedding_model` (021) and `actor` (008, SMD-1541 —
`{ name: "MCP_ACCESS_KEY", via: "smart-ingest" }`, the one key the server
holds) in the envelope, and the enhanced-thoughts columns — `type`,
`importance`, `quality_score`, `source_type`, `sensitivity_tier` — by an
update carrying neither content nor vector, on a fresh row only (`existed`
false), as rest-api and enhanced-mcp write them. Both the `add` and the
`create_revision` branch go through it; a revision passes `supersedes`, the
matched thought's id, at the envelope's top level, where the function
validates and writes it as the row's pointer (025 made the column the one
mechanism for supersession) — upstream put the id in `metadata.supersedes`, a
second place for the same fact. The label is the model that answered:
`_shared/helpers.ts` gains `embedTextLabelled`, which returns the vector with
the provider's model name (OpenAI's bare name spelled `openai/<model>`), and
`embedText` is its vector alone — this server's `embedText` falls back from
OpenRouter to OpenAI on failure, so a label read from the environment (rest-
api's shape, whose `embedText` has no fallback) would name OpenRouter's model
for a vector OpenAI made. `IngestionItem.matched_thought_id` is a string,
`extractThoughtId` answers a UUID alone (SMD-2110 made it count beside
upstream's integer; there is no integer id here), and `recordItemResult` is
one statement again — `status` and `result_thought_id` together — the
`metadata.result_thought_uuid` detour SMD-2110 put in gone.
`schemas/smart-ingest/schema.sql`: the two columns are `uuid`; a section 2b
retypes a table created under upstream's shape in place, guarded on the
column's type — an integer either column held is kept as
`metadata.<column>_bigint` (it could name no thought here; the rule is that
a `.sql` file destroys no data), and `result_thought_id` is filled from
`metadata.result_thought_uuid`; `append_thought_evidence(bigint, jsonb)` is
dropped before the `uuid` form is created, so one function answers the name,
and the REVOKE names the new form. `db/config.mjs`'s community group and
`db/README.md`'s grant table name `append_thought_evidence(uuid, jsonb)`.
`dashboards/open-brain-dashboard-pro`'s `IngestionItem` types the two ids as
strings, and its ingest route casts them so. The two READMEs describe the
form, the columns, the retype, the re-grant and `db/reembed.ts` for the rows
written before this.

**Why.** Found by SMD-2110's first suite run (2026-09-24): its one real write
answered `added_count: 0, failed_count: 1` — `extractThoughtId` read the
fork's UUID as no id — and the row it left had content and fingerprint and
nothing else. SMD-2110 took the smallest cut that let the extraction trigger
fire and filed the rest here. The 2-argument `upsert_thought` (046's body)
reads `content`, `metadata` and `actor` from the payload and nothing else:
every thought smart-ingest wrote on this fork landed without a vector — so
invisible to `match_thoughts` and every semantic search — unlabelled, and
with no `type`, `importance`, `sensitivity_tier` or `source_type`, and
`scripts/check-fork-consistency.ts` check 10 cannot see it (the write is
through the function). And the item table was upstream's: `thoughts.id` is
`uuid` here and the two columns were `bigint`, so `persistItems`' INSERT of
any item carrying a matched id — a fingerprint or semantic match — failed
whole and the job completed over an empty item list, and no executed item
could record its thought.

**Held.** `extensions/test-writes.ts`, 379 assertions. Before the sidecars are
applied, the two tables are created from the file's own text with the columns
turned back to `bigint`, an item seeded the way SMD-2110 left an executed one
(the UUID in `metadata.result_thought_uuid`, `42` in `matched_thought_id`)
and upstream's function stubbed; the sidecar then retypes both columns to
`uuid`, keeps the `42` as `metadata.matched_thought_id_bigint`, fills
`result_thought_id` from the metadata key, leaves one
`append_thought_evidence` taking a `uuid`, and applies again on its own shape.
The smart-ingest block: the first write's row has the stub's vector at its
axis under the model's label, the enhanced columns set, 008's row naming
`MCP_ACCESS_KEY` through `smart-ingest`, and the item's `result_thought_id`
is the row's id; the same text again (`reprocess: true`) is one item skipped
by fingerprint with the first thought as `matched_thought_id`, persisted, and
no second row — the arm that fails on main's `bigint` column; a stub vector
`0.88` from the first thought's (the stub's `nearOf` map — one-hot vectors
alone are 0 or 1 apart, so no arm drove either branch before) drives both
actions between the thresholds — a shorter text appends evidence through
`append_thought_evidence(uuid, jsonb)`, the entry on the thought's metadata
and the item naming it as matched and result; a longer text is a revision, a
new row with its vector and label whose `supersedes` is the first thought and
`metadata.supersedes` unset, 008's row for it too; the dry-run-then-`/execute`
arm's item carries its result id and its row a vector. The file's text: one
`rpc("upsert_thought"` call site, the actor in the envelope and the vector as
`p_embedding`, no `embedding` key inside the payload. Nine mutants, each
alone and restored, each failing the arm that holds its mechanism: the
2-argument form with the vector in the payload (five arms — the vector, both
near-match branches, which then find nothing to match, the execute arm, the
text guard), no label (two), the enhanced columns never written (two), no
actor (five), a revision without `supersedes` (one), the item's result
written as status alone (four), a fingerprint match naming no thought (one),
the retype disabled with the function on `bigint` (six — every item arm,
as on main), the result column not filled from SMD-2110's key (one).
`db/test-schema.ts` [40] applies the sidecar to a fresh brain and probes the
community group's `append_thought_evidence(uuid, jsonb)`. `test-auth.ts`
767/767; `check-fork-consistency` PASS (check 21 on the schema edit — the
`DO` block's UPDATE has its WHERE, the DROP is of a function).

**Not taken.** A foreign key from the two columns to `thoughts(id)`: a `KEY
SHARE` lock on the thought for every item write, and a deleted thought would
null or refuse the item's history — the columns are a record, not a
reference. A `matched_thought_id` from `metadata.supersedes` on old rows:
nothing wrote one. A checker rule for a vector inside `upsert_thought`'s
payload: one file did it, and the suite's text guard holds that file; a rule
for every file is a ticket when a second does. Fixing
`open-brain-dashboard-pro`'s thought page, which parses its id as an integer
and so cannot land the per-item link this change lights: the whole dashboard
types `Thought.id` as a number, a mechanism of its own — SMD-2152.
