## Changelog

n8n's brain calls go to the REST core, `http://api:8000` with `x-brain-key`, not the brain's MCP server: the profile's brain credential is pinned to `api`, and provisioning now refuses a brain credential pinned to anything but `api` alone. **Upgrading:** if you set `N8N_BRAIN_CAPTURE_KEY`, run `bun deploy/orchestration/provision.ts` again; a workflow you built that sends that credential elsewhere (an MCP Client node at `server:8000`) is then refused by n8n. The orchestration eval calls the REST core too (SMD-2295).

## FORK

n8n's brain calls go to the REST core — the profile's brain credential is pinned to `api`, and provisioning refuses one that is not (SMD-2295)

**What changed, PR 1 ([OB1 PR 465](https://github.com/MHarris-SgyMd/OB1/pull/465)): the ADR and the wording.**
- **`docs/orchestration-tool.md`:** an "Amended by SMD-2295" block, and decision 4, posture step 2 and "Not decided here" each say it.
  - A template's brain call is an HTTP Request node against the REST core's routes at `http://api:8000`, with `x-brain-key`.
  - The key discipline is unchanged: a capture-scope key, attributed and revocable, in a credential pinned to one host.
  - n8n stays on `egress` alone, and its own MCP endpoint (the act tool) is untouched.
  - Decision 1's C2 and C3 stay the POC's record of 2026-09-25.
- **The pin, measured** (posture step 2, and SMD-2211's open question answered). On the pinned n8n 2.40.6, an `httpHeaderAuth` credential pinned to the bare name `api` is sent to `http://api:8000`, and to `API` and `api.`, by the HTTP Request node. It is refused ("Domain not allowed") for:
  - a prefix or suffix of the name;
  - `api`'s own IP;
  - a userinfo trick;
  - a URL built by an expression;
  - a redirect from `api` to another host.

  The MCP Client node refuses it off-host too. The pin compares the hostname alone, not the port.
- **`deploy/orchestration/provision.ts`:**
  - `--init`'s note for the optional capture key names the REST core, recreates `server` and `api` (both read `MCP_ACCESS_KEYS` until SMD-2287 PR 6), and says to provision again;
  - the `?key=` case's URL is a neutral host, since the REST core never reads `?key=`.
- **SMD-2287 PR 5b's wording, corrected.** It called `server` "n8n's" and planned "PR 6 moves n8n to the MCP server"; nobody decided either. No shipped template calls the brain:
  - `act-linear-file-issue` calls Linear;
  - `import.per-pipeline` calls `orchestration-runner:8090`;
  - `act-mcp` and `import-on-demand` start n8n's own sub-workflows.

  No shipped template calls `server` (the orchestration eval did until PR 2; PR 2 makes it "nothing in the stack"), and `server` retires in SMD-2287 PR 6. The places that said otherwise were corrected: `deploy/compose.yaml`, `deploy/README.md` (the services tables, the v2.0.0 URL table's n8n row, the logs, `OTEL_SERVICE_NAME`, "Orchestration" with the capture route and the contract's URL), `deploy/.env.example`, `SETUP.md`, `docs/01-getting-started.md`, `docs/operator-surface-tiers.md` (the as-built notes, its n8n row), three Fork Checks comments, `mcp-server/index.ts` and check 28's comment.

**What changed, PR 2: the pin and the eval.** The pin waited for the eval's re-aim: the eval provisions the profile's credentials and its MCP Client nodes, which enforce pins, sent them to `server:8000`.
- **The pin and its rule.** The profile's brain credential and the kit's read credential are pinned to `api`. `provision.ts`'s `brainPinProblem` makes `checkBrainKey` refuse a credential that declares a `brainScope` unless `allowedHttpRequestDomains` is `domains` and `allowedDomains` is exactly `api`. The self-check holds both shipped templates to it.
- **The eval re-aimed** (`evals/orchestration/`): each capture is `POST http://api:8000/v1/thoughts` with the capture key in `x-brain-key` and a `source` naming the tool (SMD-3208's advice), and each `brain_search` is `POST /v1/search` with the read key.
  - **n8n:** HTTP Request nodes, and an HTTP Request Tool named `brain_search_thoughts`.
  - **Activepieces:** the HTTP piece, `~0.13.0`, the version 0.91.3's catalogue offers (`~0.12.0` was not installable). It takes no connection (`auth: None`), so the adapter fills the brain keys into the steps at import from placeholders, refusing one left unfilled. The keys sit in the flow, not the connection store; this was the maintainer's choice for that case. Its cost: a holder of Activepieces' own MCP token can read them through its flow tools (inferred, not measured), and its run logs echo step inputs, so they hold them too. The eval redacts where its report is built (every check's detail but E's, which is the packet capture's, and both samples) and the error it ends on, with `redactKeys`: runs of 20 or more hex characters, so a key cut to 20 or more too. The verdicts read the raw text first.
  - **Windmill:** its scripts call `fetch`, and `nativeHttpClient` stays false (a script of ours, as the POC judged).
  - **C2** reads "the tool's own HTTP client" (`adapter.ts`'s `httpClient`/`nativeHttpClient`).
  - **E:** the judge takes the brain's addresses from `api`, and `server` left its service names, so a question for it fails. A new self-check case holds that (40 cases, from 39). `vendor`'s pipeline, its emitter and the I check name `api:8000`. The sealed overlay puts `api`, not `server`, on `sealed`.
- **Two older breakages the eval had to clear first:** `ensureEnv()` minted no `OB1_FORWARDER_KEY`, which compose has required since SMD-2287 PR 5b (it now mints one, and adds its record to an existing file's key list). `--up` never started the forwarder that has held the brain's port since SMD-2583.
- **`deploy/compose.yaml`:** n8n's `depends_on` names `api`, its one way into the brain, where it named `server` since SMD-2210, so `up -d n8n` brings the REST core along.
- **Docs:** `evals/README.md` gains the re-aim, the table and an operator's note on the podman fault, beside the POC's record. Everything that said "the eval still calls `server`" now says nothing in the stack calls it, `changes/smd-2287.md`'s three such lines included.
