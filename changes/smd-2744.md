## Changelog

A new write-scoped tool, `reset_capture_stamp`, lets the operator undo a capture-only key's label that another key's re-capture settled or moved. Only a key the operator classified `operator` may use it. It puts the capture-only key's label back, records the reset in the operator's name, and lets the operator's next re-capture of the text move the label to the operator's key. `update_thought` now says which of `trust`, `actor_kind` and `actor_name` a patch named that the thought did not take, where it replied "metadata merged"; its `metadataMerged` is now true only when the patch changed something, and a patch that named only what the thought held reads "metadata unchanged" (SMD-2744).

## FORK

The operator resets a capture-only key's settled or moved label (SMD-2744)

**What changed.**
- **The reset** (migration 086, `ob1_reset_capture_stamp(id, actor)`).
  - **Who.** It refuses (`NOT_OPERATOR`) unless the actor in force is a key the registry classifies `operator`, looked up by its agent id, else its name. That is the lookup the audit row's `actor_kind` is made by, so the event names the operator. A capture-only actor is refused whatever its kind, and so are no actor and an actor naming no key.
  - **Which rows.** It locks the row as `update_thought` does. It refuses (`NOT_CAPTURE_STAMP`) a row whose label 085 does not move: its capture row carries no `"scope": "capture"` mark, or its metadata is not an object. No row: `NOT_FOUND`.
  - **What.** It acts on the declines and the restamp made since the row's latest reset. With none, it writes nothing and answers `reset: false`, before any text is hashed. A row whose text an update changed since its capture (by 003's fingerprint) is then refused (`NOT_CAPTURE_STAMP`). Otherwise it appends and projects one update event, its diff `{"restamp_reset": true}`. Where a restamp moved the label, the event's metadata puts back `actor_kind`, `actor_name` and `trust` derived from the capture row exactly as `backfill_thought_actors` derives a capture's: the trimmed name, the kind the registry holds for it now (else the capture row's), and the trust the capture recorded (or the claim it filed while unclassified) under that kind, lowered by the stamp the oldest restamp since the reset found (its diff's before-image) and never raised. So a pass after the reset finds nothing to change. A key with no value stays absent, and every other key is left as the row holds it. The answer names the keys whose restamp (`moved_by`) and declines (`declined_by`) it undid, which may be the operator's own. A refusal of the caller carries the registry's kind for it. The event declares the trust the row is left at; where the row is left with none (an unclassified capture key's), it declares nothing, and the audit row records the operator's kind. It answers the label it left.
- **The restamp.** `ob1_restamp_recapture` is 085's body, but it reads the row's restamp and the declines only from after the latest reset, by `seq`. So a reset row is weighed again by the next classified key that can read. A text change still refuses, whenever it was made.
- **The backfill.** `backfill_thought_actors` is 085's body with a reset among its candidate rows. A restamp with a reset after it is no writer, and the capture is again, when no update ever changed the text. Its update and capture arms read only text-writing updates: a restamp's or a reset's NULL after-text no longer matches a row that no update gave a text.
- **The tool.** `reset_capture_stamp(id)` is in the write group, so a read or capture key does not see it; any write key does, and the database refuses it unless the operator classified that key `operator`. Over REST it is `POST /v1/thoughts/{id}/reset-capture-stamp`, with `REFUSED_NOT_OPERATOR` as a 403 and `REFUSED_NOT_CAPTURE_STAMP` as a 409. The reply says what was cleared and whose move and declines it undid, the label it left, and the ways on by the trust the row is left at: re-capture the text exactly as stored (`fetch` shows an `ingested` row under a notice line that is not part of it) plainly, and the label moves to the operator's key at trust operator; with `trust: "ingested"`, a label at `ingested` or `agent` stays and the row is settled against every other key, while a label with no trust moves to the operator's key at `ingested`; a label at `operator` no re-capture outranks. Over MCP, a key that is not the operator's is refused by name and kind (an unclassified one given its `set_agent_kind` line, a classified one told to use the operator's own key), and a database before 086 is named in the fault; REST answers the code and status. Both stores call the function.
- **The change log.** `thought_changes` reads the event as "reset by <key>", with the label "restored" (and the marks named) or "unsettled". A decline's line names the operator's reset as the way out.

**Why.** Under 085 the first classified key that can read to re-capture a capture-only key's text moves the label or records a decline, and either settles the row against every other key. A label could stick where the operator holds it wrong: another key reached the row first, or a name-only decline was written while the registry lookup failed or was misconfigured, which settles the row for every caller. There was no reset. `update_thought`'s metadata patch naming `trust` changes nothing on a write that leaves the text (050), and a backfill pass keeps the label. A text edit changes the text, and a delete and re-capture changes the id (SMD-2664's review pass 5, scenario S6, on the real server).

**Decisions** (the maintainer's, at the plan stage).
- **A server tool for operator keys,** rather than a psql-only function. The gate is the key's registry kind, which the database holds, so the function decides and the tool is write-scoped.
- **Reopen and restore.** The reset puts back the capture-only key's label where a restamp moved it, not just clears the declines, so the weighing is as if no reader had landed (082's note stands: the capture key does not get its `supersedes` ownership back). It does not move the label to the operator itself: the operator's re-capture is weighed as any other.
- `update_thought`'s reply to a `trust` patch on a write that leaves the text: said in the reply, not refused — PR 2, below.

**Not here.**
- **The window after a reset.** The first classified key that can read to land settles the row again, so an agent key re-sending the text before the operator's re-capture is weighed first.
- **Rows from before the scope mark.** A capture-only key's row from before SMD-2638's scope mark says nothing of whose it is: the reset refuses it (`NOT_CAPTURE_STAMP`), as 085 leaves it (SMD-2745).
- **The operator's own keep.** An `ingested` re-capture settles the row against every other key, not against the operator's own key: its later plain re-capture still moves the label (085's rule for the same agent).
- **Two live keys on one agent id** (SMD-2746). The reset clears both keys' declines alike.

**Upgrading.** Apply 086 (`bun migrate.ts`). It refuses to apply without 046 or 085, and moves no row. Classify the operator's own key `operator` (`SELECT set_agent_kind('<name>', 'operator')`) before relying on the tool. A server before this one has no tool; a database before 086 answers the tool with the function missing.

**Tests.** test-schema [77], test-upgrade [20ah], test-store-sql [8e] (the row lock and the operator asked again, on two connections), test-store-postgrest [8g], test-e2e-sql [13g], test-rest-sql's reset cells (REST and MCP alike, the statuses as numbers), test-server [22] (the reply's branches and refusals), test-audit's change-log lines, and the drift guards over the manifest (test-server, test-rest, test-auth). 72 mutants, every one killed.
