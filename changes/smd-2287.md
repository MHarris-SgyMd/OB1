## Changelog

`/mcp`, `/health` and the protected-resource document are served by the MCP server built on the REST core (`mcp-server/`), as compose's new `mcp` service: on the mesh alone, every tool a call on the REST core, an OAuth token traded at the hop. `server` keeps only the legacy root route, until v2.0.0. **Upgrading:** before `up`, mint the MCP server's forward key (`cd server-portable && bun keygen.ts --name mcp-forwarder --scope forward`), its hash line in `MCP_ACCESS_KEYS` and the raw key as `OB1_FORWARDER_KEY` in `deploy/.env`: compose refuses the stack without it. `canary.sh up` mints a canary's own, rewriting its `MCP_ACCESS_KEYS` once (comments in it dropped; one written across lines refused until it is on one line) (SMD-2287).

## FORK

`/mcp` is the MCP server built on the REST core, as compose's `mcp` service on the mesh alone — every tool a REST call, a token traded at the hop, and the old server left the legacy route (SMD-2287)

**What changed.** SMD-2287 PR 5, in two halves. The maintainer's choices (2026-10-20): `compose.yaml` itself routes `/mcp` to the new service, so the canary gets it first from main and stable at a release cut; and the service runs the server image, as `api` does.
- **PR 5a, the image and the key:**
  - `server-portable/Dockerfile` installs `mcp-server/` and `rest-client/` from their own lockfiles, a deps stage each, and copies both under `/app`, where the MCP server's `../server-portable/` imports resolve as in a checkout. `.dockerignore` leaves out the client's generator, the 176 KB OpenAPI document it writes and the suites' in-process stack.
  - `release.yml`'s pull-request paths name both directories, and six inputs they missed before (`db/login-role.ts`, the two `db/*.d.mts`, `scripts/fork-index.ts`, `mechanism-yield.ts`, `commit-grammar.ts`).
  - `deploy/canary.sh`'s `env_file own-fix` mints the canary's forward key beside its write key, `<project>-mcp-forwarder:forward:<sha256>`, the raw key in `OB1_FORWARDER_KEY`; the REST core records the name as who carried each request. Trimmed, as the server reads it. Stable's `OB1_FORWARDER_KEY` counts among stable's keys, listed or not. A key of stable's, or one no forward entry holds, is replaced and said; a re-mint removes the forward entries an earlier mint made (`-2` and on), said by count; an operator's other entries stay. Before, `up` cleared stable's forward key and minted none.
- **PR 5b, the service and the route:**
  - **The `mcp` service:** the server's image, `bun --no-install ../mcp-server/index.ts` (auto-install off: the image's packages are all it loads). On `mesh` alone as `mcp.ob1.internal`: no Postgres, no provider, nothing outward. Its environment is listed, not merged from `server-env` or `plugin-env`: `OB1_FORWARDER_KEY`, `OB1_PLUGINS`, `OB1_PUBLIC_ORIGIN`, `COMPOSE_PROFILES`, `OB1_AUTH_SECRET_MCP`, `OB1_STOP_GRACE` and the OTEL block — no database URL, key list, provider key or plugin password. Its own healthcheck (podman's image format keeps none). After `api`; the proxy waits on it.
  - **`OB1_FORWARDER_KEY` is required:** `${OB1_FORWARDER_KEY:?…}`, naming the mint command, since the server exits 2 without it and no default can be one. Check 14's `REQUIRED_KNOBS` admits that form for a knob it lists and holds the knob to it; check 13's `ENV_EXAMPLE_LIVE` and `deploy/.env.example` carry it as a key every operator fills in.
  - **The route table:** `mcp`, `health` and `resource` go to the `mcp` service; `legacy` to `server`, now `server.ob1.internal` on the mesh. Checks 27 (the tiers' server renamed from that name, so `compose.tiers.yaml` is unchanged), 28 and 32 follow.
  - **`canary.sh`** recreates `mcp` after `api` on the new build, and its readiness is the keyed `/health`'s JSON — the REST core's record, which the MCP server answers only once the REST core does.
  - **The release overlay** pins `mcp` to the release's server image; its notes name the key; `release.yml`'s stack has one.
  - **Docs:** deploy/README's reachability and path tables, the upgrade note, the auth passages (no longer a preview for a keyless connector), traces and doors; FORK.md; both ADRs; the hook's registry line now in `api`'s log.

**Why.** The ADR's MCP server on the mesh alone (SMD-2282 decision 3): every tool through the REST core, which owns Postgres and the providers. Until now `/mcp` was server-portable's own, which accepts no OAuth token, so the `auth` profile was a preview for any connector without a key; SMD-2286 PR 2's exchange sat in `mcp-server/`, which nothing served.

**Held.**
- **Fork Checks, the core job:** compose's render — `mcp` on `mesh` alone, the server's image unbuilt, `--no-install`, holding none of the server's secrets, an OTEL carrier, no port; the pinned Bun in it; the daemon restart brings it back healthy; its stop exits 0 saying no pool was opened, and the protected-resource document is then the proxy's bodiless 404; stand-ins claiming `mcp` and `server` on the mesh are not reached. The legacy route still reaches `server`.
- **The auth job:** the document and challenge at the origin's Host, now the `mcp` service's; the same real tokens as the REST core's checks through the proxy's `/mcp` — a write token lists the write tools, a read token the read ones alone, a read token's `thought_stats` answers; with the authorization server stopped, a token is 503 Retry-After 30; the request lines for `/mcp` and `/health` in `mcp`'s log, the legacy route's in `server`'s, the smoke key in neither; the stream's keepalive through the proxy.
- **The image step** (5a), offline: no key exits 2 naming it; keyless `/health` is `ok`; SIGTERM exits 0.
- **The canary step:** the first `up`'s two keys exactly; an edited `up` with stable's raw and unlisted forward keys and an operator's near-miss entries; an `up --no-refresh` on the file the dogfood canary holds now; no raw key printed.
- **The release:** the overlay's self-check and `release.yml`'s render pin `mcp`.

**Measured after.** A scratch stack from this tree on podman (project `ob1-2287p5b`):
- every service healthy at `up --wait`; `smoke.sh` 11/11 at `/mcp` (the `mcp` service took the lines) and at the root (`server`);

- with the authorization server: the document and challenge; a write token's 21 tools, a read token's 14 without `capture_thought`; a write token's capture audited `oauth:operator`, act `oauth:mcp`; the server stopped, a token 503 Retry-After 30;
- `mcp` stopped: exit 0, its stop line, the document a bodiless 404.

**Not taken.**
- A third GHCR image (`ob1-mcp`), as SMD-2296's "images per server" reads: the maintainer chose one image, since a partial `up --build` would leave two apart, as `orchestration-runner-role`'s once fell behind.
- A soft `${OB1_FORWARDER_KEY:-}`: a stack upgraded without the key would start an MCP server that exits at once behind the proxy's 502, where the required form refuses before anything changes.
- `mcp` on `telemetry`: the servers reach the collector on `mesh` as `lgtm.ob1.internal`; `telemetry` is the collector's and the exporter's.
- Stopping `mcp` for a canary refresh: it writes nothing, so it is recreated after the REST core, not stopped before the migration.
- CI cases for the own-fix scope check, a taken name, the connector note with an unreadable key and the removal message's plural: the scratch harness holds the first two, and each would cost the canary step another `up`.
