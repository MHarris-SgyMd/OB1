## Changelog

The brain's MCP server as a client of its REST core, `mcp-server/`: MCP on SDK v2, every tool a call to the REST core with the caller's key forwarded, every answer worded as server-portable words it, and test-auth's assertions held to it. The REST core's `/health` answers a key that may read it the brain's record on the health surface (SMD-2287).

## FORK

The MCP server as a client of the REST core, and the REST core's keyed /health — PR 3a of SMD-2287 (SMD-2287)

**What changed.**
- **`mcp-server/`**, a top-level package (the maintainer's choice of SMD-2287's plan) on `@modelcontextprotocol/server` 2.1.0, pinned with hono and zod at server-portable's versions. `extensions/test-auth.ts`'s guard holds it to the v2 stack as it holds server-portable.
  - `app.ts`'s `createMcpApp({ rest, edge, keepalive?, warn? })`:
    - **The caller.** Each presented key (auth.ts `presentedKeys`: `x-brain-key`, `x-access-key`, `?key=`, `Bearer`) is asked of the REST core's `GET /v1/whoami` in turn. The first key it knows decides: a caller and its operations, the revocation's envelope, or busy's `-32003` and `Retry-After`. With none, the answer is `-32001`, or the public origin's challenge. A refused notification gets a bare 202 or 503 (SMD-2106). This server's own forwarder key refused is a 500, never the caller's refusal.
    - **Tools.** tools/list is the caller's operations. Each tool is validated by the SDK against `core/schemas.ts`, called through `rest-client` with the caller's key, and its answer said by `render.ts`. That covers a value, a refusal from the `refusal` the forwarder slot carries, and a fault (`FAILED`, capture's `STORE_UNAVAILABLE`, the REST core away) in the tool's fault words. A scan's links sit under the endpoint.
    - **`/health`:** `ok` without a key; with one, the REST core's keyed `/health` record and this server's `oauth` view beside it.
    - **Mirrors and jobs:** `/worker-status`, the three worker POSTs and `/jobs/<id>[/stream]` are proxied to the REST core.
    - **The rest of the edge:** SSE keepalive, the method guard, the preflight, `/.well-known` and the protected-resource document.
  - `index.ts` is the entry. It takes OB1_REST_URL (default `http://api.ob1.internal.:8000`), OB1_FORWARDER_KEY (it exits 2 without one), PORT and OB1_STOP_GRACE. The REST timeout is SSE_KEEPALIVE_MAX_MS.
  - `stack.ts` is this server with the REST core in process, for server-portable's suites. `server-portable/test-support.ts`'s `mcpUnderTest()` picks it with `OB1_MCP_UNDER_TEST=client`, else `index.ts`.
- **The REST core's `GET /health` with a key** answers as `index.ts`'s does:
  - the brain's record on the health surface for a key that may read `brain_info` and that the registry clears within `HEALTH_DEADLINE_MS`;
  - liveness, never a refusal, for any other key: wrong, out of scope, revoked, busy, or unanswered in time, its line `refused` with `REVOKED` or `BUSY` where the registry said which.

  Keyless, it is the unlogged liveness probe as before. The forwarder slot is not read there. The deadlines move to `server-portable/deadlines.ts`, which imports nothing; `core/reads.ts` re-exports them, and the core exports `HEALTH_DEADLINE_MS`.
- **A forwarded capture is answered the whole value**, whatever the key's scope, as a forwarded refusal is: the MCP server words it with `render.ts`, which picks from it what a capture-only key is told. The OpenAPI document and `rest-client/` are regenerated.
- **`server-portable/mcp-edge.ts`:**
  - the worker mirrors' refusal words (`MIRROR_WORDS`) and their body-to-input shaping (`MIRROR_INPUT`) move out of `index.ts`, which reads them from there;
  - check 25's EDGE_ROLE admits their two type imports.
- **CI:**
  - the portable-server job installs, type-checks and runs `mcp-server/`;
  - it runs test-auth a second time with `OB1_MCP_UNDER_TEST=client`;
  - check 18, `db/ci-parity.sh`, the landing check and CONTRIBUTING.md name the directory.

**Why.** SMD-2282's decision 3: MCP calls go through a server of their own that calls the REST core like any other client, so MCP's own behaviour stays in one place and the REST core is the one contract. PR 1 gave it the client and the refusal words, and PR 2 the shared edge. The ticket's Work 3 names the public `/health` "keyed BrainInfo JSON read from the REST core's internal /health". The REST core's `/health` was keyless liveness and its `/v1/brain` reads the slower tool surface, hence the keyed `/health`.
