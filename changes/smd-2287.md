## FORK

The server image carries the MCP server built on the REST core, and each brain gets a forward key of its own for it — the image and the key before the service (SMD-2287)

**What changed.** SMD-2287 PR 5a, the first half of PR 5. The maintainer's choices of 2026-10-20 are that the `mcp` service runs the server image, as `api` does, and that `compose.yaml` itself routes `/mcp` to it, the canary first through the release pipeline (PR 5b).
- **`server-portable/Dockerfile`:**
  - The deps stage installs `mcp-server/` and `rest-client/` from their own lockfiles, beside `server-portable/`.
  - The image copies both under `/app`, where the MCP server's `../server-portable/` imports resolve as in a checkout.
  - The image comment says the third server runs with `bun` as the entrypoint: it reads no store, so preflight's database check is not its readiness.
- **`.dockerignore`:** leaves out the client's generator, the OpenAPI document it reads (155 KB), and the suites' in-process stack (`mcp-server/stack.ts`).
- **`deploy/canary.sh`:**
  - `env_file own-fix` mints the canary's forward key beside its write key: `<project>-forwarder:forward:<sha256>` in `MCP_ACCESS_KEYS`, the raw key in `OB1_FORWARDER_KEY`.
  - A key of stable's there is replaced, and `up` says so. A name an entry already holds takes `-2`, as the write key's does.
  - Before this, `up` cleared stable's forward key and minted none, so the canary's MCP server would have had none.

**Why.** PR 5b's service runs this image with a key that each brain must hold for itself. Landing the image and the key first means 5b is the service and its route alone. Run offline, an image built without `mcp-server/`'s packages stops on `Cannot find module '@modelcontextprotocol/server'`. Run with a network, the same image passed this PR's first CI step: Bun installed the missing package from the registry itself, because the directory had no `node_modules` (SMD-2978).

**Held.**
- **Fork Checks, "The server image runs the MCP server as a REST client"** (the authorization-server job), against the image the stack was built from, with `--network none`:
  - with no key, exit 2 naming `OB1_FORWARDER_KEY`, after every import has loaded;
  - with a key, keyless `/health` answers `ok`;
  - a keyless `initialize` is refused on the server's own `door: "mcp"` request line;
  - SIGTERM gives exit 0 with its stop line.
- **The canary step** asserts the canary's `MCP_ACCESS_KEYS` is exactly its write key and its forward key, each by hash, and that `up` said it minted the forward key. The second `up` mints nothing.

**Measured.** Locally, on podman:
- The image built under a scratch tag passed the CI step's script.
- Images built without `mcp-server/`'s packages, or without `rest-client/`'s, failed it once offline (both had passed online).
- `own-fix` was run on scratch env files:
  - a fresh file got both keys;
  - a second run changed nothing;
  - stable's forward key was replaced;
  - a taken name gave `-forwarder-2`.

**Not taken.**
- A third GHCR image (`ob1-mcp`), as SMD-2296's "images per server" reads: the maintainer chose one image. A partial `up --build` would leave two images apart, as `orchestration-runner-role`'s once fell behind.
- `OB1_FORWARDER_KEY` in `deploy/.env.example` here: check 14 refuses a knob there that no service forwards, so it lands with 5b's service.
- `bun --no-install` in the image: the step runs offline instead, which holds every package the image lacks. Whether the service itself passes `--no-install` is 5b's choice of entrypoint.
