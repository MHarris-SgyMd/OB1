## Changelog

`resolve_agent` writes a key's row only when `last_used_at` is NULL, over five minutes old or in the future, or the presented scope changed, so a lookup of a recently used key no longer waits on a transaction holding that row; `last_used_at` now means the last use to within five minutes. A revocation that commits while a lookup's write waits on it — or before a registration writes over a row another transaction inserted — is now answered REVOKED, where the lookup answered ok and the server kept that answer for its cache TTL; under a REPEATABLE READ or SERIALIZABLE default the server retries the serialization failure instead of serving the key by name (migration 054, SMD-2090).

## FORK

resolve_agent writes a key's row only when the write says something, and a revocation that commits during its wait is answered REVOKED (SMD-2090)

**What changed.** Migration 054 redefines 010's `resolve_agent(text, text,
text)` on its own body, same signature and grants:

- **Reads first, as before.** The plain SELECT of the key, its revocation and
  its agent never waits on a row lock, so a committed revocation is refused at
  once whoever holds the row. It now also reads `last_used_at` and the
  recorded scope.
- **Writes only when stale.** The row is written when `last_used_at` is NULL,
  over five minutes old or in the future (a clock stepped back would
  otherwise hold it fresh), or when a presented scope differs from the
  recorded one. Otherwise nothing is written and no row lock is taken.
- **The write re-checks the revocation.** `WHERE key_hash = … AND revoked_at
  IS NULL`. Under READ COMMITTED an UPDATE that waited on a row re-reads its
  WHERE against the version that committed. When nothing was written the row
  is read again (each statement a fresh snapshot): revoked answers REVOKED; a
  row deleted during the wait falls through to 010's registration — the
  rotation branch, or first sight if its agent went too.
- **So does registration.** 010's `ON CONFLICT (key_hash) DO UPDATE` — the
  loser of two first sights, and now a row deleted during a wait — carries
  `WHERE ob1_agent_keys.revoked_at IS NULL`; writing nothing, it reads the row
  — still locked by the ON CONFLICT, so never deleted between — and answers
  REVOKED.
- **A guard** refuses a schema without 010's `last_used_at`, `revoked_at` and
  `scope` by name, as 049's does. Both comments state the rule.

`server-portable/agents.ts` retries SQLSTATE 40001 as it does a lock timeout
(`timedOut` is now `retryable`): under a REPEATABLE READ or SERIALIZABLE
default either write fails there instead of re-reading, and was classed an
outage — the key served by name.

**Why.** 010's body ran `UPDATE … SET last_used_at = now()` on every lookup of
a known key, taking the key's row lock, so any transaction holding the row —
an open `revoke_agent_key`, an operator's `SELECT … FOR UPDATE`, another
replica's lookup — made the lookup wait. SMD-2072 capped that wait at 250 ms
and calls the key busy; the cap bounds the cost, but the write rarely changed
anything anyone reads. And the UPDATE re-checked only `key_hash`: a lookup
overlapping an uncommitted revocation waited on the revoker, then wrote and
answered ok, which `AgentResolver` cached for its TTL (60 s by default) —
measured in SMD-2072's second review pass, three runs in three.

**Why five minutes.** Five times the default cache TTL
(`OB1_AGENT_CACHE_TTL_MS`, 60 s): a server re-resolving a key once a minute
writes its row one lookup in five, and `OB1_AGENT_CACHE_TTL_MS=0` once per five
minutes rather than on every request. Nothing reads `last_used_at` at a finer
grain than "in use, or gone quiet". A constant, not an argument: an argument
changes the signature (a drop, the grants replayed, both stores' calls) for a
knob nobody has asked to turn.

**What stays.**

- A lookup overlapping an uncommitted revocation of a key it need not write
  answers ok at once, having read the key before the commit: what 010's column
  comment allows ("takes effect within the server resolve cache TTL"). 054
  removes the ok given after the commit.
- The first lookup after five minutes still writes, so a row held then meets
  the cap. A key presented under two scopes at once (two processes on
  different `MCP_ACCESS_KEYS` during a rollout) writes on every lookup, as 010
  did for every key.
- A first sight answering REVOKED from registration keeps the agent row it
  inserted, and a later key under that label rotates onto it. It needs one
  digest under two names at once (auth.ts refuses that) or a key row inserted
  revoked by hand; 010 left the same row and answered ok. Removing it needs
  DELETE, which `db/config.mjs`'s server grants do not include, or a
  subtransaction, whose rollback would drop the refused row's lock.
- A role missing UPDATE on `ob1_agent_keys` now fails only a lookup that
  writes — a stale key, a scope change, a registration — not every known-key
  lookup; `db/config.mjs`'s server grants include it.

**Verify.**

- `db/test-schema.ts` [49] (PGlite), a write read off the row's `xmin`: fresh
  with the recorded scope or none writes nothing; four minutes is fresh, six
  stale; NULL and an hour ahead are written; another scope is written at once;
  a rename on a fresh key writes no key row; a revoked key is refused; both
  comments; the guard refuses a registry without `last_used_at` or `scope`.
- `db/test-live.ts` [24], a second connection holding the row:
  - FOR UPDATE: a fresh key answers ok without waiting, a stale key and a
    changed scope meet the cap (55P03);
  - a stale key waiting on an uncommitted revocation answers REVOKED, through
    a bare call and through `SqlStore.resolveAgent`'s capped statement;
  - a fresh key read during one answers ok, then REVOKED after the commit;
  - a row deleted during the wait is registered again under its agent;
  - a registration meeting a row another transaction inserted answers REVOKED
    if it is revoked, and ok, a rotation, if it is not;
  - under REPEATABLE READ the waiting write fails 40001, and the retry answers
    REVOKED.
- `db/test-upgrade.ts` [20h]: the guard on a baselined pre-010 schema, and
  054's body live once 010 is there.
- `server-portable/test-agents.ts` [16]: 40001 is busy, and a 40001 then a
  revocation answers revoked on the retry.
- `server-portable/test-e2e-sql.ts` [14], the keys' rows held: a recently used
  key is served without waiting, one last used an hour ago is busy after its
  retries.
- Mutants, fifteen, each killed: the write unconditional; the UPDATE's
  `revoked_at` re-check, or the re-read, dropped (both races answer ok); the
  scope ignored; NULL, or a future time, counted fresh; the window at one
  minute or ten; a deleted row answered ok; the guard gone, or without
  `scope`; registration writing over a revoked row, its re-check inverted, or
  DO NOTHING (a valid key refused); 40001 not retried.
