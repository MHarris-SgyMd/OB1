## Changelog

`resolve_agent` writes a key's row only when `last_used_at` is over five minutes old or the presented scope changed, so a lookup of a recently used key no longer waits on a transaction holding that row; `last_used_at` now means the last use to within five minutes. A revocation that commits while a lookup's write waits on it is now answered REVOKED, where the lookup answered ok and the server kept that answer for its cache TTL (migration 054, SMD-2090).

## FORK

resolve_agent writes a key's row only when the write says something, and a revocation that commits during its wait is answered REVOKED (SMD-2090)

**What changed.** Migration 054 redefines 010's `resolve_agent(text, text,
text)` on its own body, same signature and grants. The known-key branch:

- **Reads first, as before.** The plain SELECT of the key, its revocation and
  its agent never waits on a row lock, so a committed revocation is refused at
  once whoever holds the row. It now also reads `last_used_at` and the
  recorded scope.
- **Writes only when stale.** The row is written when `last_used_at` is NULL
  or over five minutes old, or when a presented scope differs from the
  recorded one. Otherwise nothing is written and no row lock is taken.
- **The write re-checks the revocation.** `WHERE key_hash = … AND revoked_at
  IS NULL`. Under READ COMMITTED an UPDATE that waited on a row re-reads its
  WHERE against the version that committed. When nothing was written the row
  is read again (a fresh snapshot, the function being VOLATILE): revoked
  answers REVOKED; a row deleted during the wait falls through to 010's
  registration, the rotation branch, as the next lookup would.

The rename branch, the rotation and first sight are 010's. The function's
comment and a new comment on `ob1_agent_keys.last_used_at` state the rule.

**Why.** 010's body ran `UPDATE … SET last_used_at = now()` on every lookup of
a known key, taking the key's row lock, so any transaction holding the row —
an open `revoke_agent_key`, an operator's `SELECT … FOR UPDATE`, another
replica's lookup — made the lookup wait. SMD-2072 capped that wait at 250 ms
and calls the key busy, refused with a retry; the cap bounds the cost, but the
write rarely changed anything anyone reads. And the UPDATE re-checked only
`key_hash`: a lookup overlapping an uncommitted revocation of the same key
waited on the revoker, then wrote and answered ok, which `AgentResolver`
cached for its TTL (60 s by default). SMD-2072's second review pass measured
it: a revocation committing 50 or 150 ms into the lookup was served ok three
runs in three.

**Why five minutes.** Five times the server's default cache TTL
(`OB1_AGENT_CACHE_TTL_MS`, 60 s): a server re-resolving a key once a minute
writes its row one lookup in five, and `OB1_AGENT_CACHE_TTL_MS=0` (a lookup
per request) once per five minutes rather than on every request. Nothing reads
`last_used_at` at a finer grain than "in use, or gone quiet". A constant in
the body rather than an argument: an argument would change the signature (a
drop, the grants replayed, both stores' calls) for a knob nobody has asked to
turn.

**What stays.** A lookup that overlaps an uncommitted revocation of a key it
need not write answers ok without waiting, having read the key before the
revocation committed — the same answer as a lookup a moment earlier, and what
010's column comment allows ("takes effect within the server resolve cache
TTL"). What 054 removes is the ok given after the commit. The first lookup
after five minutes still writes, so a row held at that moment still meets the
250 ms cap and the key is busy for its retries. The loser of two concurrent
first sights still takes 010's `ON CONFLICT … DO UPDATE` without a revocation
check: a key registered in that same instant cannot have been revoked yet.

**Verify.**

- `db/test-schema.ts` [49] (PGlite): a write is read off the row's `xmin`. A
  lookup moments after the last writes nothing, with the recorded scope or
  none; four minutes ago is fresh, six is stale and written; NULL is written;
  another scope is written at once and the next lookup with it is not; a
  rename on a fresh key moves the label and writes no key row; a revoked key
  is refused with its agent id; both comments; the guard refuses a registry
  without `last_used_at` by name, and 054 re-applies.
- `db/test-live.ts` [24] (real server, a second connection holding the row):
  - rows held FOR UPDATE: a fresh key answers ok in 2 ms, a stale key meets
    the 250 ms cap (55P03), a fresh key presenting another scope too;
  - a stale key's lookup waiting on an uncommitted `revoke_agent_key` answers
    REVOKED once it commits, the agent id attached;
  - a fresh key read during an uncommitted revocation answers ok at once, and
    the lookup after the commit is REVOKED;
  - a row deleted while the lookup waited is registered again under its agent.
- `db/test-upgrade.ts` [20h]: a ledger baselined over a pre-010 schema fails
  at 054 by name, naming `--reapply`, and records nothing.
- `server-portable/test-e2e-sql.ts` [14], the keys' rows held: the revoked key
  is refused at once, a key used in the last five minutes is served in 4 ms,
  and a key last used an hour ago is busy after its retries (1767 ms).
- Mutants, nine, each killed: the write made unconditional (the fresh key
  waits, 55P03 at 256 ms), the `revoked_at` re-check dropped and the re-read
  dropped (the race answers ok), a scope change ignored, NULL counted fresh,
  the window at one minute and at ten, a deleted row answered ok (no agent
  id, no row), and the guard gone (a bare "does not exist").
