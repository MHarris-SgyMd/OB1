## Changelog

A PR that changes `db/migrations/`, `server-portable/` or `evals/` beyond tests and docs must ship a `changes/smd-NNNN.md` fragment, or the `Repo consistency` job refuses it by file name; the ruleset record and check 20 are ready for GitHub's merge queue, which the API refuses on this user-owned repository (SMD-1857).

## FORK

A landing that changes the fork records itself, and the merge queue is built but refused — GitHub offers it to organisation-owned repositories only (SMD-1857)

**What changed.** The `Repo consistency` job gains one step,
`scripts/check-landing.ts`: given the event's range — the PR's base and head,
or a merge group's — it lists each landing (one for a PR, from the merge base;
one per first-parent commit for a group, which under the pinned `MERGE` method
is each PR's merge commit, so `git diff c^1 c` is exactly what that PR added —
a first-parent commit with one parent stops the run, since a live queue is
then not merging as the record says) and refuses one whose changes touch
`db/migrations/`, `server-portable/` or `evals/`, test files and Markdown
aside, with no `changes/smd-NNNN.md` added or modified among them, naming the
files that asked. The diff is read `--name-status -z --no-renames`, so a
non-ASCII path is not C-quoted past the prefix and a file moved out of a
directory shows as its deletion there. The job's checkout fetches history so
the range can be diffed; the step runs on `merge_group` and on a
`pull_request` into `main`. Check 20 gains the merge queue as an *optional*
rule: absent, as the record ships it; at most once; and when present, its
seven parameters each equal to `MERGE_QUEUE` — `MERGE` (the fork's
merge-commit habit), `ALLGREEN` (a red run names its own PR), one PR per group
at minimum, GitHub's five for build and merge, a sixty-minute check timeout.
The record itself does not carry the rule, for the reason under *Measured
after*.

**Why.** CI ran on a PR's head against the `main` of its trigger time, so two
PRs each green on their own could together break the tree; SMD-1856's strict
rule closed that by making the author merge `main` and run again, and three
branches carried a migration 047 each while it was off. The ticket's queue
would close it without the author's hand: the tree the checks judge is the
tree that lands. The fragment rule was CONTRIBUTING.md's sentence and nothing
held it — of the PRs on `main`'s first-parent line before the fragment
machinery, PR #93 changed four `server-portable/` files and recorded itself
only as a hand-numbered section; run over that merge, the landing check
refuses it and names the four. The migration-number rule (5b) and the rest of
`check-fork-consistency` needed no merged-tree copy: the workflow has run on
`merge_group` since SMD-1808, and on that event the checkout is the group's
head, so they would run on the merged result the day there is a queue.

**Held.** Check 20: a doubled queue rule, one with no parameters, a squashing
queue, a head-green queue, a queue waiting for a second PR — five mutants each
reporting one problem that names the field; the rule as `MERGE_QUEUE` records
it is accepted; a parameters-string non-probe throws nothing (twenty-five
mutants, one accepted addition, nine non-probes in all). `check-landing.ts`:
`landingProblem` is one pure function over a status-and-path list, eighteen
probes — a migration, a server file, an eval, a deleted migration, two asking
files both named; a fragment added beside a migration passes, one modified
beside a server change passes (a ticket landing in slices extends its
fragment), one deleted does not, a numbered change file does not; tests, a
test helper, Markdown, `db/` outside migrations, a look-alike directory pass; a
lockfile and an eval fixture ask — and the `-z` parser reads a status, a path
with a space and a non-ASCII path. The script runs its probes before the range
on every CI run; a probe failure, a range it cannot read, a PR range that
changes nothing, an empty group or a group whose first-parent commit is not a
merge exit 2 — the script's or the setting's fault, never read as the PR's.

**Measured after.** Over `main`'s history: the merge-group range
509a4b19..6d12413d reads as three landings (PR #110, #112, #111), each with
its fragment, and passes; the PR range baed5e4d...632754fa reads as one; PR
#93's merge alone fails naming `server-portable/embed.ts`, `index.ts`,
`preflight.ts` and `store-sql.ts`; the pre-fork range ad7b9eaf..71dd543e,
whose first-parent commits are plain, stops with exit 2 naming the first of
them; an empty group, an empty PR range and a bad event exit 2. The PUT of the
record with the `merge_queue` rule, on 2026-09-22, was refused: `422
Validation Failed — Invalid rule 'merge_queue'`, with no reason after the
colon; the live ruleset kept its four rules and its 14:50 timestamp. Three
disabled probe rulesets carrying only that rule were refused the same way — a
wildcard ref with the fuller "Wildcard ref names are not supported when merge
queue is enabled", so the parameters parse and the rule is what is refused; a
literal ref and the default-branch alias with the empty reason. GitHub's
documentation offers the queue on public repositories owned by an
organisation and private ones under Enterprise Cloud; `MHarris-SgyMd/OB1` is
owned by a user account (`isInOrganization: false`, `mergeQueue: null`). The
ticket's Verify — a queue rejecting a duplicated migration number, re-running
the real-Postgres jobs per queued PR — cannot be met on this repository. What
the tree keeps: strict up-to-date (SMD-1856) still makes the twelve checks
judge the tree that lands, at the cost of the author merging `main` first.

**Not taken.** Exemption by label, as the ticket wrote it — a merge group's
run carries no pull request and the workflow's token (`contents: read`) reads
none, so a label would hold on the PR run alone and by whoever remembers to
apply it; test files and Markdown are exempt by path instead, and a change
that wants no fragment for another reason writes a `changed`/`patch` one. A
thirteenth job for the landing check — a job is a context the record must
name and a re-apply; a step inside `Repo consistency` keeps the list.
Refusing a modified fragment of another ticket beside a server change — the
same shape as a ticket's second slice, which the fork lands. Holding the
fragment's ticket to the branch name — a branch carries no ticket the check
can trust. Dropping the `merge_group` path and `MERGE_QUEUE` because the rule
is refused — both are the queue's half of the work, done and held by probes;
the day the repository is organisation-owned they are a one-line record edit
away. Transferring the repository from this ticket — an owner's decision.

`siggymd/**` push run's skipped check may be the one read, is the only gate.
