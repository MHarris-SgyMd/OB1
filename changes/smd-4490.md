## Changelog

The agent runner no longer reads a Claude Code session whose result carries an error as one that finished (SMD-4490). A refused API key ends the run as an environment failure, and an error's text is never taken as a review's findings.

## Record

A session finished only if its result is a plain success: an API error, a limit or any other error result ends the run or the step as what it is (SMD-4490)

**Problem.** `run.ts` took a session that ended with a result as one that finished. Claude Code ends a session it could not finish with a result too. Measured on 2026-11-20 with Claude Code 2.1.329: the API answered 401 to the runner's key, and the session ended with one result of subtype `success`, `is_error` true, `terminal_reason` `api_error`, and the text "Invalid API key · Fix external API key". As read in `run.ts`, a worker ending so went on to import a bundle and failed there as a work failure, and a review ending so had that text parsed as one finding, the worker resumed to address it.

**Decided.** The design already says a limit is a work failure, and that Anthropic not answering before the worker session starts is an environment failure (`docs/agent-runner.md`, "On a failure"). The rule follows it:

| The session's ending | Worker | Review | Resumed worker |
| --- | --- | --- | --- |
| The API did not answer, before any tool call: no status, 401, 403, 408, 429, 500 and up | environment failure, the label kept | no findings, no resume | the pre-resume branch kept |
| The API refused the request, before any tool call: any other status | work failure | no findings, no resume | the pre-resume branch kept |
| An API error after a tool call | work failure | no findings, no resume | the pre-resume branch kept |
| The turn or budget limit | work failure | no findings, no resume | the pre-resume branch kept |
| Any other result that is not a plain success | work failure | no findings, no resume | the pre-resume branch kept |

A worker stopped by its limit does not go on to the gate, even when it left a bundle: a person decides what to do with part of the work. A review that did not finish does not stop the run, as a review that ran out of time never did; the note says it did not finish.

**Change.**

- **`run.ts`:** `sessionEnding` reads a session's outcome as one of five kinds. Only a result of subtype `success` with `is_error` exactly false is "finished"; an unknown shape is an error result. The worker, the review and the resume each act on the kind. The session's record names the kind (`api-error`, `limit`, `error-result`), so the hand-back comment and the PR body, which name any ending but `result`, name it too. A note carries the runner's own words and the result's subtype, never the result's text.
- **A review that did not finish** no longer leaves the note "review: no findings" beside the note that it did not finish.
- **`session.ts`** keeps the result's `api_error_status` (review pass 1).
- **`publish.ts`:** the PR body says a branch was not reviewed when its review did not finish (review pass 1).
- **`run-check.ts`:** seven sections, 37 cases (100 in all, from 63). `probes-check.ts` and `publish-check.ts`: one and two cases.
- **`docs/agent-runner.md` and the runner's README** say the rule.

**The probe stamp.** `session.ts` is hashed into it, and review pass 1 added one field there. The stamp on the maintainer's machine holds until the runner's install is moved to a commit with this change; then the probe sweep runs again from the install, at no cost.

**Verify.**

- The ticket's two Verify cases pass: a worker's API error before any call ends the run as an environment failure with the branch absent from the bare repository, though the stub wrote a good bundle; a review's API error gives no findings, a note that it did not finish, and no resume.
- Each new case fails with its rule removed: 34 mutants of `run.ts`, `session.ts` and `publish.ts`, each killed by an assertion (caught: mutant).
- The twelve runner self-checks pass.

**Review pass 1.**

- The limit's subtypes were keys of a plain object, so a subtype of `constructor`, `toString` or `__proto__` read as a limit, its note "stopped by its function Object() limit". They are a Map's keys (caught: run-it).
- Every API error before the first tool call was the environment's, a 400 the ticket itself causes included: the label kept, the same request sent again each run, never reaching a person. `session.ts` keeps the API's status, and only no status, 401, 403, 408, 429 and 500 and up keep the label. The note names the status (caught: cold-read).
- A run whose review did not finish goes on to the gate, and its PR body showed only "(ended api-error)" beside the review's turns. The body says the branch was not reviewed (caught: cold-read).
- The README's rule sat under "Cuts still to come". It has a section of its own, with the table (caught: cold-read).
- A mutant letting a fractional status through survived: 401.5 fell below 500 either way. The case has 500.5 (caught: mutant).

**Not done here.** No real session was run: the shapes are the one measured on 2026-11-20 and the subtypes the pinned binary names (`error_max_turns`, `error_max_budget_usd`, `error_during_execution`). A limit's `terminal_reason` was not measured, so the rule reads its subtype. Which statuses mean the API did not answer is the runner's reading of HTTP, not a list Claude Code gives. An environment failure has no back-off: a key that stays refused is tried again each tick, once there is a tick (cut 3c).
