## Changelog

Unlinking a thought (`update_thought` with `{"supersedes": null}`) now waits for a supersession accept in progress, as re-pointing one already did (SMD-3045). Before, an unlink could commit while an accept was running, and the accept then cleared a capture-only key's pointer above a link that was no longer under the accepted thought.

## FORK

An unlink takes the review lock: `update_thought` takes `ob1:supersession-review` whenever its envelope names `supersedes`, a clear included (SMD-3045)

**What changed** (migration 098).
- **`update_thought`** is 088's body under 088's signature with one change. The supersession advisory lock is taken whenever `p_provenance` names `supersedes` (`v_set_supersedes`): a thought's uuid, as before, or a JSON null that clears it, now too. It is taken before the fingerprint lock and the row, 033's order, whatever the row's pointer is: that is read under the row lock, after this one, and an unlocked read to skip the lock would reopen the race. A new sentinel `ob1:pointer-write-takes-review-lock` sits at the gate, and the function's comment says it. Nothing else moves: the same answers, refusals and writes, and the grants kept.

**Why.** `review_supersession_proposal` holds the review lock for the whole accept. Its lapse (097's `ob1_lapse_walk`, then the clears) reads the tree above the accepted row and then clears the capture-only pointers it found. A re-point onto a thought and `delete_thought` wait on that lock, but an unlink took none. SMD-3035's review pass 2 raced it on a real Postgres with a sleep between the walk and the clears. B's unlink of X (a write key's link X→S) returned during the sleep, and the accept then cleared the hook's pointer Y→X, although X was no longer under S. The same pass found a 40P01 with the same cause: one transaction unlinked a row (row lock, no review lock) and then re-pointed it (waiting on the review lock), while the accept's clear waited on that row.

**Lock order.**
- An unlink now takes supersession lock → (fingerprint lock) → row, as a re-point and `delete_thought` (036) do, so the 40P01 above has no crossing left.
- Outside the order, as before: a transaction of several calls that holds a row (a content edit, say) and then takes the review lock by any call (a pointer write, a clear now too, a delete, a citation, `rebuild_derived`, an accept) waits on the lock while a holder of it waits on something the transaction holds (a row, or an advisory lock taken after the review lock, such as a fingerprint lock or a node-state bucket), and Postgres breaks that with 40P01. Since 098 that holder can be a single-call unlink: under 088 it waited and then passed, while a single-call re-point as the holder closed the same cycle under both. Review pass 1 raced it on the row, with the transaction's later call each of `record_citation`, `delete_thought`, `rebuild_derived`, an accept and a re-point: 3 of 3 deadlocked for each under 098, 0 of 3 for each under 088. No shipped caller makes such a transaction (each store call is its own); taking the lock first (it is re-entrant) keeps one in the order.

**Not here.**
- 097's NOT HERE says that under an accept "only an unlink (which takes none, 088) moves one". Since 098 no write function moves a link out from under it. Two writes still take no review lock and move nothing out: a first capture naming supersedes (a new row; 092's check refuses or waits on a capture-only pointer onto the tree) and another taker's own lapse clears (nothing the accept's walk read as staying: a pointer it would clear too, which its re-read under the row lock then skips, or one above its frontier it never read). 097 is not edited, because migrations are append-only (`migrate.ts` checks each file's sha256), so db/README's 097 paragraph says what now holds.
- A taker that holds no review lock (a write key's re-capture, a text move, board-sync's adoption) still has the window between the walk's read and its clears: SMD-3046.

**Operators.** `098` applied after a by-hand re-apply of 088, 061 or 073 restores `update_thought` alone; `bun migrate.ts --reapply` restores every body. Preflight does not read the gate, so an 088 re-applied by hand over 098 passes its edit-signature check (073 re-applied over 088 did too): SMD-1227 has preflight read the gate, and SMD-3065 makes its printed remedies restore what they name, in the order printed.
