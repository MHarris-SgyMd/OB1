## Changelog

`deploy/canary.sh`'s env-file program is a file of its own, `deploy/canary-env.py`, where it was a 342-line string inside the script (SMD-4332). No behaviour changes.

## Record

canary.sh's env_file() program moved, unchanged, out of a `python3 -c` string into deploy/canary-env.py (SMD-4332)

**Problem.** `deploy/canary.sh`'s `env_file()` was one `python3 -c '…'` call holding a 342-line Python program: eight modes on argv and six helpers. Inside a bash single-quoted string every apostrophe is written `'"'"'`, 76 times here. The call carried a shellcheck SC2016 disable, since its text is the shell's to leave alone. No Python tool could lint, import or run the program by itself.

**Change.**

- **`deploy/canary-env.py`** is the string's text with each `'"'"'` written back as an apostrophe, and nothing else changed: no line added, none reworded, no message altered.
- **`env_file()`** is one line. It runs `python3 "$HERE/canary-env.py" "$@"` under the same six variables as before (`RT`, `PROJ`, `OWN_PROJECT`, `DROPPED`, `SET_BY_CANARY`, `FROM`). The SC2016 disable is gone with the string.
- **The comment over `env_file()`**, which tells the modes, says where the program is. **`MAINTAINING.md`** names the file beside `canary.sh` in its list of maintainer tooling.
- **`scripts/check-consistency.ts`** reads the new file. Its SMD-2873 check reads every code line of `canary.sh` and fails one that names compose.yaml's project outside the one project read. The moved lines were among them. The check now reads `canary-env.py` too, with nothing allowed there, and says so if the file is missing.

`deploy/canary.sh` is 1,588 lines, from 1,929. The script's two smaller inline blocks and its one-line JSON readers stay, as the ticket says.

**One thing a caller could see.** An error the program does not catch prints a traceback. Its `File` line said `"<string>"` and now names the file, with the source line under it. Only an error the program does not handle reaches one; its refusals are its own messages, and those are unchanged.

**Verify.**

- **The move is exact.** A script rebuilt the old block from the script as it was, undid the escapes, and compared it with the new file: identical.
- **Old and new run alike.** Each was run on scratch env files, the old as `python3 -c` text and the new as a file, 18 calls over the eight modes and their refusals. Exit code, stdout, stderr and every file written were the same, once three things that differ between any two runs were masked: the second a file was written in, keys minted from random bytes, and a traceback's `File` line (caught: run-it).
- **shellcheck is no worse.** 0.9.0 and 0.10.0 report one finding on the script before and one after; the current release reports none either way.
- **The first commit left the moved lines unguarded.** It left the checker's SMD-2873 check as it was. The check passed, since the moved lines name no project, but it no longer read them (caught: cold-read).
- **The checker guards them again.** With the check extended, the project's name planted on a code line of `canary-env.py` fails it at that line; in a comment, whole-line or trailing, it passes; with the file removed it fails saying so (caught: mutant).

**Not checked here.** The canary itself was not stood up or taken down from this branch on the maintainer's machine. CI's two canary steps do that on a runner: its refusals, held word for word, and a canary standing beside the stack.
