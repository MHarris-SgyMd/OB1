## Changelog

`deploy/canary.sh up --port N`, run without `--connect`, no longer calls a connector at the root of the canary's own port (`http://127.0.0.1:N/`) one the canary no longer answers. The proxy's legacy route still hands the root to the canary, deprecated, until v2.0.0 closes it, and the note now says that, and says `--port N --connect` moves the connector to `/mcp` (SMD-2661).

## FORK

canary.sh names a connector at the root of the canary's own port as on the deprecated root, not as one the canary no longer answers (SMD-2661)

**What changed.**
- `deploy/canary.sh`'s connector note (`up` without `--connect`): in port mode, a connector of this canary's at the root of `--port`'s port gets `connector … points at <its URL>, the root, which this canary answers only through the deprecated legacy route until v2.0.0 (SMD-2532): move it to /mcp with --port N --connect`. Any other connector of this canary's that is not at the canary's URL gets the note it got before. The root note is judged after `ours`, as the other is, so a root on another host is nobody's note.
- `.github/workflows/fork-checks.yml`'s canary step runs one more `up --port 8011 --no-smoke`, after the fallback run, with the stand-in connector at the root. It greps the new note, refuses `no longer answers` in the output, and checks that an unkeyed POST to the root answers 200 with a `Deprecation` header. The 200 is the canary's server refusing the missing key, so the root still reaches the canary, as the note says.

**Why.** SMD-2661 moves the dogfood canary from its own proxy on :8011 to `/canary/mcp` on stable's origin. When that canary was brought to v1.7.0 in port mode, with its connector still at `http://127.0.0.1:8011/`, `up` said the connector pointed where the canary no longer answers. It did answer: the smoke's own POST to the root got a 200 with a `Deprecation` header, and the connector's tools worked. The note compared the connector's port and path with `/mcp` and read any difference as gone. In path mode a connector at the old port's root is gone (the old proxy is removed), so that note stands.

**Held.**
- *The note, by case.* A harness pulled `shown`, `endpoint_of`, `ours` and the note's block from `canary.sh` by pattern, with the runtime stubbed. 15 cases:
  - port mode on 8011: the root as `/?key=x`, without a slash, and at `localhost` → the root note;
  - `/mcp` with a query or a trailing slash, a LAN host's root, stable's root → no note;
  - `/canary/mcp` on stable's port → no longer answers;
  - the canary moved to 8012 → no note for 8011's root, which is no longer the canary's;
  - path mode: 8011's root and `/mcp` with the old proxy → no longer answers; `/canary/mcp` and stable's root → no note;
  - no connector URL (none, or a stdio entry), in either mode → no note.

  All 15 hold on this branch. main's `canary.sh` fails exactly the three root cases.
- *The dogfood move.* From a worktree at tag v1.7.0, with the default runtime (the docker CLI against podman machine), `canary.sh up --connect` without `--port`. It refreshed from stable (no canary-only writes since its last refresh), and smoke passed 11/11 at `http://127.0.0.1:8010/canary/mcp`. The vector probe scored 85.5%. The connector moved there and the canary's own proxy was removed. Then the ticket's Verify: the keyed `/health` at `/canary/mcp` says tier canary, 1.7.0; stable's `/mcp` answers as stable; nothing listens on :8011.
- *The CI check's teeth.* Run against the dogfood stable's own proxy, the check passes on its root (200, `Deprecation: @1790899200`) and fails on `/mcp`, which carries no `Deprecation`. Its grep string matches the harness's output for the same URL.

**Review passes.**
- Pass 1, a cold read: no code defect. Fixed: three stale counts and descriptions of the CI runs, in deploy/README.md, the step's comment and canary.sh's header step 6; and this record's wording, which had the root's 200 as a working session (it is the server's refusal) and a harness case the script cannot reach (dropped).
- Tidy, behaviour unchanged: deploy/README.md's paragraph on moving the connector names the root note; the code comment says the exception holds with `--port`; the harness gains the two cases with no URL.

**Not taken.**
- *Every legacy path on the canary's port.* The legacy route takes every path no other route takes, so a connector at `:8011/foo` also still answers. Only the root is the documented old URL (SMD-2306); the rest keep the old note.
- *The move driven from main.* main's `canary.sh` has SMD-2677's podman fix, but `up` builds the canary from its own checkout, which would have moved the canary off v1.7.0 too. The tag's tree under the docker CLI moved it and kept the version.
