## Changelog

A tool's scope is stated once, in the manifest: the MCP server registers a tool, the REST core admits its route and the MCP server's keyed HTTP mirrors (`/health`, `/worker-*`, `/jobs/`) admit a key through the same gate, and a test holds MCP `tools/list` and the REST core's OpenAPI document to one contract — names, titles, descriptions, input fields and which keys reach each. The two REST gateways, `integrations/open-brain-rest` and `integrations/rest-api`, are retired against the REST core, each route given its fate in `docs/vendored-disposition.md`; the Chrome capture extension (0.7.0) and the `ob1-local-http` skill call the REST core at `/api`, and an upgraded extension asks for that URL once (SMD-1931).

## FORK

The MCP tools and the REST core's operations are two projections of one contract, held by a test that reads both surfaces as a client does, and the two REST gateways retire against it (SMD-1931)

**What changed.**
- **One gate.** `tools.ts` gains `scopeOf` and `mayCall`, moved from `rest/app.ts`: whether a key's scope unlocks a tool's group (`UNLOCKS`). `index.ts` registers each MCP tool only where `mayCall` holds, in place of a hand-written `canRead`/`canCapture`/`canWrite` beside each registration, and its keyed HTTP mirrors ask `mayCall` for the tool each mirrors (the keyed `/health` body for `brain_info`, `/worker-status`, the three `/worker-*` actions, `/jobs/<id>` for `job_status`), so a tool's scope is stated once, in the manifest, for every route that serves it. `openapi.ts` reads its `x-ob1-scope` through `scopeOf` too. The surface each scope sees is unchanged, on every route: read tools for a read or write key, `capture_thought` for a capture or write key, the write tools for a write key alone.
- **One contract, tested.** `test-server.ts` [10a] lists the tools from the running MCP server with a write, a read and a capture-only key, and compares them with the OpenAPI document `rest/openapi.ts` builds (the REST core serves it at `/openapi.json` with only `servers` added): the same names one for one, and per tool the same title, the same description (bar the one rewrite of a job's poll link to `/v1/jobs/`), the same input fields schema for schema, the same required fields, a body required exactly when a body field is, and each scope's `tools/list` the operations whose `x-ob1-scope` it unlocks.
- **The mirrors, tested.** `test-auth.ts` [8d] sends a read, a capture and a write key to each mirror and holds that a key is shown `ok` and nothing else exactly where the mirrored tool's scope refuses it. `auth.ts`'s `canRead`/`canCapture`/`canWrite`, which state the hierarchy for a caller without a tool name and for the vendored copies of that file (no manifest beside them), are held to `UNLOCKS` for every scope ([4]).

- **The dispositions** (`docs/vendored-disposition.md`, "The brain's outward surface"). Every route of both gateways is marked served (naming the REST core route), dropped (with why), or moved (SMD-2280 for what only a GUI needs, SMD-2690 for smart-ingest's jobs). Each surface-bearing integration is marked plugin (agent-memory-api, smart-ingest, readwise-capture: SMD-2690; slack- and telegram-capture: SMD-2101), client (the Chrome extension) or retire.
- **The gateways retire.** `integrations/open-brain-rest` and `integrations/rest-api` are deleted, with their rows in `extensions/test-auth.ts` and their blocks in `extensions/test-writes.ts`. The disposition doc's rollup moves them to remove (keep + audited 75, remove 12), and the ADR's retirement condition reads met.
- **The Chrome capture extension** (0.7.0) sends each queued payload as `capture_thought` through `POST /v1/thoughts`: source `chrome-<platform>`, trust `ingested`, metadata held to the operation's bounds (the fixed keys first, the platform's own after, the server's reserved keys never). It checks its key with `GET /v1/whoami` and says when the key cannot capture, and a refusal is logged with the facts that say why. The endpoint is stored under a new key, so an install upgraded from the gateway's release starts unconfigured: the banner asks for the REST core's URL, and the retry queue waits rather than failing on the old URL's 404. The queue keeps the old payload shape, so a capture queued before the upgrade sends after it.
- **The rest.** `skills/ob1-local-http` calls `POST /v1/thoughts`, `POST /v1/search` and `GET /v1/thoughts` at `/api`. The Next dashboards, the indexes, the connector registry and taxonomy, smart-ingest's README and the auto-capture adapter's README say the gateway is retired.

**Why.** SMD-2283 and SMD-2284 already drew both surfaces from `core/schemas.ts`'s specs and the manifest, and a tool missing a spec or a route does not compile. What was left was the gate, stated twice (and again at each HTTP mirror), and the agreement itself, which held only by name through two separate suites. The gateways re-implemented the surface a third and fourth time against the same brain, with keys of their own (one admitted no capture key; the other had no scopes at all); the ADR's retirement condition for them was a fate per route.

**Verify.** `bun test-server.ts` (832), `bun test-rest.ts` (290, with [10]: the extension's own `config.js` and `api-client.js` run against the REST app), `bun test-auth.ts` (187), `extensions/` `bun test-auth.ts` (756 with the gateways' rows gone; the five `auth.ts` copies, docblock re-synced), `extensions/` `bun test-writes.ts` (270, against Postgres, with the gateways' blocks gone), `bunx tsc --noEmit` in `server-portable/`, `bun scripts/check-fork-consistency.ts`. Eleven mutants killed: by [10a], a tool's MCP registration dropped, the scope gate removed, and in `openapi.ts` a description, a title, the input/output side of the schema, one input field, the required set and every scope changed; by [8d], a mirror asking the wrong tool's gate (the worker actions a read tool's, `/health` capture's, `/jobs/` a write tool's). Eleven more, in the extension, killed by test-rest [10]: trust undeclared, reserved keys sent, a manual capture's mode lost, a surrogate pair split, the key check skipped, a refusal's `needs` dropped, a re-capture not counted, the eight-key bound dropped, the endpoint read under the old key, a legacy sync endpoint carried over, the gateway's path re-appended.
