## Changelog

A tool's scope is stated once, in the manifest: the MCP server registers a tool, the REST core admits its route and the MCP server's keyed HTTP mirrors (`/health`, `/worker-*`, `/jobs/`) admit a key through the same gate, and a test holds MCP `tools/list` and the REST core's OpenAPI document to one contract — names, titles, descriptions, input fields and which keys reach each. The two REST gateways, `integrations/open-brain-rest` and `integrations/rest-api`, are retired against the REST core, each route given its fate in `docs/vendored-disposition.md`; the Chrome capture extension (0.7.0) and the `ob1-local-http` skill call the REST core at `/api`, and an upgraded extension asks for that URL once. `enhanced-mcp`, `delete-thought-mcp`, `update-thought-mcp` and `discord-capture` retire too: the core's tools do what the first three did, and the fourth was a README with no code (SMD-1931).

## FORK

The MCP tools and the REST core's operations are two projections of one contract, held by a test that reads both surfaces as a client does, and the REST gateways and three vendored MCP servers retire against it (SMD-1931)

**What changed.**
- **One gate.** `tools.ts` gains `scopeOf` and `mayCall`, moved from `rest/app.ts`: whether a key's scope unlocks a tool's group (`UNLOCKS`). `index.ts` registers each MCP tool only where `mayCall` holds, in place of a hand-written `canRead`/`canCapture`/`canWrite` beside each registration, and its keyed HTTP mirrors ask `mayCall` for the tool each mirrors (the keyed `/health` body for `brain_info`, `/worker-status`, the three `/worker-*` actions, `/jobs/<id>` for `job_status`), so a tool's scope is stated once, in the manifest, for every route that serves it. `openapi.ts` reads its `x-ob1-scope` through `scopeOf` too. The surface each scope sees is unchanged, on every route: read tools for a read or write key, `capture_thought` for a capture or write key, the write tools for a write key alone.
- **One contract, tested.** `test-server.ts` [10a] lists the tools from the running MCP server with a write, a read and a capture-only key, and compares them with the OpenAPI document `rest/openapi.ts` builds (the REST core serves it at `/openapi.json` with only `servers` added): the same names one for one, and per tool the same title, the same description (bar the one rewrite of a job's poll link to `/v1/jobs/`), the same input fields schema for schema, the same required fields, a body required exactly when a body field is, and each scope's `tools/list` the operations whose `x-ob1-scope` it unlocks.
- **The mirrors, tested.** `test-auth.ts` [8d] sends a read, a capture and a write key to each mirror and holds that a key is shown `ok` and nothing else exactly where the mirrored tool's scope refuses it. `auth.ts`'s `canRead`/`canCapture`/`canWrite`, which state the hierarchy for a caller without a tool name and for the vendored copies of that file (no manifest beside them), are held to `UNLOCKS` for every scope ([4]).

- **The dispositions** (`docs/vendored-disposition.md`, "The brain's outward surface"). Every route of both gateways is marked served (naming the REST core route), dropped (with why), or moved (SMD-2280 for what only a GUI needs, SMD-2690 for smart-ingest's jobs). Each surface-bearing integration is marked plugin (agent-memory-api, smart-ingest, readwise-capture: SMD-2690; slack- and telegram-capture: SMD-2101), client (the Chrome extension) or retire.
- **The gateways retire.** `integrations/open-brain-rest` and `integrations/rest-api` are deleted, with their rows in `extensions/test-auth.ts` and their blocks in `extensions/test-writes.ts`. The disposition doc's rollup moves them to remove (keep + audited 75, remove 12), and the ADR's retirement condition reads met.
- **The Chrome capture extension** (0.7.0) sends each queued payload as `capture_thought` through `POST /v1/thoughts`: source `chrome-<platform>`, trust `ingested`, metadata held to the operation's bounds (the fixed keys first, the platform's own after, the server's reserved keys never). It checks its key with `GET /v1/whoami` and says when the key cannot capture, and a refusal is logged with the facts that say why. The endpoint is stored under a new key, so an install upgraded from the gateway's release starts unconfigured: the banner asks for the REST core's URL, the retry queue waits for it, and the old URL's local key is removed. A new URL or key is checked against `GET /v1/whoami` before it is saved, so a bare origin (which the proxy's legacy route hands to the MCP server) or a key that cannot capture is refused at the Configure screen. A failed capture is sorted by what answered: the REST core's own refusal of it (a refusal code, or a 413) is rejected; an answer that is not the REST core's (no refusal code: the MCP endpoint, a proxy's 404 while `/api` is off), a path it does not serve, or a refused key is a setup failure, which waits in the queue without spending attempts and is logged with what to fix; a timeout, a 429 or a 5xx backs off and is dead-lettered after five attempts. `existing` is reported for a write key's re-capture; the brain does not tell a capture-scoped key that the text existed, so its re-capture reads `captured`. The queue keeps the old payload shape, so a capture queued before the upgrade sends after it.
- **The rest.** `skills/ob1-local-http` calls `POST /v1/thoughts`, `POST /v1/search` and `GET /v1/thoughts` at `/api`. The Next dashboards, the indexes, the connector registry and taxonomy, smart-ingest's README and the auto-capture adapter's README say the gateway is retired.

- **The vendored MCP servers retire.** `integrations/enhanced-mcp`, `integrations/delete-thought-mcp`, `integrations/update-thought-mcp` and `integrations/discord-capture` are deleted, along with their `extensions/test-auth.ts` rows (the allow-list rule now reads one list, kubernetes-deployment's, by name) and their `extensions/test-writes.ts` blocks (one raw fixture write is left: checks 10 and 26 count 1). The suite's `TZ: America/Chicago` goes with the enhanced-mcp date arm it served. `skills/deleting-thoughts` and `skills/updating-thoughts` name the core connector with a write key. The deleting skill now says what the core's delete does: it records the previous content in the audit trail, and it refuses a cited source unless `detach_citations` is set. `schemas/thought-audit`, the SDK v2 record, the registry (discord is a sink vendor now), the taxonomy tables and the indexes follow. The disposition rollup reads keep + audited 71, remove 16.

- **After review of the merged work** (PR 5). The extension's failure handling is as above (it had rejected a bare origin's every capture, and dead-lettered a wrong URL's after five tries while the docs said they waited). Text the retirements left: the deleting skill's receipt (the core's reply has no content length), the updating skill's OpenRouter requirement and its `supersedes` field (both skills 1.1.0), lint-sweep's report (`fetch`, not enhanced-mcp's `get_thought`), entity-extraction-worker's step 4, the extension's README and setup text, and docs that spoke of the gateways as present. `RESERVED_META` is exported read-only.

**Why.** SMD-2283 and SMD-2284 already drew both surfaces from `core/schemas.ts`'s specs and the manifest, and a tool missing a spec or a route does not compile. What was left was the gate, stated twice (and again at each HTTP mirror), and the agreement itself, which held only by name through two separate suites. The gateways re-implemented the surface a third and fourth time against the same brain, with keys of their own (one admitted no capture key; the other had no scopes at all); the ADR's retirement condition for them was a fate per route.
