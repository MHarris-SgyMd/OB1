## Changelog

One env file is one brain: `deploy/README.md` says how to run a second brain beside the first from its own env file — `COMPOSE_PROJECT_NAME`, its own secrets, and each host port it publishes — and how local models are shared or not. `deploy/canary.sh` reads stable's project from stable's env file, as compose does, instead of assuming `open-brain`: the canary is `<stable>-canary`, its connector the same, and its env file `.env.<stable>-canary.local` (the dogfood canary's stays `.env.canary.local`), which now names the canary's own project; `canary.sh names` prints them. `deploy/tier.sh` gains `--project`, and its `--network` default is the project's `data` and `egress` networks, the project read from `--env-file` the same way. A tracked env file of any name but an `.example` now fails the fork's checks (SMD-2873).

## FORK

One env file is one brain: the scripts take the instance's project, not `open-brain` (SMD-2873)

**What changed.**
- `deploy/canary.sh`:
  - stable's project, unless `--stable-project` names it, is the one stable's env file names: compose renders a stub carrying `compose.yaml`'s `name: open-brain`, under `--env-file`, so an env file's or the shell's `COMPOSE_PROJECT_NAME` wins over it as it does for stable's own `up`. A read that fails is refused, naming `--stable-project`;
  - a stable project ending `-canary` is refused, as a canary's;
  - the canary's project is `<stable>-canary`, and its connector defaults to that name: `open-brain-canary` beside the default stable, as before;
  - its env file defaults to `.env.<canary>.local` beside stable's, so two brains' canaries in one directory stay apart; `open-brain-canary` keeps `.env.canary.local`, the file the dogfood canary has run on since SMD-2583;
  - the canary's file names the canary's own project, `COMPOSE_PROJECT_NAME="<canary>"`, written with it and checked when made, so compose given that file alone acts on the canary (stable's name never reads as a setting there: every read is under the canary's `-p`). Every `up` refuses a file naming another project, and notes one naming none, a file made before this;
  - the read tries the runtime's compose, then either other one, strips the quotes compose puts on a name YAML would read otherwise (`"123"`), and shows compose's own reason when it fails; a refusal says whether the name came from `--stable-project`, the env file or the shell, whose `COMPOSE_PROJECT_NAME` is unset once read;
  - `names` prints stable's project, the canary's, the connector and the env file, and changes nothing; a `--runtime` not on PATH is refused as such.
- `deploy/tier.sh`: `--project NAME` names the stack whose networks it joins; unset, the project `--env-file` names, read the same way, else `open-brain`. `--network`'s default is `<project>_data,<project>_egress`. `--project` with `--network` is refused, and so is an empty value for either, which would fall through to the env file's project. A missing network says which project it was looked for under, and where that came from.
- `deploy/README.md`: a new section, "One env file is one brain": `COMPOSE_PROJECT_NAME` over `compose.yaml`'s `name:`, what the project's name carries (containers, networks, the database volume, the images), each instance's own secrets and host ports (`SERVER_PORT`, `N8N_PORT`, the host-ports overlay's three), a second brain from `.env.ob1b.local` (the root `.gitignore`'s form, which `.env.ob1b` is not), the scripts' names for it, and local models: an Ollama per instance, or one on the host every instance names (podman machine reaches the host's loopback; Docker on Linux needs the bridge address or every interface). The canary and tier sections, and the examples naming `open-brain-*` containers, say the names follow the project.
- `scripts/check-fork-consistency.ts`, check 13: a tracked env file (a name that starts `.env`, ends `.env` or holds `.env.`: `.env.x`, `.env~`, `x.env`, `x.env.local`, `.envrc`) is refused unless it is an `.example`, `.sample` or `.template` (it was `.env` and `.env.canary*`), since an instance's and a canary's files hold a database password and keys. The same check holds that canary.sh and tier.sh read the project through a stub carrying `compose.yaml`'s own `name:` (read with Bun.YAML) on one code line that reads an env file, and that no other code line in either names `open-brain` but a short list per script: so no fixed default, in any of bash's forms.
- `.github/workflows/fork-checks.yml`:
  - the tier step runs `tier.sh` with an env file naming `ob1x`, refused for want of `ob1x_data`; with `--project ob1y` over it, refused for want of `ob1y_data`; and `--project` with `--network`, refused;
  - the canary refusal step runs `canary.sh` with that env file, refused for want of project `ob1x`'s stack, with no `/tmp/.env.ob1x-canary.local` made; `canary.sh names` for it, for `--stable-project ob1y` and for the default stable each print the four names expected; and `--stable-project open-brain-canary` is refused;
  - the canary's `up` step requires the made `.env.canary.local` to name `open-brain-canary`, compose given it alone to take that project, and an `up` to refuse it once it names `open-brain`.

**Why.** SMD-2872's direction is any number of brains on one machine, each its own env file; compose.yaml already allowed it (measured in `docs/one-brain-per-stack.md`), but canary.sh assumed stable was `open-brain` and named its canary and connector once for all, and tier.sh joined `open-brain`'s networks by default. A second brain's canary would have shared the first's env file, its keys included.

**Held.**
- The project read, through compose 5.5.1 and 2.38.2: an env file naming `ob1a` plain, `"ob1b"` with a comment, `export ob1c`, one naming none (`open-brain`), and the shell's value winning over the file's.
- Live on podman: canary.sh with an env file naming `ob1x` refused for want of `ob1x`'s Postgres, writing nothing beside it; tier.sh with it refused for want of `ob1x_data`, `--project ob1y` for `ob1y_data`, and `--project` with `--network` refused.
- `env_file`, lifted out of canary.sh, on throwaway files: the canary's file written naming its project and not stable's, accepted when made; a file naming stable's project refused when made and at an `up`; one naming none let through at an `up`, refused when made; no drift.
- `canary.sh names` and tier.sh's refusals on podman: a plain name, `123` (quoted by compose), the shell's name winning, an uppercase name (compose's own reason shown), a `-canary` project, `--stable-project`, an empty `--network` or `--project`, and a `--runtime` not on PATH.
- 21 mutants of the checker's hold, each caught: fixed defaults as a bare assignment, `${X:-…}`, `declare`, `: "${X:=…}"` and indented, in either script, or behind a trailing comment that names an allowed word; a silent `open-brain` fallback on the stub's own line; an allowed word sharing a line with a default; the stub naming another project, moved into a comment, or reading no env file (`--env-file` only in a comment); a tracked `.env.ob1b`, `prod.env`, `.envrc`, `.env~`, `stack.env.local` and `.envrc.local`. A tracked `.env.sample` and `.env.template` pass.
- The guard refuses a canary file whose `COMPOSE_PROJECT_NAME` is built from a shell variable, and lets a file as written through with a `COMPOSE_PROJECT_NAME` in the shell.

**Tidied after the last pass.** Check 13's header and this record describe the tracked-env rule as it ended (a name that starts `.env`, ends `.env` or holds `.env.`), the README's `.gitignore` sentence reads plainly, and tier.sh's header marks its examples as the default project's names.
