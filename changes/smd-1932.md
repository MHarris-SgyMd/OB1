## Changelog

`db/` and `evals/` are type-checked in CI: each gains a `tsconfig.json` mirroring the server's, the four type-checked directories pin `@types/bun`, `typescript` and `@types/node` at one version (check 18 holds them in step), two `Typecheck` steps run in the portable-server job, `db/ci-parity.sh` runs the four typechecks, and the findings a first strict pass over the two directories turned up are fixed — none a runtime defect (SMD-1932).

## FORK

The workers, benches, suites and evals are type-checked — `db/` and `evals/` each get a tsconfig, the type pins and a CI step, check 18 holds the four directories' pins in step, so a call-site mismatch fails at review rather than at the first run (SMD-1932)

**What changed.** `db/tsconfig.json` and `evals/tsconfig.json` are
`server-portable/tsconfig.json` byte for byte — `strict`, `bundler`
resolution, `allowImportingTsExtensions`, `types: ["bun"]`, `include:
["*.ts"]`. `db/package.json` and `evals/package.json` pin `@types/bun` 1.4.0
and `typescript` 5.9.3 as `server-portable/package.json` and
`compat/supabase-sql/package.json` do, and all four now pin `@types/node`
26.6.2. Two step pairs in `.github/workflows/fork-checks.yml`'s portable-server
job — `bun install --frozen-lockfile`, then `bunx tsc --noEmit`, in `db/` and
in `evals/` — sit after the server's own `Typecheck`, in that job because the
imports of `../server-portable/*.ts` resolve through
`server-portable/node_modules`, which the job installs first; the evals'
install brings LanceDB, whose types `store-backends.ts` imports. The server's
step is unchanged: two more of the same shape. `db/ci-parity.sh`, which exists
to be CI's local equivalent and ran every suite and no typecheck, runs the four
directories' `bunx tsc --noEmit` after the suites, each behind its own frozen
install, an install that fails reported apart from a compile that fails.
`db/README.md`'s Testing section and `evals/README.md`'s Steps name the
one-liner and what it needs.

The first strict pass over the two directories found more than the three
shapes the ticket named, none a runtime defect, all fixed so the steps start
green: the six `resolveEmbedConfig(process.env)` call sites — three workers,
three evals — failed the weak-type check (`ProcessEnv` has no property in
common with `EmbedEnv`, whose every key is optional) and now pass `process.env
as EmbedEnv`, the type the module declares for what it reads;
`consolidate.ts` and `extract-entities.ts` declared `let configError: string |
null = null` and wrote it inside worker closures, which control-flow analysis
does not follow, so the read at the end of the run narrowed to `never`, and the
declaration is now `null as string | null`; six count reads in
`test-schema.ts` called PGlite's `query<T>` without `T` (rows `unknown`) and
name their one column; the proposal id, asserted a string on the next line and
passed to eleven calls wanting one, carries `!` beside the assert, as the file
already did for `undirected!`; Bun's `sql\`\`` and `sql.unsafe()` answer `any`,
so lists built from them in `bench-hnsw.ts`, `test-live.ts`,
`eval-recency.ts` and `eval-supersession.ts` name their element type where
they are built; `evals/_chunk-e2e-child.ts` and `evals/eval-extraction.ts`
import and export nothing, so tsc read them as scripts sharing one global scope
(each redeclaring the other's `CASES` and `BASE`, top-level `await` refused),
and each carries `export {}`, which is what Bun already treats every file as.

**Why.** CI's `Typecheck` steps ran in `server-portable/` and
`compat/supabase-sql/` only, so the workers, benches, suites and evals — the
first callers to break when a shared signature moves — were compiled nowhere.
SMD-1903's first review pass caught the shape: `providerCall` and
`getEmbedding` gained a required `subject`, the compiler fixed every server
call site, and `db/reembed.ts`'s provider probe kept its one argument. At
runtime the gate read `subject.kind` on `undefined`, the probe's catch printed
"The embedding provider is not usable: undefined is not an object…" and exited
2, so a re-embed against any endpoint not declared local could never start,
and the message blamed the provider; `test-live` did not see it because its
re-embed sections declare the stub local, where the gate returns before
touching the subject. The three evals calling `judgePair`, `extractEntities`
and `resolveEmbedConfig` directly were fixed by grep the same day. And the
pins were not one surface: `bun-types` depends on `@types/node: "*"`, so each
lockfile had frozen whatever was current at its last install — 26.4.0,
26.4.1, 26.6.2 and, in `evals/`, the 20.19 apache-arrow's range hoisted — and
`tsc --listFiles` showed each program loading its own, so `server-portable/*.ts`
was checked against one Node typing in its own step and another in `db/`'s.

**Held.** The two CI steps: with SMD-1903's probe fix reverted on the working
tree (`getEmbedding("reembed.ts provider probe")`, one argument), the `db/`
step fails with `Expected 2-3 arguments, but got 1` at `db/reembed.ts` and
nothing else does; restored, all four directories exit 0. Check 18
(`typecheckSurfaceProblems`, one pure function with five probes): the four
directories pin the three packages at `server-portable`'s values — TypeScript
dedupes by name and version, so one directory bumping alone loads two
`bun-types` into the programs that import the server's files — their
`compilerOptions` equal the server's (keys sorted at every depth, arrays in
order), and the workflow runs `bunx tsc --noEmit` under each exactly once, a
step under an unlisted directory refused; on the real tree a drifted `db/` pin,
a drifted `target` and a reworded `evals/` step each fail by name. The parity
helper: green on `db/`, red with the probe mutant's one line, and a pin the
lock does not carry reported as the install failing with bun's own reason.
The first catch came with the second merge of `main`: SMD-1806's new
`db/ingest-records.ts` imports `scripts/fragments.mjs` and
`scripts/fork-index.mjs`, plain JavaScript with no declaration file, and the
`db/` step refused both imports as implicit `any`; `fragments.d.mts` and
`fork-index.d.mts` now type them as `db/config.d.mts` types `config.mjs`.
