## Changelog

`db/` and `evals/` are type-checked in CI: each gains a `tsconfig.json` mirroring the server's and pins `@types/bun` and `typescript` at the server's versions, two `Typecheck` steps run in the portable-server job, and the pre-existing findings a first strict pass over the two directories turned up are fixed — none a runtime defect (SMD-1932).

## FORK

The workers, benches, suites and evals are type-checked — `db/` and `evals/` each get a tsconfig, the type pins, and a CI step, so a call-site mismatch fails at review rather than at the first run (SMD-1932)

CI's `Typecheck` steps ran `bunx tsc --noEmit` in `server-portable/` and
`compat/supabase-sql/` only. `server-portable/tsconfig.json` includes `*.ts` in
that directory, so the workers in `db/` — `reembed.ts`, `consolidate.ts`,
`extract-entities.ts`, the benches, `migrate.ts`, the suites — and everything
in `evals/` were never compiled anywhere, though they import
`server-portable/*.ts` and are the first callers to break when a shared
signature moves. SMD-1903's first review pass caught the shape: `providerCall`
and `getEmbedding` gained a required `subject`, the compiler fixed every server
call site, and `db/reembed.ts`'s provider probe kept its one argument. At
runtime the gate read `subject.kind` on `undefined`, the probe's catch printed
"The embedding provider is not usable: undefined is not an object…" and exited
2, so a re-embed against any endpoint not declared local could never start,
and the message blamed the provider. `test-live` did not see it because its
re-embed sections declare the stub local, where the gate returns before
touching the subject. The three evals that call `judgePair`, `extractEntities`
and `resolveEmbedConfig` directly were fixed by grep the same day, for the same
reason.

`db/tsconfig.json` and `evals/tsconfig.json` are `server-portable/tsconfig.json`
byte for byte — `strict`, `bundler` resolution, `allowImportingTsExtensions`,
`types: ["bun"]`, `include: ["*.ts"]` — and `db/package.json` and
`evals/package.json` pin `@types/bun` 1.4.0 and `typescript` 5.9.3 as
`server-portable/package.json` and `compat/supabase-sql/package.json` do, so
the four directories share one Bun type surface; both lockfiles carry the two
packages. All four also pin `@types/node` 26.6.2: `bun-types` depends on
`@types/node: "*"`, so each lockfile had frozen whatever was current at its
last install — 26.4.0, 26.4.1, 26.6.2 and, in `evals/`, the 20.19 that
apache-arrow's range hoisted — and `tsc --listFiles` showed each program
loading its own, so `server-portable/*.ts` was checked against one Node typing
in its own step and another in `db/`'s (first review pass). Two steps in `.github/workflows/fork-checks.yml`'s portable-server
job — `bun install --frozen-lockfile` then `bunx tsc --noEmit`, in `db/` and in
`evals/` — sit after the server's own `Typecheck`, in that job because the
imports of `../server-portable/*.ts` resolve through
`server-portable/node_modules`, which the job installs first. The evals'
install brings LanceDB, whose types `store-backends.ts` imports; without it the
step fails on the two `Cannot find module` lines a fresh checkout showed. The
server's step is unchanged: two more of the same shape, not a rename.
`scripts/check-fork-consistency.mjs` gains check 18, since nothing held the
pins the ticket added "so the directories cannot drift": the four directories
pin the three packages at `server-portable`'s values (TypeScript dedupes by
name and version, so one directory bumping alone loads two `bun-types` into
the programs that import the server's files), their `compilerOptions` equal
the server's, and the workflow runs `bunx tsc --noEmit` under each exactly
once, a step under an unlisted directory refused; the rule is one pure
function with five probes (first review pass). `db/ci-parity.sh`, which exists to be
CI's local equivalent, ran every suite and no typecheck at all — the server's
included; it now runs the four directories' `bunx tsc --noEmit` after the
suites, each behind its own frozen install, the exit code as the verdict
(first review pass).

A first strict pass over the two directories found more than the three shapes
the ticket named, none a runtime defect, all fixed so the steps start green.
The six `resolveEmbedConfig(process.env)` call sites — three workers, three
evals — failed the weak-type check (`ProcessEnv` has no property in common
with `EmbedEnv`, whose every key is optional); each now passes `process.env as
EmbedEnv`, the type the module declares for what it reads, which
`resolveEmbedConfig` trims through `stringOr` as before. `consolidate.ts` and
`extract-entities.ts` declared `let configError: string | null = null` and
wrote it inside their worker closures, which control-flow analysis does not
follow, so the read at the end of the run was narrowed to `never`; the
declaration is now `null as string | null`. Six count reads in `test-schema.ts`
called PGlite's `query<T>` without `T`, whose rows are then `unknown`; each
names its one column. `test-schema.ts`'s proposal id is asserted a string on
the line after it is read and then passed to eleven calls wanting one; the
read carries `!` with the assert named, as the file already did for
`undirected!`. Bun's `sql\`\`` and `sql.unsafe()` answer `any`, and a `.map`
over that is `any`, so a later `.every` or `.filter` callback had no type for
its parameter in `bench-hnsw.ts`, `test-live.ts`, `eval-recency.ts` and
`eval-supersession.ts`; each list names its element type where it is built,
and `test-live`'s pool is `new Set<string>`. `evals/_chunk-e2e-child.ts` and
`evals/eval-extraction.ts` import and export nothing, so tsc read them as
scripts sharing one global scope, where each redeclared the other's `CASES`
and `BASE` and top-level `await` was refused; each carries `export {}`, which
is what Bun already treats every file as.
