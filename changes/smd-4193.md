## Changelog

The agenda and `search_thoughts` take a call's own priority weights (SMD-4193 PR 1, migration 131). `weights` overrides the default weights by name for that call alone: `overdue`, `soon`, `unknown` and the rest of `docs/priority.md`'s table. It is `weights` on the MCP `agenda` and `search_thoughts` tools, `weights[name]=value` on `GET /v1/agenda`, and `weights` in `POST /v1/search`'s body beside `priority_weight` or `min_priority`. The answer names them. A bad weight is refused 400, naming it. A weight can make a term cross a level, as 122's own did.

## Record

A call passes its own priority weights: the agenda over REST and MCP, and `search_thoughts` beside its ranking, whose blend divides by their span; migration 131 adds that span (SMD-4193)

**Why.** `docs/priority.md` calls each weight "a setting a read overrides by name", but only SQL or the store could. The agenda's SQL took weights and the server passed NULL; search's `priority_weight` read the defaults. SMD-4177's changelog had to say the old order was reachable only through SQL.

**What changed.** The maintainer chose, on 2026-11-10, both: a call can pass weights, and the operator gets a setting every read takes as its defaults. They also chose that `search_thoughts` takes them, with its blend's scale following the weights through a span migration. The operator's setting is PR 2.
- **Migration 131** adds `ob1_priority_span(weights)`: 128's span under the defaults with the weights laid over them (5 + overdue 3 + unblocks_many 1 = 9 under 122's). `effective_priority` checks the weights over no items, so a bad one is refused 22023 in its words, naming it. NULL answers the defaults' span. 128's `ob1_priority_span()` is unchanged. `query_log.filter`'s comment names the weights an agenda row logs.
- **The input** is one `weights` object, every name optional, with 122's names and ranges, so a client sees them in the tool's schema and the schema refuses an unknown name or a value out of range by name. The database checks them again; cap below `unblocks_many_at`, which may need a default, is its alone, answered `REFUSED_WEIGHTS` (400) with the weights it names. An empty set is the defaults.
- **The agenda** passes them to 123's `p_weights`, logs them with its filter, echoes them as `weights` (null without), and says them under its list.
- **`search_thoughts`** refuses them without `priority_weight` above 0 or `min_priority` (`REFUSED_WEIGHTS`, `unranked`), since nothing would read them. With a ranking, the window's read, the page's labels and the span take them. The note names them and the scale. A brain before 131 fails only a weighted, blended search, with a hint naming the migration.
- **REST's query string** reads an object field as one parameter a field (`weights[overdue]=3`, OpenAPI's deepObject), each by its type, and the document says so. A bare `weights=…`, or an object given for a field that is not one, is refused 400 naming the field.
- **The REST client** sends an object of one level as openapi-fetch's deepObject, where it refused every object. It still refuses one holding an object, a list or null, a field name a URL would split, and an object in a list. The MCP server forwards through it, so the MCP agenda reaches the core with its weights.
