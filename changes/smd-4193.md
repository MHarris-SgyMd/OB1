## Changelog

The agenda and `search_thoughts` take a call's own priority weights (SMD-4193 PR 1, migration 131). `weights` overrides the default weights by name for that call alone: `overdue`, `soon`, `unknown` and the rest of `docs/priority.md`'s table. It is `weights` on the MCP `agenda` and `search_thoughts` tools, `weights[name]=value` on `GET /v1/agenda`, and `weights` in `POST /v1/search`'s body beside `priority_weight` or `min_priority`. The answer names them. A bad weight is refused 400, naming it. A weight can make a term cross a level, as 122's own did.

The operator sets the priority weights every read takes as its defaults (SMD-4193 PR 2, migration 132): `set_priority_weights` (MCP, or `POST /v1/priority-weights`), an operator key's alone, overrides the built-in weights by name, and `{}` clears them. A call's own weights still override them. `brain_info` shows the setting. A stored setting the database refuses fails every priority read, naming it. **Upgrading:** a database role granted the priority group before 132 needs `migrate.ts --grant` again, or every priority read fails naming `priority_weight_settings`.

### PR 2: the operator's weights, which every read takes as its defaults

**Why.** The maintainer chose both on 2026-11-10: a call's own weights (PR 1) and an operator's setting every read takes as its defaults. Until now the defaults changed only by a migration, so an operator who disagreed with level first (SMD-4177) had to pass weights on every call.

**What changed.** The maintainer chose (2026-11-11) that the setting is set by a SQL function and by an operation only an operator key may call, and that a bad setting is refused when written and, if one is stored anyway, fails every read loudly rather than being skipped.
- **Migration 132:**
  - **`priority_weight_settings`:** one standing row at most, overrides by name, never empty. A row is history: it changes only to end, once; a DELETE or TRUNCATE is refused.
  - **Its own table, not an `ob1_config` row:** the server's roles hold `SELECT` alone on `ob1_config`, and a grant to write it would reach the embedding model's row.
  - **The built-in weights:** 128's constant moves to `ob1_priority_builtin()`.
  - **`ob1_priority_defaults()`** lays the standing setting over them, so `effective_priority`, the agenda, search's ranking and both spans take it.
  - **`ob1_priority_weights_refusal`** checks a setting in `effective_priority`'s words. A stored setting it refuses raises 22000 on every read, naming the setting, its key and the weight. It is 22000, not 22023, so the server answers it as the brain's fault, not the caller's bad weight.
  - **`set_priority_weights(weights, actor)`** admits a key the registry classifies operator, by its agent id (115's rule: a name lends no kind). The weights standing already write nothing, and `{}` clears.
  - **`priority_weight_setting()`** gives the standing setting without raising.
  - **Grants:** the priority group gains the table.
- **The operation** `set_priority_weights` (write scope; `POST /v1/priority-weights`) is modelled on `reset_capture_stamp`. It answers `{changed, weights, previous, setAt, setBy, caller}`. Refusals: `REFUSED_NOT_OPERATOR` (403, its words naming the key's kind and the fix, shared with the reset), `REFUSED_WEIGHTS` (400), `REFUSED_INPUT` (400, the schema).
- **Faults:** the agenda's and a ranked search's fault names the mend for a refused setting, or the grant a role lacks.
- **Preflight's priority row**, which reads the group from `db/config.mjs`, names the setting's writes as `set_priority_weights`'. Without `SELECT` on it, the row says every priority read fails.
- **`brain_info`** gains `database.priorityWeights` and a Priority weights row, which reads one of these:
  - built in;
  - the operator's setting, with when and by which key;
  - the operator's setting REFUSED, with the check's words;
  - not read.
- **The words** say "built in" where a weight's default was meant: the weights' descriptions, and the agenda's and search's tool descriptions.
- **The REST client** carries the operation, regenerated.

### PR 1: a call passes its own priority weights

**Why.** `docs/priority.md` calls each weight "a setting a read overrides by name", but only SQL or the store could. The agenda's SQL took weights and the server passed NULL; search's `priority_weight` read the defaults. SMD-4177's changelog had to say the old order was reachable only through SQL.

**What changed.** The maintainer chose, on 2026-11-10, both: a call can pass weights, and the operator gets a setting every read takes as its defaults. They also chose that `search_thoughts` takes them, with its blend's scale following the weights through a span migration. The operator's setting is PR 2.
- **Migration 131** adds `ob1_priority_span(weights)`: 128's span under the defaults with the weights laid over them (5 + overdue 3 + unblocks_many 1 = 9 under 122's). `effective_priority` checks the weights over no items, so a bad one is refused 22023 in its words, naming it. NULL answers the defaults' span. 128's `ob1_priority_span()` is unchanged. `query_log.filter`'s comment names the weights an agenda row logs.
- **The input** is one `weights` object, every name optional, with 122's names and ranges, so a client sees them in the tool's schema and the schema refuses an unknown name or a value out of range by name. The database checks them again; cap below `unblocks_many_at`, which may need a default, is its alone, answered `REFUSED_WEIGHTS` (400) with the weights it names. An empty set is the defaults.
- **The agenda** passes them to 123's `p_weights`, logs them with its filter, echoes them as `weights` (null without), and says them under its list.
- **`search_thoughts`** refuses them without `priority_weight` above 0 or `min_priority` (`REFUSED_WEIGHTS`, `unranked`), since nothing would read them. With a ranking, the window's read, the page's labels and the span take them. The note names them and the scale. A brain before 131 fails only a weighted, blended search, with a hint naming the migration.
- **REST's query string** reads an object field as one parameter a field (`weights[overdue]=3`, OpenAPI's deepObject), each by its type, and the document says so. A bare `weights=…`, or an object given for a field that is not one, is refused 400 naming the field.
- **The REST client** sends an object of one level as openapi-fetch's deepObject, where it refused every object. It still refuses one holding an object, a list or null, a field name a URL would split, and an object in a list. The MCP server forwards through it, so the MCP agenda reaches the core with its weights.
