## FORK

The connector taxonomy — five facets per capability, one connector per vendor with its direction derived, one family schema per family as the seam any fetcher lands on, held by check 18 (SMD-1933)

**What changed.** `docs/connector-taxonomy.md` is the spec and
`docs/connector-registry.json` the one source behind it: the four closed and
near-closed facet sets (`direction`, `round_trip`, `transport`, `cardinality`),
the open `family` set with a schema per family (item, grouping key, canonical,
text, edges, metadata, identity, dividing line — SMD-1867's five outputs named
from the input side), the four fetcher kinds (low-code node, native driver, MCP
server, browser extension), and every external-touching artifact with its
capabilities. Twenty-two artifacts, thirty-two capability rows, sixteen
connectors. A **connector is a vendor**: the registry declares its direction
once and the check derives it from the capabilities that name the vendor, so
`telegram` (two sources, three sinks, four artifacts), `gmail`, `discord` and
`slack` are one `bidirectional` connector each instead of the separate capture
and digest artifacts they were. `scripts/connector-registry.mjs` renders the
family schemas and the two tables into the spec between markers; the prose
around them is hand-written. `CONTRIBUTING.md` says when a contribution is a
connector; `docs/vendored-disposition.md` points at the classification.

**Why.** SMD-1924's triage found the same vendor implemented several times —
`gmail` a source twice and a sink once, `telegram` a source twice and a sink
three times — each artifact carrying its own client, and no seam that would let
the orchestration tool SMD-1863 picks land a vendor's existing node in the
brain without an OB1 connector. The ticket's own list of "external-touching
artifacts" was prose; nothing could say whether a new recipe touching Notion
was classified. Two families the ticket's seven did not cover surfaced at
classification time: `calendar/event` (life-engine reads Google Calendar
through the client's MCP connector) is declared; `web-clip` has no instance
(the Chrome extension captures conversations) and stays declared for the
clipper that will.

**Held.** Check 18: `registryProblems`, one pure function in
`scripts/connector-registry.mjs`, run over an in-memory baseline first and then
one mutant per rule kind, each expected to yield exactly its kinds — a
transport off the set, a fourth transport added to the registry's own set, a
sixth facet, a fifth fetcher, an undeclared family, the reserved family used, a
schema field missing, a directory that does not exist, an artifact listed
twice, a path off the shape, a capability repeated, a connector declaring
`source` while its capabilities span both, a vendor with no connector, an
external-touching artifact left unclassified (by service, by tag, by the
vendor's name as a tag, by the disposition table alone), one both classified
and excused, one classified that nothing marks, a stale or reasonless excuse,
a stale, empty, reasonless or uncompilable pattern, a registry or an artifacts
block of the wrong shape — and non-probes: a model-provider service triggers
nothing, two patterns covering one service are both live, a metadata whose
tags are a string throws nothing. Then the real tree: the coverage rule sweeps
every `metadata.json`'s `requires.services` against the not-a-connector
patterns (model providers, hosting, the brain's own surface, agent runtimes),
the connector-shaped tags, the declared connector names as tags, and the
SMD-1867 rows of the disposition table; the spec's generated block must equal
the render, compared only when the registry is sound.
`bun scripts/connector-registry.mjs --check` runs the same rules by hand.

**Not taken.** A `connector` block inside each artifact's `metadata.json` — the
schema is `additionalProperties: false` and shared with upstream's gate, and a
connector spans artifacts, so the classification belongs beside the artifacts,
not inside one. Dropping `notification-target` — kept reserved, unusable until
`reserved` is removed, which the check makes a visible spec change. Building
the capture node, the envelope route or any mapper — SMD-1931 owns the route,
SMD-1867 the projection, SMD-1863 the fetcher count; this change fixes the
payload and the classification they share. A hand-written classification table
— the doc's tables are rendered, so the prose cannot drift from the data.

**Follow-ups.** The two verify items that need a pipeline — a new vendor with
only a mapping, the same vendor through a low-code node and a native driver
yielding one canonical — are specified here and proven under SMD-1867 and
SMD-1863; SMD-1814's writable Obsidian moves that connector to `bidirectional`
in the registry when it lands.

**Upstream status:** not sent — the taxonomy classifies this fork's vendored
tree and holds it in this fork's check; upstream has neither.
