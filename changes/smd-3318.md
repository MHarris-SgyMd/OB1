## Changelog

`bun db/backup.ts` exports the brain's `thoughts` and its entity graph (`ob1_entities`, `thought_entities`, `ob1_entity_edges`) as one JSON file per table, read from one snapshot. Each row is Postgres's own JSON, so it reads back into the same values, and a run that fails writes nothing. It replaces `recipes/brain-backup/backup-brain.mjs`, which reached the brain through `compat/supabase-sql`. **Upgrading:** run `bun db/backup.ts --url <the brain's postgres:// URL>` where you ran `bun backup-brain.mjs`. The files keep their names, `<table>-<date>.json`, and the tables are now the core's: the recipe's `entities`, `edges`, `ingestion_jobs` and `ingestion_items`, which no Daemonic Brain has, are gone (SMD-3318).

## Record

Three vendored maintenance scripts leave the SQL shim for `db/` — PR 1: brain-backup's export is `db/backup.ts` (SMD-3318)

SMD-3216 retires `compat/supabase-sql`. Its 2026-10-22 decision ports three maintenance scripts to `db/` scripts on Bun's Postgres client: brain-backup, lint-sweep and thought-enrichment. They go one PR each. This is PR 1, brain-backup's export.

**What changes.**
- **`db/backup.ts`, new.** It writes one JSON array per table, named `<table>-<UTC date>.json`, as the recipe did, in `./backup` or `--out`. Flags go through `cli.ts` and the connection through `connect.ts`.
  - **The tables are the core's:** `thoughts`, `ob1_entities`, `thought_entities` and `ob1_entity_edges` (migrations 001 and 016). The recipe read `entities` and `edges` from `schemas/entity-extraction`, which no Daemonic Brain has, and the retired smart-ingest schema's two tables, skipping each one that was missing. A missing table now means an unmigrated brain, and the run refuses.
  - **One snapshot:** the four tables are read in one REPEATABLE READ, READ ONLY transaction, so a mention never names a thought the thoughts file lacks. SELECT on the four tables is enough.
  - **Postgres's own JSON:** each row is `to_jsonb(row)`, written as Postgres renders it, so `jsonb_populate_record` reads it back unchanged. The recipe's rows went through JavaScript, which cut timestamps to milliseconds and turned numerics into strings.
  - **Every row once:** pages of 1,000 follow each table's primary key (keyset, not OFFSET), and each table's rows written are compared with its `count(*)` in the snapshot.
  - **All or nothing:** each file is written to a `.tmp` sibling and renamed only when all four are written. A failed run leaves the directory as it found it, an earlier backup of the same date included, and exits 1 with the database's reason. The recipe kept the tables that succeeded and overwrote their files.
  - **A 60 s statement_timeout** for the run, as the recipe's per-page bound was; the server cancels the query.
- **`recipes/brain-backup`:** `backup-brain.mjs` is removed. The README and `metadata.json` are now a pointer to the `db/` script, as `recipes/weekly-digest`'s are, and still name `pg_dump` as the whole-brain backup.
- **`db/test-live.ts`:** [26] drops the export's half and keeps lint-sweep's. The new [50] drives `db/backup.ts`. Both bodies run in a function of their own: test-live's module body was at TypeScript's control-flow limit (TS2563), and even an empty new top-level section crossed it. Wrapping [26] makes room for [50].
- **The record:** `docs/vendored-disposition.md`'s two brain-backup rows, `db/README.md`'s new section, and the hand-port mentions in `MAINTAINING.md`, `compat/supabase-sql/README.md`, `scripts/migrate-to-sql-shim.ts` and `scripts/check-consistency.ts` (whose name-check entry for the removed file goes).

**The version contract.** The removed script is vendored code, outside the contract (MAINTAINING.md, "Versioning"), so this is a `minor` with an Upgrading line.

**Evidence.**
- **[50] alone:** 8 assertions pass, in about 12 s:
  - the CLI as deployed, with 1,001 thoughts past the page and every file the table's rows, once each, read back unchanged;
  - a microsecond timestamp, a numeric's trailing zero and a vector, as Postgres wrote them;
  - two rows a page in process, with a thought and its mention written by another session between the tables and left out of both files;
  - a role with SELECT on `thoughts` alone, which exits 1 naming 42501, leaves no file or `.tmp`, and keeps the date's earlier file; the same role with SELECT on the four tables, which succeeds;
  - the URL refusals.
- **Mutants**, each against [50]:

| Mutant | Result |
| -- | -- |
| no snapshot (READ COMMITTED) | killed |
| the keyset repeats a page's last row (`>=`) | killed |
| no `ORDER BY` on a page | killed |
| a failed run leaves the finished tables' `.tmp` files | killed |
| each table renamed as it finishes | killed |
| rows through JavaScript (a `Date` cuts the microseconds) | killed |
| no count check | survives |

The count check survives because, with the paging right, no row can miss it. It is the run's own guard for when the paging is wrong: under the `>=` mutant, it is what failed the run ("wrote 1002 row(s) of 1001").

**Limits, kept.** The export is not a restore: nothing reads the files back into a brain. It is not the whole brain either; `pg_dump` is.
