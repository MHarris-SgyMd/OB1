## Changelog

`bun db/backup.ts` exports the brain's `thoughts` and its entity graph (`ob1_entities`, `thought_entities`, `ob1_entity_edges`), and any companion tables present, as one JSON file per table, read from one snapshot. Each row is Postgres's own JSON, so it reads back into the same values, and a run that fails renames nothing into place. It replaces `recipes/brain-backup/backup-brain.mjs`, which reached the brain through `compat/supabase-sql`. **Upgrading:** run `bun <checkout>/db/backup.ts --url <the brain's postgres:// URL> --out <directory>`, or keep `DATABASE_URL` in a `.env` in the directory you run from; without `--out` the files go to `./backup` there, as before. A read-only role now needs SELECT on `ob1_entities` and `ob1_entity_edges` too, or the run replaces no file. Timestamps now keep their microseconds and offset, numeric values are JSON numbers rather than strings, and `FETCH_TIMEOUT_MS` is now `--statement-timeout` (SMD-3318).

## Record

Three vendored maintenance scripts leave the SQL shim for `db/` — PR 1: brain-backup's export is `db/backup.ts` (SMD-3318)

SMD-3216 retires `compat/supabase-sql`. Its 2026-10-22 decision ports three maintenance scripts to `db/` scripts on Bun's Postgres client: brain-backup, lint-sweep and thought-enrichment. They go one PR each. This is PR 1, brain-backup's export.

**What changed.**
- **`db/backup.ts`, new.** It writes one JSON array per table, named `<table>-<UTC date>.json`, as the recipe did, in `--out` or `./backup`. Flags go through `cli.ts` and the connection through `connect.ts`.
  - **The tables:** always the core's `thoughts`, `ob1_entities`, `thought_entities` and `ob1_entity_edges` (migrations 001 and 016). The recipe's companion tables, `entities` and `edges` (`schemas/entity-extraction`) and `ingestion_jobs` and `ingestion_items` (the retired smart-ingest schema), are exported when present as tables with their schema's key, and named when absent; another relation under the name (a view, another tool's table) is named and passed over. The smart-ingest plugin's own tables (`plugin_smart_ingest`) are a plugin's, not exported. A missing core table means an unmigrated brain, and the run fails (exit 1).
  - **The database the URL names:** the run refuses with exit 2 when the connection reached another one (Bun lets `PGDATABASE` beat the URL's), and its first line names the database.
  - **One snapshot:** every table is read in one REPEATABLE READ, READ ONLY transaction, so a mention never names a thought the thoughts file lacks. Its first statement locks every table it reads (ACCESS SHARE, before the snapshot, as pg_dump does), so a TRUNCATE, drop or rename waits for the run rather than landing under it. SELECT on the tables is enough.
  - **Postgres's own JSON:** each row is `to_jsonb(row)`, so `jsonb_populate_record` reads it back unchanged. The recipe's rows went through JavaScript, which cut timestamps to milliseconds and wrote numerics as strings.
  - **Every row once:** pages follow each table's primary key (keyset, not OFFSET), 100 rows for thoughts and 1,000 for the others, each page written with one write, and each table's rows written are compared with its `count(*)` in the snapshot.
  - **Nothing in place until the reads are done:** each table is written to a new file of the run's own (`<file>.<run id>.tmp`, the id the pid and a random part, opened O_EXCL, so never through a planted path or with an older file's mode). It is renamed into place only once every table is written. A run that fails before then renames nothing and removes its files, so an earlier backup of the same date is kept; it exits 1 with the reason. The directory, when absent, is made once the connection is up and left made. A rename that fails after that point is said, naming the files already replaced. SIGINT, SIGTERM and SIGHUP remove the run's files (130, 143, 129); a run killed outright leaves them. A companion's file an earlier run wrote the same date, when this run wrote none, stays and is named. The recipe kept the tables that succeeded and overwrote their files.
  - **`--statement-timeout SECONDS`** (60; 0 for none) bounds each page, as the recipe's `FETCH_TIMEOUT_MS` did. The `count(*)`s run unbounded: on a large brain a count is longer than a page. The bound the session had is put back after each. The session's `client_connection_check_interval` (10 s, set where the server's platform has it) cancels a stopped run's statement on the server, so its count does not hold the snapshot to the end.
- **`recipes/brain-backup`:** `backup-brain.mjs` is removed, and the README and `metadata.json` are now a pointer, as `recipes/weekly-digest`'s are. The README says how to reach the stack's Postgres, where the files go, how to schedule a run, what a read-only role needs, and what changed in the files. It still names `pg_dump` as the whole-brain backup.
- **`.gitignore`:** `/backup/`, `/db/backup/` and `/recipes/brain-backup/backup/`, the default's places when run from a checkout or from the old script's directory.
- **`db/test-live.ts`:** [26] drops the export's half and keeps lint-sweep's. The new [50] drives `db/backup.ts`, in the sweep shard (~141 s on main), not the rest (~562 s, the run's longest cell). Both bodies run in a function of their own: test-live's module body was at TypeScript's control-flow limit (TS2563), and even an empty new top-level section crossed it. Wrapping [26] makes room for [50].
- **The record:** `docs/vendored-disposition.md`'s two brain-backup rows, `db/README.md`'s new section, and the hand-port mentions in `MAINTAINING.md`, `compat/supabase-sql/README.md`, `scripts/migrate-to-sql-shim.ts` and `scripts/check-consistency.ts` (whose name-check entry for the removed file goes).

**The version contract.** The removed script is vendored code, outside the contract (MAINTAINING.md, "Versioning"), so this is a `minor` with an Upgrading line.

**Limits, kept.**
- **Not a restore:** nothing reads the files back into a brain.
- **Not the whole brain:** `pg_dump` is.
- **Memory:** a page is held in memory whole: 1,000 rows, so about a gigabyte for 1 MB thoughts.
- **Vacuum:** the snapshot holds back vacuum's horizon for the run's length, as pg_dump's does.
- **A failed rename:** the files already renamed into place stay.
- **A run killed outright** (SIGKILL, the OOM killer) leaves its `.tmp` files, each a whole table's text, to be removed by hand.
- **The lock** waits for a table another session holds ACCESS EXCLUSIVE, to the statement bound; a run's held lock keeps a TRUNCATE, drop or `ALTER` of a table it reads waiting until it ends.
- **Loading the files back** is not a restore: the triggers fire and what the export leaves out stays out; pg_dump brings a brain back.
- **Not during an upgrade:** a migration altering a table the run reads waits on its lock, the brain's reads and writes of that table behind it, until the migrator's 10 s lock timeout fails the upgrade. The migrator's 55P03 message names a server, a worker or an idle transaction, not a backup.
- **Key order:** thoughts are read in key order, at random through the heap (about four times slower than heap order at a million); paging in heap order, or JSON Lines in place of one array, is a change of format left to a later decision.
- **A companion created or dropped** between the run's check and its lock is reported absent, or fails the run (42P01), respectively.
- **A signal after the renames** exits 130, 143 or 129 over a backup already in place.
- **A NUL in the URL's query** (`?application_name=x%00y`) ends the run with a stack dump, not exit 2: `connect.ts`'s door, shared by every `db/` script; the password is not printed.
