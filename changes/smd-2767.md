## Changelog

A plugin's webhook can answer before its work ends: `ctx.defer(work)` runs `work` after the answer, owned by the REST core — a failure is one line in its fault log rather than a rejection that stops the server, and the server's stop waits for it as for a request. `onceById(…, { defer: true })` claims a delivery's id at once and defers the capture, its record and its release, so a sender with a short deadline (Slack: three seconds) has its 202 in time while a resend is still told the capture is running (SMD-2767).

## FORK

A plugin webhook answers before its capture finishes: `ctx.defer`, owned by the runtime, and `onceById`'s `defer` (SMD-2767)

**What changed.**
- `HookContext.defer(work: () => Promise<unknown>)` (`server-portable/plugin-sdk.ts`), made by `core/plugins.ts`'s `runHook`:
  - `work` is a function, so it starts on the promise chain under the REST core's tracker (`track`, SMD-2250) and a throw before its first await is caught too; a promise handed instead, already running outside the tracker, is the plugin's fault, thrown (500).
  - Its failure goes to `deferredFault` as one message, whitespace collapsed and at most 300 characters; the REST core writes `api hook <path> deferred fault: …` to its fault log, the line a hook's own fault gets. The handler never rejects, and a log that throws loses the line, not the server.
  - The server's stop counts it with the requests (`N tool calls running`), waits for it within `OB1_STOP_GRACE`, and cuts it with them past that.
- `onceById(ctx, id, run, { …, defer: true })` claims the id and answers at once — `{ deferred: true }`, or as without `defer` a duplicate or one still running — and leaves the run, its record and its release to `ctx.defer`. Its type: `OnceDeferred`. Asked without a `ctx.defer` to hand, it throws before any claim.
- `plugins/README.md`: the handler is given `defer`; the "within seconds" bullet says how to answer quickly, what the runtime does with deferred work, and its cost — the sender has its 2xx, so a deferred capture that fails, or that a crash or the stop's cut ends, is not resent and is told only to the fault log — against an awaited capture, which keeps the sender's retry. A promise left running without `ctx.defer` still stops the REST core when it rejects.
- The example plugin still awaits its capture: its 202 carries the thought's id, which its README and CI's webhook step read.

**Why.** Found in SMD-2755's review: a hook answers when its handler returns, so a capture it awaits sits inside the sender's deadline, and capture's model calls take longer than Slack's three seconds. Leaving the capture running (`void ctx.call(…)`) and answering 202 was the only way, and under Bun 1.4.0 a `Bun.serve` handler that had answered and left a promise that later rejected exited the process: the whole REST core. Nothing in `server-portable` handles a stray rejection.

**Held.**
- `bun test-plugins.ts` (232, from 221): [14] through the REST app — a hook answers 202 before its deferred work runs, the work counted by the tracker; its failure is one fault line, on one line; the server answers on after it; work that throws before its first await is caught; work that succeeds writes nothing; a promise handed to `defer` is a 500 naming it. [13]: `onceById` with `defer` answers `deferred` once the id is claimed, the run not started and nothing recorded; the deferred run records its thought; one that throws gives its claim back and throws on; an id in flight defers nothing; `defer` with no `ctx.defer` throws before any claim.
- `../db/with-postgres.sh bun test-plugins-sql.ts` (104, from 101): a hook of the example's plugin deferring its capture, through `runHook` over the real table — 202 once its id is claimed (with a deadline, so an answer that waited for the capture fails rather than hangs), a resend while it runs 409, recorded against its id once it ends and a resend then its duplicate; one that throws answered 202, its claim given back, one fault.
- Ten mutants killed, none hanging a suite: the deferred failure rethrown (the suite's process exits, as the REST core did); the work not tracked; started outside the promise chain; the function check dropped; the fault message left on many lines; the REST app passing no fault log; `onceById` awaiting the deferred run, or ignoring `defer`; its check for `ctx.defer` dropped; the deferred run's release on a throw dropped.

**Not taken.**
- *A process-wide `unhandledRejection` handler in the REST core.* A stray rejection elsewhere is a bug the crash surfaces and the restart policy recovers from; swallowing it would hide it. `ctx.defer` is the plugin's way to leave work running.
- *The example deferring its capture.* Its answer would lose the thought's id, which its README's recipe and CI's webhook step read; the deferred shape is in `plugins/README.md` and held by the suites.
- *Its own line at the stop for deferred work cut.* It is counted with the requests in the stop's existing lines (`N tool calls running`, `closed unfinished`).

**Follow-ups.** SMD-2101's Slack port answers its Events API with `onceById(…, { defer: true })`.
