## Changelog

A plugin's webhook can answer before its work ends: `ctx.defer(work)` runs `work` once the answer is on its way, owned by the REST core — a failure is one line in its fault log rather than a rejection that stops the server, and the server's stop waits for it as for a request. `onceById(…, { defer: true })` claims a delivery's id at once and defers the capture, its record and its release, so a sender with a short deadline (Slack: three seconds) has its 202 in time while a resend is still told the capture is running (SMD-2767).

## FORK

A plugin webhook answers before its capture finishes: `ctx.defer`, owned by the runtime, and `onceById`'s `defer` (SMD-2767)

**What changed.**
- `HookContext.defer(work: () => Promise<unknown>)` (`server-portable/plugin-sdk.ts`), made by `core/plugins.ts`'s `runHook`:
  - Held until the handler returns an answer the runtime takes — its body serialised there, so a body JSON cannot write (a BigInt, a cycle) is the hook's fault, answered `FAILED` with nothing of why, before any work starts — then started on the event loop's next turn, after what the socket takes of the answer is written, so work that spins before its first await does not hold the sender's 2xx. A handler that throws, or answers what is refused, starts none of it, so a sender's retry of its 500 does not run it twice; `ctx.defer(work, discarded)` runs `discarded` then instead, awaited (within 5 s) before the 500 is thrown, and a deferral from a timer a failed handler left runs only its discard. Work runs on any answer taken, a retryable 409 or 503 included; the docs say such work goes through `onceById`.
  - It returns the answer as it held it — its status read once, its body as the JSON text it serialised, which must be an object's (a `toJSON` answering a string or null is refused), a body whose `toJSON` answers nothing written `{}` — and the route writes that text, so nothing read again fails the answer after its work has started.
  - `work` is a function, so it starts under the REST core's tracker (`track`, SMD-2250), counted from the answer with no gap after the request, and a throw before its first await is caught too; a promise handed instead, already running outside the tracker, is the plugin's fault, thrown (500).
  - Its failure goes to `deferredFault` as one message, made a string, whitespace collapsed and at most 300 characters, a discard's marked `discard: `; the REST core writes `api hook <path> deferred fault: …` to its fault log, the shape a hook's own fault line has. The work never rejects, and a log that throws loses the line, not the server.
  - The server's stop counts it with the requests (`N tool calls running`), waits for it within `OB1_STOP_GRACE`, and cuts it with them past that; work deferring more work extends the wait, never past its bound.
- `onceById(ctx, id, run, { …, defer: true })` claims the id and answers at once — `{ deferred: true }`, or as without `defer` a duplicate or one still running — and leaves the run, its record and its release to `ctx.defer`. Its type: `OnceDeferred`, and `Once<T> | OnceDeferred` for a `defer` that is a boolean. Asked without a `ctx.defer` to hand, it throws before any claim. Its discard gives the claim back, so a handler that fails after claiming leaves its sender's retry free to capture rather than refused until the lease. A deferred run that throws, hands back no thought (a refusal of the core's, which `ctx.call` returns rather than throws) or a `thoughtId` that is no uuid is a fault whose message names the delivery and, before its own words, what became of the claim (`delivery <scope> <id> (its id given back): …`, or `already re-claimed or pruned` when its DELETE found no claim of its own, `left to lapse at the lease` when the release failed, `kept to lapse at the lease` for a no-uuid), a key past 64 characters cut there so the fault keeps the line: its sender will not resend, so a claim given back is no longer the whole answer. Its discard says so when its release fails.
- `plugins/README.md`: the handler is given `defer`; the "within seconds" bullet says when deferred work starts, how to answer quickly, what the runtime does with deferred work and its cost — the sender has its 2xx, so a deferred capture that fails is told only to the fault log, and one a crash or the stop's cut ends only to the stop's count — against an awaited capture, which keeps the sender's retry; that a deferred run throws with a refusal's code; when to defer; raising `OB1_STOP_GRACE` for deferring hooks; that a 409 still answers the rare retry; and that a slash command answers its own text and defers the capture. A promise left running without `ctx.defer` still stops the REST core when it rejects.
- The example plugin still awaits its capture: its 202 carries the thought's id, which its README and CI's webhook step read.

**Why.** Found in SMD-2755's review: a hook answers when its handler returns, so a capture it awaits sits inside the sender's deadline, and capture's model calls can take longer than Slack's three seconds. Leaving the capture running (`void ctx.call(…)`) and answering 202 was the only way, and under Bun 1.4.0 a `Bun.serve` handler that had answered and left a promise that later rejected exited the process: the whole REST core. Nothing in `server-portable` handles a stray rejection.

**Not taken.**
- *A process-wide `unhandledRejection` handler in the REST core.* A stray rejection elsewhere is a bug the crash surfaces and the restart policy recovers from; swallowing it would hide it. `ctx.defer` is the plugin's way to leave work running.
- *The example deferring its capture.* Its answer would lose the thought's id, which CI's webhook step reads and its README describes; the deferred shape is in `plugins/README.md` and held by the suites.
- *Its own line at the stop for deferred work cut.* It is counted with the requests in the stop's existing lines (`N tool calls running`, `closed unfinished`); a deferred capture's claim, left unfinished, lapses at its lease.
- *A way for a slash command to report its deferred result.* Posting to Slack's `response_url` needs an outbound call, which check 31 keeps from a plugin; SMD-2101's to settle.

**Follow-ups.** SMD-2101's Slack port answers its Events API with `onceById(…, { defer: true })`.
