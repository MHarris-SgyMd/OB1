## Changelog

The release rehearsal on a pull request builds the arm64 images, and sets up QEMU for them, when the pull request changes what can build differently on arm64, a few files the ticket listed, or is a release cut; otherwise it builds amd64 alone. Every other rehearsal still builds the amd64 images and brings the stack up from them (SMD-3473).

## FORK

The release rehearsal builds both platforms when what can build differently on arm64 changes, or on a release cut (SMD-3473)

**What changed** in `.github/workflows/release.yml`:
- **A new step, "Whether this rehearsal builds both platforms",** runs after the facts on every rehearsal and sets `both`.
  - **A pull request** builds both platforms when `HEAD^1..HEAD` changes any of:
    - either Dockerfile, as the facts name them;
    - `release.yml`;
    - any `package.json` or `bun.lock` the Dockerfiles copy, read from their non-comment lines so a new stage's are covered too;
    - `.dockerignore` or anything under `dashboard/`. These build the same on both platforms (the dashboard stage builds on the build platform), but they're kept from the ticket's list;
    - `releases.json`, which only a release cut changes (every commit that has changed it since the one that created it, as `[]`, was one). So the tree a tag publishes has built both platforms in its own pull request first.
  - **The diff is read NUL-separated with `--no-renames`.** No path comes out quoted, and a rename lists its old path too.
  - **Any other pull request** builds amd64 alone.
  - **A dispatched rehearsal** always builds both.
  - **The step builds both, and says why, rather than failing the rehearsal,** when HEAD isn't a merge commit, git can't list the change, the change is empty, a Dockerfile the facts name is missing, or no lockfile can be read from the Dockerfiles.
- **QEMU's setup** runs on a tag or when `both` is true. **The two two-platform rehearsal builds** run only when `both` is true.
- **Unchanged:** the amd64 builds, the stack brought up from them, the overlay, the notes, the no-checkout bring-up, and everything a tag does.

**Why.** From 10-20 to 10-28 the rehearsal ran on 76% of pull requests, at 3,666 runner-s a day.
- Over the 20 green pull-request rehearsals from run 41107494355 to 41337021953, its median was 146.5 s. The figures drift: the 20 up to 41360077259 have QEMU at 7.5 s.
- The steps this skips took medians of 62 s (server, both platforms), 4.5 s (migrate, both platforms) and 6.5 s (QEMU), plus about 3 s of their post steps.
- A change to source the images copy (`db/`, `server-portable/*.ts`, `plugins/`) builds the same on both platforms, and so does a change to what neither image copies (`deploy/`, docs). arm64 differs in practice only where a RUN step executes under QEMU: the three dependency stages' `bun install`, beside the final stage's one-line `RUN printf`. The dashboard stage builds on the build platform.

**Departures from the ticket.**
- **The gate is wider than the ticket's list.** It adds each `package.json` and `bun.lock` the Dockerfiles copy. Their `bun install` runs under QEMU for arm64, so a lockfile that brings in a package with no arm64 build is exactly what the two-platform build exists to catch.
- **"Dockerfiles"** is the two this workflow builds, as its facts name them. The others in the repository (`jev/`, `deploy/auth/`, the runner's) are built by other jobs. `deploy/auth/Dockerfile` and `deploy/orchestration/runner.Dockerfile` fall under this workflow's `deploy/**` path, so a change to them runs the rehearsal, which builds amd64 alone.

**What this gives up.** Before, every rehearsal built arm64. So something outside the repository that breaks the arm64 build showed on any pull request:
- the `oven/bun:1.4.3-alpine` tag re-pushed, since it's pinned by tag, not by digest;
- an npm package's arm64 build withdrawn under an unchanged lockfile.

Now it shows only on a pull request that builds both platforms, a dispatched rehearsal, or the tag's own run.
- **Every release cut is one of those pull requests,** since it changes `releases.json`. So the tree a tag publishes has built both platforms first.
- **What remains is a break between the cut's last rehearsal and its tag,** the pre-tag soak included. The tag rebuilds arm64 cold, since the cut's rehearsal cached it under the pull request's own scope. Such a break fails "Build ob1-server" on the tag before anything is pushed:
  - a multi-platform build pushes only once both platforms are done;
  - `db/Dockerfile` runs nothing, and shares the server's base image.
  The cost is a failed tag run, and a new cut.
- **Pinning the base image by digest** would close its share of that.

**Projection, and why it is below the ticket's.** In run 41336268584 the two-platform server build took 46 s: 19 s building, 27 s exporting both platforms' layers to the Actions cache (`mode=max`).
- On a pull request that skips it, the amd64 share of that work moves into the single-platform build.
  - That build's median is 7 s today, because the two-platform build has just filled the cache.
  - 3.8 s of that 7 s is loading the image into Docker, which it does on either path.
- So of the skipped steps' ~75 s, roughly 35–50 s is saved. That puts the rehearsal's median near 95–110 s, not the ticket's ~85 s, until a run measures it.
  - The export includes the amd64-only dashboard stage's layers, so the amd64 share is likely more than half.
  - Run 41113444091 wrote 139 layers in about 48 s of export.
- **This PR edits `release.yml`, so its own rehearsal builds both platforms.** The first measurement of the skip path is the next pull request that skips it.
- If the Verify's ~85 s is missed, the export is the lever: a pull request's rehearsal writes `mode=max` cache for a scope only its own later runs read.

**Held.**
- **The gate step's body,** run against scratch repositories shaped as a pull request's checkout: a merge commit with the base as first parent and the PR's head as second, with the base moved after the branch. 17 cases:
  - `db/migrate.ts`, docs, `server-portable/core/*.ts` and `db/package.json` build amd64 alone (`db/package.json` is named only in a comment of `db/Dockerfile`);
  - each Dockerfile, `dashboard/src/…`, `server-portable/bun.lock`, `mcp-server/package.json`, `rest-client/bun.lock`, `.dockerignore`, `release.yml`, and a mix of a source file with a Dockerfile, build both;
  - a dispatched rehearsal, and a HEAD that isn't a merge commit, build both;
  - main moving `dashboard/` or a Dockerfile while the pull request changes only `db/` or docs builds amd64 alone. The base's own change isn't the pull request's.
- **Review passes 1 and 2 ran the step under bash 5.2.37 against 32 more cases.** All 49 come out right with exit 0:
  - `releases.json`, which builds both;
  - a name holding a newline that ends in a lockfile's path, which builds amd64 alone;
  - names with spaces, non-ASCII or backslashes;
  - renames away of `.dockerignore`, of `dashboard/` files and of a lockfile;
  - a deleted lockfile, and mode-only changes;
  - 1,500 files and 1,500 renames;
  - `Dockerfile.dev` and `db/tier.Dockerfile`, which aren't built here;
  - a root or nested `package.json`;
  - a non-merge HEAD with a parent, and an empty merge diff;
  - a shallow checkout, and dispatches from a branch;
  - Dockerfiles that name no lockfile, and an empty or missing Dockerfile path.
- **Three mutants of the fixed step** each turn the case meant for them wrong: no empty-diff check (N02), no merge-commit check (N01), and newline-separated reading (the odd names and renames).
- **The checker and actionlint 1.7.7 with shellcheck** pass. zizmor isn't run in CI; the new step takes its expressions through `env:`.
