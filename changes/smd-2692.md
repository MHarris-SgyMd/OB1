## Changelog

The Kubernetes deployment's server now gives each embedding or chat call `OB1_LLM_TIMEOUT` seconds, 120 unless set, the core server's knob and default. An embedding that stops answering fails the tool at that deadline with an error naming the knob. A chat call that stops answering, is refused, or answers something that is not JSON now leaves the thought stored without its tags, as on the core server, and the confirmation says so; before, a refusal or an unreadable answer failed the capture. Before this, the only bound was Bun's own 300 s fetch cut, and with the reply kept alive a client waited through all of it (SMD-2692).

## FORK

kubernetes-deployment's provider calls end at OB1_LLM_TIMEOUT, and a failed chat call costs a capture its tags, not the capture, as on the core server (SMD-2692)

**What changed.**
- `integrations/kubernetes-deployment/index.ts` gains `withDeadline(what, base, call)`. It reads `OB1_LLM_TIMEOUT` per call, in seconds, with `DEFAULT_LLM_TIMEOUT_S` (120) for an unset, non-numeric or non-positive value: `server-portable/embed.ts`'s name, default and rule. It hands the call `signal: AbortSignal.timeout(…)` and `timeout: false`, so this deadline replaces Bun's 300 s idle cut instead of running under it. A `TimeoutError` becomes a `ProviderTimeout` reading `Embeddings request to <base> timed out after N s (OB1_LLM_TIMEOUT)` (or `Chat completion …`), `embed.ts`'s wording. `getEmbedding` and `extractMetadata` run their fetch and their body read inside it, so a body that stalls after its headers is bounded too.
- `extractMetadata` falls back as `server-portable/metadata.ts` does. A timeout, a status outside 2xx, or a body that is not JSON is logged as `extractMetadata: …`, and the thought is stored as `uncategorized`/`observation` with `metadata_extraction_failed` set to `provider_timeout`, `provider_<status>` or `invalid_response_body`. The confirmation ends `Tags not extracted: <reason>`. Before, it read `r.json()` without checking the status, so a 502 page failed the capture with `Unexpected token`. A JSON answer whose message content is not JSON still falls back silently, as it did.
- The README's local-model section names the knob and the fallback, and `k8s/openbrain.yml` lists the knob at 120. The README's stop paragraph said a call silent for 10 s is closed because "this server has no keepalive", which SMD-2001 made false. It now says a call still running at the drain bound, whether on a query or on a provider call, is cut off, and the stop exits 1.
- `vendoredStalledLine`'s docblock in `server-portable/sse.ts`, with its three copies, no longer says no vendored server bounds its provider calls. The line it returns is unchanged.

**Why.** SMD-2001's keepalive stopped Bun resetting a silent reply at 8–12 s. That reset had been hiding a hung provider: the client failed fast while the tool hung on alone. Afterwards a client waited out Bun's fetch cut, about 300 s, and on SIGTERM the call held the drain to its bound. SMD-2001's review pass 3 found it, and put the bound on the fetches rather than shortening the keepalive. A 120 s deadline would fail a capture that a chat model taking 120–300 s used to complete, so the chat call falls back as the core's does, the embedding being what a capture needs.

**Held.** `extensions/test-auth.ts`, against a real provider server reached through the server's own fetch with its init as given, under `OB1_LLM_TIMEOUT=2`:
- *Search.* `search_thoughts`, whose embedding stalls after its headers, answers at about 2.0 s with the embeddings error naming the knob.
- *Capture, chat stalled.* When the chat call never answers, `capture_thought` logs the chat-completion timeout at about 2.0 s and goes on to its write. The write is refused, since there is no database in this suite, and the refusal is how the test sees the write was reached.
- *Capture, 502 or HTML.* A chat call answered 502, or answered with an HTML page, is logged with its reason, and the capture goes on.
- *Default.* The server's `DEFAULT_LLM_TIMEOUT_S` equals `embed.ts`'s.
- *Mutants.* Seven mutants each fail at least one case:
  - no deadline on the embedding call (no reply in 8 s);
  - no deadline on the chat call (no reply in 8 s);
  - the timeout left unnamed (`The operation timed out.`);
  - the knob read once at import;
  - a chat timeout that fails the capture;
  - the chat status unchecked;
  - a default of its own.

**Measured after.** test-auth 706/706; the new cases add about 4 s.

**Review passes.**

| Pass | Finding | Caught |
|---|---|---|
| 1 | A chat timeout failed the whole capture, though the embedding had finished, where the core server stores the thought without tags. With a 120 s deadline below Bun's 300 s cut, a chat model taking longer than the deadline but under 300 s lost captures it used to complete. `extractMetadata` also read the body without checking the status. It now falls back as `metadata.ts` does. The default was a bare 120 with nothing tying it to the core's, and is now a named constant held by test-auth. The README's stop limit named a provider call alone and read the knob as a cap; `vendoredStalledLine`'s docblock did not follow from its premise. The test block could be skipped silently when the import failed, and its 4 s upper bound is now 6 s. | cold read |

**Not taken.**
- *Cancelling the sibling call when the other fails.* A capture runs the embedding and the chat call together, so an embedding refused at once leaves the chat call running to its deadline. The core's capture runs the same `Promise.all`, and the call is now bounded (review pass 1).
- *Cancelling provider calls when the client leaves.* A capture whose client has gone still completes and is stored, as on the core server, where SMD-1864 logs the leaving client and nothing more (review pass 1).
- *One shared fetch helper for the two calls.* After pass 1 they handle failure differently: an embedding fails the tool, while a chat call falls back (review pass 1).
- *A test of the 120 s default.* It would take two minutes per run; the guard holds the value to `embed.ts`'s instead.
- *A test of `timeout: false`.* Only a deadline past 300 s would show it.
- *Aborting provider calls in flight on SIGTERM.* A call within its deadline can still outlast the 28 s drain and be cut off; the core server's drain is the same.
- *agent-memory-api's and readwise-capture's embedding fetches*, which also carry no deadline. They are HTTP handlers whose replies are not kept alive, so Bun resets a slow one at 8–12 s and the client does not wait.
