## Changelog

The Kubernetes deployment's server now gives each embedding or chat call `OB1_LLM_TIMEOUT` seconds, 120 unless set, the core server's knob and default. An embedding that stops answering fails the tool at that deadline with an error naming the knob. A chat call that stops answering, answers a status outside 2xx, or answers without usable tags now leaves the thought stored without them, as on the core server, and the log and the confirmation say why; before, a refusal whose body was not JSON, such as a proxy's 502 page, failed the capture, and any other failure (a refusal with a JSON error body among them) was stored as `uncategorized` with no word. An embedding that answers a body that is not JSON, or no embedding, now fails the tool saying so, and an embedding's error body is cut to 500 characters. Before this, the only bound was Bun's own 300 s fetch cut, and with the reply kept alive a client waited through all of it (SMD-2692).

## FORK

kubernetes-deployment's provider calls end at OB1_LLM_TIMEOUT, and a failed chat call costs a capture its tags, not the capture, as on the core server (SMD-2692)

**What changed.**
- `integrations/kubernetes-deployment/index.ts` gains `withDeadline(what, base, call)`. It reads `OB1_LLM_TIMEOUT` per call, in seconds, with `DEFAULT_LLM_TIMEOUT_S` (120) for an unset, non-numeric or non-positive value: `server-portable/embed.ts`'s name, default and rule. It hands the call `signal: AbortSignal.timeout(…)` and `timeout: false`, so this deadline replaces Bun's 300 s idle cut instead of running under it. A `TimeoutError` becomes a `ProviderTimeout` reading `Embeddings request to <base> timed out after N s (OB1_LLM_TIMEOUT)` (or `Chat completion …`), `embed.ts`'s wording. `getEmbedding` and `extractMetadata` run their fetch and their body read inside it, so a body that stalls after its headers is bounded too.
- `extractMetadata` falls back as `server-portable/metadata.ts` does, with its reasons. Each failure below is logged as `extractMetadata: …`, and the thought is stored as `uncategorized`/`observation` with `metadata_extraction_failed` set to the reason:

  | Failure | Reason |
  |---|---|
  | The deadline passes | `provider_timeout` |
  | A status outside 2xx | `provider_<status>`; the log carries the first 500 characters of the body |
  | A body that is not JSON, or one whose read fails before the deadline | `invalid_response_body` |
  | No message content | `no_message_content` |
  | Content that is not JSON | `unparseable_model_output` |
  | JSON that is not an object | `unexpected_json_shape` |

  The confirmation ends `Tags not extracted: <reason>`, and a `metadata_extraction_failed` key in the model's own answer is dropped, so the model cannot set the marker. Before, `extractMetadata` read `r.json()` without checking the status. A refusal whose body was not JSON, such as a 502 page, failed the capture with `Unexpected token`. Every other failure, a JSON error body included, was stored with no marker and no log. A chat endpoint that cannot be reached at all still fails the capture, as on the core server.
- `getEmbedding` reads its body as the chat call does. A read that fails before the deadline is an empty body, and the deadline passing during an error body is the named timeout, not `Embedding API failed: 503 ` with nothing after it. An error body is cut to 500 characters, as on the core server. A body that is not JSON, or one with no embedding in it, fails with an error saying so, naming the base, where before it read `Unexpected token` or `Cannot read properties of undefined`. Any embedding failure still fails the tool, since a capture or search needs the vector.
- The README's local-model section names the knob and the fallback, and `k8s/openbrain.yml` lists the knob at 120. The README's stop paragraph said a call silent for 10 s is closed because "this server has no keepalive", which SMD-2001 made false. It now says a call still running at the drain bound, whether on a query or on a provider call, is cut off, and the stop exits 1.
- `vendoredStalledLine`'s docblock in `server-portable/sse.ts`, with its three copies, no longer says no vendored server bounds its provider calls. The line it returns is unchanged.

**Why.** SMD-2001's keepalive stopped Bun resetting a silent reply at 8–12 s. That reset had been hiding a hung provider: the client failed fast while the tool hung on alone. Afterwards a client waited out Bun's fetch cut, about 300 s, and on SIGTERM the call held the drain to its bound. SMD-2001's review pass 3 found it, and put the bound on the fetches rather than shortening the keepalive. A 120 s deadline would fail a capture that a chat model taking 120–300 s used to complete, so the chat call falls back as the core's does, the embedding being what a capture needs.

**Held.** `extensions/test-auth.ts`, against a real provider server reached through the server's own fetch with its init as given, under `OB1_LLM_TIMEOUT=2`:
- *Search.* When the embedding answers 200 or 503 and its body then stalls, `search_thoughts` answers at about 2.0 s with the embeddings error naming the knob. An embedding answered 503 with a 2,000-character body, answered HTML, or answered `{"data":[]}` fails the search with the capped body, `not JSON`, or `no embedding`.
- *The shell's environment.* test-auth unsets `EMBEDDING_API_BASE`, `CHAT_API_BASE` and `OB1_LLM_TIMEOUT` before the import, and puts the database on port 1. The suite passes with all four set to conflicting values in the shell, and no case writes to a Postgres listening on 5432.
- *Capture, the control.* A capture whose tags arrive logs nothing from the extractor and gets its write's answer. There is no database in this suite, so the write is refused, and the control records whatever refusal this machine gives.
- *Capture, each fallback.* The chat call stalls, answers 502, answers HTML, cuts its body off (a raw socket that promises 100 bytes and sends six), answers with no content, answers prose, or answers a JSON array. Each case logs its reason and gets the control's answer, so it reached the same write. The stalled call does so at about 2.0 s.
- *Default.* The server's `DEFAULT_LLM_TIMEOUT_S` equals `embed.ts`'s.
- *Mutants.* Fifteen mutants each fail at least one case. Pass 3 re-ran the first and the sixth, whose anchors it changed, and added the last four; the rest are on code it did not touch:
  - no deadline on the embedding call (no reply in 8 s);
  - no deadline on the chat call (no reply in 8 s);
  - the timeout left unnamed (`The operation timed out.`);
  - the knob read once at import;
  - a chat timeout that fails the capture;
  - the chat status unchecked;
  - a default of its own;
  - a body read that fails the capture;
  - message content unchecked;
  - the shape unchecked;
  - content that is not JSON falling back silently;
  - an embedding's error-body read that swallows the deadline;
  - an uncapped embedding error body;
  - a missing embedding unchecked;
  - an embedding body that is not JSON, left unnamed.
- *Not held.* Dropping the model's own marker is visible only in the stored row, which this suite has no database to read.

**Measured after.** test-auth 716/716; the new cases add about 6 s.

**Not taken.**
- *Cancelling the sibling call when the other fails.* A capture runs the embedding and the chat call together, so an embedding refused at once leaves the chat call running to its deadline. The core's capture runs the same `Promise.all`, and the call is now bounded (review pass 1).
- *Cancelling provider calls when the client leaves.* A capture whose client has gone still completes and is stored, as on the core server, where SMD-1864 logs the leaving client and nothing more (review pass 1).
- *One shared fetch helper for the two calls.* After pass 1 they handle failure differently: an embedding fails the tool, while a chat call falls back (review pass 1).
- *Keeping the base URL out of the error a client sees.* The timeout and bad-body errors name `EMBEDDING_API_BASE` or `CHAT_API_BASE`, as the core's `providerCall` does. A base carrying credentials in its userinfo or query string would show them to any key. Credentials belong in `EMBEDDING_API_KEY` and `CHAT_API_KEY` (review pass 3).
- *Copying `providerCall` and `extractMetadata` into `integrations/_shared/`, held byte-equal as `auth.ts` and `sse.ts` are.* They carry the egress gate, the config resolver, the type normaliser and the people gate. The reasons now match by hand, and the default is held (review pass 2).
- *The core's tag-key allowlist (SMD-2510).* This server has always stored whatever keys the model returns. Only the marker the confirmation prints is dropped here (review pass 2).
- *Clearing the deadline's timer when a call finishes.* `AbortSignal.timeout` leaves its timer pending to the deadline. The core's `providerCall` does the same, and the cost is one small timer per call for 120 s (review pass 2).
- *A test of the 120 s default.* It would take two minutes per run; the guard holds the value to `embed.ts`'s instead.
- *A test of `timeout: false`.* Only a deadline past 300 s would show it.
- *Aborting provider calls in flight on SIGTERM.* A call within its deadline can still outlast the 28 s drain and be cut off; the core server's drain is the same.
- *agent-memory-api's and readwise-capture's embedding fetches*, which also carry no deadline. They are HTTP handlers whose replies are not kept alive, so Bun resets a slow one at 8–12 s and the client does not wait.
