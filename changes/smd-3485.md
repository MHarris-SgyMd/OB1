## Changelog

Preflight's `re-embed pass` and `consolidate pass` rows no longer tell the operator to finish a pass by hand beside the sleep scheduler when a dead worker left expired leases on the scheduler's key. They read the key as the scheduler's, name the expired claims as its to reclaim when it next works the key — once re-embed runs again after a set-down, or once the followers beside it, which end it, stop — and give the `release_stale_leases` tool as the way to return them now. A consolidation key from an earlier prompt or decide version, which no worker runs any more, is said to be one, with nothing to do. Before, the rows fell back to "Finish it", a second worker beside the scheduler that nothing refused, since a one-shot run writes no heartbeat (SMD-3485).

## FORK

Preflight credits the sleep scheduler with a key that holds a dead worker's expired leases, which its next sleep reclaims (SMD-3485)

**What changed.** `server-portable/preflight.ts`:
- **The `re-embed pass` row:** the scheduler's branch no longer needs `l.expired === 0`. Expired claims add a clause to its words, "N left by a worker that died, which the scheduler reclaims when it next works this key", with ", once re-embed runs again" when it is set down for the sleep, ", once the follower(s) beside it stop" beside any follower the scheduler refuses beside (`followersBeside`: the workers profile's, and a re-embed follower run by hand beside this version), which ends it at its next poll, or both. They also make the row a warning whose fix ends with `reclaim(key)`: the next pass reclaims them, and `release_stale_leases` returns them now. The set-down's remedy, the failed rows' and the followers' come first, since the reclaim waits on them. A key the scheduler has set aside, or one whose record differs, keeps the record's own words, as before.
- **The `consolidate pass` row:** the same, for `sleeper = l.expired === 0 ? sleeping : undefined`, which SMD-1794's review pass 2 kept so that "a dead worker's leases keep their words". It now credits the scheduler only with the key it runs now (`consolidatePassKey`), with or without expired claims. The row's `ownKey` also matches an earlier prompt or decide version of this judge's key, which no worker runs any more (consolidate.ts has no `--job`). Such a key now reads "an earlier prompt or decide version's pool, which no worker runs any more: consolidate.ts and the sleep scheduler judge these thoughts under <the current key>, nothing here to finish or retry", ok, whether a scheduler runs here or not, its failed rows and expired claims included. Before, beside a fresh scheduler it read as the scheduler's; with an expired claim, or with no scheduler, it gave "Finish it", which runs the current key (beside the scheduler, where one ran) and never clears it. `ownKey` also holds for the current key whatever a model name holds: the parse split a `+` in a name wrongly. Its failed-last-pass branch carries the clause, and the reclaim after the cause; followers beside it as on the re-embed row.

**Why.** Held by SMD-2679 PR 4b-2's review: "a dead worker's expired leases still send the scheduler's key to Finish it". It arises when the scheduler's process is killed mid-pass (an OOM, a `podman kill`, a host reboot), or a hand follower on the key dies holding claims. The leases expire, `supervise` restarts the scheduler, and its row is fresh again. It reclaims them when it next works the key: `reembedBacklog` and sleep.ts's `poolOf` count an expired claim as work, so the pass starts — or a running consolidation pass's next poll — and `claim_thoughts` takes the row back. Review pass 1's run took 1 to 10 s once the next sleep began.
