## Changelog

The agent-memory plugin's write-back names each memory whose capture made no vector, and why: the egress policy kept the text in (`refused`, which no retry changes) or the embedding provider did not answer (`provider_down`), as the core's capture tells the two apart (SMD-3984).

## Record

The agent-memory write-back says when the egress policy kept a memory's text in (SMD-3984)

SMD-3984 found the old `agent-memory-api` server embedding every recall query and write-back memory through OpenRouter with its own key, outside the egress gate. SMD-2690 PR 2a (OB1 PR 708) replaced the server with the `agent-memory` plugin, which embeds only through the core (check 31 refuses `fetch` in plugin code), so the defect went by construction, but for one Verify item: a write-back under `deny` kept its memories without vectors and said nothing of it, so a runtime could not tell the gate's refusal, which no retry changes, from a provider that did not answer.

**What changed.** `plugins/agent-memory/index.ts`'s write-back reads each capture's `embeddings.allowed` and `vectorFailed`, as `core/deliverables.ts` reads them for `noVector`, and answers `no_vector`: each memory whose capture in this request made no vector, with `why` (`refused` or `provider_down`) alone, for every key: the gate's words name the provider's host, which no door's value carries. It says what this request's capture did, not what the thought holds: a text already a thought keeps any vector it had, and a memory answered from its idempotency key (a write-back sent again) had no capture here and is not in it. Absent when every capture made its vector. The plugin's README and its metadata.json (2.1.0) say so.

**Held.** `server-portable/test-plugin-ports.ts`, agent-memory: the stub counts every embedding request. With a local embedder a write-back's thought carries the brain's `embedding_model` and no `no_vector`. Under `deny` with a remote provider, a write-back and a recall make none; the write-back keeps its memory without a vector and names it `refused`; the recall is refused `REFUSED_EGRESS`, final; a capture key is told `refused` too. Terms naming the keys let both through, the thought carrying the brain's model. While the provider is down, `no_vector` names the memory `provider_down`, and of a write-back's two memories it names the one whose embedding failed alone. The suite sets the policy on the servers' own environment, which root.ts freezes at the first request and the core reads at each call; its `finally` puts it back, and a leak would fail the sections after it. Mutants each fail the suite: no `no_vector`; a refusal read as the provider down, or the reverse; the provider down unsaid; a capture key told nothing; every memory named rather than matched by its thought. A `reason` put back is dropped by the operation's output schema, so no caller sees it.

**SMD-3984's other Verify items, already held:** the plugin names no provider URL, model or key, and check 31 refuses `fetch` and `process` in plugin code; a brain whose configured width differs from its recorded one is refused at start, and a model at the same width is preflight's warning (`server-portable/preflight.ts`), the REST core's image running preflight before it serves.
