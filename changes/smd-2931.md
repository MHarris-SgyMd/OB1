## FORK

sse.ts's comment says what Bun's idle timeout closes (SMD-2931)

**What changed.**
- **`server-portable/sse.ts`'s header**, and its byte copy `extensions/_shared/sse.ts`, held by `bun run sync-sse` and extensions/test-auth. The comment said the timeout "never reaches into a handler that has not yet returned a response" and "stays at the runtime's default", so raising it to 255 s "would move the cliff". Both claims were wrong:
  - on 1.4.3 the default cuts a pending GET too;
  - the REST core and the MCP server have both served with `IDLE_TIMEOUT_S = 255` since SMD-2287 PR 3a, for that GET.
  The comment now gives the measurement, and says the keepalive stays on the brain's streams for the proxy and for a call past 255 s. The vendored MCP servers stay on the default: a tool call of theirs is a POST answered with a stream at once, which the keepalive holds. Its note on the SDK's own 15 s keepalive names the MCP server's transport, where it has lived since SMD-2287, not the core's.
- **`SSE_KEEPALIVE_MAX_MS`'s docblock** names the timeout that takes over past the ceiling: 255 s on the REST core's streams, 10 on the vendored servers'. The MCP server's stream is the exception. Its SDK v2 transport writes its own frame every 15 s with no ceiling, so at 255 s that stream is never reaped. It ends with the call instead, since the call's request to the REST core is bounded at the same ten minutes (`REST_TIMEOUT_MS`). The README's keepalive caveat says the same.
- **server-portable/README.md's keepalive caveat** no longer says the idle timeout stays at the runtime's default. **test-server [17]'s premise comment** says a pending POST is left alone, not any pending handler.

No code or assertion changed.

**Why.** SMD-2931 was filed when `server-portable/index.ts` still served on the default, so its GETs could reset on a slow store. SMD-2287 PR 6b retired index.ts, and test-rest [16] already measures the cut. What was left was a comment that would mislead the next person tuning the timeout.

**Measured locally**, Bun 1.4.3 on macOS, each case silent for 14 s:

| | default | 255 |
|---|---|---|
| GET, handler pending | ECONNRESET at 12.0 s | 200 at 14.0 s |
| POST, handler pending | 200 at 14.0 s | 200 at 14.0 s |
| SSE stream, silent | ECONNRESET at 12.0 s | 200 at 14.0 s |

**Checked and not exposed:** the operator GUI (`dashboard/serve.ts`) sets no idle timeout, and its server-rendered GETs wait up to 30 s on the REST core. It serves on adapter-node's `node:http` server, which answered a 14-second GET with a 200 at 14.0 s.

**Follow-ups.** SMD-3308: agent-memory-api, the one vendored server with GETs that wait on the store, serves on the default, so a read held past about 10 s is reset.
