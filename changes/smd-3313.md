## Changelog

The session-capture hook delivers each summary to every brain its config lists (`"brains": [{"name", "url", "key"|"key_file"}, …]`), each with its own capture key, its own queue and its own supersedes chain. A brain that does not answer waits in its own queue and delays no other. The one-brain config works as before. **Upgrading:** nothing for one brain. To add a canary, mint a capture key on it, then move the config to a `brains` list with the current brain first, so it keeps its state (SMD-3313).

## FORK

The session-capture hook delivers to every brain it is given (SMD-3313)

**What changed.** In `recipes/session-capture-hook/session-capture.mjs`:
- **`loadBrains()`** reads the config's one-brain shape, or a `brains` list.
  - Each list entry has a name of lower-case letters, digits and hyphens, given once, and its own url and its own `key` or `key_file`.
  - A top-level `url`/`key`/`key_file` beside the list is refused, since which brain it meant is no answer.
  - `OB1_BRAIN_URL` in the environment is one brain, over the list, as it was over the file's url.
  - The first brain's state root is the one a one-brain config uses (`STATE_BASE`, today's `STATE_DIR`), so a move to a list keeps its chains. Each brain after it gets `STATE_BASE/brains/<name>/`.
  - `loadConfig(name?)` is one brain's settings. The model-summary settings are shared.
- **`STATE_DIR`** is now settable (`useStateRoot`), and every queue, chain and log helper reads it when called. So each brain has its own `pending`/`inflight`/`dead` queues, its own chain per session (the id an episode supersedes is that brain's), its own claim window and its own log.
- **The hook** runs `prepare` and posts once per brain, each in a child of its own. With several brains the child is given `--brain <name>`, and every line is led by the brain's name. The exit is the worst brain's.
- **`--post --brain <name>`** drains that brain's queue by hand. With no `--brain`, it drains the first brain's.
- **`--check`** checks each brain, naming it, and exits with the worst brain's code.
- **Provenance:** `derived_from` is sent to every brain as is. The ids are those the session read, from whichever brain served them. For a capture key, the server keeps the ids it holds and drops the rest (`liveSubset`, `core/writes.ts`), so a canary keeps those copied to it and the capture lands. This settles the ticket's provenance question without code.
- README "Several brains" and `--check`'s several-brain lines; metadata version 1.5.0.

**Why.** The canary is its own deployment, fed the same inputs as stable from the sources themselves (SMD-2872, SMD-2541's decision of 2026-10-25). Since its last refresh on 2026-10-13, stable has taken 307 session-hook captures and the canary none.

**Held.** `test-session-capture.mjs` [11], 22 assertions, against the fake endpoint and a second fake brain with ids and a capture key of its own:
- the config: two brains on their roots, key_file read, a refusal for each malformed list (with no key quoted), `OB1_BRAIN_URL` over the list, and `loadConfig` of a missing name;
- the hook in sync: each brain captured under its own key on its own chain, and the next ending superseding each brain's own id;
- the canary away: stable's capture lands and exit is 1. The canary's payload waits in its own queue, `--post --brain canary` lands it once the canary answers, and stable sees no duplicate;
- detached: each brain's child posts to its own brain;
- `--check`: each brain named with its own state, and a brain away fails it while the other still says ok.

The 703 existing assertions pass unchanged (the one-brain path). Five mutants, each dropping one mechanism, were all killed:
- one state root for every brain (9 failures);
- the hook running the first brain alone (8);
- the detached child not told its brain (1);
- `--post` ignoring `--brain` (3);
- `--check` checking the first brain alone (2).
