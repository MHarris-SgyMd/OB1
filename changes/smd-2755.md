## Changelog

A plugin's webhook can now refuse a replayed delivery. The plugin SDK's `verifyTimestamped` checks an HMAC over the time and the body (Slack's `v0:` form, a plain `<timestamp>.<body>`, and others through a small options object) and refuses a timestamp more than five minutes from the server's clock, so a recorded delivery verifies for five minutes rather than forever. The example plugin's `capture` webhook now signs that way: `x-example-timestamp` beside `x-example-signature`, the HMAC of `<timestamp>.<body>`. A sender that signs the body alone, as the example's did before, is refused `401 BAD_SIGNATURE` until it signs the time too. A delivery carrying an `id` is captured once: a resend is answered with the first thought and runs nothing, in a new table of the example's own, `plugin_example.deliveries` (its `migrations/002_deliveries.sql`, applied by the migrator while the example is enabled) (SMD-2755).

## FORK

A plugin's webhook refuses replays: a timestamped signature, and a delivery's id run once (SMD-2755)

**What changed.**
- `server-portable/plugin-sdk.ts` gains `verifyTimestamped(request, secret, scheme, now?)` and its types, `TimestampedScheme` and `TimestampVerdict`.
  - It checks the hex HMAC-SHA256 of `<prefix><timestamp><separator>` and the body's bytes against `signatureHeader`, after `signaturePrefix`, in constant time.
  - It refuses a timestamp that is not Unix seconds (`NO_TIMESTAMP`), a signature that does not match (`BAD_SIGNATURE`), and a signed one more than `toleranceSeconds` (300 by default) from the clock either way (`STALE_DELIVERY`).
  - The signature is checked before the time, so only a delivery the secret's holder signed is told it is stale. A tolerance that is no positive number is thrown, the plugin's fault.
- `plugins/example/`:
  - `capture` verifies with it (`x-example-timestamp`, `x-example-signature` over `<timestamp>.<body>`) and answers its code as 401.
  - It takes an optional `id`, 1 to 200 characters, else `400 BAD_ID`. It claims the id in a short transaction of its own, after pruning ids older than eleven minutes (twice the tolerance and a minute's margin). A resend of a captured id is `200 { id, duplicate: true }` and runs nothing; one whose first is still running is `409 IN_FLIGHT`, retryable. A capture the core refuses, or one that throws, gives the claim back so the sender's retry runs. A claim left unfinished past a three-minute lease (a server that stopped mid-capture) is taken by the next retry. The capture is recorded by an upsert, so one that outlived the prune is still recorded, and a record that fails is still the sender's 202.
  - The core's refusal keeps its `retryable`: a retryable one is `503`, the rest `422`.
  - `migrations/002_deliveries.sql` makes `deliveries (id, thought_id, claimed_at)`. The claim is not held across the capture's model calls, which would hold one of the plugin's two pooled connections for as long. The ids are in a table rather than process memory, which a restart empties and each replica keeps apart.
- `plugins/README.md`'s webhooks section gains "Replays": a webhook signs the time and remembers ids, and how. The example's README carries the new `openssl` recipe, the answers and a `STALE_DELIVERY` troubleshooting entry. `deploy/README.md`'s "Keys and secrets" says a handler refuses a stale delivery.
- The window bounds a replay of the same bytes. A sender's retry signed afresh with the same id is told apart only inside it, which the docs say, with what a sender that signs no time (Telegram) needs instead, and that a sender wanting an answer in seconds (Slack) counts a 409 as a failure.
- CI's webhook step signs each delivery with its time. Through the proxy, a delivery signed ten minutes ago is `401 STALE_DELIVERY`, and the captured delivery resent with its id is `200`, the same thought, marked a duplicate.

**Why.** Found closing SMD-2310: the SDK offered `hmacSha256Hex` and `safeEqual` alone, and the example signed the body alone. A recorded delivery verified forever, and each resend ran capture's embedder, metadata extraction and genre classifier before landing on the existing row, which `recapture: "keep"` left as it was. No data changed, but the model spend was a stranger's to trigger without a key, and nothing at the proxy limits deliveries.
