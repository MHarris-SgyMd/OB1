## Changelog

`brain_info`, a read-scoped MCP tool, and `GET /health` with a read or write key answer what a brain is — version and release range, the commit the image was built from, store, tier, Postgres and pgvector versions, schema version, the ledger's highest migration against the server's own, row counts, size, HNSW parameters; preflight's version, ledger and pgvector rows read the same facts, and `initialize` reports the fork's version instead of `1.0.0` (SMD-2041).

## FORK

A brain says what it is at runtime — `brain_info`, a keyed `/health` body, and preflight reading the same facts (SMD-2041)

**What changed.** `server-portable/brain-info.ts` holds one read.
`readDatabaseFacts` runs one transaction on one connection: the statement and
lock timeouts set once as ceilings (a stricter role keeps its own), one catalog
statement — `server_version`, pgvector's version and schema, which tables
resolve for this role (`to_regclass`) and which exist anywhere (`pg_class`; the
ledger only with migrate.ts's `sha256` column), every HNSW index on the search
path with its `m` and `ef_construction` — then each read a role or a lock can
refuse in a savepoint of its own: `ob1_config`'s schema version and embedding
contract, the ledger's names, the four row counts, the database's size. An
unread fact carries its reason — `refused` (42501), `timeout` (57014, 55P03),
`deadline`, `invisible` (it exists where this role cannot resolve it — never
"no table", so preflight never answers it with `--baseline`), `error` — and a
value whose savepoint failed after it was written is taken back. Facts are
written into a progress record as they arrive, so a caller's deadline keeps
what was read and names the rest; an abandoned read starts nothing more; a
failure after the catalog answered keeps the facts too. `brainInfo()` sets the
server's own facts beside them — the version, the release range `releases.json`
records for it and the migrations this tree adds past it (`unreleased`), the
tree's last migration, the commit (`OB1_GIT_SHA`), the store, `OB1_TIER`, the
configured embedding — and judges the ledger `current`, `behind` or `ahead`: the
ledger's highest number against the tree's last, and no more (a skipped,
renumbered or edited file is `migrate.ts --dry-run`'s; SMD-2069).
`ThoughtStore.databaseFacts()` is the SQL store's pool running the read; the
PostgREST store (Workers) has no catalog reads and says so.

Two surfaces, one function. The `brain_info` tool (`tools.ts`, read scope,
`readOnlyHint`) renders a short table, its read capped at 5 s per statement, 1 s
per lock wait and 15 s in all. `GET /health` with a read or write key answers the
record as JSON within 2.5 s (`HEALTH_DEADLINE_MS`; statements 800 ms, lock waits
300 ms); no key, a wrong key, a capture-only key, a revoked one — or a registry
that has not answered by the deadline, since it could still say revoked — gets
the literal `ok`, and a keyless probe never dials the database. A `HEAD` is the
bodiless `ok` and reads nothing. The status is 200 either way. Concurrent
callers share one read per surface, and requests of one key share one
agent-registry lookup (`AgentResolver`, for the MCP route too) — on the SQL store
only: on Workers a fetch belongs to the request that started it.

Preflight's `vector extension` row now names pgvector's version, and its
`migration ledger` and `schema version` rows read `readDatabaseFacts` (without
the counts and size) in place of their own reads — the ledger set every
ledger-aware remedy consults comes from it too — so the gate and the tool cannot
report two databases. The ledger row judges the highest migration against the
tree: behind warns with the migrate command, ahead that a newer tree migrated
the brain, a timed-out ledger could-not-verify, an invisible one where it is. In
a checkout a `version module` row holds `version.ts` to `db/migrations/`.

The version module. `db/version.mjs` is node-only and the Workers build bundles
the server; a Worker has no filesystem and the image has no `db/migrations/`.
`scripts/gen-version.ts` writes `server-portable/version.ts` — `FORK_VERSION`,
`RELEASE_RANGE`, `LATEST_MIGRATION`, no imports — and check-fork-consistency's
**17e** round-trips it; `assemble-release --write` regenerates it, and
`CONTRIBUTING.md` says a new migration reruns it. The MCP `initialize` reply read
a literal `1.0.0` that never moved through `1.1.0`; it reads `FORK_VERSION`.

The commit. `server-portable/Dockerfile` takes `OB1_GIT_SHA` as a build arg into
the environment, after every `COPY`; compose passes it to the four server builds,
the release job the tagged commit, CI the commit it built. Check 14 excuses it
from the runtime forward. `deploy/smoke.sh`'s check 10 reads the keyed body
without following redirects (curl forwards a custom header to the next host);
with `OB1_SMOKE_COMMIT` set (CI) it asserts the commit, and the version and the
tree's last migration against the checkout's — otherwise it prints them, since a
pinned deployment is smoked from any checkout.

**Why.** An agent or operator connected to a brain could not ask it what it was.
Preflight read the version, the ledger and pgvector once at container start;
`thought_stats` counted thoughts; `/health` said `ok`. Nothing read the commit,
Postgres's version, the database's size, the audit count, the tier or the HNSW
parameters, so "is the dogfood brain on 052 yet?" was answered by a scratch
script over the compose network after SMD-1296 landed, and a resuming agent
could not tell which server it was talking to — `initialize` said `1.0.0` to a
`1.1.0` server.
