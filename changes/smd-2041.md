## Changelog

`brain_info`, a read-scoped MCP tool, and `GET /health` with a read or write key answer what a brain is — version and release range, the commit the image was built from, store, tier, Postgres and pgvector versions, schema version, the ledger's highest migration against the server's own, row counts, size, HNSW parameters; preflight's version, ledger and pgvector rows read the same facts, and `initialize` reports the fork's version instead of `1.0.0` (SMD-2041).

## FORK

A brain says what it is at runtime — `brain_info`, a keyed `/health` body, and preflight reading the same facts (SMD-2041)

**What changed.** `server-portable/brain-info.ts` holds one read.
`readDatabaseFacts(sql)` asks the database, each fact its own statement so a
refused read (named in `unread`) leaves the rest: `server_version`, pgvector's
`extversion` and schema, `ob1_config`'s `schema_version`, `embedding_model` and
`embedding_dim`, the ledger (visible, readable, every name, the highest prefix),
the rows in `thoughts`, `thought_audit`, `thought_chunks` and `ob1_entities`,
`pg_database_size(current_database())`, and every HNSW index on the search path
with its `m` and `ef_construction` (pgvector's defaults when built with none).
`brainInfo()` sets the server's own facts beside it — the version, the release
range `releases.json` records for it, the tree's last migration, the commit
(`OB1_GIT_SHA`, `unknown` when unset), the store, `OB1_TIER`, the configured
embedding model and width — and judges the ledger `current`, `behind` or `ahead`
of the tree; it never raises (a database that cannot answer is `database.error`).
`ThoughtStore.databaseFacts()` is the SQL store's pool running the read; the
PostgREST store refuses, since PostgREST exposes no catalog reads.

Two surfaces, one function. The `brain_info` tool (`tools.ts`, read scope,
`readOnlyHint`) renders a short table. `GET /health` with a read or write key
answers the record as JSON; no key, a wrong key, a capture-only key and a key
revoked in the registry all still get the literal `ok`, so nothing about the
deployment reaches an unauthenticated probe, and a keyless probe never dials the
database. The status is 200 either way — the process is serving. The answer is
bounded: each read runs in its own transaction under a 2 s `statement_timeout`
and a 1 s `lock_timeout` (a read that runs out is `unread`), the registry check
and the read race one 2.5 s deadline (`HEALTH_DEADLINE_MS`; the tool's is 15 s),
and a keyed `HEAD` is the bodiless `ok` and reads nothing. The ledger is found by
`to_regclass('schema_migrations')`, as every other table is: the
`information_schema.tables` read preflight used lists only tables the role holds
a privilege on, and matched the name in any schema.

Preflight's `vector extension` row now names pgvector's version, and its
`migration ledger` and `schema version` rows read `readDatabaseFacts` in place of
their own reads (the ledger set every ledger-aware remedy consults comes from it
too), so the gate and the tool cannot report two databases. The ledger row judges
the highest migration against the tree the server was built from: behind warns
with the migrate command, ahead warns that a newer tree migrated the brain.

The version module. `db/version.mjs` is node-only and the Workers build bundles
the server, and neither a Worker nor the image holds `releases.json`'s ranges or
`db/migrations/`. `scripts/gen-version.ts` writes `server-portable/version.ts` —
`FORK_VERSION`, `RELEASE_RANGE`, `LATEST_MIGRATION`, no imports — and
check-fork-consistency's **17e** round-trips it; `assemble-release --write`
regenerates it after writing `releases.json`, and `CONTRIBUTING.md` says a new
migration reruns it. The MCP `initialize` reply read a literal `1.0.0` that
predated the version scheme and never moved through `1.1.0`; it reads
`FORK_VERSION`.

The commit. `server-portable/Dockerfile` takes `OB1_GIT_SHA` as a build arg into
the environment, after every `COPY`. Compose passes it to the server and the
three tier servers; the release job passes the tag's commit to both server
builds; the CI stack writes it into `deploy/.env`. Check 14 excuses it from the
runtime forward (`NOT_FORWARDED`): a forward would let `.env` name a commit the
image was not built from. `deploy/smoke.sh`'s check 10 reads the keyed body
without following redirects (curl forwards a custom header to the next host),
prints the version, commit and highest migration, and asserts the version equals
the checkout's `version.ts` and, with `OB1_SMOKE_COMMIT` set (CI sets it), the
commit.

**Why.** An agent or operator connected to a brain could not ask it what it was.
Preflight read the version, the ledger and pgvector once at container start;
`thought_stats` counted thoughts; `/health` said `ok`. Nothing read the commit,
Postgres's version, the database's size, the audit count, the tier or the HNSW
parameters, so "is the dogfood brain on 052 yet?" was answered by a scratch
script over the compose network after SMD-1296 landed, and a resuming agent
could not tell which server it was talking to — `initialize` said `1.0.0` to a
`1.1.0` server.
