## Changelog

The session hook (1.10.2) reads the tickets an ask names with the ask's secrets blanked, so a ticket-shaped value a secret holds, such as `password=ABC-1234`, no longer reaches the brain in a summary's header, where the brain keyed it as the session's subject, or in an episode's "begun with" and "ended when … was taken up" lines (SMD-4292). Such a value also no longer begins an episode or decides where a session splits.

## Record

An ask's tickets are read with its secrets blanked, so a ticket-shaped secret heads no summary and begins no episode (SMD-4292)

**Problem.** The capture hook blanks secrets in a session's prompts before it renders the summary (SMD-2127, `redactEpisode`). The tickets an ask names were read from the raw ask, before any blanking: `apply` filled the episode's `named` from them, and the segmenter read them to decide where an episode ends and what began the next. So a ticket-shaped value inside a secret (`set password=ABC-1234 and go`) was blanked in the listed prompt but:
- headed the summary (`headerTickets` lists `named`), the payload saying `tickets_from: asks`, and the brain's subject rule keyed it as one of the session's subjects (found by SMD-3306 PR 7a-3b-2's review pass 4);
- began a new episode, whose summary said "begun with ABC-1234", while the episode before said "ended when ABC-1234 was taken up" (found by this change's own end-to-end case, after a first fix that filtered `named` in `redactEpisode` alone left it there).

The rendered text's second scan cannot see it: a ticket-shaped word alone matches no secret pattern. A short password typed in that shape was stored in clear text in a thought every reader of the brain can find.

**Change** (`recipes/session-capture-hook/session-capture.mjs`, 1.10.2).
- **`askTickets`**, beside `ticketsIn`, reads an ask's tickets from the ask with `redactSecrets` applied. Both readers of an ask's tickets go through it: `apply` (the session's rollup and each episode's `named`) and the segmenter's boundary check. So nothing downstream sees a ticket a secret held: the header, `tickets_from`, an episode's `about`, its boundaries, the begun and ended lines, and the dry run's line per episode.
- **Every mode.** Under `refuse` the session is not sent, so where its episodes split matters to nothing sent; the ticket's Work had limited the fix to `redact`, but one rule is simpler than two.
- **Its cost.** The scan runs once per ask, cached per event, since three readers see each ask, and only for an ask with a ticket-shaped word, since blanking only takes words away. On 3,000 asks of 2 KB each naming a ticket, the worst case, a summary took 39 ms before and 128 ms now.
- The README's secret-scan paragraph and `metadata.json` (1.10.2) say so.

**Held.** The hook's suite:
- **Segmenter cases:** a password `ABC-1234` with no team known, and `smd-4321` on an `smd-610` branch, are in no `named`, head no summary (the second falls to the place's SMD-610) and are in no text. A second ask holding the secret splits no episode. A ticket named outside the secret in the same ask stays on the header, from the asks.
- **Through `prepare`:** a transcript whose ask sets a ticket-shaped password. The value is in no field of the payload, the prompt shows `[redacted:password assignment]`, one redaction is counted, and the payload has no `tickets_from`.
- **`--dry-run`** on a two-episode transcript whose first ask holds the password: the episode lines say "no ticket", and the output carries the value nowhere.
- **Mutants,** each failing a case:
  - the asks read raw;
  - `apply` alone reading them raw;
  - the segmenter alone reading them raw;
  - the fast path inverted;
  - one cached text shared by every ask.
