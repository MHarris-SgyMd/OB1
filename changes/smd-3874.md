## Changelog

The session hook's claims hook also runs on Claude Code's PostToolUseFailure, where a refused MCP call arrives, so the agent's own refused `renew_claim` or `claim_work` marks a `WORK_CLAIMED` and records a `CLAIM_UNATTRIBUTED`'s lapse again; re-paste the claims hook (SMD-3874).

## Record

The claims hook takes PostToolUseFailure — the agent's own refused claim calls reach it in Claude Code (SMD-3874)

**Probed.** One headless Claude Code session on the canary, with only a logging hook on PostToolUse and PostToolUseFailure, made two calls. The payloads, tokens masked:
- `list_claims`, a success: `PostToolUse`, with `tool_response` the reply's text as a string (`{"claims":[],"truncated":false}`), and no structured content.
- `renew_claim` with an id no claim has, a refusal: `PostToolUseFailure`, with `error` the reply's text whole (`Refused: no claim 00000000-0000-4000-8000-000000003874.`), `is_interrupt: false`, `tool_input` with the token, and no `tool_response`.

So in Claude Code every refusal of the agent's own claim calls reached the hook's PostToolUseFailure, which the claims hook did not take. The `WORK_CLAIMED` marker from SMD-3602 and SMD-3807's `CLAIM_UNATTRIBUTED` lapse never came from the agent's call; only the hook's own renewal marked the claim. No hook is handed the reply's structured content: the words are what a Claude Code hook reads.

**What changed.** In `recipes/session-capture-hook/session-capture.mjs` (1.7.3):
- `claimsHookJson`, which `--print-hook claude-code --claims` prints, adds a `PostToolUseFailure` entry on every tool, async and running `--claims` as the others do.
- `noteAgentClaimCall` takes PostToolUseFailure as well as PostToolUse, and reads the reply's text from `error` there. Its paths read words already: `WORK_CLAIMED` writes the `.blocked.json`, a `CLAIM_UNATTRIBUTED` with the claim's lapse records it and the same run checks the claims made since.
- Any tool's failure renews what is due, as a success does.
- The docblocks say what the probe found.

The README's "The agent's own claim calls" and the claims hook's paste instructions say so, and say to paste the claims hook again: one pasted before 1.7.3 takes PostToolUse alone.

**Why.** Found by SMD-3807's review pass 1. Claude Code's hooks reference says PostToolUseFailure runs when "an MCP tool returned an error result", and the probe confirmed it.

**Held.** test-session-capture passes (962 assertions). The new rows in [13] send a PostToolUseFailure shaped as the probe's:
- `renew_claim` refused `WORK_CLAIMED`: a `.blocked.json`, read off `error`;
- `claim_work` refused `CLAIM_UNATTRIBUTED` with the claim's lapse: the lapse recorded, and the same run marks the claim made since, the registry still away;
- a claim call's failure that is no refusal (a transport fault): nothing marked or recorded;
- another tool's failure: what is due is renewed.

`--print-hook --claims`'s row holds the new entry.

**Verified in a real session.** One headless Claude Code session on the canary, in a scratch worktree, with this branch's hook as the claims hook on PostToolUse and PostToolUseFailure:
- The agent claimed SMD-3874 piece `verify-piece` for 60 seconds, let it lapse, and covered it with a whole-ticket claim of its own key.
- It wrote the piece's token file, with the hook's state saying the claim wasn't due, so the hook's own renewal could not be what marked it.
- It then renewed the piece itself, and was refused `WORK_CLAIMED`.

The refusal reached the hook as PostToolUseFailure, with no `tool_response`. The hook wrote `<id>.blocked.json`, code `WORK_CLAIMED`, with no token in it. Its one log line was the agent-call path's: "the agent's own renew_claim met WORK_CLAIMED". Both claims were released after.

**Mutants:** three run, all killed: the failure event ignored, `error` not read, and the entry not printed.
