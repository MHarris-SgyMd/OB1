## Changelog

A supersession proposal's review can take one consolidation pass at a time: `list_supersession_proposals` (and `GET /v1/proposals`) takes `judge_key`, the pass key each proposal names — its model, or under decide mode the decider and the writer, with the prompt and decide versions — selected before the 200-row cap, and each proposal's value now carries `judgeKey`; `consolidate.ts --list <status> --key <judge key>` lists one pass's proposals, and `--list relations --key` its relations (SMD-3248, migration 109).

## FORK

One pass's proposals, selected by the key each names — the listing takes `p_judge_key`, and the value carries the key (SMD-3248)

**What changed** (migration 109).
- **`list_supersession_proposals(p_status, p_limit, p_lineage, p_judge_key)`**, redefined on 070's body: the same columns, joins, order (`confidence DESC, judged_at, id`), cap and lineage selector, plus a trailing `p_judge_key text DEFAULT NULL` and the term `(p_judge_key IS NULL OR p.judge_key = p_judge_key)`. Exact match, before the order and the cap, so a page of N holds N of that pass; NULL every pass. 070's three-argument form is dropped first (another argument list is another function), and 029's two-argument one with it if a hand re-apply left it standing. A call of two or three arguments — a server or CLI from before 109, mid-upgrade — resolves to the new form through the default and lists as before. The sentinel `ob1:listing-selects-a-pass` joins 070's `ob1:listing-flags-the-lineage-pair`, which stays in the body. Refuses by name without 016, 025 or 029; a re-apply is a no-op; DDL alone, no grant carried (EXECUTE is PUBLIC).
- **Four arguments, always,** in every fork caller: the store, `consolidate.ts`. 029 or 070 re-applied by hand lands its form beside 109's, and a call short of four is then ambiguous (42725, not unique) and fails — 070's rule, one argument on.
- **The tool and the REST core** take `judge_key` (1–200 characters) and echo it in the value; the reply's headline names it ("N pending supersession proposal(s) judged by <key>", and "No … judged by <key>." when none). The REST core already answered each row's `judgeKey` (it sends the store's whole value); the MCP reply's value now carries it too.
- **`judgeKey` in the value is held to a pass key's shape** — `consolidate:<model>[+<writer>]@p<N>[d<N>]`, a model name in letters, digits and `. _ : / -`, at most 120 characters each — a rule of `render.ts`'s guard beside the list cursor's. The guard turns any other free string in a value to null, so a raw recording's key of another shape (a sentence, another prefix, a third model) reads null there and stays in the text, where every reply quotes it through `snipText`.
- **`consolidate.ts --list <status> --key <judge key>`** and **`--list relations --key <judge key>`** (the relation facet's `payload->>'judge_key'`); the header names the key. `--key` without `--list`, or past 200 characters, is refused before the client (SMD-2015's rule: a flag that would be dropped without a word is refused).
- **Preflight's `lineage` check** reads 109's four-argument form and both sentinels, and names 109 where the listing is older (a brain at 108 or before: every listing fails, the callers passing the fourth argument) or where an older form stands beside it. `--status`'s lineage clause and `--list`'s missing-form message name 109; the tool's error hint names 109 beside 029.

**Why.** Every proposal names the pass that judged it in `judge_key` (029, NOT NULL), and the key carries the pass's whole version: `consolidate:h2o-lightning-4b+qwen3.8:27b@p4d3` is decide mode's verdict from H2O-Lightning-4B, the 27B's proposal, prompt 4, decide version 3. 070's listing read the key but could not select on it, and caps a page at 200 with no cursor, so a reader filtering afterwards lost every row past the cap. The canary on 2026-10-23 held 337 pending proposals — 242 under `@p4d1`, 94 under `@p4d3`, 1 under the 7B's `@p4` — and its upgrade past 38aad32e starts a fourth set, `@p4d4` (SMD-3203). SMD-3115's review grades one decide version's precision at a time, and brain_info's "337 pending" hid that it was three passes. Of the ticket's claim that the REST answer lacked the key: it did not — only the MCP value did.

**Not taken.**
- *Paging.* The order is `confidence DESC, judged_at, id`, so a cursor carries a numeric's exact text and a microsecond time through four doors — not cheap here. The key filter comes before the cap, and a pending queue drains as it is reviewed, which covers reviewing one pass: SMD-3249.
- *A prefix or pattern match* (all of a decider's passes): an exact key is what each row prints, and a `LIKE` would need escaping rules at every door.
- *An index on `judge_key`.* The term reads the rows of the status the listing already scans — hundreds on the dogfood brains.
- *Lifting `judgeKey` out of the guard.* The key is written by whoever records a proposal; the pass key's shape is what the value can promise.
