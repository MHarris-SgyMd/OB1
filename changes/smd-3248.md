## Changelog

A supersession proposal's review can take one consolidation pass at a time. `list_supersession_proposals` (and `GET /v1/proposals`) takes `judge_key`, the pass key each proposal names — its model, or under decide mode the decider and the writer, with the prompt and decide versions — selected before the 200-row cap, and each proposal's value now carries `judgeKey`. `consolidate.ts --status` counts the pending proposals by pass; `--list <status> --key <judge key>` lists one pass's proposals, and `--list relations --key` its relations. A server or CLI from before this release reads a brain at 109 as missing migration 070: upgrade it, do not re-apply 070 (SMD-3248, migration 109).

## FORK

One pass's proposals, selected by the key each names — the listing takes `p_judge_key`, and the value carries the key (SMD-3248)

**What changed** (migration 109).
- **`list_supersession_proposals(p_status, p_limit, p_lineage, p_judge_key)`**, redefined on 070's body: the same columns, joins, order (`confidence DESC, judged_at, id`), cap and lineage selector, plus a trailing `p_judge_key text DEFAULT NULL` and the term `(p_judge_key IS NULL OR p.judge_key = p_judge_key)`. Exact match, before the order and the cap, so a page of N holds N of that pass; NULL every pass. 070's three-argument form is dropped first (another argument list is another function), and 029's two-argument one with it if a hand re-apply left it standing. A call of two or three arguments — a server or CLI from before 109, mid-upgrade — resolves to the new form through the default and lists as before. The sentinel `ob1:listing-selects-a-pass` joins 070's `ob1:listing-flags-the-lineage-pair`, which stays in the body. Refuses by name without 016, 025 or 029; a re-apply is a no-op; DDL alone, no grant carried (EXECUTE is PUBLIC).
- **Four arguments, always,** in every fork caller: the store, `consolidate.ts`, `evals/eval-consolidate.ts`. 029 or 070 re-applied by hand lands its form beside 109's, and a call both forms take — under three arguments beside 029's, under four beside 070's (measured) — is then ambiguous (42725, not unique) and fails: 070's rule, one argument on.
- **An older server or CLI on a brain at 109** lists through its three-argument call, but its preflight and `--status` probe 070's signature, which 109 drops, so they read the listing as from before 070 and name 070's file. The fix is this tree's server, never that remedy: 070 re-applied stands its form beside 109's and makes the older server's own calls ambiguous. The window is a migrate ahead of its server; a release's `up` migrates and starts the server from one tree.
- **One rule for a key, `server-portable/pass-key.ts`**, read by every door: a selection takes 1–200 of a pass key's own characters (letters, digits, `. _ : / @ + -`) — no space, no control character, none a shell reads, so a key offered for pasting runs nothing; the value's guard holds a key to a pass key's whole shape; and a line of text shows a recorded key whole when a selection can take it, else quoted after `snipText`, so a key with spaces cannot pass for the line's own words.
- **The tool and the REST core** take `judge_key` (PASS_KEY_CHARS; in a query string `+` goes as `%2B`, said in the refusal) and echo it in the value; the reply's headline names it ("N pending supersession proposal(s) judged by <key>"), and an empty selection says the match is exact and where each key is printed, not "run the pass", which no run fills for an older pass's key. The REST core already answered each row's `judgeKey` (it sends the store's whole value); the MCP reply's value now carries it too.
- **`judgeKey` in the value is held to a pass key's shape** — `consolidate:<model>[+<writer>]@p<N>[d<N>]`, a model name in letters, digits and `. _ : / @ -` (Cloudflare's `@cf/…`), at most 120 characters each and 200 in all — a rule of `render.ts`'s guard beside the list cursor's. The guard turns any other free string in a value to null, so a raw recording's key of another shape (a sentence, another prefix, a third model) reads null there and stays in the text. The text quotes every key through `snipText`, the one cleaner, in the tool's reply and in `--list` and `--status` (before this change the row line printed it raw: a recorded key holding a newline forged an `ID:` line).
- **`consolidate.ts --status`** adds `pending by pass: N judged by <key>, …`, most first — the keys `--key` takes. **`--list <status> --key <judge key>`** and **`--list relations --key <judge key>`** (the relation facet's `payload->>'judge_key'`); the header names the key; a capped page says what to do next (`capNote`: a pending page drains as it is decided, any other selection waits for SMD-3249's paging); `--status` names ten passes at most, the rest counted, and marks (and quotes) a recorded key `--key` cannot take; and `ANOTHER JUDGE KEY` is left off once the pass is chosen. `--key` without `--list`, past 200 characters, or with a space or control character is refused before the client (SMD-2015's rule: a flag that would be dropped without a word is refused).
- **Preflight's `lineage` check** reads 109's four-argument form and both sentinels, and names 109 where the listing is older (a brain at 108 or before: every listing fails, the callers passing the fourth argument) or where an older form stands beside it. `--status`'s lineage clause and `--list`'s missing-form message name 109; the tool's error hint names 109 beside 029.

**Why.** Every proposal names the pass that judged it in `judge_key` (029, NOT NULL), and the key carries the pass's whole version: `consolidate:h2o-lightning-4b+qwen3.8:27b@p4d3` is decide mode's verdict from H2O-Lightning-4B, the 27B's proposal, prompt 4, decide version 3. 070's listing read the key but could not select on it, and caps a page at 200 with no cursor, so a reader filtering afterwards lost every row past the cap. The canary on 2026-10-23 held 337 pending proposals — 242 under `@p4d1`, 94 under `@p4d3`, 1 under the 7B's `@p4` — and its upgrade past 38aad32e starts a fourth set, `@p4d4` (SMD-3203). SMD-3115's review grades one decide version's precision at a time, and brain_info's "337 pending" hid that it was three passes. Of the ticket's claim that the REST answer lacked the key: it did not — only the MCP value did.

**Not taken.**
- *Paging.* The order is `confidence DESC, judged_at, id`, so a cursor carries a numeric's exact text and a microsecond time through four doors — not cheap here. The key filter comes before the cap, and a pending queue drains as it is reviewed, which covers reviewing one pass: SMD-3249.
- *A prefix or pattern match* (all of a decider's passes): an exact key is what each row prints, and a `LIKE` would need escaping rules at every door.
- *An index on `judge_key`.* The term reads the rows of the status the listing already scans — hundreds on the dogfood brains.
- *Lifting `judgeKey` out of the guard.* The key is written by whoever records a proposal; the pass key's shape is what the value can promise.
- *A per-pass count in brain_info and keyed `/health`.* `--status` is where a reviewer starts; brain_info's queue line stays one total.
- *Narrowing the value's guard further.* It admits a key shaped like a URL in the model's place (`consolidate:https://x/approve@p1`): still one token with no space, which is what the value promises.
- *Zero-width characters in `snipText`'s drop list.* A key ending in U+200B reads as the real one in the text; the class is older than this change and reaches thought text too: SMD-3282.
- *A capped-page note in the tool's reply.* The tool never said a page was capped, before this change too; it goes with SMD-3249's cursor.
