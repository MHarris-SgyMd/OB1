## Changelog

`deploy/canary.sh up` stands a canary brain beside a running stack in one command, and re-running it brings the canary level with stable again. It runs `deploy/compose.yaml` again as the project `open-brain-canary`, with its own Postgres, volume, network and images. The server is built from the checkout and listens on `127.0.0.1:8011` with `OB1_TIER=canary`. `up` stamps an untiered stable `tier=stable`, refreshes the canary from it through `deploy/tier.sh`, and runs a smoke test that includes the vector arm. `--connect` registers the Claude Code connector. `down [--volumes]` removes that project alone and deregisters the connector (SMD-2038). `tier.ts --refresh` now copies the source's database-level settings, which the dump leaves out, onto the target. That includes migration 014's HNSW bounds, so a refreshed brain no longer walks at pgvector's defaults (SMD-2037).

## FORK

`deploy/canary.sh` stands a canary beside a running stack and takes it down again; a refresh copies the source's database settings (SMD-2038 / 2037)

**What changed.**
- `deploy/canary.sh up`:
  - runs `compose -p open-brain-canary --env-file <stack's> -f deploy/compose.yaml`, with `SERVER_PORT` (default 8011), `OB1_TIER=canary`, an empty `COMPOSE_PROFILES` and the checkout's `OB1_GIT_SHA` set for those calls alone;
  - finds stable's Postgres by its compose labels, stamps it `tier=stable` when it has no stamp, and refuses one stamped `canary` or `working`;
  - refuses a port that a container of another project publishes;
  - starts the canary's Postgres and refreshes it through `tier.sh` on both projects' networks, by container name;
  - builds and recreates the server with `--no-deps`, then waits for `/health`.
- The smoke test, which needs `OB1_SMOKE_KEY` (`--no-smoke` skips it):
  - the keyed `/health` must say `tier: canary`;
  - `smoke.sh` must pass;
  - `list_thoughts` names one thought, and `search_thoughts` must find it by its own text with a similarity, which covers the vector arm.
- `up --connect` runs `claude mcp add --scope user open-brain-canary …` and discards its output, which echoes the key back.
- `down` deregisters the connector and runs `compose down --remove-orphans` on the canary project. The connector is only touched when `claude mcp get` shows it at the canary's own port, and only that `URL:` line is read, since `get` prints the key too. `up --connect` refuses to replace a connector of that name that points anywhere else. `--volumes` deletes the canary's database only once `ob1_config.tier`, or failing that the refresh mark, says `canary`.
- `deploy/tier.sh --network` takes `NAME,NAME`. It checks each network and passes one `--network` per name.
- `db/tier.ts` (SMD-2037):
  - `databaseSettings()` reads a database's own `setconfig` through `DB_LEVEL_SETTINGS_SQL`, without the mark, and checks each name.
  - `applyDatabaseSettings()` loads pgvector, resets each target setting the source lacks, and sets each source setting.
  - A list setting (`search_path` and pg_dump's other five) is written as SQL list syntax, element by element. Anything else is written as one literal.
  - `refresh()` reads the source's settings with its guards and applies them after the restore, before `migrate.ts`.
- The deploy-stack CI job:
  - compares the tier step's copy's settings with stable's (014's two bounds present);
  - adds a canary step: `up` twice, then `down --volumes`, checking the stamp, the probe thought on the canary, the vector search, and afterwards that stable's Postgres container, its thought and its server are unchanged;
  - extends the runner's provider stub to answer `POST /v1/embeddings` with the probe thought's vector.
- test-live [20] adds five cells (708): the source's settings read without its mark, the target's equal to the source's (a quoted list included), a stale target setting reset, each database keeping its own mark, and a new session on the target running at the source's HNSW bound.

**Why.** Standing the canary up on 2026-09-23 took about eight manual steps: a hand-built Postgres, a refresh run with a runtime `apk add`, the HNSW settings re-seeded by hand, a server env file copied from the running container's, `claude mcp add`. None of it was in the tree, so a second operator or a rebuild could not reproduce it. That standup's first attempt put the canary in a second database on stable's server. A canary exists to take the risky migration, reembed or index rebuild, and a shared server shares its memory, WAL and crash domain with the record, so each tier gets its own server. The refresh dropped 014's per-database HNSW bounds (pg_dump without `--create` carries no `ALTER DATABASE … SET`), and a refreshed brain answered broad filtered searches short until someone re-seeded them. Only the target's next preflight noticed, and only as a warning.

**Not taken.**
- A `deploy/compose.canary.yaml` overlay. Check 13 refuses `extends`, so the canary server's environment would have been a copy of `compose.yaml`'s, the drift this fork keeps finding. The same file under a second project name copies nothing.
- Attaching the canary's Postgres to stable's network instead. Compose aliases a service by its name on every network it joins, so a canary `postgres` there would answer to stable's name.
- Re-seeding the two HNSW settings in `canary.sh`. Every refresh loses them, so `refresh()` copies them, and whatever else the source sets.

**Measured.**
- On a throwaway stable stack on this Mac (docker CLI over podman 6, host Ollama), `up` took 12.7 s once the images were cached. The results:
  - smoke 10 of 10;
  - `search_thoughts` found the one captured thought by its text at 76%;
  - the canary's preflight reported `filtered search ✓ … walk bounded at 100000 tuples, memory x8` with no manual step (SMD-2037's Verify item);
  - its database settings equal stable's plus its own mark.
- Each refusal fired with exit 2 before anything changed:
  - a port held by the hand-built canary;
  - stable stamped canary, or carrying a mark;
  - `down --volumes` on a canary stamped and marked other than canary.
- `down --volumes` on a canary stamped `stable` but marked `canary` (a refresh that died after its restore) went through. Stable's container ids were the same before and after, its thought and `/health` too.
- The connector:
  - `up --connect` registered it and `claude mcp list` showed it `✔ Connected`;
  - `up --connect` refused a same-named connector at another URL, and `down` left that one registered.
- A replica of the deploy-stack job (the workflow's own stub on another port, and its tier and canary steps extracted from the YAML) passed. Stable's settings were `hnsw.max_scan_tuples=100000,hnsw.scan_mem_multiplier=8`, and so were the copy's.
- The dogfood's own canary, switched over from the hand-built one (2026-09-25; 677 thoughts):
  - one command, 13.7 s;
  - migration 054 applied to the canary, which stable does not yet have;
  - smoke 10 of 10, and the vector arm found a real thought;
  - `claude mcp list` showed `open-brain` and `open-brain-canary` both `✔ Connected`;
  - preflight clean but for the two warnings stable shares (unclassified audit rows, schema version);
  - thoughts, vectors and audit rows equal to stable's; the canary's query log is two ahead, its own smoke's searches;
  - a `--diff` found nothing moved;
  - a broad filtered `match_thoughts` (`type=task`, 500) returned 423 rows with the same ids on both (SMD-2037's third Verify item).

  Stable's containers ran on untouched throughout.
- Mutants, each caught:
  - no reset of a stale target setting (test-live, 2 cells);
  - a list setting written as one literal (1 cell);
  - the source's mark copied across (2 cells). The same mutant, live in the checkout while the CI replica ran, failed its tier step with "the refresh did not mark its target";
  - a stub that answers no embeddings (the canary step, "Embeddings request … failed: 404").
