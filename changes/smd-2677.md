## FORK

canary.sh reads a port's bound address from the binding's JSON, which both runtimes spell `HostIp`, so `--runtime podman` stands a path-mode canary (SMD-2677)

**What changed.**
- `deploy/canary.sh` gains `bound_ip`: the address a container's first published port is bound to, read from each binding's `json` and taken from its `"HostIp"` key with `sed`, with no new dependency. `host_of` maps its answer as before, and path mode's `STABLE_BOUND` is `bound_ip "$STABLE_PROXY"`. Both used to name the field `.HostIp` in an `inspect -f` template.
- `scripts/check-fork-consistency.ts` check 30: a Go template action anywhere in the tree that names `.HostIp` or `.HostIP` fails, with probes on both sides.

**Why.** A Go template's field is the runtime's Go struct field, not the JSON key. Docker's struct calls it `HostIp`, podman's (`define.InspectHostPort`) `HostIP`, and both runtimes' JSON spell it `HostIp`. Under the podman CLI the template failed. `STABLE_BOUND` is a plain assignment under `set -euo pipefail`, so path-mode `up` ended before changing anything, which is the mode SMD-2661 moves the dogfood canary to. `host_of` failed too, printing the error each time. Its path-mode call, a command substitution that does not inherit errexit, fell back to `127.0.0.1`, two lines before `STABLE_BOUND` ended the run. Its call in `canary_hosts`, read through a process substitution that does inherit errexit, died after loopback's three spellings. So a connector check matched loopback alone, never a stable proxy's LAN address. The docker CLI evaluates `.HostIp` even against podman machine, and `canary.sh` picks docker first, so only `--runtime podman` or a podman-only host saw it. CI runs docker, so check 30 holds what no job exercises.

**Held.**
- *Both CLIs, one helper.* Against created scratch containers, `bound_ip` and `host_of` read under podman 6.0.2 and the docker 29.8 CLI against podman machine (its compatibility API, not Docker Engine):
  - `127.0.0.1` → `127.0.0.1`;
  - `0.0.0.0` and no address → `0.0.0.0`, dialled at `127.0.0.1`;
  - `[::1]` → `::1`, dialled at `[::1]`;
  - a LAN address → that address;
  - no published port, and `--expose` alone → nothing, dialled at `127.0.0.1`;
  - two ports → the first binding, as before.

  Under the docker CLI each answer equals the old template's. Docker Engine keeps `""` for a binding given no address, which `bound_ip` prints as empty and `host_of` dials at `127.0.0.1`, as before. Under podman the old template errors on every bound case. An assignment from `bound_ip` under `set -euo pipefail` survives a container with no binding.
- *Path mode under podman, end to end.* A scratch stable (`smd2677-stable`, its proxy on 127.0.0.1:18770, routing `/canary/mcp`), and a copy of `canary.sh` whose project is renamed (`smd2677-canary`), so `open-brain-canary` was not touched (SMD-2537). `--runtime podman --stable-project smd2677-stable up` passed its pre-checks, refreshed, built and served at `http://127.0.0.1:18770/canary/mcp`; smoke 11/11.
- *Port mode's caller.* `canary_hosts`, the only caller of `host_of` in `--port` mode, run under podman against the scratch stable's proxy, prints `127.0.0.1 localhost [::1] 127.0.0.1` with no error. With the old `host_of` it prints the dogfood log's `can't evaluate field HostIp in type define.InspectHostPort`.
- *Mutant.* With `.HostIp` back in `bound_ip`, check 30 fails at `deploy/canary.sh:266`; the podman probes fail as above.

**Not taken.**
- *Ending the action at a newline.* An unclosed action opener could then no longer reach the field on a later line, but a template spanning lines would pass silently. Today's worst case is a loud false hit, which this paragraph's first draft met and a rewording answered (review pass 1).
- *Catching any case of the field name.* The names it would add, such as `.hostip`, are no field in either runtime and fail under both CLIs already (review pass 3).
- *`jq`.* `canary.sh` has no `jq` today; `sed` over one binding's JSON object does it.
- *A CI step that runs the helper through podman.* The runner's job runs docker; check 30 refuses the template field at the source, in every file, for less.
- *The "stable's proxy listens on …" note, run live under podman.* That needs a stable proxy bound past loopback, which would put a brain with the dogfood keys on the LAN. `STABLE_BOUND` is `bound_ip`, and `bound_ip` reads a LAN address under podman, measured above.

**Notes.** The end-to-end run met a podman machine fault outside the fork: on the maintainer's Mac, some freshly created compose networks had no host egress and did not forward their published ports, while long-lived networks did. The rehearsal reached the host's Ollama through a relay on a network that worked. Port mode's own proxy published a port that never forwarded, so the `--port` run was checked through `canary_hosts` above.
