## Changelog

A command run from `db/`, `server-portable/`, `rest-client/`, `mcp-server/`, `dashboard/`, `evals/`, `jev/`, `deploy/auth/`, `compat/supabase-sql/` or `dashboards/open-brain-dashboard/` no longer has Bun install a missing package at run time. Each directory has a `bunfig.toml` setting `[install] auto = "disable"`, as `extensions/` already did. A script whose packages its installs do not hold now fails at import, naming the package, instead of running on whatever npm serves; a suite that runs a child through `db/test-support.ts`'s `runScript` prints that line once. `test-live.ts` and `test-search-path.ts` need `bun install` in `server-portable/` as well as `db/`, since both run its preflight. Most of server-portable's suites need the `mcp-server/` and `rest-client/` installs, the MCP server and its suites `server-portable/`'s and `rest-client/`'s, and the REST client's generator and suite `server-portable/`'s, as their READMEs and FORK.md's rebase steps now say (SMD-2978).

## FORK

Bun's auto-install is off in every directory CI runs a script from, and db-live installs server-portable (SMD-2978)

**What changed.**
- **Ten `bunfig.toml` files**, one in each package directory a Fork Checks step runs a script from: `db/`, `server-portable/`, `rest-client/`, `mcp-server/`, `dashboard/`, `evals/`, `jev/`, `deploy/auth/`, `compat/supabase-sql/` and `dashboards/open-brain-dashboard/`. Each sets `[install] auto = "disable"`, as `extensions/bunfig.toml` has since SMD-1991. Bun reads the file in the working directory alone, not a parent's: measured on Bun 1.4.3, with the file in a parent, a script run from the child still fetched `zod`. So each directory needs its own. A script a suite spawns reads the file of the directory it runs from, which is how `server-portable/preflight.ts` is covered when `db/`'s suites run it.
- **db-live installs `server-portable/`**, a step after `db/`'s. test-live's [9], in the long cell, and `test-search-path.ts`, in the rest cell, run `server-portable/preflight.ts` from `server-portable/`, and preflight's imports reach `zod` through `core/plugins.ts`. The job installed `db/` alone, so Bun fetched `zod` at run time. With no egress, a run hung for over 30 minutes (SMD-3392's review pass 2). Every cell installs it, so a section moved between cells needs no change here.
- **Check 44** of `scripts/check-fork-consistency.ts` reads fork-checks.yml with check 34's reader, `scriptRunsIn`. Each directory a step may run a script from, its working-directory or a `cd` it names, that holds a `package.json` must have a `bunfig.toml` whose `[install] auto` is `"disable"`. Its probes pin which files turn it off: another mode, a commented-out line, the key outside `[install]` or under another table, a file that does not parse, and no file all fail. It fails loudly if its reading misses `db/`, `server-portable/` or `extensions/`. The header docblock and the workflow's comment name it among the checks that parse YAML.
- **`runScript` names a missing package** (`db/test-support.ts`). When a child's stderr carries Bun's `error: Cannot find package` (or `module`) line for a bare name, colour codes stripped, it prints that line once a run, with the script and the directory it ran from, and says to install the package the importing file belongs to. A missing relative file, which Bun also reports as `Cannot find module`, prints nothing. Its callers are in `db/`, `server-portable/` and `evals/`. A suite's assertions see only the exit code and what the output lacks, so without it a dropped install failed 17 of test-search-path's assertions, or 20 of the long cell's, and named nothing.
- **The READMEs:** db/README.md's prerequisite for `test-live.ts` names `server-portable/`'s install, and why. server-portable/README.md's Install step names the suites that also need `mcp-server/`'s and `rest-client/`'s installs (all but `test-rest`, `test-thoughts`, `test-jobs`, `test-store-sql` and `test-preflight`), and mcp-server/README.md's Run and Test sections `server-portable/`'s and `rest-client/`'s. rest-client/README.md's Regenerate step installs `server-portable/` first, and FORK.md's rebase steps install `rest-client/`, `mcp-server/`, `server-portable/` and `db/` first, in one loop, since server-portable's suites load the first two (the page stays under its 64 KiB cap). db/README.md's next prerequisite says `test-upgrade.ts` and the benches need no `server-portable` install. `extensions/bunfig.toml`'s comment names check 44.
- **fork-checks.yml, data-layer:** the comment on the REST client's and MCP server's installs said Bun would otherwise fetch their packages; it now says the imports would fail.

**Why.** The ticket: a CI step whose imports cross into a directory its job did not install still passed, with Bun auto-installing the packages from its cache or npm, unpinned. SMD-2287 PR 3b's review found it for `../mcp-server/stack.ts`, and SMD-3392's for preflight in db-live.

**Held.** On two copies of the tree with no `node_modules` (tracked and untracked files copied, the two committed `node_modules` links kept as links), Bun 1.4.3 on macOS:
- **The ticket's first Verify.** With `server-portable/` installed alone, `test-auth.ts` fails at import, `Cannot find package 'openapi-fetch' from '…/rest-client/index.ts'`. With `rest-client/` and `mcp-server/` installed too, it passes 191 of 191, and `test-client.ts` and `test-mcp.ts` pass. `test-rest.ts` (490 of 490), `test-thoughts.ts` and `test-jobs.ts` pass on `server-portable/`'s install alone, as CI runs them before the other two installs.
- **Preflight.** Run from `server-portable/` with no install, `preflight.ts` exits 1 at once: `Cannot find package 'zod' from '…/server-portable/core/plugins.ts'`. With the `bunfig.toml` moved aside, it loads `zod` from the cache and runs to its own report.
- **db-live's rest cell, without the new install:** with `db/` installed alone, `test-search-path.ts` fails 17 of its 35 assertions, its preflight cases, and `runScript` prints `!! preflight.ts, run from …/server-portable: error: Cannot find package 'zod' from '…/server-portable/core/plugins.ts'` once. With `server-portable/` installed too, it passes 35 of 35, and the long shard, [9] among its sections, passes 280 of 280, each on a throwaway Postgres 16 container.
- **replay-gate and db-schema,** with `db/` installed alone: each suite and self-check their steps run passes, among them `test-schema.ts` (3063), `test-connect.ts` (889), `test-engines.ts` (656) and `test-cli.ts` (461), which spawn every `db/` script.
- **portable-server's later steps,** each after the installs CI performs before it: the GUI's check and `test-oauth.ts`, `test-plugins.ts`, `test-server.ts`, `test-jev.ts`, the thirteen evals self-checks, orchestration's two, the authorization server's five and `extensions/test-auth.ts` all pass.

The typecheck and the consistency checker pass.

**Mutants** on check 44: each of the eleven `bunfig.toml` files removed in turn fails the check, naming that file, and `auto = "fallback"` in one fails it too. So the check reads exactly the eleven directories that have one.

**Not taken.**
- *A `bunfig.toml` at the repo root, or in `deploy/` or `deploy/orchestration/`.* changes/291 turned the root's down: it would reach every command run from the root, recipes with installs of their own included. None of the three holds a `package.json`, so check 44 does not read them, and auto-install stays on for what CI runs from them. Today that fetches nothing: their scripts' import graphs reach no package at run time (`test-parsers.ts`' import of `zod` through server-portable is type-only), and the reviewers ran them under `bun --no-install` from a tree with no installs. A package import added there later would be fetched unseen, which is this ticket's class left open.
- *A child spawned in a temporary directory.* test-live starts `db/tier.ts`, `db/weekly-digest.ts` and the recipe importers with `tmpdir()` or a scratch directory as their working directory, where no `bunfig.toml` is, so auto-install is on for them. Bundled with packages left external, none of their import graphs reaches a package today.
- *`scripts/`.* CI runs only `bunx tsc` from it. `bunx` ignores the setting: under it, `bunx --bun @commitlint/cli@19.6.1 --version` still fetched and ran.
- *`--no-install` on each step.* It would not reach the scripts a suite spawns, which run as plain `bun <file>` and read their own directory's `bunfig.toml`.
- *The images.* Their Dockerfiles copy named files, never a `bunfig.toml`, and compose already runs the `mcp` and `app` services under `bun --no-install`. The tier containers are the exception: `deploy/tier.sh` hands each half `git ls-files` of `db/`, `evals/`, `scripts/`, `server-portable/` and `plugins/`, now three `bunfig.toml` files among them, and `db/tier.Dockerfile` runs from `/repo/db` with no `node_modules`. Auto-install is off there now, and nothing they run needs it: `tier.ts`, `migrate.ts`, `connect.ts` and `brain-compare.ts` reach no package.
