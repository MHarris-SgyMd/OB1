## Changelog

A keyed, read-only `worker_status` MCP tool (and a matching keyed `GET /worker-status`) reports the background-work pools over `thought_work_claims` — per `work_type`: pending / claimed (in flight) / succeeded / failed counts, how many thoughts are unpooled, the corpus total, how many claimed leases are STALE (a dead worker's lease past its `ttl_expires_at`) with the oldest one's time and holder, and whether the pool is the brain's active one — so an operator or agent can ask a running brain about its queues without shelling into Postgres (SMD-2131).

## FORK

`worker_status` — a read surface for the extraction / consolidation / re-embed queues (SMD-2131)

**What changed.** Since SMD-1844 closed the host Postgres port, the only way to see
queue depth was `podman exec … psql` or a worker's `--status` from inside a
container. This surfaces the same truth over the read API, in the `brain_info`
mould (SMD-2041): a read of `thought_work_claims`, no write.

- **`worker_status`** (new read tool, `server-portable/index.ts`; scope `read` in
  `tools.ts`, so a capture-only key never sees it). No inputs; returns a JSON array,
  one row per `work_type`:
  `{workType, pending, claimed, succeeded, failed, unpooled, thoughts, stale, oldestStaleClaimedAt, staleWorkerId, active}`.
  - The four status counts and `thoughts`/`unpooled` reproduce
    `db/extract-entities.ts`'s `counts()`. A stale lease stays in `claimed` (the
    reaper is lazy — migration 015), exactly as the workers count it.
  - **`stale`** is the derived subset — `claimed AND ttl_expires_at < now()` — with
    the oldest lease's `claimed_at` and `worker_id`, so a dead worker's lease (the
    25h-lapsed 27B trial that motivated this) is flagged at a glance.
  - **`active`** is whether the pool is the brain's current one — the
    `ob1_config.entity_extraction_key` verbatim, or `reembed:<model>@<dim>` from the
    recorded embedding model/dim — so a superseded `@p1` pool reads `active: false`.
    consolidate records no active key, so its pools read `active: null` rather than a
    false negative.
- **`GET /worker-status`** — the REST mirror, the same authentication as `/health`
  (a read key gets the JSON, a capture/wrong/no/revoked key gets plain `ok`, `HEAD`
  gets `ok`). Kept OFF the `/health` BrainInfo body deliberately: this read is
  SQL-backend only and would otherwise couple a work-queue read into the health
  path's identity budget and its both-backend contract.
- **`ThoughtStore.workerStatus`** — SQL store: one `GROUP BY work_type` (the status
  counts + the stale subset + its oldest lease), a corpus count, and the `ob1_config`
  reads for `active`; `unpooled = corpus − pooled` (the PK is `(thought_id,
  work_type)`, so a work_type's rows are its pooled thoughts). PostgREST shim: throws
  "requires the SQL backend" — `thought_work_claims` is not published to PostgREST
  (migration 015), as `databaseFacts` throws for the catalog reads.

**Read-only.** No lock, no reaper, no `UPDATE` (contrast SMD-2090's write-on-read):
the tool reports the queue, it never touches it. Releasing a dead lease or draining a
queue is an action — SMD-2132, out of scope here.

**Not taken.**
- `unpooled`'s generic definition ("thoughts with no claim row for this work_type")
  matches extraction exactly; reembed and consolidate pool by model-aware rules
  (`poolable()` / `consolidation_pool()`) their workers own, so `unpooled` for those
  keys is the honest generic count, not their private pool size. The status counts,
  `stale` and `active` are exact for all three.
- Folding queue state into the `/health` BrainInfo body — see the REST-mirror note.

**Tested.**
- `server-portable/test-store-sql.ts` [5e]: exact per-work_type counts (2 pending, 2
  claimed = fresh + stale, 1 succeeded, 1 failed), `unpooled = corpus − 6`, the stale
  lease named to its dead worker with its `claimed_at`, and `active` true / false
  (superseded `@p1`) / null (consolidate).
- `server-portable/test-store-postgrest.ts` [8e]: the shim throws the SQL-only reason.
- `server-portable/test-e2e-sql.ts` [6d]: the tool over HTTP returns the array with
  the right shape, and the keyed `GET /worker-status` returns it while a no-key GET is
  plain `ok`.
- `server-portable/test-server.ts` / `test-auth.ts`: the manifest, `readOnlyHint` and
  capture-only invisibility, from `tools.ts`.
