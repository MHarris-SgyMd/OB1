## Changelog

The vector mender's page read and brain_info's count of thoughts waiting for a vector now go through an index that holds only those rows, so they no longer read every thought: migration 098 (SMD-3056). Both take well under a millisecond at 100,000 thoughts.

## FORK

The thoughts with no vector by an index of their own — the vector mender's page and the vectorless count stop reading every thought (SMD-3056)

**What changed** (migration 098).
- **`thoughts_vectorless_idx`**: a btree on `thoughts (id)`, partial on `embedding IS NULL`. It carries the page's order and its predicate together:
  - both of `store-sql.ts` `listVectorless`'s statements (no cursor, and `id > cursor`) read it from where they start and stop at the page;
  - brain_info's `vectorless` count, which keyed `/health` also reads, is an index-only scan of it.
- **Nothing else moves:**
  - No column of `thoughts` changes, and no grant (the readers' SELECT on `thoughts` covers the index).
  - No statement changes; only the two comments that said "a sequential scan" do.
- **The write cost:** the index holds only the rows waiting for a vector.
  - A capture with its vector never enters it. A mend writes a row version that leaves it.
  - It stays a page or two on a healthy brain.
  - HOT updates are unchanged: `embedding` was already an indexed column (the HNSW index's expression), and a column in an index's predicate counts the same.

**Why.** SMD-2889's mender reads a page of `embedding IS NULL` in id order on every tick, from each server, and nothing indexed that predicate. The cost grew with the thought count, not with the waiting rows:
- 0.9 ms over stable's 2,023 thoughts;
- 5.3 ms at 20,000 thoughts with every row vectored ("Rows Removed by Filter: 20000");
- 2–4 ms at 100,000, on the way to the 1B horizon (SMD-2754, SMD-2758).

Both servers pay it every tick, and each keyed `/health` call pays it again inside an 800 ms ceiling.

**Held.**
- **test-schema [88]:** the index's definition (`btree (id) WHERE (embedding IS NULL)`), its comment, and a re-apply that changes nothing.
- **test-store-sql [18]**, real Postgres, 1,000 vectored thoughts and 3 without:
  - the store's own two page statements and brain_info's count each add a scan to `thoughts_vectorless_idx` (read from `pg_stat_user_indexes` after a forced flush on the reads' one connection);
  - neither page adds a scan of `thoughts`.
  - Mutants: each statement's predicate as `embedding::text IS NULL` (the same rows, which the index's predicate no longer implies) fails it, and so does the index built without its WHERE. `IS NOT DISTINCT FROM NULL` is no such mutant: Postgres folds it to `IS NULL`, and the index still serves it.
- **test-upgrade:** the window guard (sixty-nine) and both enumerations name 098.

**Measured after.** EXPLAIN (ANALYZE), 100,000 thoughts, pgvector 0.8.6 on PG 16. The page queries are verbatim `listVectorless`, with its `origin` subquery; the cursor form is also run as a prepared statement under `plan_cache_mode = force_generic_plan`. Before 098 → after:

| Waiting | Page, no cursor | Page, cursor (literal / generic) | Count |
|---|---|---|---|
| 0 | 2.8 ms seq scan + sort → 0.016 ms | 2.8 / 2.8 ms seq scan → 0.006 / 0.005 ms | 3.2 ms seq scan → 0.004 ms index-only |
| 1% (984) | 0.14 ms pkey + filter → 0.017 ms | 0.11 / 0.11 ms → 0.025 / 0.036 ms | 3.1 ms → 0.071 ms |
| 10% (9,830) | 0.036 ms pkey + filter → 0.021 ms | 0.038 / 0.030 ms → 0.016 / 0.016 ms | 3.8 ms → 0.62 ms |

Every after-plan names `thoughts_vectorless_idx`.
- **The worst case before was a healthy brain:** no row waiting, and a full scan on every tick.
- **The pkey + filter plan at 1% and 10%** was cheap only because the waiting rows were spread evenly by id. The tail of a sweep, past the last waiting id, walked the rest of the key.
- **The count is now linear in the waiting rows**, not in every thought.

**Not taken.**
- **An index on `(created_at, id)`:** `listVectorless` pages by `id` alone, so `(id)` is the page's order.
- **`CREATE INDEX CONCURRENTLY` in the file:** the migrator applies each file in a transaction, which CONCURRENTLY refuses. 074's index has the same shape: a brain far past a few hundred thousand thoughts can build it by hand first, under this name, and the file then finds it.
- **A plan check in test-schema:** PGlite's planner on a few rows says nothing about a real brain's. test-store-sql [18] holds the store's own statements on a real Postgres instead.

**Upgrading.** Apply 098 (`bun migrate.ts`). It needs nothing past 001 and moves no row. While it builds, writes to `thoughts` wait: one read of every row, seconds at a few hundred thousand.

**Upstream status.** Fork-only: upstream has no vector mender.
