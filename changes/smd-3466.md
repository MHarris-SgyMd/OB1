## Changelog

Fork Checks' four stack jobs pull their stack's images while they build its server and migrate images, where `docker compose up --build` pulled first and built after; `.github/ci/full-stack-up.sh` then brings the stack up from what it built, with `--wait` as before (SMD-3466).

## FORK

The stack jobs pull beside the build (SMD-3466)

**What changed.**
- **`.github/ci/full-stack-up.sh`,** the bring-up all four stack jobs run ("Bring up the compose stack"), ends in four commands where it ran `docker compose up -d --build --wait --wait-timeout 240`:
  - `docker compose pull --quiet &`;
  - `docker compose build` in the foreground;
  - `wait` on the pull;
  - `docker compose up -d --no-build --wait --wait-timeout 240`.
- **What is pulled:** a plain `pull` skips the default services compose.yaml marks `pull_policy: never`: `api` and `migrate`, and `mcp` and `app`, which run `api`'s image. So it fetches `forwarder`, `postgres` and `proxy`, the three `up --build` pulled (review pass 2: the build listed them by a `compose config` query, on a wrong reading that a plain `pull` would ask the registry for `api`'s image).
- **Failures:** a failed pull fails the step at its `wait`, so after the build where it used to fail before it; a failed build fails it at once, and an `EXIT` trap, set only across the build, kills the pull still running.

**Why.** In this run of every stack job (PR 566's, 40806959046), the up pulled, then built, one after the other: pull 6.0–12.7 s (Full stack 6.0, brains 9.1, auth 8.7, observability 12.7), build 13.4–20.4 s, the up itself 4.6–6.8 s. Over main's runs since SMD-3310 retired the dashboards (run 40716009935 on), the bring-up's median is 36 s in Full stack; over the 26 main runs from 10-27, which include the ones before, it is 43 s. The ticket's "20 s pull" was the dashboards' background install competing for the network, which went with them. Brains and auth take 31 s and observability 47 s, medians over the same 25–26 runs from 10-27 (the dashboards' install was Full stack's alone).

**Held.**
- **On a real Docker daemon** (these runs are of the build's script, which listed the pulled services by a `compose config` query; review pass 2 records two of the plain pull's, 23.1 and 21.3 s, and pass 3 one more): `docker:28.0.4-dind` in podman, with compose v2.38.2 installed (the runners' Docker Engine 28 and compose 2.38), the worktree copied in without `.git`, `node_modules` or env files, each run on a fresh daemon so nothing was cached; the script ran as CI runs it (`GITHUB_ENV` set, its stub on the dind's own :11434, nothing published to this Mac).
  - main's script: 38.3, 30.3 and 25.9 s, its pull ending 11.6–23.5 s in, the build after it;
  - this branch's: 30.0, 20.3, 19.7 and 21.5 s, pull and build both starting 0.2–0.3 s after the script did (the rehearsal's key minting and stub start take less than CI's ~2.6 s) and ending within ~1 s of each other;
  - every run green: all six default services healthy, `api`, `mcp` and `app` on `open-brain-server`, the image the build made.
- **The control flow,** with a fake `docker` logging each call in a Linux container (rerun on the plain pull before pass 2's commit):
  - passing: the up runs only after the pull has ended;
  - the pull failing: rc 1 at the wait, no up;
  - the build failing: rc 1 in 1.1 s, and the pull is killed (it never logs its end).
- shellcheck (as CI's "shellcheck on .github/ci's scripts" runs it) and the checker pass.
- The jobs' own runs are not rehearsed here: they bring up the `open-brain` project on :8010, which on this Mac is the dogfood stack. This PR's CI run is the first.

**Not taken.** The ticket's second item, starting Full stack's dashboards' background install after the pull: SMD-3310 retired the dashboards, and the job runs no background install now.

**Verify** (the ticket's): over ten main runs, "Bring up the compose stack" drops by at least 10 s in Full stack and at least 5 s in brains and auth. The pull this overlaps is 6–13 s, so the drop can be at most that, and Full stack's bar was set against a 20 s pull the dashboards caused: from its post-SMD-3310 median of 36 s, a 10 s drop would need more than its 6 s pull. So Full stack's bar can't be met as written; it is the maintainer's to restate, against this PR's CI run, or to accept as missed.

**Tidied while the files were open.** The script's header said its step body was "moved verbatim", which stopped being true after SMD-3051; it now says SMD-3051 moved it there. The new comment drops its pull and build timings, which the next image change would make wrong (they are under Why), and reads as one paragraph.

## Review pass 1

A cold read and a run-it. The run-it ran the script on fresh `docker:28.0.4-dind` daemons with compose v2.38.2: four more passing runs (23.9–32.3 s; main's 32.8 s beside them), each with all six services healthy and no error, retry or layer conflict in its log, and the failure modes on a real daemon.

- **Fixed (run-it):** the comment said "The pull is quiet". Under v2.38 without a terminal, `--quiet` still prints each service's `Pulling` and `Pulled` lines; it keeps the progress out. The comment says so.
- **Fixed (cold read):** the `EXIT` trap stayed set across a failed `wait`, so it signalled a pid already reaped. It is now cleared before the `wait`, so it covers the build alone, the one place the pull can be left running.
- **Fixed (cold read, then checked here):** the claim that `pull` is refused named v5.6.1 and v2.39.1 but not the runners' v2.38.2. Under v2.38.2 the same toy project gives `mcp Error denied`. "The 26 runs to 10-29" now names its last run, and Full stack's 6 s pull is sourced (6.0 s in run 40806959046).
- **Held (run-it), on a real daemon:**
  - a missing image (`traefik:v0.0.0-…`): rc 1, the registry's `manifest unknown` shown despite `--quiet`, no up. It failed at the `wait`, after the build, 16.6 s in, where main's script fails before building. That is the cost of the overlap, and a pull failing is rare.
  - a failing build, with a ~400 MB image added to the pull: rc 1 in 6.0 s, no compose process left, and the daemon stopped pulling once the client was killed (`/var/lib/docker` flat over 30 s). A missing Dockerfile: rc 1 in 0.6 s, the pulls `Interrupted`.
  - a pull slower than the build (the same image added): the build ended at 19.0 s, the pull at 23.8 s, and the up began at 24.0 s.
  - the running `api`, `mcp` and `app` containers are on the image ID `build` produced, and a keyed `/health` answers `"commit"` with the `GITHUB_SHA` the script was given, so the build arg reaches the image through `deploy/.env` with `build` run on its own.
  - the jq's list under v2.38 is `forwarder postgres proxy`, exactly the services main's `up --build` printed `Pulling` for.
- **Recorded, not changed (cold read):** the Dockerfiles' `FROM oven/bun:1.4.3-alpine` is the image `forwarder` pulls by digest. Run side by side, BuildKit and the pull may both fetch its layers, which would take a little off the gain. This PR's CI run shows how much; pinning the FROMs to the digest would be a change of its own.

## Review pass 2

A cold read of the whole branch and a run-it on six fresh `docker:28.0.4-dind` daemons (compose v2.38.2), main and the branch alternating, counting the bytes each received.

- **Fixed (cold read):** the build's case for listing what to pull was wrong for the real compose.yaml. `api`, `migrate`, `mcp` and `app` are marked `pull_policy: never`, and `pull` skips such a service (compose v2.38.2's `pull.go`); the toy project the build and pass 1 used had no such line. A `--dry-run pull` of compose.yaml under v2.38.2 gives the four `Skipped` and the other three pulled. The `compose config` query, `mapfile` and empty-list guard are gone, and the script runs a plain `docker compose pull --quiet &`. Two fresh-daemon runs: green, 23.1 and 21.3 s, the log saying `api`, `app`, `mcp` and `migrate` `Skipped`. Pass 1's record of the query is left as it was.
- **Fixed (cold read):** two medians for one thing in Why now say which runs each covers; the rehearsal's 0.2–0.3 s now names its zero; and Verify says what follows from Full stack's bar being out of reach.
- **Held (run-it):** no double download of `oven/bun`. Each pair's bytes differed by 0.12–0.39 MB, where a second copy is 47.9 MB (its compressed arm64 size). BuildKit's `extracting` lines on the branch are its view of the daemon's one shared download, and the image store holds one copy (95.55 MB reported shared). Pinning the Dockerfiles' `FROM` to the digest changed nothing for the branch (it would save main ~0.8 s of metadata lookup).
- **Held (run-it):** the branch's median was 24.5 s against main's 31.7 s, by 7.2, 7.8 and 8.1 s a pair. Beside the build the pull is slower (13.8–16.2 s against 11.5–13.5 s), sharing the bandwidth with the build's installs, and in one run it finished after the build, so the step sometimes waits on it.

## Review pass 3

A cold read of the final branch and a run-it on fresh `docker:28.0.4-dind` daemons (compose v2.38.2).

Held's real-daemon runs now say they were of the build's script; the control-flow cases say they were rerun on the plain pull; brains' and auth's 31 s say which runs they cover; the record's one "my" is gone.
- **Held (run-it):** the committed script: rc 0 in 21.6 s, `api`, `app`, `mcp` and `migrate` `Skipped`, the other three pulled by 12.5 s inside a build ending at 16.9 s, every service healthy.
- **Held (run-it), what an edit to compose.yaml would do:** with `pull_policy: never` removed from `mcp`, the pull fails at once (`pull access denied for open-brain-server`) and the step at its `wait` (rc 1, no up). Removed from `api` or from `migrate`, compose prints a `Warning` for that service, pulls the rest, then exits 1 (`1 error occurred`), and the step fails the same way. None is silent; the comment now says a service without the line fails the step. `pull --ignore-buildable` would cover `api` and `migrate` without the line but not `mcp` or `app`, so the line stays the mechanism.
