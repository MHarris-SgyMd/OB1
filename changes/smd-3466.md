## Changelog

Fork Checks' four stack jobs pull their stack's images while they build its server and migrate images, where `docker compose up --build` pulled first and built after; `.github/ci/full-stack-up.sh` then brings the stack up from what it built, with `--wait` as before (SMD-3466).

## FORK

The stack jobs pull beside the build (SMD-3466)

**What changed.**
- **`.github/ci/full-stack-up.sh`,** the bring-up all four stack jobs run ("Bring up the compose stack"), ends in four commands where it ran `docker compose up -d --build --wait --wait-timeout 240`:
  - `docker compose pull --quiet <pulled services> &`;
  - `docker compose build` in the foreground;
  - `wait` on the pull;
  - `docker compose up -d --no-build --wait --wait-timeout 240`.
- **The pulled services** are read from `docker compose config --format json`: every service with no `build` whose image no service builds. Today that is `forwarder`, `postgres` and `proxy`, the three `up` itself pulled. `mcp` and `app` run `api`'s built image. `pull` asks the registry for it and is refused (`denied`) under compose v5.6.1, v2.39.1 and the runners' v2.38.2, even with `--ignore-buildable`, so a plain `pull` can't be used; `up` skips them because it knows `api` builds them. An empty list, or a `compose config` that fails, fails the step.
- **Failures:** a failed pull fails the step at its `wait`, so after the build where it used to fail before it; a failed build fails it at once, and an `EXIT` trap, set only across the build, kills the pull still running.

**Why.** In this run of every stack job (PR 566's, 40806959046), the up pulled, then built, one after the other: pull 6.0–12.7 s (Full stack 6.0, brains 9.1, auth 8.7, observability 12.7), build 13.4–20.4 s, the up itself 4.6–6.8 s. Since SMD-3310 retired the dashboards (from run 40716009935), the bring-up's median is 36 s in Full stack (43 s over the 26 main runs from 10-27 through 27db1e32's, and the ticket's "20 s pull" was the dashboards' background install competing for the network, which went with them) and 31 s in brains and auth, 47 s in observability.

**Held.**
- **On a real Docker daemon:** `docker:28.0.4-dind` in podman, with compose v2.38.2 installed (the runners' Docker Engine 28 and compose 2.38), the worktree copied in without `.git`, `node_modules` or env files, each run on a fresh daemon so nothing was cached. The script ran as CI runs it (`GITHUB_ENV` set, its stub on the dind's own :11434, nothing published to this Mac).
  - main's script: 38.3, 30.3 and 25.9 s, its pull ending 11.6–23.5 s in, the build after it;
  - this branch's: 30.0, 20.3, 19.7 and 21.5 s, pull and build both starting at 0.2–0.3 s and ending within ~1 s of each other;
  - every run green: all six default services healthy, `api`, `mcp` and `app` on `open-brain-server`, the image the build made.
- **The control flow,** with a fake `docker` logging each call in a Linux container:
  - passing: the up runs only after the pull has ended;
  - the pull failing: rc 1 at the wait, no up;
  - the build failing: rc 1 in 1.1 s, and the pull is killed (it never logs its end);
  - `compose config` naming nothing to pull, or failing: rc 1, said.
- **The list:** with `--profile auth` the same query gives `breakglass` beside the three, and not `auth`, which is built.
- shellcheck (as CI's "shellcheck on .github/ci's scripts" runs it) and the checker pass.
- The jobs' own runs are not rehearsed here: they bring up the `open-brain` project on :8010, which on this Mac is the dogfood stack. This PR's CI run is the first.

**Not taken.** The ticket's second item, starting Full stack's dashboards' background install after the pull: SMD-3310 retired the dashboards, and the job runs no background install now.

**Verify** (the ticket's): over ten main runs, "Bring up the compose stack" drops by at least 10 s in Full stack and at least 5 s in brains and auth. The pull this overlaps is 6–13 s, so the drop can be at most that, and Full stack's bar was set against a 20 s pull the dashboards caused: from its post-SMD-3310 median of 36 s, a 10 s drop would need more than its 6 s pull.

## Review pass 1

A cold read and a run-it. The run-it ran the script on fresh `docker:28.0.4-dind` daemons with compose v2.38.2: four more passing runs (23.9–32.3 s; main's 32.8 s beside them), each with all six services healthy and no error, retry or layer conflict in its log, and the failure modes on a real daemon.

- **Fixed (run-it):** the comment said "The pull is quiet". Under v2.38 without a terminal, `--quiet` still prints each service's `Pulling` and `Pulled` lines; it keeps the progress out. The comment says so.
- **Fixed (cold read):** the `EXIT` trap stayed set across a failed `wait`, so it signalled a pid already reaped. It is now cleared before the `wait`, so it covers the build alone, the one place the pull can be left running.
- **Fixed (cold read, then checked here):** the claim that `pull` is refused named v5.6.1 and v2.39.1 but not the runners' v2.38.2. Under v2.38.2 the same toy project gives `mcp Error denied`. "The 26 runs to 10-29" now names its last run, and Full stack's 6 s pull is sourced (6.0 s in run 40806959046).
- **Held (run-it), on a real daemon:**
  - a missing image (`traefik:v0.0.0-…`): rc 1, the registry's `manifest unknown` shown despite `--quiet`, no up. It failed at the `wait`, after the build, 16.6 s in, where main's script fails before building. That is the cost of the overlap, and a pull failing is rare.
  - a failing build, with a ~400 MB image added to the pull: rc 1 in 6.0 s, no compose process left, and the daemon stopped pulling once the client was killed (`/var/lib/docker` flat over 30 s). A missing Dockerfile: rc 1 in 0.6 s, the pulls `Interrupted`.
  - a pull slower than the build (the same image added): the build ended at 19.0 s, the pull at 23.8 s, and the up began at 24.0 s.
  - the running `api`, `mcp` and `app` containers are on the image ID `build` produced, and a keyed `/health` answers `"commit"` with the `GITHUB_SHA` the script was given, so the build arg reaches the image through `deploy/.env` with `build` run on its own.
  - the jq's list under v2.38 is `forwarder postgres proxy`, exactly the services main's `up --build` printed `Pulling` for.
- **Recorded, not changed (cold read):** the Dockerfiles' `FROM oven/bun:1.4.3-alpine` is the image `forwarder` pulls by digest. Run side by side, BuildKit and the pull may both fetch its layers, which would take a little off the gain. This PR's CI run shows how much; pinning the FROMs to the digest would be a change of its own.
