## Changelog

`migrate.ts --reapply` now passes on a brain that holds a judged relation, an own subject, a settled part, a literal search or a set of subjects. It failed at migration 064, 059 or 111 on any such brain, so the documented recovery path could not run on a brain that had consolidated (SMD-3149).

## Record

`--reapply` leaves a rule a later migration loosened to the file that decides it last (SMD-3149)

**What changed.**

- `db/config.mjs` gains `supersededStatements(files)`. It reads the migrations in order and finds, in each, a statement of the file's own that makes a rule a later file loosens:
  - `ALTER TABLE … ADD CONSTRAINT <c> CHECK (…) [NOT VALID]`, and `ALTER TABLE … VALIDATE CONSTRAINT <c>`, where a later file says `ADD CONSTRAINT <c>` anywhere outside a comment;
  - `CREATE UNIQUE INDEX <i> …`, where a later file's own statement is `DROP INDEX <i>`.

  It returns each such file's text with those statements blanked, newlines kept, and what was left to which file.
- `db/migrate.ts` runs that text under a live `--reapply`, and prints a line beside each file it left a statement out of. A plain run applies every file whole, as before.
- `db/test-upgrade.ts` gains section [24]. `db/README.md` §5 says what the re-run leaves out; three passages that said `--reapply` fails at 064 are corrected.

On main the rule strikes four files:

| File | Left out | Decided last by |
| --- | --- | --- |
| 059 | the ADD of `query_log_arm_check` | 106 |
| 064, 084, 111 | the ADD and VALIDATE of `derivations_artifact_kind_check` | 151 |
| 111 | the CREATE of `thought_facets_subject_active_uniq` | 130 |

**Why.** A re-run runs every file in order in one transaction. 064 adds the lineage kind CHECK with the six kinds it knew and validates it, so a row of a kind 084, 111 or 151 added later fails it. 059 does the same to the search arms 106 widened. 111 makes the unique index that held one standing subject a thought, which 130 replaced with one a thought and key, so a thought with a set of two fails its build. Released migrations are frozen, so the fix is the migrator's.

The index case is not in the ticket. It is the same shape, it sits behind 064 in the same re-run, and the ticket's Verify (a re-run over a copy of each brain) cannot pass without it on a brain that holds a set.

**Measured.** One scratch Postgres, every migration applied, one row planted a run:

| The brain holds | Main | This change |
| --- | --- | --- |
| no row of a later kind | exit 0 | exit 0 |
| a `relation` lineage row | exit 1 at 064 | exit 0 |
| a `subject` lineage row | exit 1 at 064 | exit 0 |
| a settled part | exit 1 at 064 | exit 0 |
| a `literal` search row | exit 1 at 059 | exit 0 |
| a thought with two standing subjects | not run on main: 064 fails first | exit 0 |

After the runs both CHECKs read as before them, validated, and of the two subject indexes 130's alone stands.

**Held.** Read narrowly, so nothing else is struck. Section [24] holds each: the one file that defines a constraint; a later file that names it only in a comment; an ADD inside a `DO` block; an ALTER with a second action; a foreign key; a unique index no later file drops, or one dropped only inside a block (120's guarded drop of 084's index, which 084's `IF NOT EXISTS` then leaves standing); an index that is not unique.

One mutant, the upgrade suite run once with it:

| Mutant | Result |
| --- | --- |
| The re-run runs each file whole (the blanked text not passed) | section [24] fails two rows: the re-run exits 1 at 059 on `query_log_arm_check`, and no file is said to be left out. 902 of 904 pass |

**Measured after.** The upgrade suite, 904 of 904.

**Not taken.**

- Putting the last definer's list into the earlier file's statement. On a brain behind this tree a later list could name what an earlier point of the re-run does not have yet. Leaving the statement out needs nothing of the kind: the file's drop still runs, and the last definer adds the constraint back in the same transaction.
- A new migration that replaces the list CHECK with something an earlier file's drop cannot match. It would mend this one constraint and leave the next widening to be mended again.
- Refusing up front. It would name the failure sooner and still leave no recovery path.

**Follow-ups.** The ticket's Verify asks for a re-run over a copy of stable and a copy of the canary. That needs a dump of each, which this session cannot take. Until it is run, what is shown is the planted rows above, not a real brain's.
