## Changelog

`db/rebuild.ts`, the operator's door to `rebuild_derived`, is now an importable engine: `run(opts)` runs it in-process and `sweepOrphans(sql, opts)` runs its orphan sweep on a caller's client. The CLI is unchanged (SMD-2679, the first of its PRs).

The sleep scheduler now runs each sleep under a budget (SMD-2679, its second PR). A sleep runs at most 60 minutes (`--budget`, `OB1_SLEEP_BUDGET`; 0 for no clock). Then its passes stop after the thought in hand, and the next sleep begins only after a live call. Each pass's connections open with `statement_timeout` 300 s, `work_mem` 4 MB and `maintenance_work_mem` 64 MB (`--statement-timeout`, `--work-mem`, `--maintenance-work-mem`, and their `OB1_SLEEP_*` settings). A statement past its timeout stops the sleep; before, it ended the scheduler. The heartbeat and preflight's `sleep` row say which stopped a sleep, the budget in force, and how many sleeps stopped on it. **Behaviour change:** a long quiet night now holds the model for an hour, not until the queues drain.

Each sleep now begins with a re-derive pass (SMD-2679, its third PR): `rebuild_derived`'s orphan sweep deletes the lineage rows whose artifact is gone — up to 500 thoughts a sleep, no model — before extraction claims. The log says how many it swept. Re-embed's hard stop now aborts the embedding call in hand, so `db/reembed.ts`'s in-process `run()` — the sleep scheduler's, once re-embed joins sleep — returns at once rather than when that call does, up to `OB1_LLM_TIMEOUT` later; the CLI already exited on the release (SMD-2679, PR 4a-1). `db/reembed.ts --follow [SECONDS]` polls after its pass, pooling again at each poll, as the claim workers' followers do; a follower never switches the model — a configured model other than the one the brain records is refused as `model-switch` (SMD-2679, PR 4a-2a). A follower waits a database or provider outage out, and ends, refused `provider`, when the provider refuses the request itself (SMD-2679, PR 4a-2b). The sleep scheduler now re-embeds before it extracts, when the brain has vectors not at the configured embedding model; a brain with none starts no re-embed pass and calls no embedding endpoint. Whatever refuses re-embed sets it down for that sleep, and a brain recording another embedding model than the stack's sets it aside, each said in the log and on `heartbeat:sleep`, while extraction and consolidation run on (SMD-2679, PR 4b-1). **Behaviour changes:** a brain from before migration 021 has its unlabelled vectors re-embedded and labelled by its first sleeps, one embedding call a row, before extraction (`bun db/reembed.ts --dry-run` says how many), and so is a thought saved with no vector; `heartbeat:sleep` reads failed while re-embed is set aside or down for a cause the operator mends, and preflight says "its last pass failed"; a `reembed.ts --follow` run by hand keeps the scheduler from starting (2); a one-shot `sleep.ts` whose re-embed was set down or aside exits 1.

### PR 4a-2b: re-embed's follower waits outages out

**What changed.** `db/reembed.ts --follow` waits outages out as the claim workers' followers do (`worker-bootstrap.ts`). The database gone at the start's reads, the first pool or a poll is waited for and said; a thought in hand records nothing, its lease returned at the next poll; a stop meanwhile exits 0 at a poll (130 at the start), the counts unread. The provider not answering at the start is waited for after the start's other checks (the check says `out` without waiting; a model not served there is the start's `model`); mid-pass, it or the model not served sends the thought in hand back to the pool unrecorded, says `waitingMidPass: ["reembed"]` on the follower's own row (brain-info reads it there alone until sleep runs re-embed) and probes until it answers — under the outage thought's egress subject when the gate refuses the probe's own; a thought it fails again right after a probe answered is recorded failed, as its own, but never on a 429, a 503 or the model not served; a 400 about its length is the thought's, and so is any other 4xx, a body not of the shape or an error no rule knows when the probe's text then gets answered. An outage back within a minute of the probe answering, nothing re-embedded since, carries on the last one's schedule, so a rate limit no row gets past waits longer each time. Whose each error is, is one pure rule, `worker-bootstrap.ts`'s `followClassify`, at the claim, the write and the poll alike: the thought's only when it names the thought (its length, the egress gate, its data) or the probe's text is answered right after; else the database's state (a wait; a moment's, the thought back unrecorded; or the end — a privilege, a function gone, a statement timeout — the follower ended, its row failed) or the provider's (backpressure making no suspect, any other outage a suspect). `ProviderOutage.resumeFrom` holds the carried schedule. The live cases are `test-live.ts`'s own section, [9f], in the extract shard. The provider refusing the request itself (a key, a width) stops every worker, marks nothing failed and ends the follower refused `provider` (2). A moment's database state at a pool — a deadlock, a lock, resources, a read-only transaction, a thought deleted under its insert — costs that pool, the first's included (its record and `--retry-*` go with it); a privilege, a function gone or a statement past `statement_timeout` (which 4a-2a swallowed) ends the follower, its row failed.

### PR 2: the budget

**What changed.**
- **`db/connect.ts`:** `openSql(url, { max, session })`. `session` is Postgres settings every connection of the client opens with: Bun's `connection` startup parameters, so a connection the pool opens later carries them too (measured on Bun 1.4.3). It takes settings by name only: no `user`, `database`, `replication`, `options` or `password`, and no NUL. A transaction pooler (PgBouncer, a managed host's pooled endpoint) refuses startup parameters, so the scheduler connects to Postgres directly, as the compose stack does.
- **The engines** (`extract-entities.ts`, `consolidate.ts`): `run({ session })` applies them to the run's own client. Beside a caller's `sql`, which it would not reach, it is refused.
- **`db/sleep.ts`:**
  - **Four flags,** each run()'s option and each a compose setting:
    - `--budget MINUTES` (60; 0 none), `OB1_SLEEP_BUDGET`;
    - `--statement-timeout SECONDS` (300; 0 leaves the role's or the database's own), `OB1_SLEEP_STATEMENT_TIMEOUT`;
    - `--work-mem MB` (4), `OB1_SLEEP_WORK_MEM`;
    - `--maintenance-work-mem MB` (64), `OB1_SLEEP_MAINTENANCE_WORK_MEM`.

    The memory defaults are Postgres's own, so a server sized up for its awake index does not hand them to the background passes. These are stated defaults until SMD-1499 derives them.
  - **Where the settings apply.**
    - Every pass, and the start's check, run under them through `budgetSession()`.
    - A startup setting beats the role's and the database's own, so a timeout of 0 is left out.
    - The scheduler's own two connections take the memory settings and statement_timeout 0 (`schedulerSession()`), beating a role's or database's own. Its poll reads the pools, a scan of every thought, and a timeout there would end the scheduler. The clock is read between those reads, so a sleep can run one read past it.
  - **The clock.** Once spent, the passes stop after the thought in hand, every lease returned, and none starts. One still in hand 300 s later is stopped hard, a cut (101). A wake in that grace ends the sleep at once. The stop is counted and marked only when it cut work: either pool not drained as the drain reads it (consolidation's not yet enqueued included), or a pass waiting for its provider. An idle clock-out ends the sleep as quietly as a drained one, the next still after a live call, and one sleep's exits 0.

Before, the pass's rejection ended the scheduler with 1.

- **The row** (`db/pass-stamp.ts`, `server-portable/brain-info.ts`):
  - `slept.budget` (`clock` or `statement`) says which stopped the last sleep, and `slept.limit` the bound it stopped at (minutes, or seconds);
