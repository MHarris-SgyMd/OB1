## Changelog

The session capture hook lets a checkpoint's post land before the session's end posts, so the end supersedes the checkpoint instead of standing beside it (SMD-2035).

## FORK

A session's end waits for the checkpoint its child is still posting, and supersedes it (SMD-2035)

**What changed.** `recipes/session-capture-hook/session-capture.mjs`: before a
run posts a payload, `awaitPredecessors` looks under `inflight/<pid>/` for a
payload of the same session that another live child holds and that is older
than its own — a payload's name leads with the millisecond it was prepared, so
the names order them — and waits until that claim is gone: posted and
unlinked, failed and returned to `pending/`, or its child dead. Then the state
is read, and the pointer comes from there, as it did (seventh and eighth
passes of SMD-1298 decided the pointer at post time). Only the newer of two
waits, so two children never wait on each other; a child that is gone holds no
one; the wait is bounded by one request's timeout, `POST_TIMEOUT_MS` (90 s),
shared across the run's payloads so a run cannot outlive the fifteen-minute
claim sweep; the log says whom it waited on and for how long at most, and the
capture's `note=` says how long it waited and whether the wait ran out.
`sessionPayloads` now says which child holds each payload, and the request
timeout has a name.

**Why.** SMD-2012 put PreCompact beside SessionEnd on the default path, and
its second review pass (cold read) found the case SMD-1989's record had named
as a gap the server would arbitrate: `/compact` then `/exit`, or an automatic
compaction on the last turn. The compaction's child posts A (an embedding
takes seconds; a `derived_from` refusal adds a retry); the end prepares B
meanwhile, with `supersedes` from a state that does not yet name A; B's child
lands first and writes the state; A lands after it, sees the state newer and
leaves it — right for the state — but A is a live thought whose `Checkpoint:`
line says "continuing" of a session that has ended, with no successor, beside
the final summary. Two current summaries, one of them wrong about its own
state.

**Held.** `test-session-capture.mjs` (in CI's repo-consistency job), a
section of its own: a compaction's payload posted by a child against the fake
endpoint's 2.5 s answer, the session's end prepared while that claim stands
and posted in-process — the end waits, the checkpoint lands first, the end
second superseding the checkpoint's id, the state names the end's id, the
note and the log say so, `pending/` and `inflight/` empty. The rule alone,
against planted claims: a newer payload of the session, an older one of
another session and one under a dead pid hold nothing; an older one under a
live pid that never clears holds the run for the bound and the result says
the wait ran out; a spent budget does not wait. The run's shared budget across
several payloads is held by reading, not by a test — five children of one
session each holding an older payload is not a case a suite can stage in its
time.

**Not taken.** Treating a payload as obsolete because a newer one of its
session is in another child's hands: the wait alone orders both holdings —
when the children have each other's payload, the one with the older posts at
once and the one with the newer waits — and the obsolete rule as it stands
already drops the older on the next run once the newer's summary is in the
state. Waiting without a bound: a claim under a live pid that is not a hook
(a pid reused after a reboot) would hold the end for the fifteen minutes the
sweep takes. Server-side arbitration (the ticket's option 2): it needs a
session identity the server can see, which today is only in the content; it
pairs with the structured checkpoint field SMD-2013's design note should
settle. Waiting in `prepare`, in the foreground: the SessionEnd budget is 1.5 s.
