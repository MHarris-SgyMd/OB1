## Changelog

The session capture hook lets a checkpoint's post land before the session's end posts, so the end supersedes the checkpoint instead of standing beside it (SMD-2035).

## FORK

A session's end waits for the checkpoint its child is still posting, and supersedes it (SMD-2035)

**What changed.** `recipes/session-capture-hook/session-capture.mjs`: before a
run posts a payload, `awaitPredecessors` looks under `inflight/<pid>/` for a
payload of the same session that another live child holds and that is older
than its own — a payload's name leads with the millisecond it was prepared, so
the names order them — and waits until that claim is gone: posted and
unlinked, failed and returned to `pending/`, or its child dead. Then the state
is read, and the pointer is the session's newest landed thought by the time
its payload was prepared — `pointerFor`: what the state records, or a landed
payload whose bookkeeping is still owed under `pending/` (`landedBefore`
reads its `captured_id`), as the seventh and eighth passes of SMD-1298
decided the pointer at post time; the per-run map of what the run itself
landed was a third spelling of one of those two and goes. Only the newer of two waits, so
two children never wait on each other; a child that is gone holds no one; a
payload this run holds a newer sibling of, or that has landed, waits nothing;
the wait is bounded by one request's timeout, `POST_TIMEOUT_MS` (90 s),
shared across the run's payloads. A wait that runs out, or a run with no
budget left, does not post past the predecessor — that is the race itself,
back on the slow-server path that causes it — but defers the payload to
`pending/`, and the run that lands the predecessor follows up once with the
payloads of the sessions it landed, so the chain completes in that child;
failing that, the next hook run posts it. An older payload whose session
has a newer landed one owed its bookkeeping is obsolete though the state is
silent (`landedAfter`). The claim directory's mtime moves at every payload, so
the fifteen-minute sweep judges a run by its last step. The log says whom a
run waited on and for how long at most, and what it deferred and why; the
capture's `note=` says how long it waited. `sessionPayloads` now says which
child holds each payload, and the request timeout has a name.

**Why.** SMD-2012 put PreCompact beside SessionEnd on the default path, and
its second review pass (cold read) found the case SMD-1989's record had named
as a gap the server would arbitrate: `/compact` then `/exit`, or an automatic
compaction on the last turn. The compaction's child posts A (an embedding
takes seconds; a `derived_from` refusal adds a retry); the end prepares B
meanwhile, with `supersedes` from a state that does not yet name A; B's child
lands first and writes the state; A lands after it, sees the state newer and
leaves it — right for the state — but A is a live thought whose `Checkpoint:`
line says "continuing" of a session that has ended, with no successor, beside
the final summary. Two current summaries, one of them wrong about its own
state.

**Held.** `test-session-capture.mjs` (in CI's repo-consistency job), a
section of its own: a compaction's payload posted by a child against the fake
endpoint's 2.5 s answer, another session's slow payload behind it in the same
child, the session's end prepared while those claims stand and posted
in-process — the end waits, the checkpoint lands first, the end second
superseding the checkpoint's id while the child still lives (the claim
clearing releases it, not the child's exit), the state names the end's id,
the note and the log say so; a second end in the same run, left the
rest of a 3 s budget, is deferred and posted by the checkpoints' child once it
has landed, superseding it, `pending/` and `inflight/` empty. The
predecessor landing with its state write failing (the state path a
directory): the end supersedes the id read from the payload under `pending/`,
and the next run finishes both bookkeepings without posting. The pointer by
the rule alone, over planted owed payloads under `pending/` and a claim:
the newest by time between the state's thought and the owed payload, by
`summary_at` not `captured_at`, a future or garbage state time deciding
nothing, a payload without `prepared_at` ranked by its name's millisecond,
the newest owed one found whatever order the directories are read in. An
older checkpoint whose end has landed in another child's hands, owed its
bookkeeping, obsolete. One run over five payloads with a 300 ms budget
against never-clearing claims: the older sibling and the outdated one

deferred, the next session's deferred with the budget spent, a landed one
waiting nothing, one `waiting` line in the log, both deferred back under
`pending/`. The rule alone, against planted claims: a
newer payload of the session, an older one of another session, one under a
pid proven dead, one under `pending/` and one in the run's own hands hold
nothing; an older one under a live pid that never clears holds the run for
the bound; a spent budget neither waits nor logs, nor does a bound that is no number.

**Not taken.** Treating a payload as obsolete because a newer one of its
session is in another child's hands when that payload is not yet landed: the wait alone orders both holdings —
when the children have each other's payload, the one with the older posts at
once and the one with the newer waits — and the obsolete rule as it stands
already drops the older on the next run once the newer's summary is in the
state. Waiting without a bound: a claim under a live pid that is not a hook
(a pid reused after a reboot) would hold the end for the fifteen minutes the
sweep takes. Server-side arbitration (the ticket's option 2): it needs a
session identity the server can see, which today is only in the content; it
pairs with the structured checkpoint field SMD-2013's design note should
settle. Waiting in `prepare`, in the foreground: the SessionEnd budget is 1.5 s. A
per-session lock held through the state write (first review pass, for the
owed-bookkeeping case): reading the landed payload's own id is the smaller
fix. Posting past a predecessor when the wait runs out, as the first cut did
and the ticket allowed: the deferral costs the end's summary a delay of one
run and keeps one current thought, which is the ticket. Bounding a run's
requests as the wait is bounded: the claim's mtime moving per payload makes
the sweep judge progress instead.
