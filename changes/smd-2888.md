## Changelog

A capture made while the model provider is down (stopped, unreachable, timing out, or answering 5xx, 408 or 429) is now saved without its vector instead of failing with "Unable to connect" and being lost. The reply says the provider was unavailable, keyword search finds the thought at once, and the same text captured again once the provider answers takes its vector. An outage now records the tagging failure alone, with no placeholder topics or type, so re-capturing a thought during an outage no longer replaces its tags. A misconfigured provider (a 4xx, a vector of the wrong width) still fails the capture (SMD-2888).

## FORK

A capture survives its provider's outage — saved without its vector, said, and marked on the audit row (SMD-2888)

**What changed.**
- **`embed.ts` `providerDown(e)`:** one rule for "the provider did not answer". It covers:
  - a `ProviderError` timeout, or a 5xx, 408 or 429;
  - Bun's own fetch error for a refused, reset or unroutable connection, or a name that does not resolve. Bun 1.4.3 throws a `TypeError` with `code: "ECONNREFUSED"`, or `"ENOTFOUND"` with `syscall: "getaddrinfo"`.

  It is read by fields, never by message. Everything else returns null: an egress refusal, any other 4xx, a body that is not JSON, the width mismatch and any plain `Error`.
- **`embed.ts` `exchange`:** a body read that fails after a 2xx with an outage is rethrown as the runtime's own error. A provider that crashes mid-answer resets the socket (`ECONNRESET`, measured), which used to read as "a body that is not JSON" and fail the capture. Any other body fault (a corrupt gzip, a malformed chunk) is still the body that was not JSON. After an error status the status still stands, as before.
- **`core/writes.ts` `capture`:** the embedding call's failure goes through `providerDown`.
  - **An outage** lands the row as an egress-refused capture lands: text and fingerprint, no vector, no model label, no windows.
  - **Anything else** still fails the capture.
  - **The server log** says so when the capture's embedding call meets an outage, and when its tagging call meets one at the socket (a timeout or a status is logged by `extractMetadata`, as before).
  - **The audit row** carries the word as `actor_context.vector_failed` (`store.ts` `Actor.vectorFailed`, written by `actorPayload`), beside the gate's `egress` record. No migration: the trigger keeps every key it does not read by name.
- **The tags (`metadata.ts`, `core/writes.ts`):** an outage writes `metadataUnavailable(reason)`, the marker alone, with no topics and no type. That is what an egress refusal writes, and for the same reason: `upsert_thought` merges a write key's re-capture over the row, so placeholder tags would replace an existing thought's real ones.
  - `extractMetadata` returns it for a `ProviderError` outage (the deadline, 5xx, 408, 429), where it used to write `uncategorized`/`observation` placeholders. A 4xx, a body that is not JSON, or an answer with no content keeps the placeholders.
  - The runtime's own error (a refused connection) is still thrown by `extractMetadata`, so board-sync fails the item and retries it on its next pass, as before. The capture path catches it and writes the marker.
- **The reply (`render.ts`):** a note per what is known of the row.
  - A fresh row: "saved WITHOUT a vector — the embedding provider at <base> was unavailable (<detail>)", plus keyword search and the two ways to the vector.
  - A reader's re-capture: "it keeps the vector it had, if it had one". The egress note's same sentence gets the same clause.
  - A database that does not say, or a key that cannot read: both readings. A key that cannot read is told neither the endpoint nor the detail.
  - The marker alone gets its own tagging note: "no topics, people or type were extracted — the chat provider [at <base>] was unavailable (<word>)", or on a re-capture, that the existing thought keeps its tags.
  - Every note this change adds or touches names the endpoint to a reader only: the placeholder note's "Check the chat endpoint (<base>)", the situating-context note's "check the model at <base>", and the head-window note's provider error, whose words carry the base. With one provider for both calls, they would have told a capture key exactly what the vector note hides.
  - The typed result adds `vectorFailed` (the word).
- **REST (`rest/app.ts`, `rest/openapi.ts`, rest-client regenerated):**
  - `embeddingAttached` is false when `vectorFailed` is set;
  - a reader gets `vectorFailed` whole (word, words, endpoint), and a key that cannot read gets the word alone.
- **`update_thought` is unchanged:** an edit whose provider does not answer is refused whole. Nothing is lost, since the caller keeps its patch, and storing the new text would clear a vector the thought had.
- **Docs:**
  - server-portable/README.md: the two calls' failure paragraph covers both outage shapes, and that `vector_failed` says this write's call failed;
  - SETUP.md: the gate paragraph;
  - docs/01-getting-started.md: the "no vector" troubleshooting entry names the provider-down note.

**Why.** SMD-2887 measured it on 2026-10-11: with the provider's socket closed, `capture_thought` answered `isError` with Bun's "Unable to connect" and stored nothing. Only the session hook keeps a payload to retry. A connector, n8n or a script lost the thought. The dogfood stack's stable brain uses the host's Ollama, which no restart policy covers.

**Held.**
- The vector is attached later only by a re-capture of the same text (033/080's coalesce, now tested from a real failure) or a re-embed pass. Attaching it automatically is SMD-2889, which is to merge before the next release cut.
- **The session hook.** It used to keep a capture that failed in an outage under `pending/` and land it whole later. Now the capture succeeds, so the hook drops the payload, and the summary stays vectorless until SMD-2889. A hook re-send was weighed and not taken: a capture-only key cannot tell whether the thought still exists, so a re-send after a delete would re-create a summary that key cannot remove. Its tags stay the marker alone until a re-tag worker (SMD-2298).
- After the provider is back, a write key's re-capture merges the real tags and leaves the marker beside them. That is the stale marker README already describes.
- On long content, one window's failed call fails the whole embedding, so the row lands vectorless though the whole-content call may have answered. That is not new; it used to fail the capture.
- The egress notes still give a capture key the gate's reason, which names the host the text was not sent to, as before this change. Through REST direct, a capture key is told none of it.
- Semantic search with the provider down, starting degraded, and coded provider errors on the other tools are SMD-2887's other children.
