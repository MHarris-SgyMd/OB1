## Changelog

No service in `deploy/compose.yaml` or its overlays can now take the proxy's traffic by answering to a backend's mesh name, by joining stable's mesh under a second key, or by reaching into the proxy's namespaces. Nor can one publish on the proxy's host port. The fork's checks hold who joins each network under which names, what each overlay changes, the keys compose.yaml's services set and what they mount, each published port's knob and default, the settings `deploy/.env.example` leaves live, and compose.yaml's proxy as a whole. The compose files are unchanged but for comments. A local overlay kept in `deploy/` now fails `scripts/check-fork-consistency.ts` until it is declared there (SMD-2685).

## FORK

Only the proxy's backends answer it — no alias, second network key or shared namespace in compose.yaml or an overlay can take its traffic, and compose.yaml's proxy is held whole (SMD-2685)

**What changed.**
- **Check 28** (`scripts/check-fork-consistency.ts`) gains two rules and widens three, over the same files (every compose file directly in deploy/ but compose.tiers.yaml):
  - **`networks`:** each file defines exactly the networks `FILE_NETWORKS` holds, and each service joins exactly what `SERVICE_NETWORKS` holds, under the names held there. compose.yaml's proxy's are the `proxy` rule's. So only a backend answers to its own mesh name, and no second key joins a network the first already names. compose.yaml names the project `open-brain`, which prefixes every network.
  - **`keys`:** each file sets only what is held for it.
    - An overlay is an `OVERLAYS` entry and sets only the services and keys it declares there. compose.api-public.yaml sets the proxy's `configs`, `labels` and `depends_on`; compose.host-ports.yaml sets `ports` on postgres, ollama and jev; compose.canary.yaml sets `networks` on server and api. A file that is no entry fails.
    - compose.yaml's services set only `SERVICE_KEYS`, which act inside the service's own container. So no `pid`, `ipc`, `privileged`, `network_mode`, `volumes_from`, `container_name`, `hostname`, `env_file`, hook or other key until it is added there on purpose.
    - Each service's `cap_add`, `cap_drop`, `security_opt` and `read_only` are exactly as `CONFINEMENT` holds them: the import runner's five capabilities over a drop of all, the authorization server's read-only root, and no-new-privileges for both.
    - Each service's mounts are exactly `SERVICE_MOUNTS`', its build `SERVICE_BUILDS`', and the named volumes `COMPOSE_VOLUMES`' (each the engine's default, since driver options bind a host path). Passes 1 and 2 refined a rule for which mounts are safe, and passes 2 and 3 each found a spelling past it, so the list is held instead.
    - No service name but lower-case letters, digits and hyphens, since compose adds a service's name on each network it joins.
    - No top-level key but the file's own. This takes over `name` in an overlay, `secrets` and `include` from the `proxy` rule.
  - **`proxy`:** compose.yaml's proxy is `PROXY_SERVICE`, its label aside: image, user, capabilities, every `TRAEFIK_*` setting, its mount, port, networks, search domains, healthcheck, waits and restart policy. This replaces the `$` rule, which it covers. An overlay with a table still mounts only that table, and `table` now holds that the proxy carries no label but its table's.
  - **`tags`:** also refuses `!reset` and `!override`, which compose honours and Bun.YAML reads past.
  - 38 new probes, 72 in all. By the rule that alone catches each: table 9, characters 4, proxy 11, keys 31, tags 4, networks 4, parse 1; 8 more are caught by two rules.
  - The names podman-compose reads with no `-f` (`podman-compose.yaml`, `container-compose[.override].yaml`) are swept and refused as compose's own are, and CI's file listing counts them.
  - The release's install is held here, not only by the generator's self-check, which an edit to the generator edits too: its files (`ASSETS` in `scripts/release-artifacts.ts`), since the env asset becomes every install's `.env`, and the notes' "Run it" commands, rendered for a tag and a rehearsal, comments aside, since a third `-f` there (`oci://…` is fetched from a registry) or an exported `COMPOSE_*` would load what no check reads. A violation of `keys` or `networks` names SMD-2685.
- **Check 13** (published ports):
  - A mapping's host port is its own bind knob's `_PORT` (`${JEV_BIND…}:${JEV_PORT…}`), with a default written plainly (compose reads `08000` as 8000).
  - Across compose.yaml and its overlays, no two mappings share a knob or a default host port. Whichever binds first takes the other's clients, and jev starts before the proxy.
  - Each live line of `deploy/.env.example` is exactly `KEY=`, with nothing after it, for one of `ENV_EXAMPLE_LIVE`'s keys (the database password, the access keys, the OpenRouter key). Every stack brought up from a copy of it runs with what it sets, and no check renders it: a `COMPOSE_PROJECT_NAME` would rename the project, a `COMPOSE_FILE` add a file no check reads (with no `-f`, as deploy/README.md runs compose), a `JEV_PORT=8000` move jev onto the proxy's port. Exactly, because compose's dotenv reader goes on after a closing quote and runs a quoted value over a line that reads as a comment; with no value on a live line, no quote opens. This subsumes SMD-1844's rule that a live `_BIND` line says 127.0.0.1, which goes.
  - No tracked file is named `.env`, in any case. compose reads one with no `--env-file`, and `git pull` writes a committed one over an operator's own, which git ignores.
- **CI's "The proxy loads only the held route tables"**, for each `-f` combination, substituted and with `--no-interpolate`, now also holds:
  - **Each file reads alike to compose and to Bun.YAML.** compose's render of the files must equal its render of Bun.YAML's reading of each, written to JSON beside it. So a character, tag or number the two read apart (`!!binary`, `!reset`, U+2028, `012`) fails in whichever file carries it. Checks 27 and 28 read the files with Bun.YAML, so this is what makes their reading the one compose runs. The release's overlay, which the checker does not read, is left out.
  - **The whole render is compose.yaml's alone but for what its overlays declare.** This compares against compose.yaml rendered under the same profiles and `-p`. `declared()` names each overlay's paths, as check 28's `OVERLAYS` does, and for the release's overlay an image and its pull policy on any service but the proxy; the proxy and the configs are held as before. So an overlay that adds an alias, a service, a network or a namespace beside what it declares fails.
  - **No two networks share a name, and no two mappings publish on one host address and port.** No combination defines a profile its first file lacks: every profile is on in each render, so a service under a new one would be in none.
- **release.yml** holds the overlay a release ships the same way. Every service, network, config and the project's name are compose.yaml's, under every profile, but for an image and its pull policy on any service but the proxy, and it defines no profile of its own. Before, it compared only the name, networks, configs and proxy.
- **The generator's self-check** (`scripts/release-artifacts.ts`) holds a tag's and a rehearsal's overlay to the same shape. No list the generator keeps feeds either workflow, so a change to the generator cannot widen what they allow.
- **Docs:** deploy/README.md's "Adding a service" names `SERVICE_NETWORKS`, `SERVICE_KEYS`, `CONFINEMENT`, `SERVICE_MOUNTS`, `SERVICE_BUILDS` and `COMPOSE_VOLUMES`, and its route-table paragraph names `OVERLAYS`. compose.yaml's header and compose.canary.yaml's header say what holds them.

**Why.** SMD-2658 held the proxy's route tables and what an overlay sets on the proxy, but read no other service. Its review pass 3 (run-it, on the pinned Traefik) took the proxy's traffic three ways, each past the checker and CI:
- **A mesh-name alias.** With two containers aliased `mcp.ob1.internal`, the one registered first took 30 of 30 requests. compose.host-ports.yaml could add one; `api` aliased `auth.ob1.internal` takes `/auth` sign-in POSTs while the auth profile is off.
- **A sidecar in the proxy's PID namespace.** `pid: "service:proxy"` with `SYS_PTRACE` wrote a route file through `/proc/<pid>/root/etc/traefik/dynamic/`, and Traefik loaded it live.
- **A second network into stable's mesh.** compose.canary.yaml could define `stable-mesh-2` under `${CANARY_STABLE_MESH}` with a shadow on it, which takes stable's `/mcp`. CI counted only the key `stable-mesh`.

compose.yaml's own proxy beyond its table and mounts was left to review.

**Not taken.**
- **ARP or IP spoofing on the mesh by a service that keeps `NET_RAW`.** Docker's default capabilities include it, and only the proxy, the import runner and the authorization server drop all. That is code running in a container, not a compose edit a review misses; the network move (SMD-2583) narrows who is on the mesh.
- **A symlink committed at a held mount's path** (`deploy/orchestration/pipelines.json` pointing out of the checkout). The mounts are held as written; a symlink in the tree is a review's.
- **A name the proxy dials that nothing on the networks holds** (the auth server with its profile off, an absent tier). Docker's resolver forwards it to the host's, and one answering `*.ob1.internal` would get the route's requests. That is the host's DNS, not a compose edit; the network move (SMD-2583) puts the proxy on internal networks alone.
- **Another image for a service other than the proxy in a release's overlay.** Pinning images is what the overlay is for; the proxy's is held.
- **`deploy/auth/provision.ts` and `deploy/orchestration/provision.ts`, which write keys into an operator's `deploy/.env`.** They are host-side code that could write any file; what they write is their reviewers'.
- **An edit to `deploy/canary.sh` or `deploy/tier.sh`** naming another overlay. A script can run any container on stable's mesh (`docker run --network-alias …`); no static gate holds shell, and its reviewers do.
- **What `extra_hosts`, `environment` or `command` make a backend itself do** (the server's own health probe of the authorization server, say). That changes the legitimate backend, not who answers the proxy.
- **The value of an overlay's `depends_on` on the proxy.** It only orders start-up, and a wait on a service that is not declared fails `keys` first.
