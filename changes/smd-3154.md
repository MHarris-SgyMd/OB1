## Changelog

`deploy/canary.sh up --no-refresh` brings a standing canary level in place, keeping the rows only it holds: its env file and keys are mended as `up` does, this checkout's `migrate` run on its own database, and the servers, proxy and forwarder recreated on the new build. Every other `up` still refreshes it from stable; `--no-refresh` is refused, changing nothing, on a canary with no database to keep. Either form now stops the canary's servers and a running `sleep` worker before its Postgres is touched and brings the worker back, and refuses a running service of another profile (SMD-3154).

## FORK

A canary brought level in place, its own rows kept (SMD-3154)

**What changed.**
- `deploy/canary.sh`: `up --no-refresh`. Every refusal and step 2 run as `up` runs them (the env file's own port, address, tier, profiles and keys; the canary's database password). Step 3's refresh through `tier.sh` gives way to:
  - `migrate` built from this checkout and run once (`run --rm`, not `up`, which stays attached) on the canary's own database;
  - the smoke's vector check reading the canary's own vectors before the migration where it read stable's.

  Step 4 recreates the servers, proxy and forwarder, then the smoke and `--connect` as `up` does. With no `<canary>_pgdata` volume it is refused before anything changes, beside `up`'s other refusals, and one whose database holds no relations once its Postgres is up (exit 1); stable's data network is no refusal for it. The option goes with `up` alone, and every failure's advice names the run's own form (`re-run up --no-refresh`).
- **Either form:** the images are built while the canary serves; then its servers and a running `sleep` worker stop before its Postgres is touched, which compose recreates when its own configuration changed (the dogfood canary's Postgres predates 096's preload). Once the smoke has passed, the worker comes back on the new build, from `compose.yaml`'s definition; with no `OB1_WORKER_KEY` left in the env file it stays stopped, `up` says how to mint one and start it, and exits 1. A run that fails after the stop says what it left stopped and how to go on, through the EXIT trap where no step said so itself; after a failed migration it says to leave the worker stopped, since this checkout's expects the new schema; a later run notes a worker left stopped. A running writer of another profile (board-sync, extract, consolidate, the import runner and the role one-shots) is refused before anything changes, and a `ps` that fails refuses too. The connector notes name the run's own form (`then up --no-refresh --connect`).
- CI's canary step: a key only the canary holds, in its `ob1_config`, which a refresh's restore replaces, survives `up --no-refresh`; no tier half runs; the canary answers; its ledger is at the highest migration. A stand-in carrying compose's labels for its `sleep` service (`--init`) is, with no `OB1_WORKER_KEY`, left stopped with exit 1, and, with one, replaced by a container of compose's (another id, not the stand-in's command). On an empty canary database the option exits 1; after `down --volumes`, it is refused (exit 2) and makes no volume.
- `deploy/README.md`'s "A canary beside the stack" names it.

**Not taken.**
- Refusing a plain `up` on a canary that holds rows of its own: keeping them stays opt-in per run. SMD-3155 is the guard (a mark on the canary, and a forcing flag).

**Why.** The dogfood canary holds rows stable does not, SMD-3006's ingested fork records and SMD-3115's decide-mode proposals, so a refresh would erase them, and since 2026-10-13 every canary upgrade has been a hand-made script in path mode. SMD-2874's dogfood move needs `up --port 8011 --connect`, which refreshed; the maintainer chose (2026-10-20) this option over another hand-made script.
