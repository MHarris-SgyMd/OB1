## Changelog

The orchestration POC kit: `evals/eval-orchestration.ts` stands n8n, Activepieces or Windmill up beside a throwaway brain (`evals/orchestration/compose.<tool>.yaml` over `deploy/compose.yaml`), provisions the same Linear-ingestion and MCP-server workflows from files with no UI step, and verifies them against the criteria posted on the ticket; n8n and Activepieces pass, Windmill all but the MCP-client criterion, and `evals/README.md` records the footprint, the license terms and what each needed; `docs/orchestration-tool.md` decides for n8n, as an opt-in sidecar talking to the brain through MCP only, with the licence and egress gates and the rollout (SMD-1863).

## FORK

The orchestration tool is n8n — the same two workflows on three tools, a POC kit that holds each to the ticket's criteria, and the decision record it informs (SMD-1863)

**What changed.** `evals/eval-orchestration.ts --up|--verify|--down <tool>`
runs one candidate as the compose project `ob1-orch-<tool>`: the shipped
`deploy/compose.yaml` (a brain built from the checkout, the host's Ollama) plus
`evals/orchestration/compose.<tool>.yaml` — the candidate as a sidecar, its state
in its own database on the brain's Postgres server under its own login role,
loopback only. `orchestration/stack.ts` writes the gitignored
`orchestration/.env` once (database passwords, the candidate's keys, two brain
keys minted as keygen.ts mints them: `orch-capture` at capture scope, `orch-read`
at read scope) and runs compose with that file and an allowlisted environment.
One adapter per candidate (`orchestration/{n8n,activepieces,windmill}.ts`)
provisions the workflows in `orchestration/<tool>/` — n8n by its public REST API
(its key minted once through the editor's internal endpoints), the other two by
their REST APIs — and the verifier holds each to the ticket's criteria:
it deletes what `orch-capture` wrote, runs the ingestion twice (ten Linear issues
must become ten thoughts, then none), and asks the candidate's own MCP endpoint
for `brain_search` and `linear_issue` and to refuse a missing and a wrong key
with 401/403 (the MCP SDK client, `orchestration/mcp-client.ts`;
`@modelcontextprotocol/sdk` 1.30.0 added to `evals/package.json` at the
server's pin), reading memory per container before and after; with
`--wait-schedule` it then waits up to 20 minutes for a run the schedule started
to succeed, by the tool's own run history.

After review pass 2, at the maintainer's request, the n8n adapter moved from
n8n's CLI to its public REST API (`/api/v1`, OpenAPI-described) with its key
minted once through the editor's internal endpoints, and the verifier gained
C1s, the schedule seen to fire, on all three.

**Why.** The ticket's go/no-go is a live POC per candidate, and its priors were
a survey's; the corrections checked before the run (Windmill's license, the
catalogue sizes) are on the ticket.

**Measured after.** One clean cycle each on the dogfood Mac (2026-09-25, the
host's Ollama otherwise idle), `--verify --wait-schedule` on the verifier as it
now stands: n8n 2.40.6 and Activepieces 0.91.3 pass C1–C4 and C1s; Windmill CE
1.817.0 passes C1, C1s, C3 and C4 and fails C2 — its capture is a script of
ours, and the posted criterion asks for the tool's MCP client. Each run's ten
captures answered by the tool's own record, ten rows on the first run in 23.5 s,
26.4 s and 22.4 s (one wall-clock run each, mostly the brain's model calls),
none more on the second; each schedule seen to fire (after 692 to 875 s);
missing and wrong keys refused with 403 (n8n) or 401. Memory at the end (cgroup
usage, after the schedule wait): n8n 361 MiB, Activepieces 1,176 MiB, Windmill
235 MiB, beside a shared Postgres container at 90, 187 and 664 MiB. Found on
the way, each in `evals/README.md`: n8n's public API covers credentials,
workflows, publishing and run history but neither minting its own key nor
"run now", and it enforces a per-credential domain allowlist (the Linear key
pinned elsewhere was refused); n8n calls the brain's Postgres 16
"compatibility support only"; Activepieces needs its cloud catalogue to
provision a fresh stack (measured with the sync off), refused known pieces on
ten of eleven fresh boots until a restart, offers an AI client 42 of its own
flow-editing tools beside the two, and its MCP client step has no timeout
property (a run failed at 60.7 s under load); Windmill needs superuser-made
cluster roles (`windmill_admin WITH BYPASSRLS`) on the brain's server, has no
Linear or MCP-client step (the scripts are the connectors), and held its
path-scoped MCP token against `runScriptByPath`.

**Not taken.** Gmail as the ingestion source — self-hosted OAuth needs the
operator's own Google Cloud client on all three; Linear with an API key stands
in, and OAuth custody is untested. An egress probe (containers on an internal
network after provisioning). The reference multi-container shapes. A
`--self-check` in CI: the kit needs
three images, Linear and a model server; the evals typecheck covers the driver
and adapters, not the Windmill scripts, which run inside Windmill.

**The decision.** `docs/orchestration-tool.md` (the second pull request on the
ticket): n8n, over Activepieces (operations) and Windmill (fails C2; licence
conditional), as an opt-in `orchestration` compose profile with a store of its
own — not a database on the brain's server; a Postgres 17 or SQLite is
SMD-2210's to measure — reaching the brain through MCP only with a
capture-scope key; OB1 ships templates and provisioning, not the runtime or a
node; n8n's public API is the contract, with its two gaps (no "run now", no key
minting) named; stateful workflows to n8n, one call on demand to the client's
own MCP connector — so n8n's MCP endpoint carries act tools, not the brain's;
one owner per source per brain, so board-sync keeps Linear until an n8n
template can upsert by identity; v1 sends no brain content to a vendor, with
what does leave or linger (act-tool arguments, n8n's saved execution data)
named. The licence gate, marked as the fork's reading: self-hosted personal or
internal use of the referenced image is inside the SUL; the SUL is stricter
than OB1's FSL (which permits professional services and becomes MIT), so a
combined deployment is held to the SUL. The sync trigger for the capture layer:
poll now, native push receivers until SMD-1846, n8n's triggers after. A
headless Claude Code session given only n8n's MCP endpoint listed both tools,
searched the brain and read Linear (recorded in `evals/README.md`). SMD-949's
connectors are re-scoped against n8n (a comment on the ticket).
