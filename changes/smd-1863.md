## FORK

The same two workflows on three orchestration tools — a POC kit that stands each beside a throwaway brain, provisions it from files and holds it to the ticket's criteria (SMD-1863)

**What changed.** `evals/eval-orchestration.ts --up|--verify|--down <tool>`
runs one candidate as the compose project `ob1-orch-<tool>`: the shipped
`deploy/compose.yaml` (a brain built from the checkout, the host's Ollama) plus
`evals/orchestration/compose.<tool>.yaml` — the candidate as a sidecar, its state
in its own database on the brain's Postgres server under its own login role,
loopback only. `orchestration/stack.ts` writes the gitignored
`orchestration/.env` once (database passwords, the candidate's keys, two brain
keys minted as keygen.ts mints them: `orch-capture` at capture scope, `orch-read`
at read scope) and runs compose with that file and an allowlisted environment.
One adapter per candidate (`orchestration/{n8n,activepieces,windmill}.ts`)
provisions the workflows in `orchestration/<tool>/` — n8n by its CLI, the other
two by their REST APIs — and the verifier holds each to the ticket's criteria:
it deletes what `orch-capture` wrote, runs the ingestion twice (ten Linear issues
must become ten thoughts, then none), and asks the candidate's own MCP endpoint
for `brain_search` and `linear_issue` and to refuse a missing and a wrong key
with 401/403 (the MCP SDK client, `orchestration/mcp-client.ts`;
`@modelcontextprotocol/sdk` 1.30.0 added to `evals/package.json` at the
server's pin), reading memory per container before and after.

**Why.** The ticket's go/no-go is a live POC per candidate, and its priors were
a survey's; the corrections checked before the run (Windmill's license, the
catalogue sizes) are on the ticket.

**Measured after.** One clean cycle each on the dogfood Mac (2026-09-25, the
host's Ollama otherwise idle): all three pass C1–C3 on the verifier as it now
stands, and `--up` took no UI step (C4). Ten issues in 24.1 s (n8n 2.40.6),
22.2 s (Activepieces 0.91.3), 33.6 s (Windmill CE 1.817.0) — one wall-clock run
each, mostly the brain's model calls — and none on the second run; missing and
wrong keys refused with 403 (n8n) or 401. Memory after the runs (cgroup usage):
n8n 371 MiB, Activepieces 1,462 MiB, Windmill 236 MiB, beside a shared Postgres
container at 78, 198 and 343 MiB. Found on the way, each in `evals/README.md`:
n8n calls the brain's Postgres 16 "compatibility support only"; Activepieces
needs its cloud catalogue to provision a fresh stack (measured with the sync
off), refused known pieces on six of seven fresh boots until a restart, offers
an AI client 42 of its own flow-editing tools beside the two, and its MCP
client step cannot be given a timeout past 60 s; Windmill needs superuser-made
cluster roles (`windmill_admin WITH BYPASSRLS`) on the brain's server, has no
Linear or MCP-client step (the scripts are the connectors), and held its
path-scoped MCP token against `runScriptByPath`.

**Review passes.**

| pass | finding | caught by | fix |

| 1 | egress and memory claims stated as measured (switches set, not probed; cgroup usage, no brain-only baseline) | cold read | record reworded |

**Not taken.** Gmail as the ingestion source — self-hosted OAuth needs the
operator's own Google Cloud client on all three; Linear with an API key stands
in, and OAuth custody is untested. An egress probe (containers on an internal
network after provisioning). The reference multi-container shapes. A live AI
session (the ADR's check, for the pick). A `--self-check` in CI: the kit needs
three images, Linear and a model server; the evals typecheck covers the driver
and adapters, not the Windmill scripts, which run inside Windmill.

**Follow-ups.** The ADR — the pick, the boundary, the gates — in the next PR on
this ticket.
