## FORK

The same two workflows on three orchestration tools — a POC kit that stands each beside a throwaway brain, provisions it from files and holds it to the ticket's criteria (SMD-1863)

**What changed.** `evals/eval-orchestration.ts --up|--verify|--down <tool>`
runs one candidate as the compose project `ob1-orch-<tool>`: the shipped
`deploy/compose.yaml` (a brain built from the checkout, the host's Ollama) plus
`evals/orchestration/compose.<tool>.yaml` — the candidate as a sidecar, its state
in its own database on the brain's Postgres server under its own login role,
loopback only. `orchestration/stack.ts` writes the gitignored
`orchestration/.env` once (database passwords, the candidate's keys, three brain
keys minted as keygen.ts mints them: `orch-capture` at capture scope, `orch-read`
and `orch-verify` at read scope). One adapter per candidate
(`orchestration/{n8n,activepieces,windmill}.ts`) provisions the workflows in
`orchestration/<tool>/` — n8n by its CLI, the other two by their REST APIs —
and the verifier checks the same things of each: the ingestion run twice (ten
Linear issues become ten thoughts written by `orch-capture`, then none), the
candidate's own MCP endpoint listing and answering `brain_search` and
`linear_issue` and refusing a session with no credential (the MCP SDK client,
`orchestration/mcp-client.ts`; `@modelcontextprotocol/sdk` 1.30.0 added to
`evals/package.json` at the server's pin), and memory per container idle and
after the runs.

**Why.** The ticket's go/no-go is a live POC per candidate, and its priors were
a survey's. Checked against the sources before the run: Windmill is AGPLv3 with
a proprietary CE image (not Apache 2.0), Activepieces has 763 pieces (not ~280),
n8n lists 2,274 integrations (not 400+).

**Measured.** One clean cycle each on the dogfood Mac (2026-09-25): all three
pass C1–C4 — ten issues in 27.3 s (n8n 2.40.6), 24.2 s (Activepieces 0.91.3),
31.5 s (Windmill CE 1.817.0), none on the second run; both tools answered and a
session with no credential was refused on each. Resident memory after the runs:
n8n 373 MiB (+77 MiB in the shared Postgres), Activepieces 1,969 MiB (+204),
Windmill 201 MiB (+384 — Postgres is its queue). Found on the way, each in
`evals/README.md`: n8n calls the brain's Postgres 16 "compatibility support
only"; Activepieces needs its cloud catalogue to provision a fresh stack
(measured with the sync off), refused known pieces on two of three fresh boots
until a restart, and offers an AI client 42 of its own flow-editing tools
beside the two; Windmill needs superuser-made cluster roles (`windmill_admin
WITH BYPASSRLS`) on the brain's server, has no Linear or MCP-client step (the
scripts are the connectors), and held its path-scoped MCP token against
`runScriptByPath`.

**Not taken.** Gmail as the ingestion source — self-hosted OAuth needs the
operator's own Google Cloud client on all three; Linear with an API key stands
in, and OAuth custody is untested. The reference multi-container shapes. A live
AI session (the ADR's check, for the pick). A `--self-check` in CI: the kit needs
three images, Linear and a model server, none of which CI has; the evals
typecheck covers the code.

**Follow-ups.** The ADR (`docs/orchestration-tool.md`) — the pick, the boundary,
the gates — lands in the next PR on this ticket.
