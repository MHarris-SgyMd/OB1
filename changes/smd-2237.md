## Changelog

Preflight no longer tells an empty, unmigrated database to `migrate.ts --baseline`: with no schema the `migration ledger` row now says what the `schema` row says — apply the migrations — not the adoption step, which over no schema records every migration as applied without running one and leaves every later plain run skipping everything. And `migrate.ts --baseline` refuses when `public.thoughts` does not exist, naming the plain run and a `--force` override, so following the old remedy can no longer brick a database (SMD-2237).

## FORK

preflight's ledger row, and `migrate.ts --baseline`, no longer offer to baseline an empty database (SMD-2237)

**What changed.** `server-portable/preflight.ts`: the `migration ledger` row's
"no schema_migrations" branch now asks whether there is a fork schema to adopt —
`public.thoughts` (migration 001's table), by `pg_class` so a role's search_path
does not hide it, the predicate the `schema` row's off-path probe uses. With the
schema present it keeps the adoption remedy ("the schema was applied by hand …
adopt it with `--baseline`"); with no schema it warns "no schema_migrations
table and no schema — nothing has been migrated here" and gives the `schema`
row's own remedy, `cd db && bun migrate.ts --url $DATABASE_URL`. The two rows no
longer contradict each other on an empty database.

`db/migrate.ts`: `--baseline` refuses, before the ledger table is created, when
`public.thoughts` does not exist — `--baseline` records every migration as
applied without running one, and over no schema that is never adoption; it leaves
a ledger the next plain run reads as done. The refusal names the plain run and a
new `--force` flag, the escape hatch for an operator who means to record the
ledger over a schema built some other way. `--force` does nothing without
`--baseline`, so it is refused on its own rather than dropped.

**Why.** Found by SMD-2062's second review pass, running preflight on a fresh,
unmigrated PG16 (identical on `main`). The `migration ledger` row warned "the
schema was applied by hand" and recommended `--baseline` whether or not any
schema existed, while the `schema` row on the same screen correctly said "Apply
the migrations". An operator who followed the ledger row got a ledger at the tree
head over an empty schema, and every later plain `migrate.ts` then skipped every
file — the dangerous remedy was the one phrased as adoption.

**Held.** `db/test-upgrade.ts` against real Postgres, 325 assertions (from 320):
a new `[22]` — `--baseline` on an empty database refuses (exit 2), names
`public.thoughts`, the plain run and `--force`, and creates no
`schema_migrations` table (the refusal is before any write); another tool's
`thoughts` in a non-public schema over an empty public still refuses (the guard
reads public alone); `--baseline --force` records every migration over the empty
schema; `--force` without `--baseline` is refused (exit 2). The existing
`--baseline` cases — `[7]`, `[20i]`, `[20j]`, which baseline over a schema built
by hand — still pass: the guard fires only on an empty one.
`server-portable/test-preflight.ts` against real Postgres, 466 assertions (from
463): the `[5]` un-migrated run's `migration ledger` row names the migrate
command, never `--baseline` or "applied by hand"; a stray `thoughts` in another
schema off the path reads the same (public alone); the migrated-but-hand-applied
run still offers `--baseline` (the legitimate adoption case). Both directories
typecheck clean.

## Not taken

Exempting `--baseline --dry-run` from the guard. `--dry-run` elsewhere touches
nothing and never refuses, so a case could be made that a dry run should preview
"would baseline N" even on an empty database. It refuses instead: a preview of a
ruinous adoption reads as endorsement, and the refusal is itself the useful
answer — there is nothing to adopt. The guard writes nothing either way, so the
`--dry-run` contract ("touch nothing") holds; only its "never refuses" habit
does not, deliberately.

Resolving `thoughts` by anything wider than schema `public`. Both probes ask
`pg_class` for `public.thoughts` specifically, where `migrate.ts`'s `--reapply`
pre-checks use `to_regclass('thoughts')` (search_path-dependent). A fork schema
built in a non-public schema would therefore have its legitimate `--baseline`
refused and need `--force`. That is the same "public alone" narrowing SMD-2062
took for preflight's schema row — a `thoughts` outside public is treated as
another tool's — and `--force` is the deliberate escape hatch, so the two probes
match the schema row rather than widening past it.
