## Changelog

Fork Checks' "Schema migrations" job runs `test-schema.ts` at the default embedding width and at 768 side by side in one step, where it ran them one after the other; each run writes its own log, both are printed (a failing one open, under an error annotation), and the step fails when either run does (SMD-2092).

## FORK

"Schema migrations" runs test-schema.ts at both embedding widths at once, not one after the other (SMD-2092)

**What changed.** The job had two steps that each ran `bun test-schema.ts`: "Apply migrations and assert the schema" at the default width, and, after the board sync and ingestion self-checks, "Schema builds at a non-default embedding width" with `OB1_EMBEDDING_DIM=768` and `OB1_EMBEDDING_MODEL=nomic-embed-text`. They are now one step, "Apply migrations and assert the schema, at the default width and at 768". It starts both runs in the background, each writing its own log under `$RUNNER_TEMP` with stdout and stderr together, since a failed assertion goes to stderr. It then waits on both. Nothing prints until both have exited, where the two steps streamed, so each run is under `timeout --kill-after=10s 15m`: a hung run ends as exit 124, reported as over the limit, with its log printed. Without it, a step killed at the job's limit or cancelled prints neither log. A passing run's log prints inside a folded `::group::`. A failing run's log prints open, under an `::error::` annotation that names its width and exit code. The step ends with two summary lines, each run's `N assertions: …` line with its exit code (or "no summary line" when the run died before its report), then fails when either run did. The job keeps its name and stays one required check, so `.github/rulesets/main.json` is untouched. The board-sync and ingestion self-checks still follow the schema step, and now run when it has failed too (`!cancelled()` and a successful install). The 768 run used to come after them, so a break at 768 alone left them running; one step holding both widths would otherwise skip them on any break. The summary reads the line `report()` in `db/test-support.ts` prints, and a comment there now says so.

The ticket calls the legs "1536- and 768-dim". The default width has been 1024 since change 19 (`db/config.mjs` `DEFAULT_EMBEDDING_DIM`), so the step says "the default width", which follows the config if it moves.

**Why.** "Schema migrations" was the last job to finish in 34 of 40 Fork Checks runs (median 336 s, against a run median of 5.7 min), and in run #504 its two runs took 187 s and 142 s one after the other. Each run is one single-threaded process whose PGlite databases live in memory (a second, `cdb`, opens for one section). `test-schema.ts` writes no file, opens no port and spawns nothing (it reads `migrations/`, `schemas/` and `README.md`), so the two share nothing they write, and a public repository's `ubuntu-24.04` runner has four cores (a private one has two).

**Held.** The step's text, extracted from the workflow and run as CI runs it (`bash --noprofile --norc -eo pipefail` in `db/`, with `RUNNER_TEMP` set), passes on this tree with both runs at 1590/1590 in `oven/bun:1.4.0` (Debian: GNU coreutils and grep, as on the runner), and passed on macOS before the limit was added (macOS has no `timeout`, so the step no longer runs there as written). Two probes stand in for a hang, in the container:
- The limit set to 20 s: both runs end at exit 124, the step exits 1 after 20 s, and both partial logs print open under an error reading "exit 124, over the 20s limit".
- Each run swapped for a Bun process that ignores SIGTERM, the limit at 5 s: `--kill-after` fires, both runs end at exit 137 after about 15 s, both logs print under an error reading "exit 137, killed: over the 5s limit with TERM ignored, or out of memory", and the step exits 1.

Four mutants each fail it:
- `thoughts.embedding` hard-coded to `vector(1024)` in migration 001 breaks the 768 run only. The step exits 1, the default run's log stays folded, and the 768 run's log prints open under the error, its first `✗` naming the mismatch. Its summary reads "no summary line", because the run died before its report.
- `db/README.md`'s quoted total set to 1589 fails both runs' doc check: both logs print open, and both summary lines read "1 doc check(s) failed".
- On the README-1589 tree, a bare `wait` in place of `wait … || rc=$?` ends the step at exit 1 with neither log printed, which is why the comment asks for the `||`.
- On the same tree, dropping the step's last line (`[ "$default_rc" -eq 0 ] && [ "$narrow_rc" -eq 0 ]`) passes two failed runs.

A fifth mutant was discarded: a width literal in migration 041's `match_thoughts` survives, because a later migration redefines the function, so it tests nothing.

actionlint 1.7.7 with shellcheck passes on both workflows, zizmor 1.30.1 reports nothing on `fork-checks.yml`, and check-fork passes.

**Measured after.** On an 18-core Mac, one run takes 63.3 s and the pair 64.1 s; in the container capped at four CPUs (`--cpus 4`, faster cores than the runner's), the pair with the limit takes 79.4 s. CI's four-core runner is the number that counts; the PR's runs are to be recorded here before it merges.

**Not taken.** A second job or a matrix leg would be a new required check: a ruleset edit, and check 20 refuses a matrix job. `db/ci-parity.sh`, the local mirror of CI's database suites, runs `test-schema.ts` at the default width only, as it did before this change. The fixture loads, which the CI audit put at most of each run, are SMD-2097's. A `timeout-minutes` on the job, which would bound a hang anywhere else in it, is SMD-2094's. A cancelled run still prints no log; a trap to print them on the way out was judged not worth its lines. Writing the summaries to `$GITHUB_STEP_SUMMARY` as well is left for later: the log's last lines carry them.
