## Changelog

`search_thoughts` can weigh what matters (SMD-3668), with two opt-in inputs. `priority_weight` (0–1, default 0) orders the top matches by meaning and effective priority together, so of four High tickets the one due tomorrow comes first even when it matches the query least. `min_priority` (0 none to 5 critical) keeps only matches whose priority is known and at least that level, urgency included.
A match's priority is its own, or that of a ticket it is filed under; a ticket it only mentions doesn't count. The header says what was ranked and kept, and with neither input set, search is exactly as before.

## Record

`search_thoughts` takes `priority_weight` and `min_priority`, ranking and filtering a window of its matches by effective priority, PR 1 of 3 (SMD-3668)

**What changed.**
- **Two inputs on `search_thoughts`**, so on REST `/v1/search` too:
  - `priority_weight`, clamped to 0–1 as `recency_weight` is;
  - `min_priority`, an integer 0–5 as `set_priority`'s level is.
- **A window re-rank in the core** (`core/reads.ts`), not a migration:
  - With either set, the hybrid (or `search_thoughts_current` under `prefer_current`) is asked for min(100, 4 × limit) matches, 077's window.
  - One `effective_priority` read (122) covers the whole window: each match's own item, and the tickets its metadata files it under.
  - **A match's priority** is the highest *known* effective priority among those (`prioritiesOf`). Known means stated, or inherited from what it serves. With none known, it is its own unknown.
  - **The order** is `(1 − w) × relevance + w × priority` (`rankByPriority`). Relevance is the score over the window's top. Priority is effective over 9, the default weights' largest (level 5, overdue 3, unblocks 1). Ties keep the window's order.
  - **The floor** keeps known priorities at or above `min_priority`, urgency included, per decision 5's composition. An unknown never passes.
- **With neither set:** no window and no read, so the same SQL call and the same reply.
- **The reply:** the header says how the window was ranked, how many matches carry a known priority, what a floor kept, and whether a match past the window went unread. The structured value carries `priority`: weight, floor, window, read, kept and known.
- **The query log:** a search with either set is not logged, as one with `min_trust` isn't. The log has no column for them, so a replay would run it without them.
- **Docs:** `server-portable/README.md` has a section on it, and `docs/priority.md`'s "A read" names the window and the filed-ticket rule.

**Why not in SQL.** `recency_weight` blends inside `match_thoughts`' four branches (074), and the hybrid's score is its fusion score (075). A 0–1 blend there needs a migration through those branches and 059's frozen callers. `prefer_current` already re-ranks a window (077), and so does this, from one read per search.

**Narrowed.** The ticket names `priority_weight` on the compat `search` too. That tool takes only its query, which is ChatGPT's shape, and already pins `recency_weight` and `prefer_current` off. A client never sends it more, so it doesn't rank by priority. PR 2's label reaches it.

**Measured.** One `effective_priority` read for a full window (125 items over 5,000 thoughts, no priorities stored) takes 11.9 ms median, 14.2 ms p90. That cost applies only with either input set.
