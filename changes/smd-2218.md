## Changelog

`db/graph-centrality.ts`'s dependency read (`--startable`, `--decay-blocked`) gates only on a system that states a lifecycle: the links of a system none of whose rows carries a known status_type — an `--items` source that never says a ticket is done — block nothing and name no ticket rather than hide its tickets for good, the dependency line names each source and says which gate nothing, and the JSON's `dependencies.systems` lists each system's facets and whether it gates; while the board is the only source, and states its lifecycle, every report reads as before (SMD-2218).

## FORK

graph-centrality's dependency read gates only on a system that states a lifecycle — an --items source with no statuses no longer blocks its tickets forever (SMD-2218)

**What changed.** SMD-2061 read the dependencies when board-sync was their only
writer. Since SMD-2136, `ingest-records.ts --items` writes `blocks` /
`blocked_by` for any system it is given, and both flags read them. A blocker is
settled by its row's lifecycle; a row of another system has one only if its
source stated it (an items file, in `facets.status_type`, one of the six types
`LIFECYCLE_TYPES` knows), and by SMD-2061's rule a blocker with no known status
blocks. So an items source that never states a status would have hidden every
ticket it said was blocked, for good. Decided on the ticket: every system is
kept, and a system GATES only when some source row of it states a known
status_type on its own metadata — not one it borrows through a Linear ticket
claim. A gating system's links are read exactly as the board's are — a settled
blocker frees its ticket, an unknown one blocks and is counted. A system that
states none cannot say a blocker is settled, so its links gate nothing:
`gating`, a new CTE in `dependencySql`, holds the systems present in the links
for which one source row of their own carries a known type, and `deps` keeps
only theirs, so an ungated system's links block no thought, carry no blocker and
name no ticket, and everything downstream reads as before. The board gates by
the same rule, not by name. `facets` still counts every link read;
`Dependencies.systems` lists each system's facets and whether it gates. The
dependency line, while the board is the only source and gates, is SMD-2061's
word for word; otherwise it names each source with its facets, says each is as
current as its source's last passes, names the systems that gate nothing in one
clause and, where an items file could be the source, how it states a status, and
counts the tickets a gating dependency names — the rest have no gating
dependency, not "none recorded". The 053-missing error no longer says "the
board's". The known types reach the gate through a new `dependencySql` slot,
bound in the existing order so the known types stay the last slot coverage
reads.

**Why.** A Jira export with its `blocked_by` links and no statuses would have
emptied `--startable` of every Jira ticket it named, and sunk each one under
`--decay-blocked`, with the line crediting "the board" and board-sync for links
neither wrote. Live, every dependency facet is the board's, so no report moves:
on the dogfood brain (2026-09-25, 168 facets, all `linear`, gating), main's
`graph-centrality.ts` and this one render the same report byte for byte under
`--status open --startable`, `--status open --decay-blocked`, `--startable`,
`--decay-blocked`, a subject under the decay, and `--status open`; the
dependency counts agree, `systems` is `[{linear, 168, gates}]`, and the gate
costs nothing measurable (within 10–100 ms of main's 150–960 ms either way).

**Not taken.** *Reading the board's links alone* and *keeping every system
gating, an unknown blocker blocking* were the ticket's other two options: the
first discards dependencies a user imported on purpose, the second hides a
status-less source's tickets for good. *Gating per ticket rather than per
system* (a blocker whose own row states no lifecycle gating nothing): that would
stop an unknown blocker of the board blocking, which SMD-2061 decided it must.
*The lifecycle line naming its sources*: "Ticket status is read from synced
metadata (board-sync)" is SMD-1994's, and an items row's own `status_type`
counts in it; its wording is a question for that line. *Refusing `issue` /
`ticket` in an item's facets*: SMD-2136's contract passes them through to the
row's metadata, where they claim a Linear ticket's status and dependencies; that
is the contract's rule to change, not this reader's: SMD-2227. *A status that
sticks* (pass 1): the pipeline merges an item's facets into the row's metadata
and never replaces them (SMD-2136), so a file that stops stating `status_type`
leaves the last one, and its system gating, until it states `null`; that is the
contract's merge rule. *One freshness per source*: the line gives the latest
facet change across all of them.

**Upstream status:** not sent — upstream has no entity graph, board sync or
link facets.
