## Changelog

`server-portable/test-preflight.ts` runs as two shards (`OB1_PREFLIGHT_SHARD=first|rest`), and the data-layer job runs them as two background legs, the rest on a Postgres of its own, so test-preflight's time is split across two legs; each background leg's log is stamped line by line (SMD-3468).

## FORK

test-preflight in two shards — the data-layer job's floor split in half (SMD-3468)

**What changed.**
- **Shards.** `test-preflight.ts` takes `OB1_PREFLIGHT_SHARD=first|rest`, as `db/test-live.ts` takes `OB1_LIVE_SHARD`:
  - `SHARDS` lists first's sections, [5] and [9]; rest runs every section `SHARDS` does not list, so a new section runs unless it is listed. Unset, every section runs, in the order it always did.
  - Each header reads `want(id)`. A name that is no shard, or a section listed twice, exits 2. A shard prints its name first, as test-live's do.
- **[5] split at its full re-apply.** [5] was one 4,200-line section, 62% of the suite's time (93 of 149 s). Its second half, from the capturing role's case on, is [5b].
  - [5b] opens its own client and drops the schema first, a guard: the full apply that opened that half already took nothing from what came before ("whatever state the reapply blocks above left"), and the full run passes without the drop (a mutant that survives).
  - [5] now ends as [5b] does: its thoughts deleted, then preflight's `--json` must say ok. [9]'s one database case reads that state, after [5] in the first shard and after [5b] in a full run, so a fail-level row [5] left would fail in [5], not in [9].
- **[doc]** reads `server-portable/README.md`'s count lines for the suite, as test-live's [doc] reads `db/README.md`'s, on every run:
  - one count for each shard, adding up to the full run's: an assertion outside a `want()` section would count in both shards and break the sum;
  - every header's id is its own;
  - every id `SHARDS` lists has a header;
  - this run's count is the README's, for the full run or the shard, when nothing was skipped.
- **The README** gives the three counts: 994, first 441, rest 553.
- **The data-layer job** (`.github/workflows/fork-checks.yml`) starts three background legs where it started two:
  - test-upgrade and the first shard on `pair-postgres`, as before;
  - the rest on a new service, `preflight-postgres` (5434), a Postgres of its own;
  - each leg is one call, `leg <name> <command>`, with the suite's own assignments before it: it writes the name to `data-layer.legs`, starts the leg in the background, and keeps its log and code under the name. A name given twice is refused there. Name, registration and command share one line, so no edit to one line can part a leg from its name. The last step waits on the legs that file lists (refusing an empty list) and prints a summary line for each.
- **`/dev/shm`.** Both background services get `--shm-size=1g`, as `db/with-postgres.sh` gives its containers. A parallel HNSW build takes `maintenance_work_mem`'s 64 MB of it, which is all of Docker's default. With two suites building at once, a build ran out ("could not resize shared memory segment … No space left on device").
- **Stamped logs.** Each line of each leg's log carries `+<s>s` since the start step, to a tenth, from bash's own clock (`EPOCHREALTIME`). A leg's exit code is the suite's (`PIPESTATUS`), with `-e` off in its subshell. The summary grep reads past the stamp.
- **`db/ci-parity.sh`** runs the two shards in series, as check 35 holds it to what CI runs.

**Why.** SMD-3195 had moved the upgrade/preflight pair into the background. After that, test-preflight was the job's floor: setup about 18 s, plus the pair's median 219 s (p90 238), plus about 3 s, for a job of about 242 s (the ticket's figures, from the 2026-10-28 review's runs). Which leg was the long one is inferred, as the ticket says: CI logged neither leg's times, but test-upgrade's own section stamps put its [20as] at +88 to +128 s with about 17 short sections left, so it ends near +110 to +155 s while the pair ran to +151 to +237 s. The foreground suites took about 114 s. Over main's six green push runs of 2026-10-29 and 10-30, before this change, the job's median was 252 s, the slowest Fork Checks job. Timed here, test-preflight took 149 s whole. [5] was 93 s of that, [12] 25.5 s and [9] 13.2 s.

**Departures from the ticket.**
- **A third Postgres, not a second database on pair-postgres with the `pf_*` roles suffixed per shard.** A choice, made before the split showed the shards' roles apart:
  - suffixing would rewrite about 60 assertions that match a role's name in preflight's printed fixes (`ALTER ROLE pf_reader IN DATABASE …`);
  - as split, the roles don't overlap after all (first makes `pf_stray_reader` and `pf_board`, rest the others, all in [5b] and [12]), so a second database would have needed no suffix;
  - the third service keeps rest off the CPU, `/dev/shm` and transaction horizon that test-upgrade and first share, at the cost of one more pgvector container. First shares pair-postgres with test-upgrade, as the whole suite did before; "a Postgres of its own" in the Verify (SMD-3195's horizon issue) means apart from ob1test.
- **[5] split, where the ticket split by section.** No split of whole sections comes near even while [5] is 93 of 149 s.
- **"[doc]'s count check fails if a section is in neither shard":** with rest as the catch-all, no section can be in neither. [doc] fails what would take one out of both instead: an id `SHARDS` lists that no header has, an id two headers share, and shard counts that don't add up to the full run's.
- **`--shm-size`** was not in the ticket. The rehearsal found it.
