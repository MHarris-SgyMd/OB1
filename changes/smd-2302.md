## Changelog

Every `db/` script reaches its database through one module, `db/connect.ts`: one `--url`/`DATABASE_URL` resolver, one client (which uses the URL's database even with `PGDATABASE` exported), one close-then-exit door, and one "may this database be reset?" rule — `tier.ts --refresh` now refuses a `--to` with an empty host, hands `pg_dump`/`pg_restore` the database its client reached rather than the URL as typed, and `OB1_EVAL_ALLOW_REMOTE_DB` is no longer read (use `OB1_ALLOW_REMOTE_DB=1`) (SMD-2302, SMD-2134).

## FORK

One connection module for every db/ script — one loopback rule, one target for Bun and libpq, and no exit that skips the close (SMD-2302 / 2134)

**What changed.** `db/connect.ts` is how a `db/` script reaches its database,
SMD-2134's second cut after the flag scanner.
- `databaseUrl`, the one resolver: `--url`, else `DATABASE_URL`, else exit 2
  with the one refusal. Refused too, with exit 2: a blank URL, one that does not
  parse, one whose scheme is not `postgres:`, and one with a bad percent-escape.
  Neither refusal prints anything of the URL.
- `openSql`, the one client: one connection unless asked (the claim workers
  ask for one per worker and a spare).
  - It uses the URL's database when the URL names one. Bun 1.4.0 lets an
    exported `PGDATABASE` override the URL's path, so `--url …/canary` with
    `PGDATABASE=stable` reached stable.
  - It throws fixed messages, never the client's own error, whose dump printed
    the URL whole.
- `resetRefusal`/`mayReset`, the one answer to "may this database be reset?",
  printing why not. A URL passes if the host Bun's client reaches is loopback by
  name (`localhost`, `127.0.0.1`, `[::1]`, `0.0.0.0`) and not empty.
  `OB1_ALLOW_REMOTE_DB=1`, exactly, lets anything through. `tier.ts --refresh`
  and the suites' `assertThrowawayDatabase`/`dropSchema` both ask it.
- `libpqTarget`, for a libpq tool, rebuilds its target from what the client
  resolved:
  - host, port, database and user as a URL, keeping only the TLS, timeout and
    label parameters;
  - the password as `PGPASSWORD`, off the command line;
  - every other `PG*` variable taken out of the tool's environment.

  `tier.ts --refresh` gives `pg_dump` and `pg_restore` these targets.
- `closeThenExit`: runs a body that returns an exit code, closes every pool,
  flushes stdout and stderr, then exits. A code that is not an exit status
  exits 1 (256 would read as 0). A throw still closes, then reaches the
  script's handler.

Nine scripts' URL blocks, the benches' and `measure-1288.ts`'s clients and
`tier.ts`'s ten `new SQL(...)` go through the module. `hnsw-graph.ts`,
`graph-centrality.ts` and `tier.ts --replay/--diff` exit through the door.
`evals/eval-quant.ts` reads the loopback set instead of keeping a copy. The
migrator image (`db/Dockerfile`, `.dockerignore`, `release.yml`'s paths) and the
import runner's image (`deploy/orchestration/runner.Dockerfile`) copy
`connect.ts`, since `migrate.ts`, `ingest-records.ts` and `reembed.ts` import it.

Behaviour that moved:
- **`tier.ts --refresh` refuses a `--to` with an empty host**
  (`postgres:///db`), which its old rule trusted. Bun's client resolves it
  through `PGHOST`. The rule now admits `0.0.0.0`, which it did not know, and
  the refusal says which check failed.
- **`pg_dump` and `pg_restore` reach the database the guards checked.** They
  used to take the operator's URL, which libpq can read as another server. This
  was verified with a real `pg_restore`:
  - libpq has no fragment, so `…/db#?host=prod` is a query to it;
  - it splits the userinfo at the first `@` (Bun at the last), so
    `u@prod:5432,x@localhost/db` sends it to prod;
  - it follows `?host=`, `?hostaddr=`, `?port=`, `?dbname=`, `?service=`,
    `PGHOSTADDR` and `PGSERVICE`, which Bun ignores.

  Bun would have dropped the schema on localhost while `pg_restore` restored
  into prod. The rule before this change had the same hole.
- **A URL that names a database is used over an exported `PGDATABASE`**, in
  every script.
- **`OB1_EVAL_ALLOW_REMOTE_DB` is no longer read**, and the suites' refusal
  says so when it is set. It is the eval-local name the suites' guard also
  honoured. `deploy/tier.sh` passes `tier.ts` every `OB1_*` variable in the
  stack's env file except `OB1_ALLOW_REMOTE_DB`, which it sets itself, never for
  a URL `--to`. So a second name read by the one rule would have been a way past
  it.
- `hnsw-graph.ts` without a URL prints the shared refusal; `tier.ts --replay`
  exits 0 explicitly; `tier.ts`'s messages show an empty host as `$PGHOST`.

**Why.** Nine copies of `cli.value("url") ?? process.env.DATABASE_URL` and its
refusal, and every script built its own client. Two rules answered "may this
be dropped":
- `tier.ts`'s `isLoopback` trusted an empty host and did not know `0.0.0.0`;
- `test-support.ts`'s refused the one, admitted the other, and read a second
  override name.

And two scripts called `process.exit` inside the `try` whose `finally` closed
the pool, so the close never ran: `hnsw-graph.ts` on every run, and
`tier.ts --replay/--diff` on a missing `query_log` and on `--diff`'s verdict.

**Held.** `db/test-connect.ts` (468 checks, no database, CI's replay-gate job
beside test-cli; every child `--no-env-file`, with a timeout):
- **The rule, as one truth table.** Twenty-two URLs, each checked with no
  override, with `OB1_ALLOW_REMOTE_DB=1`, and with the retired name, and each
  reason checked to hold no password. The suites' refusal and `tier.ts
  --refresh`'s are run: they refuse before connecting, pass the override, and
  refuse the retired name. A developer's `PGSERVICE` does not refuse a suite.
- **`libpqTarget` on seven shapes** under ten redirecting `PG*` variables. The
  shapes are the reviewers' fragment and first-`@` URLs, a query setting every
  libpq redirect, IPv6, an encoded user and database, no userinfo, and no host.
  For each, a libpq-rules parser and WHATWG both read the target as the host,
  port, database and user Bun resolved, with nothing else in its query. The
  password is not in the URL, and no `PG*` variable that picks the server is
  left. `tier.ts` hands both tools these targets.
- **The resolver and the client.** Each refusal is checked through
  `DATABASE_URL`, through `--url` and through `openSql`. The URL's database
  beats `PGDATABASE`.
- **The door, run with pools that record their close.** The order is checked.
  `255` stands, and seven non-codes (256 among them) exit 1. A close that
  rejects or throws strands nothing. 5 MB written to stdout or stderr reaches a
  slow reader whole.
- **The census**, with teeth shown on the shapes a refactor would write:
  - no non-suite `db/` file reads `DATABASE_URL` or builds a client (aliases and
    namespace imports included);
  - no `db/` or `evals/` TypeScript spells a loopback host;
  - every `--url` goes through `databaseUrl`;
  - no door body exits or closes.

Sixty-five mutants each fail it.

**Not taken.**
- A remote guard on the workers: on the dogfood stack they reach
  `postgres:5432` by service name (SMD-1869), and the guard is for a command
  that drops a schema.
- The workers' ~15 explicit close-then-exit sites each: they close today (SMD-2304).
- A door that traps `process.exit` (a `catch` in the body could swallow it),
  or a call graph for a helper that exits inside a body (a linter's job).
- A close that never settles, or a body that destroys `process.stdout`, still
  hangs the door. Bun then neither calls back from `end()` nor reports the
  stream destroyed, and a bound on the wait would cut off a slow reader. No
  script does either.
- `OB1_ALLOW_REMOTE_DB` set from `evals/.env`, `.env` or `deploy/.env` on a
  host run (`loadEnv`; tier.sh's container turns the files off). It predates
  this change and is SMD-2312.
- `config.mjs`'s `isLocalHostname`: it answers another question, whether a
  model endpoint needs a credential.
