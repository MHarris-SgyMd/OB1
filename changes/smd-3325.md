## Changelog

`migrate.ts --baseline`, which recorded every migration as applied without running one, and `--force`, its override, are retired: each is refused by name (exit 2) before the run reads anything, and a schema with no ledger is brought under the migrator by `--reapply`: every file idempotent, in one transaction, after its checks that the shell agrees with the brain (SMD-3325).
Preflight's `migration ledger` row tells a schema with no ledger to re-apply the migrations over it, not to adopt it, and no remedy or hint of preflight's, reembed's or the migrator's names `--baseline`; the hint inside migrations 030–111 still asks "adopted with --baseline?", the files being hashed.
**Upgrading:** drop `--baseline` and `--force` from any `migrate.ts` command; to bring a hand-applied schema under the ledger, run `migrate.ts --reapply` with the server and every worker stopped.

## FORK

`migrate.ts --baseline` and `--force` are retired, refused by name, and a schema with no ledger is re-applied (SMD-3325)

**What changed.**
- `db/migrate.ts`:
  - `--baseline` and `--force` are refused by name, with why each went and "Nothing was changed." (exit 2), in `retiredFlagRefusal`. The CLI asks it before anything else, the URL and a lonely `--groups` included, and `run()` before its own checks, so the two refuse in the same words. The CLI still parses both flags so an old command reaches the refusal, not the unknown-flag one; its flag list marks them retired.
  - What recorded a file without running it goes: the loop's branch, the empty-database guard (SMD-2237), "baselined N", and the plugin phase's `--baseline` skip. `--reapply` beside `--grant` is still refused.
  - The header says a schema with no ledger is brought under the migrator by `--reapply`. A plain run would give each file its own transaction, leaving older definitions if it stopped part-way, and would skip `--reapply`'s checks. Those checks refuse a shell of another embedding width, and one whose model 006 would re-record in `ob1_config`. The CLI no longer passes the two flags on to `run()`, having refused them.
  - A live `--reapply` over a database with no ledger makes `schema_migrations` inside its one transaction, not before its checks. A refused or failed re-run leaves no empty ledger behind, so its "Nothing was written." holds.
  - The `--reapply` usage line says "recorded or not". The refusal of a path reaching another schema's brain says public holds "no ledger of its own", not "no brain".
- `db/config.mjs`: `pinPublicFirst` loses `adopting`, which took public's `thoughts` alone as a brain for `--baseline`. `apply039`'s no-ledger remedy drops its "not --baseline" clause.
- `server-portable/preflight.ts`: the `migration ledger` row over `thoughts` with no ledger says the schema is there, that adopting it unrun was retired, and names `--reapply` over it, with the server and every worker stopped. An empty ledger beside the schema warns the same way; it was an "ok" row. With `OB1_PLUGINS` set, the remedy adds the plain run that `--reapply` leaves plugins' migrations to. The `--reapply` remedies (`REAPPLY`, 014, 023, the thought indexes) say the ledger is ahead of the schema from outside the migrations, not "adopted with --baseline". The invisible-ledger fixes drop their `--baseline` clause.
- `db/reembed.ts`: the refusal on a ledger ahead of its schema drops "(--baseline?)".
- Docs: `db/README.md` §4 becomes "A schema with no ledger", with `--reapply` as the way in, the retirement, and a note that a new migration does not paste the guard (52 files between 030 and 111 carry it). §5 and five other places follow, the engine's options among them, and so do `server-portable/README.md`, `db/cli.ts` and two comments in `brain-info.ts`.
- Suites:
  - test-upgrade [22] tests the refusals: on an empty database, over a schema with no ledger, beside `--dry-run` and `--grant`, and `--force` alone and with `--baseline`. Nothing is written in any of them. It also checks the remedy on two schemas with a thought in each: the whole schema, and one built through 007. Over the whole schema, `--reapply` from a shell of another model refuses up front and leaves no ledger table. From the brain's shell, with public off the connection's path, it applies every file, records each in public, and the thought comes through. [7] refuses it beside `--reapply`, and [23] loses its adoption case.
  - test-engines refuses the retired flags in-process as in the CLI, with no URL and beside `--groups` too. Its null-grant case uses `--reapply`.
  - test-preflight warns on an empty ledger beside the schema, and checks the plugin clause with and without `OB1_PLUGINS`.
  - test-preflight, test-schema, test-cli, test-live and test-e2e-sql follow the new wording.
- PR 1 had moved the suites' 35 fixture runs of `--baseline` to test-support's `plantLedger`, which writes the rows it wrote.

**Why.**
- The brain deploys as the compose stack alone (SMD-2288). Its migrate service runs every file on an empty database, and no deploy script or setup step called `--baseline`. The stable and canary ledgers record files they ran.
- The flag still cost a guard pasted into 52 migrations and about 200 mentions across the code, docs and suites. Preflight's ledger row also offered adoption.
- The maintainer decided on 2026-10-25 to retire it, and on 2026-10-26 that `--force` goes with it.
- It is a major: `--baseline` and `--force` are flags of a command the `ob1-migrate` image runs, so dropping them falls inside the version contract (FORK.md, "Versioning"). The bump rests on that rule's bullet.

**Held.** test-upgrade [22] and test-engines' refusal cases fail if either flag runs anything, writes a ledger or falls through to another mode. test-preflight's ledger rows pin the new wording on both sides of SMD-2237's split.

**Not taken.**
- The applied files' guards and their hints are unchanged: a changed applied file reads as drifted and stops a plain run. The canary has applied 104–112.
- `pinPublicFirst`'s `adopting` went with `--baseline`. A run over a hand-built `public.thoughts` with no ledger is still refused where the path also reaches another schema's ledger, as a plain run was before. That refusal tells it to take the other schema off the path.
- A route for a hand-built schema on pgvector below 0.8.0. `--reapply` refuses on 014's floor and a plain run stops there. The fork requires 0.8.0, and both name the upgrade.
- `--dry-run` still makes an empty ledger, which is SMD-2291's to change. Preflight now warns on one beside the schema.
- A plain run as the remedy for a schema with no ledger (the ticket's other option, and the first draft here). It gives each file its own transaction and checks nothing first (review pass 2).
