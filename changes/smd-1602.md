## Changelog

`compat/supabase-sql` answers what PostgREST answers in the five places change 77's review found it did not — a count without `head` is the total, `.single()` over several rows is `PGRST116`, `head` without a count is no rows, an upsert's conflict target is the primary key when none is named and every payload column is assigned, an `.rpc()`'s shape is what `pg_proc.proretset` declares — and an array column is read through `to_json`, so a `real[]` holding a `NULL` and a `uuid[]` arrive as PostgREST's JSON has them (SMD-1602).

## FORK

The SQL shim answers what PostgREST answers — five silent divergences closed, and an array column read as JSON so a `real[]` with a `NULL` lands and a `uuid[]` is a list (SMD-1602)

**What changed.** `compat/supabase-sql/index.ts`, in `QueryBuilder.compile()`,
`execute()` and `SupabaseSqlClient.rpc()`, with the catalog reading two more
things. A `{ count: "exact" }` select that is not `head` carries
`count(*) OVER ()` on every row of the page — the total before `LIMIT` and
`OFFSET`, lifted off the rows before the caller sees them — and, when the page
comes back empty (an offset past the end), runs the count query PostgREST runs
for `Content-Range`, the same `WHERE` without the page. `.single()` and
`.maybeSingle()` answer `PGRST116` for several rows as for none (`maybeSingle()`
differs only on none), where the first row was the answer. `{ head: true }`
with or without a count compiles to one `count(*)` query: `data: null`, the
count only when asked. An upsert's conflict target is `onConflict`'s columns,
split at their commas, or the table's primary key read from `pg_index`
(`Catalog.primaryKeyOf`, memoised per table) — a table with neither is refused
at the call, naming the option — and every payload column is assigned from
`EXCLUDED`, the target's among them, so the statement is always `DO UPDATE` and
always returns the row. `.rpc()` reads `pg_proc.proretset` beside the argument
types (`Overload.returns.set`) and shapes the answer by it when every candidate
overload agrees: a set-returning function is rows, one row of one column
included (`[{ col: v }]`), unless its rows are scalars (`RETURNS SETOF int`),
which are listed bare; a scalar function is its value; a function returning one
composite row is that row as an object. Where the candidates disagree, or the
function is unknown, the old rule stands (one row of one column is the value).
The call is aliased with the function's own name, so a scalar's one column
keeps the name the shape map keys it by.

An array column — `typcategory = 'A'`, a domain over one included — is read
through `to_json("c") AS "c"` wherever the shim renders the column: a named
select item, a `RETURNING` item, a function's declared `RETURNS TABLE` column.
A `*` on a table with an array column is spelled out from the catalog's map
that way, with `pg_class.relnatts` read as `__natts` beside the rows; `execute()`
compares it with the count the map was read at (`Catalog.nattsOf`, stored by
`readColumns`) and forgets the map when it moved, and a `42703` on a spelled-out
star — the map naming a column since dropped — forgets it too. A table without
an array column keeps `SELECT *`, and a row carrying a key the map lacks stays
the signal there, as change 77 left it.

**Why.** Each was a silent wrong answer, the failure class the shim exists to
avoid, found by SMD-1588's reading reviewer and left as change 77's "Not done":
`.select("*", { count: "exact" }).range(0, 9)` over 57 rows answered
`count === 10`; `.eq(user).eq(week).single()` over a duplicated pair answered an
arbitrary row; `.select("*", { head: true }).limit(5)` streamed the table as
`data`; an upsert with no `onConflict` targeted the payload's first key, `42P10`
whenever that key was not unique, and a one-column payload on a one-column
target rendered `DO NOTHING`, so a following `.single()` was `PGRST116` where
PostgREST returns the row; a set-returning function that happened to return one
row of one column answered `v`, and the caller's `data.length` was a string's.
The seventh, from SMD-1719's fourth pass: `PostgrestStore.logSearch` through
this shim failed with `Failed to read data` when `result_scores` carried a
`null` — not at the bind, as the ticket guessed, but on the row the insert
returns: Bun's binary array decoder refuses a `NULL` element
(`ERR_POSTGRES_NULLS_IN_ARRAY_NOT_SUPPORTED_YET`), and the shim's queries are
always parameterised, always binary; over the simple protocol the same row
decodes. The same decoder hands a `uuid[]` back as the literal text `{…}` —
`traverse_graph`'s `path` column, which SMD-1798 puts in front of a driven tool.
SMD-1798 moves six more servers onto the shim and lists this ticket as its
prerequisite, since every one of these becomes reachable by more callers.

**Held.** `compat/supabase-sql/test-compat.ts` [19], 24 assertions on a
57-row table with a `real[]`, a `uuid[]` and a compound unique index: the total
over a page, a filtered page, an empty page past the end; `single()` and
`maybeSingle()` over two rows, over one; `head` without a count, and a bad
filter under it still the database's error; an upsert resolved to the primary
key whatever the payload's key order (the SQL text), a table with none refused,
a multi-column target, a one-column payload returning its row; a set-returning
function's one row as `[{…}]`, none as `[]`, `RETURNS SETOF text` as a bare
list, a scalar still its value; `[0.9, null]` and a `uuid[]` back through a
named select and through `*`, the spelled-out star's SQL, a table without
arrays keeping `SELECT *`, a function's `uuid[]` column, and a column dropped
under the client costing one `42703` then a fresh map. [13]'s composite pin
moves from `data[0].b` to `data.b`; [18]'s star pin says the first call after
an `ADD COLUMN` lacks the column and the second has it (the table there has an
array column, so its star is spelled out), and a table without one keeps its
star. `server-portable/test-store-postgrest.ts` [11] writes its search row
through `store.logSearch` on the shim, the call that failed, instead of seeding
it by SQL. Every shim consumer on the changed shim: test-compat 205/205,
test-store-postgrest 115/115, test-tools 122/122, test-writes 281/281.

**Not taken.** Rendering every row through `to_jsonb(t)`, which would give
Postgres's spelling of a `timestamptz` (`+00:00`, microseconds) where change 73
chose `toISOString()`'s and the README promises it: a wider change than the
seven answers here, and no migrated file needs it. Retrying a select on the
decoder's error with the star spelled out, and spelling out only `RETURNING`:
two rules where one serves, and a write cannot be retried. VARIADIC arguments
through `.rpc()`, which cannot be called by name: nothing in the tree is
variadic. `ignoreDuplicates` on upsert (`DO NOTHING` asked for): one caller,
`recipes/repo-learning-coach`, on the shim already and not driven; its rows are
still refused as PostgREST refuses them, since the option is not read either
way.

**Upstream status:** not sent — the shim is the fork's.
