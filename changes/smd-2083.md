## Changelog

`integrations/rest-api`'s paging parameters (`limit`, `offset`, `page`, `per_page`) are each held to a finite integer in range before they reach SQL, so `GET /recent?offset=Infinity` (which rendered `LIMIT NaN OFFSET Infinity` and answered 500), a fractional `limit`, and a `page` past int4 no longer 500 — they clamp. A JSON body that is `null` (or any non-object) is a named 400 on every JSON route, where before a valid-JSON `null` was a 500 (SMD-2083).

## FORK

rest-api holds every paging parameter to a finite integer, and a non-object body to a 400 (SMD-2083)

**What changed.** `integrations/rest-api/index.ts`: one `intParam(value, { min,
max, default })` — `Number.isFinite`, `Math.trunc`, clamp; a missing, empty or
non-numeric value is the default, a non-finite one (Infinity, NaN, 1e400) is the
default and never rendered into SQL — replaces the `Math.min(Math.max(Number(v)
|| d, lo), hi)` idiom at every `limit`, `offset`, `page`, `per_page` and the
`/count` days window across the routes. `page` is bounded so `(page - 1) *
per_page` stays within int4, and the computed offset is clamped to `INT4_MAX` as
a belt. The four JSON body routes (`/search`, `/capture`, `PUT /thought/:id`,
`/duplicates/resolve`) now read through the existing `readJsonWithCap`, which
caps the body and refuses a non-object with `Body must be a JSON object` (400) —
so a `null` body is a named 400, not a `TypeError` the catch mistook for a 500.

`compat/supabase-sql/index.ts`: `limit()` and `range()` refuse a non-integer
argument with a named `RangeError` before any SQL is built (`requireIntArg`). It
is the backstop — a well-behaved caller clamps first — but it turns a generic
query failure into a legible one at the call site, since the compiler renders
`LIMIT`/`OFFSET` by interpolation, not a bound parameter.

**Why.** Found by SMD-2054's fourth review pass, adversarial, of the rest-api
file; all pre-existing, none a leak. `handleRecent` parsed `offset` as
`Math.max(Number(v) || 0, 0)`, so `offset=Infinity` reached the shim as
`offsetN = Infinity`, `limitN = NaN`, and Postgres saw `LIMIT NaN OFFSET
Infinity` — read as column names — and the route answered a generic 500. A
fractional `limit` survived the clamp and bound to an `INTEGER` argument; a `page`
past int4 refused at `p_offset INTEGER`; and `await req.json()` yielding `null`
threw a `TypeError` the `instanceof SyntaxError` catch did not cover.

**Held.** `bun extensions/test-writes.ts` against real Postgres (the rest-api
block), 386 assertions (from 381): `GET /recent?offset=Infinity` clamps to 0,
`?limit=2.5` truncates to 2, `POST /search` text mode `page=1e9` answers a page
(not an int4 overflow), `limit=2.5` reports an integer `per_page`, and a JSON
`null` body is a `400 Body must be a JSON object` — each a 500 on the pre-fix
file. `bun compat/supabase-sql` typecheck clean; the shim's other consumers hold
— `server-portable/test-store-postgrest.ts` 124 and `extensions/test-tools.ts`
185 against real Postgres.

## Not taken

`intParam` on the non-paging numeric fields (`min_similarity`, `importance`,
`threshold`): they are floats bound to non-INTEGER arguments and already clamp
finite, outside this ticket's paging scope. Rejecting an out-of-range `page` by
name rather than clamping: the other paging parameters clamp, so `page` clamps
too, for one shape across the routes. The `/ingest` `job_id` (`Number(jobId)`):
it is an id validated by the smart-ingest server downstream (a non-number is its
400), not a paging parameter this ticket holds.
