## Changelog

The agent runner reads a Claude Code session that was refused at startup as one that never started, where it read it as finished (SMD-4489). The runner's probes pass on Claude Code 2.1.329, the new pin.

## Record

A result before any init event ends an agent-runner session as an init failure, and the probes pass on Claude Code 2.1.329 (SMD-4489)

**Problem.** The runner had no valid probe stamp, so it could not start a real session. Claude Code's updater had pruned the pinned 2.1.319, and the worktree the last stamp named was gone. The maintainer chose 2.1.329 as the new pin. The full sweep on it passed 34 of 35 probes and wrote no stamp.

The failure was `invalid-settings`. The probe gives a session a profile whose `sandbox.enabled` is the string `"yes"`, and expects the runner's init check to end it. On 2.1.329 Claude Code refuses to start instead: no init event, one error result (`error_during_execution`, `startup_failure_reason: sandbox_required_unavailable`), and it exits. No tool ran, but `session.ts` recorded the session as ended with its result.

That ending is what `run.ts` takes for a session that finished: it never reads the result's error flag. As read there, not run: a review session refused at startup would have given an empty report, so no findings, with no note that it never ran.

**Change.**

- **`session.ts`:** a result that comes before any init event ends the session as `init`. The reason says Claude Code ended before its init event, and carries the result's subtype, its startup failure reason and its first error, each shown as untrusted text. The result's text is not taken as a report.
- **`probes-check.ts`:** a `result-first` scenario in the offline self-check, with two cases.
- **The `invalid-settings` probe is unchanged** and passes again.
- **`README.md` and `docs/agent-runner.md`:** the pin is 2.1.329, with what the probes found on it.
- **The pinned binary is the runner's own copy** (review pass 1): `~/.local/share/open-brain/agent-runner/claude/2.1.329`, as the design's decision 16 says and nothing had made. The README gives the commands.

**Verify.**

- **The sweep passes on 2.1.329.** All 35 probes pass and the stamp is written. `invalid-settings` ends as `init`, with Claude Code's own words on the failed validation as the reason (caught: run-it).
- **The new cases have teeth.** `probes.ts --self-check` passes 314 cases, from 312. Without the `session.ts` rule both new cases fail (caught: mutant).

**The probe stamp.** `session.ts` is hashed into it. The stamp written on 2026-11-20 is for this branch's `session.ts`, the runner's copy of Claude Code 2.1.329 and the worktree the sweep ran from; a run from another checkout needs a sweep of its own.

**Review pass 1.**

- The first sweep probed the binary in `~/.local/share/claude/versions`, the directory the updater prunes and 2.1.319 was lost from. The stamp names the binary's path, so it would have died the same way. The binary was copied to the runner's directory and the sweep run again on the copy: 35 of 35 (caught: cold-read).
- The stamp's install is a working worktree that changes branch with each task. The README now says the install should be a checkout that stays on one commit; making one is the maintainer's, after this merges (caught: cold-read).
- `session.ts`'s header said a settings file that fails validation is ignored without a word, and did not tell the new rule. It does now, and the sweep above ran after that edit (caught: cold-read).
- The README said the other probes' notes read as on 2.1.319. The 2.1.319 records kept each probe's pass, not its notes, so it now gives 2.1.329's notes and says they are not compared (caught: cold-read).
- The brief probe, the one real-model session, was run on 2.1.329. The first try reached no model: the API answered 401 to the runner's Anthropic key, at no cost. With the key the maintainer then installed it passes, in 17 turns for $0.21. The guard refused three of its sixteen calls, each for a command's shape and none for a tool input it didn't know (caught: run-it).

**Not done here.** A result with an error flag after a normal init still reads as a finished session. The brief probe showed one: the session whose key the API refused ended with the result `success`, its error flag set, and "Invalid API key" as its report. The comments in `guard.ts` and `profile.ts` still name 2.1.319 as where their facts were measured: both files are hashed, and the facts were not re-measured.
