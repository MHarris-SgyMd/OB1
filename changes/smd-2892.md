## Changelog

An embedding provider that refuses the brain's call now answers the caller with a coded refusal, `EMBEDDING_PROVIDER_ERROR`, where it reached the caller raw. Before, a provider refusing the brain's key (401), a model it does not serve (404), a request it refuses (400) or a 200 whose body is not JSON failed a search with `FAILED` (500) carrying the provider's body, and a capture with the store's `STORE_UNAVAILABLE`, retryable. An edit whose provider did not answer failed the same way. The refusal names the provider's word (`provider_401`, `provider_body`, `provider_unreachable` …), its status and the setting to check (`OB1_LLM_BASE_URL`); its text names the masked endpoint, the key or model to check and the provider's own words, to a key that can read. It is final on the provider's other answers and retryable while the provider does not answer, `providerDown`'s rule. Over REST it is a 503, with `Retry-After` when retryable. A plugin answers it as `422 CORE_REFUSED`. The session hook keeps a capture refused so under `pending/`, rather than in `dead/` (SMD-2892).
**Upgrading:** pull the session hook (1.7.4) with the server: an older hook reads the code as a final refusal and files the summary in `dead/`. A client keying on capture's `STORE_UNAVAILABLE` for a provider's refusal reads `EMBEDDING_PROVIDER_ERROR` instead.

## Record

An embedding provider's refusal is a coded refusal, not the provider's raw error (SMD-2892)

Measured 2026-11-12 on main `8e16a109`, during SMD-2690's Verify, with an embeddings stub answering `401 invalid_api_key`:
- `search_thoughts` answered `500 FAILED`, its message the provider's body under the base it was sent to;
- `capture_thought` answered `503 STORE_UNAVAILABLE`, `retryable: true`, the same message: it named the store, and no retry could help;
- the agent-memory plugin's `recall` and `writeback` answered that 500 as their own.

SMD-2888 and SMD-2891 had already turned an outage into a capture saved without its vector and a search answered by its literals. The two cases still raw were the ticket's rescope (2026-10-25): a provider error `providerDown` does not count as down, and an edit with content while the provider is down. The maintainer's call (2026-10-26): `retryable` is `providerDown`'s, so a 401 is final and a 429 retryable, until SMD-2461's one classifier takes the rule.

**What changed.**
- **`server-portable/embed.ts`:** `providerFault` reads a provider call's failure: `providerDown`'s outages, retryable; an error status that is no outage, and a 2xx whose body is not JSON, final, with the provider's status and capped words. The gate's refusal and a plain error (the width mismatch) are none of these, and stay what they were.
- **`server-portable/core/provider-refusal.ts`:** the refusal made from it. A key that can read is given the masked endpoint and the provider's words; a capture-only key neither, SMD-2284's rule for a capture's provider.
- **The three request-time callers of the embedder:**
  - a search (`search_thoughts`, `search`, `plan_context`): an outage is still answered by the query's literals; the provider's other answers refuse the search, final;
  - a capture: an outage still lands the thought without its vector; the provider's other answers refuse the capture, final;
  - an edit with content: refused retryable while the provider does not answer, final on its other answers. It is still refused whole, as before.

  Each logs the provider's words, with the endpoint, as the capture's outage line does.
- **`core/refusal.ts`:** the code, its facts the word, the status and the setting. The endpoint and the provider's words ride the text, as `EMBEDDING_PROVIDER_UNAVAILABLE`'s endpoint does: a URL is no token, and the MCP layer's guard nulls it.
- **`render.ts`:** `Error:` while the provider is away, `Refused:` otherwise, naming the endpoint (to a reader), the setting, and for a 401 or 403 the key (`OB1_LLM_API_KEY`, else `OPENROUTER_API_KEY`), for a 404 the model (`OB1_EMBEDDING_MODEL`). The session hook's prose rule for a server without codes reads the same split.
- **`rest/routes.ts`:** 503, as a refusal waiting on an operator when final; `Retry-After` when retryable. The OpenAPI document and the generated client say so.
- **The session hook (`recipes/session-capture-hook`, 1.7.4):** a capture refused `EMBEDDING_PROVIDER_ERROR` is kept under `pending/`, final or not: the summary is not at fault, and an operator's mend of the key lets it land. It goes to `dead/` after a week, as any kept payload does.

**Held.**
- `server-portable/test-e2e-sql.ts` (740 assertions), on the real server and SQL store:
  - a capture under 400, 401 and 404: refused coded and final, nothing stored, the provider's words and the setting to check in the text;
  - a capture key's 401: no endpoint and no provider words;
  - a body that is not JSON: `provider_body`;
  - an edit while the provider is down: retryable, said as an `Error:`, no runtime text; under 401, final; neither edit made;
  - `search_thoughts`, `search` and `plan_context` under 401: refused coded and final.
- `server-portable/test-rest.ts` (686): a final refusal at 503 without `Retry-After`, a retryable one with it, each body its facts.
- `server-portable/test-plugin-ports.ts` (1331): agent-memory's `recall` and `writeback` under 401 answer `422 CORE_REFUSED` naming `EMBEDDING_PROVIDER_ERROR`, final, with no provider words.
- `recipes/session-capture-hook/test-session-capture.mjs` (967): the refusal keeps the payload.
- `rest-client/test-client.ts` (204), regenerated.

**Not done.**
- SMD-2690's Verify item for SMD-1992 asked for a 502 or 503 from agent-memory. A plugin's refusal is retryable exactly when it is a 503 (`plugins/README.md`), so a final provider refusal is the plugin's `422 CORE_REFUSED`, coded, naming `EMBEDDING_PROVIDER_ERROR`.
- The chat provider's failures are not this code: capture's tagging call already lands its marker on any provider error, and a plugin's model call has `PROVIDER_REFUSED`.
- The background passes (the vector mender, re-embed, extraction) keep their own handling of a refused call.
