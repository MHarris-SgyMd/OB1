## Changelog

An embedding provider that refuses the brain's call now answers the caller with a coded refusal, `EMBEDDING_PROVIDER_ERROR`, where it reached the caller raw. Before, a provider refusing the brain's key (401), a model it does not serve (404), a request it refuses (400), a redirect, or a 200 that is not JSON failed a search with `FAILED` (500) carrying the provider's body (a 200 holding no embedding, a message naming the base and the model), and a capture with the store's `STORE_UNAVAILABLE`, retryable; an edit with new text failed with `FAILED`, whether the provider was away or refusing. The refusal's values are the provider's word (`provider_401`, `provider_body`, `provider_unreachable` …), its status, `setting` (`OB1_LLM_BASE_URL`) and `check`, the settings to look at for that status; its text says what to check, and to a key that can read the masked endpoint and the provider's own words (where a redirect points among them), which the REST core's log carries too. It is final on the provider's other answers and retryable while the provider does not answer, `providerDown`'s rule. Over REST it is a 503, with `Retry-After` when retryable; the request log and the fault panels count it as an error. agent-memory answers it as `422 CORE_REFUSED`, saying so; smart-ingest answers `422 EMBEDDING_PROVIDER_REFUSED`, failing a job while deciding, so the same text runs again once the provider is mended, and pausing one while executing, for `execute_job` after; the readwise and example webhooks answer `503 EMBEDDING_PROVIDER_REFUSED`, which the sender sends again. The session hook keeps a capture or a copied write refused so under `pending/`, rather than in `dead/`. Each holds whatever the provider's status, a 400 among them, which a hosted provider answers to every call for a setting it will not take (SMD-2892).
**Upgrading:** pull the session hook (1.7.4) *before* the server; it reads an older server as 1.7.3 did. An older hook reads the code as a final refusal: it files in `dead/` a summary refused so, the summaries it had already kept under `pending/` among them, and gives up a copied write, whose thought's later edits and delete that brain then skips. A payload filed so can be moved back from `dead/` to `pending/` within its week. A REST client sees capture's `503 STORE_UNAVAILABLE` and a search's, `plan_context`'s or an edit's `500 FAILED` become `503 EMBEDDING_PROVIDER_ERROR` when the provider refuses the call; an edit's also becomes it, with `Retry-After`, while the provider is away. The plugins' answers to such a refusal were each a `500 FAILED`: agent-memory's are now `422 CORE_REFUSED`, the readwise and example webhooks' `503 EMBEDDING_PROVIDER_REFUSED`, smart-ingest's `422 EMBEDDING_PROVIDER_REFUSED`, its job failed or paused where each item had failed. The request log's `error.type` for these is `EMBEDDING_PROVIDER_ERROR`, where it was `FAILED` or `STORE_UNAVAILABLE`. The `api` and `mcp` services run one image: recreate both.

## Record

An embedding provider's refusal is a coded refusal, not the provider's raw error (SMD-2892)

Measured 2026-11-12 on main `8e16a109`, during SMD-2690's Verify, with an embeddings stub answering `401 invalid_api_key`:
- `search_thoughts` answered `500 FAILED`, its message the provider's body under the base it was sent to;
- `capture_thought` answered `503 STORE_UNAVAILABLE`, `retryable: true`, the same message: it named the store, and no retry could help;
- the agent-memory plugin's `recall` and `writeback` answered that 500 as their own.

SMD-2888 and SMD-2891 had already turned an outage into a capture saved without its vector and a search answered by its literals. The two cases still raw were the ticket's rescope (2026-10-25): a provider error `providerDown` does not count as down, and an edit with content while the provider is down. The maintainer's call (2026-10-26): `retryable` is `providerDown`'s, so a 401 is final and a 429 retryable, until SMD-2461's one classifier takes the rule.

**What changed.**
- **`server-portable/embed.ts`:**
  - `providerFault` reads a provider call's failure: `providerDown`'s outages, retryable; an error status that is no outage, and a 2xx that is not JSON or holds no embedding, final, with the provider's status and capped words. The gate's refusal, a width mismatch and a runtime error no outage names (TLS) are none of these, and stay what they were.
  - A 200 holding no embedding is a body error (`ProviderError` of kind `body`), no longer a plain `Error`; its message, which reembed and the orchestration runner match, is the same. The vector mender holds such a row as it holds a proxy's page, an outage-shaped stop.
  - A redirect's error carries where it points as its words, so a reader's refusal still says where to set the base (SETUP.md).
- **`server-portable/core/provider-refusal.ts`:** the refusal made from it, with `check`, the settings to look at by the status (the key for a 401, 402 or 403, the model for a 404, the model and its width for a 400, 413 or 422). A key that can read is given the masked endpoint and the provider's words; a capture-only key neither, SMD-2284's rule for a capture's provider. Each log line carries the provider's words, a gateway's body among them. The words are cleaned before either: the brain's own key and anything shaped like a credential redacted (an endpoint echoing the request sends the brain's `Authorization` back), invisible characters dropped, one line, capped; the reply quotes them.
- **A 200 holding no embedding** is told by its own `error` or `message` alone, never the whole answer, which an echoing endpoint fills with the brain's own headers and which a deep nest made `JSON.stringify` throw on.
- **`refusalValue`** says a code its `FACTS` does not know as itself rather than throwing, so an older `mcp` beside a newer `api` reaches its `Refused: <code>` from here on (this release's older `mcp` still throws on this code, and answers the old retryable fault).
- **The three request-time callers of the embedder:**
  - a search (`search_thoughts`, `search`, `plan_context`): an outage is still answered by the query's literals; the provider's other answers refuse the search, final;
  - a capture: an outage still lands the thought without its vector; the provider's other answers refuse the capture, final;
  - an edit with content: refused retryable while the provider does not answer, final on its other answers. It is still refused whole, as before.

  Each logs the provider's words, with the endpoint, as the capture's outage line does.
- **`core/refusal.ts`:** the code, its facts the word, the status, the setting and `check`. The endpoint and the provider's words ride the text, as `EMBEDDING_PROVIDER_UNAVAILABLE`'s endpoint does: a URL is no token, and the MCP layer's guard nulls it.
- **`render.ts`:** `Error:` while the provider is away, `Refused:` otherwise, naming the endpoint (to a reader), the setting, and what to check by the status: for a 401 or 403 the key (`OB1_LLM_API_KEY`, else `OPENROUTER_API_KEY`), for a 404 the model (`OB1_EMBEDDING_MODEL`), for a redirect where it points, for a 402 the key's account credit, for a 400, 413 or 422 a setting sent with it or the text, for a body a proxy or gateway. The session hook's prose rule for a server without codes reads the same split.
- **`rest/routes.ts`:** 503, as a refusal waiting on an operator when final; `Retry-After` when retryable. The OpenAPI document and the generated client say so.
- **`telemetry.ts`:** the code is a fault's: its request line is `error` (ERROR) and `error.type` on the duration histogram, as the thrown provider error was, so the fault panels keep a refused key. Both doors' tool spans end it as `error` too (the MCP server's `ended`, the REST core's `traced`).
- **Capture** answers the refusal as soon as the provider refuses, not after the tags' and the priority's calls beside it, which run on as they did before.
- **The provider's health** (`brain_info`, the log) says a capture, a search or an edit is refused, not a capture alone.
- **`docs/01-getting-started.md`:** a troubleshooting entry for the refusal, apart from the brain key's own 401.
- **The session hook (`recipes/session-capture-hook`, 1.7.4):** a capture refused `EMBEDDING_PROVIDER_ERROR`, and a write copied to another brain refused so, is kept under `pending/`, final or not and whatever the provider's status: an operator's mend lets it land. It goes to `dead/` after a week, as any kept payload does. The provider's own words saying "metadata" no longer mend the capture's metadata.
- **The plugins:**
  - smart-ingest: the provider refusing the call while deciding fails the job once, `422 EMBEDDING_PROVIDER_REFUSED` with its `reason`, `provider_status`, `setting` and `check`, where each item failed and the job answered complete, holding the text; while executing it pauses the job, a dry run's again with its items ready, where each item failed and the job ended complete. Named apart from `EXTRACTION_FAILED`'s `refused: PROVIDER_REFUSED`, the chat model's refusal;
  - readwise and example: a delivery whose capture the provider refuses answers `503 EMBEDDING_PROVIDER_REFUSED`, which a sender sends again, where it answered a final 422;
  - agent-memory: `422 CORE_REFUSED`, as any final core refusal, its message saying it is the embedding provider's.
