## Changelog

An embedding provider that refuses the brain's call now answers the caller with a coded refusal, `EMBEDDING_PROVIDER_ERROR`, where it reached the caller raw. Before, a provider refusing the brain's key (401), a model it does not serve (404), a request it refuses (400), a redirect, or a 200 that is not JSON or holds no embedding failed a search with `FAILED` (500) carrying the provider's body, and a capture with the store's `STORE_UNAVAILABLE`, retryable; an edit with new text failed with `FAILED`, whether the provider was away or refusing. The refusal names the provider's word (`provider_401`, `provider_body`, `provider_unreachable` …), its status and the setting to check (`OB1_LLM_BASE_URL`); its text names the masked endpoint, what to check and the provider's own words (where a redirect points among them), to a key that can read. It is final on the provider's other answers and retryable while the provider does not answer, `providerDown`'s rule. Over REST it is a 503, with `Retry-After` when retryable; the request log and the fault panels count it as an error. agent-memory answers it as `422 CORE_REFUSED`; smart-ingest answers `422 PROVIDER_REFUSED`, failing a job while deciding, so the same text runs again once the provider is mended, and pausing one while executing, for `execute_job` after; the readwise and example webhooks answer `503 PROVIDER_REFUSED`, which the sender sends again. The session hook keeps a capture or a copied write refused so under `pending/`, rather than in `dead/`, unless its status (400, 413, 422) may mean the text's own (SMD-2892).
**Upgrading:** pull the session hook (1.7.4) with the server: an older hook reads the code as a final refusal and files the summary, or a copied write, in `dead/`. A REST client sees capture's `503 STORE_UNAVAILABLE`, a search's or `plan_context`'s `500 FAILED`, and an edit's `500 FAILED` become `503 EMBEDDING_PROVIDER_ERROR` for a provider's refusal, and an edit's become it, with `Retry-After`, while the provider is away.

## Record

An embedding provider's refusal is a coded refusal, not the provider's raw error (SMD-2892)

Measured 2026-11-12 on main `8e16a109`, during SMD-2690's Verify, with an embeddings stub answering `401 invalid_api_key`:
- `search_thoughts` answered `500 FAILED`, its message the provider's body under the base it was sent to;
- `capture_thought` answered `503 STORE_UNAVAILABLE`, `retryable: true`, the same message: it named the store, and no retry could help;
- the agent-memory plugin's `recall` and `writeback` answered that 500 as their own.

SMD-2888 and SMD-2891 had already turned an outage into a capture saved without its vector and a search answered by its literals. The two cases still raw were the ticket's rescope (2026-10-25): a provider error `providerDown` does not count as down, and an edit with content while the provider is down. The maintainer's call (2026-10-26): `retryable` is `providerDown`'s, so a 401 is final and a 429 retryable, until SMD-2461's one classifier takes the rule.

**What changed.**
- **`server-portable/embed.ts`:**
  - `providerFault` reads a provider call's failure: `providerDown`'s outages, retryable; an error status that is no outage, and a 2xx that is not JSON or holds no embedding, final, with the provider's status and capped words. The gate's refusal, a width mismatch and a runtime error no outage names (TLS) are none of these, and stay what they were.
  - A 200 holding no embedding is a body error (`ProviderError` of kind `body`), no longer a plain `Error`; its message, which reembed and the orchestration runner match, is the same. The vector mender holds such a row as it holds a proxy's page, an outage-shaped stop.
  - A redirect's error carries where it points as its words, so a reader's refusal still says where to set the base (SETUP.md).
- **`server-portable/core/provider-refusal.ts`:** the refusal made from it. A key that can read is given the masked endpoint and the provider's words; a capture-only key neither, SMD-2284's rule for a capture's provider.
- **The three request-time callers of the embedder:**
  - a search (`search_thoughts`, `search`, `plan_context`): an outage is still answered by the query's literals; the provider's other answers refuse the search, final;
  - a capture: an outage still lands the thought without its vector; the provider's other answers refuse the capture, final;
  - an edit with content: refused retryable while the provider does not answer, final on its other answers. It is still refused whole, as before.

  Each logs the provider's words, with the endpoint, as the capture's outage line does.
- **`core/refusal.ts`:** the code, its facts the word, the status and the setting. The endpoint and the provider's words ride the text, as `EMBEDDING_PROVIDER_UNAVAILABLE`'s endpoint does: a URL is no token, and the MCP layer's guard nulls it.
- **`render.ts`:** `Error:` while the provider is away, `Refused:` otherwise, naming the endpoint (to a reader), the setting, and what to check by the status: for a 401 or 403 the key (`OB1_LLM_API_KEY`, else `OPENROUTER_API_KEY`), for a 404 the model (`OB1_EMBEDDING_MODEL`), for a redirect where it points, for a 400, 413 or 422 the text or a setting sent with it, for a body a proxy or gateway. The session hook's prose rule for a server without codes reads the same split.
- **`rest/routes.ts`:** 503, as a refusal waiting on an operator when final; `Retry-After` when retryable. The OpenAPI document and the generated client say so.
- **`telemetry.ts`:** the code is a fault's: its request line is `error` (ERROR) and `error.type` on the duration histogram, as the thrown provider error was, so the fault panels keep a refused key. Both doors' tool spans end it as `error` too (the MCP server's `ended`, the REST core's `traced`).
- **Capture** answers the refusal as soon as the provider refuses, not after the tags' and the priority's calls beside it, which run on as they did before.
- **The session hook (`recipes/session-capture-hook`, 1.7.4):** a capture refused `EMBEDDING_PROVIDER_ERROR`, and a write copied to another brain refused so, is kept under `pending/`, final or not: an operator's mend of the key lets it land. It goes to `dead/` after a week, as any kept payload does. One with a 400, 413 or 422, which may be the text's own, is final as any refusal; kept, a copy would hold its queue. The provider's own words saying "metadata" no longer mend the capture's metadata.
- **The plugins:**
  - smart-ingest: the provider refusing its key, model or address while deciding fails the job once, `422 PROVIDER_REFUSED` with its `reason`, `provider_status` and `setting`, where each item failed and the job answered complete, holding the text; while executing it pauses the job, a dry run's again with its items ready, `422 PROVIDER_REFUSED`, where each item failed and the job ended complete; a 400, 413 or 422 fails that item alone;
  - readwise and example: a delivery whose capture the provider refuses for its key, model or address answers `503 PROVIDER_REFUSED`, which a sender sends again, where it answered a final 422; a 400, 413 or 422 stays `422 CORE_REFUSED`;
  - agent-memory: `422 CORE_REFUSED`, as any final core refusal.
