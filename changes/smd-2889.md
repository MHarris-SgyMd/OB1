## Changelog

A thought saved without a vector — captured while the model provider was down, refused by the egress gate, or imported bare — now gets its vector by itself: the servers embed such thoughts once the provider answers and the gate allows the call (a policy change takes a restart), 8 a tick per server (`OB1_VECTOR_MEND_INTERVAL`, every 60 seconds unless set; `off` for none). Before, only re-capturing the same text or a hand-run `db/reembed.ts` gave one a vector, and a session summary saved during an outage stayed out of semantic search. The cost lands as the rows do: a backlog after an outage, or an import written bare for a later `db/reembed.ts`, is embedded on the configured provider, a hosted one's bill included, unless the knob is off. `brain_info` and a keyed `/health` say how many thoughts wait for a vector, and preflight says the knob (SMD-2889).

## FORK

The servers give a thought saved without a vector its vector, by themselves — the vector mender (SMD-2889)

**What changed.**
- **`core/mend.ts` (new), `mendOnce`:** one tick, under the store's leader lock (`store.mendLock`: `pg_try_advisory_lock(hashtext('ob1:vector-mender'))` on a client of one connection of its own, beyond `OB1_PG_POOL`; another holder makes the tick a skip; a release the database says did not let go, on a session still open, is reported).
  - It reads thoughts with `embedding IS NULL` in id order from a cursor (`store.listVectorless`; the SQL store adds the door of each row's capture event, PostgREST none), passing over rows the gate refuses and rows held, until it has embedded 8 rows (a long row is a call per window and one for the whole, plus a blurb call per window under `OB1_CHUNK_CONTEXT`), read 256, or reached the end. A policy that refuses every call to the embedding endpoint makes it idle.
  - Each row is embedded by the capture's path and written through `update_thought` with the text and the stamp it read, actor `vector-mender` through the server's door, marked `background`, with the egress decision. 088's presence-flip arm makes that one `update` event; its same-text arm keeps the row's stamp, so who wrote the text and its trust stand. The event moves `updated_at`.
  - **The provider away, decided by two calls.** An outage (`providerDown`) makes its row pending, and the next call decides: answered, the row failed alone (held as its own, marked `alone`, so its outages never speak for the provider again); an outage too, the provider is away (both held as an outage's, 1, 2, 4, up to 8 sweeps; the tick stops, two calls spent); no next call, alone if the provider answered this tick or the last, else away. The provider answering after an outage lets the outage's holds go at once; answering the tick right after the stop marks the rows that stopped it `alone`. Only an HTTP status is an answer: an egress refusal or a body that is not JSON is the row's failure. A sweep's end drops the holds of rows no longer waiting, and with no outage's hold still running the outage is over.
  - **A failure** (a 4xx, the wrong width, a write the database refuses with a SQLSTATE) holds the row for 1, 2, 4 … 32 sweeps. A write that cannot reach the database (no SQLSTATE, or class 08, 53, 57, 58) throws out of the tick. A raced write (`STALE_READ`, `NOT_FOUND`, `DUPLICATE_CONTENT`) is left for the next sweep.
- **The egress gate asks what the row's writer asked.** A row a key captured through a server (its capture's `origin` `open-brain` or `open-brain-api`) is asked as the capture was — the key (the DB-stamped `actor_name`) and the text — and as a pass asks of a row, its metadata too; sent only when both allow, so a claimed `source:` opens nothing (SMD-1941) and a `source:`/`type:`/`topic:` deny term keeps it home. Any other row (an import, board-sync's, a raw write) is asked as `db/reembed.ts` asks — metadata and text, no actor — and again with its `actor_name`, so a deny term naming it keeps it home and a label opens nothing. Blurbs refused for a row are left off; its windows go in bare, as a capture's do.
- **`startVectorMender`:** the first tick 5 s after start, then one every interval, never two at once, on an unref'd timer clamped below `setTimeout`'s ceiling. A tick that throws doubles the wait, up to 32 times. Over the PostgREST store it starts nothing, said once. It logs a mend (and how many got the head window's vector or bare windows), the outage once and its end, a sweep's leftovers when they change, a throwing tick when its words change, an idle policy once, and a kept lock once.
- **`index.ts` and `api.ts`** both start it under `OB1_VECTOR_MEND_INTERVAL` (whole seconds 1 to 86400, `0` or `off` for none; a value that does not read is the default, said) and stop it in the drain's every-path hook. The REST core runs one so the mender outlives `/mcp` moving to `mcp-server/` (SMD-2287). The knob is in `root.ts`'s `Env`, both compose files, `.env.example`, and a preflight row when set; preflight's egress rows follow it.
- **`db/sleep.ts`:** the quiet check and its `--dry-run` twin read past audit events marked `background`, which only the server writes.
- **`brain-info.ts`:** `vectorless` (a guarded `count(*) … WHERE embedding IS NULL`) — `brain_info`'s `Vectors` row, keyed `/health`'s `database.vectorless`.
- **Replies (`render.ts`):** the no-vector notes say the server embeds the thought by itself once the provider answers, or once the egress policy allows the call (a changed policy takes a restart) — the clause SMD-2888 promised. A key that cannot read is told no endpoint.
- **Docs:** server-portable/README.md "The vector mender"; SETUP.md; docs/01-getting-started.md; docs/03-faq.md; deploy/README.md; db/README.md; `.env.example`; the adaptive-capture recipe.

**Why.** Since SMD-2888 a capture made during an outage lands without its vector, and egress-refused captures always have. Nothing gave such a row its vector but a re-capture or a hand-run `db/reembed.ts`, which no service runs. The session hook no longer re-sends an outage capture (a capture-only key cannot see a delete), so its summaries stayed out of semantic search — why this was to merge before the next release cut.

**Where it runs, and why.** On the servers, on a timer, under a leader lock: a server is the one process every brain runs, the dogfood's included, and holds the capture's embedder, the egress policy and the store. Both run one, so it survives SMD-2287; the lock keeps two processes or replicas from embedding a row twice (pass 1 measured 60 of 60 twice without it). Each server keeps its own cursor, holds and log.

**Held.**
- **The egress policy is read at start,** so a refused row is mended after the restart that allows it.
- **The replies say the server embeds the row by itself even where no mender runs** — `OB1_VECTOR_MEND_INTERVAL=off`, Cloudflare Workers, the PostgREST store on Bun: the process that answers cannot tell.
- **The only row waiting through an outage** has no other row's answer to show the provider back, so it waits out its hold, up to 8 sweeps (about 10 intervals). A text the provider fails alone, with nothing else waiting, reads as the provider away: one call per hold, the holds growing to 8 sweeps.
- **An outage of exactly one tick** marks the two rows that stopped it `alone`: their later outages count as their own, so they wait out their own holds after the provider returns.
- **The door and actor the mender trusts** are what the capture's session declared (046, 050): a capture-group database role can name a server's door and a key, as it can name any actor; such roles are trusted as the servers are.
- **The mender logs a provider's fault as its status or kind,** never its body, which can echo the text.
- **A held row is the process's:** a restart tries every row again; each server tries it on its own schedule.
- **`reembed.ts` beside the mender:** neither writes over the other's newer text, but a row both reach may be embedded and written twice.
- **The lock is a session lock:** behind a pooler in statement or transaction mode it is not let go where it was taken, said once. If its connection drops mid-tick, another server takes it and both work that tick's rows: each written once, some embedded twice.
- **One window's failed call fails a long row's embedding,** as on a capture, so the row is held and tried again.

**Not taken.**
- **A sleep-scheduler step:** absent on a brain without `--profile sleep`; the scheduler hard-codes its two passes in four places.
- **`reembed.ts --vectorless`:** its pool already takes these rows; what was missing was something that runs it.
- **The claim table:** `embedding IS NULL` is the state; a claim row needs the worker grant group the server's role lacks, and a failed claim waits for `--retry-failed`, a hand step.
- **A partial index on `embedding IS NULL`:** it needs a migration; the read is a sequential scan at 0.9 ms over stable's 2,023 thoughts and a pkey range scan per page at 100,000 (1.5–4.7 ms). Left to the scale work (SMD-2754, SMD-2758).
