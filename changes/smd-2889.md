## Changelog

A thought saved without a vector — captured while the model provider was down, or refused by the egress gate — now gets its vector by itself: the MCP server embeds such thoughts once the provider answers and the gate allows the call, a few a minute (`OB1_VECTOR_MEND_INTERVAL`, 60 seconds unless set; `off` for none). Before, only re-capturing the same text or a hand-run `db/reembed.ts` gave one a vector, and a session summary saved during an outage stayed out of semantic search. `brain_info` and a keyed `/health` say how many thoughts wait for a vector (SMD-2889).

## FORK

The server gives a thought saved without a vector its vector, by itself — the vector mender (SMD-2889)

**What changed.**
- **`core/mend.ts` (new), the vector mender:**
  - **`mendOnce`:** one tick. It reads up to 8 thoughts with `embedding IS NULL` in id order from a cursor (`store.listVectorless`, both stores), embeds each by the capture's path (`ctx.embedder.embedCapture`: windows, blurbs and the head-window fallback), and writes it through `update_thought` with the text and the stamp it read, actor `vector-mender` through the server's door.
    - 088's presence-flip arm makes that one `update` event, and its same-text arm keeps the row's stamp, so who wrote the text and its trust stand.
    - **An outage** (`providerDown`) stops the tick at its row with the cursor held: one call a tick until the provider answers.
    - **Any other failure** (a 4xx, the wrong width) passes the row, and the next sweep tries it again.
    - **A write refused as `STALE_READ`, `NOT_FOUND` or `DUPLICATE_CONTENT`** (the row was edited, deleted or given a vector since the read) is left for the next sweep, which reads it afresh.
    - **A short page** ends the sweep, and the next tick starts over.
  - **The egress gate is asked twice**, and the text is sent only when both answers allow:
    - as the capture was asked: the key that wrote the text (the row's DB-stamped `actor_name`) and the text;
    - as a pass asks of a row: its metadata too, for the embeddings endpoint and, under `OB1_CHUNK_CONTEXT`, the chat endpoint.

    So a `source:` the caller claimed opens nothing (SMD-1941), and a `source:`/`type:`/`topic:` deny term keeps the row home, as `db/reembed.ts`'s gate does.
  - **`startVectorMender`:** the loop. The first tick comes 5 s after start, then one every interval, never two at once, on an unref'd timer.
    - A tick that mends nothing and fails a row doubles the wait, up to 32 times. A mend resets it, as does an outage alone.
    - It logs when it mends, when the counts it refuses or fails change, and on the first outage, never once per idle tick.
    - `stop()` starts no further row.
- **`index.ts`:** starts the mender at boot under `OB1_VECTOR_MEND_INTERVAL` (`mendIntervalFrom`: whole seconds, `0` or `off` for none, a value that does not read is the default and is said), and stops it in the drain's every-path hook, before the pool closes.
  - It is not a tracked call, so a stop never waits on a re-embed.
  - The REST core (`api.ts`) starts none, so a stack runs one.
  - The knob is declared in `root.ts`'s `Env` and forwarded by `deploy/compose.yaml` and `compose.tiers.yaml`, with an entry in `.env.example`.
- **`brain-info.ts`:** a guarded read, `vectorless` (`SELECT count(*) … WHERE embedding IS NULL`, with stats), so `brain_info`'s new `Vectors` row and a keyed `/health`'s `database.vectorless` say how many wait.
- **The replies (`render.ts`) and preflight:** each no-vector note says the server embeds the thought by itself once the provider answers, or once the egress policy allows the call. That covers the capture's provider-down note (the clause SMD-2888 promised), its egress-refused note in both forms, and the edit's no-vector note. Preflight's egress rows say the same. A key that cannot read is still told no endpoint.
- **Docs:**
  - server-portable/README.md: "The vector mender" paragraph, plus the knob in the optional list;
  - SETUP.md: the gate paragraph;
  - docs/01-getting-started.md: both "no vector" remedies;
  - docs/03-faq.md;
  - deploy/README.md: "no service runs it";
  - db/README.md: what `reembed.ts` is for now;
  - comments in `store.ts` and the adaptive-capture recipe.

**Why.** Since SMD-2888 a capture made during an outage lands without its vector, and egress-refused captures always have. Nothing gave such a row its vector but a re-capture or a hand-run `db/reembed.ts`, whose default pool takes these rows already but which no service runs. The session hook no longer re-sends an outage capture (a capture-only key cannot see a delete), so its summaries stayed out of semantic search until this landed. That is why this was to merge before the next release cut.

**Where it runs, and why.** On the MCP server, on a timer. It is the one process every brain runs, the dogfood's included, and it already holds the capture's embedder, the egress policy and the store.

**Not taken.**
- **A sleep-scheduler step:** absent on a brain without `--profile sleep`, and the scheduler hard-codes its two passes in four places. Also, the mender's audit events would wake its quiet check.
- **`reembed.ts --vectorless`:** its pool already takes these rows. What was missing was something that runs it.
- **The claim table:** `embedding IS NULL` is the state the mender resumes from. A claim row would need the worker grant group, which the server's documented role lacks, and a failed claim is terminal until `--retry-failed`, a hand step.
- **A leader lock across server replicas:** two menders make a duplicate provider call, never a wrong write, because the second write's stale stamp is refused.
- **A partial index on `embedding IS NULL`:** it would need a migration. The batch read is a sequential scan, measured at 0.9 ms over stable's 2,023 thoughts; a follow-up holds it for scale.

**Held.**
- **The egress policy is read at start,** so a row the gate refused is mended after the restart that allows it.
- **The replies say the server embeds the row by itself even where `OB1_VECTOR_MEND_INTERVAL=off`:** the process that answers (the REST core, the MCP server as its client) cannot tell whether a mender runs.
- **On long content one window's failed call fails the whole embedding,** as on a capture, so such a row waits for the next sweep.
- **Each mend is an audit event,** which the sleep scheduler reads as activity, once per row mended.
