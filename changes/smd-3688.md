## Changelog

`db/ci-parity.sh` runs `db/test-live.ts`'s four shards side by side, each on a Postgres of its own as Fork Checks' db-live cells are, and starts every lane once the installs are done. Before, the shards ran one after another on the shared Postgres, and the other lanes waited for the rest shard. A full run takes about 390 s on this Mac, where it took about 1,140 (SMD-3688).

## FORK

ci-parity's test-live shards side by side, every lane from the start — ~1,140 → ~390 s (SMD-3688)

**What changed.**
- **Live lanes.** Each test-live shard is a lane of its own. The script runs itself again as `--live <shard>` under a `with-postgres.sh` per shard, as its pair lane already did with `--pair`, so each shard has a Postgres of its own.
  - One Postgres per shard, not one Postgres with four databases. Roles and backends are the cluster's, and the suite makes roles and counts connections (SMD-3617), so four shards in one cluster could meet.
  - `live_rows` runs the shard's row; each row is a line of its own, which is how check 35 reads ci-parity's rows.
- **Every lane starts once the installs are done:** the four live lanes, the pair lane (test-upgrade, then test-preflight's two shards) and the database-free lane. The pair and database-free lanes used to wait for the rest shard, whose [2] edited the tracked `db/migrations/002` until SMD-3639.
- **The shared Postgres** keeps the data-layer job's database suites, test-search-path to extensions' test-tools, in CI's order. They share CI's one Postgres service too, so state one leaves behind is still caught here.
- **Reporting** is as it was: each shard prints its row in its own lane's block, in the order rest, sleep, long, extract, then the pair and database-free lanes. A lane still running when the shared Postgres's rows are done says which row it has in hand and for how long (SMD-3647). A Ctrl-C stops every lane, the live ones included.
- **Docs:** ci-parity's header and its pair lane's comment, test-live's header, db/README.md's shard lines and FORK.md now say the shards run side by side. Never two on one database, since each drops the schema.
