## Changelog

A token signed in as the operator is a principal per client: `oauth:operator+gui` for the operator GUI, `oauth:operator+<client>` for each connector reached through `/mcp`, whose id the authorization server's exchange now nests in the token's `act`. Each has its own registry row, kind and trust, jobs and revocation, and the audit row names it. **Upgrading:** on a stack running the `auth` profile, nothing that named `oauth:operator` binds a client any more: a registry ban on it refuses no one, an `OB1_EGRESS_DENY` term `actor:oauth:operator` stops refusing, and an `OB1_EGRESS_ALLOW` term stops admitting. A connector whose metadata document URL the brain cannot name (a query, `HTTPS://`, `+` or `:` in its path, over 180 characters) is refused from now on. Ban, classify and name each client instead (`set_agent_kind('oauth:operator+gui', 'operator')`) (SMD-3064).

## FORK

A token signed in as the operator is a principal per client — the GUI and each connector get their own kind, trust, jobs and revocation, and the audit row names the client (SMD-3064)

**What changed.**
- **The authorization server** (`deploy/auth/server.ts`):
  - the exchange nests the subject token's client in the exchanged token's `act`, `{sub: "mcp", act: {sub: <the connector>}}` (RFC 8693 §4.1), and refuses a subject token naming no `client_id`;
  - a client the REST core cannot name (`layout.ts` `clientNameable`) fails the client metadata validator, which the library runs on every client it loads, so it gets no authorization or refresh. The exchange refuses an `/mcp` token issued to one before the rule, within its ten minutes.

  The runner-up, `evals/auth/better-auth.ts`, nests the client too, so the proof of concept's rows hold for both.
- **The REST core** (`server-portable/oauth-token.ts`):
  - the caller is `oauth:<sub>+<client>`, the client being the token's own `client_id` (the GUI's `gui`) or, on an exchanged token, the nested connector. A service's token, whose subject is its own client, stays `oauth:<sub>`;
  - the registry digest is of the issuer, subject and client; a service's is unchanged;
  - a client is a subject's characters or an https URL of a host, an optional port and a path alone, at most 180 characters, the same rule as the authorization server's. A token naming any other client is refused as invalid, and so is a caller name over 200 characters, the `actor` filter's limit. No subject holds `+`, so no subject reads as another's client.
- **Docs:**
  - the ADR's Identity section (`docs/operator-surface-tiers.md`) records the decision and the option declined;
  - `deploy/README.md` shows classifying, revoking and upgrading per client;
  - the server and MCP READMEs, the OpenAPI bearer text and the REST client generated from it, the GUI session's comments and the proof of concept's stand-in name the new form.

**Why.** The authorization server has one account, so every token signed in through it named the subject `operator`, and the REST core made one principal of it: `oauth:operator`, one registry row and one digest. The GUI and every connector shared one kind and trust ceiling, one revocation switch and one job owner, and an exchanged token's `act` named only the MCP service, so no audit row said which connector wrote. SMD-3322's write verbs needed this settled. The maintainer chose a principal per client (2026-10-28).

**Not taken.** Egress `actor:` terms match case-insensitively (`egress.ts`), while client ids are case-sensitive, so a term naming one metadata URL also matches the same URL with a path cased differently. Only the host that serves the first can serve the second, so it stays as keys have it. Nor does the server refuse an unnameable metadata URL before fetching it (`clientIdMetadataDocument.allowFetch`): it fetches any URL it has not cached already, so the refusal after the fetch adds no exposure.

**Upgrading.** Inside the version contract: the `auth` profile is (FORK.md, "Versioning"), and a configured `OB1_EGRESS_DENY` or `OB1_EGRESS_ALLOW` term or registry ban naming `oauth:operator` stops binding, so this is a major (the next cut is 2.0.0 already). Neither dogfood brain runs the `auth` profile, so no OAuth audit rows or bans exist to carry over. A stack that runs it bans, classifies and names each client in place of `oauth:operator`; the old registry row stays, unused.
