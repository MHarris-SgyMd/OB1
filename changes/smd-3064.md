## Changelog

A token signed in as the operator is a principal per client: `oauth:operator+gui` for the operator GUI, `oauth:operator+<client>` for each connector reached through `/mcp`, whose id the authorization server's exchange now nests in the token's `act`. Each has its own registry row, kind and trust, jobs and revocation, and the audit row names it. **Upgrading:** a stack running the `auth` profile classifies the new names (`set_agent_kind('oauth:operator+gui', 'operator')`, and each connector's) in place of `oauth:operator`, and an egress term naming `actor:oauth:operator` names the client instead (SMD-3064).

## FORK

A token signed in as the operator is a principal per client — the GUI and each connector get their own kind, trust, jobs and revocation, and the audit row names the client (SMD-3064)

**Why.** The authorization server has one account, so every token signed in through it named the subject `operator`, and the REST core made one principal of it: `oauth:operator`, one registry row and one digest. So the GUI and every connector shared one kind and trust ceiling, one revocation switch and one job owner. An exchanged token's `act` named only the MCP service, so no audit row said which connector wrote. SMD-3322's write verbs needed this settled first. The maintainer chose a principal per client (2026-10-28) over one principal with a kind and revocation per nested actor, which would have built a second registry beside the first.

**What changed.**
- **The authorization server** (`deploy/auth/server.ts`): the exchange refuses a subject token that names no `client_id` and nests that client in the exchanged token's `act`: `{sub: "mcp", act: {sub: <the connector>}}` (RFC 8693 §4.1). The runner-up, `evals/auth/better-auth.ts`, does the same, so the proof of concept's rows hold for both.
- **The REST core** (`server-portable/oauth-token.ts`):
  - The caller is `oauth:<sub>+<client>`. The client is the token's own `client_id` (the GUI's `gui`), or on an exchanged token the nested connector. A service's token, whose subject is its own client, stays `oauth:<sub>`.
  - The registry digest is of the issuer, subject and client. A service's is unchanged.
  - A client is a subject's characters or a metadata document's https URL with a path, at most 180 characters, so the name fits the 200-character `actor` filter. Anything else is refused as an invalid token: no `client_id`, a query, a comma, credentials, an exchanged token with no nested client, or `act` nested three deep.
  - No subject holds `+`, so no subject reads as another's client.
- **The ADR's Identity section** (`docs/operator-surface-tiers.md`, Work 3) records the decision and why the other way was declined. `deploy/README.md` shows how to classify and revoke per client. The server and MCP READMEs, the OpenAPI bearer text and the GUI session's comments name the new form.

**Tests.**
- `server-portable/test-rest.ts` [5d]:
  - the GUI's token is `oauth:operator+gui`, with its own digest;
  - a metadata document's URL is taken, the longest one included;
  - two connectors through one MCP service are two principals;
  - a service is named and digested as before;
  - each malformed client above is refused.
- `server-portable/test-rest-sql.ts` [6c], on Postgres:
  - two connectors and the GUI each write an audit row naming its own client, with its own registry row (Verify 1);
  - a connector classified `agent` writes at agent trust while the GUI writes at operator trust (Verify 3);
  - revoking one connector refuses it, while the other connector and the GUI go on.
- `mcp-server/test-mcp.ts`: the stand-in authorization server nests the connector, and a capture runs as `oauth:operator+connector-w`.
- **CI**, the full stack's "REST core accepts the authorization server's tokens" step: a third sign-in registers a second write connector. Each connector's capture's audit row names `oauth:operator+<its client>` with `oauth:mcp` as `act`; that is Verify 1 against the real authorization server. `restart-check.ts --tokens` prints the client it registered. The GUI's smoke expects `oauth:operator+gui`, and the proof of concept's X2 expects the nested client.
- **Rehearsed** on a fresh scratch stack: the CI step as written, its port moved off the dogfood stack's. It passed. A REST core rebuilt with the old one-name rule fails it at whoami. The first rehearsal caught the step's own mistake: both connectors captured the same text, and the brain answered the second with the first's thought and audit row. Each connector now captures its own text.
- **Proof of concept** (`bun eval-auth.ts --verify`): oidc-provider passes 36/36 checks and Better Auth 32/32, X2 showing the nested client (a metadata document's URL). With the nesting dropped from `server.ts`, only X2 fails.
- SMD-3064's Verify 2 points at SMD-3307's page of grants, which this leaves as it was.

**Upgrading.** Inside the version contract? No: no URL, route, port, setting or flag changes. Neither dogfood brain runs the `auth` profile, so no OAuth audit rows exist to carry over. A stack that runs it and classified `oauth:operator` classifies the new names instead; the old row stays in the registry, unused.
