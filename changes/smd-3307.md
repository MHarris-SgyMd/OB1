## Changelog

On a stack configured with the authorization server (`COMPOSE_PROFILES` naming `auth`), the operator GUI at `/dashboard` signs the operator in through it, by code with PKCE, as its `gui` client: the password and the consent at the AS, then every page under a token the GUI holds and renews itself, never in the browser. Sign-out revokes it. Key sign-in stays off on the public origin (SMD-3307).

## FORK

The operator GUI signs in through the authorization server — code with PKCE, tokens renewed server-side (SMD-3307)

**What changed in PR 1** (the plan's three, SMD-3307's 2026-10-25 comment: sign-in, break-glass, the page of grants).
- **`deploy/auth/server.ts`:** the `gui` client takes `refresh_token` beside `authorization_code` (the maintainer's choice). It asks `offline_access` with `prompt=login consent` — the consent the only way oidc-provider grants it, the login so a sign-out of the GUI is one, and its refresh tokens rotate under SMD-2286's policy.
- **`deploy/compose.yaml`:** `app` gets `OB1_AUTH_SECRET_GUI`, its one secret; check 28's `APP_SERVICE` holds it whole. `serve.ts` warns at the start when the stack is configured and the GUI has no secret or no sound origin.
- **`dashboard/src/lib/server/oauth.ts`** (new): the settings (`edgeSettings`' origin, the secret), the authorization request (S256, `resource=<origin>/api`, `brain:write offline_access`, `prompt=login consent`: the password every time, so a sign-out of the GUI is one), the PKCE verifier derived from the state by a per-process HMAC (a start holds nothing), the code's exchange, a refresh and a revocation as `gui` on the mesh (`http://auth.ob1.internal.:3000/auth`; a 429 is no answer, not a refusal), and `createRenewer` — a session's token renewed a minute before it lapses, from the session as it is now, once per session at a time, a refused renewal ending the session and an unanswered one leaving it.
- **`session.ts`:** a session holds a key or the AS's tokens (`Credential`), read live (`liveTokens`) and written back on renewal (`storeTokens`); `openSession` hands back the tokens of sessions it evicted, and `closeSession` what it held, for the AS to revoke (`revokeEnded`, in the background). An answer is taken once (`spendSignIn`); the sign-in's state rides a cookie on `/dashboard/auth` alone (no login CSRF).
- **`routes/auth/start`** (a POST: no preload starts one; the AS down, back to the page) and **`routes/auth/callback`**: the answer taken with this browser's state (a stray callback leaves the cookie alone) and once, the code traded, whoami under the token (`oauth:operator`), a session opened; every failure back to `/signin?refused=<word>`, said in the GUI's own words (`Object.hasOwn`), never the AS's; tokens a failed sign-in got are revoked.
- **The sign-in page's states** (ADR decision 16): not configured, the key; configured and the AS answering, its button; not answering, "unavailable", pointing to break-glass (PR 2); no secret or origin, said as the operator's to fix. **`rest.ts`** sends a session's key or renewed token, an AS its probe finds down failing at once; **sign-out** revokes the refresh token, not waiting on a down AS.
- **`dashboard/test-oauth.ts`** (new, the portable-server job; `db/ci-parity.sh`'s line) and **`dashboard/smoke-oauth.ts`** (new, deploy-stack-auth's new step, after `restart-check.ts --gui-refresh`, new too). Docs: `dashboard/README.md`, `SETUP.md` step 5, `deploy/README.md`'s AS section, `.env.example`.

**Why.** A configured stack's GUI signed no one in: key sign-in is off on its public origin (ADR decision 16), and nothing else was built. SMD-2286 moved the GUI's sign-in here with its only consumer.

**Held.**
- **`smoke-oauth.ts`** in deploy-stack-auth, through the proxy against the real AS: the start's authorize request (`gui`, S256, no verifier, `prompt=login consent`, `offline_access`, the REST core), the sign-in cookie's path; the password and consent back to the callback; a session cookie on `/dashboard`; the views under the token, the who line `oauth:operator`; nothing JWT-shaped in any page, header, `__data.json`, script or cookie, the GUI's one cookie the session id (the Verify line); a stray callback mid-sign-in leaving its cookie; a replayed callback refused (with its sign-in cookie put back too: the answer is spent), a forged one, and a real answer opened in another browser; sign-out, and the next sign-in in that browser asking the password; a denied consent; an unknown refusal word. Then CI counts the AS's refresh tokens of `gui`: none, so sign-out revoked.
- **`restart-check.ts --gui-refresh`** in the same step: the code gives `gui` a refresh token, a refresh rotates it, and revoked it is refused.
- **`test-oauth.ts`**, 36 assertions: settings, the request, the exchange, refresh and revocation forms (the secret form-encoded in Basic), each way the AS answers, the verifier from the state within its window, a 429 as no answer, the calls' timeout, `revokeEnded`, and the renewal's single flight, the call after it reading the live session, refusal and silence.
- **deploy-stack's configured step:** with the AS not running, the page says sign-in is unavailable, and a key's post is still the GUI's 403.

**Measured after.**
- Scratch stack `ob1-3307` (podman, `COMPOSE_PROFILES=auth`, the origin `https://brain.example.test`, the secrets by `provision.ts`'s `initSecrets`), in-network through the proxy: `smoke-oauth.ts` 22 of 22; `restart-check.ts --gui-refresh` held; `test-oauth.ts` 36 of 36. With `--renewal`, 620 s on, past the first access token's expiry, two pages at once and the overview still rendered: the GUI renewed unseen. After every sign-in signed out, the AS's store held no refresh token of `gui` (CI's count). The key path, `app` recreated unconfigured on the same stack: the full `smoke.ts` 87 of 87. With the AS stopped, the page says unavailable and a key's post is the GUI's 403. Five mutants, each caught: the `gui` client without the refresh grant (the callback refused, `--gui-refresh` fails), the callback without the cookie binding, a verifier taken twice, the sign-in cookie on `/dashboard`, sign-out without the revocation (CI's count).

**Not taken.**
- **A silent re-authorize** in place of the refresh token: a redirect mid-page, and a form post landing on an expired token lost (the maintainer chose the refresh token).
- **A read-only sign-in:** the operator's token asks `brain:write`, as the one account holds every scope; a read key still signs in on an unconfigured stack.
- **The AS's end-session at sign-out** in place of `prompt=login`: the AS has RP-initiated logout off; asking the password every time does the same for the next visitor. **A lost refresh answer:** if the AS spent the token and its answer was lost, the next try is a reuse it refuses, ending the session — rotation's price. **Revoking at a GUI restart:** its sessions are in its memory, gone before it could (review pass 1).
