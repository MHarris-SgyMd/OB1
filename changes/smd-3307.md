## Changelog

On a stack configured with the authorization server (`COMPOSE_PROFILES` naming `auth`), the operator GUI at `/dashboard` signs the operator in through it, by code with PKCE, as its `gui` client: the password and the consent at the AS, then every page under a token the GUI holds and renews itself, never in the browser. Sign-out revokes it. Key sign-in stays off on the public origin. **Upgrading** a configured stack: `compose up -d --build --wait` from the stack's checkout, `auth` in `COMPOSE_PROFILES` — it rebuilds the server image `app` runs (a plain `up` recreates `app` on the old one, whose GUI signs no one in) and the authorization server, whose `gui` client now takes refresh tokens; it signs everyone out of the GUI (SMD-3307).

## FORK

**What changed in PR 1** (the plan's three, SMD-3307's 2026-10-25 comment: sign-in, break-glass, the page of grants).
- **`deploy/auth/server.ts`:** the `gui` client takes `refresh_token` beside `authorization_code` (the maintainer's choice). It asks `offline_access` with `prompt=login consent` — the consent the only way oidc-provider grants it, the login so a sign-out of the GUI is one, and its refresh tokens rotate under SMD-2286's policy. The interaction policy asks a `gui` client the password on every authorization whatever its request says (a URL's `prompt` is the browser's to change), its ID token always carries `auth_time` (`require_auth_time`), the password's own time (the login result's `ts`), and each GUI consent is a grant of its own made from its request alone, so a replaced session's revocation, which ends its whole grant, ends no live one, even landing while the consent page is up (review passes 4 and 5); `prompt=none` is answered `login_required`.
- **`deploy/compose.yaml`:** `app` gets `OB1_AUTH_SECRET_GUI`, its one secret; check 28's `APP_SERVICE` holds it whole. `serve.ts` warns at the start when the stack is configured and the GUI has no secret or no sound origin.
- **`dashboard/src/lib/server/oauth.ts`** (new): the settings (`edgeSettings`' origin, the secret), the authorization request (S256, `resource=<origin>/api`, `brain:write offline_access`, `prompt=login consent`: the password every time, so a sign-out of the GUI is one), the state and the PKCE verifier both derived, by a per-process HMAC, from a binding in the httpOnly sign-in cookie that no URL carries (a start holds nothing, and a callback URL seen elsewhere completes no sign-in this browser started), the code's exchange (with the ID token's `auth_time`, which must not precede the sign-in's start: a URL whose `prompt=login` was dropped gets no password-less sign-in from the AS's day-long session), a refresh and a revocation as `gui` on the mesh (`http://auth.ob1.internal.:3000/auth`; a 429 is no answer, not a refusal), and `createRenewer` — a session's token renewed a minute before it lapses, from the session as it is now, once per session at a time, a refused renewal ending the session and an unanswered one leaving it; and `createRevoker` — every refresh token no one holds revoked, one at a time, one the AS does not answer tried again every 30 s while it is down (14 days, a thousand at most).
- **`session.ts`:** a session holds a key or the AS's tokens (`Credential`), read live (`liveTokens`) and written back on renewal (`storeTokens`); every way a token session leaves the store — signed out, evicted, replaced, found expired, refused by the REST core — and a renewal stored after its session ended go through one door, `onTokensEnded`, which `hooks.server.ts` hands the revoker; no call site has an ending to remember. An answer is taken once among the last thousand (`spendSignIn`), the AS's single-use code past them; the binding rides a cookie on `/dashboard/auth` alone.
- **`routes/auth/start`** (a POST: no preload starts one; the AS down, back to the page) and **`routes/auth/callback`**: the answer taken with this browser's state (a stray callback leaves the cookie alone) and once, the code traded, the password's time checked, whoami under the token (`oauth:operator`), a session opened; start and sign-out also refuse a post from another origin with no body, which SvelteKit's own check passes; every failure back to `/signin?refused=<word>`, said in the GUI's own words (`Object.hasOwn`), never the AS's; tokens a failed sign-in got are revoked.
- **The sign-in page's states** (ADR decision 16): not configured, the key; configured and the AS answering, its button; not answering, "unavailable", pointing to break-glass (PR 2); no secret or origin, said as the operator's to fix. **`rest.ts`** sends a session's key or renewed token, an AS its probe finds down failing at once; **sign-out** ends the session and leaves the revocation to the revoker, not waited on (a hung AS, or a queue an outage left, would hold it: review pass 4).
- **`dashboard/test-oauth.ts`** (new, the portable-server job; `db/ci-parity.sh`'s line) and **`dashboard/smoke-oauth.ts`** (new, deploy-stack-auth's new step, after `restart-check.ts --gui-refresh`, new too). **Not taken.**
- **A silent re-authorize** in place of the refresh token: a redirect mid-page, and a form post landing on an expired token lost (the maintainer chose the refresh token).
- **A read-only sign-in:** the operator's token asks `brain:write`, as the one account holds every scope; a read key still signs in on an unconfigured stack.
- **The AS's end-session at sign-out** in place of `prompt=login`: the AS has RP-initiated logout off; the AS asking `gui` the password every time, and the GUI refusing a sign-in whose `auth_time` precedes it, does the same for the next visitor. **A consent page left open:** the password typed, the page left, the next person at that browser may press Allow within the AS's interaction (600 s), as with a GUI left signed in. **A grant per GUI sign-in:** one whose token is revoked goes with it; one never exchanged waits for the store's purge (30 days, `GRANT_TTL_S`), and only the password makes one (review pass 5). **A fresh grant for `gui` alone, and `require_auth_time`,** are held by review (pass 5's mutants): no CI step re-consents a third-party client, and without the setting the GUI fails closed. **The callback's whoami-failed and cannot-read revocations** are held by review alone (pass 4 stopped `api` mid-sign-in and counted): a CI arm would stop the REST core mid-step. **A lost refresh answer:** if the AS spent the token and its answer was lost, the next try is a reuse it refuses, ending the session — rotation's price. **Revoking at a GUI restart:** its sessions are in its memory, gone before it could (review pass 1). **A sign-in someone else started** and the operator completed, its callback URL then seen by the one who started it: OAuth's own residual, the GUI's binding bound to the starter's browser (review pass 3). **The access token after sign-out:** good at the REST core until it lapses (600 s at most), which checks it locally; it never left the GUI's memory. **The probe's answer kept after the AS recovers:** a page due for renewal is a 503 for up to 30 s more, the price of not waiting 10 s on each page while it is down (review pass 2).
