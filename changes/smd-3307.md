## Changelog

On a stack configured with the authorization server (`COMPOSE_PROFILES` naming `auth`), the operator GUI at `/dashboard` signs the operator in through it, by code with PKCE, as its `gui` client: the password and the consent at the AS, then every page under a token the GUI holds and renews itself, never in the browser. Sign-out revokes it. Key sign-in stays off on the public origin (SMD-3307).

## FORK

The operator GUI signs in through the authorization server — code with PKCE, tokens renewed server-side (SMD-3307)

**What changed in PR 1** (the plan's three, SMD-3307's 2026-10-25 comment: sign-in, break-glass, the page of grants).
- **`deploy/auth/server.ts`:** the `gui` client takes `refresh_token` beside `authorization_code` (the maintainer's choice). It asks `offline_access` with `prompt=consent`, the only way oidc-provider grants it, and its refresh tokens rotate under SMD-2286's policy.
- **`deploy/compose.yaml`:** `app` gets `OB1_AUTH_SECRET_GUI`, its one secret; check 28's `APP_SERVICE` holds it whole. `serve.ts` warns at the start when the stack is configured and the GUI has no secret or no sound origin.
- **`dashboard/src/lib/server/oauth.ts`** (new): the settings (`edgeSettings`' origin, the secret), the authorization request (S256, `resource=<origin>/api`, `brain:write offline_access`), the code's exchange, a refresh and a revocation as `gui` on the mesh (`http://auth.ob1.internal.:3000/auth`), and `createRenewer` — a session's token renewed a minute before it lapses, once per session at a time, a refused renewal ending the session and an unanswered one leaving it.
- **`session.ts`:** a session holds a key or the AS's tokens (`Credential`), written back on renewal (`storeTokens`); sign-ins in flight keep their state and verifier server-side, single-use, ten minutes, the state also in a cookie on `/dashboard/auth` alone (no login CSRF). `closeSession` hands back what it held.
- **`routes/auth/start`** (a POST: no preload starts one) and **`routes/auth/callback`**: the answer taken with this browser's state and its verifier once, the code traded, whoami under the token (`oauth:operator`), a session opened; every failure back to `/signin?refused=<word>`, said in the GUI's own words, never the AS's.
- **The sign-in page's states** (ADR decision 16): not configured, the key; configured and the AS answering, its button; not answering, "unavailable", pointing to break-glass (PR 2); no secret or origin, said as the operator's to fix. **`rest.ts`** sends a session's key or renewed token; **sign-out** revokes the refresh token.
- **`dashboard/test-oauth.ts`** (new, the portable-server job; `db/ci-parity.sh`'s line) and **`dashboard/smoke-oauth.ts`** (new, deploy-stack-auth's new step, after `restart-check.ts --gui-refresh`, new too). Docs: `dashboard/README.md`, `SETUP.md` step 5, `deploy/README.md`'s AS section, `.env.example`.

**Why.** A configured stack's GUI signed no one in: key sign-in is off on its public origin (ADR decision 16), and nothing else was built. SMD-2286 moved the GUI's sign-in here with its only consumer.

**Held.**
- **`smoke-oauth.ts`** in deploy-stack-auth, through the proxy against the real AS: the start's authorize request (`gui`, S256, no verifier, `prompt=consent`, `offline_access`, the REST core), the sign-in cookie's path; the password and consent back to the callback; a session cookie on `/dashboard`; the views under the token, the who line `oauth:operator`; nothing JWT-shaped in any page, header, `__data.json`, script or cookie, the GUI's one cookie the session id (the Verify line); a replayed callback refused (with its sign-in cookie put back too: the verifier is spent), and a forged one, and a real answer opened in another browser; sign-out; a denied consent. Then CI counts the AS's refresh tokens of `gui`: none, so sign-out revoked.
- **`restart-check.ts --gui-refresh`** in the same step: the code gives `gui` a refresh token, a refresh rotates it, and revoked it is refused.
- **`test-oauth.ts`**, 28 assertions: settings, the request, the exchange, refresh and revocation forms (the secret form-encoded in Basic), each way the AS answers, and the renewal's single flight, refusal and silence.
- **deploy-stack's configured step:** with the AS not running, the page says sign-in is unavailable, and a key's post is still the GUI's 403.

**Measured after.**
- Scratch stack `ob1-3307` (podman, `COMPOSE_PROFILES=auth`, the origin `https://brain.example.test`, the secrets by `provision.ts`'s `initSecrets`), in-network through the proxy: `smoke-oauth.ts` 19 of 19; `restart-check.ts --gui-refresh` held; `test-oauth.ts` 28 of 28. With `--renewal`, 620 s on, past the first access token's expiry, two pages at once and the overview still rendered: the GUI renewed unseen. After every sign-in signed out, the AS's store held no refresh token of `gui` (CI's count). The key path, `app` recreated unconfigured on the same stack: the full `smoke.ts` 87 of 87. With the AS stopped, the page says unavailable and a key's post is the GUI's 403. Five mutants, each caught: the `gui` client without the refresh grant (the callback refused, `--gui-refresh` fails), the callback without the cookie binding, a verifier taken twice, the sign-in cookie on `/dashboard`, sign-out without the revocation (CI's count).

**Not taken.**
- **A silent re-authorize** in place of the refresh token: a redirect mid-page, and a form post landing on an expired token lost (the maintainer chose the refresh token).
- **A read-only sign-in:** the operator's token asks `brain:write`, as the one account holds every scope; a read key still signs in on an unconfigured stack.
