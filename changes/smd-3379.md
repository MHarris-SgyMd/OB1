## Changelog

A `migrate.ts` run now takes a session advisory lock, `ob1:migrate`, before it writes anything, and holds it until it returns: a pending file, a plugin's file or repair, 096's re-run, or `--reapply`. A second run meanwhile is refused by name, exit 2, writing nothing, and the refusal names the backend that holds the lock, with the `pg_terminate_backend` that ends a run that was killed. Before, two runs at once raced on the ledger's rows and the catalog's, and one failed at once on a duplicate key, sometimes as a stack dump. `--dry-run`, `--grant` and a run with nothing to write take no lock (SMD-3379).

## FORK

`migrate.ts` holds a lock while it writes, and a second run is refused by name: PR 1a (SMD-3379)

**What changed.**
- `db/config.mjs`:
  - `MIGRATE_LOCK = "ob1:migrate"`, beside `GRANT_LOCK` (a transaction lock on another key).
  - `MIGRATE_LOCK_HOLDER_SQL` reads who holds it (`pid`, `backend_start`) from `pg_locks` without taking it. A probe that took the lock would refuse a run arriving meanwhile. A bigint key is pg_locks' `classid` (its high 32 bits, 4294967295 where `hashtext`'s int4 is negative) and `objid` (its low 32).
- `db/migrate.ts`, `takeLock()`:
  - It takes the lock once, by `pg_try_advisory_lock`, and sets `application_name` `ob1-migrate`.
  - Refused, it names the holding backend and the `pg_terminate_backend` that ends it, exit 2.
  - It is called before each first write of its kind:
    - before the ledger's `CREATE TABLE`, when the ledger as it stands shows a core file pending, or for `--reapply`. A run refused there writes nothing. The read that decides what runs comes after, under the lock, so a run that took it after another let it go applies only what that one left.
    - where the plugins write, on a run whose core may have had nothing to apply: the plugin ledger (now made only where it is missing), the login role, a plugin's role, schema or grant, the hand-back of a schema another role owns, and each plugin file.
    - before 096's re-run, where PUBLIC can read `pg_stat_statements` again.
  - It says whether it took the lock just now. Where it did, what the caller read to decide on its write (a plugin's role, schema and grant, the hand-back's owners, 096's grant) is read again under it, and a plugin file whose ledger was read before the lock has its row read again: another run may have made that write and let the lock go meanwhile.
  - `run()` lets it go in its `finally`, however the run ends: a caller's own client lives on past the run (test-live's).
  - The header says all of this.
- `db/README.md`: the run section says when the lock is taken, what a second run sees, the killed-run case and its remedy, and that the lock is a signal, not a barrier. The engine paragraph adds `application_name` to the session state a run leaves, and says `run()` lets the lock go.
- **Tests:**
  - `db/test-live.ts` [1]:
    - beside a lock held by another session, on an empty database, a plain run is refused with the holder's pid and the remedy, and leaves no ledger and no `thoughts`;
    - a `--dry-run` and a run with nothing to apply go on beside the held lock, and `--reapply` is refused;
    - on a caller's client, the lock is gone after a run that applied a file, and after one that applied a file and then failed on drift.
  - `db/test-live.ts` [44]: 096's re-run beside a held lock is refused, PUBLIC's grant left; once the lock is let go, the next run takes it back.
  - `server-portable/test-plugins-sql.ts` [11], beside a held lock:
    - a plugin file pending is refused, the file neither run (its table stays dropped) nor recorded;
    - a run that read the plugin ledger before another applied the file and let the lock go (the other run started from this one's Writer, between the read and the lock) skips the file, where it re-ran it and failed on a duplicate key;
    - a hand-back with nothing pending is refused, the schema left as it was;
    - the login role's grant missing is refused, not granted;
    - the plugin ledger missing is refused, not made;
    - a run with everything in place goes on;
    - with the lock let go, each applies.

**Why.** SMD-3379's sleep scheduler (PR 1c) must stop its passes while a migration writes, and nothing marked a run in progress. The design took a lock in `migrate.ts` as the signal (draft 3's choice 4, accepted 2026-10-27).
- **No lock for a no-op:** the compose stack's `migrate` service runs on every `up`, and a no-op run there must not stop the passes. The repairs a no-op run can still make are DDL after a restore without owners or privileges, and they take the lock where they write.
- **Measured on main:** two runs at once, the second started 0–800 ms after the first.
  - At 0 ms one failed with a stack dump on the ledgers' `CREATE TABLE` race (`pg_type_typname_nsp_index`), and in one trial that was the first run.
  - At 100–400 ms the second failed within half a second on `schema_migrations_pkey`, at whichever file it reached.
  - From 600 ms the second was a no-op.
  - Now the second is refused by name in every case.

**Version contract.** `migrate.ts` is a command the `ob1-migrate` image runs. No flag or named value changes, and there is no migration. Two runs at once already failed; now the second fails at once, in its own words. FORK.md's PATCH is a change with no schema change, so this is a patch.

**Held.**
- **test-live [1] fails if:**
  - the lock is not taken (the blocked run goes on);
  - it is taken after the ledger is made (the refused run leaves one);
  - `run()` does not let it go (the caller's session still holds it);
  - a run with nothing to apply, or a `--dry-run`, takes it;
  - `--reapply` does not;
  - the refusal does not name the holder.
- **test-plugins-sql [11] fails if:**
  - the call before a plugin file, the hand-back, the grant or the plugin ledger is dropped, or a plugin file's call moves after the file runs;
  - a plugin file's row is not read again after a fresh take (the race case fails on the duplicate key);
  - a run with the plugin in place takes the lock.
- **test-live [44] fails if** the call before 096's re-run is dropped (the held lock's run takes the grant back).

After pass 2, 89 of 90 again: test-live's rest shard is 1023/1023 and test-plugins-sql 116/116. **Tidied.**

**Not taken.**
- **A lock that waits** (`pg_advisory_lock`). A second run would hang behind a long migration with no word. The refusal names the cause, and the operator runs again.
- **Locking every run.** The no-op run on every `compose up` would stop the sleep scheduler's passes each time (SMD-3379's third review, F8d).
- **Widening the early check to every repair instead.** It would copy each repair's own test of whether it is needed, and drift from them. A call at each write stands where the write is.
- **The lock named in the no-ledger refusal.** A plain run beside a `--reapply` that is making the ledger on a schema without one is refused with that refusal's words (run `--reapply`), not the lock's. It writes nothing, and the case is a once-only repair.
- **Trying the lock again when the holder has just let go.** The refusal says so, and the next run takes it.
- **Making a `--dry-run` leave no ledger.** On an empty database it makes the empty table, as it always has (SMD-2291), with no lock; it applies nothing. That predates this change, and the docs say it.
- **Tests of the login role's creation, or a plugin's role or schema made anew, beside a held lock, and of the re-reads after a fresh take at the role, the hand-back and 096.** Each needs a cluster role dropped in a cluster the suites share, or a second run let in between a read and the lock. Each is the same one-line call as the four held, and the same re-read as the plugin file's, which the race case holds.

**Follow-ups.** SMD-3379 PR 1c reads the lock with `MIGRATE_LOCK_HOLDER_SQL`: the scheduler waits it out at start, and stops its passes and exits when a run takes it. Where 096 cannot take PUBLIC's grant back, every run takes the lock to try again, so 1c sees a lock on each `compose up` there with no ledger row added; it should exit only for a new ledger row, or treat a lock with none as a pause.
