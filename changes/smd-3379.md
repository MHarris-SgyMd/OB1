## Changelog

A `migrate.ts` run that will apply anything (a pending file, a plugin's file or login role, or `--reapply`) now holds a session advisory lock, `ob1:migrate`, until it returns. A second run meanwhile is refused by name, exit 2, writing nothing, where it used to meet the first run's row locks at its 10 s `lock_timeout`. `--dry-run`, `--grant` and a run with nothing to apply take no lock (SMD-3379).

## FORK

`migrate.ts` holds a lock while it applies, and a second run is refused by name: PR 1a (SMD-3379)

**What changed.**
- `db/config.mjs`: `MIGRATE_LOCK = "ob1:migrate"`, beside `GRANT_LOCK`, which is a transaction lock on another key.
- `db/migrate.ts`:
  - **When it locks:** a run that is not `--dry-run` decides whether it will apply anything: `--reapply`; a migration file the ledger doesn't record; or a plugin with files whose ledger lacks one, or no login role yet (`pluginsNeedLogin`). If it will, it takes `pg_try_advisory_lock(hashtext(MIGRATE_LOCK))`.
  - **The order:** the decision reads `public.schema_migrations` as it stands, before the ledger's `CREATE TABLE`, so a refused run writes nothing. The read that decides what runs comes after, under the lock, so a run that took the lock after another let it go applies only what that one left.
  - **The refusal:** a held lock refuses the run with its own words, exit 2: "another migrate.ts run is applying to this database now … Wait for it to finish, then run this again … Nothing was changed."
  - **The release:** `run()` lets the lock go in its `finally`, however the run ends. A caller's own client lives on past the run (test-live's), and would otherwise hold it for the session.
  - **The header** says all of this.
- `db/README.md`: the run section says when the lock is taken, what a second run sees, and that the lock is a signal, not a barrier. The engine paragraph says `run()` lets it go.
- `db/test-live.ts` [1]:
  - with the lock held by another session on an empty database, a plain run is refused by name and leaves no ledger and no `thoughts`;
  - a `--dry-run` goes on beside the held lock;
  - on a caller's client that outlives the run, the lock is gone after a run that applied a file, and after one that applied a file and then failed on a drifted one;
  - beside a held lock, a run with nothing to apply goes on, and `--reapply` is refused.

**Why.** SMD-3379's sleep scheduler (PR 1c) must stop its passes while a migration applies, and nothing marked a run in progress. The design took a lock in `migrate.ts` as the signal (draft 3's choice 4, accepted 2026-10-27). It is taken only when a run will apply something: the compose stack's `migrate` service runs on every `up`, and a no-op run there must not stop the passes. It also turns two runs at once from a wait on row locks into a refusal that names the cause.

**Version contract.** `migrate.ts` is a command the `ob1-migrate` image runs. Two runs at once already failed, at the second's `lock_timeout`, with words that named a table. Now the second is refused at once, by name. No flag or named value changes, so this is a minor.

**Held.** test-live [1] fails if:
- the lock is not taken (the blocked run goes on);
- it is taken after the ledger is made (the refused run leaves one);
- `run()` does not let it go (the caller's session still holds it);
- a run with nothing to apply, or a `--dry-run`, takes it;
- `--reapply` does not.

**Measured after.** test-live, the `rest` shard: section [1]'s lock cases pass; full results under Review passes.

**Tidied.**

**Not taken.**
- **A lock that waits** (`pg_advisory_lock`). A second run would hang behind a long migration with no word. The refusal names the cause, and the operator runs again.
- **Locking every run.** The no-op run on every `compose up` would stop the sleep scheduler's passes each time (SMD-3379's third review, F8d).
- **A test of the race between the decision and the lock.** Two runs can't be interleaved there deterministically. The order (decide, lock, then read what runs) is held by review, and the header says why.

**Follow-ups.** SMD-3379 PR 1c reads the lock: the scheduler waits it out at start, and stops its passes and exits when a run takes it.
