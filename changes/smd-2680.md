## Changelog

What consolidation found now shows without a query. `brain_info`, keyed `/health` and `GET /v1/brain` gain `proposals` (the supersession proposals pending review, how long ago the oldest was judged, how many pair two tickets the board does not link, and the stale ones) and `relations` (the judged relations standing, 084, by word, with their board pairs), and the tool's table gains a `Proposals` row and a `Relations` row.

Preflight gains a `proposals` row. It is ok while the queue is young and warns, but never fails, once the oldest pending proposal has waited past `OB1_PROPOSALS_WARN_DAYS` (whole days, 7 unset). It names `consolidate.ts --list` and the `list_supersession_proposals` tool. The `consolidate pass` row no longer carries the queue. The server grant group gains `SELECT` on `supersession_proposals`, so a capture-and-server `--grant` role reads the queue (run `migrate.ts --grant` again for an existing role), and under a migration's lock on a table a read of its own refuses first, later reads that touch the table are not sent (SMD-2680).

## FORK

brain_info, keyed /health and preflight report the proposal queue and the standing judged relations, so a sleep pass's findings are seen without a query (SMD-2680)

**What changed.**
- **`server-portable/brain-info.ts`: four guarded reads.**
  - `proposals` counts the queue (pending, stale, the oldest pending verdict's age) over `supersession_proposals` alone. It is not a stats read, so preflight's lean read has it.
  - `relations` counts the standing `relation` facets (no `valid_until`) by word. It is a stats read.
  - `proposals.boardPairs` and `relations.boardPairs` count each one's board pairs, last, as reads of their own, and only where 079's function exists. Measured on a scratch brain, one statement passed the 800 ms health cap at about 45k pending proposals (about 18 µs a row on average, most rows needing no link lookup; 079 measured its predicate at 0.1–0.2 ms a call), or about 5k on one hub ticket, and took the whole queue with it. Now a timeout takes the board count alone, named in `unread`. An empty queue, or no standing relation, sends no board statement and counts none, so a refusal of 079's predicate never speaks for an empty queue; a lock or the deadline does not undo that, and a board count whose field was not read leaves no entry of its own (`settleBoardPairs`, on the finished read and on a snapshot). A board count counts rows, not distinct pairs of tickets, and a pair can be in both.
  - A board pair is two thoughts filed under two different tickets (`coalesce(metadata->>'ticket', metadata->>'issue')`, 079's identity, so a Linear section row counts as its ticket's and one ticket's two rows are not a pair) that the board relates in no way now: 079's `consolidation_tickets_linked` says no, and no active Linear `duplicate_of` joins them either way. 079 leaves `duplicate_of` to the judge, but a pair Linear marks duplicate is linked for anyone reading this count. A link made after a verdict does not move its row (only a text move makes a row stale, 063), so the link is read, not assumed. Before 079 (the catalog statement reports whether the function exists) the count is not taken: `boardPairs` is null and no row prints it.
  - The age is the oldest pending verdict's, since it was judged; a pass that re-judges a stale row restarts it, and the docs say so.
  - `proposalsValue`, `relationsValue` and `boardPairsValue` admit only counts, plus whole seconds for the age, since the record is rendered unguarded (`AS_RECORD`).
  - Either table absent reads null with no `unread` entry.
  - The two fields render as `Proposals` (always) and `Relations` (with the counts; `none — migration 084 is not applied` before 084).
- **One lock wait per table.** A single-table read refused its lock (55P03) puts its table in a set. Each later read that touches that table, including through a join (`joins`), is named in `unread` as `timeout`, "not tried — a lock on <table> (the table or one of its indexes) was refused to an earlier read here", without being sent.
  - A table enters the set only through a read of that table alone (any read but the two board counts), so a lock on `thoughts` costs one wait, not one per read, on a read with the counts. Preflight's lean read has no read of `thoughts` alone, so there a lock on it is waited on by the queue's board count.
  - Under a migration holding `thoughts`, `thought_audit` and `thought_chunks`, keyed `/health` answered in about 0.9 s here. The watermark, which reads `thoughts` alone, and the two board counts, which join it, are not sent. Without this rule each would have waited 300 ms, bringing the probe to the 1.8 s the e2e bound refuses.
- **Preflight's `proposals` row.**
  - It reads `facts.proposals`: skip before 029; a warning when the queue is refused, naming `migrate.ts --grant <role> --groups capture,server`; a board count that did not answer said as such (`board pairs not counted (…)`), never shown as none, and when refused a warning with its grant (GRANT EXECUTE on 079's function, or the SELECT its predicate needs); a warning with the search_path remedy when invisible; ok while the oldest pending verdict is younger than `OB1_PROPOSALS_WARN_DAYS` days (1–3650, 7 unset); a warning past it.
  - A value of the knob that is not whole days warns and keeps 7, and an old queue keeps its words and remedy beside it.
  - The `consolidate pass` row's queue query and every `; N proposal(s) pending review …` tail are gone; the stale wording moved to the new row.
  - `DIRECT_CHECKS` gains `proposals`, so the PostgREST run's catalog-only skips number 23.
- **The knob is wired as check 14 requires:** `root.ts`'s `Env`, `server.environment` in `deploy/compose.yaml` and `deploy/compose.tiers.yaml`, and a commented line in `deploy/.env.example`.
- **`db/config.mjs` `ROLE_GRANTS.server`** gains `supersession_proposals SELECT` (since 029, soft), and so does `db/README.md`'s grants table.
- **The `brain_info` description** names the two fields (`tools.json` carries no descriptions, so it is unchanged), as does `docs/open-brain-assistant-gpt-context.md`.
