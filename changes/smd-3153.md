## Changelog

The `EMBEDDING_NOT_ATTACHED` refusal is gone, along with the REST core's 201 that answered it and the store's `embeddingFailed` flag behind it: the retired PostgREST store was the only thing that ever produced them. A capture's 201 keeps `embeddingAttached`, which still says whether the vector was written with the row (SMD-3153).

## FORK

`EMBEDDING_NOT_ATTACHED` and `CaptureResult.embeddingFailed` are removed — no store has produced them since the PostgREST store left (SMD-3153)

**What changed.**
- **Core:**
  - `CaptureResult.embeddingFailed` is gone from `store.ts`;
  - `core/writes.ts` no longer refuses on it;
  - `core/refusal.ts` drops the union member and its `id` detail.
- **REST:**
  - `rest/routes.ts` drops the code's 503.
  - `rest/app.ts` drops the branch that answered it as a 201 with `embeddingAttached: false` (and, forwarded, the refusal beside it). Every capture refusal is now answered at its status.
  - `rest/openapi.ts` no longer excludes the code from the status lists, and the capture's 201 description loses its "PostgREST two-step" sentence.
  - `rest-client/openapi.json` and `schema.d.ts` are regenerated (`bun generate.ts`).
- **Renderers:** `render.ts` drops the code's words.
- **The MCP server:**
  - `outcomeOf` reads a success first. The refusal check came first only because of that 201, the one success that carried a `refusal`.
  - With that, `pluginOutcomeOf` was the same function, so it is folded into `outcomeOf`. A plugin value with a field named `refusal` is still a value (test-mcp asserts it).
- **db/bench-live.ts:** a refusal's answer no longer hands back an id for deletion, since no refusal saves a thought. Its self-check row is now "a refusal saves nothing".
- **The session hook:** an error reply is never a save. It used to read an error whose text named an id ("Thought saved (id …)", this code's words) as a capture with a note; it now classifies every error by its verdict before looking for an id. `CAPTURED_ID_RE` loses its "Thought saved" arm.
- **Tests:**
  - test-rest [5b]: the forwarded 201 case is now a forwarded capture refusal (`SUPERSEDES_UNJUDGED`) answered at 503, with the refusal whole beside it, and without the forwarder, the facts alone.
  - test-rest [7]: the creation-flagged case is removed.
  - test-rest [2]: the status-list check names every code, with no exception.
  - test-plugins and test-plugins-sql: their retryable core refusal is `SUPERSEDES_UNJUDGED`.
  - test-store-sql: the "no degraded-write flag" assertion is removed.
  - test-mcp [3] and the session hook's verdict table: their rows are removed.
  - the session hook: its `[[embedding-failed]]` stub and two asserts are replaced by `[[refused-naming-id]]`, a refusal whose words name an id, asserted refused. The `sent` check those asserts carried is held by the mended-supersedes cases (`r5`, `rsup`).
  - test-e2e-sql [2]: "no degraded-write note" now matches the live notes (saved WITHOUT a vector, no vector was made, the call not made), not the removed words.
  - eval-write-path: the no-id input no longer echoes the removed words.
- **Docs:**
  - `server-portable/README.md` no longer lists the code among the capture refusals, nor describes the 201.
  - `deploy/README.md`'s log outcome and span text no longer describe a capture logged `refused` on one door and `ok` on the other.

**Why.** Only the PostgREST store's two-step fallback set `embeddingFailed`. The SQL store writes the content, the metadata and the vector in one `upsert_thought` statement. SMD-3152 retired the PostgREST store and kept this code, so that a contract change would not widen that PR. Backwards compatibility is owed only to upgrading stable and canary (maintainer, 2026-10-20). Their clients are this tree's MCP server and session hook:
- neither ever received the code from a SQL store;
- the hook read that answer as a saved capture with a note, because its text carried the id. It now treats any error as unsaved, which is right for every answer a SQL store sends.

`embeddingAttached: false` on a 201 is still live: the egress gate refusing the embedding call, or the provider not answering it (`vectorFailed`).

**Held.**
- `git grep EMBEDDING_NOT_ATTACHED` finds only `changes/` history. The two-step survives only in migrations' comments (004, 008, 033, 035, 046, 060, 073, 080), which are append-only.
- Mutants, all four caught:
  - answering a capture refusal as a 201 (test-rest [5b]'s two new rows, among others);
  - `outcomeOf` reading a `refusal` field before success (test-mcp: "a value with a field named refusal");
  - the hook reading an error that names an id as a save (its new `[[refused-naming-id]]` assert);
  - a degraded note on a plain capture (test-e2e-sql [2]'s "no degraded-write note").
- bench-live's new row is a regression check, not a mutant-backed one: no capture refusal carries an `id`, so returning one on an error is unobservable with today's refusals.
