## Changelog

A supersession proposal records who decided it, for a reject as for an accept. Before, a reject left no trace of the key that ran it unless it cleared a pointer. `consolidate.ts --list accepted|rejected` prints `decided by:` on each row (the key's name and the kind it had when it decided, or "no agent id recorded" for a run without `OB1_WORKER_KEY`), and `--accept`/`--reject` print it after deciding. Classify your keys first (`set_agent_kind`) to tell your decisions from the workers'. The `list_supersession_proposals` tool, `GET /v1/proposals` and the GUI don't show it yet. Rows decided before the upgrade get their reviewer from the audit where the decision wrote or cleared a pointer; the rest say none was recorded (SMD-2608, migration 114).

## FORK

Who decided a proposal, on its row — stamped from the key that made the decision (SMD-2608)

**What changed** (migration 114).
- **Three columns on `supersession_proposals`**, the audit row's three: `reviewed_by` (the actor envelope's name, verbatim as the audit records it), `reviewed_by_agent_id` (its agent, in the server's id form) and `reviewed_by_kind` (`ob1_registry_kind`, read at the decision and only when an agent is named: a name alone, anyone's to write, lends no kind, so a keyless `consolidate` decision carries none even if a key of that name is classified).
- **One writer, a BEFORE trigger** (`supersession_proposals_stamp_reviewer`, `ob1_stamp_proposal_reviewer`) on any write that names `status`, `reviewed_at`, `review_note` or one of the three. `reviewed_at` NULL clears them. Otherwise they are the envelope present (`ob1.actor`), never the statement's values (050's rule). `review_supersession_proposal` sets the envelope from `p_actor`, so its accept and reject, and 067's settle through it, are stamped with the key that decided. 067's reopen clears them. Neither function is redefined. Sentinel `ob1:proposal-reviewer-from-the-envelope`.
- **Two CHECKs:** `reviewed_by_kind` is one of the registry's kinds and only beside an agent, and an unreviewed row carries no reviewer.
- **The backfill, from the audit:** a decision before 114 that wrote a pointer has that write's `thought_audit` row in the same transaction (`created_at` equals the row's `reviewed_at`). That row names the reviewer of an accepted row with `pointer_written` (the write onto the other side) and of a rejected row (the clear on either side): its name and agent, and its kind only where it names an agent and the audit trigger stamped that kind at the write (`backfilled_at` NULL). The audit reads a kind from a name alone (055), and 046's backfill fills one in later; neither is a key's kind when it decided. Every other decided row stays NULL; nothing is guessed. It runs before the trigger exists, and a re-apply fills only rows with no reviewer.
- **`db/consolidate.ts`:**
  - `--list` reads the three by the page's ids, beside the listing, as it reads the writers (094), and prints `decided by:` on an accepted or rejected row: the name and the kind at the decision, else the registry's kind now ("classified after it decided"); a name with no agent reads "no agent id recorded (run with no key, or a key that did not resolve)". On a brain short of 114 it says so, once.
  - `--accept` and `--reject` read it in the decision's own transaction (a column probe first, so a brain short of 114 rolls nothing back) and print it, or say the row records none. The reject moved into a transaction to do so, so a `--reject` killed while it waits on the review lock now writes nothing, as `--accept` already did; before, its autocommit statement waited on in the server and committed after the CLI had gone.
- **Docs:** deploy/README.md says a decision (no longer only an accept) is recorded under `OB1_WORKER_KEY`'s agent, which SMD-2424 had narrowed until this landed, what the line prints, to classify keys first, and that a person's decision under the workers' key and the pass's settle read alike but for the settle's note; db/README.md's consolidation identity paragraph; dashboard/README.md says the proposals page does not show it.

**Decided.**
- **Columns, not a reject event in `thought_audit`.** That log is the thoughts' (every row has a `thought_id`, and since 060 the row is its projection). A reject that clears nothing changes no thought, so an event would project nothing and name a thought it did not touch. The decision belongs to the proposal, beside `reviewed_at` and `review_note`. An accept's and a clearing reject's audit rows still name the same actor.
- **A trigger, not a redefined `review_supersession_proposal`.** `reviewed_at` has two writers, the review (036) and 067's reopen inside `rebuild_derived`, and both bodies are long and frozen. The trigger takes both, and a raw write too, with nothing copied.
- **No key is a name without an agent.** `consolidate.ts` with no `OB1_WORKER_KEY` decides as `consolidate` with no agent id, as its audit row says; `--list` prints "consolidate, no agent id recorded (run with no key, or a key that did not resolve)". A raw call with no envelope records none, printed as not recorded.

**Not taken.**
- **The listing's columns.** A RETURNS TABLE cannot gain a column under CREATE OR REPLACE, and 110 re-applied after a wider form of its own argument list would fail ("cannot change return type"). A wider listing is another argument list, and with it another round of every reader's and preflight's probes (070, 109 and 110 each paid one). So the REST core and the MCP tool do not show the reviewer yet. SMD-3338, the REST-core review operation, decides how they do.
- **A history of decisions.** The columns hold the decision that stands; a later decision replaces them, as it replaces `reviewed_at` and `review_note`. An accept's and a clearing reject's audit rows keep their actors.

**Upgrade.** MINOR: three nullable columns, a trigger and two CHECKs. Nothing a caller passes or reads changed. An older server or CLI deciding through the same functions gets the reviewer stamped. No grant moves: a keyed decision now reads `ob1_agents` for the kind, as the audit trigger does, and every role the READMEs have decide holds the capture group's `SELECT` on it. A role granted the worker group alone, which could reject a proposal that clears nothing and no other part of a review, is refused that reject under a key. A data-only reload (`pg_restore --data-only`, a COPY) with the trigger enabled empties every reviewer; a full `pg_restore` creates triggers after the data. The backfill credits a hand-run transaction that decided one row twice to its first clearing decision; nothing in the tree decides twice in one transaction.

**Verify.** test-schema [102]: the stamp, the restamp, no key, no envelope, a name alone lending no kind, a statement's values ignored, the reopen under an envelope, the CHECKs, the backfill (a clear then a reject clearing nothing guessed as none) and a re-apply. test-upgrade [20bf]: refused without each of 008, 029, 046 and 050, and onto a populated brain at 112 the backfill names the audit's reviewer, a second key's clear included, and guesses none. test-live [16]: `--accept`/`--reject` and `--list rejected` with the worker's key, a reject with no key, and a key classified after it decided.
