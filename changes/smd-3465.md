## Changelog

Fork Checks' canary step stops the canary's board-sync along with its Postgres before it asks a plain up over a stopped canary stamped `stable`, where it stopped Postgres alone, so the up no longer waits ~30 s on stopping a board-sync whose database is gone (SMD-3465).

## FORK

The canary step stops board-sync with the canary's Postgres in its late stamp case (SMD-3465)

**What changed.**
- **fork-checks.yml, "A canary stands beside the stack from deploy/canary.sh".** SMD-3155's late stamp case, a plain up over a stopped canary whose database is stamped `stable`, stops `board-sync` and `postgres` together, with `--profile board-sync`, where it stopped `postgres` alone. Compose stops board-sync first, since it depends on Postgres. The case still asks what it asked: the up starts the stopped Postgres after the writers stop, and `canary.sh`'s late guard (~1558) refuses it with exit 1, naming `--refresh`, before anything is kept.
- A new line fails the case if the up's output says `canary board-sync stopped for`. That would mean board-sync was still running when the up began, so a step that grew by ~30 s again would fail rather than pass slowly.

**Why.** The ticket: run in CI, the case's one up took 35.3–36.7 s, where a refused up over a running Postgres takes 6–7 s. Stopping Postgres alone left the previous up's board-sync running with its database gone. `canary.sh` then stopped it with `stop -t 60`, and the stop waited while board-sync's loop-end heartbeat waited on a connection (SMD-3464, the product side, not this ticket). With Postgres up, that stop took 0.6 s. The canary step's median went from 113 to 155 s with SMD-3155, and the brains job's from 205 to 250 s.

**Held.**
- Compose stops the two in the order the case needs, under this Mac's compose (v5.6.1) and under v2 (`docker:28.3.2-cli` on the podman socket, as the runners' 2.38 stand-in from SMD-3200). The check used a scratch project of the same two services, with board-sync depending on Postgres and taking 3 s to exit on TERM: in both, board-sync finished before Postgres.
- The profile is needed: compose resolves `board-sync` only with `--profile board-sync`. Compose interpolates every service's block whether its profile is on or not (compose.yaml's comment on board-sync's `LINEAR_API_KEY`), so the profile needs no variable the old line didn't.
- What the case asserts is unchanged: rc=1, `is stamped 'stable', not canary`, `Run up --refresh to finish one.`, and no `the canary's database is kept`. Nothing in the step asserted the refusal's `Board-sync is stopped too` text, so no assertion goes. The later check that board-sync runs after the next up still holds: board-sync was stopped before that up either way.
- Pinned actionlint 1.7.7 with shellcheck passes, and so does the checker.
- The step itself is not run here. It drives the `open-brain` and `open-brain-canary` projects, which on this Mac are the dogfood stacks. This PR's CI run is its rehearsal and its first timing.

**Verify** (the ticket's): over ten main runs, the canary step's median is at most ~125 s and the brains job's at most ~220 s.
