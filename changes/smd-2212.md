## Changelog

The `orchestration` profile ships its first n8n templates. An import runner service (Bun and python3, no published port, its own key) runs an allowlisted pipeline's emitter over a read-only imports directory, refuses a batch with a line of another source, and runs the ingestion pipeline under its own actor, and one generic import template is loaded per pipeline, on a schedule and on demand. An act tool, `linear_file_issue`, is a multi-step Linear flow on its own MCP endpoint, loaded only when its Linear key is set. `db/ingest-records.ts` gains `--actor`. Provisioning skips an optional credential's workflows, refuses one of OB1's keys in two credentials, and resolves one template's reference to another (SMD-2212).

## FORK

The first n8n templates — the import runner and a generic import template, and an act tool on its own MCP endpoint (SMD-2212)

**What changed.** The ticket's Gmail and Linear templates moved to
SMD-2257 and SMD-2258, each behind its gate. This builds what nothing blocks.

**The import runner** (`deploy/orchestration/runner.ts`, image
`runner.Dockerfile`, compose `orchestration-runner` under the profile). The
ADR decided it in SMD-2210, and this builds it:
- `POST /run/<pipeline>` with `x-runner-key` (401 without, 403 wrong); a
  pipeline not in `pipelines.json` is 404, a second run of one going is 409.
- The emitter runs over `/imports/<pipeline>/`, a read-only mount of
  `deploy/imports/` (`IMPORTS_DIR`), with no database URL or key in its
  environment, a timeout and an output cap.
- Every line must carry the pipeline's one source and scope, or the batch is
  refused whole before the ingester runs.
- Then `db/ingest-records.ts --source items --items - --allow <scope>
  --actor orchestration-runner`, then `db/reembed.ts`. The answer is the
  report: the count line and the items the ingester named.
- The request names the pipeline and nothing else, so the export never
  passes through n8n: its run history holds the report, not the content.
  The ADR's "items in the request body" is amended to this.
- The allowlist ships empty. Each recipe's ticket (SMD-2147–2150, SMD-2021)
  adds its line, its emitter and its packages.
- The image copies the pipeline's import graph file by file (a bundle ran
  `scripts/fork-index.ts`'s main block, which writes `FORK.md`, measured) and
  its build resolves every import, so a module the pipeline gains fails the
  build. `deploy/imports/` is kept out of git and of every build context.

**The import template** (`templates/import.per-pipeline.json`): a Schedule
trigger every `everyHours`, and a Webhook (`/webhook/ob1-import-<pipeline>`,
the run key), both calling the runner with its credential, then a Report step
that fails the run with the runner's reason. Provisioning loads it once per
pipeline, with the name, path, schedule and a webhook id derived per
instance (`instanceFor`).

**The act tool** (`templates/act-mcp.json`, `act-linear-file-issue.json`).
`/mcp/ob1-act` lists one tool, `linear_file_issue`, under `N8N_MCP_KEY`. The
tool calls a sub-workflow: find the team and the label in one query, create
the label if the team lacks it, create the issue, answer its identifier and
URL. Its credential is `N8N_LINEAR_API_KEY`, pinned to `api.linear.app`, and
optional: unset, the endpoint is not loaded. No brain tools (decision 7).

**Provisioning** (`provision.ts`):
- `--init` writes `OB1_RUNNER_KEY`; the runner's credential is pinned to
  `orchestration-runner`.
- A credential marked `optional` whose value is unset is skipped, with every
  workflow that needs it and every workflow naming a skipped one; the run
  says which and why. A required one still refuses the run.
- None of OB1's own keys may sit in two credentials (`sharedSecrets`). A
  vendor's key, in the vendor's own type, may serve two templates.
- `"ob1wf:<template>"` names another template's workflow. It loads first and
  the reference becomes its id; a reference to no template, and a cycle, are
  refused.
- `--self-check` covers each against the fake n8n, which now records what it
  was given.

**`db/ingest-records.ts --actor <name>`** names the envelope for a tool that
runs the ingester on its own behalf. The door stays `ingest-records`
(test-live [22]: the row's actor and the audit row's origin).

**The kit** loads the profile's templates, instanced for its own
`runner/pipelines.json` (a Python fixture emitter over a five-entry export,
and `stray`), which `compose.n8n.yaml` mounts over the empty allowlist. The
runner starts with n8n. Two checks join K, P and E:
- **A:** `/mcp/ob1-act` lists exactly `linear_file_issue`, and refuses a
  missing and a wrong key; the tool, asked for a team that does not exist,
  runs to Linear's "no Linear team" and files nothing. Sealed, it must fail.
- **I:** the fixture's rows deleted through `delete_thought`, then the
  first run inserts five under `orchestration-runner`, each with a vector; a
  rerun writes nothing; `stray` is 422, nothing written.
- **E** admits a connection to the runner's `:8090` (its addresses read from
  the engine), and nothing else of it: 39 cases in CI.

**CI** runs `runner.ts --self-check`, builds the runner's image in the full
stack job, and pins the profile's runner to no published port.

**Verified** live on the kit (`--up n8n`, `--verify n8n --wait-schedule`):
- A, I, K and C3 pass. I inserted 5 with vectors, a rerun inserted 0, and
  `stray` answered 422 with nothing written.
- C1, C1s and P were blocked by another session's model holding the host's

- In CI terms: the three self-checks pass, `test-live` is 756/756, and 24
