# 539. The MCP request's line says which revision it named — `rev`, held to the revisions served, so the log can count the clients on each (SMD-4363)

**Why.** Since SMD-4345 `/mcp` serves the 2026-07-28 revision beside the 2025-era ones, and a request's line read the same for both: the method, the tool, the key's name, how it ended. Nothing said how many requests, or which keys, used either. Whether a client had moved to 2026-07-28 could be read only sideways, from a `server/discover` answered 200 with no `initialize` after it, which is how the canary's upgrade was checked. Three hosted clients went unmeasured in SMD-4344 because measuring them needed a probe at a public address; a brain they already reach shows it, once its line says.

**What changed.**

- `revisionOf` in `server-portable/mcp-edge.ts` reads the revision a request names: its envelope's (`params._meta`'s `io.modelcontextprotocol/protocolVersion`, a 2026-07-28 request's word on itself, over a header that disagrees and whatever its method: the SDK sends a request that claims an envelope to its 2026-07-28 handler, to answer or refuse, an `initialize` too where the envelope is whole and names 2026-07-28); else what an `initialize` offers (`params.protocolVersion`, which is what the SDK's 2025-era transport acts on, over a 2025-era header sent with it); else its `MCP-Protocol-Version` header's; else `unnamed`. A caller's own `unnamed` is written `other`.
- `mcp-server/app.ts`'s route sets it on the request's record wherever it reads the body: for a request it serves, and for one refused at the key, whose body it reads for the refusal's id.
- `server-portable/telemetry.ts`: `rev` is a field of the line, after `rpc`, held to `MCP_REVISIONS`: 2026-07-28, the five revisions the SDK's 2025-era transport negotiates, and `unnamed`. Any other string is written `other`, as an unknown method is.
- The request's span carries it as `mcp.protocol.version` where it is a revision, and as `ob1.rev` where it is `unnamed` or `other`, the way `ob1.rpc` holds what `mcp.method.name` cannot say. A request refused at its key carries neither. OpenTelemetry defines the attribute as the version used, and such a request used none; it is answered 200, so a caller with no key would count under whichever revision it named. `gen_ai.tool.name` is withheld there for the same reason. The line keeps the word, beside its `refused`.
- `deploy/README.md`'s table of the line's fields and its account of the span, and `mcp-server/README.md`'s "Every request's line", say so. `deploy/README.md`'s "a line never holds a header" names its second exception. `docs/mcp-client-refresh.md` said the log records no revision; a dated note there says it does now.

**Decided.**

- **The client's name is not recorded.** It is the caller's own string (`clientInfo.name`), so writing it needs an allow-list of names kept by hand, and a name on that list is anyone's to send. The key's name is already on the line and is the server's word for who called; where each connector has a key of its own, the key and the revision together say which client speaks what.
- **A request that names no revision is `unnamed`.** The 2025-06-18 and 2025-11-25 revisions have a client send the header on every request after `initialize`, and have a server assume 2025-03-26 without one; 2025-03-26 and earlier define no such header, though the SDK's client sends the revision it negotiated whichever that is. The line says what the request named, not what the server assumed.
- **No label on the duration histogram.** The line counts requests by revision. A label would multiply every series of the histogram by the revisions served, and `scripts/check-consistency.ts` holds that histogram's labels to a measured list.

**What a count of `rev` means.** It counts what requests said, not what the server did.

- A request with no header that is no `initialize` is `unnamed`. That is a client on 2025-03-26 or earlier sending what its revision defines, and a later one that leaves the header out. The two cannot be told apart, and such a client's revision shows on its `initialize` line alone.
- A client built on the SDK names its revision on every line. Measured: the 2.4.0 client and the 1.30.0 one, held to 2024-11-05, 2025-03-26 and 2025-06-18, each send the revision they negotiated as the header on every later request.
- A refused request has its `rev`: a 2026-07-28 request the handler refused (400) still says `2026-07-28`. So has one refused at its key, and that one is answered 200: a caller with no key, a wrong one or a revoked one writes a 200 line under whichever revision it names. Count with the status and the outcome.
- An `initialize` says what it offers, not what it is answered. One offering a revision this server does not serve is `other`, though the transport answers it with one it does; one offering `2026-07-28` with no envelope says `2026-07-28` and is answered as a 2025-era handshake; one whose envelope claims a revision and is not whole says the claim, and is answered as a 2025-era handshake too.
- So the clients on a revision are the `agent`s of its lines with `status` 200, an `outcome` other than `refused` and an `rpc` other than `initialize`. That leaves out a call its tool refused, which costs a count of clients nothing. For every such line that names a revision, the SDK served the request as that revision.
- A batch is read by its header alone, a batch of one too: with no header it is `unnamed`, though a batch of one's `rpc` is its message's.
- A request the route never came to read has no `rev`: one gone before the route ran, or whose key check threw. A body unread (a keyless one past the refusal's 64 KiB) or not JSON has the header's word, or `unnamed`. The GET a 2025-era client opens for a stream is a 405 line with no `rev`.

**Also changed.** CI's `deploy-stack-auth` job counts a `thought_stats` call's line with a pattern anchored at both ends (`STATS_LINE` in `.github/workflows/brain-checks.yml`); the line has `rev` in it now, so the pattern names `"rev":"unnamed"`, its probe naming no revision. The one other workflow pattern on an MCP request's line spans fields with `.*`; the pattern anchored on the REST core's `/v1/whoami` line is untouched, a REST line having no `rev`.

**Not changed.** What any request is answered. The REST core's lines and every other route of the MCP server: no `rev`. The metric's labels.
