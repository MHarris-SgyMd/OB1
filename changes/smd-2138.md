## Changelog

`recipes/local-ollama-embeddings` is gone: capture without a cloud embedding key is the fork's default — the server embeds through `OB1_LLM_BASE_URL` (`--profile local-models` runs the Ollama), `db/reembed.ts` walks existing rows — and `embed-local.py` reached `upsert_thought` only over a PostgREST the stack does not run; its two test-writes guards and its check 24 entry go with it, its two measured models become rows of `SETUP.md`'s table, and `db/README.md` carries the operator's paragraph (SMD-2138).

## FORK

The local-Ollama embedding recipe retires — the fork embeds locally by default, so the recipe's whole story is a paragraph of `db/README.md` and two rows of `SETUP.md`'s model table (SMD-2138)

**What changed.** `recipes/local-ollama-embeddings` — `embed-local.py` (376
lines), its README, `metadata.json`, `.env.example`, `requirements.txt` and
`.gitignore` — is deleted. The script read thoughts from an argument, stdin, a
`.txt` or a `.jsonl`, embedded each through Ollama's `/api/embed` (default
`nomic-embed-text`; `--model`, `--source`, `--dry-run`; a `--batch-size` declared, never read) and
POSTed `/rest/v1/rpc/upsert_thought` — the 3-argument form with the model's
bare name as the label, SMD-1524's fix — under `metadata.source =
ollama-local`. Every piece is core here: the server embeds through
`OB1_LLM_BASE_URL` declared local by the operator's own `OB1_LLM_LOCAL=1`, a capture is
`capture_thought`, existing rows are `bun db/reembed.ts`, the width is
`db/config.mjs`'s, the label per row is 021's. What follows the directory out:

   script to the function (SMD-1524's record); the comment above them says the

**Why.** SMD-2126 decided the class: an import becomes an adapter of the
contract, a maintenance script moves onto the shim, and a script whose
capability is in core retires. This one is the clearest of the three: the
recipe existed so an operator could capture without paying a cloud embedding
provider, and that is this fork's default configuration, not a recipe. Its
one transport, `${SUPABASE_URL}/rest/v1/…` with a service-role key, is one the
stack does not have, so on the fork it fails at its first request
(`--dry-run` ran). Its README's `ALTER COLUMN embedding TYPE` example was
already annotated "not altered by hand on this fork". Nothing is handed to
another ticket: no filter, label or scan of the recipe's lacks a home.
