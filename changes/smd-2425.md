## Changelog

`db/extract-entities.ts` and `db/consolidate.ts` now behave like `db/reembed.ts` in two places (SMD-2425). Their `run()` refuses a blank string option first, in the CLI scanner's words, before anything connects: extract's `job: ""` used to pool and record under the key `''`, and consolidate's `note: "  "` used to reach the decision. And a hard stop whose lease release beats a worker's own no longer leads to a false report that the row's "lease lapsed".

## FORK

Blank options and the hard-stop lapse in extract and consolidate, as reembed since SMD-2304 PR 4 (SMD-2425)

**What changed.**
- **One blank rule for every engine.** `db/cli.ts` gains `blankProblem(spec, values)`. It returns the scanner's refusal of the first blank value (empty or whitespace only) in the flag table's order: "--job is empty; give it a value", "--list is empty; give it a value or leave it out", "one of --accept-failed's values is empty".
  - `scanArgs` takes its blank wording from the same helper, so the two cannot drift apart.
  - `run()` checks first, then appends the flag list. extract checks `dump` and `job`. consolidate checks `dump`, `list`, `accept`, `reject`, `direction` and `note`; `reviewProblem` refused some of these, but in its own words, and let a blank `note` through.
  - reembed's own copy (`job`, `retire`, `acceptFailed`) is replaced by the shared helper, with the same words and order.
- **No lapse reported after the caller's own hard stop.** The hard stop's `release_claims_for_worker` can commit before a worker's in-flight `release_thought`, which then answers false. In both engines' two release paths (the thought's release, and recording a failure after the pauses), a worker now returns quietly when the hard stop has come. Before, it printed "the claim was no longer this worker's at release — … its lease lapsed …" and counted the row as lost.
  - The check sits on the false branch only, so a release that won the race is still counted. This is the undercount reembed's pass 4 caught when the check sat before `ok` was read.

**Held by:**
- **test-engines:** 10 new cases compare `run()` with the spawned CLI, stream by stream, before connecting. Three are extract's: a blank `job` with no URL, a blank `dump`, and a blank `job` before a bad `--workers`. Seven are consolidate's: each of its six options, and a blank `note` before a bad `--workers`.
  - With the check removed, each engine's cases fail. Consolidation and reembed get far enough to connect, which crashes the run.
- **test-cli:** `blankProblem` gives the scanner's own refusal for every kind of flag, treats an absent option or an empty list as not blank, and takes the flag table's order.
- **The race:** it is a single round trip, so no suite test holds it. A harness of the shape the ticket names ran: 150 rows, 2–4 workers, a soft stop, then a hard stop fired 0–10 ms after a stub answer. A 6 ms sleep was added before `release_thought` in every copy, to widen the window. Over 60 rounds each:

  | Copy | Rounds with a lapse line after the stop | Summary vs `after:` mismatches |
  |---|---|---|
  | This change | 0 | 0 |
  | Main's code | 28 (43 lines) | 0 |
  | Guard placed before `ok` is read | 0 | 5 |

  Without the widening, main's code showed no lapse in 16 rounds: the window is a connection acquisition, since the worker checks `hardStopped` right before the release.
  - Run on extract only; consolidate's two guards are the same code in the same place.
