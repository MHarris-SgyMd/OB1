## Changelog

A test-live row in the sleep shard that failed some runs now sets the order of extraction it tests, where it left that order to a tie (SMD-4515). No shipped code changes.

## Record

test-live [38]'s "in the fixed order" row sets the claims' order it tests, where a tie decided whether consolidation joined early (SMD-4515)

**What changed.** In `db/test-live.ts`, section [38]'s one-period case:

- At the period's first extraction call, the two older notes' claims still to be taken are dated after today's note's. A backlog note is then the last extracted, whichever way the tie fell.
- The row's message names the line consolidation joined on, so a failure says which way the period went.

No file a release ships changes, and `db/sleep.ts` is as it was.

**Why.** The row failed 2 runs of 7 on 2026-11-21, once in `ci-parity` and once in CI, on a branch that touched only the agent runner. Its message gave a judgement 1541 ms and 1533 ms after the last extraction, so the timing half had passed.

Measured on this branch, with the row made to say what its period did:

- The period's first pool takes the case's three notes in one statement, about 80 ms after the period starts. Their claims' `enqueued_at` are equal, so the order the one worker takes them in is a tie.
- Today's note is no backlog under SMD-4468's rule: pooled since the start and dated today. The two older notes are.
- In 6 runs of 6 the order was older note, today's note, deploy note. A backlog note was last, extraction drained as the backlog ended, and the row passed.
- With today's note put last by hand, consolidation joined 25 ms into its extraction, on SMD-4468's line ("extraction has done the thoughts captured before the period began …"), and the row failed on the line it asks for. Every other row of the shard passed.

So the scheduler did what SMD-4468 decided, and the row was asking for one of two orders it did not set. The other order is [38c]'s to test.

**Held.** The row asks what it asked: no judgement before the last extraction, the "extraction drained" line after "working:", and the period's end. The fixture's notes, dates and pooling are untouched; only the tie is settled.

**Measured after.** The `sleep` shard six times at once, each on its own Postgres: 6 of 6 pass, and the row joins on "extraction drained" in each. Two of the six first put today's note last by hand, the order that failed before; the row's own dating then puts the older notes after it.

**Not taken.**

- Accepting either join line in the row. In the early order a judgement beside today's extraction is by design, so "no judgement before the last extraction" would hold there only by a 25 ms margin.
- Pooling the notes before the period, which makes today's note backlog. It would take the period's first pool out of the case.

**Follow-ups.** Five other rows wait on the "extraction drained" line alone (one more in [38], three in [38b], one in [38s]). As read, not run: each has a note of today's that can be in extraction when a poll lands, in a window of milliseconds where this row's was 1.5 s. None has been seen to fail.
