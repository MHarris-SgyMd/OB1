## Changelog

`run_worker` — the third worker-queue action — arrives as a write-scoped MCP tool and keyed `POST /worker-run`, for now as its **preview half only**: `run_worker(work_type, { dry_run: true, limit? })` reports, without claiming anything, what a drain of that pool would process — the same census `worker_status` shows (pending / claimed / stale / unpooled) plus a `backlog` and a `limit`-bounded `wouldClaim`. The executing drain is deliberately refused as a value (`RUN_WORKER_DRAIN_NOT_AVAILABLE`): the server does not run the bulk LLM passes, so the drain will land on a callable worker core later. SQL-backend only, like the rest of the worker surface (SMD-2272).

## FORK

`run_worker` dry_run — an operator can preview a pool drain over MCP/REST without shelling in (SMD-2272)

**What changed.** SMD-2131 shipped `worker_status` (the read), SMD-2132 shipped `retry_failed` and `release_stale_leases` (the two pure-SQL write actions) and **deferred the third, `run_worker` (the drain)** on three recorded constraints: the server deliberately never runs the bulk LLM passes; the claim→provider→release loop has no importable core (it is inline in each `db/*.ts` `main()`); and a real drain runs for minutes against a POST/SSE transport whose keepalive caps at 10 min. The third constraint is now met — SMD-2273's job registry and SMD-2318's durable `jobs` table give a handle/poll/stream that survives even a restart — but the first two stand (the callable core is SMD-2304, still open). So this lands the one slice that is independent of them, which the ticket itself flags as "buildable now": the `dry_run` preview.

- **`run_worker` MCP tool** (`server-portable/index.ts`; `scope: "write"` in `tools.ts`, so a read or capture key never sees it — the same gate as its two siblings). Arguments `work_type` (required), `dry_run` (must be `true`), `limit?`. A blank `work_type` is refused as a value (`REFUSED_EMPTY_WORK_TYPE`); a call without `dry_run: true` — including the default — is refused as a value (`RUN_WORKER_DRAIN_NOT_AVAILABLE`), so an operator never mistakes a silent no-op for a real drain. On `dry_run: true` it returns the pool preview. Unlike `retry_failed`/`release_stale_leases` it writes **no** action-log row — a dry run mutates nothing, so there is no thought to record an action against; the write scope still refuses a read/capture key, and it will not change when the drain lands.
- **`POST /worker-run`** — the REST mirror, in the same write-scoped `app.post` guard as the other two actions: args in the JSON body, JSON census on success, the two refusals as 400s carrying the same codes, the SQL-only reason (the PostgREST shim throws) as a 200 body, and the bodiless `ok` for a read/capture/no/wrong/revoked key.
- **`ThoughtStore.dryRunClaim(workType, limit?)`** — SQL store: one pure SELECT. The census is `workerStatus`'s per-work_type row scoped to one pool (the same four status counts and stale subset, `unpooled` = corpus − pooled), so a dry run and `worker_status` agree by construction; `backlog` = `pending + stale + unpooled` (what a full pass would draw into processing now — the pending rows a `claim_thoughts()` would lease, the stale leases it reaps back to the pool before claiming, and the unpooled thoughts a pass would enqueue first; a live `claimed` lease is skipped), and `wouldClaim` is that backlog bounded by `limit`. `backlog`/`wouldClaim` are exact for an extraction pool but an **upper bound** for reembed/consolidate — their eligibility is model-aware, and the generic `unpooled` counts every un-pooled thought (and a stale row at max attempts fails rather than re-claims) — so the field docs and the tool description say so. No `claim_thoughts`, no `enqueue_thoughts`, no lease. PostgREST shim: throws "requires the SQL backend" — `thought_work_claims` is not published to PostgREST (migration 015), as the sibling worker methods do.

**Why.** An operator still could not *run a pass* (or even ask what one would do) from a running brain without shelling into the stack (`podman run … bun db/extract-entities.ts`, `DATABASE_URL` hand-wired) — the remote-over-HTTP gap SMD-2131/2132 set out to close. The preview alone closes the "what would a pass claim right now" half over a keyed tool/route, and establishes the tool/route/scope surface the real drain slots into unchanged once the callable core exists.

**Held.** `dry_run only, drain deferred`: the two open constraints (no bulk LLM in the server; no importable claim loop — SMD-2304) are real, so the executing drain is refused as a value rather than half-built against them; the async plumbing it will use (SMD-2273/2318) is already merged. `write-scoped, no audit row`: gated as a write action (a drain is a write) so the scope is right for the day the drain lands and a read/capture key is refused today — but a `dry_run` mutation-free call stamps no action, since the action log records mutations (`retry_failed` logs one row per requeued thought). `census matches worker_status by construction`: `dryRunClaim` reuses `workerStatus`'s counting rather than a second definition, so the preview and the read surface can never disagree (the ticket's "reports the same pool the worker's --status and worker_status show"). `no new env knobs / no migration`: the preview is pure SQL over the existing migration-015 table.

**Measured after.** typecheck clean; test-server 365/365 (+1: `run_worker` is `readOnlyHint: false`, and the manifest-derived tools/list drift guards pick it up); test-store-sql 192/192 (+10: block [5g] — the census, `backlog`/`wouldClaim`, a `limit` cap, an un-enqueued pool reading `unpooled` = the whole corpus, agreement with `workerStatus`, and that it claims nothing); test-store-postgrest 143/143 (+1: the shim throws the SQL-only reason); test-e2e-sql 304/304 (+16: block [6h] — the dry_run tool and `POST /worker-run` over real Postgres, the census matching `worker_status`, `limit`, the executing drain refused as a value and a 400 with the code, no action-log row, that both the preview and the refused drain claim nothing, and capture/no-key parity); check-fork-consistency PASS; `bunx wrangler deploy --dry-run` builds (the worker surface is unchanged on Workers — the shim throws).

**Not taken.**
- The executing drain (`dry_run: false`). Deferred to the callable worker core (SMD-2304) — the server does not run the bulk LLM passes, and the claim loop is inline in each `db/*.ts` `main()`. Options A (a detached `bun db/<worker>.ts` subprocess, needing SMD-1869's compose `tools` service) and B (a bounded in-process drain through the now-durable job registry) both wait on that; the surface here carries over to whichever lands.
- An action-log row for a dry run (it mutates nothing).
- Enqueuing a re-embed backfill into the pool as the first real consumer (SMD-2320), and retiring/repurposing `scan_thoughts` (SMD-2273's demo consumer) — both wait on the executing drain.

**Follow-ups.** SMD-2304 (the callable worker core) unblocks the drain; SMD-1869 (compose `tools` service) is Option A's home; SMD-2320 (re-embed backfill) and SMD-1794 (the sleep scheduler that runs the passes when idle) are the drain's first consumers.

**Upstream status.** Fork-only; the fork's MCP/REST surface diverges from upstream's.
