## Changelog

A command that drops a schema asks the server which database it reached: `dropSchema` and `tier.ts --refresh` refuse when an exported `PGDATABASE` beat the URL's database, or the URL names no database or no host, and every `db/` script refuses a database URL that Bun and libpq read as different targets (a query key other than `sslmode`, `application_name` and `options`, a fragment, a stray `@`, a host list, a `.`/`..` path segment, a `+` or a malformed part in the query), whatever `OB1_ALLOW_REMOTE_DB` says (SMD-2317).

## FORK

The reset guards ask the connection, not the URL — a URL two clients read as two databases is refused, and PGDATABASE no longer picks what is dropped (SMD-2317)

**What changed.** `db/connect.ts`'s resolver and reset rule, and their two
destructive callers.
- `databaseUrlProblem`, in the resolver every script uses (`databaseUrl`,
  `openSql`), refuses a URL that Bun and libpq take to different places:
  - a query key other than `sslmode`, `application_name` and `options`
    (`URL_QUERY_KEYS`, exact case), or one given twice; a `+` in the query;
    a query part libpq refuses (empty, no `=`, a second raw `=`) or an
    `sslmode` value in capitals;
  - a fragment, an `@` other than the one ending the user, a `,` or `%2C` in
    the host, a path the parser rewrites (a `.` or `..` segment, compared
    decoded, so `/café` stands);
  - whitespace or a control character anywhere, or a scheme that is not an
    exact `postgres://` or `postgresql://`.

  The reason names a query key when it is a plain word, and nothing else of
  the URL.
- The reset rule has a part no override lifts. `identityRefusal` refuses,
  before connecting, a URL the resolver refuses, or one naming no host or no
  database. `reachedDatabaseRefusal` asks the live connection for
  `pg_catalog.current_database()` and refuses one that is not the URL's.
  `socketRefusal` refuses a unix-socket connection unless
  `OB1_ALLOW_REMOTE_DB=1`, which still lifts the loopback host rule.
- `test-support.ts`: `assertThrowawayDatabase` is async and asks the server
  too. `dropSchema` asks on the connection that drops. A refusal no override
  lifts says so instead of offering `OB1_ALLOW_REMOTE_DB`. The five callers
  (`bench-hnsw.ts`, `test-bench-reuse.ts`, three evals) await it.
- `tier.ts --refresh` checks both sides' URLs before opening either, asks
  each side's server for its database at the guard, and asks `--to` again on
  the connection that marks and drops. Every `current_database()` on the
  destructive paths (the mark, the settings reads, `dropSchema`'s resets) is
  `pg_catalog`'s, since `options=` may set search_path.

**Why.** SMD-2302's review measured three readers of one URL disagreeing:
the rule, Bun 1.4.0, and libpq 17's `pg_dump`/`pg_restore`.
- Bun forwards `?database=`/`?user=` to the server, which keeps the last
  value, and connects over a unix socket for `?path=`. Its `options` still
  name the URL's database.
- An exported `PGDATABASE` beats the URL's database in Bun.
  `dropSchema(".../canary")` with `PGDATABASE=stable` dropped stable's
  `thoughts`, `schema_migrations` and `ob1_config`.
- libpq has no fragment, ends the user at the first `@`, and follows
  `?host=`/`hostaddr=`/`port=`/`dbname=`/`service=`. With
  `--to …/canary?host=stable-host`, every guard judged canary and
  `pg_restore` restored into stable-host.

Two passes of that review reconciled the readers by parsing the URL, and
both leaked. This asks the server instead, and refuses what cannot be
reconciled.

**Where the ticket's sketch moved.** The ticket proposed refusing a server
address outside 127.0.0.0/8, and building `pg_restore`'s target from the
server's reported address and port. Through a container's published port,
a connection to `127.0.0.1:55062` reached a server reporting
`inet_server_addr()` 10.88.11.140, port 5432 (podman, measured). So that
rule would refuse every `with-postgres.sh` run and CI's service container,
and that target is unreachable from the host. The database name answers "is
this the database you named" for both a port forward and a tunnel; the
loopback rule stays on the hostname. The ticket's allowlist of `sslmode` and
`application_name` rested on a grep for literal URLs; `test-upgrade` failed
on it, because the fork documents `options=` (`-c search_path=…`) as the
route for a path pgvector sits off (SETUP.md, preflight, SMD-2238). `options`
names no host, database or user, so it is on the allowlist.

**Not taken.**
- Pinning the URL's database in `openSql` (SMD-2302 pass 3 split a run
  across two databases).
- Comparing `inet_server_addr()` with loopback (above).
- `options=-c search_path=x` moves `dropSchema`'s unqualified drops to schema
  `x` of the same database, as before this change; the database is the named
  one. `tier.ts`'s connections after the drop (settle, migrate, stamp) are not
  re-asked: the check guards the drop.
- Objects planted in the target database beyond `current_database()` (an
  `ob1_config` of its own on an `options=` path): the guards stop an
  operator's mistake, and whoever can write the target can already drop it.

**Follow-ups.** SMD-2317's second PR: the environment-borne libpq redirects
(`PGHOSTADDR`, `PGSERVICE`) that reach `pg_dump`/`pg_restore` when the URL
itself is clean, and a URL with no port, where an exported `PGPORT` picks
the server for both clients (review pass 1, measured, as before this
change), and a percent-encoded host libpq decodes (`%2Ftmp` is a socket
directory to it; Bun fails to connect first). Three review rounds found a
libpq URL rule the resolver lacked; that PR removes the class. The plan: a keyword connection string built from the parsed URL, so
libpq parses no URL, the password in `PGPASSWORD`, redirecting `PG*`
variables removed, and a `pg_dump` identity probe of `--to` before the drop.
