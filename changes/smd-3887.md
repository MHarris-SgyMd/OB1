## Changelog

A thought's state on three axes, read from the records the brain already keeps: `thought_validity` says whether it still holds, whether someone decided on it, and whether what was derived from it has caught up, naming the records it read and any it could not (SMD-3887, migration 149). The `validity` tool and `GET /v1/validity` serve it to any read key. It labels only; no default read changes.

## Record

A thought's validity, review and freshness are read from the records that exist — no record contesting it reads unchallenged, never supported (SMD-3887)

**What changed.** Migration 149 adds `thought_validity(uuid[])`, the read `docs/claim-validity.md` decides (rows 1 to 7 and 9 to 11, accepted by the maintainer on 2026-11-19). It is STABLE and SECURITY INVOKER, and writes nothing.
- **The call.** Up to 100 distinct ids, answered in the order given; a repeat is answered once, NULL is `NO_IDS`, and a call over the cap is refused whole (`TOO_MANY`). An id that is no thought answers found false, and forgotten with its time when 139's ledger holds it.
- **Validity:** superseded (068's projection, naming the superseder, the key that wrote its pointer and the proposal that did, if one did); contested (a pending proposal on it as the side that falls, both texts as judged; or a corrected verification whose checkpoint reads current or unmatched); unresolved (the same proposal once a side's text moved since judged, or a stale one; or a corrected verification at an earlier checkpoint, a stale stored key among them); supported (an active citation whose source stands and, one level deep, is neither superseded nor challenged); else unchallenged. Unknown when a table the caller's role cannot read could have set a state above the one found, which is named in `found`.
- **Review:** pending, decided (the reviewer and kind, and whether the pass settled it), checked (every verification, newest first, with its status), unchecked, none.
- **Freshness:** over the lineage rows naming it whose artifact still stands, the worst of stale (an input's key moved, read as `rebuild_derived` reads it), requested (a rebuild asked, or a proposal is stale), legacy and current; none with no such row. A row whose artifact is gone is listed as orphaned and not read. A stale or requested kind no pool re-runs says so. A `source:` pass's extraction stays current on a moved text, as `rebuild_derived` keeps it; a rejection the pass settled is read, since 067 reopens it.
- **Versions and numbers.** Each thought carries its key now (the stored one, else the text's) and its newest audit seq. A judge's number carries `calibrated: false`. Without the audit log, a corrected checkpoint that is neither the text's key nor a stale stored key reads unknown.
- `unread` names each record kind the role could not read.

**The operation** (PR 2b): `validity`, read scope, over REST (`GET /v1/validity?ids=…`, `ids` once per id) and MCP alike. It takes up to 100 ids a call, a repeat counted, by the input's own rule (more is `REFUSED_INPUT`, 400): a REST request line carries about 400 ids before Bun refuses it (431), so the database's raw bound of 1,000 could not be reached. Its value is the read's JSON; its text gives each thought's three states, validity's found state under an unknown, up to three records behind its validity and its three newest review records with who decided or checked, the rest counted, and its orphaned lineage rows counted, a judge's number marked uncalibrated. A role that cannot read thoughts faults it. Preflight's `validity` row says whether 149 is applied, fails when the ledger records 149 but the function is missing, and names a table the server's role cannot read.

**Why.** Seven records say in their own words whether a thought holds, and nothing read them together. SMD-3900's eligible read and the revision tickets beside it (SMD-3895 to SMD-3903) wait on one read and one vocabulary. On stable on 2026-11-19, no lineage row was marked stale while 2,266 standing derived artifacts had been made on a text that has since moved, so freshness is the fingerprint read; and nothing calls `rebuild_derived` on an edit, so a pending proposal on an edited text stays pending, and unresolved is read from fingerprints too.

**Held.** test-schema [134]: the call's shape and refusals; no record reads unchallenged, never supported; each transition the record names, read back through the function (a pointer set and cleared; a proposal pending, its text moved, stale under a forced rebuild, accepted, rejected; a citation's source standing, superseded and deleted; a deliverable unverified, corrected at the current, an earlier and an unmatched checkpoint, and verified again; a lineage row current, stale, requested and current again; a `source:` extraction kept on a moved text; a relation's judge number; a pass-settled rejection read; an orphaned row listed; a checkpoint compared case-blind, and at a stale stored key earlier); one thought unchallenged, pending and stale at once; an unread table unknown on the axes resting on it, without the ledger or the verifications under a generic plan too, and NOT_READABLE without thoughts; forgotten; the function's shape; a re-apply a no-op. test-upgrade [20cl]: refused by name without 068's projection, then applied onto a populated brain, whose thoughts read superseded, contested and unchallenged. Twenty-five mutants of the migration, each killed by [134]. test-rest-sql [28]: both doors alike for a read key, over 100 ids refused by the input's rule (REST 400 `REFUSED_INPUT`, MCP an error), a malformed id 400, a capture-only key 403, a review record's time in the API's form (`…Z`). test-preflight: the `validity` row warns naming `thought_audit` when the role cannot read it, is ok with every table readable, fails when the function is gone while the ledger records 149, and warns when it is gone and the role cannot read the ledger.
