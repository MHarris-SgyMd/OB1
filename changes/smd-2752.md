## Changelog

A database restart while the sleep scheduler starts a pass no longer ends it. Every statement an extraction or consolidation follower makes before its first claim now waits out a database that is not answering, on the follower's outage schedule, and so does the worker key's lookup, which used to carry on with the rows unattributed (but for too many connections, which it still warns of). A stop that lands while the scheduler reads is now a clean stop unless a pass throws, and a heartbeat row once ended is no longer stamped over by a pass still finishing (SMD-2752).

## FORK

A follower's start outlasts the database going away, so the sleep scheduler survives a restart at any sleep (SMD-2752)

**What changed.**
- **The shared wait.** `db/worker-bootstrap.ts` gains `throughOutage(run, { wake, said, out, err })`, moved from `db/sleep.ts`'s `readThrough`. The scheduler's own reads now call it.
  - It runs the statement again after each wait, on `outageWait`'s schedule (SMD-2599: 5 s, doubling, at most 5 min), and the schedule carries across tries.
  - The statement is its own check. A `SELECT 1` on another connection can answer while the statement cannot: the key's lookup opens a connection of its own.
  - It reports the outage once and its end once, and returns null when `wake` ends the wait. Any other error is thrown.
- **What waits.** Under `--follow`, `db/extract-entities.ts` and `db/consolidate.ts` run every statement before the first claim through it (`atStart`):
  - extract: the tables check, the worker key's lookup, and the `entity_extraction_key` read and write;
  - consolidate: the tables check, the worker key's lookup, 079's check, and the relations grant read (`relationsOff`).

  The operators' `--retry-*` statements stay outside the wait. The scheduler never runs them, and a count committed but lost with its connection would be retried into a false 0.

  A stop during the wait returns 130 before the pass begins, so a wake during it stops the pass as one that never started. A run without `--follow` is unchanged: the error still rejects.
- **The key's lookup.** `workerIdentity` gains an `outage` option. An error from `resolve_agent` that matches it is thrown for the caller to wait out. Before this, a database down there was a warning, and the run went on with no agent id on its rows.
  - The followers pass `lookupOutage`: `databaseUnavailable` but not too many connections (53300).
  - The lookup opens a connection of its own beside the pass's pool. At `max_connections` it is refused for as long as the brain stays busy while the pool answers, a wait with no end at every sleep, so that one is still a warning.
- **A stop during a read.** `db/sleep.ts`'s `asleep()` now checks for a stop after its reads, before it looks for a pass that ended.
  - Before this, a stop that landed mid-read, with a pass that settles at once (a pass waiting at its start returns 130), read as "extract ended by itself (exit 130)": the row ended failed and the exit code was 130.
  - A soft stop in the poll that finds a follower outside no longer hard-stops the passes, so the thought in hand finishes.
  - A pass that throws still rejects out of the stop, and the row ends failed.
- **An ended row.** In `db/pass-stamp.ts`, a row once ended takes no stamp, `alive()` or running-timer write; only another end writes it. On a second signal the scheduler ends its row once the leases are returned, but a pass still finishing then stamped its word through the scheduler's stamper, and the row read running and ended at once (test-live [38]'s CLI case caught it under load).

**Why.** The scheduler starts its passes afresh at every sleep, about 16 a day on stable, so a database restarting at any of those starts reached a start statement outside every wait. That threw, the pass's rejection ended the scheduler, and the compose service spent one of its three restarts. A standalone follower meets that window once.

**Not taken.**
- The `workers` profile's followers have no `init: true`, so a `compose stop` while one waits at its start, now for the database too, waits out the grace and ends 137. That gap is SMD-2666's, commented there: the `sleep` service has its init.
- A follower whose `DATABASE_URL` names a host that is down or wrong (Bun says "Failed to connect" for both) waits, saying so once, as the provider's start wait does, where it used to exit and spend its restarts.
- A pass's own fresh pool can meet too many connections (53300) at its start, and then waits it out through the sleep while the scheduler's pool answers. That is better than ending the scheduler. PR 3's waiting word will say so on the row.
- A pass that refuses (exit 2) in the same poll a stop lands is read as stopped, not failed. This was run in pass 2. The operator's stop wins here, as it does at the loop's top and against a follower found, the refusal's own words still print, and the next start meets it again.
- The mutant dropping the stop branch at 079's check is equivalent: the next `stoppedEarly()` returns 130 before anything reads the value.
- An outage at a sleep's start prints up to three near-identical "not answering" lines: the scheduler's, and one for each pass, tagged. Each is true of its own reader.
- A pass's start says "answers again" with no duration, as the scheduler's reads do. The in-pass wait names one.
- From before this ticket, seen on the outage run: a follower woken during its in-pass back-off says "stopped while the database was not answering" after the scheduler has seen it answer; and a SIGINT while the database is down cannot end the row, saying so.
