## Changelog

A database restart while the sleep scheduler starts a pass no longer ends it. Every statement an extraction or consolidation follower makes before its first claim now waits out a database that is not answering, on the follower's outage schedule, and so does the worker key's lookup, which used to carry on with the rows unattributed (but for too many connections, which it still warns of). A stop that lands while the scheduler reads is now a clean stop unless a pass throws, and a heartbeat row once ended is no longer stamped over by a pass still finishing. The scheduler now checks each pass's start once, before its first quiet, so a bad worker key, a model not served (the judge's included) or an extraction key recorded under another model stops the `sleep` service at once with exit 2; each pass's banner is printed once there, and the passes each sleep starts no longer run their end-of-run summary queries. A worker key revoked, or the extraction key moved by another process's `--switch-key`, now ends the service at the next sleep instead of being retried until a restart (SMD-2752).

## FORK

The sleep scheduler survives a database restart at any sleep, checks each pass's start once before its first quiet, says each banner once, and ends on a start refusal no retry mends (SMD-2752)

**What changed** (PR 1, #374).
- **The shared wait.** `db/worker-bootstrap.ts` gains `throughOutage(run, { wake, said, out, err })`, moved from `db/sleep.ts`'s `readThrough`. The scheduler's own reads now call it.
  - It runs the statement again after each wait, on `outageWait`'s schedule (SMD-2599: 5 s, doubling, at most 5 min), and the schedule carries across tries.
  - The statement is its own check. A `SELECT 1` on another connection can answer while the statement cannot: the key's lookup opens a connection of its own.
  - It reports the outage once and its end once, and returns null when `wake` ends the wait. Any other error is thrown.
- **What waits.** Under `--follow`, `db/extract-entities.ts` and `db/consolidate.ts` run every statement before the first claim through it (`atStart`):
  - extract: the tables check, the worker key's lookup, and the `entity_extraction_key` read and write;
  - consolidate: the tables check, the worker key's lookup, 079's check, and the relations grant read (`relationsOff`).

  The operators' `--retry-*` statements stay outside the wait. The scheduler never runs them, and a count committed but lost with its connection would be retried into a false 0.

  A stop during the wait returns 130 before the pass begins, so a wake during it stops the pass as one that never started. A run without `--follow` is unchanged: the error still rejects.
- **The key's lookup.** `workerIdentity` gains an `outage` option. An error from `resolve_agent` that matches it is thrown for the caller to wait out. Before this, a database down there was a warning, and the run went on with no agent id on its rows.
  - The followers pass `lookupOutage`: `databaseUnavailable` but not too many connections (53300).
  - The lookup opens a connection of its own beside the pass's pool. At `max_connections` it is refused for as long as the brain stays busy while the pool answers, a wait with no end at every sleep, so that one is still a warning.
- **A stop during a read.** `db/sleep.ts`'s `asleep()` now checks for a stop after its reads, before it looks for a pass that ended.
  - Before this, a stop that landed mid-read, with a pass that settles at once (a pass waiting at its start returns 130), read as "extract ended by itself (exit 130)": the row ended failed and the exit code was 130.
  - A soft stop in the poll that finds a follower outside no longer hard-stops the passes, so the thought in hand finishes.
  - A pass that throws still rejects out of the stop, and the row ends failed.
- **An ended row.** In `db/pass-stamp.ts`, a row once ended takes no stamp, `alive()` or running-timer write; only another end writes it. On a second signal the scheduler ends its row once the leases are returned, but a pass still finishing then stamped its word through the scheduler's stamper, and the row read running and ended at once (test-live [38]'s CLI case caught it under load).

**What changed** (PR 2).
- **The engines' start, typed and checkable.** `db/extract-entities.ts` and `db/consolidate.ts` gain four options:
  - `check: true` runs a follower's start alone and returns 0 before the pass's first write (the key's lookup writes, as at every start: it is how a revoked key is found), without waiting for a provider that does not answer: the banner, the egress gate, the tables, the model's probe (extract's escalation listing too), the worker key, and extraction's recorded key (consolidate: its 079 and relations reads);
  - `banner: false` leaves out the start's banner: the job, model, window and egress lines, the agent line or the no-key warning, the key's note and the workers line (consolidate's relations note is said at the check and again by every pass, as grants can change between sleeps);
  - `summary: false` leaves out the end-of-run counts, graph, queue, partial and failed rows, and a stopping pass's last count of the pool;
  - `onStart(result)` reports the start: through, the provider up or out; or refused, as one of `usage`, `egress`, `tables`, `model`, `provider`, `identity`, `key` or `lookup` (`StartRefusal` in `db/worker-bootstrap.ts`, with `PERMANENT_REFUSALS` and `probeRefusal`). Every start refusal reports one; a mid-pass refusal is not a start's.
- **The scheduler's start.** Before its first quiet, `db/sleep.ts` runs each pass with `check`. A refusal ends it with 2 at once, `heartbeat:sleep` ended failed (the same `endAtStart` the follower refusal uses), naming the pass and the kind. A start that got through with the provider answering counts as the pass's first start in this process (`begun`). A provider that does not answer is no refusal: each pass waits for it at its own start, as before.
- **The passes each sleep starts** run with `banner: false` and `summary: false`, so a sleep prints no banner and a wake waits for no scan of the graph.
- **The refusal rule.** A pass's start refusal of a kind in `PERMANENT_REFUSALS` (`usage`, `egress`, `tables`, `identity`, `key`) ends the scheduler with 2 at any sleep. Until now a revoked worker key or another process's `--switch-key` was retried until a restart, since the pass had got through its start before. `model`, `provider` and `lookup` (the egress gate asked again without the worker key as actor, its lookup not having named it) keep the rule: retried once the pass got through its start (now the check counts), the configuration's otherwise.

**Why.** PR 1: the scheduler starts its passes afresh at every sleep, about 16 a day on stable, so a database restarting at any of those starts reached a start statement outside every wait. That threw, the pass's rejection ended the scheduler, and the compose service spent one of its three restarts. A standalone follower meets that window once. PR 2: the service met its configuration only at the first quiet — seconds or hours after its start, and for consolidation's judge only once extraction's backlog drained, which then ended the service — and printed each pass's whole banner (about 20 lines for extract, 13 for consolidate) at every sleep, roughly 300–500 lines a day on stable. Every wake waited for the passes' end-of-run summaries, `count(DISTINCT thought_id)` over the mentions and the like, scans at the moment the brain is live again.

**Not taken.**
- PR 2, moved to PR 3: preflight's `sleep` row reads a service ended by a start refusal as "ended on a failure … start it again", which would only refuse again. The row records `failed` and not which refusal, and was the same before this PR when the first sleep met it. Saying the kind on the row, and preflight the remedy, belongs with PR 3's word on the same row.
- PR 2: no test fails if a stopping pass's skipped last count comes back, since it prints nothing. The scratch stack's `log_statement=all` Verify held it. The check's probes also call each model once at the service's start, whatever the traffic: on a tight GPU that may swap a model in once per start.
- PR 2: a provider refusing the check's probe (a gateway answering 401, 404 while it starts) or a model `ollama-pull` is still pulling at a first boot ends the check, and compose's three restarts can pass before it is ready. That is the `workers` profile's rule for a follower's start, which compose.yaml's own comment calls configuration a restart does not fix; the deploy README says to start `sleep` once the pull is done.
- PR 2: `lookup` is every lookup that did not name the key, so it also retries a lasting cause after a pass got through its start — EXECUTE on `resolve_agent` revoked, the function dropped mid-run — on the 5-minute cap, the row failed meanwhile. The causes seen are passing (53300, a lock timeout), and telling them apart would need `workerIdentity` to return the error it warns of. At the check, a first start, `lookup` ends the service with 2, as `model` and `provider` do there.
- PR 2: the `lookup` label at the two re-gate sites has no live case: it needs an actor-only egress policy against a remote endpoint and a lookup that fails. test-worker-bootstrap holds that `lookup` is not permanent.
- The `workers` profile's followers have no `init: true`, so a `compose stop` while one waits at its start, now for the database too, waits out the grace and ends 137. That gap is SMD-2666's, commented there: the `sleep` service has its init.
- A follower whose `DATABASE_URL` names a host that is down or wrong (Bun says "Failed to connect" for both) waits, saying so once, as the provider's start wait does, where it used to exit and spend its restarts.
- A pass's own fresh pool can meet too many connections (53300) at its start, and then waits it out through the sleep while the scheduler's pool answers. That is better than ending the scheduler. PR 3's waiting word will say so on the row.
- A pass that refuses (exit 2) in the same poll a stop lands is read as stopped, not failed. This was run in pass 2. The operator's stop wins here, as it does at the loop's top and against a follower found, the refusal's own words still print, and the next start meets it again.
- The mutant dropping the stop branch at 079's check is equivalent: the next `stoppedEarly()` returns 130 before anything reads the value.
- An outage at a sleep's start prints up to three near-identical "not answering" lines: the scheduler's, and one for each pass, tagged. Each is true of its own reader.
- A pass's start says "answers again" with no duration, as the scheduler's reads do. The in-pass wait names one.
- From before this ticket, seen on the outage run: a follower woken during its in-pass back-off says "stopped while the database was not answering" after the scheduler has seen it answer; and a SIGINT while the database is down cannot end the row, saying so.
