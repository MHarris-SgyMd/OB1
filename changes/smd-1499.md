## Changelog

Preflight warns when the server is too small for the brain (SMD-1499). `vector index memory` compares the HNSW indexes over `thoughts` and `thought_chunks` with `shared_buffers`, and `filter bitmap memory` compares the bitmap a broad filter collects (64 bytes a heap page) with `work_mem`; each names the setting the brain needs. The compose stacks take `POSTGRES_SHARED_BUFFERS` and `POSTGRES_WORK_MEM`, defaulting to the image's 128MB and 4MB, and `db/with-postgres.sh` takes `OB1_PG_ARGS`. Measured at ten million rows, sizing `shared_buffers` to the indexes gives about three times the throughput at ten connections.

## FORK

The server sized for the table — preflight compares the HNSW indexes with shared_buffers and a broad filter's bitmap with work_mem, the compose stacks take both settings, and at ten million rows the sized pool triples ten-connection throughput (SMD-1499)

**What changed.**
- **`db/config.mjs`:** `memorySizing`, the rule as a pure function of the numbers preflight reads, and `BITMAP_BYTES_PER_PAGE` (64).
  - *Resident:* the HNSW indexes against `shared_buffers`, the lever an operator sets, rounded up to 64 MB. Pages the OS page cache holds serve a walk too (change 80), so this is a warning and says so.
  - *Bitmap:* a filter's matches are collected one entry per heap page. PostgreSQL 16's `tidbitmap.c` sizes an exact entry at 48 bytes plus two hash pointers and caps the exact entries at `work_mem` divided by that; past it the bitmap goes lossy and every lossy page is rechecked row by row. A filter whose matches lie across the `thoughts` heap needs heap pages × 64 bytes, rounded up to a whole MB.
- **`server-portable/preflight.ts`:** two rows after `filtered search`, both warnings, since a managed platform may not let the operator change either setting.
  - `vector index memory` finds the HNSW indexes by access method, so 039's halfvec swap and any later rename read alike.
  - `filter bitmap memory` reads the `thoughts` heap's main fork. Its remedy prices the recommendation at about one `work_mem` per connection of this server's pool (`OB1_PG_POOL`), as measured below.
  - A `thoughts` that isn't on the search_path is a skip, not a fit; a failed read prints both rows. Both join `DIRECT_CHECKS`, so the PostgREST path prints each as a catalog-only skip.
- **`deploy/compose.yaml`, `deploy/compose.tiers.yaml`:** the postgres services run with `shared_buffers=${POSTGRES_SHARED_BUFFERS:-128MB}` and `work_mem=${POSTGRES_WORK_MEM:-4MB}`, the image's own defaults, so an unset `deploy/.env` runs exactly as before. Check 27 holds the tiers file to the same command.
- **`db/with-postgres.sh`:** `OB1_PG_ARGS`, `-c name=value` pairs only, each checked.
- **Docs:**
  - `deploy/.env.example` has the rule with the shipped width's figures: halfvec at about 2.5 KB a vector, so 128MB holds about 50,000 vectors; 4MB of `work_mem` covers 65,536 heap pages.
  - `deploy/README.md` and `server-portable/README.md` describe the two rows.

**Why.** SMD-1018 measured the 10M bench at the container's defaults: a 5.4 GB HNSW index against 128 MB of `shared_buffers`, and a broad filter's generic plan rechecking 460,687 lossy heap blocks (11.6 s). SMD-1500 then found ten connections capped at about 4× one connection's throughput with the database on half its CPUs (SMD-2750). Nothing derived a server size from the table, and preflight said nothing. On the stable brain today (1,764 thoughts, 6.5 MB of HNSW, 373 heap pages) both rows are ok.

**Held.**
- test-schema [74] (+7): the 64 bytes; fits and does not fit at the boundary, one MB of index and one heap page past it; the 64 MB and 1 MB rounding and its floor; change 28's 10M corpus (`work_mem` 31MB, `shared_buffers` 6592MB); `bytesText`.
- test-preflight (+2): both rows ok on the fixture. With 4,500 inline rows (1,125 heap pages) under `ALTER DATABASE … SET work_mem = '64kB'`, the bitmap row warns, naming the `work_mem` and its cost across the pool. Over PostgREST the catalog-only skips are 24, the two rows among them.
- test-live [40] (+1): the 64 bytes against the server. A ~2,000-page heap and a forced bitmap heap scan, 16 kB either side of the rule: lossy under it, exact over it. So a server whose entry is another size fails there, rather than leaving preflight's arithmetic quietly wrong. First measured on PostgreSQL 16.15 at 4,243 pages: lossy at 256 kB, exact from 272 kB, the rule's 265 kB between them.
- `OB1_PG_ARGS` was run: the settings reach the server, and a value with `;` and a bare `name=value` are refused.

**Measured after.** The kept 10M bench corpus (`hnsw10m`, 64 dimensions; HNSW 6.4 GB, heap 3.9 GB) on SMD-1500's VM (8 vCPUs, 14.8 GB), four runs back to back on one day with `OB1_BENCH_LOAD=1,10`. The order matters, because the VM's page cache outlives a container: the first run started cold, and every later one warm. So the comparison is the warm defaults' column against the two sized ones.

| 10M rows | defaults, cold | defaults, warm | `shared_buffers` 6592MB | + `work_mem` 31MB |
| --- | ---: | ---: | ---: | ---: |
| unfiltered QPS, 1 → 10 connections | 71 → 355 | 82 → 411 | 162 → 1,194 | 181 → 1,400 |
| database CPUs at ten (of 8) | 3.4 | 3.3 | 7.1 | 7.1 |
| broad (50%) QPS at ten | 194 | 230 | 636 | 593 |
| 50% / 10% / 1% median alone, ms (B) | 31 / 111 / 1,302 | 20 / 68 / 660 | 11 / 36 / 508 | 14 / 41 / 951 |
| exact branch at 1% / 0.1%, ms (E) | 2,109 / 230 | 1,691 / 218 | 1,010 / 115 | 925 / 141 |
| generic plan, 50% walk, ms (C) | 58,232 | 19,726 | 29,864 | 14,938 |
| forced generic walk, 0.01%, ms (D) | 21 | 16 | 16 | 1,425 |
| ten broad filters' memory growth, MiB | 5 | 4 | 4 | 229 |

Read together:
- **`shared_buffers` is the lever.** With the indexes resident, ten connections go from about 5× one connection's throughput to 7–8×, the database runs CPU-bound (7.1 of 8), and the broad path's QPS nearly triples. SMD-1500's ceiling was waits inside the server, not the client or the port forward (SMD-2750). The medians alone improve too.
- **`work_mem` at the rule** helps the exact branch on the band tier (1,010 → 925 ms) and the generic plan's lossy bitmap. It also changes the forced generic plans: section D's chunk side took the HNSW index under it, 16 ms → 1.4 s. `match_thoughts` runs its walk through `EXECUTE` (074) and is planned per call, so its own calls (B, E, F) don't take that plan.
- **What a larger `work_mem` costs is memory, about one `work_mem` per busy connection.** A direct run, ten connections on broad filters for 20 s each: 51 MiB of growth at 4MB, 260 MiB at 31MB with `hnsw.scan_mem_multiplier` 8, and 257 MiB at 31MB with it at 1, at 785–801 QPS. So the multiplier does not bound it, and the remedy prices `work_mem` against the pool instead.
- **The band tier's latency does not follow `work_mem`.** B's 508 → 951 ms is inside its run-to-run spread (508–1,302 ms across the day's four runs). A direct run of 30 queries put it at 507 ms at 4MB, 522 ms at 31MB ×8 and 527 ms at 31MB ×1, every answer identical.
- **The bench pins the vector-search bounds to 014's seeds,** so the sized runs kept `hnsw.scan_mem_multiplier` 8; the direct runs above set it per session.

**Review passes.** None yet.

**Not taken.**
- `work_mem` set on `match_thoughts` itself: that is a migration, and SMD-1464 decides plan mode.
- A container memory limit read by preflight: the cgroup is readable only by a superuser, and the servers' role is not one.
- Lowering `hnsw.scan_mem_multiplier` alongside a larger `work_mem`: measured above, it changes neither memory nor latency. An earlier draft of the remedy recommended it.
