## Changelog

Preflight warns when the server is too small for the brain (SMD-1499). `vector index memory` compares the HNSW indexes over `thoughts` and `thought_chunks` with `shared_buffers`, and `filter bitmap memory` compares the bitmap a broad filter collects (64 bytes a heap page) with `work_mem`; each names the setting the brain needs. The compose stacks take `POSTGRES_SHARED_BUFFERS` and `POSTGRES_WORK_MEM`, defaulting to the image's 128MB and 4MB, and `db/with-postgres.sh` takes `OB1_PG_ARGS`.

## FORK

The server sized for the table — preflight compares the HNSW indexes with shared_buffers and a broad filter's bitmap with work_mem, and the compose stacks take both settings (SMD-1499)

**PR 1 — the rule and the warning.**

**What changed.**
- **`db/config.mjs`:** `memorySizing`, the rule as a pure function of the numbers preflight reads, and `BITMAP_BYTES_PER_PAGE` (64).
  - *Resident:* the HNSW indexes against `shared_buffers`, the lever an operator sets. Pages the OS page cache holds serve a walk too (change 80), so this is a warning, and its text says so. The recommendation is the index size rounded up to 64 MB.
  - *Bitmap:* a filter's matches are collected one entry per heap page. PostgreSQL 16's `tidbitmap.c` sizes an exact entry at 48 bytes plus two hash pointers, and caps the exact entries at `work_mem` divided by that; past it the bitmap goes lossy and every lossy page is rechecked row by row. A filter whose matches lie across the `thoughts` heap needs heap pages × 64 bytes.
  - *The walk's cap:* raising `work_mem` raises each HNSW walk's memory cap (`work_mem` × `hnsw.scan_mem_multiplier`, 014's header). `keepMultiplier` is the multiplier that keeps the cap under the recommended `work_mem`, and `capRises` says when none can.
- **`server-portable/preflight.ts`:** two rows after `filtered search`, both warnings, since a managed platform may not let the operator change either setting.
  - `vector index memory` finds the HNSW indexes by access method, so 039's halfvec swap and any later rename read alike.
  - `filter bitmap memory` reads the `thoughts` heap's main fork. Its remedy names `ALTER DATABASE … SET work_mem` and the multiplier that keeps the walk's cap.
  - Both join `DIRECT_CHECKS`, so the PostgREST path prints each as a catalog-only skip. A failed read prints both rows.
- **`deploy/compose.yaml`, `deploy/compose.tiers.yaml`:** the postgres services run `postgres -c shared_buffers=${POSTGRES_SHARED_BUFFERS:-128MB} -c work_mem=${POSTGRES_WORK_MEM:-4MB}`, the image's own defaults, so an unset `deploy/.env` runs exactly as before. Check 27 holds the tiers file to the same command.
- **`db/with-postgres.sh`:** `OB1_PG_ARGS`, `-c name=value` pairs only, each checked, for a bench to measure the server sized for the table (PR 2).
- **Docs:**
  - `deploy/.env.example` has the rule with the shipped width's figures: halfvec at about 2.5 KB a vector, so 128MB holds about 50,000 vectors; 4MB of `work_mem` covers 65,536 heap pages.
  - `deploy/README.md` and `server-portable/README.md` describe the two rows.

**Why.** SMD-1018 measured the 10M bench at the container's defaults: a 5.4 GB HNSW index against 128 MB of `shared_buffers`, and a broad filter's generic plan rechecking 460,687 lossy heap blocks under 4 MB of `work_mem` (11.6 s). Nothing in the repo derived a server size from the table, and preflight said nothing when the indexes outgrew the pool.

On the stable brain today, 1,764 thoughts, the indexes are 6.5 MB and the heap 373 pages: both rows are ok.

**Held.**
- test-schema [74] (+8): the 64 bytes; fits and does not fit at the boundary, one MB of index and one heap page past it; the 64 MB and 1 MB rounding; the multiplier that keeps a 32 MB cap (6 at 5 MB); change 28's 10M corpus (`work_mem` 31MB at multiplier 1, `shared_buffers` 6592MB); a heap whose need passes the cap; `bytesText`.
- test-preflight: both rows ok on the fully migrated fixture. With 4,500 rows of ~1.9 KB (inline, past 1,024 heap pages) and `ALTER DATABASE … SET work_mem = '64kB'`, `filter bitmap memory` warns, naming the `work_mem` and the multiplier. Over PostgREST the catalog-only skips are 24, the two rows among them.
- test-live [40] (+1): the 64 bytes against the server. A ~2,000-page heap, a forced bitmap heap scan, and `work_mem` 16 kB either side of pages × 64 bytes: lossy under it, exact over it. So a server whose bitmap entry is another size (a later PostgreSQL) fails there, rather than leaving preflight's arithmetic quietly wrong. Measured first on PostgreSQL 16.15 at 4,243 pages: lossy at 256 kB (2,065 lossy blocks), exact from 272 kB, the rule's 265 kB between them.
- `OB1_PG_ARGS` was run: the settings reach the server, and a value with `;` and a bare `name=value` are refused.

**Not taken.**
- `work_mem` set on `match_thoughts` itself: that is a migration, and SMD-1464 decides the plan mode the 11.6 s cell turns on.
- A container memory limit from preflight: the cgroup is readable only by a superuser, and the servers' role is not one.
