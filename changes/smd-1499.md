## Changelog

Preflight warns when the server is too small for the brain (SMD-1499). `vector index memory` compares the valid HNSW indexes over `thoughts` and `thought_chunks` with `shared_buffers`, and `filter bitmap memory` compares with `work_mem` the bitmap of the broadest filter the router leaves on the GIN route; each names the setting and the statement that sets it. `db/with-postgres.sh` takes `OB1_PG_ARGS`. Measured at ten million rows, `shared_buffers` sized to the indexes gave about three times the throughput at ten connections.

## FORK

The server sized for the table — preflight compares the HNSW indexes with shared_buffers and the broadest GIN-routed filter's bitmap with work_mem, and at ten million rows a sized pool triples ten-connection throughput (SMD-1499)

**What changed.**
- **`db/config.mjs`:** `memorySizing`, the rule as a pure function of the numbers preflight reads, `BITMAP_BYTES_PER_PAGE` (64) and `BITMAP_PAGE_SHARE_GATED` (1 − 1/e).
  - *Resident:* the HNSW indexes against `shared_buffers`, rounded up to 64 MB.
  - *Bitmap:* PostgreSQL 16's `tidbitmap.c` sizes an exact page entry at 48 bytes, and `tbm_calculate_entries` divides `work_mem` by that plus two pointers. Past it the bitmap goes lossy and rechecks whole pages.
    - Which filters build a bitmap is 074's router's choice. On a heap of 8,192 pages or more, 037's gate sends a filter to the HNSW walk, which builds none, only when its 8-page sample holds at least 8 hits on 3 pages. So every filter averaging under about one match a page takes the GIN route, and one at that rate, placed at random, touches 1 − 1/e of the pages.
    - Below the gate every filter takes the GIN route, so the whole heap counts there.
- **`server-portable/preflight.ts`:** two rows after `filtered search`, both warnings, since a managed platform may not let the operator change either setting.
  - `vector index memory` counts valid HNSW indexes by access method, so 039's halfvec swap, a later rename and an INVALID or staging index are read correctly. Its remedy is `ALTER SYSTEM SET shared_buffers` and a restart of postgres.
  - `filter bitmap memory`'s remedy is `ALTER DATABASE … SET work_mem` and a restart of the servers. It prices that at one `work_mem` per pooled connection (the MCP server and the REST core each hold `OB1_PG_POOL`). It also says to raise it watchfully: `match_thoughts`' default walk is static SQL that plpgsql can move to a cached generic plan, and a larger `work_mem` changed the generic plans (below; SMD-1464).
  - A `thoughts` that doesn't resolve is a skip, not a fit. Each row prints once on every path, and both join `DIRECT_CHECKS` for the PostgREST path.
- **`db/with-postgres.sh`:** `OB1_PG_ARGS`, `-c name=value` pairs only, each checked.
- **Docs:** `deploy/.env.example` has the rule and the two statements; `deploy/README.md` and `server-portable/README.md` describe the rows.

**Why.** SMD-1018 measured the 10M bench at the container's defaults (128 MB `shared_buffers`, 4 MB `work_mem`), and SMD-1500 found ten connections capped at about 4× one connection's throughput with the database on half its CPUs (SMD-2750). Nothing derived a server size from the table, and preflight said nothing. On the stable brain today (1,764 thoughts, 6.5 MB of HNSW, 373 heap pages) both rows are ok.

Read together:
- **`shared_buffers` is the lever.** The page cache held the indexes in every run. Moving them into `shared_buffers` took ten connections from about 5× one connection's throughput to 7–8×, ran the database CPU-bound (7.1 of 8), and nearly tripled the broad path's QPS. So SMD-1500's ceiling was waits inside the server, not the client or the port forward (SMD-2750). The page cache alone gave about a third of the throughput.
- **The exact branch's cost per row** at 0.1% (10,231 rows) went from 21 µs (warm defaults) to 11–14 µs, towards the ticket's 6–8 µs at 1M but not to it.
- **`work_mem` at 31MB changed generic plans.** In section C the 2,000-row walk's chunk side took the HNSW index (27 ms → 17.4 s), and section D's forced generic walk followed (16 ms → 1.4 s). The bench prints no lossy counts, so the 50% generic cell (58 → 15 s, noisy) is not put down to the bitmap.
  - `match_thoughts`' default walk is static plpgsql SQL. Only the `min_trust` walk runs through `EXECUTE` (074), so the default one can take a cached generic plan.
  - It did not here: B's 50 calls a session and F's thousands stayed on custom-plan latencies (the 2,000-row tier 47 ms in both runs).
  - That is plpgsql's cost choice, not a guarantee, and why the remedy says to raise `work_mem` watchfully; SMD-1464 settles plan mode.
- **What a larger `work_mem` costs is memory.** A direct run on this corpus, ten connections on 50% filters for 20 s each: 51 MiB of growth at 4MB, 260 MiB at 31MB ×8, 257 MiB at 31MB ×1.
  - The 50% walk visits about 80 tuples, and 014's tuple cap (about 21 MB a node here) binds before 31MB × 1. So the growth is from elsewhere in the plan, and these runs say nothing about the multiplier on walks that run long.
  - The bench's own broad-10 runs grew 4–5 MiB at 4MB; the direct run's fresh pools grew more, and only each run's deltas are compared.
- **The band tier's latency does not follow `work_mem`.** A direct run of 30 queries: 507 ms at 4MB, 522 ms at 31MB ×8 and 527 ms at 31MB ×1, every answer identical.

**Not met, or met another way.**
- "The 11.6 s generic plan loses its lossy blocks": lossy counts were not measured, and today's 50% generic cell is 15–58 s across runs.
- "test-live covers the check with the default and a SET-lowered pool": test-preflight covers the `work_mem` row both ways. The `shared_buffers` warning runs end to end nowhere, since a pool cannot be lowered for one database; test-schema holds its arithmetic.
- The bench ran at `work_mem` 31MB, the first rule's figure for this corpus, not the ticket's 64MB.
- Managed platforms: the remedies name the parameter group, no more.

**Not taken.**
- Compose knobs for the two settings: `postgres -c` outranks `ALTER SYSTEM` and `postgresql.conf`, so a default there would reset an operator's tuning on upgrade.
- Lowering `hnsw.scan_mem_multiplier` alongside a larger `work_mem`: on this corpus it changed neither memory nor latency, and these walks never reached it.
- A container memory limit read by preflight: the cgroup is readable only by a superuser.
