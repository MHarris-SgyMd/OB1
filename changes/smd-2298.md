## Changelog

`update_thought` settles the tags' lineage row when a re-tag comes out the same (migration 148, SMD-2298 PR 1a). When the envelope names the tags' recipe and the row the call would leave is not the row standing — there is none, it is marked stale, or it names another fingerprint or recipe — the row is recorded, with no event. So a row `rebuild_derived` marked stale clears, and a thought tagged before 061 gains its row, once the extractor runs on its text again. A re-send under the recipe the row already names, on its text, still records nothing, and a row whose metadata is SQL NULL (which takes no patch) is never settled. **Upgrading:** `bun db/migrate.ts`; nothing else changes until SMD-2298's re-tag worker (PR 1b) runs.

`bun db/retag.ts` re-tags every thought whose tags are behind its text (SMD-2298 PR 1b, SMD-3318 PR 3b): tagged with no tags row (before 061), its tags row marked stale or at other text, or a capture that fell back. It runs the capture's own extractor through the egress gate and writes through `update_thought` with the extractor's recipe, so the row is re-recorded and the mark cleared, with no event when the tags came out the same. It takes `--status`, `--dry-run`, `--limit`, `--retry-failed` and `--switch-key`, and records its key in `ob1_config.retag_key`; each run pools the backlog itself until `rebuild_derived` feeds it. thought-enrichment's `enrich-thoughts.mjs`, the last of that recipe's scripts on the SQL shim, is retired for it: its summary, importance and confidence fields are not the core's. **Upgrading:** run `bun db/retag.ts --url … --status` to see the backlog, then `bun db/retag.ts --url …`; a job that ran `enrich-thoughts.mjs` runs `db/retag.ts` instead.

`rebuild_derived` hands a stale tags row to the re-tag pool (migration 150, SMD-2298 PR 2): with `ob1_config.retag_key` recorded by `db/retag.ts`, a text move's rebuild requeues the thought under that key, as it requeues an extraction under its own, and `db/rebuild.ts` names `bun db/retag.ts` as the pool's drainer; with no key recorded the row is marked alone, as before. **Upgrading:** `bun db/migrate.ts`. Preflight gains a `retag pass` row (SMD-2298 PR 3a). It counts each `retag:` key's pool by the rule the `re-embed pass` and `consolidate pass` rows use. A pool reads as a run in progress, rows waiting for a run (one that stopped, or a rebuild's requeue), a worker that died holding a lease, or an earlier key's pool that no worker runs any more. Waiting rows get the command that finishes them under the key's own model; a key at an older prompt version than this tree's gets `--switch-key`, and one a newer tree recorded is left to that tree. With nothing unfinished, the row says how many thoughts are behind their tags and waiting for a run. The backlog's predicate moves from `db/retag.ts` to `db/config.mjs` (`RETAG_DUE_SQL`, `RETAG_BACKLOG_SQL`), so the worker and the row count one backlog. The recorded key is now the tags' target recipe (SMD-2298 PR 3b): a tags row made under another model or prompt version is behind it, so a first run, or a `--switch-key` to a new model or prompt version, re-tags the corpus under its key, and `--status`, `--dry-run` and the refusal count the backlog as recording a key finds it; preflight says where the server tags captures under another key than the recorded one. `bun db/retag.ts --follow [SECONDS]` keeps re-tagging (SMD-2298 PR 4a-2): it polls, pooling again at each pass, waits out a provider or a database that stops answering, and stamps `heartbeat:retag:<job>`, which preflight reads.
