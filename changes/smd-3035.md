## Changelog

What a supersession proposal's review says an accept would clear is now the same walk the accept's lapse runs, not a copy of it kept in step by hand (SMD-3035). The listings read as before, and an accept's `lapsed:` lines now come in the order the listing named them. The lapse itself changes only on cycles a raw write closed and past its 1,001-row bound.

## FORK

One definition for 082's lapse: the trigger clears what `ob1_lapse_walk` returns, and the review listing's read returns it (SMD-3035)

**What changed** (migration 096).
- **`ob1_lapse_walk(row, onto)`**: the pointers 082's lapse clears for an event that leaves the row's pointer at `onto`, as `[{id, onto}]` in the order they are cleared. None unless the row is taken now (094's `ob1_accept_takes`: 092's read). Otherwise it walks up from the row: each row's capturer's capture-scoped pointers onto it that no update has re-pointed (never the row's own); on through the pointers that stay; and on from a cleared row 082's log had already taken; up to 1,000 rows above.
- **`ob1_lapse_capture_pointers()`** (092's trigger) keeps its gates and clears what the walk returns. Each pointer is re-read under its row lock and left alone if it moved or an update has written it since. The re-read of "an update has written it since" is a statement of its own once the lock is held, so a writer the lock waited for is seen. Its own clearing events do not fire it again: each is named in `ob1.lapse_clearing` (transaction-local) before it is appended, and only a firing from inside a trigger on an event that is that clear and nothing else reads it. A write function's event fires at depth 1, so a flag set by hand turns none of its lapses off; a raw write's or a cascade's pure clear of exactly the pair named it can, which a raw writer can do worse than. The walk already went on from them.
- **`ob1_accept_lapses(side, other)`** (094's read) keeps its own no-event gates (the side already points somewhere; the pointer would loop or run past update_thought's 1,001-row walk) and then returns the walk.
- `ob1_accept_takes`' comment names it the walk's gate; its body is 094's.

**Three changes to the trigger**, all the walk's (the first two the maintainer's choice at the plan stage, the third found in review pass 1):
- **The bound:** the walk-on shares the event's one 1,001-row bound, where 092 gave each re-firing a fresh one.
- **The order:** clears land breadth-first, in the walk's order, where 092's re-firing cleared the pointers onto a cleared taken row before that row's siblings'. `db/consolidate.ts --accept` prints its `lapsed:` lines in that order (by the audit log's `seq`; they were sorted by event uuid, so in no order).
- **The event's own row:** never cleared, through the walk-on too. A raw write's cycle back through it let 092's re-firing clear the event row's own pointer, whose clear then projected ahead of the event, and 060 refused the write.

Outside raw cycles, none changes what is cleared below the bound.

**Why.** 094's read was 092's trigger copied and kept in step by hand. SMD-2707's review passes 2–4 found it drifting four times, each caught only by a one-off fuzz:
- lapses promised for refused accepts;
- the loop bound;
- the walk on from a row the log already took;
- the takes gate.

A later change to the trigger that missed the copy would make the listing promise lapses that don't happen, or hide ones that do.

**Not here.**
- Why a pointer lapsed, on its own event: SMD-2933.
- The listing's cost: SMD-3036.
- The fuzz as a committed check (SMD-3038): it would now compare one function with itself.
- The walk past its bound is held by review, not by a suite (as 092).
- The walk reads one snapshot; each cleared row is re-read under its lock, not the path below it. A write key moving a link between the two still has the pointers above it cleared, and a link moved in misses its own. Under an accept only an unlink moves one, since a re-point onto a thought waits on the review lock and an unlink takes none (088). 092 had the same window, one level wide (raced live in review pass 2). Follow-ups: SMD-3046 (the path), SMD-3045 (an unlink taking the review lock).

**Tests.**
- test-schema [86]:

  - the read, the walk and the listing agree on one case;

  - the walk stops at a cleared row 082's log never took, even when that row's chain reached outside;
  - the flag reset after the lapse, and a second taking in the same transaction lapses;
  - a flag set by hand turns no lapse off: not for the very unlink a write key then makes of a taken row, and not for a raw write that moves the text with the pointer;

Only a writer committing between the walk's read and the lock tells them apart, so the re-read is held by review, as 092's EvalPlanQual re-check was. Review pass 2 raced the trigger against concurrent writers on a real Postgres, with the window widened: a re-point onto a thought, a delete and a capture-only key's capture all came out correct, and the snapshot residual under Not here was reproduced, as under 092.

Review pass 3 diffed every reader live, main against the branch, and found them the same apart from the two documented changes, with the branch's log replaying to the same state under either schema.
