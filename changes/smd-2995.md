## Changelog

`list_thoughts` pages: `sort` newest (the default) or oldest first, and `after`, the cursor the previous page ended with, so a GUI list or an agent can walk every thought once, whatever is captured meanwhile. A cursor of the other sort, or no cursor of this tool's, is refused (SMD-2995).

## FORK

list_thoughts pages by a keyset cursor, newest or oldest first — every thought once, to the microsecond, in index time at any depth outside a tie (SMD-2995)

**What changed.**
- **`core/schemas.ts`:** `list_thoughts` takes `sort` (`newest`, the default, or `oldest`) and `after`, and its description says how to page. `limit` is a whole number from 1 to 1000; 0 or -1 had read as an empty brain, 1.5 rounded, and 2^31-1 overflowed the row read past the page. `days` is positive and at most 365,000 (a larger one put the window's start past timestamptz's range, a 500), and says its window moves with each call, so its oldest can leave it between pages.
- **`core/list-cursor.ts`** (new) and **`core/reads.ts`:**
  - `listCursor` / `parseListCursor`, in a module of their own so `render.ts` can read them: the cursor is base64url of `[sort, at, id]`, where `at` is Postgres's own text of the page's last `created_at` (null when undated).
  - A cursor is read back only if:
    - its sort is one of the two;
    - its id is a uuid;
    - `at` is timestamptz's text shape: a day its month has, BC's leap years Postgres's, or ±infinity.
  - A cursor of that shape whose time Postgres's cast still cannot read (a year 0, past timestamptz's range, an offset past ±15:59) is the store's `ListCursorRefused` (SQLSTATE 22007, 22008, 22009 from reading the cursor's time alone, before the page), so the core gives the same refusal, never a fault quoting the value, and no other cast error is taken for it.
  - The reply carries `sort` and `cursor`. `cursor` is null exactly when no thought follows; the store reads one row past the page to know.
- **`core/refusal.ts`:**
  - `REFUSED_CURSOR` gains `reason` (`shape` or `sort`) and, for `sort`, the sort the cursor was made under, as facts.
  - The cursor itself is never echoed.
- **`store.ts` / `store-sql.ts`:** `listThoughts` returns a page, `{ thoughts, next }`, and takes `sort` and `after`.
  - **The order:** `thoughts_created_at_idx`'s own order. Newest first is `created_at DESC` with the undated first, ties by id; oldest first is its reverse.
  - **Two runs:** each order is read as two runs, the undated and the dated, each by a plain index condition (`created_at IS NULL`, or `<=`/`>=` the cursor's). The next run is read only while the page is short.
  - **The place:** a row's place is `created_at::text`, which `::timestamptz` reads back exactly (microseconds, ±infinity, a BC date). A JS Date keeps milliseconds, and a cursor built from one would skip or repeat rows within a millisecond.
- **`render.ts`:**
  - The MCP reply ends with `More follow. Cursor: … — pass it as \`after\` …` when more follow, and says "oldest" for that sort.
  - `structuredContent` carries `sort` and `cursor`. The guard, which holds a field named `cursor` to a uuid, lets a list cursor through by `parseListCursor`'s rule (it decodes to a sort word, a time and a uuid).
  - Each `REFUSED_CURSOR` reason is worded, naming `after` or the sort the cursor needs.
- **`rest-client/`** regenerated. **Docs:** `server-portable/README.md`'s read surfaces and the GPT context's tool line.

**Why.** `list_thoughts` returned at most `limit` recent thoughts, with no way on. SMD-2922 (2026-10-14) chose keyset paging in the shape the core already uses. The GUI's browse view (SMD-2280 PR 2) is the first caller to need it.

**Held.**
- **`test-store-sql.ts` [4b]**, fourteen rows of a type of their own: a three-way tie, two rows 800 µs apart within one millisecond, two undated, ±infinity and a BC date.
  - Walked at page sizes 1, 2, 3, 5, 14 and 20 in each sort, each run is Postgres's own `ORDER BY` row for row.
  - `next` is null exactly at the end.
  - Past the `.000900` row, the next is the `.000100` row.
  - Captures landing between pages (now, an hour back, undated) leave every row there at the start seen once and none twice.
  - The `days` filter holds page by page.
- **`test-rest-sql.ts` [2]**, through the in-process MCP door beside REST:
  - In each sort, the first page's cursor takes either door to the same next page: text, `structuredContent` and cursor.
  - MCP's `structuredContent` carries the first page's cursor, a string, equal to REST's.
  - A non-cursor, a cursor whose time Postgres cannot read, and a cursor of the other sort are each REST's 400 `REFUSED_CURSOR`, with its reason and sort and without echoing the cursor, and the MCP reply words them as `render.ts` does.
  - `limit` 0, -1, 1.5 and 1001 are REST's 400 `REFUSED_INPUT`, and so is `days` 1,000,000 beside a cursor (never taken for the cursor's refusal).
- **`test-e2e-sql.ts` [5]**, in both MCP modes (the in-process server and `mcp-server/` over REST):
  - `structuredContent` carries the cursor the text names.
  - An agent's walk, a page of one at a time by the reply's own cursor line, visits all three thoughts once, and oldest first is the reverse.
  - Both refusals' words.
- **`test-server.ts`:** the guard passes a list cursor at `cursor` alone and as given: padded, or at `after`, it is null.
- **`test-e2e-sql.ts` [15]**: its own check that `structuredContent` holds only tokens beside the text admits the list cursor by `parseListCursor`.
- **Mutants**, each failing its suite: the guard nulling the cursor and the cast's SQLSTATE unmapped (`test-rest-sql`), and, failing [4b]:
  - a cursor from the JS Date;
  - `<=` for `<` on the id;
  - the undated run dropped (oldest first);
  - the dated run dropped (past an undated row);
  - the undated run's ids ascending;
  - the tie-break dropped.

**Measured after.** 200,000 rows on a throwaway Postgres 16, a page of 50 through the store, medians of 20:

| Page | Newest first | Oldest first |
|---|---|---|
| First page | 0.47 ms | 0.24 ms |
| After 150,000 rows | 0.24 ms | 0.24 ms |

Before the two runs, oldest first past a dated row OR-ed the undated rows into its predicate. The planner read that as a filter (150,001 rows removed, 7.5 ms), growing with depth. Inside a group of rows sharing one `created_at` a page still reads the rest of the group (review pass 1: 1.9 ms 10k into a 20k tie, 27.5 ms 1k into a 200k one, a walk of it quadratic): SMD-3228.

**Not taken.**
- **Offset paging:** SMD-2922 chose a keyset, which a capture cannot shift.
- **An index on `(created_at, id)` here:** outside a tie `thoughts_created_at_idx` answers in index time. A large tie (an import batch on one coarse time) is where it would pay; that index on the largest table is a migration of its own, SMD-3228.
- **A cursor the session-capture hook leaves alone:** its secret scan reads a cursor (72–130 base64url characters) as a high-entropy token. A cursor reaches a session only when a prompt or reply quotes one, and the hook's redaction is the right answer to a string it cannot read.
- **Undated rows last when newest first:** they stay where 001's index and the existing order put them, first.
