## Changelog

`list_thoughts` pages: `sort` newest (the default) or oldest first, and `after`, the cursor the previous page ended with, so a GUI list or an agent can walk every thought there when it began once (newest first, one captured meanwhile is not among them; oldest first, it comes at the end). A cursor of the other sort, or no cursor of this tool's, is refused (SMD-2995).

## FORK

list_thoughts pages by a keyset cursor, newest or oldest first — every thought once, to the microsecond, in index time at any depth outside a tie (SMD-2995)

**What changed.**
- **`core/schemas.ts`:** `list_thoughts` takes `sort` (`newest`, the default, or `oldest`) and `after` (at most 512 characters, the cursor's own bound), and its description says how to page and what a walk sees. `limit` is a whole number from 1 to 1000; 0 or -1 had read as an empty brain, 1.5 rounded, and 2^31-1 overflowed the row read past the page. `days` is positive and at most 365,000 (from about 740,000 the window's start is a year 0 or before, which JS's ISO text writes as a year Postgres cannot read, a 500), and says its window moves with each call, so its oldest can leave it between pages.
- **`core/list-cursor.ts`** (new) and **`core/reads.ts`:**
  - `listCursor` / `parseListCursor`, in a module of their own so `render.ts` can read them: the cursor is base64url of `[sort, at, id]`, where `at` is Postgres's own text of the page's last `created_at` (null when undated).
  - A cursor is read back only if:
    - its sort is one of the two;
    - its id is a uuid;
    - `at` is timestamptz's text shape: a day its month has, BC's leap years Postgres's, or ±infinity.
  - A cursor of that shape whose time Postgres's cast still cannot read (a year 0, past timestamptz's range, an offset past ±15:59:59) is the store's `ListCursorRefused` (SQLSTATE 22007, 22008, 22009 from reading the cursor's time alone, once a page's cast has failed, so a good page pays no read before it), so the core gives the same refusal, never a fault quoting the value, and no other cast error is taken for it.
  - An empty or blank `after` is refused as no cursor, as `list_thought_ids` refuses one: taken for the first page, a client sending `after=` at a walk's end read page one forever.
  - The reply carries `sort` and `cursor`. `cursor` is null exactly when no thought follows; the store reads one row past the page to know.
- **`core/refusal.ts`:**
  - `REFUSED_CURSOR` gains `reason` (`shape` or `sort`) and, for `sort`, the sort the cursor was made under, as facts.
  - The cursor itself is never echoed.
- **`store.ts` / `store-sql.ts`:** `listThoughts` returns a page, `{ thoughts, next }`, and takes `sort` and `after`.
  - **The order:** `thoughts_created_at_idx`'s own order. Newest first is `created_at DESC` with the undated first, ties by id; oldest first is its reverse.
  - **Two runs:** each order is read as two runs, the undated and the dated, each by a plain index condition (`created_at IS NULL`, or `<=`/`>=` the cursor's). The next run is read only while the page is short.
  - **The place:** a row's place is `created_at::text`, which `::timestamptz` reads back exactly (microseconds, ±infinity, a BC date). A JS Date keeps milliseconds, and a cursor built from one would skip or repeat rows within a millisecond.
- **`render.ts`:**
  - The MCP reply ends with `More follow. Cursor: … — pass it as \`after\` …` when more follow. An oldest-first page is headed `N thought(s), oldest first:`; newest first keeps main's `N recent thought(s):`, which the old dashboard's parser reads.
  - `structuredContent` carries `sort` and `cursor`. The guard, which holds a field named `cursor` to a uuid, lets a list cursor through by `parseListCursor`'s rule (it decodes to a sort word, a time and a uuid).
  - Each `REFUSED_CURSOR` reason is worded, naming `after` or the sort the cursor needs.
- **`rest/openapi.ts`:** `list_thoughts`' 200 names `thoughts`, `sort` and `cursor` (null at the end) and the refusal's facts, so a REST client can page from the document. **`rest-client/`** regenerated. **Docs:** `server-portable/README.md`'s read surfaces and the GPT context's tool line.

**Why.** `list_thoughts` returned at most `limit` recent thoughts, with no way on. SMD-2922 (2026-10-14) chose keyset paging in the shape the core already uses. The GUI's browse view (SMD-2280 PR 2) is the first caller to need it.

**Held.**

  - `next` is null exactly at the end.
  - Past the `.000900` row, the next is the `.000100` row.

**Measured after.** 200,000 rows on a throwaway Postgres 16, a page of 50 through the store as it stands, medians of 100 in one run:

| Page | Newest first | Oldest first |
|---|---|---|
| First page | 0.88 ms | 0.41 ms |
| After 150,000 rows | 0.47 ms | 0.43 ms |

Newest first's first page is two statements, the undated run (empty here) and then the dated. Pass 2's probe, the cursor's time read before every page, was one more round trip (0.14–0.31 ms) until pass 3 read it only after a failure.

Before the two runs, oldest first past a dated row OR-ed the undated rows into its predicate. The planner read that as a filter (150,001 rows removed, 7.5 ms), growing with depth. Inside a group of rows sharing one `created_at` a page still reads the rest of the group (review pass 1: 1.9 ms 10k into a 20k tie, 27.5 ms 1k into a 200k one, a walk of it quadratic), and the undated rows are one such group, read by id past `created_at IS NULL`: SMD-3228.

**Not taken.**
- **Offset paging:** SMD-2922 chose a keyset, which a capture cannot shift.
- **An index on `(created_at, id)` here:** outside a tie `thoughts_created_at_idx` answers in index time. A large tie (an import batch on one coarse time) is where it would pay; that index on the largest table is a migration of its own, SMD-3228.
- **A cursor the session-capture hook leaves alone:** its secret scan reads a cursor (72–130 base64url characters) as a high-entropy token. A cursor reaches a session only when a prompt or reply quotes one, and the hook's redaction is the right answer to a string it cannot read.
- **Undated rows last when newest first:** they stay where 001's index and the existing order put them, first.
- **The filters in the cursor:** a cursor carries its sort, not its filters. Passed with others, it reads those filters' rows past its place, a keyset of its own; the description asks for the same filters.
- **A newest-first header saying its order:** `N recent thought(s):` is main's, read by the old dashboard's parser and the session hook's fixture; it goes with that dashboard (SMD-2280 PR 6).

**Follow-ups.** SMD-3228: a page inside a large tie re-reads the rest of the group. SMD-3234: the other GET string inputs are unbounded, so a long one is the REST core's 431 and a fault through the MCP server.
