## Changelog

`list_thoughts` pages: `sort` newest (the default) or oldest first, and `after`, the cursor the previous page ended with, so a GUI list or an agent can walk every thought once, whatever is captured meanwhile. A cursor of the other sort, or no cursor of this tool's, is refused (SMD-2995).

## FORK

list_thoughts pages by a keyset cursor, newest or oldest first — every thought once, to the microsecond, in index time at any depth (SMD-2995)

**What changed.**
- **`core/schemas.ts`:** `list_thoughts` takes `sort` (`newest`, the default, or `oldest`) and `after`, and its description says how to page.
- **`core/reads.ts`:**
  - `listCursor` / `parseListCursor`: the cursor is base64url of `[sort, at, id]`, where `at` is Postgres's own text of the page's last `created_at` (null when undated).
  - A cursor is read back only if:
    - its sort is one of the two;
    - its id is a uuid;
    - `at` is timestamptz's text shape: a day its month has, BC's leap years Postgres's, or ±infinity.
  - A forged cursor is therefore this refusal, never a cast error.
  - The reply carries `sort` and `cursor`. `cursor` is null exactly when no thought follows; the store reads one row past the page to know.
- **`core/refusal.ts`:**
  - `REFUSED_CURSOR` gains `reason` (`shape` or `sort`) and, for `sort`, the sort the cursor was made under, as facts.
  - The cursor itself is never echoed.
- **`store.ts` / `store-sql.ts`:** `listThoughts` returns a page, `{ thoughts, next }`, and takes `sort` and `after`.
  - **The order:** `thoughts_created_at_idx`'s own order. Newest first is `created_at DESC` with the undated first, ties by id; oldest first is its reverse.
  - **Two runs:** each order is read as two runs, the undated and the dated, each by a plain index condition (`created_at IS NULL`, or `<=`/`>=` the cursor's). The next run is read only while the page is short.
  - **The place:** a row's place is `created_at::text`, which `::timestamptz` reads back exactly (microseconds, ±infinity, a BC date). A JS Date keeps milliseconds, and a cursor built from one would skip or repeat rows within a millisecond.
- **`render.ts`:**
  - The MCP reply ends with `More follow. Cursor: … — pass it as \`after\` …` when more follow, and says "oldest" for that sort.
  - `structuredContent` carries `sort` and `cursor`.
  - Each `REFUSED_CURSOR` reason is worded, naming `after` or the sort the cursor needs.
- **`rest-client/`** regenerated. **Docs:** `server-portable/README.md`'s read surfaces and the GPT context's tool line.

**Why.** `list_thoughts` returned at most `limit` recent thoughts, with no way on. SMD-2922 (2026-10-14) chose keyset paging in the shape the core already uses. The GUI's browse view (SMD-2280 PR 2) is the first caller to need it.

**Held.**
- **`test-store-sql.ts` [4b]**, fourteen rows of a type of their own: a three-way tie, two rows 800 µs apart within one millisecond, two undated, ±infinity and a BC date.
  - Walked at page sizes 1, 2, 3, 5, 14 and 20 in each sort, each run is Postgres's own `ORDER BY` row for row.
  - `next` is null exactly at the end.
  - Past the `.000900` row, the next is the `.000100` row.
  - Captures landing between pages (now, an hour back, undated) leave every row there at the start seen once and none twice.
  - The `days` filter holds page by page.
- **`test-rest-sql.ts` [2]**, in both MCP modes:
  - In each sort, the first page's cursor takes either door to the same next page: text, `structuredContent` and cursor.
  - A non-cursor and a cursor of the other sort are each REST's 400 `REFUSED_CURSOR`, with its reason and sort and without echoing the cursor, and the MCP reply words them as `render.ts` does.
- **`test-e2e-sql.ts` [5]**, in both MCP modes:
  - An agent's walk, a page of one at a time by the reply's own cursor line, visits all three thoughts once, and oldest first is the reverse.
  - Both refusals' words.
- **Mutants**, each failing [4b]:
  - a cursor from the JS Date;
  - `<=` for `<` on the id;
  - the undated run dropped (oldest first);
  - the dated run dropped (past an undated row);
  - the undated run's ids ascending;
  - the tie-break dropped.

**Measured after.** 200,000 rows on a throwaway Postgres 16, a page of 50 through the store, medians of 20:

| Page | Newest first | Oldest first |
|---|---|---|
| First page | 0.47 ms | 0.24 ms |
| After 150,000 rows | 0.24 ms | 0.24 ms |

Before the two runs, oldest first past a dated row OR-ed the undated rows into its predicate. The planner read that as a filter (150,001 rows removed, 7.5 ms), growing with depth.

**Not taken.**
- **Offset paging:** SMD-2922 chose a keyset, which a capture cannot shift.
- **An index on `(created_at, id)`:** `thoughts_created_at_idx` with an incremental sort on the rare tie answers in index time; a second index on the largest table is a migration for no measured need.
- **Undated rows last when newest first:** they stay where 001's index and the existing order put them, first.
