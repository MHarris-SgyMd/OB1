## Changelog

Preflight's `write privileges` row reads `ob1_config` schema-qualified, as its privilege test was, so a role with `public` off its search path no longer takes 27 later rows down as "not checked"; that row and `chunk context` each get their own try/catch, and the `schema` row stops saying to migrate a brain whose `public.thoughts` exists but does not resolve for the role, and names the missing USAGE, the search path, or both instead (SMD-2062).

## FORK

Preflight reads a table off the role's path in one row, not the block — `write privileges` qualified and bounded, `chunk context` too, and the `schema` row names the missing USAGE or path (SMD-2062)

**What changed.** `server-portable/preflight.ts`, two rows of the direct-connection block and the `schema` row before it:

- **`write privileges`** tested `has_table_privilege('public.ob1_config', 'SELECT')`, then read the extraction key from a bare `ob1_config`. The read is now `public.ob1_config`, as the test was. The row also gets its own try/catch, as the other rows in the block that read a table rather than the catalog have: a raise inside it is its own `could not verify` warning. The role's name, which the `transaction isolation` remedy uses later, is taken from the vector probe's read, outside the try.
- **`chunk context`** read a bare `thought_chunks`, and had no try/catch of its own. It now reads `public.thought_chunks`, its column check reads `information_schema.columns` for schema `public` only, and a raise is its own warning.
- **`schema`**, when `countThoughts` fails with "does not exist" on the SQL store, asks `pg_class` whether `public.thoughts` exists, and `has_schema_privilege` whether the role has USAGE on `public`. If the table exists, the row says so and names each cause that holds, with its statement, instead of `migrate.ts`:
  - `GRANT USAGE ON SCHEMA public TO <role>;`
  - `ALTER ROLE <role> IN DATABASE <db> SET search_path = <its schemas>, public;`, which keeps what the path already has. A role's setting in a database outranks its plain `ALTER ROLE` setting and the database's; only the connection string outranks it, and the remedy says so.

  `current_schemas()` leaves out a schema the role has no USAGE on, so the setting (`current_setting('search_path')`) is parsed as Postgres parses it: `searchPathSchemas()` keeps a quoted name as written, folds an unquoted one to lower case, and drops the empty name a `''` path reads back as. The statement is rebuilt from those names, each quoted, never echoed. A `thoughts` in any other schema is another tool's, and an empty `public` still gets the migrate remedy.

**Why.** A role granted SELECT on every table with `search_path = nowhere` passed the privilege test and then raised `relation "ob1_config" does not exist` on the read. The raise reached the block's catch, which reported the 27 rows after it as "not checked — the direct connection failed before it", `migration ledger` and `schema version` among them. The `schema` row above them said "Apply the migrations" for a brain that was migrated. SMD-2041's third review pass found it. test-preflight's limited role had no grant on `ob1_config`, so the read never ran.

With the read qualified, the next raise was `chunk context`'s bare `thought_chunks`, which took the ten rows after it. With no USAGE on `public`, `to_regclass('public.…')` itself raises (checked on PG16), so qualifying alone does not keep the rest of the block running; the try/catch does.

**Held.** test-preflight, 456 → 465. In the `pf_reader` leg:

- **The ticket's role** (SELECT on every table, `public` off its path):

- **An empty path:** the row says so and sets `public` alone.

**Not taken.** The extraction key is still read in the row, not from `readDatabaseFacts`, the ticket's other option.
