## Changelog

`docs/mcp-listen-streams.md` decides how `/mcp` will tell a connected client its tool list changed: hold the 2026-07-28 `subscriptions/listen` streams open and send no notification on them, so that a restart of the MCP server ends them and the client lists again. `docs/mcp-client-refresh.md` gains what Claude Code 2.1.327 does across a restart and how long the stack's own restarts take, measured with new modes of the probe in `evals/mcp-clients/` (SMD-4347). The MCP server can now hold such a stream and does not yet: its stop closes held streams last, each with its closing frame, a stream's log line is written as it opens, and one key holds at most 32 and the server 256, all behind `tools.listChanged`, which still says `false`. No migration, and nothing the brain serves changes yet.

## Record

The decision on listen streams, and the measurements under it — a restart of the MCP server is what tells Claude Code its list changed, if the server is back within 12 seconds; and a server that can hold the streams, and does not yet: PRs 1 and 2a (SMD-4347)

**Why.** SMD-4344 measured that Claude Code fetches its tool list again on a `subscriptions/listen` notification and not on a `ttlMs`. SMD-4345 then served the 2026-07-28 revision with `tools.listChanged: false`, so no stream is held and a connected session keeps an old list until it is reconnected by hand. SMD-4347 asked whether to hold the streams, with four open questions about where a change event would come from and whom it would reach. Its first step is the decision.

**What was found.**

- **The end of its stream is what tells the client.** Claude Code 2.1.327 asks for its stream again 6, 8 and 12 seconds after it is ended with the SDK's closing frame, and at about 1, 3 and 7 after it is dropped with none. It lists at once when one is opened. A 502, the edge's busy answer and a 500 each use an attempt up, and after three it stops: it did not ask again in 160 seconds, a new turn among them, while its tool calls were served on the old list.
- **A server it cannot reach it treats differently.** With the port closed it connects again from `server/discover`: by itself after 20 and after 60 seconds, and at its next tool call after 180. An interactive session, after 60, began its next turn with the model saying the server had failed to connect, and its tool call then reconnected and was served.
- **With no stream it notices nothing.** Through 20 seconds of 502 and through 60 of a closed port it sent no request, and kept its list.
- **What changes a list, and whether the MCP server is replaced in time.** A plugin enabled replaces both servers: the MCP server away 6.9 seconds. An upgrade replaces both, and in one `up -d` the migrator runs while the MCP server is away: 6.6 seconds with nothing to migrate, 25.8 with a migrator that takes 15, and 7.3 with that migrator run first. A key's scope replaces the REST core and leaves the `mcp` container running, its key's list gone from 49 tools to 24.
- **The client's documentation names limits the runs did not reach:** five reopens in an hour and then about six hours' wait, and for a server that drops, five reconnects and then a failed state.

**Decided, in `docs/mcp-listen-streams.md`.** Go: declare `tools.listChanged: true`, hold each stream, and send no notification on it. A restart of the MCP server ends the streams, its stop with the closing frame. That works for a plugin, and for an upgrade whose migrator is run first; for a key's scope the operator recreates `mcp` after it, or the client reconnects as now. The page says what that buys, what it does not fix, what it costs against today (a session that cannot reach the server finds out) and what the build is; then what the build must make true, with what the reviews found by building it, in three cuts. Merging the page is the decision.

**What changed.**

- `docs/mcp-listen-streams.md`: the decision.
- `docs/mcp-client-refresh.md`: a dated section, "A restart, measured 2026-11-18", with the client's runs, the baseline with no stream, the stack's procedures and what is thin. The 2026-11-14 text is as written, but for one sentence that said a restart heals and now points at the section.
- `evals/mcp-clients/probe.ts`: five controls that end every listen stream, forget the sessions, change the tool set and then answer as something that is not serving for N seconds: `down/N` (502), `busy/N` (the edge's busy answer), `fault/N` (the route's 500), `refuse/N` (the port closed), and `cut/N`, which drops every connection with no closing frame first. And `LISTEN=off`, which declares `tools.listChanged: false` as the brain's server does today.
- `evals/mcp-clients/selfcheck.ts` holds each, in the mode it is told to expect: 42 rows with a stream, 38 without, 20 before. The two run scripts name the new steps.

**Not changed.** What the brain serves. `mcp-server/app.ts` still declares `false` and holds no stream, and `deploy/compose.yaml` is as it was.

**Held.**
- `bun selfcheck.ts` beside a fresh probe, and `LISTEN=off bun selfcheck.ts` beside one started so: every row passes; the one in the wrong mode fails its first; a probe that goes away part-way ends the check with a failed row and its count.
- Twenty-two Claude Code sessions, eighteen of them in the doc's tables with their times, and sixteen timed restarts of a scratch stack.

**Found by review, before the first push.** Five rounds, ten independent readers, each given the branch and the raw logs and none of this record's reasoning. Every measured number held from the second round on. What changed was the decision, and it changed by getting smaller.

- **The scope edit.** The first draft said every change of a list restarts "the servers"; a key's scope restarts the REST core and not the MCP server. Four mechanisms were then put up to cover that one edit, and each was taken down by a reader or a run:
  - a notification kept by key name, which loops when two callers share a name;
  - the same kept for access keys alone, which the legacy key's fixed name reopens, and kept by credential, which wants a bound and a rule for tokens;
  - compose's `restart: true`, run: the MCP server away 11.3 and 11.5 seconds;
  - a label on `mcp` that carries the keys, run: 6.1 to 6.3 seconds, and it lengthens a key edit's outage for tool calls from 7.7 seconds to 11.5, ends every stream at any edit of the list, and puts the key list on a service the project holds to "no key list".

  The decision covers the scope edit with one more command for the operator, and says so.
- **The stop.** Written out as steps twice, and found wrong three times by readers who built it: the SDK's `close()` closes calls too; the order at the bound; the real `drainOnSignal` exiting before the closing frame is sent. The page says what must hold at a stop and lists what is known to bite. The wiring is the build's.
- **The upgrade.** The first timing was of `mcp` recreated alone; the real procedures were then run, with nothing to migrate. A reader saw that both servers start at the end of one `up`. Run with a 15-second migrator, the MCP server is away 25.8 seconds; with the migrator first, 7.3. The page says an upgrade works when the migrator is run first, and the build changes the upgrade's steps.
- **What it costs.** "Nothing gets worse" had no baseline. One was run, and the closed port for 60 and 180 seconds, and an interactive session for 60. The cost is said from those: a session that cannot reach the server finds out.
- **What the first draft did not have:** the client's documented limits, the vendor's switch, the quick tunnel that does not carry event streams, the proxy's own stop, the size of the build, and the decision anywhere near the top.
- **The probe.** Its 500 was JSON where the route's is plain text; every measured stream had ended with the closing frame; three busy answers had not been run. Changed and run. The self-check took its mode from the probe, held no stream across three controls and no outage to its length, held `busy` and `fault` to a change of the tool set only as a pair, and stopped with no count when the probe went away. Mended, by mutants and by stopping a probe under it.
- **A script that typed into a real session.** The two interactive runs were driven through a terminal by an `expect` script. In one it pressed Enter on a dialog the client had raised that had nothing to do with the test. Mended once, a reader with a stand-in client still made it do so five ways. It is not in the tree: an interactive run is typed by hand.

**Thin.** Each case ran once, but a few. One client, with one outage a session; two interactive runs. The probe, not the brain's server, and no stream through the stack's own path. The stack was timed on one machine, idle, with no collector, and the slow migration was the stack's own migrator behind a wait.

## PR 2a: the server can hold a stream, and does not yet

**What changed.**

- `mcp-server/listen-streams.ts`, new: `HOLD_LISTEN_STREAMS = false`, read by the entry alone; the bounds, 256 for the server and 32 for one caller's name; and the object the app and the entry share, a count of open streams and the app's close.
- `mcp-server/app.ts`: an app given streams to hold declares `tools.listChanged: true` on 2026-07-28. A `subscriptions/listen` then takes a place under the two bounds or is refused as the SDK refuses one past its own (a 200 carrying -32603), its line `refused` with the code `LISTEN_LIMIT`. A held stream's line is written as it opens, `ok`, its `ms` the time to open it; it has no stall bound, no keepalive frame of this server's and no abandonment warning; its place is given back when it ends, its client closes it or its connection drops.
- `server-portable/sse.ts`: `held`, a stream the wrapper neither keeps alive nor bounds; and `onEnd` may return a promise the wrapper waits on before it ends the answer.
- `server-portable/shutdown.ts`: `drainOnSignal` takes `held` and `closeHeld`. Given them, it does not wait on the held streams, closes no connection at the bound, closes the streams after the flush and the pool, then awaits the server's own end, or after a cut closes the connections once the streams' answers have ended. Its two lines count the streams.
- `mcp-server/index.ts` gives the stop those two only where the server holds streams, so today's entry stops as it did.
- `mcp-server/test-listen-on.ts`, new: a preload that starts the suite's spawned entry with that one constant `true`. Its `test-` name keeps it out of the image, and `scripts/check-consistency.ts` names it among the suites not run, with why.

**Decided in the build, and written into `docs/mcp-listen-streams.md` under "As built in PR 2a".**

- The line at the open, not at the end with the stream's lifetime as the decision first had it. A record open at the stop must be ended before the flush, and the stream closed after it; ended at the open, the record goes out like any request's and `server-portable/telemetry.ts` is untouched. Nothing records when a stream ended.
- Inert where the capability is off, where the decision said it would not be.
- The caps are the route's count. The handler's `maxSubscriptions` was set to the same number and taken out: no row could tell the two apart.

**Found by running it.**

- With a stream held, a 2026-07-28 call cut at the bound was answered 200 with an empty stream that ended whole, and no warning was written: closing the SDK's handler ends its calls in flight too. The route now says such a call `cut`, writes its warning and leaves its answer for the connections' close to drop. (caught: run-it)
- With nothing waited on after the streams are closed, a closing frame was lost. Awaiting the server's own end was enough in five runs of five, and the two event-loop turns first written beside it were taken out. (caught: mutant)
- A row allowed the stop 1.5 seconds against a bound of one, so a drain that waited on the held stream passed it; it now allows half a second, where the stop takes about 20 ms. (caught: mutant)
- Two rows read a refusal with no deadline, so a stream held where a refusal was due hung the suite; and an entry that never started threw out of it. Each now fails its row. (caught: mutant)

**Held.**

- `mcp-server/test-mcp.ts`, 268 rows from 241. [9c], in process: the capability, the line at the open, no stall and no abandonment past a shortened bound, each bound and its refusal, a place given back and retaken, a listen the SDK ends or refuses, a 2025-era request by that name. [8h], the real entry in a process of its own with a collector: today's entry says `false` and stops as before; a stop with one stream and nothing else exits 0 in under half its bound, the frame read and the span sent; with a call running, the call answered in full and the stream closed after it; with 24 streams and two calls that never end, one of each revision, both cut and dropped with a warning each, all 24 frames read, exit 1; a connection after the signal refused.
- `server-portable/test-server.ts`, 1,734 rows from 1,725: the stop's order with held streams on a stand-in server, the cut, a second signal, a close that hangs or throws, a count that throws; the wrapper's `held`, and an end its caller holds.
- Mutants: thirty, each killed by one suite or the other. The entry alone does not kill two of the drain's, the close's bound and the wait for the answers after a cut; the stand-in's rows do. The stand-in does not kill the wait on the server's own end; the entry does.

**Not in 2a.** The capability, the documents, a count of open streams outside the stop's lines, and a real client: PR 2b.
