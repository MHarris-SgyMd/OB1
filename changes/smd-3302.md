## Changelog

A server left running across a migration that adds a column to a function it reads no longer fails that read with "cached plan must not change result type" until it restarts: the store and `db/consolidate.ts` name the columns they read, and check 41 keeps `SELECT *` off core functions (SMD-3302).

## FORK

A running server's reads survive a migration that adds a column to the function they read — each names its columns (SMD-3302)

**What changed.**
- **The six `SELECT *` reads of a function name their columns,** each function's whole current list in its RETURNS TABLE order, so the rows the readers map are unchanged:
  - `server-portable/store-sql.ts`: `list_supersession_proposals` (110's 22), `list_proposal_writers` (107's 16) and `thought_changes` (052's 15);
  - `db/consolidate.ts`: `list_supersession_proposals`, `list_proposal_writers` and `stale_entities` (029's 5).
  The store's other function reads (`match_thoughts`, the search forms, `trace_provenance`, `find_derivatives`, `ticket_status_inputs`) already named theirs.
- **Check 41** fails a `SELECT *` or `t.*` over a function the core migrations define, in the brain's own code: `server-portable/`, `mcp-server/`, `dashboard/`, `plugins/` and `db/`, comments blanked, strings read. It catches the bare, qualified and quoted names, and `*` after DISTINCT or before more columns. Named columns, a table, a subquery, a function no migration defines (`unnest`) and `count(*)` pass. Tests and benches are not read. Its probe pins all of these.

**Why.** SMD-3249's review pass 3 measured it against migration 110, which added `page_key` and `remaining` to `list_supersession_proposals`. Servers started at 109 listed six times. Then 110 was applied, and every later listing failed: REST with `{"code":"FAILED","message":"cached plan must not change result type"}` and the MCP tool with the same error. Bun prepares each statement and never re-prepares it, and the store's connections have no lifetime limit. A redefined function invalidates the plan, and Postgres re-analyses the statement: `*` now expands to more columns, so the result type changes and Postgres refuses (0A000). A named list re-analyses to the same type and runs. On a scratch Postgres 16 over one Bun connection, `SELECT *` failed 0A000 after both a `DROP`+`CREATE` with a trailing column and 110's shape (a new form with a defaulted argument, the old dropped). `SELECT a, b` read both times.

**Held.**
- **test-store-sql [20]**, on a store of one connection, for each of the three functions:
  - it reads once, then widens the function as a migration would: the real one renamed aside, and one under its name and arguments returning its columns plus one more;
  - it reads again on the same connection, and the read must succeed;
  - a raw connection that prepared `SELECT *` before the widening must then fail 0A000. That control shows each widening is the kind that breaks `*`.
- **Mutants:** each of the three store reads back to `SELECT *` fails its own assertion with "cached plan must not change result type" (295/296). Check 41 names a store read and a consolidate read put back to `*`. No test reaches consolidate.ts's reads: it is a one-shot CLI that runs each once per run, apart from `--list lineage`'s two listings. So check 41 is their guard.

**Not taken.**
- **Catching 0A000 and retrying on a fresh connection.** That costs a failed call per stale statement per connection and needs a retry path in every reader, where naming the columns costs nothing.
- **`prepare: false` on the store.** It would re-plan every query on every call to cover the few that read a function.
- **A connection lifetime** shortens the window but doesn't close it.
- **The benches** (`db/bench-hybrid.ts`) time `SELECT *` on purpose, so that every column is computed. **`recipes/vercel-neon-telegram`**'s `SELECT * FROM match_thoughts(` is a vendored recipe, outside check 41's directories.
- **Surviving a column dropped, renamed or retyped.** That still fails a running server's named read, and it should: the reader has to change with the function.
