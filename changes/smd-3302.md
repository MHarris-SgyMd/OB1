## Changelog

A server left running across a migration that adds a column to a function it reads no longer fails that read with "cached plan must not change result type" until it restarts: the store and `db/consolidate.ts` name the columns they read, and check 41 keeps `*` off the brain's functions, tables and views (SMD-3302).

## FORK

A running server's reads survive a migration that adds a column to the function they read — each names its columns (SMD-3302)

**What changed.**
- **The six `SELECT *` reads of a function name their columns,** each function's whole current list in its RETURNS TABLE order, so the rows the readers map are unchanged:
  - `server-portable/store-sql.ts`: `list_supersession_proposals` (110's 22), `list_proposal_writers` (107's 16) and `thought_changes` (052's 15);
  - `db/consolidate.ts`: `list_supersession_proposals`, `list_proposal_writers` and `stale_entities` (029's 5).
  The store's other function reads (`match_thoughts`, the search forms, `trace_provenance`, `find_derivatives`, `ticket_status_inputs`) already named theirs.
- **Check 41** covers the brain's own code: `server-portable/`, `mcp-server/`, `dashboard/`, `plugins/`, `db/` and `deploy/`, tests and benches aside.
  - **It fails** a `*`, `t.*` or `(x).*` anywhere in a select list over a function, table or view that the core's or a plugin's migrations define, `TABLE` it, and a `RETURNING *` on any table. The same failure comes from a table that gains a column, which CLAUDE.md allows on `thoughts`.
  - **How it reads:**
    - Only the code's strings, as SQL. Each JS string and template is read, a `${…}` in it as an opaque value, a template nested in one as its own string.
    - One left-to-right pass masks SQL comments, literals (`'…'`, `E'…'`) and dollar quotes.
    - Each SELECT is read alone. Its list runs to the FROM at its own depth, and its FROM clause is split into items with their aliases: a join, a LATERAL, ROWS FROM, a parenthesised join. ON and USING conditions are dropped, and a subquery is read in turn.
    - A qualified star reads the item it names, a bare star every item.
    - Failures name the file and line.
  - **It passes** named columns, a CTE's name, a function no migration defines (`unnest`), an ON condition, a literal, a comment and `count(*)`.
  - **Stricter than 0A000 needs:** a star whose columns never reach the result, such as `EXISTS (SELECT * …)`, is read too.
  - **The migrations' names** are read off the same masked text, so a CREATE in a DO body, or a `$tag$` in a comment, changes nothing.
  - **Its probe** pins each of these, the line reported, and that its walk reads each kind of file the brain's code has (the store, db/, a plugin, mcp-server, the dashboard, deploy/, `.mjs`) and leaves the tests and benches.
  - **Today it finds nothing** beyond the six reads above. Pointed at the whole repo it finds 146 reads, all in tests, benches, evals, the recipe and its own probe strings.

**Why.** SMD-3249's review pass 3 measured it against migration 110, which added `page_key` and `remaining` to `list_supersession_proposals`. Servers started at 109 listed six times. Then 110 was applied, and every later listing failed: REST with `{"code":"FAILED","message":"cached plan must not change result type"}` and the MCP tool with the same error. Bun prepares each statement and never re-prepares it, and the store's connections have no lifetime limit. A redefined function invalidates the plan, and Postgres re-analyses the statement: `*` now expands to more columns, so the result type changes and Postgres refuses (0A000). A named list re-analyses to the same type and runs. On a scratch Postgres 16 over one Bun connection, `SELECT *` failed 0A000 after both a `DROP`+`CREATE` with a trailing column and 110's shape (a new form with a defaulted argument, the old dropped). `SELECT a, b` read both times.

**Held.**
- **test-store-sql [20]**, on a store of one connection, for each of the three functions:
  - it reads once, then widens the function as a migration would: the real one renamed aside, and one under its name and arguments returning its columns plus one more;
  - it reads again on the same connection, and the read must succeed;
  - a raw connection that prepared `SELECT *` before the widening must then fail 0A000. That control shows each widening is the kind that breaks `*`.
- **Mutants:**
  - Each of the three store reads put back to `SELECT *` fails its own assertion with "cached plan must not change result type" (295/296).
  - Check 41 names a store read and a consolidate read put back to `*`.
  - Of 47 mutants of its scanner, names, walk and probe, 45 are caught. The two left are equivalent: `''` inside a literal masks the same as two literals, and no valid WHERE clause holds a depth-0 comma or JOIN.
  - A 20,000-line string of `SELECT * FROM c` with no `;` reads in 32 ms (189 s before a bare SELECT ended a FROM clause). So does 20,000 lines of JS `select(a, b)`; the check adds about 0.1 s to the checker.
  - test-live runs consolidate.ts's reads, but no test widens a function under them. It is a one-shot CLI that runs each read once per run, apart from `--list lineage`'s two listings, so check 41 is their guard.

**Not taken.**
- **Catching 0A000 and retrying on a fresh connection.** That costs a failed call per stale statement per connection and needs a retry path in every reader, where naming the columns costs nothing.
- **`prepare: false` on the store.** It would re-plan every query on every call to cover the few that read a function.
- **A connection lifetime** shortens the window but doesn't close it.
- **The benches** (`db/bench-hybrid.ts`) time `SELECT *` on purpose, so that every column is computed.
- **Outside check 41's directories:** `evals/eval-consolidate.ts` (a one-shot script) and the vendored recipe `recipes/vercel-neon-telegram` still read `SELECT *` from a core function.
- **`compat/supabase-sql`'s `rpc()`** builds `SELECT * FROM fn(…) AS fn` at run time when no output column is an array. Bun prepares it, so the integrations that call `rpc("match_thoughts")` (agent-memory-api, smart-ingest) would fail the same way after a column is added. A check cannot see text built at run time, and the shim's `*` maps a whole row for callers it doesn't know, so that is the shim's own change: SMD-3329, with its 62 `.select("*")` calls.
- **`db/config.mjs`'s `ownedFunctionsIn`** (check 7's set) strips dollar quotes before comments, as check 41's names did, so it misses `ob1_rebuild_source_gate_for_types` too. That predates this change and is check 7's to fix: SMD-3330.
- **A way to suppress a flag.** Nothing in the code needs one.
- **Surviving a column dropped, renamed or retyped.** That still fails a running server's named read, and it should: the reader has to change with the function.

**Follow-ups.**

- SMD-3330: `ownedFunctionsIn` reads names off one left-to-right masking pass, so check 7 guards `ob1_rebuild_source_gate_for_types`.
