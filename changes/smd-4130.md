## Changelog

A release's notes now fit GitHub's 125,000-character limit on a release's body: past it, the review-yield table, then the list of change files, then the CHANGELOG section become links to what the release attaches or the tag holds, and notes that still can't fit stop the release job before anything is built or pushed. v2.0.0's notes, 143,644 characters, were refused at the job's last step after its images were published. A tag whose release failed after its push can now be published without moving the tag: `gh workflow run release.yml --ref main -f publish_tag=v<X.Y.Z>` runs main's release script on the tag's tree, reads the images' digests from GHCR instead of building, brings the stack up from them, and creates the release (SMD-4130).

## FORK

A release's notes fit GitHub's limit, and a dispatch publishes an existing tag's release (SMD-4130)

**What changed.**
- `scripts/release-artifacts.ts`: `renderNotes` renders the full notes, then steps down while they are over `NOTES_BUDGET` (120,000, under GitHub's `NOTES_LIMIT` of 125,000): the yield table linked to its asset; then the change-file list linked to `changes/` at the tag; then the CHANGELOG section linked to it in `CHANGELOG.md` at the tag (`changelogAnchor`). It throws when even that is over. The self-check holds each step and the refusal.
- `.github/workflows/release-steps.yml`: an `existing_tag` input. With it, the job checks out the tag, refuses a tag that isn't `v<X.Y.Z>` or already has a release, takes `scripts/release-artifacts.ts` from the dispatching commit, skips the GHCR login and both builds, and reads the version's digests with `docker buildx imagetools inspect`. Every run renders the notes with placeholder digests first, so notes that can't fit fail before a build.
- `.github/workflows/release.yml`: `workflow_dispatch` takes `publish_tag`. With it, the `publish-existing` job runs from main alone, with `contents: write` and no `packages`. Without it, a dispatch rehearses as before. A dispatch for one tag queues behind another.
- MAINTAINING.md's "Cutting a release" and release.yml's header say what to do when a tag's release fails after its push.

**Why.** v2.0.0's tag ran `release.yml` (run 42298962203). Every step passed, then `gh release create` got HTTP 422, "body is too long (maximum is 125000 characters)": the CHANGELOG section was about 112,000 characters, the yield table 19,863. The images were already on GHCR (SMD-3172's gap), there was no release and none of its assets, and stable's upgrade reads those. A tag's run uses the tag's own workflow and scripts, so re-running it failed the same way, and a dispatch only rehearsed. Rendered with this change, v2.0.0's notes are 98,513 characters, the CHANGELOG section inline and the change files and yield table linked.

**Held.** The self-check: notes that fit stay whole; a yield table past the budget becomes a link and the CHANGELOG stays; a change-file list past it becomes a link before the CHANGELOG does; a CHANGELOG section past it becomes a link to the anchor GitHub gives its heading; notes still over are refused. A mutant that returns the full notes whatever their length fails three of them.

**Not here.** SMD-3172, pushing under a candidate tag until the smoke passes, would have kept the images unpublished too; it stays its own ticket.
