## FORK

The consolidation pass settles a stale proposal it no longer finds in conflict, and a pass-settled row is the pass's to reopen (SMD-2297)

**What changed.** Migration `064_pass_settles_stale.sql` adds `settle_supersession_proposal(id, note, actor, judge_key, older_fingerprint, newer_fingerprint, recipe, agent)` — the pass's rejection of a `stale` row through 036's reject arm (which checks no status and sets `reviewed_at`, as 063's unreviewed CHECK requires of a row leaving stale), with a note beginning **`settled by the pass:`** (the marker: one constant, `PASS_SETTLED_PREFIX` in `server-portable/consolidate.ts`, one literal in the two SQL bodies, held to each other by test-schema) and the proposal's lineage row rewritten at the fingerprints the pass judged, under the pass's key — and redefines `rebuild_derived` on 063's body with the proposal arm alone changed: a rejected row whose note carries the marker is the pass's, so a text move under it sets the row stale again (unreviewed, the note cleared, the pair requeued); a person's rejected or accepted row is kept, as before. `db/consolidate.ts` re-pools every stale row's newer thought under its own key at the start of a run (a pair both sides of which have a vector, with no live or failed claim there), judges a stale pair the top-k left out when it still meets the candidate rule, and on each stale pair: a conflict at the floor → 063's replacement in place; agree, unrelated or a conflict under the floor → the settle; a pair the rule no longer admits (no shared entity, under the similarity floor, a side superseded) → the settle with a note saying so; a side without a vector → left waiting, re-pooled by the run after the vector lands; a call that timed out, was refused by the egress gate or drew a malformed answer → the row stays stale and the thought is recorded failed, for `--retry-failed`. `--status` counts the pass's rejections apart from a person's and places each stale row against the pools (in a pass's pool, waiting for a vector, failed in a pass, waiting for the next run — one SQL in `server-portable/consolidate.ts`, read by both doors); `--list stale` tags each row's standing; `--dry-run` counts the re-pool. `db/rebuild.ts --status` places the stale rows the same way. Preflight's `lineage` check warns when 063 is re-applied by hand over 064 (rebuild_derived's reopen sentinel gone where the settle function stands), naming 064. The status column's and 029's table comments are re-issued; `db/README.md` gains the 064 paragraph and a stale-rows paragraph in the consolidation section, and its `--list` usage line gains `stale`, which it had lacked since 063.

**Why.** 063 gave a pending proposal whose text moved under the verdict the `stale` status and had the next pass judge the pair again — replacing the row when it found the conflict again. The pass writes a proposal only for a conflict at its confidence floor, so when the edit had resolved the conflict — the likely outcome — the pass judged, found none, wrote nothing, and the row stayed stale for ever: counted by three status surfaces, listed with a reviewer's `--accept … --force / --reject` line, requeued by every later rebuild of either thought. 063's second review pass found the dead end and left the mechanism to this ticket. The maintainer chose the reopen (2026-09-27) over keeping a pass-settled row as a person's decision — which would leave a pair the pass once found clear unproposable when its texts later come to conflict — and over a fifth status.

**Held.** 029's posture: the pass proposes and never applies — a rejection applies nothing. 063's file untouched (brains hold its sha in the ledger); 064 re-issues the comments. A pending row is a reviewer's — the settle refuses it (`NOT_STALE`); a decided row is decided. The lineage row, not the proposal row, carries the texts the settle judged: the proposal keeps the verdict as proposed (`--list rejected` says edited-since, truthfully), and `rebuild_derived` reads staleness from the lineage row, so a settled pair reads current until a text moves again — left at the old texts' fingerprints, every later rebuild would have reopened it and the pass settled it again, for ever (the build's first cold read of its own design). A failed claim stays `--retry-failed`'s (015's rule); a malformed answer on a stale pair leaves the row stale and the thought failed. No grant moves: the settle writes the tables the worker role writing proposals reaches already.

**Measured after.** On a read-only copy of the dogfood brain (1,042 thoughts, 2,585 lineage rows, 24 proposals — 22 stale by fingerprint and every one rejected by hand, so none was stuck; PostgreSQL 16 in a throwaway container; four runs, three beside a running suite, `.planning/scratch/measure-064.ts`, every write rolled back): the queue read 0.9–3.6 ms; the re-pool read 0.4–2.1 ms; a rebuild setting a proposal stale 1.2–2.5 ms a call (29–60 ms for 24); the pass's per-thought stale-row read 0.5–1.2 ms; the uncapped candidate read for a stale pair the top-k left out 3.4–4.9 ms a pair; `settle_supersession_proposal` 0.3–3.4 ms a row, median 0.5–0.8 ms (24 of 24 ok, one lineage row each after); a rebuild after the settle with nothing moved read all 24 settled rows current (neither reopened nor kept — the `kept` on those thoughts is their `source:linear` rows, 063's rule); a rebuild after a second raw move reopened all 24 (34–44 ms for 24); a rebuild over every thought 595–829 ms for 1,042 calls (063 measured 120–523 ms for 1,025 with 2,472 rows on an idle machine).
