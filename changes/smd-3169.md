## FORK

The live suite's four shards are one matrix job, not four copies of it (SMD-3169)

**What changed.**
- **`.github/workflows/fork-checks.yml`:** `db-live`, `db-live-sleep`, `db-live-long` and `db-live-extract` are one job, `db-live`.
  - Its `strategy.matrix.shard` is `[rest, sleep, long, extract]`, with `fail-fast: false`, so one shard's failure leaves the others running, as four jobs did.
  - Each cell sets `OB1_LIVE_SHARD` from the matrix and gets a Postgres service of its own. Its check is "Schema against real Postgres (rest)", "(sleep)", "(long)" or "(extract)".
  - "pgvector off the search path" runs in the rest's cell alone (`if: matrix.shard == 'rest'`), as it ran in the rest's job.
  - `fork-checks-passed` needs `db-live` in place of the four. The workflow is 113 lines shorter (17 added, 130 removed).
- **Check 35's reader** (`scripts/check-fork-consistency.ts`, the one check 34 shares) reads a matrix job once a cell. Each `${{ matrix.<key> }}` in an env value, the run text or the working-directory is filled in from the cell, its key matched ignoring case, as GitHub fills them before the shell runs. So it holds each shard's `OB1_LIVE_SHARD=… run db test-live.ts` line in `db/ci-parity.sh` to its cell, both ways, as it held the four jobs.
  - Cells are expanded as GitHub expands them: the axes' product, less every `exclude` match; each `include` entry is merged into each product cell whose axis values it keeps, or else becomes a cell of its own, which no later include extends.
  - A key the cell lacks, and a null value, render empty, as on GitHub.
  - A matrix, an axis, an include or exclude list, or one entry of either that an expression gives (`fromJSON(…)`) is left unfilled. Its value then matches no ci-parity.sh line, which fails loudly.
  - **A step's `if:` is decided per cell** when it is `matrix.<key> == '<value>'` or `!=` on a string value, alone or joined by `&&` to parts that read no matrix (`${{ !cancelled() && matrix.shard == 'rest' }}`), inside `${{ }}` or not.
    - It compares ignoring case, as GitHub compares strings, and a key the cell lacks counts as `''`, as GitHub dereferences it.
    - One matrix part that is false makes the whole `if:` false.
    - So a shard renamed or misspelt under the rest's step leaves `test-search-path.ts` reading as unrun, not run in all four cells.
  - **Any other `if:` that reads the matrix, on a step that runs a suite, is reported by check 34** as one it can't decide:
    - an `||` at its top;
    - a matrix part negated, parenthesised, reversed or indexed (`matrix['shard']`);
    - `toJSON(matrix)`;
    - a number or boolean value, which GitHub compares as numbers.

    The message's fix: write each part that reads the matrix as one comparison, joined by `&&`. A property named `matrix` (`needs.matrix.outputs.…`), or the word inside a string, reads no matrix.
  - An `if:` that reads no matrix is not evaluated, as before, unless it is `false`. `${{ false }}` now counts as `false` too, where only a bare `false` did.
- **Prose:** `db/ci-parity.sh`, `db/test-live.ts`'s header and `db/README.md` say "one cell each" where they said "one job each".

**Why.** The four jobs differed only in `OB1_LIVE_SHARD`, the name and the rest's one extra step. Any change to the Postgres image, its health check or the suite's setup had to be made four times, and the copies could drift. They were four named jobs only because the ruleset named each check, and check 20 refused a matrix. SMD-3168 made the ruleset require "Fork Checks passed" alone, which needs `db-live` whatever its cells are called. So this PR needs no ruleset PUT: the first job change since SMD-3168 to land without one.

**What the aggregate relies on.** `needs.db-live.result` is the matrix's result as a whole: it is `failure` when any cell fails and `success` only when all succeed. GitHub's contexts reference lists `needs.<job_id>.result`'s values but doesn't say how a matrix reaches them. The rule is what re-actors/alls-green, the common all-green aggregate, builds on ("the resulting outcome of the whole matrix"). This PR's run will show the green side. A red cell won't be seen, since that would take a deliberately failing push.

  - whether include and exclude match case-sensitively (read here as yes);
  - object values compared by their JSON;
  - how GitHub renders `1.0` or `0x10`.
