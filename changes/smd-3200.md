## FORK

The authorization server step: the refusal's 30 s sleep in the background (SMD-3200)

**What changed** (`.github/workflows/fork-checks.yml`, "The authorization server starts, refuses a bad setting, and keeps its state across a restart").
- **Built and created first:** `auth up --no-start --build --no-deps auth` builds the image and creates the volume and the server's container first. The refusal's `run` and the server's `up` then race to build or create nothing; the auth-data volume didn't exist before the step.
- **The refusal in the background:** started as before, with one setting blanked, the origin given a path and the profiles without auth. Its output goes to a file while the server comes up, the proxy serves its document, the MCP server's answers are read, and a client is registered.
- **Waited for before the restart:** the step waits for it before the server's restart, and asserts it as before: exit 2, naming all three settings. From the restart on, the step's compose calls (`restart`, `logs`, `ps`) list the service's containers, which a one-off `run` alive beside the server would be one of. The ticket named the first `ps`, which comes later.
- **One container:** compose lists exactly one auth container after the refusal.

**Why.** The step took a median of 70 s over 36 runs. The refusal's 30 s sleep before its exit (deploy/auth/server.ts, so a crash loop doesn't spin) is independent of the rest. A one-off `run` container joins the project's networks without the service's alias (compose's `--use-aliases` is off), so it never answers for `auth` while it sleeps.

**Held.** The refusal's assertions are the step's, as before: exit 2 and the three settings named. The new check holds that compose sees the server's container alone after it.

**Measured.** actionlint 1.7.7 and its shellcheck pass, and so does the consistency checker. The step's run on a stack, and the ticket's mutant (a server that starts on the bad origin), are the review pass's.
