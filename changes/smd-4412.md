## Changelog

The session hook (1.10.1) gives up a queued write copy that parses but is no copy, such as `null`, `{}` or a copy with no `args`, as it gives up one that does not parse, so the copies behind it land (SMD-4412). Before, such a file threw on every drain and stopped its brain's queue for good. A copy whose answer the hook cannot read is now kept, as a fault is, and given up after the week, rather than ending the drain.

## Record

A queued write copy that is no copy goes to `writes/dead/`, and a throw on one copy keeps it, so neither stops its brain's queue for good (SMD-4412)

**Problem.** The session hook's write fan-out keeps one queue per receiving brain (`writes/pending/`), drained in order (SMD-3314). `drainWrites` moved a file that does not parse to `writes/dead/`. A file that parsed to `null`, or to an object with no `args`, threw on every drain, in `opLabel` or `postWrite`. The throw came before the week's give-up, so the file was never moved aside, and every copy queued behind it waited for good. SMD-1723 PR 3's review pass 9 confirmed it: 3 drains, 3 exits of 1, and the queue behind the file never moved. Only a hand edit or a corrupt file makes such a file: the hook writes every copy whole, through a temp file and a rename.

**Change** (`recipes/session-capture-hook/session-capture.mjs`, 1.10.1).
- **`isCopy`:** a copy as the hook writes one is an object with a string `tool`, an object `args` (not a list) and an `at` that parses as a date. `drainWrites` gives up any other parsed file as it gives up one that does not parse: moved to `writes/dead/`, and logged `not copied (given up): <name> is not a copy`.
  - The date is beyond the ticket's list. A copy with no date that a fault kept was never given up, since its age read as no number, so it stopped the queue for good too. Every copy the hook has written since the fan-out began carries one.
- **A throw from `postWrite`** keeps its copy, as a fault does, rather than ending the drain with an exception. It is marked `sent`, since the send may have reached the brain, and its line says `the copy failed in the hook` with the error. After a week it is given up like any other kept copy.
- The README's "What is skipped" bullet and `metadata.json` (1.10.1) say so.

**Held.** The hook's suite [12]:
- Eight queued files that parse but are no copy, ahead of a valid capture: `null`, `{}`, a capture with no `args`, one whose `args` is a list, one with no date, `[]`, a `tool` that is a number, and an edit whose `args` is `null`. One drain moves the eight to `writes/dead/`, logs each `is not a copy`, and lands the capture behind them, its one call to the canary.
- A capture the fake canary answers with `content` that is not a list, which throws in `textOfResult`: the drain exits 1 with no exception, and the copy stays queued, marked `sent`, with the line logged. The same copy queued eight days ago is given up after a week, into `writes/dead/`.
- **Mutants:** each of these fails the case that holds it:
  - no shape check;
  - no date in the shape;
  - `args` allowed to be a list;
  - `args` allowed to be `null` (it survived the first run, which seeded no such file: the `null` edit was added for it);
  - no `try` around `postWrite`;
  - a throw not marked as maybe sent;
  - a throw given up at once.

**Left as it is.** A copy whose `tool` is a string the brain has no tool for is a copy by this rule. It is kept, as a tool missing from an older server is, and given up after the week.
