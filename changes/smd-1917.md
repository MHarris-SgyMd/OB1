## FORK

FORK.md is the front door, and every change is one file — `changes/NNN-<slug>.md` with a fixed shape and a 150-line cap, an index generated from the directory, fragments numbered into it at release, and check 15 holding the sizes, the numbering and every citation of a change number (SMD-1917)

**What changed.** The 85 `### N.` sections FORK.md carried for changes 18–102
(and 103, which reached `main` while this was in review) are one file each under
`changes/`, named `NNN-<slug>.md`, the heading level changed and the text
otherwise as it was at the split. FORK.md keeps the pin, the version scheme, what
the fork is for, the 1–17 table, "Files we own", the drift guards and the
standing sections, and carries a **generated index** — one row per change, the
title's first clause and its ticket, linked to the file, and the fragments landed
since the last release by ticket — between two marker comments that
`scripts/fork-index.mjs` rewrites from the directory. A change file has a shape
(`changes/README.md`) and a **150-line cap**, fragment or numbered. SMD-1804's
fragments keep their shape and their rule — a PR ships `changes/smd-NNNN.md`, the
release step assigns the number — and the release step writes each fragment as
the next numbered *file* and regenerates the index instead of appending a
`### N.` section to FORK.md; its FORK-count check is retired, its fragment rules
live in `scripts/fragments.mjs` where the step runs them too, and its release
pairing reads a released ticket from a numbered file's title. Two placements
moved at the split: SMD-1038's "second vector store" design, written inside
change 19's span, is in change 79, the measurement it pre-registered; "The
recurring defect in this fork" is a standing section of FORK.md. Two standing
paragraphs that were a change's narrative are a paragraph each. Change 102 is the
first record cut to the shape (470 lines to 119); this record is the second.

**Why.** FORK.md was 1,237,711 bytes and 17,705 lines at `main` c6fc294 — about
300k tokens, larger than any context window in use, growing ~100 KB per merged
PR as every review pass appended a paragraph whose facts already sat in the
commit body's `(caught: …)` tags (change 100's tooling reads those from commits,
never from FORK.md). No reader took it whole; a reviewer verifying one record
re-read a 457-line section on each of eight passes. The one file also made the
numbers hand-kept: every merge of `main` renumbered a section — change 102 was
100 on its branch — and the 231 citations of "FORK.md change N" kept whatever
number a section had when they were written, wrong silently after a renumber.
SMD-1804 ended the hand numbering ten minutes after this branch's first commit;
it still wrote the record into FORK.md.

**Held.** Check 15, a pure `forkLayoutProblems({ entries, forkText, citations })`
with layout probes and citation-reader probes on every run (the drop-the-mechanism
harness that proves the probes runs a copy of the check with both files excluded
from its own scan — its baseline is checked before any mutant counts): a file under
`changes/` is `NNN-<slug>.md` or `smd-NNNN.md` (or the README) and a regular
file; the numbers run contiguously from 18 with no duplicate and none below; a
numbered file opens with `# N. <title>` matching its name; a file is at most 150
lines, the 47 over it when the split landed listed in `OVERSIZE_AT_SPLIT` with a
ceiling they may only shrink under, the list held stale two ways; FORK.md is
under 64 KB outside its generated index, carries no numbered section at any
heading level, and its index equals what `fork-index.mjs` renders; and every
citation of a change number in a file git tracks or would track — "FORK.md
change N" in any spelling (`FORK change`, `` `FORK.md` §N``, `FORK.md's`, `(FORK 79)`,
a "change N" within a few words of a ticket in a code comment), lists,
a `changes/NNN-<slug>.md` path (or a relative link inside the record) that must
name a file that exists, as it is, `db/README.md`'s "NNN change M" map, and the bare
"change N" the record itself uses, lists and wrapped lines included — names a
number with a file or a row of the 1–17 table; a thousands group, a decimal, a
date or a number before a unit word is not a citation. Check 16
(`fragmentProblems`, `scripts/fragments.mjs`) holds a fragment's front matter, a
changelog line naming its tickets and no other, and a FORK body — to the end of
the file — whose first line is the plain title naming every ticket; check 17b
reads a released ticket from the numbered files' titles alone. The release step refuses a stray, a
gap, a duplicate ticket, a fragment check 16 would refuse or one naming a
migration outside the range, a half-applied earlier cut (by its
changelog section, its release entry or the numbered files it wrote), a
hand-written Unreleased note, a shallow clone and a dirty tree, and renders
every file before it writes one.
Every branch of the three decisions bites under a drop-the-mechanism harness,
and real-file mutants bite at their lines (a link renamed under a change file, a
`### 104.` left in FORK.md, a fragment past the cap, an index row edited, a
citation of 175 in `deploy/README.md`).

**Measured after.** FORK.md 61,615 bytes (50,061 outside the index) and 828
lines, 86 index rows and two fragments; `changes/` 86 numbered files, two
fragments and a README, 39 under the cap, 47 listed; the check runs in under a
second.
`bun scripts/fork-index.mjs` twice leaves no diff. A release assembled with
`--write` on a copy of the tree passes the check, a second cut after it too. A
reviewer's record of one change is one file: under 4k tokens for the two cut to
the shape, about 12k for the largest legacy file, against a grep into 1.2 MB.

**Review passes.** A cold read beside a run-it reviewer with a mutation harness
on the real files and a throwaway copy of the tree, each pass; one row per
finding that changed the mechanism, the rest in the pass commits. Each pass's top
finding was in the previous pass's additions and real, so no stop signal yet.
