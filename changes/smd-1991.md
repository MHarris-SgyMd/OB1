## Changelog

A recipe or integration server run from a checkout now resolves its packages from the pinned install in `extensions/`, the MCP SDK included, with no `NODE_PATH` on its command and from any working directory. `recipes/node_modules` and `integrations/node_modules` are committed links to `../extensions/node_modules`, so `(cd extensions && bun install)` once serves every server. Before, the documented `NODE_PATH=extensions/node_modules` did not reach the SDK's subpaths (`@modelcontextprotocol/sdk/server/mcp.js`), so `ob-graph` and `work-operating-model-activation` started only because Bun downloaded whatever SDK version npm served into its cache, which needed network access and was unpinned. The run lines in those READMEs now pass `--no-install`, so a skipped install fails the start, naming the package, instead of downloading. Without the flag Bun still downloads in a checkout where `extensions/` was never installed, since a link to nothing counts as no `node_modules` (SMD-1991).

## FORK

recipes/ and integrations/ resolve extensions/' pinned install through committed node_modules links, and test-auth starts their servers under --no-install (SMD-1991)

**What changed.**
- `recipes/node_modules` and `integrations/node_modules` are committed symlinks to `../extensions/node_modules`. Bun resolves a bare import by walking up from the importing file, so every server under either directory finds the pinned `hono`, `zod`, `@hono/mcp` and MCP SDK, the SDK's `exports` subpaths included, without `NODE_PATH`. A recipe with a `package.json` of its own (`repo-learning-coach`, `vercel-neon-telegram`, the import recipes) resolves its own `node_modules` first once installed. Run without its install, with `extensions/` installed, it resolves whatever `extensions/node_modules` holds (the SDK's own dependencies included) and fails with `Cannot find package` on the rest, where Bun used to download what was missing. `.gitignore`'s `node_modules/` matches directories only, so it does not ignore a link.
- `extensions/test-auth.ts` holds both links: each must read `../extensions/node_modules`. It starts each server under `bun --no-install`, with any `NODE_PATH` from the shell removed, so a package that does not resolve fails the start instead of being fetched.
- `extensions/bunfig.toml` sets `[install] auto = "disable"`. Bun reads it for any command run from `extensions/`: the three suites and `package.json`'s scripts. So a recipe or integration the suites import in-process fails at import when its packages do not resolve, rather than running on whatever npm serves. `bun install` is unaffected, and the servers test-auth spawns run from the root.
- The loader plugin in `test-auth.ts` and `test-writes.ts`, which rewrote the four package names in recipe and integration files to `extensions/node_modules`, is gone: Bun's own resolution now finds the same files through the links. `test-tools.ts`, which had no loader, ran `ob-graph` on downloaded packages until now. Measured without the links and with an empty cache, importing it from `extensions/` downloaded hono 4.13.13 (pinned at 4.13.8) and SDK 1.32.1 (pinned at 1.30.0).
- The run commands in the READMEs of `ob-graph`, `work-operating-model-activation` and `agent-memory-api`, in `compat/supabase-sql/README.md` §3, in `bring-your-own-context`'s pointer and in CONTRIBUTING's example drop `NODE_PATH=extensions/node_modules` and pass `--no-install`. Their text says what resolves through the links. `primitives/deploy-remote-mcp` and `primitives/troubleshooting` no longer tell an operator to add `NODE_PATH`. `kubernetes-deployment`'s README says that without its own install the server now resolves `extensions/`' install through the link rather than failing. `extensions/package.json`'s comment, `db/test-support.ts`'s `STACK` docblock, `scripts/contributions.ts`' `NOT_CONTRIBUTIONS` docblock and the header docblocks of test-auth and test-writes name the links. The extension template's `AGENT_SPEC.md` no longer says to add a new package to test-auth's `PACKAGES`, which only the loaders needed.
- CONTRIBUTING's Required Files gains a Dependencies bullet. A server that imports only the stack needs no install; anything else goes in a `package.json` in the contribution's own folder, created before installing. Once `extensions/` is installed, npm run in a recipe folder with no `package.json` takes `recipes/` as its project. It deletes the link, installs a real `node_modules` there and writes `recipes/package.json` and `recipes/package-lock.json`, which breaks every recipe server (measured with npm 10; with the link dangling, npm installs in the recipe folder). CONTRIBUTING says how to recover, and test-auth's guard fails "not a link".

**Why.** Under Bun 1.4.0, `NODE_PATH` resolves a package's main entry but not its `exports`-mapped subpaths. `hono`, `zod` and `@hono/mcp` resolved through it, and the v1 SDK's `@modelcontextprotocol/sdk/server/mcp.js` did not. A file with no `node_modules` anywhere above it then falls back to Bun's auto-install, which fetches the latest version from npm: the cache here held SDK 1.24.3, 1.30.0, 1.30.1, 1.31.0 and 1.32.1, against a pin of 1.30.0. test-auth's under-bun starts passed the same way. The ticket's comment of 2026-09-27 ordered this after SMD-2279, and it was taken now on request. The v2 packages are imported by bare name, which `NODE_PATH` does reach (measured: `@modelcontextprotocol/server` and `/core` through `server-portable/node_modules`). But the links resolve both stacks, and they make the commands independent of the working directory, which `NODE_PATH`'s relative path was not.

**Held.**

  - Survives: `NODE_PATH` put back in the spawn environment. Bun finds the links walking up from the file before it reads `NODE_PATH`, so the variable is never consulted. Removing it is for the docs, not the resolution.

**Not taken.**
- *A `package.json` and install of their own for `recipes/` and `integrations/`.* Two more installs to keep in lockstep with `extensions/`, which the links share instead.
- *`[install] auto = "disable"` in a root `bunfig.toml`.* It would refuse Bun's auto-install for every command run from the root, recipes with installs of their own and scripts included. The links already stop it under `recipes/` and `integrations/` once `extensions/` is installed, and the effect on the rest of the tree is unmeasured. The file in `extensions/` covers only commands run from `extensions/`.
- *`--no-install` on every run line in the tree.* The extensions' READMEs, `primitives/deploy-remote-mcp` and the integrations that import only the shim keep `bun <file>`. An extension's install sits beside it, and a shim-only server imports no package. A skipped install there downloads as it always has (review pass 1).
- *A guard confining recipe and integration imports to the stack.* `extensions/node_modules` also holds the SDK's own dependencies (express, cors, jose, ajv), so a server importing one resolves it from the lockfile's pin without failing. Before this, the loaders rewrote only the stack, and anything else was downloaded (review pass 1).
- *A check refusing `recipes/package.json` and `integrations/package.json`.* test-auth's guard already fails when npm replaces a link, and `git status` shows the deletion (review pass 1).
- *Windows checkouts.* These are the first symlinks in the tree. Under `core.symlinks=false` they check out as text files. test-auth's guard then fails, and the suites and the `--no-install` run lines fail with `Cannot find package`; only a plain `bun <file>` run outside `extensions/` downloads. A text-file link was tried on macOS, not on Windows (review passes 1 and 4).
