## Changelog

Each plugin's SQL logs in as a Postgres role of its own, `ob1_plugins_<name>`, that may switch to its own plugin's role alone, so SQL in one plugin that undoes its role is refused every other plugin's tables; each role's password is derived from the one `OB1_PLUGIN_DB_PASSWORD`, and the migrator retires the shared `ob1_plugins` (SMD-2756).

## FORK

Each plugin logs in as a role of its own — SQL that undoes one plugin's role reaches no other plugin's tables (SMD-2756)

**What changed.** Before, every plugin's SQL ran on a connection logged in as one role, `ob1_plugins`, which held `SET` on every plugin's role (SMD-2310). The maintainer decided on 2026-10-28, in SMD-3215's ADR, that each plugin gets a login of its own. This builds it:
- **`db/config.mjs`.** `pluginIdents` names a third role, the login `ob1_plugins_<name>`. `pluginLoginPassword(secret, name)` is the hex HMAC-SHA256 of that role's name under `OB1_PLUGIN_DB_PASSWORD`, and `pluginLoginUrl(url, name, secret)` builds the plugin's connection string from it. `SHARED_PLUGIN_LOGIN` names the retired role. `deploy/.env` still holds one secret, under the same name.
- **The migrator** (`db/migrate.ts`). For each named plugin with migrations it makes the login role (LOGIN, NOINHERIT, no superuser, its derived password) when missing, and grants it `SET` on the plugin's role and nothing else. It does so beside the role and schema, under the run's lock, and never changes an existing role's password. Each plugin's files run on its own login connection. A run that would make a login without the secret is refused before anything runs, as before. `--dry-run` names the login it would make.
- **The move.** A plain run whose core is clean, and whose plugins (if any are named) applied cleanly, retires `ob1_plugins` whether or not it names a plugin. It does so under the run's lock:
  - in one transaction, every `ob1_plugin_*` role it holds is revoked from it, each grant by its own grantor (`GRANTED BY` on PG 16), and it is made NOLOGIN; one left after the revoke fails the run;
  - then it is dropped;
  - a role something still depends on (a privilege granted to it, say) is kept, NOLOGIN and holding no plugin role, and the run says so. A later run finds it so, says so in a line, and takes no lock.

  The plugins' schemas and rows are not touched. A plugin not named gets its own login when a run names it. `--dry-run` says it would retire it, and `--reapply` leaves it alone.
- **The servers** (`server-portable/store-sql.ts`). Each plugin's pool logs in as that plugin's login, checked once by `session_user`. A pool refused its first login (no role yet, or one made under another secret) says so, naming the role, rather than Postgres's bare "password authentication failed".
- **Preflight's `plugin tables` row,** per enabled plugin with migrations, checks its login role:
  - it exists and logs in with the derived password;
  - it is no superuser, and NOINHERIT;
  - it holds `SET` on its plugin's role;
  - it is a member of no other role (another plugin's included);
  - it holds no table privilege on the core's relations or on another plugin's schema.

  The row fails while `ob1_plugins` still holds any plugin's role.
- **`deploy/canary.sh`.** `set_canary_password` sets each `ob1_plugins_*` role's password to the one derived from the canary's own secret, where the canary's Postgres has the role. It used to set `ob1_plugins` to the secret. The derivation is `config.mjs`'s own, run by `bun`, and the passwords reach psql on its stdin.
- **CI's canary step** plants `ob1_plugins_example` under stable's secret, and holds that the canary's derived password logs in after the up and stable's does not. Comments and docs that described the shared role now describe each plugin's: `db/README.md` §6, `plugins/README.md`, the example's README, `docs/operator-surface-tiers.md`, `docs/brain-coordinator.md` ("Built"), `deploy/README.md`, `.env.example`, `compose.yaml`, `tier.sh`, check 31's comment.

**Why.** From `ob1_plugins`, SQL in one plugin that undid its own role (`RESET ROLE`, `END;`, `set_config('role', …)`) could `SET ROLE` to any other plugin's role and read or write that plugin's tables. Check 31 refused the undoing as an accident guard, and curation was the control. Only the example plugin exists today. But SMD-2311, SMD-2690 and SMD-2101 port nine plugins that carry SQL, and the ticket asked for the boundary to be Postgres's before the first of them lands.

**Version.** `minor`: a new preflight check, and a database role the release's migrator retires. No URL, route, setting or table a client sees changes, and `OB1_PLUGIN_DB_PASSWORD` keeps its name. An operator who changed `ob1_plugins`' password by hand, as the example's README told them to, changes each plugin login's password instead. The README now says how.
