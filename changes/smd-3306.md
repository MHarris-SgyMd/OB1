## Changelog

A work thread can be read: the `thread` operation (MCP `thread`, REST `GET /v1/thread`, read scope) returns the thoughts holding one subject in the order they were captured, by its key (`ticket:SMD-3306`, or the ticket alone) or around a thought by its id, a page at a time. A superseded thought stays in its thread and is labelled, a ticket's own row shows its status as that row records it, and a ticket's thread names the threads its board links reach. `fetch` says, for each thread a thought stands in, the thought it continues and the one that continues it (SMD-3306 PR 7a-2a).

An unlinked work thread is said (SMD-3306 PR 7a-2c): `brain_info` gains a `threads` fact and a `Threads` row, and preflight a `threads` row, counting the threads and the keys whose edges differ from their thread's — a thread the upgrade to migration 120 has not linked, or a gap a delete left — and the run that links them, `cd db && bun threads.ts --url <the owner's connection string>`. The census is bounded and exact, the first 10,000 subjects and thread edges in key order, and says when it stopped there; `threads.ts --status` reads every key. Preflight warns, never fails.

### PR 7a-2c: an unlinked thread is said

**What changed.**
- **One census** of the work threads, now in `server-portable/brain-info.ts`: whether each thread's standing edges (migration 120) are the ones its thoughts want, compared edge by edge as `thread_relink` reads them.
  - A key whose edges differ is unlinked: a thread the upgrade has not linked yet, or a gap a delete left.
  - A key no thought holds that still carries edges is orphaned.
  - `db/threads.ts --status` reads it with no bound, as it did before; the census was its own.
- **Bounded and exact** (the maintainer's call, 2026-11-08).
  - `brain_info` and preflight walk the standing subjects in key order through 111's key index, at most 10,000 rows, and leave out a key the bound cuts, so every key read is read whole.
  - The thread edges are walked the same way through 120's key index, at most 10,000 rows. A key their bound cuts is left out too, and so is every key from the first cut on, of either walk.
  - `complete` says whether everything was read. A brain the upgrade left unlinked shows in any keys read; a gap a delete left shows only within them.
  - Past the bound, every count is of the keys before the first cut, and the row says so and how many subject keys that was. A `phrase:` key sorts before `pr:`, `ticket:` and `version:`, so the phrases are read first.
- **`brain_info`** gains a `threads` fact:
  - the threads, the thoughts in them, the edges standing and wanted, the unlinked and orphaned keys, how many subject keys were read, and `complete`;
  - it names no key: a phrase key is the judge model's words, and the record carries none;
  - it is null before 120, where every thread would read unlinked. The gate finds `thread_relink` in any schema, so a role whose search_path misses the brain's schema is told that, not that 120 is missing;
  - it is not a stats read, because preflight reads it;
  - the table gains a `Threads` row.
- **Preflight** gains a `threads` row:
  - ok when every key read is linked;
  - a warning, never a failure, on an unlinked or orphaned key, naming the run that links them (`cd db && bun threads.ts --url <the owner's connection string>`);
  - each says when the census stopped at its bound;
  - a warning, not a pass, when the first key in key order alone passes the bound, so that no key was read (`brain_info`'s row says `not counted`);
  - with only orphaned keys before the cut, it says no subject key came before it, and warns on the orphans;
  - skipped before 120.
  - The row is `threadsRow` in `brain-info.ts`, a function of the fact alone, so test-server holds each branch.

A delete by a role short of a re-link's writes leaves a gap (120's NOT HERE). Only `--status` said so, and only to someone who ran it. The maintainer asked for the signal in both preflight and `brain_info`, bounded (2026-11-06). On stable on 2026-11-08 the whole census took 19 ms over 3,948 subjects and 2,303 thread edges, and it grows with the brain.

**Not taken.**
- `--status` reading the census with a bound it never reaches is about 25% slower than its own unbounded query was (11.7–13.1 s against 10.0–10.4 s at 3M thoughts). It is an operator's one-off run, and one census keeps the two from drifting.

### PR 7a-2a: a work thread can be read

**What changed.**
- **`thread`** (read scope; MCP `thread`, REST `GET /v1/thread`), in `server-portable/core/threads.ts`. Exactly one of `key` or `id`:
  - `key` reads that subject's thread from its start, `limit` thoughts a page (1–100, default 20). A key is read as the extractor writes it: `ticket:` and its id in any case; a ticket alone (`SMD-3306`) when its team is one a text means as a ticket — `PR-12` and `UTF-8` are refused, a ticket filed under such a team read with `ticket:` before it (`ticket:ES-5`); `pr:` and `version:` in any case, their numbers without leading zeros. When more follow, the thread carries a `cursor`, passed back as `after` with the same key.
  - `id` reads each thread the thought stands in, around it: up to half the page before it, then it and those after, its `place` marked.
- **What a page carries.** Each member has its id, title, time and place (1 the first). A superseded member carries `supersededBy` and stays in the thread, which keeps its history. A board ticket's own row — board-sync's, `metadata.source` `linear` (which no key may write), the ticket's head row (068's `ob1_ticket_head`), its `metadata.issue` a ticket's shape — carries `ticket`: the ticket and its status as that row records it. The row is rewritten in place, so it keeps its first place. These are the maintainer's decisions of 2026-11-06.
- **Linked threads.** A ticket's thread names the threads its ticket's board links reach (`linked`): each one's key, how its ticket stands to this one (`parent`, `child`, `blocks`, `blocked_by`, `relates_to`), and how many thoughts its thread holds. They are read from 053's `linear` links, the ticket's rows' own and the other rows' naming it. Only the first 50 are shown, with `linkedMore` set when there are more. No thread runs across a link, and `duplicate_of` and a text reference link none.
- **`fetch`** carries `threads` where the thought stands in one: per thread, its key, the thought's place, the thread's size, and the member it continues and the one that continues it (`continues`, `continuedBy`), each with its title and `supersededBy`. A thought in no thread adds nothing to ChatGPT's shape. A failed read gives `threads: null` and is said in the log, as the `claimed` label's is.
- **The store** has two new reads: `threadPage` and `threadPlaces`. Both read a thread from its standing subjects (111's key index), numbered in 120's order (created_at, ties by id, an undated thought last), not from 120's edges. So a thread reads whole on a brain that `db/threads.ts` hasn't linked yet. A ticket's own row is its head in 068's `ob1_ticket_head`, so the read needs SELECT there, as `prefer_current` does.
- **A refusal**, `REFUSED_THREAD_INPUT` (400), with `problem`:
  - `key_or_id`: neither key nor id is given, or both are;
  - `key_shape`: the key is not a subject key. It is named in MCP's text, never in its value;
  - `after_needs_key`: `after` is given with an id.

  A cursor of another tool's is `REFUSED_CURSOR`. An id that no thought has is `NOT_FOUND`.
- **MCP's value** carries a ticket's, pull request's or version's key. A phrase key is the judge model's words, so it rides the text alone, quoted.
- `tools.json`, OpenAPI and `rest-client` are regenerated, and `server-portable/README.md` gains a "Work threads" section.

**Why.** Migration 120 made a thread's edges stand, but nothing read them: a thread was visible only to `db/threads.ts --status`. The maintainer cut 7a-2 in three (2026-11-06): this read; SMD-2726's relations read (7a-2b); and the unlinked-threads signal in preflight and `brain_info` (7a-2c). The `thread` read takes a thought's id or a subject key, as the maintainer chose.
