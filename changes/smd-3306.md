## Changelog

A work thread can be read: the `thread` operation (MCP `thread`, REST `GET /v1/thread`, read scope) returns the thoughts holding one subject in the order they were captured, by its key (`ticket:SMD-3306`, or the ticket alone) or around a thought by its id, a page at a time. A superseded thought stays in its thread and is labelled, a ticket's own row shows its status as that row records it, and a ticket's thread names the threads its board links reach. `fetch` says, for each thread a thought stands in, the thought it continues and the one that continues it (SMD-3306 PR 7a-2a).

A thought's own subject can be a set (SMD-3306 PR 7a-3a, migration 130): one standing subject per thought and key, at most three, found one way by one pass, so a thought stands in each of its subjects' threads. `record_thought_subjects` writes a set; `record_thought_subject` and `close_thought_subject` keep their answers as sets of one. Nothing finds a set yet: the rules and the judge's question that do follow (PR 7a-3b).

An unlinked work thread is said (SMD-3306 PR 7a-2c): `brain_info` gains a `threads` fact and a `Threads` row, and preflight a `threads` row, counting the threads and the keys whose edges differ from their thread's — a thread the upgrade to migration 120 has not linked, or a gap a delete left — and the run that links them, `cd db && bun threads.ts --url <the owner's connection string>`. The census is bounded and exact, the first 10,000 subjects and thread edges in key order, and says when it stopped there; `threads.ts --status` reads every key. Preflight warns, never fails.

### PR 7a-3a: a thought's subjects are a set (the database side)

**What changed.**
- **Migration 130:** one standing `subject` per thought and key (111's index on the thought alone replaced), at most three, found one way by one pass; statistics on a facet's key (`thought_facets_key_stats`), so the planner reads a thread by its rows.
  - `record_thought_subjects(thought, keys, by, judge_key, agent, fingerprint, recipe)` keeps a subject the set names found the same way by the same pass (its lineage moved to the text read now), closes the rest, and writes each key it lacks with its lineage; an empty set closes them all. It refuses as 113's door does (a text moved, a filed ticket disagreeing). `metadata` names one key; four keys, a NULL key or a malformed one are parameter errors.
  - `record_thought_subject` and `close_thought_subject` keep their signatures, refusals and answers as sets of one. `close_thought_subjects` closes only the set the caller read.
  - 120's trigger function: before the first re-link at a writer's commit, once a transaction, thought and set of keys moved, it locks every key the transaction wrote or closed on the thought, in key order (`ob1_thread_lock_keys`), and the thought and its neighbours in those keys' threads (KEY SHARE), so on a linked thread the re-links never wait on a thought after closing an edge to it; a subject kept beside a replace is not locked. Above READ COMMITTED the re-link's refusal comes first. 120 locked a close's key and the thought's one standing key: with a set, a replace could take a later key before an earlier one.
- Every reader of a thread already reads subjects by key, so a thought with a set stands in each key's thread, and the census counts it in each. db/README (125 migrations, the map, a paragraph), server-portable/README and the census's docblocks say so.

**Why.** The maintainer decided on 2026-11-05 that a thought's own subject can be a set: a multi-ticket session (7 of 275 canary thoughts drawn, SMD-3306's measure) is a segment of each ticket's work. On 2026-11-09 they cut 7a-3 in two (this PR the database side), and chose one rule's set of at most three.

### PR 7a-2c: an unlinked thread is said

**What changed.**
- **One census** of the work threads, now in `server-portable/brain-info.ts`: whether each thread's standing edges (migration 120) are the ones its thoughts want, compared edge by edge as `thread_relink` reads them.
  - A key whose edges differ is unlinked: a thread the upgrade has not linked yet, a gap a delete left, or a raw write's. A key no thought holds that still carries edges is orphaned.
  - `db/threads.ts --status` reads it with no bound, as it did before; the census was its own. It now prints each key it names on a line of its own, quoted as the shell takes it, since a phrase key may hold an apostrophe, a comma or a space. A role whose search_path misses the brain's schema is told that, not that 120 is missing.
- **Bounded and exact** (the maintainer's call, 2026-11-08).
  - `brain_info` and preflight walk the standing subjects in key order through 111's key index, and the thread edges through 120's, at most 10,000 rows each. A key either walk cuts is left out, and so is every key from the first cut on, so every key read is read whole.
  - `complete` says whether everything was read. A brain the upgrade left unlinked shows in any thread among the keys read; a gap a delete left shows only within them. Past the bound, every count is of the keys before the first cut, and the row says so and how many subject keys that was. A `phrase:` key sorts before `pr:`, `ticket:` and `version:`, so the phrases are read first.
- **`brain_info`** gains a `threads` fact and a `Threads` row:
  - the threads, the thoughts in them, the edges standing and wanted, the unlinked and orphaned keys, how many subject keys were read, and `complete`. It names no key: a phrase key is the judge model's words, and the record carries none;
  - it is null before 120, where every thread would read unlinked. The gate looks for `thread_relink(text, boolean)` in `thought_facets`' own schema, and in any schema only when that table does not resolve, so a role whose search_path misses the brain's schema is told that, not that 120 is missing;
  - it is not a stats read, because preflight reads it. It joins `thoughts`, so after a lock refused there it is not sent, and its row names `thoughts`. A census whose edges wanted are not its thoughts less its threads lost members to its join (a `thoughts` table earlier on the role's search_path) and is an error, never every thread unlinked.
- **Preflight** gains a `threads` row, `threadsRow` in `brain-info.ts`, a function of the fact alone, so test-server holds each branch:

  - a warning, not a pass, when the first key in key order alone passes the bound, so that no key was read, or when the keys read before the bound are each held by one thought, so that no thread was (`brain_info`'s row says `not counted`).

**Why.** Migration 120 keeps a thread's edges as its subjects land and leave, but a brain upgraded to it holds its threads unlinked until `db/threads.ts` runs. A delete that cannot re-link leaves a gap: a role without the writes, above READ COMMITTED, or beside a held key (120's NOT HERE). Only `--status` said so, and only to someone who ran it. The maintainer asked for the signal in both preflight and `brain_info`, bounded (2026-11-06). On stable on 2026-11-08 the whole census took 19 ms over 3,948 subjects and 2,303 thread edges, and it grows with the brain.

### PR 7a-2a: a work thread can be read

**What changed.**
- **`thread`** (read scope; MCP `thread`, REST `GET /v1/thread`), in `server-portable/core/threads.ts`. Exactly one of `key` or `id`:
  - `key` reads that subject's thread from its start, `limit` thoughts a page (1–100, default 20). A key is read as the extractor writes it: `ticket:` and its id in any case; a ticket alone (`SMD-3306`) when its team is one a text means as a ticket — `PR-12` and `UTF-8` are refused, a ticket filed under such a team read with `ticket:` before it (`ticket:ES-5`); `pr:` and `version:` in any case, their numbers without leading zeros. When more follow, the thread carries a `cursor`, passed back as `after` with the same key.
  - `id` reads each thread the thought stands in, around it: up to half the page before it, then it and those after, its `place` marked.
- **What a page carries.** Each member has its id, title, time and place (1 the first). A superseded member carries `supersededBy` and stays in the thread, which keeps its history. A board ticket's own row — board-sync's, `metadata.source` `linear` (which no key may write), the ticket's head row (068's `ob1_ticket_head`), its `metadata.issue` a ticket's shape — carries `ticket`: the ticket and its status as that row records it. The row is rewritten in place, so it keeps its first place. These are the maintainer's decisions of 2026-11-06.
- **Linked threads.** A ticket's thread names the threads its ticket's board links reach (`linked`): each one's key, how its ticket stands to this one (`parent`, `child`, `blocks`, `blocked_by`, `relates_to`), and how many thoughts its thread holds. They are read from 053's `linear` links, the ticket's rows' own and the other rows' naming it. Only the first 50 are shown, with `linkedMore` set when there are more. No thread runs across a link, and `duplicate_of` and a text reference link none.
- **`fetch`** carries `threads` where the thought stands in one: per thread, its key, the thought's place, the thread's size, and the member it continues and the one that continues it (`continues`, `continuedBy`), each with its title and `supersededBy`. A thought in no thread adds nothing to ChatGPT's shape. A failed read gives `threads: null` and is said in the log, as the `claimed` label's is.
- **The store** has two new reads: `threadPage` and `threadPlaces`. Both read a thread from its standing subjects (111's key index), numbered in 120's order (created_at, ties by id, an undated thought last), not from 120's edges. So a thread reads whole on a brain that `db/threads.ts` hasn't linked yet. A ticket's own row is its head in 068's `ob1_ticket_head`, so the read needs SELECT there, as `prefer_current` does.
- **A refusal**, `REFUSED_THREAD_INPUT` (400), with `problem`: `key_or_id`, neither key nor id is given, or both are; `key_shape`, the key is not a subject key, named in MCP's text, never in its value; `after_needs_key`, `after` is given with an id. A cursor of another tool's is `REFUSED_CURSOR`. An id that no thought has is `NOT_FOUND`.
- **MCP's value** carries a ticket's, pull request's or version's key. A phrase key is the judge model's words, so it rides the text alone, quoted.
- `tools.json`, OpenAPI and `rest-client` are regenerated, and `server-portable/README.md` gains a "Work threads" section.

**Why.** Migration 120 made a thread's edges stand, but nothing read them: a thread was visible only to `db/threads.ts --status`. The maintainer cut 7a-2 in three (2026-11-06): this read; SMD-2726's relations read (7a-2b); and the unlinked-threads signal in preflight and `brain_info` (7a-2c). The `thread` read takes a thought's id or a subject key, as the maintainer chose.
