## Changelog

`claim_work` now caps how many live claims one key can hold at once, so no runaway or buggy agent can hoard the board and lock every other agent out of work it never touches (SMD-3606, migration 140). The cap is per holder — a key's agent id, or its name where it has none — and counts only live claims (unreleased and unexpired), so a lapsed claim frees a slot. A new claim past the cap is refused `CLAIM_LIMIT`; a renewal of the holder's own claim is never capped, so work in hand is never cut off. The default cap is 50, and an operator sets it at runtime with `SELECT set_work_claim_cap(<cap>, <actor>)` in psql — no migration, no redeploy. (The MCP/REST `set_work_claim_cap` operation and its `brain_info` reading follow in PR 1b.)

## Record

A per-holder cap on live work claims, operator-settable — `claim_work` refuses `CLAIM_LIMIT` past it, migration 140 (SMD-3606)

**Why.** `work_claims` (115) let any key hold any number of live claims at once. A session that never releases, or a loop that claims a ticket a tick, could fill the board with one key's claims; 115's rules stop two keys claiming one ticket, but nothing capped one key across tickets (SMD-3606). The maintainer chose (2026-11-13) a cap the operator sets at runtime, not a constant only a migration changes.

**What changed.** Migration 140 adds the cap and redefines `claim_work` to enforce it.

- **The cap.** A new table, `work_claim_cap_settings`, holds the operator's cap settings, one standing at most — the same shape as 132's `priority_weight_settings`: a row is history (it changes only to end, once; a DELETE or TRUNCATE is refused), a partial unique index keeps one standing, and a trigger holds the cap to `ob1_work_claim_cap_refusal`'s range and the maker (and ender) to an operator key by its agent id (115's forced-release rule, SMD-2608: a name alone lends no kind). `ob1_work_claim_cap_builtin()` is the default, 50 — generous, since the dogfood's Claude Code sessions share one key (115), so a fleet of worktrees counts as one holder. `ob1_work_claim_cap()` reads the standing setting over the builtin; a stored cap the refusal names (a later migration narrowed the range, or a raw write with the trigger off) raises, so a new claim fails loudly rather than be capped by a value the operator did not choose (132's principle). `set_work_claim_cap(cap, actor)` is the operator's write (`NOT_OPERATOR`/`BAD_CAP` as 132's setter answers; `NULL` clears); `work_claim_cap_setting()` gives the standing cap without raising, for `brain_info` to read (wired in PR 1b).
- **The enforcement.** `claim_work` (115's, redefined with the same signature) counts the holder's live claims before it inserts a new one, under a per-holder advisory lock taken after the per-ticket lock — a consistent order, so the two never deadlock, and the count and the insert are atomic against the same holder's concurrent claims on other tickets (without it two could each read one below the cap and both insert). At or above the cap the call returns `{outcome: refused, code: CLAIM_LIMIT, cap, held}`. The renewal branch is before the count, so a renewal never reads the cap and is never refused by it.
- **The surface.** `CLAIM_LIMIT` is a refusal the claim surface relays like `WORK_CLAIMED` — the store union, the core op's code, the REST status (409) and the rendered words (release one, or an operator raises the cap) — so a capped claim reads cleanly on MCP and REST. The `claims` grant group gains `work_claim_cap_settings` (SELECT for the cap read on every claim, INSERT/UPDATE for the setter), carried to roles holding the group already (132's carry). The operator sets the cap through the SQL function `set_work_claim_cap` (an operator key, by its agent id), callable in psql. `rest-client/openapi.json` and `schema.d.ts` are regenerated, the claims endpoints' error schema now listing `CLAIM_LIMIT` (409).

**Scope / deferred.** PR 1 is the backstop: the cap, its enforcement, the `CLAIM_LIMIT` relay, and the operator SQL setter (runtime-settable via psql). The MCP/REST `set_work_claim_cap` operation and its `brain_info` reading — the surface by which the operator sets the cap as they set the priority weights (132) — follow in **PR 1b** (which regenerates the rest-client again, for the new route). The keyset cursor on `list_work_claims` is PR 2, release-by-holder PR 3.

**Not changed.** Nothing stored is altered; a brain whose keys each hold fewer than 50 live claims is unaffected on the upgrade. The core `thoughts` table is untouched. A lapsed claim still counts as free (115's definition), so the cap never blocks work a holder has let go.

**Review passes.**
- **Pass 1 (an adversarial cold-read):** no correctness bug in the enforcement path — the per-holder lock is taken after the per-ticket lock (consistent order, no deadlock), the count and the insert are atomic under it (the `[20cd]` race proves it), a renewal reads no cap, a lapsed claim does not count, and re-taking one's own lapsed work rightly counts against the cap. A fallback to the built-in 50 on a bad stored cap is a one-line alternative if the maintainer prefers it.
