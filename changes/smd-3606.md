## Changelog

`claim_work` now caps how many live claims one key can hold at once, so no runaway or buggy agent can hoard the board and lock every other agent out of work it never touches (SMD-3606, migration 140). The cap is per holder — a key's agent id, or its name where it has none — and counts only live claims (unreleased and unexpired), so a lapsed claim frees a slot. A new claim past the cap is refused `CLAIM_LIMIT`; a renewal of the holder's own claim is never capped, so work in hand is never cut off. The default cap is 50, and an operator sets it at runtime — no migration, no redeploy — either with the `set_work_claim_cap` operation (over MCP, or REST `POST /v1/work-claim-cap`) as they set the priority weights, or with `SELECT set_work_claim_cap(<cap>, <actor>)` in psql; `null` clears it. `brain_info` shows the standing cap.

`list_work_claims` now takes a keyset `after` cursor (SMD-3606, migration 143), so a full read of who-holds-what pages to the end instead of stopping at 1,000 rows: the reply gives a `cursor` for the next page while more follow, and `remaining` counts how many do. A cursor carries the filters it was made under, so one passed with others is refused. (That keeps the board readable past 1,000 live claims — which 140's cap now keeps from happening in the first place.)

## Record

A per-holder cap on live work claims, operator-settable — `claim_work` refuses `CLAIM_LIMIT` past it, migration 140 (SMD-3606)

**Why.** `work_claims` (115) let any key hold any number of live claims at once. A session that never releases, or a loop that claims a ticket a tick, could fill the board with one key's claims; 115's rules stop two keys claiming one ticket, but nothing capped one key across tickets (SMD-3606). The maintainer chose (2026-11-13) a cap the operator sets at runtime, not a constant only a migration changes.

**What changed.** Migration 140 adds the cap and redefines `claim_work` to enforce it.

- **The cap.** A new table, `work_claim_cap_settings`, holds the operator's cap settings, one standing at most — the same shape as 132's `priority_weight_settings`: a row is history (it changes only to end, once; a DELETE or TRUNCATE is refused), a partial unique index keeps one standing, and a trigger holds the cap to `ob1_work_claim_cap_refusal`'s range and the maker (and ender) to an operator key by its agent id (115's forced-release rule, SMD-2608: a name alone lends no kind). `ob1_work_claim_cap_builtin()` is the default, 50 — generous, since the dogfood's Claude Code sessions share one key (115), so a fleet of worktrees counts as one holder. `ob1_work_claim_cap()` reads the standing setting over the builtin; a stored cap the refusal names (a later migration narrowed the range, or a raw write with the trigger off) raises, so a new claim fails loudly rather than be capped by a value the operator did not choose (132's principle). `set_work_claim_cap(cap, actor)` is the operator's write (`NOT_OPERATOR`/`BAD_CAP` as 132's setter answers; `NULL` clears); `work_claim_cap_setting()` gives the standing cap without raising, which `brain_info` reads.
- **The enforcement.** `claim_work` (115's, redefined with the same signature) counts the holder's live claims before it inserts a new one, under a per-holder advisory lock taken after the per-ticket lock — a consistent order, so the two never deadlock, and the count and the insert are atomic against the same holder's concurrent claims on other tickets (without it two could each read one below the cap and both insert). At or above the cap the call returns `{outcome: refused, code: CLAIM_LIMIT, cap, held}`. The renewal branch is before the count, so a renewal never reads the cap and is never refused by it.
- **The surface.** `CLAIM_LIMIT` is a refusal the claim surface relays like `WORK_CLAIMED` — the store union, the core op's code, the REST status (409) and the rendered words (release one, or an operator raises the cap) — so a capped claim reads cleanly on MCP and REST. The operator sets the cap through the `set_work_claim_cap` **operation** (an MCP tool and REST `POST /v1/work-claim-cap`), an operator key's by its agent id — `REFUSED_NOT_OPERATOR` otherwise, `CLAIM_CAP_UNATTRIBUTED` (retryable) while the registry is away — mirroring `set_priority_weights` (132), or with the SQL function in psql. `brain_info` shows the standing cap (`work_claim_cap_setting()`): built in, the operator's, or the operator's refused. The `claims` grant group gains `work_claim_cap_settings` (SELECT for the cap read on every claim, INSERT/UPDATE for the setter), carried to roles holding the group already (132's carry). `rest-client` is regenerated — the claims endpoints' error schema lists `CLAIM_LIMIT` (409), and the `/v1/work-claim-cap` route is added.

**What changed (PR 2).** Migration 143 redefines `list_work_claims` with a keyset `after` cursor on its own order (issue, piece_key, claimed_at, id), as 110 gave `list_supersession_proposals`. All four order columns are NOT NULL and ascending (piece_key is `COALESCE(lower(piece), '')`), so the keyset is one row-value comparison — no NULL to unroll; the four cursor parameters are all-set-or-none (a partial cursor refused by name), and two trailing columns ride each row — `page_key` (the four values a reader passes back) and `remaining` (`count(*) OVER ()`, so a reader knows whether more follow before asking past the cap). The function becomes plpgsql (a sql function cannot raise the refusal) and 115's four-argument form is dropped first (a RETURNS TABLE cannot gain columns under CREATE OR REPLACE). The readers mirror `list_thoughts`/`list_supersession_proposals`: the store passes eight arguments always and returns a `ClaimPage`, the core op takes `after` and answers `cursor`/`remaining`/`pastCursor` (keeping `truncated` = more follow, now exact via `remaining`), a cursor is base64url of its selection (tag `claims`) and the position, so one passed with other filters is refused `REFUSED_CURSOR` (400, `reason` shape or filters), and `list_claims`'s MCP tool and `GET /v1/claims` take `after`. `list_work_claims`' EXECUTE stays PUBLIC (no grant to carry, as 115's listing read was); preflight reads the eight-argument signature; `rest-client` is regenerated. The `truncated` rule in `CLAUDE.md`/`AGENTS.md` now points at the cursor.

**Scope.** This change (PR 1, PR 1b and PR 2) is the backstop, its operator surface, and the listing cursor: the cap, its enforcement, the `CLAIM_LIMIT` relay, the `set_work_claim_cap` operation (MCP + REST) and SQL function, the `brain_info` reading, and the keyset `after` cursor on `list_work_claims`. (PR 1 landed the migration and the relay; PR 1b the operation and `brain_info`; PR 2 the cursor, migration 143.) Still ahead on SMD-3606: `release_holder_claims` (PR 3).

**Not changed.** Nothing stored is altered; a brain whose keys each hold fewer than 50 live claims is unaffected on the upgrade. The core `thoughts` table is untouched. A lapsed claim still counts as free (115's definition), so the cap never blocks work a holder has let go.
