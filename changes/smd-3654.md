## Changelog

A renewal that revives a lapsed work claim now says so: `renew_claim`, and `claim_work` with a token, answer when the claim had lapsed and name any claim made on its work meanwhile. The session hook marks such a renewal for the agent, and AGENTS.md's rule drops its own check. A plain release's refusal now says to ask the user before claiming again, and the own-key words and `list_claims`' description no longer send an agent to a lost-token path it doesn't need (SMD-3654).

## FORK

Claim replies that lead an agent right — a revived lapsed claim names what was claimed meanwhile, a release asks before a re-claim (SMD-3654)

**What changed.**
- **The lapse, reported.** `renew_claim`, and `claim_work` with a token, read the claim's lease before 115's writer runs. 115 answers with the new lease, so the old one is read first (`claimLease`): by id and token for `renew_claim`, which the primary key finds, by token for `claim_work`.
  - If the renewal revived a lapsed claim, the value carries `lapsed: { at, claimedSince }`. The claims are those made on overlapping work after the lapse, read by 115's own piece key (`claimsMadeSince`): the same piece, or either the whole ticket.
  - Each claim made since carries its id, work, holder, `ownKey`, times and `state`, never its label or reason. Those are another key's words, and its piece is quoted in the text.
  - The first ten are named, and `moreSince` counts the rest.
  - `claimedSince` is null when it couldn't be read, and `at` is null too when the lease before couldn't be. The renewal stands either way.
  - The words add: "It had lapsed at T; no other claim was made on its work meanwhile." Or: "…and since then another claim was made on its work: … Another agent may have built part of the work: stop, and tell the user before carrying on." Unread, they give one check and what each answer means: "list the ticket's claims with list_claims and include_ended: one on its work claimed after T means another agent may have built part of it, so stop, and tell the user; with none, carry on." With the lease unread, they start "Whether it had lapsed could not be read".
  - A live claim's renewal is unchanged. No migration: two reads beside 115's writers, the token a bind parameter matched by its hash, the server role's existing SELECT.
- **A plain release** refusing a renewal says "ask the user before claiming it again: a release may be an operator's, made on purpose", where it said "claim it again".
- **The own-key words** name this session's own claim on overlapping work, its id in the worktree's `.work-claims/` (work under it, or release it and claim the piece), before another session and a lost token. On a renewal's `WORK_CLAIMED` they say to release the claim being renewed instead.
- **The descriptions:** `list_claims` says a session finds its own claims by its worktree's token files, and that `holder` lists every session of a key. `renew_claim`'s and `claim_work`'s say the reply reports a lapse. The OpenAPI document and the rest-client are regenerated.
- **The session hook** (recipe 1.7.1) marks a renewal that reports claims made while the claim had lapsed, or couldn't read them or the lapse, with a `<id>.blocked.json` coded `CLAIMED_WHILE_LAPSED`. That covers its own renewal, and the agent's own when the claims hook reads it. It records the renewal, and the log says "renewed — but it had lapsed …". `--renew-claims` exits 1 on one it marked. The expiry it records from the agent's reply is the first `until … (claim <id>).`, so a piece named later can't set it. The lapse check it makes before reviving a claim it knows lapsed stays, for brains from before this change.
- **The rule** (AGENTS.md and CLAUDE.md):
  - The check before renewing a claim that may have lapsed stays.
  - Every renewal's reply is read for a lapse, expected or not. One naming claims made meanwhile is handled as `WORK_CLAIMED`, the marker's carry-on not waiting on a claim that already ended. An unread one gets the reply's own check.
  - After any lapse the agent finds the ticket's work again before pushing. On resume it looks beside each token file again after renewing.

**Why.** SMD-3602's review passes found that 115 revives a lapsed claim nothing covers without a word, so an agent renewing after a long absence could carry on over work another agent built while the claim was free. The client could only patch around it: a marker for one window, and a check the agent had to remember. Three reply texts also contradicted the rule they serve. The maintainer kept SMD-3602 client-only and raised this to Medium.

**Review pass 1** (a walkthrough reviewer and a cold reader):
- **The rule dropped the check before renewing a claim that may have lapsed,** leaning on the reply alone. Stable runs the old server until the next release, and nothing tells an agent which brain it is on. Restored, with the reply an added signal. (caught: walkthrough)
- **On a renewal, the own-key words said to release the claim in the way,** this session's live one, to claim the piece, where the rule says release the older. They now say to release the claim being renewed. (caught: walkthrough)
- **The unread words and the rule said opposite things:** a check with no meaning given for its answers, and a stop on any unread reply. Both now say one thing: list the claims; one claimed since the lapse means stop, none means carry on. (caught: walkthrough)
- **`WORK_CLAIMED`'s carry-on didn't fit a lapse report.** The claim is already renewed and nothing live need end. The carry-on waits on the other claim only while it is live. (caught: walkthrough)
- **The hook's detached renewal can take the report first,** so the agent's own renewal on resume sees no lapse. On resume the agent looks beside each token file again after renewing. (caught: walkthrough)
- **The rule named no label, code or search after a lapse.** One under the agent's own key is given to the user by its `list_claims` label, the marker's code `CLAIMED_WHILE_LAPSED` is named in the rule and the README, and a lapse sends the agent back to step 1's search for the ticket's work. (caught: walkthrough)
- **Another key's piece in the lapse list was unquoted,** read as the reply's own words. One naming `until … (claim <id>)` also steered the hook's greedy pattern, which took the last match. Quoted as `WORK_CLAIMED`'s text quotes it, and the hook takes the first. (caught: cold-read)
- **A failed lease read hid the lapse for good.** `leaseBefore` swallowed the error, so the renewal answered as a live one. It now reports `at: null`, and the words say whether it had lapsed couldn't be read. (caught: cold-read)
- **`claimLease` scanned the table by token hash,** which has no index. `renew_claim`'s reads by id and token. (caught: cold-read)
- **The agent's own unread reply was untested in the hook.** Tested, with the unknown one. (caught: cold-read)
- **`--renew-claims` exited 0 on a renewal it marked,** where the README says a blocked one exits 1. (caught: cold-read)
- **`claim_work`'s description didn't say a renewal through it reports a lapse.** It does now. (caught: cold-read)
- **The list of claims since had no bound.** Ten are named, and the rest counted. (caught: cold-read)
- **Declined:**
  - the agent's own piece, released at merge, read as a claim made meanwhile: it arises only when the split step was skipped, and costs one needless question;
  - a renewal within a millisecond of the expiry: it can only say "no other claim was made", which is harmless.

**Not taken.**
- **A migration changing 115's writer to report the old lease.** Two reads in the core say the same, and leave 115, which every brain runs, untouched.
- **Refusing to revive a lapsed claim when claims were made meanwhile.** The renewal still stands: the claim is the agent's, and the reply tells it to stop. A refusal would leave a claim held by nobody, while unmerged work may still exist.
