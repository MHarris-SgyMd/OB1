## Changelog

A tool call to a vendored MCP server that answers over an event stream and runs longer than about ten seconds is now answered: the stream is kept alive by the core server's keepalive frame. Before this, Bun closed the stream with no log line. A client that leaves any of these servers mid-call is now logged (SMD-2001).

## FORK

A vendored MCP server's slow tool call is answered, not reset — the core server's SMD-1864 keepalive and its abandoned-request line reach the ten @hono/mcp servers (SMD-2001)

**What changed.**
- `server-portable/sse.ts` gains `mcpReply(c, respond)`. For a POST, the transport's reply goes through `withSseKeepalive`, with a `: keepalive` comment every 5 s up to the 10-minute ceiling. A client that closes the connection before the reply is complete, mid-upload included, is logged once with `abandonedRequestLine`, named by `requestLabel` (method and tool, never the arguments); the listener is registered before the body is read. A client already gone when the call would start is logged and answered 408, and the tool never runs (the server has been built by then, unlike at the core route). A stream held to the ceiling is logged with `vendoredStalledLine`, which names no `OB1_LLM_TIMEOUT` — no such bound exists in these servers. Any other method's reply passes through unread and unwatched. Both helpers moved here from `index.ts`, which imports them and re-exports them for its suites. The core route itself is unchanged.
- A byte-for-byte copy of `sse.ts` now sits beside `auth.ts`'s in `extensions/_shared/`, `recipes/_shared/` and `integrations/_shared/`, the three directories that hold MCP servers. `bun run sync-sse` in `extensions/` rewrites them, as `sync-auth` does for `auth.ts`.
- Each of the ten servers built on `@hono/mcp`'s `StreamableHTTPTransport` now sends its reply through `mcpReply(c, () => transport.handleRequest(c))`: the six extensions plus meal-planning's shared server, `ob-graph`, `work-operating-model-activation` and `kubernetes-deployment`. The branch wired thirteen; SMD-1931 retired `enhanced-mcp`, `delete-thought-mcp` and `update-thought-mcp` while it was in review, and their wiring went with them on the merge. `mcpReply` reads the body for the label, and Hono caches it, so the transport's own read sees the same text. The Kubernetes image copies `_shared/sse.ts` too, and `integrations/.dockerignore` admits it by name; without that entry the image build fails with `"/_shared/sse.ts": not found`.

**Why.** SMD-1864 measured that Bun 1.4.0 closes a streamed response silent for its idle timeout at the next 4-second sweep, between 8 and 12 s of silence. It fixed only the core server. `@hono/mcp` answers a POST on an event stream it writes nothing to until the tool returns; its own 30 s ping is on the GET stream alone. Every vendored MCP server ran on Bun's defaults (`export default { port, fetch }`, SMD-1799), so a tool call silent past the sweep was reset with no trace. The calls most likely to hit it pay a provider round trip before they answer: kubernetes-deployment's search and capture, and enhanced-mcp's capture until SMD-1931 retired it. professional-crm answers JSON (`enableJsonResponse`), and Bun does not reap a handler that is still pending, so it was already answered; for that server only the abandoned line is new. The ticket's plan, one wrap in `compat/deno-on-bun.ts`'s `serve`, no longer had a place to go: SMD-1799 removed that file, and SMD-2284 had already moved the keepalive out of `index.ts`.

**Held.** `extensions/test-auth.ts`, in the server job:
- *The probe.* kubernetes-deployment's real `search_thoughts`, served by `Bun.serve` on the runtime's defaults, with the provider's embedding stubbed to answer after 13 s. The call is answered at about 13.0 s with its JSON-RPC envelope after two `: keepalive` frames. A second call whose client gives up at 1.5 s logs one abandoned line naming `tools/call search_thoughts`, and its query appears in no warning or error line. The probe ran on enhanced-mcp's `brain_capture_thought` until the merge with SMD-1931.
- *Mutants.* Two mutants fail the probe with the original failure, `ECONNRESET` at 12.0 s and no log line: one drops the wrap in the probed server (enhanced-mcp, then kubernetes-deployment after the merge), the other drops `withSseKeepalive` from `mcpReply`.
- *Guards.*
  - Every `_shared/sse.ts` is byte-for-byte `server-portable/sse.ts`, the tree's copies match the list, and `sync-sse` names each directory.
  - Every held MCP server imports `../_shared/sse.ts` and calls `transport.handleRequest` only inside `mcpReply`.
  - The set of files that build a `StreamableHTTPTransport` equals the set held, so a new server cannot skip it.
- *mcpReply's edges.* A GET's stream comes back untouched, and its client leaving logs nothing. A POST whose client is already gone is answered 408 with one line, and the tool never runs. A client that leaves mid-upload from kubernetes-deployment's real route and transport is logged once. A stall is logged in the line given, and the vendored line names no core-only bound. A mutant for each of the first three fails its case. In the probe, both calls are seen reaching the provider before "never the query" is asserted, so that check has a positive control.
- `server-portable/test-server.ts` [17] passes with the helpers in their new home.

**Measured after.** On the merge with main: test-auth 700/700 (SMD-1931 took the retired servers' cases), and the probe adds about 13 s. test-server 832/832.

**Not taken.**
- *Raising `idleTimeout`.* SMD-1864 declined it with the measurement: it moves the cliff and lets dead sockets linger.
- *A wrapper around each server's whole `fetch`.* It could only label a request by reading a copy of its body, and a copied body is where Bun has hung before when the client left mid-upload (`auth.ts`'s `requestAt`, SMD-2595). The route already has the body cached.
- *The Next.js route under `recipes/vercel-neon-telegram`.* It runs on Vercel under Node and builds the SDK's own transport, so Bun's idle sweep does not apply.
- *Importing `server-portable/sse.ts` across the tree* instead of copying it. Most servers already import `compat/` that way, but the ticket's Verify forbids an import from `server-portable/`, and the copies follow `auth.ts`'s Edge Function pattern (review pass 2).
- *Moving the core route onto `mcpReply`.* That route starts its watch before the key check and has its own stop-cut line (SMD-2250); one helper with hooks for both is a refactor of its own (review pass 2).
- *A shorter ceiling for the vendored servers.* `kubernetes-deployment` calls its provider with no deadline of its own (and `update-thought-mcp` did, until SMD-1931 retired it), only Bun's fetch cut at 300 s (`server-portable/embed.ts`). So a hung provider now holds the stream for about 5 minutes where Bun used to reset it at about 10 s. The tool hung either way. The bound belongs on those fetches, not on the keepalive: SMD-2692 (review pass 3).
- *Answering a failed body read with 408 before the transport.* If the read rejected before the signal aborted, the transport's 400 would settle the request and the abort after it would log nothing. On Bun 1.4.0 the abort comes first, 20 of 20 measured, so the listener registered before the read logs it, and a guard for the other order would have no failing mutant (review pass 4).
- *A request settled before the keepalive's flush.* A client that closes right after the last chunk, before `flush` runs, could in principle be logged as abandoned. The core route has used the same `onEnd` settle since SMD-1864, and it has not been observed (review pass 5).
- *Parsing the body once and handing it to the transport.* `requestLabel` parses it a second time, as at the core route; that is small beside a provider call (review pass 2).
- *A clause in each server's README.* Nothing changes for an operator: no setting and no command.
