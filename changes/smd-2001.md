## Changelog

A tool call to a vendored MCP server that runs longer than about ten seconds is now answered: the reply's event stream is kept alive by the core server's keepalive frame, and a client that leaves is logged. Before this, Bun closed the stream with no log line. This mattered most for enhanced-mcp's captures, which pay a classification and an embedding (SMD-2001).

## FORK

A vendored MCP server's slow tool call is answered, not reset — the core server's SMD-1864 keepalive and its abandoned-request line reach the thirteen @hono/mcp servers (SMD-2001)

**What changed.**
- `server-portable/sse.ts` gains `mcpReply(req, bodyText, respond)`: the transport's reply goes through `withSseKeepalive`, with a `: keepalive` comment every 5 s up to the 10-minute ceiling. A client that closes the connection before the reply is complete is logged once with `abandonedRequestLine`, named by `requestLabel` (method and tool, never the arguments). Both helpers moved here from `index.ts`, which imports them and re-exports them for its suites. The core route itself is unchanged.
- A byte-for-byte copy of `sse.ts` now sits beside `auth.ts`'s in `extensions/_shared/`, `recipes/_shared/` and `integrations/_shared/`, the three directories that hold MCP servers. `bun run sync-sse` in `extensions/` rewrites them, as `sync-auth` does for `auth.ts`.
- Each of the thirteen servers built on `@hono/mcp`'s `StreamableHTTPTransport` now sends its reply through `mcpReply(c.req.raw, await c.req.text().catch(() => null), () => transport.handleRequest(c))`: the six extensions plus meal-planning's shared server, `ob-graph`, `work-operating-model-activation`, `delete-thought-mcp`, `update-thought-mcp`, `enhanced-mcp` and `kubernetes-deployment`. Hono caches the body, so the transport's own read sees the same text. The Kubernetes image copies `_shared/sse.ts` too, and `integrations/.dockerignore` admits it by name; without that entry the image build fails with `"/_shared/sse.ts": not found`.

**Why.** SMD-1864 measured that Bun 1.4.0 closes a streamed response silent for its idle timeout at the next 4-second sweep, between 8 and 12 s of silence. It fixed only the core server. `@hono/mcp` answers a POST on an event stream it writes nothing to until the tool returns; its own 30 s ping is on the GET stream alone. Every vendored MCP server ran on Bun's defaults (`export default { port, fetch }`, SMD-1799), so a tool call silent past the sweep was reset with no trace. enhanced-mcp's `brain_capture_thought` hit this in practice. The ticket's plan, one wrap in `compat/deno-on-bun.ts`'s `serve`, no longer had a place to go: SMD-1799 removed that file, and SMD-2284 had already moved the keepalive out of `index.ts`.

**Held.** `extensions/test-auth.ts`, in the server job:
- *The probe.* enhanced-mcp's real `brain_capture_thought`, served by `Bun.serve` on the runtime's defaults, with the provider's classification stubbed to answer after 13 s. The call is answered at about 13.0 s with its JSON-RPC envelope after two `: keepalive` frames. A second call whose client gives up at 1.5 s logs one abandoned line naming `tools/call brain_capture_thought`, and the thought's text appears in no log line.
- *Mutants.* Two mutants fail the probe with the original failure, `ECONNRESET` at 12.0 s and no log line: one drops the wrap in enhanced-mcp, the other drops `withSseKeepalive` from `mcpReply`.
- *Guards.*
  - Every `_shared/sse.ts` is byte-for-byte `server-portable/sse.ts`, the tree's copies match the list, and `sync-sse` names each directory.
  - Every held MCP server imports `../_shared/sse.ts` and calls `transport.handleRequest` only inside `mcpReply`.
  - The set of files that build a `StreamableHTTPTransport` equals the set held, so a new server cannot skip it.
- `server-portable/test-server.ts` [17] passes with the helpers in their new home.

**Measured after.** test-auth 847/847 (818 before), and the probe adds about 13 s. test-server 699/699.

**Not taken.**
- *Raising `idleTimeout`.* SMD-1864 declined it with the measurement: it moves the cliff and lets dead sockets linger.
- *A wrapper around each server's whole `fetch`.* It could only label a request by reading a copy of its body, and a copied body is where Bun has hung before when the client left mid-upload (`auth.ts`'s `requestAt`, SMD-2595). The route already has the body cached.
- *The Next.js route under `recipes/vercel-neon-telegram`.* It runs on Node on Vercel, where nothing reaps a silent stream.
- *A clause in each server's README.* Nothing changes for an operator: no setting and no command.
