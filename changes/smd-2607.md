## Changelog

`extract-entities.ts --switch-key` back to a model or prompt version the brain used before now re-extracts the thoughts the other key read. It re-extracted nothing: each thought kept its finished row under that key, so the graph stayed the other model's while `--status` read done. A brain already switched back that way is mended by its next run (SMD-2607).

## Record

`--switch-key` to a key used before returns the rows that key cannot vouch for (SMD-2607)

**What changed.**

- `db/extract-entities.ts`, at the switch. A run with `--switch-key` under a key other than the recorded one records the key, returns some of that key's rows to the pool, and pools every thought with no row under it, in one transaction. The rows returned are the ones the key cannot show are its reading of the text their thought holds:
  - the failed ones, and the leases expired with no live holder;
  - the finished ones another extraction key read since (that key's finished row for the thought is the later one);
  - the finished ones with no lineage row of this key at the thought's fingerprint: a thought edited while the other key was recorded, or a reading that named nothing.

  A finished row its lineage vouches for stays. The recorded key is read again under a lock first, so a switch another run made meanwhile is not made twice.
- `db/extract-entities.ts`, on every run. At its first pass a run returns the finished rows another extraction key read since. A brain that kept one key has none.
- The run prints how many rows it returned and the key it replaced. `--dry-run` and `--status` count what a run would return. `--retry-failed` beside a switch says the switch returned the failed rows.
- A first run, with no key recorded, is as it was. So is a switch to a key the brain never used.
- `db/test-live.ts`, section [10], gains seven rows. `deploy/README.md`'s "Changing the model" drops its warning, and `db/README.md` says what a switch and a run return.

**Why.** `enqueue_thoughts` adds a row only where a thought has none under the key (migration 015). `record_thought_entities` replaces a thought's extracted entities whatever key wrote them. So after A, then B, each thought B read held B's entities and a finished row under A, and a switch back to A pooled nothing.

The record and the return are one transaction because a record that landed alone would read as this key's at the next run.

The every-run rule is there for two reasons. A brain switched back before this change has its key recorded already, so no switch will happen on it. And it costs a brain that kept one key nothing but the read.

**Why not every row.** The ticket's Work asks for every terminal row back, which it calls `reembed.ts`'s rule. That is `reembed.ts`'s rule for a backfill key. Under a model's own key it returns the failed rows and lapsed leases, and a finished row only when its thought is not at the model. Returning every row would send the whole corpus again after a trial of another model over 25 thoughts. This change follows the second shape: it returns what the data says is not this key's.

**Measured.** One scratch Postgres and a stub model that names one entity for key A's model and another for B's. Six thoughts, each standing a different way when the brain comes back to A:

| The thought | Returned at the switch back | Why |
| --- | --- | --- |
| A read it, then B did | yes | another key read it since |
| A failed it, B read it | yes | failed |
| A read it, B failed it | no | A's reading stands at the text it holds |
| A read it and named nothing, B failed it | yes | no lineage row vouches for it |
| A read it, B failed it, then it was edited | yes | its lineage is of other text |
| A read it, B read it, A's row left leased | yes | a lease expired with no holder |

The switch back made five calls, and the graph was A's reading. A plain run after it made none.

Then the key was set back to B by hand, as a switch before this change left it. `--status` counted three finished rows another key had read since, the next run returned and read them with no flag, and the run after that returned none.

Six mutants, the `claims` shard run once with each. Each fails:

| Mutant | Rows of [10] that fail |
| --- | --- |
| The switch returns no row | 3: the switch back makes 2 calls, not 5, and leaves a failed row |
| No every-run rule | 1: the brain set back by hand is not mended (1 call, the graph still A's) |
| No lapsed-lease clause | 2: the counts say 4, not 5 |
| No lineage clause | 3: the counts say 3, and the edited thought and the one that named nothing are not read again |
| Every row returned | 3: the counts say 6, and the thought whose reading stands is sent again |
| The record not read again under the lock | 1: the switch is made a second time |

**Measured after.** The `claims` shard of `db/test-live.ts`, 254 of 254.

**Not taken.**

- Reading a thought's mentions for another extraction key's rows, in place of the claim rows. A reading that named nothing leaves no mention, and the claim rows say which key read last either way.
- Comparing `thoughts.updated_at` with the row's finish time for an edit. A re-tag moves `updated_at` for every thought, so it would return the corpus.

**Follow-ups.**

- The ticket's Problem also says consolidation never judges again after a switch back, since its pool under the old judge key is finished too. Its Work does not ask for that, and this change does not touch `db/consolidate.ts`.
- A thought edited while another key was recorded, and not read under that key, keeps its old reading on a brain switched back before this change: the every-run rule sees only what another key read. A switch made with this change returns it.
