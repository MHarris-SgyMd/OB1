## Changelog

`extract-entities.ts --switch-key` back to a model or prompt version the brain used before now re-extracts every thought. It re-extracted nothing: each thought kept its finished row under that key, so the graph stayed the other model's while `--status` read done (SMD-2607).

## Record

`--switch-key` to a key used before starts that key's pass over (SMD-2607)

**What changed.**

- `db/extract-entities.ts`: a run with `--switch-key` under a key other than the recorded one now does three things in one transaction. It records the key, returns that key's rows to the pool, and pools every thought with no row under it. The rows returned are every finished or failed one, and every lease expired with no live holder. That is the rule `reembed.ts` has for a model change. It reads the recorded key again under a lock first, so a switch another run made meanwhile is not made twice.
- The run prints how many rows it returned. `--dry-run` counts them in what it would do, and `--status` under such a key says how many a switch would return.
- A first run, with no key recorded, is as it was. So is a switch to a key the brain never used: there is no row to return.
- `db/test-live.ts`, section [10], gains five rows. `deploy/README.md`'s "Changing the model" drops its warning, and `db/README.md`'s command list says what the switch returns.

**Why.** `enqueue_thoughts` adds a row only where a thought has none under the key (migration 015). `record_thought_entities` replaces a thought's entities whatever key wrote them. So after A, then B, every thought held B's entities and a finished row under A. A switch back to A pooled nothing and extracted nothing. The record and the return are one transaction because a record that landed alone would read as this key's at the next run, which returns nothing.

**Measured.** One scratch Postgres and a stub model that names one entity for key A's model and another for B's. Three thoughts, one of which A's first run fails:

| Step | Main | This change |
| --- | --- | --- |
| A, then `--switch-key` to B | 3 mentions, B's | the same |
| `--switch-key` back to A | 0 calls; 3 mentions, B's; A's rows 2 finished, 1 failed | 3 calls; 3 mentions, A's; A's rows 3 finished |
| A again, no flag | 0 calls | 0 calls |

Main's column is the mutant below, which is main's behaviour.

| Mutant | Result |
| --- | --- |
| The switch returns no row (the UPDATE's predicate made false) | [10] fails two rows: the switch back makes 0 calls and the graph stays B's, and the run after it exits 1 on the row still failed |

**Measured after.** The `claims` shard of `db/test-live.ts`, 252 of 252.

**Not taken.**

- Returning only the finished rows. A failed row under the earlier key is as old as the finished ones, and `reembed.ts` returns both; `--retry-failed` beside the switch then finds none left.

**Follow-ups.** The ticket's Problem also says consolidation never judges again after a switch back, since its pool under the old judge key is finished too. Its Work does not ask for that, and this change does not touch `db/consolidate.ts`.
