## FORK

FORK.md's index lists numbered changes alone — a fragment needs no FORK.md edit, and a merge of main no longer conflicts on it (SMD-2084)

**What changed.** `scripts/fork-index.ts`'s `renderIndex` takes the numbered files as its only argument, so the compiler holds that a fragment cannot reach the block. In place of the line that listed every fragment by ticket, it renders one fixed sentence, `FRAGMENTS_LINE`, linking the directory: "Changes landed since the last release, if any, are the `changes/smd-*.md` files, numbered at the next cut (SMD-1804)." The sentence is the same before a cut and after it. Check 15 (`index-stale`) compares the committed block with the same render, so a fragment's presence or absence no longer changes what the block must say. The fragment checks (name, line cap, check 16's shape) are unchanged. `scripts/assemble-release.ts` still reads the fragments from the directory, never from the index. After the cut it renders the block from the numbered files it will have written, and that block ends in the same sentence. `changes/README.md`, `CONTRIBUTING.md` and FORK.md's "Versioning" section say that a fragment needs no FORK.md edit and that the index is the release step's to move.

**Why.** The numbered table moves at a release cut, or when a numbered record is retitled. The fragments line was the only part that moved between releases, and it was one line that every fragment-adding PR appended to. Under the strict ruleset (SMD-1856) every PR merges main before its checks run, and each merge conflicted on that line: SMD-1986 resolved it twice, SMD-2059 twice, SMD-1800 three times. The resolution was always the same (take main's copy, re-render), so it was never a decision. Generating the index on main after each merge was not an option: main is PR-only, a workflow commit would need bypass rights, and two merges in a row would race.

**Held.** In check 15's layout self-check, a numbered file added with FORK.md untouched fails `index-stale`, and a new probe holds that a fragment added with FORK.md untouched passes. A mutant that puts the fragments list back into the block fails that probe and the live tree. This PR's own fragment is the live case: FORK.md's index is the same with and without `changes/smd-2084.md`.

**Measured after.** On this branch, `git merge-tree` against a sibling branch off the same base that adds a different fragment reports no conflict. The same pair built on main's renderer conflicts on FORK.md. `bun scripts/assemble-release.ts` (dry run) on this tree lists all sixteen fragments, this one included. On those same files, the new renderer's numbered table is byte-equal to main's.
