## FORK

FORK.md's index lists numbered changes alone — a fragment needs no FORK.md edit, and a merge of main no longer conflicts on it (SMD-2084)

**What changed.** `scripts/fork-index.ts`'s `renderIndex` reads the numbered files and nothing else. In place of the line that listed every fragment by ticket it renders one fixed sentence, `FRAGMENTS_LINE`: "Changes landed since the last release are the `changes/smd-*.md` files, numbered at the next cut (SMD-1804)." Check 15 (`index-stale`) compares the committed block with the same render, so a fragment's presence or absence no longer changes what the block must say; the fragment checks (name, line cap, check 16's shape) are unchanged. `scripts/assemble-release.ts` is unchanged: it reads the fragments from the directory, never from the index, and re-renders the block after the cut from the numbered files it will have written, which never carried a fragments line. `changes/README.md`, `CONTRIBUTING.md` and FORK.md's "Versioning" section say that a fragment needs no FORK.md edit and that the index is the release step's to move.

**Why.** The numbered table moves only at a release cut. The fragments line was the only part that moved between releases, and it was one line that every fragment-adding PR appended to. Under the strict ruleset (SMD-1856) every PR merges main before its checks run, and each merge conflicted on that line: SMD-1986 resolved it twice, SMD-2059 twice, SMD-1800 three times. The resolution was always the same (take main's copy, re-render), so it was never a decision. Generating the index on main after each merge was not an option: main is PR-only, a workflow commit would need bypass rights, and two merges in a row would race.

**Held.** Check 15's layout self-check now includes three probes. A numbered file added with FORK.md untouched fails `index-stale`. A fragment added with FORK.md untouched passes. A fragment removed with FORK.md untouched passes. A mutant that puts the fragments list back into `renderIndex` fails both fragment probes. This PR's own fragment is the live case: FORK.md's index is the same with and without `changes/smd-2084.md`.

**Measured after.** On this branch, `git merge-tree` against a sibling branch off the same base that adds a different fragment reports no conflict. The same pair built on main's renderer conflicts on FORK.md. `bun scripts/assemble-release.ts` (dry run) on a tree with two fragments lists both, and renders the same numbered table as before.
