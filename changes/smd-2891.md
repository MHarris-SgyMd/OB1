## Changelog

With the embedding provider down, `search_thoughts` and the compat `search` answer with the thoughts that hold the query's identifiers and quoted spans, matched exactly, and say so — the endpoint, what happened there, and that `search_thoughts_keyword` finds any word — where they failed with the runtime's raw "Unable to connect" (SMD-2891). Migration 104 adds the query log's arm `literal` for such a search, and the replay gate counts a brain answering that way as failing the search.

## FORK

A search the embedding provider does not answer for is answered by its exact-literal arm, said so and logged as arm literal (SMD-2891)

**What changed** (migration 104).
- **The search operation** (`server-portable/core/reads.ts`'s `runSearch`, which both tools share): when the query's embedding call fails as an outage (`providerDown` — refused, unresolved, timed out, 5xx, 429 — SMD-2888's rule), the same hybrid function is called with no vector. `match_thoughts` finds nothing on `NULL`, so the rows are 017's exact-literal arm alone: the needles `extract_search_needles` takes and its rarity rule, under `prefer_current` (059) and `min_trust` (075) alike. No SQL function changes; the store passes `NULL::vector`. Any other failure — a 4xx, a width mismatch — still fails the search, as it fails a capture.
- **The facts when nothing matched.** The function reports its needle facts only on a row, and without a vector a literal too common to match yields none. The store's new `literalFacts` probes each needle for its 101st matching row exactly as 075's hybrid does (012's escaping, the `OFFSET` that plans it through the trigram index). It runs only where no literal matched an unfiltered search, so each needle is absent there or too common, and no needle says the query has none. The facts keep the hybrid's terms — an absent literal a needle counted 0, a common one in `commonNeedles` alone — and `literalOnly` is null then (unknown, not false). The compat `search`'s empty answer carries them too, worded in its `note`.
- **A literal held outside the search's scope.** An empty answer whose unfiltered probe counts a literal (a filter, `said_by`, `actor` or `min_trust` kept its thoughts out) now says "Held only by thoughts outside this search's filter, said_by, actor or min_trust: X (in N thoughts)", with a vector or without; it said nothing before.
- **The value** carries `vectorFailed: { reason, detail, base }`, present only then, the base as a row prints it (userinfo masked, SMD-2885). `search_thoughts`' text leads with "Semantic search is unavailable — the embedding provider at <base> failed: <detail>. So the query was matched only by its identifiers and quoted spans, exactly — not by meaning", names `search_thoughts_keyword`, calls each hit an "exact match" and drops the "rest by similarity" notes; its typed result carries the marker word. The compat `search` marks each title `[exact match — semantic search unavailable]` (the field every ChatGPT surface hands the model, as `[ingested]` is) and adds the marker word and a `note`. REST answers the core's value (the OpenAPI text says so); the MCP server words it as in-process.
- **The query log** records such a search as arm `literal` (104 widens 059's check; the column's comment says what it is).
- **The replay** (`db/brain-compare.ts`): a reply carrying `vectorFailed` is that brain failing the search, as it was when the search errored; literal rows are left out of a plan and counted apart in the gate, as rows with no arm are, and neither count takes a query the plan replays on another arm.
- The tool descriptions, `db/tier.ts`'s docblock, `evals/utilization.ts`'s arms and `LoggedSearchRow.arm`'s type name the new arm.

**Why.** Measured 2026-10-11 on a scratch brain with a stub provider whose socket was closed (SMD-2887): `search_thoughts` answered `isError` "Unable to connect. Is the computer able to access the url?", Bun's text, though `search_thoughts_keyword` answered in the same moment and the hybrid's literal arm needs no model. The caller was not told a working search existed. The compat `search` — ChatGPT's only search, which cannot reach `search_thoughts_keyword` — failed the same way. SMD-2890 (start degraded rather than refuse) waits on this.

**Not taken.**
- **A coded refusal** (`EMBEDDING_PROVIDER_UNAVAILABLE`, the ticket's first option): the literal arm answers without a model, a search that names an identifier still finds its thought, and the compat `search` has no other tool to send its caller to.
- **The whole query as one substring** for a query with no literal: a sentence occurs verbatim in no thought (017's header), so it would answer nothing while looking like a keyword search; the reply names `search_thoughts_keyword` instead.
- **Logging `keyword` or `hybrid`**: either would replay as something that did not run. `literal` is one value for both functions; whether `prefer_current` was asked is not recorded for it, since no replay takes the row.
- **A provider that hangs**: a search still waits `OB1_LLM_TIMEOUT` before it falls back, as a capture does; a shorter query deadline is SMD-2890's degraded state to decide.
- **A filtered "too common"**: a literal common across the brain but absent from a filter's scope is said too common, with a vector or without — the probe has always been unfiltered.
- **The probe's race**: the facts come from a second statement after the search, so a thought captured between the two can make "No thought contains" or "Held only by thoughts outside" stale for that one answer; one statement for both was not worth a function change.
