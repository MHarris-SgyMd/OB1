## Changelog

With the embedding provider down, `search_thoughts` and the compat `search` answer with the thoughts that hold the query's identifiers and quoted spans — then, those matching nothing, the query as one text — and say so: the endpoint, what happened there, what was matched, and that `search_thoughts_keyword` finds any word. They failed with the runtime's raw "Unable to connect" before (SMD-2891). The compat `search` with nothing found is refused `EMBEDDING_PROVIDER_UNAVAILABLE`, retryable. Migration 106 adds the query log's arm `literal`; the replay gate and the live bench count a brain answering that way as failing the search.

## FORK

A search the embedding provider does not answer for is answered by its exact matches, said so and logged as arm literal (SMD-2891)

**What changed** (migration 106).
- **The rule.** When the query's embedding call fails as an outage (`providerDown`: refused, unresolved, timed out, 5xx, 429 — SMD-2888's rule), `runSearch` (`server-portable/core/reads.ts`) hands the search to `answerWithoutVector`:
  1. the hybrid function with no vector — `match_thoughts` finds nothing on `NULL`, so the rows are 017's exact-literal arm, with its rarity rule, filter, `min_trust` and `prefer_current` (no SQL function changes);
  2. that matching nothing, the trimmed query as one text, case aside, when it is 3 to 64 characters and holds a word the English parser keeps (017's rule for a span) — through the store's bounded `textThoughts`: one scan, filter and floor inside it, that stops at the first 1,001 matching rows and orders them newest first; `prefer_current` ranks no text match, and the reply says so;
  3. otherwise nothing could be matched.

  Any other failure — a 4xx, a width mismatch — still fails the search, as it fails a capture. Plain words (`Kubernetes`) and an identifier too common to match exactly (`GitHub`) are answered by step 2: the ticket's "fall back to keyword search" (pass 4, the maintainer's call).
- **With nothing found, why**, first fact first: a literal held only by thoughts outside a filtered search's scope (the hybrid's unfiltered probe, counted); the text held only outside the scope; each literal absent or too common (the store's `literalFacts`, 075's `OFFSET 100` probe — all a literal can be once no unfiltered search matched it); the text held by none; or that nothing could be matched. The facts keep the hybrid's terms; `literalOnly` is null without a vector.
- **The value** carries `vectorFailed: { reason, detail, base, matched }` (`literals`, `text` or `none`), the base as a row prints it (userinfo masked, SMD-2885). `search_thoughts`' text leads with "Semantic search is unavailable — the embedding provider at <base> failed: <detail>. So …" and what was matched, names `search_thoughts_keyword`, calls each hit an "exact match", says a text's count past the limit (past 1,000: "more than 1000 … the newest of the first 1001 the scan found, not of all"), and drops the "rest by similarity" notes; its typed result carries the marker word. The compat `search` marks each title `[exact match — semantic search unavailable]` and adds the marker word and a `note`; with nothing found it is refused `EMBEDDING_PROVIDER_UNAVAILABLE` (retryable; REST 503 with Retry-After) — an empty list would read as nothing stored where the outage was an error before (pass 4, the maintainer's call) — naming over MCP the endpoint, what was matched and each literal absent or too common (REST's value: the code, the word and `matched`). With the provider up, no reply changes.
- **The query log** records such a search as arm `literal` (106 widens 059's check; the column's comment says what it is).
- **The replay** (`db/brain-compare.ts`): a reply carrying `vectorFailed` is that brain failing the search, as it was when the search errored; literal rows are left out of a plan and counted apart in the gate, as rows with no arm are, neither count taking a query the plan replays on another arm. `db/bench-live.ts` counts such a search degraded, not a latency sample.
- The tool descriptions, `db/tier.ts`'s docblock, `evals/utilization.ts`'s arms and `LoggedSearchRow.arm`'s type name the new arm.

**Why.** Measured 2026-10-11 on a scratch brain with a stub provider whose socket was closed (SMD-2887): `search_thoughts` answered `isError` "Unable to connect. Is the computer able to access the url?", Bun's text, though `search_thoughts_keyword` answered in the same moment and the hybrid's literal arm needs no model. The caller was not told a working search existed. The compat `search` — ChatGPT's only search, which cannot reach `search_thoughts_keyword` — failed the same way. SMD-2890 (start degraded rather than refuse) waits on this.

**Not taken.**
- **A coded refusal for every outage search** (the ticket's first option): the literal and text matches answer without a model, so only the compat `search`'s empty answer is refused; `search_thoughts`' empty answer says why in its text and facts.
- **Logging `keyword` or `hybrid`**: either would replay as something that did not run. `literal` is one value for both functions; whether `prefer_current` was asked is not recorded for it, since no replay takes the row.
- **429 as an outage** (SMD-2888's rule): a rate-limited hosted provider now degrades a search, said so, rather than failing it; nothing reads its Retry-After.
- **The text match's order**: within its first 1,001 matching rows, newest first — not `search_thoughts_keyword`'s occurrence ranking, which would need the whole set. Past 1,000 holders the shown are the newest of the rows the scan met — whichever those are, and not the same twice — and the reply says "not of all".
- **A scope that excludes every holder of a common text**: the scan finds no row to stop at and reads the table — about 0.5 s at 200,000 thoughts, linear, as `search_thoughts_keyword`'s function did; a selective filter or floor takes its index instead (1–2 ms). A statement timeout on the outage path was not added.
- **A search's wall time**: nothing bounds it, and a client's abort does not cancel its statement — so before this change, for `search_thoughts_keyword` and the hybrid's own needle extraction too.
- **The refusal's REST value** is the code, the marker word and `matched`: the endpoint and the literals are the server's words and the caller's input, which `FACTS` keeps out, as for every refusal.
- **"Exact"**: the match is the keyword arm's, case-insensitive and by substring, so `SMD-1` also matches `SMD-12` and a three-letter text (`log`) matches inside a word (`catalog`); the hybrid's own words ("Searched exactly for") are kept, and the span rule keeps out only the shortest and the stopwords.
- **A provider that hangs**: a search still waits `OB1_LLM_TIMEOUT` before it falls back, as a capture does; a shorter query deadline is SMD-2890's degraded state to decide.
- **A filtered "too common"**: a literal common across the brain but absent from a filter's scope is said too common with a vector (the probe has always been unfiltered), and without one when the query's whole text is held nowhere; a text held outside the scope is said held there first.
- **The probe's race**: the facts come from a second statement after the search, so a thought captured between the two can make "No thought contains" or "Held only by thoughts outside" stale for that one answer; one statement for both was not worth a function change.
