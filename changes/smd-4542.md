## Changelog

The session hook (1.11.5) blanks three shapes of password it let through to the brain before: a second keyword (`password: password = <it>`), a getter's default (`password = os.environ.get("X", "<it>")`), and a quoted value whose first word is short (`password="<ab> <cd> <ef>"`) (SMD-4542). The brain's sensitivity table (`db/sensitivity.ts`) copies the rule, so a quoted value like that after a keyword such as `PGPASSWORD` is now marked restricted too; the brain already marked the other shapes, and the plainer spellings, restricted. **Upgrading:** replace the script and its `lib/` together; no config changes.

## Record

The session hook's password rule finds three shapes it let by (SMD-4542)

**What changed** (`recipes/session-capture-hook/lib/secrets.mjs` and `db/sensitivity.ts`, the same literal; 1.11.5). The `password assignment` rule:
- **A second keyword is no value.** The value may not itself be a password keyword followed by `:` or `=`. In `password: password = Tr0ub4dor3x` the match moves to the second keyword and takes its value; before, it blanked the keyword and left the value.
- **A getter's call is stepped over to its default.** In `os.environ.get("X", "<it>")`, `getenv(…, …)`, `env.get(…, …)` or `ENV.fetch(…, …)`, the literal default is the value, when it ends the argument: a literal or a name, then `,` or `)`. Before, `os.environ.get(` was blanked and the default after it sent. A nested call or an expression as the default (`getenv("A", getenv("B"))`, `"<it>" + SUFFIX`) is read as before, the outer call blanked. The call's receiver is dotted names of letters (`os.`, `process.`), so a password glued onto the getter (`<it>getenv(`) is not taken for one.
- **A reference is still a value, as on main.** `process.env.X`, `os.environ[…]`, a getter's call with no default or a short one, and `${…}` are blanked as before. So a line like `password = process.env.X || "<it>"` is still found: refuse refuses it and the model's excerpt is withheld, though under redact the fallback goes out as on main. The one exception is a getter's call whose default is already a whole redaction marker, the argument's last: it is no value, or the second scan would find the call once the first had blanked its default. A marker with more after it in the argument, or one left unclosed, does not make the exception.
- **A quoted value that reads as a token runs to its closing quote** on its line, spaces and all, though its first word is under six characters: it has a digit, no whole word of three letters or more, and does not start at a placeholder's `{`, `<` or `$`. Before, `password="Kp7m Wq2z R9x"` was never found, since the value had to start with six characters. Quoted prose and a placeholder (`"Enter your password"`, `"<your password>"`, `"*** ***"`, `"{{ db_pass_2 }}"`) are read as before. The branch applies only after an opening quote, so unquoted prose with a quote later on its line is read as before too.
- **What is kept:** the six-character floor of an unquoted value, a `[…]` placeholder as no value, and SMD-4506's prose (`Password: XYZ-1234 (reset flow)`), blanked as before and no more.
- **`db/sensitivity.ts`** copies the table rule for rule, and `db/test-live.ts` holds the two equal. The brain's copy already marked the second keyword's and the getter's lines restricted, through the call or the keyword the rule blanked, and a quoted value after `password` or `DB_PASSWORD` through its own password rules. What it newly marks restricted is a quoted value with a short first word after a prefixed keyword: `PGPASSWORD="Kp7m Wq2z R9x"`, `DBPASSWORD=…`.
- **1.11.5**, in `lib/hook.mjs` and `metadata.json`; the README's Testing list names the cases.

**Why.** SMD-3656's review pass 1 (secrets adversary) found all three shapes on main, each sending a password to the brain in a listed prompt or the outcome. The second shape is a realistic code line. The second keyword's case defeated the gate as well: once the keyword is a marker, the second scan is clean.

**Not taken.**
- **`$VAR` and `${…}` as references.** The rule matches case-insensitively, so a `$`-led word reads as a reference in any case, and a real password like `$ecr3tPass` would go out. A `${…}` exclusion sent a default's password (review pass 1). Both stay values, as on main.
- **Values contrived to look like a second keyword** go out where main blanked them, as review pass 1 found:
  - one ending in `password` before a `:` or `=` (`Secretpassword:99`), which the brain reads standard after a prefixed keyword (`PGPASSWORD=Secretpassword:99`) where main read it restricted (review pass 4);
  - a second keyword whose own value is under six characters or starts with `[` (review pass 3).

  The `\b` after the keyword keeps the realistic neighbour blanked: `passwordX9!`.
- **Text that already carries a whole marker as a getter's default** is read as no value in both copies, so the brain reads a stored `PGPASSWORD = os.getenv("X", "[redacted:…]")` standard where main read it restricted. A fallback after it (`… or "<it>"`) is not found there either. Such text has been through a redaction already: from the raw line, main's hook sent that fallback too, and main's brain read the stored line standard (review pass 4).
- **A getter's default in other shapes** goes out under redact as on main, the reference blanked and the default sent; it is still found, so refuse and the model's excerpt hold it back. Only the call's second argument is stepped to, so these are missed:
  - `os.environ.get("X") or "<it>"`, `process.env.X || "<it>"`, `?? "<it>"`;
  - a default named by keyword, whose `default=` is blanked and the value sent;
  - a nested first argument, curly quotes in the call, and `ENV.fetch("X") { "<it>" }`;
  - a nested call or an expression as the default (`getenv("A", getenv("B", "<it>"))`, `"<it>" + SUFFIX`), whose outer call is blanked (review pass 5).

  `System.getenv("X")` without a default is still blanked as the value, as on main. Stepping past a fallback to its literal was not taken: a `||` or `or` chain has many shapes, and each would need its own exclusion and its own second-scan guard.
- **Short quoted prose with a digit** is blanked where main kept it, as review pass 2 found: `"8 to 64"`, `"v2 or v3"`. Telling it from a password with short words would take a dictionary, and such a line beside a password keyword is rare.
- **A value is judged up to its first apostrophe.** The guards read no further, and the blank then runs on to the closing quote, so `"8 to 64 I'd say"` is blanked whole where main kept it (review pass 2). Such a line is blanked more than on main, never less.
- **A quoted value across a line break** is SMD-4543's, the outcome blanked as written.
