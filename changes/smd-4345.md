## Changelog

The MCP endpoint's edge is ready for a 2026-07-28 client: its CORS preflight allows the `mcp-method` and `mcp-name` headers that revision requires, and the request log names `server/discover` and `subscriptions/listen` (SMD-4345, PR 1). No migration. The revision itself is not served yet.

## Record

The MCP edge meets a 2026-07-28 client halfway — the preflight allows its headers and the log names its methods, before the revision is served (SMD-4345)

**Why.** Claude Code 2.1.325 offers the 2026-07-28 revision first: its first request to a server is `server/discover`, carrying that revision's envelope, and it falls back to `initialize` when that is refused (SMD-4344's record). The brain serves the 2025-era revisions alone, so that probe is refused. Two things at the edge were wrong for it whichever revision is served. A browser-hosted client sending a 2026-07-28 POST must send `Mcp-Method`, and `Mcp-Name` with a tool call, and the CORS allow-list named neither, so its preflight failed before the server could answer. And the request log knew the 2025-06-18 method names only, so every such probe was written `rpc: other`.

**The plan, two PRs.** This is PR 1: the edge and a 2026-07-28 client for the suite, with no change to what is served. PR 2 routes a 2026-07-28 request through the SDK's `createMcpHandler` and leaves a 2025-era request on today's wiring, told apart by the SDK's own `isLegacyRequest`. What the plan settled, all but the fourth by measurement on SDK 2.4.0:

- A per-request value given to the handler as `authInfo` reaches the server factory as the same object, so the caller's standing, the call record and the raw arguments reach `buildServer` as they do now.
- With `responseMode: "sse"` the handler answers at once with an event stream, as the 2025-era transport does, so `withSseKeepalive` keeps a long call's stream open and writes the request's line at its end. In the default mode the answer is one JSON body that arrives when the tool ends, with nothing to keep alive.
- A server that declares `tools.listChanged: false` was not sent `subscriptions/listen` by Claude Code 2.1.325 at all (one run, 45 s), and the SDK ends such a stream at once if one arrives. So PR 2 holds no connection open; serving that stream is SMD-4347's decision.
- `ttlMs` stays the SDK's 0 with `cacheScope: private`; a real value is SMD-4346.
- The handler refuses a body past 4 MiB that it reads itself, 413, and applies no bound to a body it is handed parsed. The 2025-era transport refuses a body past the same 4 MiB already, in the same words, so PR 2 lets the handler read the body and keeps one bound for both revisions. One cap aligned across the proxy, this server and the REST core is SMD-2307's. (This bullet first said the 2025-era path had no cap and that PR 2 would hand the body over parsed: PR 2's tests found the transport's bound.)

**What changed (PR 1).**

- `corsHeaders` in `server-portable/mcp-edge.ts` allows `mcp-method` and `mcp-name`. No `mcp-param-*` header is listed: no tool declares an `x-mcp-header`.
- `RPC_METHODS` in `server-portable/telemetry.ts` gains `server/discover` and `subscriptions/listen`, and `deploy/README.md`'s row for the line's `rpc` field says so. The request's span takes its name and `mcp.method.name` from it too, where `other` gave it neither.
- `mcp-server/test-mcp.ts`'s `rpc` helper takes `modern: true`: the request as a 2026-07-28 client sends it, the envelope in `params._meta` and the revision, the method and a called tool's name as headers.

**Not changed.** What `/mcp` serves. A 2026-07-28 `server/discover` with a key is still answered 400 by the SDK's 2025-era transport ("Unsupported protocol version: 2026-07-28"), and the suite now pins that, to be turned over by PR 2. With no key it is refused at the key as a 2025-era request is, before its revision is read.

**Held.**
