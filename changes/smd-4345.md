## Changelog

The MCP endpoint serves the 2026-07-28 protocol revision beside the 2025-era ones: a client that offers it is answered `server/discover`, `tools/list` and `tools/call` with no `initialize`, and gets the same tools, replies, refusals and request lines as before (SMD-4345). The CORS preflight allows that revision's `mcp-method` and `mcp-name` headers, and the request log names its two new methods. No migration, and no client needs to change anything.

## Record

`/mcp` serves the 2026-07-28 revision beside the 2025-era ones — a request with the envelope goes to the SDK's handler, any other to the transport it always had (SMD-4345)

**Why.** Claude Code 2.1.325 offers the 2026-07-28 revision first: its first request to a server is `server/discover`, carrying that revision's envelope, and it falls back to `initialize` when that is refused (SMD-4344's record). The brain serves the 2025-era revisions alone, so that probe is refused. Two things at the edge were wrong for it whichever revision is served. A browser-hosted client sending a 2026-07-28 POST must send `Mcp-Method`, and `Mcp-Name` with a tool call, and the CORS allow-list named neither, so its preflight failed before the server could answer. And the request log knew the 2025-06-18 method names only, so every such probe was written `rpc: other`.

**The plan, two PRs.** PR 1 was the edge and a 2026-07-28 client for the suite, with no change to what is served. PR 2 routes a 2026-07-28 request through the SDK's `createMcpHandler` and leaves a 2025-era request on today's wiring, told apart by the SDK's own `isLegacyRequest`. What the plan settled, all but the fourth by measurement on SDK 2.4.0:

- A per-request value given to the handler as `authInfo` reaches the server factory as the same object, so the caller's standing, the call record and the raw arguments reach `buildServer` as they do now.
- With `responseMode: "sse"` the handler answers at once with an event stream, as the 2025-era transport does, so `withSseKeepalive` keeps a long call's stream open and writes the request's line at its end. In the default mode the answer is one JSON body that arrives when the tool ends, with nothing to keep alive, unless the tool sends a message of its own first, which turns it into a stream.
- A server that declares `tools.listChanged: false` was not sent `subscriptions/listen` by Claude Code 2.1.325 at all (one run, 45 s), and the SDK ends such a stream at once if one arrives. So PR 2 holds no connection open; serving that stream is SMD-4347's decision.
- `ttlMs` stays the SDK's 0 with `cacheScope: private`; a real value is SMD-4346.
- The handler refuses a body past 4 MiB that it reads itself, 413, and applies no bound to a body it is handed parsed. The 2025-era transport refuses a body past the same 4 MiB already, in the same words, so PR 2 lets the handler read the body and keeps one bound for both revisions. One cap aligned across the proxy, this server and the REST core is SMD-2307's. (This bullet first said the 2025-era path had no cap and that PR 2 would hand the body over parsed: PR 2's tests found the transport's bound.)

**What changed (PR 1).**

- `corsHeaders` in `server-portable/mcp-edge.ts` allows `mcp-method` and `mcp-name`. No `mcp-param-*` header is listed: no tool declares an `x-mcp-header`.
- `RPC_METHODS` in `server-portable/telemetry.ts` gains `server/discover` and `subscriptions/listen`, and `deploy/README.md`'s row for the line's `rpc` field says so. The request's span takes its name and `mcp.method.name` from it too, where `other` gave it neither, and the `http.server.request.duration` histogram gains those two values of `mcp.method.name`, such requests leaving its `ob1.rpc="other"` series. The set is still the allow-list's: no caller's string reaches a label. No dashboard or alert here reads either.
- `mcp-server/test-mcp.ts`'s `rpc` helper takes `modern: true`: the request as a 2026-07-28 client sends it, the envelope in `params._meta` and the revision, the method and a called tool's name as headers.

After PR 1 alone a keyed 2026-07-28 `server/discover` was still answered 400 by the SDK's 2025-era transport, and the suite pinned that for PR 2 to turn over.

**What changed (PR 2).**

- `mcp-server/app.ts`'s route asks the SDK's `isLegacyRequest` which family a request speaks, once the caller is known. A request carrying the 2026-07-28 envelope goes to one `createMcpHandler` for the app (`legacy: "reject"`, `responseMode: "sse"`); a well-formed 2025-era request goes to a `WebStandardStreamableHTTPServerTransport` built for it, as before. What the rule cannot place goes to the handler too, as the SDK asks: a request that mixes the two revisions' header and body, a JSON body that is no JSON-RPC message, a body past the bound.
- `buildServer` takes the family. The 2026-07-28 server declares `tools.listChanged: false`; the 2025-era one declares what the SDK declares, as it did.
- The handler is given, as `authInfo`, the function that builds this request's server, so that server holds the caller's standing, call record, raw arguments and tool-call count as a 2025-era request's does. No token and no identity is put in it.
- Each path reads the request's body itself, under the SDK's 4 MiB bound.
- A fault the handler catches, a throw building the server among them, it answers 500 and tells only its `onerror`. The route keeps that error for the request that is running (an `AsyncLocalStorage`) and, when the answer is a 500, throws it into the catch a 2025-era request's fault meets: this server's 500, one line in the log, the fault on the trace. An error for a request the handler refused (a 4xx) is let go.
- The handler keeps its own 15 s keepalive, as the 2025-era transport does, so `server-portable/sse.ts`'s account of a stream past its bound holds for both.
- `mcp-server/README.md` gains "The revision" under how a request is answered, and `docs/mcp-sdk-v2-migration.md` a section on serving 2026-07-28.

**Not changed.** A well-formed 2025-era request: the same transport, server, replies, refusals and lines. The key's refusals, which come before the revision is read. What a client must do: nothing. Nothing makes a connected client fetch the tool list again: a 2026-07-28 client told `listChanged: false` is as stale as a 2025-era one when a key's tools change, until SMD-4347. The request's line does not say which revision it spoke.

**Changed for a request that is not well formed.** The handler's answers stand where the transport's did. A 2025-era `initialize` sent under a `MCP-Protocol-Version: 2026-07-28` header was served and is refused 400 `-32020`; so is a request with the envelope and no such header. A JSON body that is no JSON-RPC message (`{}`, `null`, a batch with one bad element) is 400 `-32600` where it was 400 `-32700`; `[]` is 400 where it was 202. The first is a row in [9b]; the others are the independent review's measurements against the app. The SDK's own client sends no 2026-07-28 header on its fallback `initialize`.

**Not tested.** The entry's stop with a 2026-07-28 call in flight (its 2025-era row, [8f], shares the route's code for it). One mutant survives: the handler left to serve 2025-era traffic itself, which the route never sends it.
