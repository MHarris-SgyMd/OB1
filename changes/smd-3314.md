## Changelog

`capture_thought` takes a `client_key`: a UUID, by convention the thought's id on the brain where the write was first made, when a client copies the write to another brain. The copy keeps it, one thought per key (migration 112), and `update_thought`, `delete_thought` and the `supersedes` and `derived_from` of either accept it wherever they take an id: the thought with that id, else the one keeping that key. A key that names a thought already returns it and writes nothing. Only a key that can read may send one. `metadata.client_key` is the server's now: a caller's `metadata` or `metadata_patch` naming it is refused. **Upgrading:** migration 112 refuses, by name, rows that already share a `metadata.client_key` value (a caller's metadata could set the key until now); keep one per value and re-run (SMD-3314).

The session-capture hook copies your writes to another brain: with a `connector` on the brain your Claude Code connector writes to and a `write_key` on each brain that should receive copies, an async `PostToolUse` hook (`--print-hook claude-code --fan-out`) repeats each capture, edit and delete that landed through that connector, in order, through each brain's own write key and queue, a capture under the first brain's id as its `client_key`. A write through any other connector (the canary's own) is not copied. **Upgrading:** nothing unless you want copies; the receiving brain needs migration 112 (`--check` says) (SMD-3314, its second PR).

## FORK

Your writes reach the canary too: a copied write names its thoughts as the first brain did (`client_key`), and the session hook copies each write (SMD-3314)

**What changed.**
- **Migration 112:** a unique partial btree on `thoughts ((metadata->>'client_key'))`, where the value is not null.
  - Rows already sharing a value are refused by name before the build.
  - An index of another shape, on another table, or INVALID under its name is refused naming the statement that clears it (100's rule).
  - A key is set once: a trigger (`ob1_client_key_set_once`) refuses a write that would give a keyed row another key, in the write's own transaction so its event goes with it. Taking a key away is not refused.
  - Needs nothing past 001; a re-apply is a no-op; no grant moves.
  - The key lives in metadata, not a column: the event carries the row's metadata (055, 060), so a replay keeps it with no change to the projector.
- **`capture_thought`'s `client_key`** (`core/writes.ts`, `core/schemas.ts`), for a key that can read:
  - One read (`thoughtsNamed`) before the model calls resolves the key and every pointer. A key naming a thought (as its id or its key) returns it: `keyed: "matched"`, nothing written, no model call — unless that thought holds this very text, when the capture goes on as a re-capture of it without the key (`recaptured`), so the copy merges what the first brain's re-capture merged.
  - Otherwise `keyAtText` reads the row already holding the text: a row keeping another key keeps it (`held`, the key not sent), else the key is stamped into the payload's metadata (`recorded`), a re-capture's merge included.
  - A write that meets 112's index (a copy racing under the same key) is answered as a match.
  - `supersedes` and `derived_from` resolve by id, else by key.
  - A capture-only key is refused the key (`REFUSED_CLIENT_KEY_SCOPE`), and its pointers resolve by id alone, as before: the match would be an existence oracle (SMD-1298). A non-UUID is `REFUSED_CLIENT_KEY_SHAPE`.
- **`update_thought` and `delete_thought`** resolve their `id`, and an edit its `supersedes`, the same way (`targetNamed`), and say when a key reached the thought (`byClientKey`). A `metadata_patch` naming `client_key` is refused (`REFUSED_METADATA_SHAPE`, `reserved_key`).
- **`client_key` joins `RESERVED_META`**, so a capture's `metadata` cannot set it.
- **The store:** `thoughtsNamed(names)` (the id first, then the key's arm over 112's index) and `keyAtText(content)` (003's fingerprint).
- **Replies:** MCP words each outcome (`Already captured — id …`; the held note; `, named by its client_key …`). The two refusals have REST statuses 400 and 403. `heldKey` and `byClientKey` join render.ts's ID_KEY, so the guard holds them to a uuid rather than nulling them as non-tokens.
- `server-portable/README.md` "A write copied to another brain: `client_key`"; `db/README.md` migration 112's paragraph, the count (112) and `\d thoughts` (thirteen indexes).

**Why.** The canary is a brain of its own, fed the same inputs as stable from the sources themselves (SMD-2872). The maintainer chose a client fan-out and an idempotency key on 2026-10-26. A thought captured on each brain separately has two ids, and the fan-out (this ticket's next PR) repeats an edit or a supersession by the id the first brain gave it. With the key kept on the copy, each brain resolves that one id to its own thought, and no client keeps a map.

### PR 2: the session hook copies your writes

**What changed** (`recipes/session-capture-hook/session-capture.mjs`):
- **The config.** A brain in a `brains` list may name its `connector` (the MCP server whose writes reach it directly) and carry a `write_key` or `write_key_file`. A connector that is no server's name, a write key given twice or empty, and one connector named for two brains are refused, no key quoted.
- **`fanOutPlan`.** A `PostToolUse` of `mcp__<server>__(capture_thought|update_thought|delete_thought)` is copied when a brain names `<server>` as its connector, to every other brain with a write key; a write through any other server is that brain's alone. The result is read in every shape it may arrive in (`resultText`), since an MCP tool's `tool_response` is undocumented, and copied only when it is the tool's success (`Captured as`, `Updated`, `Deleted`) with no refusal's or fault's code — never a capture its key matched on the first brain, which wrote nothing. A capture is copied with its own arguments and `client_key` = the first brain's id (`structuredContent.id`, else the id after the reply's type); an edit or delete by the id the first brain answered, an edit without `if_unchanged_since`.
- **The queue.** Each receiving brain has its own `writes/pending/` and one drain at a time: a lock made whole (written, then linked into place), renewed before each copy, taken back from a dead holder or one silent fifteen minutes by renaming it aside and judging it again, and checked by each drain before each copy. `postWrite` posts through the write key:
  - NOT_FOUND is skipped and logged;
  - an unknown pointer, a supersedes that would close a loop, or metadata the brain refuses is dropped and the write sent again;
  - a transient, a fault (`FAILED`), an unreachable brain, or a key that cannot write is kept, and stops the queue so nothing lands out of order;
  - anything else goes to `writes/dead/`, and so does a copy kept past a week.
- **The hook.** On `PostToolUse` it queues and drains (a detached child, or in process under `OB1_SESSION_CAPTURE_SYNC=1`), and exits 0 (1 under the sync switch when a copy did not land), logging a queue or drain that throws. Other hook runs drain a held queue at most every five minutes, and a session's end at once. `--drain-writes --brain <name>` drains by hand. `--check` names the connector and its receivers, and checks each receiver's write key and that its `capture_thought` takes `client_key` (a server before 112 fails it), with the queue's counts and its oldest copy's age. `--print-hook claude-code --fan-out [--connector <server>]` prints the async, anchored `PostToolUse` entry; Codex is refused.
- README "Copying your writes to another brain" and step 4's fan-out hook; metadata 1.6.0.

**Why.** PR 1 gave a copied write a way to name its thoughts on the second brain. This is the client that copies, keeping PR 1's contract: the first brain's id as `client_key`, no `if_unchanged_since`, unknown pointers dropped, the first brain's order.

**Held.** `test-session-capture.mjs` [12], 48 assertions, against a fake canary that keeps `client_key` and resolves names as the server since 112 does: the config and its refusals; a capture copied under the first brain's id with its own arguments, logged without its text; the id from each result shape, from `structuredContent`, and never from a note or a type; an edit and a delete copied by the id answered, landing on the copy; nothing copied from the canary's own connector, a read, a refusal, a fault, a matched capture or an id-less reply; the canary away, then landing in order; a kept copy holding the queue; NOT_FOUND skipped; unknown pointers, a loop and refused metadata dropped; a fault and a capture key holding the queue; an invalid and a week-old copy given up; two drains at once, gated so they provably overlap, each copy once; a live lock left alone, a stalled and a dead one taken back, one taken back mid-drain; the held stamp and a session's end; `--check`; `--print-hook --fan-out`; the detached child. The 725 assertions before it pass unchanged. Mutants (each dropping one mechanism) killed: 14 at build, 8 in pass 1 (plus 2 that died after a failed assertion), 8 in pass 2.

**Not taken.**
- A late capture after its thought's delete brings it back: the copying client's per-brain order prevents it, and an audit read before every keyed capture would cost every copy.
- A key's insert can take its event seq before the delete that freed the key: nothing rebuilds thoughts from events today; the ADR's rebuild step should take a key lock.
- Two parallel tool calls editing one thought may queue opposite to stable's order, and a wall-clock step back can swap copies seconds apart: dependent writes are a model turn apart.
- A copied delete the canary refuses as cited goes to dead; an unreadable `write_key_file` stops the config as an unreadable `key_file` does.
- A stable capture of text the canary alone holds names that canary thought by stable's id (the server's rule: one text, one thought); the log says so.
- Mutants that survived: a stale take-back by unlink in place of the rename (each drain's check before each copy still stops the loser), and the lock made empty then written (its race reproduced on every run while the case was built and not in the mutant run; the link makes it impossible by construction).
