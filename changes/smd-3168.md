## Changelog

`main`'s ruleset requires one check, "Fork Checks passed", in place of every Fork Checks job by name. That job needs every other job and fails unless each one succeeded, so a job added, renamed or split no longer needs the ruleset re-applied before its merge (SMD-3168).

## FORK

One required check that needs every job, so the ruleset names no job but it (SMD-3168)

**What changed.**
- **`.github/workflows/fork-checks.yml`:** a new job, `fork-checks-passed` ("Fork Checks passed").
  - It `needs:` all sixteen jobs and runs `if: always()`. A job whose needs failed would otherwise be skipped, and GitHub reads a skipped required check as passing.
  - Its one step reads `toJSON(needs)` with jq. It fails, naming each job and its result, unless every job succeeded or was skipped where `MAY_SKIP` names it. When it passes, it logs how many succeeded and how many were skipped. `MAY_SKIP` is `commit-lint`, whose own `if:` runs it on pull requests and the merge queue alone.
  - The two comments that put a step in a job "because main's ruleset requires it" no longer give that reason.
- **`.github/rulesets/main.json`:** requires that one context, still pinned to the Actions app, with strict up-to-date on. It drops the sixteen job names.
- **Check 20** (`scripts/check-fork-consistency.ts`) holds the record to the one context: anything else required is reported, and so is the context missing. It holds the aggregate job:
  - present under its name, `if: always()`, no strategy;
  - needing every other job in the workflow and nothing else;
  - one step that reads NEEDS from `toJSON(needs)`, whose `run:` is `AGGREGATE_RUN` verbatim;
  - on `ubuntu-24.04`;
  - `MAY_SKIP` spelled as `AGGREGATE_MAY_SKIP` in the checker records it (commit-lint), and those being exactly the jobs that have an `if:` of their own, none of which another job needs. Making a job skippable is then a reviewed change to check 20. A skippable job with dependents is refused: a skipped need skips its dependents, and with those skippable too a run would pass having run nothing. SMD-2435's `changes` job must therefore stay unskippable;
  - no job it needs setting `continue-on-error`, or calling a reusable workflow. A job that ignores its own failure reaches `needs` as a success, and a called workflow's jobs are out of check 20's sight;
  - no key on the job, the step or its env beyond the few allowed (`timeout-minutes` and a step `id` are allowed; a timeout is a failure). So no `continue-on-error`, step `if:`, `shell:`, `defaults:` or `PATH` can turn a failed verdict into a passing job;
  - no job in any workflow under `.github/workflows/` whose name could report as it. That covers carrying it in any case, or rendering as it once each `${{ … }}` is read as any text (a matrix value, `format()`, the PR's title). The match is a glob read with `indexOf`, never a RegExp built from the name. `Tests (${{ matrix.shard }})` can't, and is allowed.
- **Check 20 runs `AGGREGATE_RUN` itself:** under `bash -eo pipefail` with jq, on ten cases:
  - every job succeeded;
  - a job failed;
  - a job was cancelled;
  - a job `MAY_SKIP` doesn't name was skipped;
  - commit-lint was skipped, and commit-lint failed;
  - a skipped job whose name contains `MAY_SKIP`'s, or is contained in it;
  - an empty result;
  - a NEEDS that does not parse.

  It looks for jq first, so a missing jq is named rather than read as every case failing. So the step's verdict is tested, not only its text.
- **Check 20 lifts the matrix and expression-name bans.** The record names no job but the aggregate. That unblocks SMD-3169 and simplifies SMD-2435.
- **`FORK.md`:** the protected-`main` section describes the one check.

**Why.** Every add, rename or split of a job was a ruleset change:
- SMD-3048 added three test-live shards, SMD-3051 split the full-stack job, and SMD-3152 renamed "Portable server". Each needed the maintainer's `gh api -X PUT …/rulesets/22189960` from the branch, after CI was green and just before the merge.
- While that PUT was live and the PR unmerged, every other open PR waited on the new names until it merged main.

**Merging.** This PR still runs all sixteen jobs under their names, so the live ruleset, which still lists them, is satisfied and the PR merges as any other. Then, from `main`:

```
gh api -X PUT repos/MHarris-SgyMd/OB1/rulesets/22189960 --input .github/rulesets/main.json
```

- From then on the live ruleset asks for "Fork Checks passed" alone.
- An open PR that has not merged this `main` reports no such check and waits until it does, which strict up-to-date makes it do anyway.
- Putting the previous file back restores the sixteen names.
- This is the last ruleset PUT a job change needs.

The walkthrough read GitHub's documentation and this repository's own check runs. Its findings:
- `needs` results are success, failure, cancelled or skipped, and anything else fails the step.
- `always()` runs when the run is cancelled, and reports failure there.
- A skipped required check passes.
- Of two check runs with one name on a commit, the latest wins: PR 440's head carries a failed and a later passed "Portable server (Bun + Workers)", and it merged.
- "Re-run failed jobs" re-runs the aggregate with them.
- Merging first, then the PUT, leaves no window for a red merge.

**Tidied after the last pass.** `scripts/check-fork-consistency.ts` drops `expressionEnd`, a helper from SMD-1799 that nothing calls.

**Not taken.**
- **Shapes that block every PR rather than pass one.** None of these lets a red job merge; each holds every PR until it is undone:
  - a merge key (`<<`) or a duplicated job key, which Bun's YAML reader resolves and GitHub refuses;
  - a `needs:` cycle;
  - a `paths-ignore`, `types` or `branches` filter on `pull_request`, or that trigger removed.

  GitHub shows an invalid file on the run, and a filtered-out check stays pending. Each was the same under the sixteen names. SMD-2435's docs-only skip must filter inside the workflow for this reason.
- **The same as under the sixteen names:**
  - a step-level `continue-on-error` in a needed job (check 34 holds it for the suites' steps);
  - a status or check run posted with the workflow's own token;
  - a `pull_request_target` trigger.
- **The workflow's own `env:` and `defaults:`.** These reach the aggregate's step, so a `BASH_ENV` or another default shell there could change what the verdict runs. They reach every job at once, which makes this the next item's case.
- **A PR that edits its own workflow can make the check pass.** A `pull_request` run uses the PR's own workflow files, so a PR could edit the aggregate, or add a workflow of its own with a job of that name. That was equally true of the sixteen names: a ruleset can't tie a check to a workflow file, and required workflows are an organisation feature. What holds is that only the maintainer merges and the diff to `.github/workflows/` is read.
- **A skipped commit-lint on another kind of run.** A `workflow_dispatch` run, or a push run on a `siggymd/**` branch, skips commit-lint, and its aggregate passes as the latest check on that commit. The old "Commit messages" check, skipped, did the same; SMD-2249 drops the `siggymd/**` trigger.
- **`if: ${{ !cancelled() }}` in place of `always()`.** A cancelled run would then skip the aggregate, and a skipped required check passes.
- **Putting the verdict in a script under `.github/ci/`.** The job would need a checkout before its one step. Held inline and run by check 20, it is tested all the same.
- **Letting any job skip.** A job whose `if:` is wrong would then skip into a pass. Only the jobs `MAY_SKIP` names may skip, and check 20 holds that list to the jobs with an `if:`.
