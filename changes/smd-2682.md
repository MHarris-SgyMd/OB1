## Changelog

The brain now says what became of the findings board-sync posted to the board: `db/board-findings.ts --report` lists each ticket pair and word as accepted (its proposal accepted, or the board linking the two tickets since), rejected, withdrawn, open, or unanswered after 30 days (`--days` changes it), and `brain_info` (so keyed `/health` and `GET /v1/brain`) gains a `Findings` row with the same counts. The acceptance rate is accepted over accepted, rejected and unanswered, with the median time from the post to the answer, read from the brain alone, never Linear (SMD-2682).
The server group gains `SELECT` on `board_findings_posted`; a role granted before needs `--grant` again, and without it the row says the table is not readable.

## FORK

What became of each finding posted to the board, and the acceptance rate, from the brain alone (SMD-2682)

**What changed.**
- **One read, `server-portable/brain-info.ts`'s `FINDING_OUTCOMES_SQL`.** It returns one row per `board_findings_posted` row (087), with three lateral reads:
  - **The earliest active Linear link** between the two tickets, in either direction, held by any of their rows (a section row included): 079's `child_of`, `blocks`, `blocked_by` and `relates_to`, plus `duplicate_of`. This is the rule the finding was posted under, read now. It probes 053's link-target index.
  - **The named proposals (outdates)** by status, with the first acceptance's and the last rejection's `reviewed_at`.
  - **Whether a relation of the word still stands (relations)** where a named facet stood. A re-judge at the same word closes the facet and writes its successor on the same two thoughts (084's one active relation per pair), so the successor counts.
- **`findingOutcome` (pure)** decides each row; the first match wins:

  | | outdates | relation |
  |---|---|---|
  | accepted | a named proposal accepted | the board links the pair |
  | rejected | none pending, one rejected, a link notwithstanding | — |
  | accepted | the board links the pair | |
  | open / unanswered | a proposal pending (unanswered past 30 d) | the relation stands (unanswered past 30 d) |
  | withdrawn | the rest: stale or gone | the judge no longer says it |

  `findingsValue` sums the rows into `{ posted, comments, found, accepted, rejected, withdrawn, open, unanswered, windowDays, medianAnswerS }`. A comment is a distinct (pair, `posted_at`), as `postedToday` counts. `found` rows are another poster's, counted apart and never in the rate. `acceptance` returns the rate's two terms.
- **`brain_info`.** `DatabaseFacts.findings` is a stats read, as `relations` is:
  - `board_findings_posted` joins the catalog's known tables, so before 087 the field is null with no `unread` entry;
  - it is not tried after a lock refused on a table it joins;
  - a refused or malformed answer is unread, naming the table, while the rest stands.

  The `Findings` row comes after `Proposals`. The tool's description names it.
- **`db/board-findings.ts --report [--days N]`.** It prints the summary, then each row this brain posted (newest first, with the time to its answer), then the `found` rows apart. It reads only: it needs no key, no egress and no write. `--dry-run` and `--cap` with it, `--days` without it, and a zero window are each refused with exit 2. It imports the read and the outcome from `brain-info.ts`, so the CLI and `brain_info` cannot disagree.
- **Grants.** The `server` group gains `SELECT` on `board_findings_posted`, since 087.
- **Docs.** `db/README.md` has the findings section's "What became of it" and the grants row; `server-portable/README.md` has the `Findings` row, the JSON field and the test count.

**Why.** SMD-2682's "done when" is a month of posted findings with a measured acceptance rate: whether the brain's suggestions are worth a maintainer's attention. SMD-2681 posts and records them, but nothing measured them, and its Verify asked for a hand count. Everything the rate needs is already in the brain: the record, the proposals' reviews, the links board-sync brings back and the relations the judge keeps. So no migration and no Linear request is needed.
