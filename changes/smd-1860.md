## Changelog

A release job: on a `v<X.Y.Z>` tag, `.github/workflows/release.yml` publishes `ob1-server` and `ob1-migrate` to GHCR, brings the stack up from the pulled images under the full-stack job's checks plus preflight's schema-version row, and creates the GitHub release with a compose overlay pinning both images and Ollama by digest, the cut's change files and the review yield; the migrator is an image (`db/Dockerfile`), Ollama is pinned by tag in `deploy/compose.yaml`, and a release cut is two commits the assembler now orders (SMD-1860).

## FORK

A release publishes what it names — the two images, a digest-pinned compose, the change files — and a cut is a tree that already says its version (SMD-1860)

**What changed.** `.github/workflows/release.yml` runs on a `v[0-9]*` tag: it
reads the tree through `scripts/release-artifacts.ts facts`, builds
`server-portable/Dockerfile` and the new `db/Dockerfile` for linux/amd64 and
linux/arm64, pushes both to GHCR as `ghcr.io/<owner>/ob1-server:<X.Y.Z>` and
`ob1-migrate:<X.Y.Z>` with OCI labels, resolves `deploy/compose.yaml`'s Ollama
tag to a digest, renders `compose.release.yaml` (the two images by tag and
digest, Ollama by digest, one anchor as in the base file), pulls the images
back, brings the stack up from them with `--pull never` under the `Full stack,
no Supabase` job's `.env` and its four log lines plus a fifth — preflight's
`schema version <version> · highest migration NNN` row — then `smoke.sh` and the
no-Supabase-binary check, and last creates the GitHub release: the CHANGELOG
section, the run commands, the digests, the change files the cut numbered, and
`scripts/mechanism-yield.ts`'s table since the previous tag, with the overlay,
`compose.yaml`, `env.example`, the yield and the change files as assets. On a
pull request that touches what it builds from, and on `workflow_dispatch`, the
same job runs as a rehearsal: both platforms built and discarded, amd64 loaded,
the stack from the loaded images, the overlay and notes kept as an artifact,
nothing published. `db/Dockerfile` is the migrator as an image — `migrate.ts`,
`config.mjs`, `version.mjs`, the migrations and `releases.json`, no install —
and `deploy/compose.yaml`'s `migrate` builds from it instead of mounting the
checkout's `db/` into a stock Bun image; the server image now carries
`releases.json` too. Ollama is one anchor, `x-ollama-image`, pinned to
`ollama/ollama:0.34.3` for both services. `scripts/assemble-release.ts` records
the change numbers a cut assigned (`changes: [first, last]` in `releases.json`)
and refuses `--write` on a tree whose `FORK_VERSION` or highest migration does
not yet say the version, printing the same two lines as the dry run's next
step; `db/version.mjs` gains `schemaVersionValue`, the one reader check 17d and
the assembler share. `scripts/check-landing.ts` reads `releases.json` written
as a landing's record, so the cut PR — a migration added, fragments deleted —
passes with no fragment of its own.

**Why.** Nothing published a runnable artifact: an operator built from a
checkout, `deploy/compose.yaml` ran `ollama/ollama:latest`, and the migrator
was a bind mount of `db/`, so no machine without a checkout could apply a
release's schema. SMD-1804's assembler said to add the version migration
*after* `--write`, which left a brain one migration past the release it named
until the next cut — the range must end on the migration that writes the
version. And the release job's checks had to be able to fail before anything
was published: the release object is created last, so a run that stopped
half-way leaves images with no release naming them, never a release naming
images the stack did not come up from.

**Held.** `release-artifacts.ts --self-check` (run first in the job): the
facts for a matching tag, manifest, tree and pin; twelve refusals, one problem
each naming it — a tag without the `v`, a tag naming another version, an
empty manifest, `FORK_VERSION` not bumped, a migration past the range, a
fragment left in `changes/`, a numbered file missing, an entry without
`changes` or without a range, a tag off `main`, no `origin/main`, no Ollama
pin; a rehearsal on an unreleased tree; the overlay parsed back (tag@digest,
Ollama by digest on both services, the rehearsal form by tag alone); the
changelog section reader, including the last section's link foot and
`1.0.0` against `1.0.0-rc.1`; the notes; GITHUB_OUTPUT's multi-line form.
`assemble-release.ts --self-check` reads the version migration through the
shared reader; the dry run on today's tree prints the two next steps. Check
15 held the probe fixtures to change files that exist (twice). The landing
check's probes gain a release cut (passes), a deleted manifest and a manifest
elsewhere in the tree (refused). check-fork, tsc over `scripts/`, actionlint
1.7.7 with shellcheck over both workflows.

**Measured after.** Locally, on this Mac: both images built from the root
context (the migrate image lists `config.mjs migrate.ts migrations
version.mjs`, 47 migrations, `/releases.json`); the overlay rendered against
them with Ollama's real digest; a stack under its own project name on port
8020 came up from the images with `--pull never`, `migrate` applied 47,
the server's log carried the four `Full stack` lines and `schema version
0.0.0+upstream.9543c29 · highest migration 047`, `smoke.sh` passed 9 of 9,
no Supabase binary. The PR's own `Release` rehearsal run is the job's proof on
the runner; a tag's run — the pull from GHCR, the release object — waits for
the first cut.

**Not taken.** A merge of `image:` into `compose.yaml` itself
(`ghcr.io/…:${TAG:-dev}`) — the mount had to go anyway, and an overlay keeps
the base file the one every check reads. A standalone rendered compose as
the asset — `config` drops the comments that document the knobs, and the
base file is attached beside the overlay instead. Provenance attestations —
they add an `unknown/unknown` entry to GHCR's tag list beside the two
platforms. A `release: published` trigger — the job creates the release, so
a red run leaves none. Native arm64 runners with a manifest merge — QEMU
first; if the arm64 `bun install` proves slow or unstable under emulation,
that is the follow-up. A composite action sharing the stack-up lines with
`fork-checks.yml` — the lines are copied verbatim, and the duplication is
named here. The first cut itself — publishing is the owner's action.
