## Changelog

The server stops on SIGTERM: it stops accepting, finishes the requests in flight for up to 8 s, closes its pool and exits 0, where every `docker stop` used to wait out the 10 s grace period and kill it mid-request. A stop during preflight ends the container at once, and the Kubernetes image stops the same way (SMD-2250).

## FORK

The server and the Kubernetes image stop on SIGTERM, finishing what is in flight — no more 10 s kill on every stop (SMD-2250)

**What changed.**
- **`server-portable/shutdown.ts`, new.** On SIGTERM or SIGINT it logs `SIGTERM: no longer accepting; N requests in flight`, and calls Bun's `server.stop()`. On Bun 1.4 that refuses new connections, closes idle keep-alive sockets at once, and resolves when the last response body ends, a tool call's SSE stream included (measured). Then it closes the database pool (bounded at 1 s), logs `stopped in X s; database pool closed; exit 0` (`no database pool was opened` when no request opened one) and exits 0.
  - **The bound.** The wait is bounded at 8 s (`DRAIN_BOUND_MS`, under Docker's 10 s default). A call still running then is closed unfinished with a line naming how many, and the exit is 1.
    - `stop(true)` is called, not awaited. Bun closes the sockets at once, but its promise waits for every handler, and one stalled before returning a response would hold the exit until the kill.
    - The call's own close line says `request cut off by the server's stop`, not SMD-1864's `abandoned by the client … runs to its end`.
  - **A second signal** cuts the wait short, the drain's or the pool close's.
- **`index.ts`.** Bun serves the default export itself and passes the `Server` only to the fetch handler, as its second argument. So the export's `fetch` now keeps the first one it sees (`isStoppable`, which a Workers `env` is not). Before any request nothing can be in flight, and a stop exits at once.
  - The handlers go in only when `import.meta.main` under Bun. Workers has no signals, and the suites that import the module keep their own.
  - The export's shape, and the Workers bundle, are otherwise unchanged.
- **The Dockerfile's ENTRYPOINT** traps TERM (exit 143) and INT (130), and runs preflight in the background under `wait`.
  - Until the `exec`, the shell is PID 1 and ignores a signal it has no handler for, and a trap runs only once a foreground command returns. A stop sent during preflight was therefore lost: the server started, and the stop was killed at 10 s.
  - A failing preflight still fails the container with its own code (1, checked).
- **`integrations/kubernetes-deployment/index.ts`** gets the same handler, cut to that server: a 20 s bound under the pod's 30 s grace period, then `sql.close()`.
- **Two Fork Checks steps** in the full-stack job:
  - **"The Kubernetes image stops on SIGTERM, finishing a call in flight":** a `search_thoughts` call is in flight when `docker stop` lands, its embedding endpoint a stub that answers 503 after 2 s. The stop must wait for the call and count it: exit 0 in 1–5 s, `1 in flight` in the log, the call answered.
  - **"The server stops on SIGTERM, serving and in preflight":** it stops the compose server, which must exit 0 inside 3 s with the shutdown line. It then starts it with the provider stub holding `GET /models` for 2 s (a new `/tmp/provider-stub-slow` toggle), stops it 0.5 s later, and requires exit 143 inside 1 s. The log is read into a variable once, and the check is on the last stop line.

**Why.** The image ran `exec bun index.ts`, which made Bun PID 1, and the kernel gives PID 1 no default action for SIGTERM. So every `docker stop`, compose restart and upgrade waited out the grace period and ended in SIGKILL (exit 137), cutting off anything in flight.
- A minimal probe on `oven/bun:1.4.0-alpine`: 10.3 s and exit 137 as shipped, against 0.1 s with a handler.
- The full-stack job stops a server three times (the canary's refresh, `canary.sh down`, the teardown): 10–12 s each in run 36221013361, about 30 s of a 148–157 s job that is the run's critical path.
- The Kubernetes image had the same shape against a 30 s default grace period.
- `jev/serve.ts` already had the handler (SMD-2050), but it exits as soon as `stop()` is called, which cuts off what is in flight. The mutant below shows the difference.

| --- | --- | --- |

**Not taken.**
- **`init: true` on the compose service.** Tini as PID 1 fixes a compose stack alone, not the image run any other way. The handler and the traps fix every runtime.
- **A handler in `preflight.ts`.** Docker signals PID 1, which is the shell during preflight, so a handler in preflight never sees the signal.
- **Serving from an explicit `Bun.serve` to get the handle.** A default export with a `fetch` is served by Bun itself, so the file would need a second, Bun-only entry. Keeping the first request's handle leaves the export, Workers and the suites as they were.
- **A knob for the bound.** Each image's constant sits under its reference platform's default grace period: Docker's 10 s for the core image, the pod's 30 s for the Kubernetes one. The core image run where the grace period is longer (EKS, ECS: 30 s) now cuts a call of 8–30 s at 8 s, where before SIGTERM was ignored and the call finished before the kill. A platform with a shorter one (Fly's 5 s) kills sooner, as it did before. A knob would need forwarding in compose (check 14) and a matching `stop_grace_period`; it waits on a deployment that needs it.
- **A `preStop` sleep in `k8s/openbrain.yml`.** It lets endpoints drain to other replicas, and this StatefulSet has one.
