## Changelog

When a classified key that can read captures text a capture-only key captured first, at a higher trust, the row's trust and its writer's marks now move to that key. A text the capture-only key labelled outside text is then found under `min_trust` and shown without the outside-text notice. Only a capture-only key's label yields, only to the first classified key that can read to capture the text after it, and only on captures a server at migration 082 or later wrote; a lowering by a key that can read, the operator's own included, stands (SMD-2664).

## FORK

A capture-only key's stamp yields to the first classified key that can read to re-capture the text, at a higher trust (SMD-2664)

**What changed.**
- **The restamp** (migration 083, `ob1_restamp_recapture`). When a capture by a key that can read lands on a row that already holds the text, both stores call it after 082's `ob1_note_recapture`, passing the text's fingerprint and the trust the write declared.
  - **Which rows.** It moves nothing unless the row's stamp is still a capture-only key's: the row's capture row carries 082's `"scope": "capture"` mark, and no update since has changed the text (by 003's fingerprint, so a whitespace-only edit doesn't count) or restamped it.
  - **Which writers.** An unclassified writer, or a call with no actor, moves and records nothing. A classified writer is weighed: the stamp the write would have put on a new text (the key's kind, or the declared trust when that is lower) against the row's (operator > agent > ingested > none).
  - **Higher.** It appends one update event and projects it. The event moves the whole stamp (`actor_kind`, `actor_name`, `trust`) to the writer and carries `"restamped": true` in its diff. Once moved, no later re-capture moves it.
  - **Not higher.** It records the decline once per agent: an update event whose diff is `{"restamp_declined": true}`, the audit row naming the key and the trust it was weighed at.
  - **Settled.** A decline by another agent refuses every later weighing. The same agent's own later landing may still move the stamp. "The same" is by agent id, so a decline naming none settles the row for every caller. A name-only writer is board-sync, whose actor never carries an agent id, or any key while its registry lookup fails, through an outage or a misconfiguration, or is refused.
  - **Refused outright:** a capture-only actor (passed, or the session's), and a fingerprint that is no longer the row's (the text moved between the capture and the call).
  - Either event moves `updated_at`, as 082's note does.
- **The backfill.** `backfill_thought_actors` reads a restamp with no text-writing row after it, by `seq`, as the row's writer. A pass after a restamp keeps the stamp rather than putting the lower one back. A key reclassified down still takes its rows down.
- **The order.** The restamp is a second statement after the capture and after the note, so a restamp that fails never holds up the note. A restamp that fails throws after the capture landed, and the caller's retry makes it. A database before 083 has no such function, and the capture stands without it.
- **The description.** `capture_thought`'s `trust` says a text already captured keeps its trust, unless its trust is still the one a capture-only key gave it and no other classified key that can read has been weighed against it since.
- **The change log.** `thought_changes` reads a restamp as "re-captured by <key> — the capture-only key's label moved to this key" with the marks that moved, and a decline as "re-captured by <key> — the capture-only key's label kept", where both read as edits before.
- **The cost.** The restamp reads the cheap facts first (the scope mark, an earlier restamp, a decline) and hashes edits' texts last, so a row already moved or settled pays nothing for them.

**Why.** A capture-only key may declare a trust below its kind: the Chrome extension labels every capture `ingested`. When a write key later captured the same text, the capture landed on that row (035), and 050's rule for a write that leaves the text kept the stamp. So the writer's thought kept the capture key's `trust`, `actor_kind` and `actor_name`. It dropped out of `search_thoughts` with `min_trust: "agent"` and carried the outside-text notice, though the writer's own capture would have been stamped at its kind had it come first. SMD-2638's first review pass reproduced it on the real server. 082 ended the capture key's ownership of such a row; the stamp is a separate fact, and stayed.

**Decisions** (the maintainer's).
- **At the plan stage, the higher of the two writers**, the ticket's first option. Not trust per holder, which would redesign SMD-1724's one trust per row. Not refusing a capture-only key its lowering, which would drop the extension's honest outside-text label.
- **After review pass 1, capture-key rows only.** The first build let any key that can read raise any row, and an agent key re-sending the operator's own outside text relabelled it as the agent's. A lowering by a key that can read is that key's statement about its text, and stands.
- **After review pass 2, the first reader settles the row, and the writer must be classified.** With a capture key first, the operator's equal `ingested` re-capture recorded nothing, and an agent key re-sending the text after relabelled it. Separately, a writer of no kind could spend the row's one move at `ingested` and lock the operator out.
- **After review pass 3, the restamp keeps its own record.** Pass 2 read 082's note as the record of the first landing, but 082 writes its note by conditions of its own: for an unclassified key and a call with no actor too, neither of which can move the stamp, and not on a row it counts as taken. So those landings settled rows they could never move. The restamp now records the decline itself, and only a classified writer is weighed.
- **Mine, within those:**
  - The whole stamp moves, not the trust alone, so a row's trust is never above the kind its marks name.
  - The stores call a function, rather than `upsert_thought`'s three bodies being redefined, as 082 did for its note.

**Before upgrading.** Apply 083, then run the new server. A server from before 083 never calls the function, so nothing is restamped. The new server against a database before 083 makes the call and treats the missing function as nothing to do.

**Not taken.**
- **Rows a write key re-captured before 083.** A merge's update event can't be told from a metadata edit, and a re-capture that changed nothing wrote no event. Those rows keep their stamp until a classified key that can read re-captures the text at a higher trust.
- **A capture-only key's row from before SMD-2638's scope mark.** Nothing says whose it is: every capture a server before 082 wrote, the Chrome extension's pages on 1.6.0 included. Recognising them by the registry's key scope is SMD-2745.
- **A name-only writer's decline** settles the row against every caller, that writer's own later landings included: board-sync always, and any key for as long as its registry lookup fails, a misconfiguration such as a role not re-granted after an upgrade included.
- **Settling low.** The first classified writer settles the row whatever it declared: an agent key declaring `ingested`, or an `ingested`-kind key, landing first leaves the capture key's stamp and refuses the operator after it. Over a row with no trust (an unclassified capture key's), an `ingested` writer is higher, so it moves the stamp once, to `ingested`. Both keep trust low, the direction a label may err in.
- **Two live keys on one agent id.** A key renamed and a new key given its old name read as one agent under 010's rotation, so one's decline is the other's own. The registry's to fix, as it is for 082's and SMD-2473's agent checks: SMD-2746.
- **A stuck label.** Nothing resets a settled or restamped row's stamp: a text edit by a key that can read, or deleting the thought and capturing the text again, stamps it afresh. The db/README gives the query that lists settled rows. An operator reset is SMD-2744.
- **The hashing on a row still able to yield.** A capture-key row with many case- or whitespace-only edits, not yet moved or settled, still hashes each edit's texts on every re-capture. A cheaper text-change test is SMD-2747.
- **A decline's stale read.** A decline moves `updated_at` with nothing visible changed, so a client's `update_thought` holding an earlier `if_unchanged_since` is refused once per row, as after 082's note.
- **A metadata edit.** `update_thought` and a raw UPDATE that leave the text still keep the stamp (050), board-sync's metadata patch adopting a row in place included. Board-sync's capture that lands on a row in the instant before is a re-capture like any other, and moves nothing unless the operator classified board-sync's key.
- **A caller of `upsert_thought` outside the stores**, a recipe or script calling it directly, restamps nothing: only the stores call the restamp.
- **A text change written with the audit trigger off after a restamp.** The backfill can't see it, and the restamp's key stands. A restamp carries no text to check.
- **SMD-2653**, a capture-only key's `metadata.importance` read by the weekly digest, is the same family (a value one key set on a row other keys come to hold) and has its own ticket.

**The version.** MINOR: a migration, and two new diff keys in the audit log (`restamped`, `restamp_declined`). `thought_changes` shows each as a re-capture by the key, the label moved or kept. A capture-only key's row can now take a higher trust after a key that can read re-captures it, where it never did.

**Follow-ups.** SMD-2744 (an operator reset for a settled label), SMD-2745 (pre-082 capture-key rows), SMD-2746 (two live keys on one agent id), SMD-2747 (the restamp's text-change hashing).
