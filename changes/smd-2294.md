## Changelog

The proxy routes `/canary/mcp` and `/working/mcp` to that tier's MCP server, reached by name on the stack's mesh (`mcp.canary.ob1.internal`, `mcp.working.ob1.internal`), and answers a bodiless 404 while no such tier is up; every other path that starts with either word is a 404 too, never stable's server. The proxy dials stable's own server by its mesh name, `mcp.ob1.internal`, so another project's container on the mesh, which compose also calls `server`, cannot take stable's traffic. `deploy/canary.sh` stands the canary there: its MCP server and REST core join stable's mesh under the canary's names alone (`deploy/compose.canary.yaml`), its connector is `/canary/mcp` on stable's origin, and beside a stable from before this release, `--port N` gives it its own loopback proxy as before (SMD-2294).

## FORK

The tier stack on proxy paths — the canary answers at /canary/mcp on stable's origin, its servers on stable's mesh, and a tier's URL never reaches stable (SMD-2294)

SMD-2294 moves the canary and working tiers from host ports (8010–8012) onto
paths of stable's one origin, in three cuts. Each tier's MCP server is today's
server-portable, beside its own REST core; SMD-2287's server replaces it by
changing only the service the routes name.

**PR 1 (#314) — the routes.** In `deploy/compose.yaml`'s `x-proxy-routes`:
- `canary` and `working` (30) send `/canary/mcp` and `/working/mcp`, and
  everything under each, to `mcp.<tier>.ob1.internal.` on `mesh`, prefix
  intact, with `not-legacy`. `tier-absent` turns Traefik's 502 (no such name, a
  stopped or starting tier) into a bare 404. A tier's own 4xx and 5xx pass.
  A tier's protected-resource path is not routed: keys only (OAuth per tier is
  SMD-2286's).
- `tier-off` (25), ``PathRegexp(`(?i)^/(canary|working)`)``, answers every
  other path starting with either word, in any case and whatever follows,
  with a 404. Without it, `POST /canary/`, `/CANARY/mcp`, `/canary%2Fmcp` or
  an invisible space pasted after `canary` fell to `legacy` and wrote to
  stable with the same key. No boundary after the prefix: three were tried
  and each leaked (review passes 2–4). `/canry/mcp` still reaches legacy until
  SMD-2532.
- Every backend is a rooted mesh name, `mcp.ob1.internal.` for stable's server.
  Compose aliases a container under its service name on every network it
  joins: with a canary stand-in on the mesh and stable's server recreated
  after it, 20 of 20 `/mcp` requests reached the canary as `server` (podman 6).
- Held by CI: the backend URLs held to the rooted names (static); a full-stack
  step with a stand-in per tier (17 off-prefix 404s, Host, legacy marker,
  status pass-through, `server` naming several containers from the mesh, 404s
  again once gone); a guard on route-table errors in the proxy's log.
- Measured: 22 route-table mutants killed (the bare `server` backend by the
  static check alone); a real second project on stable's mesh answered
  `tier: "canary"` while stable kept `/mcp` 20 of 20; SSE streams live through
  `tier-absent` (not held in CI); an absent tier's name is forwarded upstream
  by the default network's resolver (shown with a decoy; SMD-2583).

**PR 2 — `canary.sh` at `/canary/mcp`.**
- `up` finds where the canary answers. If stable's running proxy carries the
  route (its `ob1.proxy-routes` label names `mcp.canary.ob1.internal`) and stable
  has a mesh, the canary answers on stable's origin at
  `http://<stable's bound address>:<port>/canary/mcp`. Otherwise `up` refuses,
  unless `--port N` gives the canary its own loopback proxy, as every canary
  had before (8011 was the default). Switching back removes that proxy.
- `deploy/compose.canary.yaml` joins the canary's `server` and `api` to
  `${CANARY_STABLE_MESH}` (external, `<stable project>_mesh`), under a network
  key of its own, with only `mcp.canary.ob1.internal` and
  `api.canary.ob1.internal`. Redefining `mesh` would have brought the canary's
  `mcp`/`api`/`auth.ob1.internal` names onto stable's network.
- The REST core is now always the canary's, started and recreated with the
  server; a refresh stops both.
- `COMPOSE_PROFILES` stays empty for the canary, so its server advertises no
  OAuth. On stable's mesh it resolves stable's authorization server, which
  answers the ADR's question of how the canary reaches it.
- A connector is the canary's at `/canary/mcp` on loopback or on stable's
  bound address, or at a canary proxy's port, never at stable's own `/mcp`. A
  mode switch without `--connect` names a connector left at the old URL.
  Stable's mesh is left alone; with a canary attached, stable's `compose down`
  leaves it in place.
- On stable's origin the canary is reached wherever stable is (the LAN, a
  tunnel) with stable's keys. `up` says so when stable is bound past loopback
  or has a public origin; `--port` keeps it on loopback.
- Held by CI:
  - the overlay rendered as the canary project, with only the canary's names
    on stable's mesh and its own `mesh` its own (static);
  - the refusal of a stable whose proxy label has no route;
  - `--port` for the port refusals;
  - the life step:
    - path mode: the connector at `/canary/mcp`, no canary proxy, tier `canary`
      with OAuth not configured, no stable name on the canary's aliases;
    - the second `up` as the `--port 8011` fallback: the proxy on loopback,
      off stable's mesh, `/canary/mcp` a 404 again;
    - a third `up` back on stable's origin: the proxy removed, 8011 free, the
      old connector named;
    - a connector at stable's `/mcp` left alone by `down`.
- Measured on a scratch stable (`-p ob1-2294`), with a renamed canary project
  beside the running dogfood:
  - path mode passed all 11 smoke checks, and the vector probe found its thought
    first at 86.3%;
  - the switch to `--port` and back worked;
  - an old stable got its refusal (exit 2);
  - `down` left a connector at stable's `/mcp` and removed the canary's.
