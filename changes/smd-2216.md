## Changelog

A role set up by `migrate.ts --grant` can run entity extraction, a structured pass, `merge_entities` and a merging `apply_entity_type_gate()`: the **extraction** group grants `UPDATE` on `thought_entities` and `ob1_entity_edges`, which `record_thought_entities` has upserted since migration 053, and a new **structure** group grants a structured pass its source row (`thought_sources`) and its `link` facets. Before, each failed under such a role with `permission denied` — every extraction since 053, every structured pass (053 added them with no grant), `merge_entities` since 016, and the gate wherever a retype merged (SMD-2216).

## FORK

A --grant role can run the entity writer and a structured pass — UPDATE on the mention and edge rows, and a structure group for the source row and its links (SMD-2216)

**What changed.** `db/config.mjs`'s `ROLE_GRANTS`, and the README table rendered from it:

- **extraction** gains `UPDATE` on `thought_entities` (since 016: `merge_entities`
  re-points mentions with one) and `ob1_entity_edges` (since 053). The community
  row for `thought_entities`, issued on every migrated brain, keeps to the
  extraction row's privileges, so it gains `UPDATE` too — which is also
  upstream's `GRANT ALL` now.
- **structure**, a new group after extraction: `SELECT, INSERT, UPDATE, DELETE`
  on `thought_sources` (`record_thought_source` upserts the row, and on a take
  deletes the old holder's) and `INSERT` on `thought_facets`
  (`record_source_links` adds `link` facets; capture's `SELECT, UPDATE` already
  cover the reads and the closing). `--grant` issues it with the rest; the README
  says to add it for a structured pass.

No migration and no function changes. A role already granted gets the new
privileges by running `migrate.ts --grant <role>` again.

**Why.** Since 053, `record_thought_entities` writes both tables with
`INSERT … ON CONFLICT DO UPDATE` (the structured-wins rule). Postgres checks
`UPDATE` for that each time the statement runs, whether or not a row conflicts.
So under a `--grant` role every extraction pass (`extract-entities.ts`) failed
with `permission denied for table thought_entities`. So did `merge_entities`
(its UPDATE has been unconditional since 016), and 056's
`apply_entity_type_gate()`, re-run by an operator as that role, on a brain where
a retype merges (its re-pointing UPDATE runs only then). SMD-1935's third review
pass found it.

Planning this fix turned up the rest of 053's gap: no group named
`thought_sources` at all. A structured pass (`sync-linear.ts`, an ingest
adapter's structure step) calls `record_thought_source` first, so it failed on
`thought_sources` before it reached the entity writer, where it would have
failed next. The dogfood stack connects as the owner, so it never hit either
gap.

**Held.** test-schema [53] sets up a role exactly as `--grant` does (every group,
the objects present, `grantVerifySql` clean) and runs each path as that role:

- an extraction;
- a structured pass's source row and link;
- its mentions landing on the extracted rows through the upsert (mention and
  edge keys become `source:linear`);
- an extraction onto the structured rows, which leaves them standing;
- a take (holder's source row deleted, its link closed, its mentions removed);
- `apply_entity_type_gate()` merging a pre-gate place into its tool.

Then it revokes each added privilege in turn and watches that path fail on that
table's name. It also holds the class: every table in the migrated schema is
named by one of the migrations' own groups (it would have caught
`thought_sources`), and the community and extraction mention rows grant alike.
test-schema 1780 → 1792.

**Measured after.** Six mutants, all killed: each added `UPDATE` dropped, the
`thought_sources` row dropped, its `DELETE` dropped, the `thought_facets` row
dropped, and the community row narrowed. Four are killed by the role's runs.
Two, extraction's `thought_entities` `UPDATE` dropped and the community row
narrowed, are killed only by the "grant alike" check: `--grant` merges the two
rows, so either one alone still gives the role `UPDATE`.

**Review passes.**

| Pass | Finding | Caught | Fix |
| --- | --- | --- | --- |
| 1 | The table check read every group, so a migration table sharing a community table's name (`entities`) counted as named | cold read | reads the migrations' groups only; migrate.ts's ledger exempt by name |
| 2 | That filter excluded three named groups, so a new non-migration group would weaken it silently, and nothing held it (its mutant survived) | cold read, mutant | a group is the migrations' when every row's `since` is a migration number; asserted, `entities` not named |
| 2 | The revoke leg's restore granted the privilege whether or not `--grant` had | cold read | restores only what the role held; "not held" otherwise |

**Not taken.** `TEMPORARY` on the database: the writers stage rows in temp
tables, which `PUBLIC` may create by default; the README now says so, and
`--grant` does not issue a database-level grant.
