## Changelog

rest-api's `POST /ingest` and `POST /ingestion-jobs/:id/execute` proxy to the smart-ingest server at `SMART_INGEST_URL` — its root and `/execute` — and answer `503 smart_ingest_not_configured` naming the variable when it is unset; smart-ingest's extraction trigger after a write POSTs to `ENTITY_EXTRACTION_WORKER_URL`, and is skipped when that is unset. Both built the URL from `SUPABASE_URL`, the Postgres connection string on this fork, so every call handed `fetch()` the database credentials and failed — the proxy with `502 upstream_unreachable`, the trigger silently inside its timeout. An address under any scheme but `http`/`https` is refused when the server starts, the message naming the variable and the scheme and none of the value. smart-ingest reads the fork's UUID as the written thought's id, where it reported every add failed and so never triggered; the wiki compiler's `${OPEN_BRAIN_URL}/functions/v1/…` fallback is gone (SMD-2110).

## FORK

rest-api's ingest proxy and smart-ingest's extraction trigger read their upstream from a URL variable of their own, http(s) only — both built it on `SUPABASE_URL`, the Postgres connection string on this fork, so every call handed `fetch()` the database credentials and failed, the proxy answering `502` on every deployment and the trigger never firing (SMD-2110)

**What changed.** `integrations/rest-api/index.ts`: `httpTargetFrom(name)`
reads one variable, answers `null` when it is unset, and otherwise parses it
when the module loads and throws unless it is a bare http(s) address —
scheme, host, port, an optional path prefix; no query, fragment or
credentials, since a path is appended to it (review pass 1) — returning it
without trailing slashes. The message names the variable and the scheme
("it is a postgres:// URL"), never the value, whose userinfo is the database
password; Bun's own "Invalid URL" error quotes the value, so it is caught and
not rethrown. `SMART_INGEST_URL` is the
smart-ingest server's address: `handleIngest` POSTs its body to it and
`handleExecuteJob` to its `/execute` (the server strips an optional
`/smart-ingest` prefix itself), through `proxyFetchJson` as before; unset,
both answer `503 { error: "smart_ingest_not_configured", variable:
"SMART_INGEST_URL", hint }` before reading the body. The `/ingestion-jobs`
reads are untouched — they read `schemas/smart-ingest`'s tables through the
shim. `integrations/smart-ingest/index.ts`: the same helper for
`ENTITY_EXTRACTION_WORKER_URL`; `scheduleEntityExtraction` returns when it is
unset (the server says so once, at start) and otherwise POSTs to it with the
key and `?limit=` set on a parsed `URL`, so an address carrying a query of its
own keeps it. Its `extractThoughtId` accepts a UUID string beside upstream's
integer: `upsert_thought` answers `{ id: <uuid>, fingerprint }` here, which
the file read as no id, so every add was reported failed after the row was
written and the trigger's count was always zero — the smallest cut that lets
the trigger fire. With it the item's row had to follow: one statement set
`status` and `result_thought_id` together, and the UUID in that bigint column
failed it whole, unread, leaving the item `ready` under a job marked complete
(review pass 1); `recordItemResult` sets the status, puts an integer id in the
column and a UUID in the item's `metadata.result_thought_uuid`, and logs the
update's error. The rest of that write path's fork gap is SMD-2128's.
`recipes/wiki-compiler/compile-wiki.mjs`: `triggerEntityExtraction` takes
`ENTITY_EXTRACTION_WORKER_URL` alone, refuses a non-http value, and no longer
derives `${OPEN_BRAIN_URL}/functions/v1/entity-extraction-worker`, upstream's
Edge Function path; its usage text and README say so. The rest-api README's
route table, Prerequisites, Step 2, "How It Connects" and troubleshooting
entry describe the knob and the `503`; smart-ingest's and the worker's READMEs
describe the trigger; the two dashboards' "Ingest page" entries name rest-api
as the gateway that proxies and cite this ticket where they cited SMD-2114.

**Why.** SMD-1798/1800 repointed `SUPABASE_URL` at the Postgres connection
string (`createClient` refuses anything else), and three callers kept
building HTTP URLs on it: rest-api's two proxy routes fetched
`postgres://user:password@host/db/functions/v1/smart-ingest…`, which Bun's
`fetch` refuses ("protocol must be http:, https: or s3:"), so the catch
answered `502 upstream_unreachable` on every deployment with the credentials
in the URL it had been handed; smart-ingest's trigger fetched
`…/functions/v1/entity-extraction-worker?limit=N` the same way and logged a
warning nobody saw; the wiki compiler's fallback would have, given
`OPEN_BRAIN_URL`. Found by SMD-2079's second review pass (the proxy) and
SMD-1802's fourth (the other two). One rule for all three: an HTTP target
comes from its own variable, never from the connection string, and a
`postgres://` value in that variable is refused before the first request.
