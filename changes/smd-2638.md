## Changelog

A capture-only key can no longer mark superseded a thought that another key or board-sync has taken: once a key that can read captures the same text, someone edits its text, or board-sync adopts it as a ticket's row, the key's `supersedes` naming it is dropped, and a pointer the key had already written onto it lapses, whichever came first. Migration 081 holds the rule in the database and re-checks the key's pointer at its own write; a vector filled in later, a tag or an operator's metadata backfill does not take a thought, so the session hook still supersedes its own earlier summaries, and a write key's pointers are never touched (SMD-2638).

## FORK

A capture-only key's thought stops being its own once another key or board-sync takes it, a pointer it wrote onto it lapses, and its pointer is re-checked at its own write (SMD-2638)

**What changed.**
- **The rule** (migration 081, `ob1_takes_thought`). An update event takes a thought from the agent that captured it when it comes from another agent (or none) and it does one of these:
  - records a re-capture by a key that can read;
  - moves the text;
  - gives the metadata an `issue` it lacked, which is how board-sync adopts a row. A key that cannot read may not set `issue` (SMD-2617).
  
  After any of these, someone else holds the text. None of these takes a thought:
  - a metadata move alone, attributed or not: a writer's tag, a kanban move, `backfill_thought_actors`, a recipe;
  - a vector arriving;
  - a pointer;
  - a fingerprint.
- **The check.** For a capture-only key's `supersedes`, the server reads `ob1_thought_taken` for every target, beside the capture row and the existence read (`core/writes.ts`, and both stores' new `takenFromCapturer`). So every target now costs three reads where it cost two. A read that fails is the server's error to retry, never "not taken". The check at the write (below) is the authority; this read spares a key the retry when its target is already taken.
- **The no-op re-capture, recorded.** A write key's re-capture that changes nothing writes no audit event. So when a capture by a key that can read lands on an existing row, both stores call `ob1_note_recapture`. It appends one update event, diff `{"recaptured": true}`, and projects it, so only `updated_at` moves. It does so only when all of these hold:
  - the row's capture row says a capture-only key wrote it;
  - the row isn't taken yet;
  - the caller is another agent.

  Every other row is left as 060 leaves it.
- **The lapse.** An AFTER INSERT trigger on `thought_audit` fires when an event takes thought T. It clears the pointer onto T from each thought that T's capturer captured with that pointer, under the capture scope, and that no update has re-pointed since. Each clearing is an update event of its own, under the actor of the write that took T. A pointer a write key set is never lapsed.
- **The check at the write.** A second trigger runs on a capture-scoped capture event that names `supersedes`. It locks the target `FOR SHARE`, which waits for any taker, since every taker holds the row `FOR NO KEY UPDATE` before its append. It refuses the capture (SQLSTATE `OB004`) when the target is not the key's alone: another key captured it, it is taken, or something already supersedes it. The server drops the pointer and writes again without new model calls, as it already did for a target deleted mid-write.
- **The mark.** A capture-only key's capture says so on its audit row: `actor_context` carries `"scope": "capture"`.
- **The descriptions.** `capture_thought`'s `supersedes`, the server README, the session hook's README and `db/README.md`.

**Why.** The capture scope promises a key that it cannot alter a thought it did not write. Under SMD-2473 the target's capture row decided ownership, and nothing written to the row later counted. A write key's capture of text that is already a thought lands on the existing row (035), and board-sync adopts a row holding a ticket's text in place.

SMD-2617's review pass 1 showed the result on the real server. The capture key captured a text, a write key captured the same text with its ticket's facets, and the capture key's next capture named the row as `supersedes`. The pointer was kept, and the writer's thought read superseded and ranked ×0.25. Through board-sync, a capture key's pasted ticket header, or a capture of the ticket's next text, became the ticket's head row, and the key could then mark it superseded.

Checking ownership only when the pointer is asked for leaves three ways round it. Review passes 1 and 2 showed each on the real server, the board-sync route through `syncIssue` itself:
- **The reverse order.** The key supersedes its own row first, while it is still only its own, and the writer or board-sync lands on it afterwards.
- **A no-op re-capture.** A write key's re-capture that changes nothing writes no event. That is the ordinary case: the extractor is deterministic, and both sides default to `source: "mcp"`.
- **The race.** The server checks before its model calls and writes seconds later. Under concurrent traffic, 11 of 30 pointers landed on thoughts taken in between.

**Decisions** (the maintainer's, at the plan stage and after each review pass):
- **What takes a thought:** someone else holding the text, one rule for both the check and the lapse. A lapse is not fail-safe: it puts a summary the hook superseded back to current. So nothing that leaves the text only the key's may cause one. That rules out:
  - a writer's tag or kanban move, which the first cut counted;
  - a backfill, which the plan first counted;
  - a vector.
- **The race:** the database re-checks at the capture's own write, under a lock every taker conflicts with, and refuses. The server mends as it does for the self-FK. This avoids redefining `upsert_thought`, which would move preflight's `atomic capture` remedies from 080.
- **One superseder per target** for a capture-only key. A key pointing thousands of its own captures at one thought made the taker's write pay one lapse event for each: 17 s at 8,000 pointers, and under a statement timeout the taking failed outright.
- **The note** only on a capture-only key's rows, so a re-capture that changes nothing still moves nothing on any other row.
- **Board-sync unchanged.** When no row holds Linear's text, it still takes the newest row of a ticket's group as the head. Its adoption now takes the row and lapses the key's pointer onto it. SMD-2617 declined to change the adoption design.

**Before upgrading.** Apply 081 first, then run the new server.
- **The new server on a database without 081:** every capture-only key's `supersedes` is the server's error to retry (the target "could not be checked"). The session hook keeps the payload, then drops the pointer once four attempts have failed or the payload is a week old.
- **081 under an older server:** that server sends no scope mark, so nothing is noted, lapsed or checked at the write, and the old pointer check alone holds.

No new grant: the reads, the note and the triggers use `thought_audit` and `thoughts` as every capture already does.

**Not taken.**
- **Rows from before the scope mark.** A pointer written before the server sent the mark, and a capture-only key's row from before then, carry no mark. Neither is lapsed, noted or checked at the write; the server's check still holds a new pointer.
- **Rows a capture key forged with `issue` before SMD-2617.** Board-sync's patches find `issue` there already, so they do not take the row.
- **A vendored integration calling `upsert_thought` directly** records no re-capture. Its metadata merges carry no agent id and take nothing.
- **A stale PostgREST schema cache.** Right after 081 is applied, the PostgREST store reads a missing note as a database before 081, so re-captures in that window are not recorded.
- **Two hook summaries naming the same earlier one.** The second lands without its pointer.
- **Timing.** A kept pointer costs a projection that a dropped one does not, so a key that cannot read could time whether its own thought was taken. SMD-2473 left timing out of the oracle rule.
- **Deadlocks.** Two concurrent multi-row writes can still deadlock on 068's node-projection locks. Postgres aborts one, and the caller retries.
- **A data-only reload of `thought_audit`** fires both triggers. `pg_dump`/`pg_restore` creates triggers after the data.
- **A lowered `trust` set by a capture key** survives a write key's merge (`ob1_actor_stamp_kept`): SMD-2664, beside SMD-2653.

**Follow-ups.** SMD-2657 (a capture-only key's `metadata.ticket`), SMD-2664 (a capture-only key's lowered trust survives a write key's re-capture).

**The version.** MINOR: a migration, a new diff key in the audit log (`recaptured`), and a scope mark on a capture-only key's capture rows. `list_changes` shows a noted re-capture as an edit that changed no field, and a lapse as an edit by the taking key that cleared a pointer. No other reply changes. A capture-only key's `supersedes` naming a taken thought, or one something already supersedes, is dropped where it used to be kept, and a pointer it wrote lapses when its target is taken. Nothing tells the client either way.
