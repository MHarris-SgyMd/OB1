## Changelog

Preflight's `vector index memory` row no longer counts a staging halfvec index built by hand for migration 039 to adopt. While `match_thoughts` still orders its walk by the vector column and the vector index (001's on `thoughts`, 007's on `thought_chunks`) holds the shipped name, the walk uses that index, so the row used to overstate the resident need and the `shared_buffers` it recommends by the staging index's size (about a third of the full-width index). The row now names what it left out and its size, and the index searches use until then, and asks for a fresh run after 039. A warning's remedy has 039 applied first: a plain migrator run where the ledger does not record it, a re-apply (`--reapply`, with the server and every worker stopped) where it does, both where the ledger could not be read, with any table 039 would build on in its own transaction staged CONCURRENTLY before that, and says the size it then gives is for the indexes as they stand. In every other state, after 039 included, the row reads as before (SMD-2871).

## FORK

Preflight's resident-memory row leaves out a staging index 039 is about to adopt, and says so (SMD-2871)

**What changed.**
- `db/config.mjs` gains `residentIndexes({ indexes, dim, bodyCasts })`. It returns the bytes of the valid HNSW indexes a search walks, and any staging index left out, apart. A staging index (`<table>_embedding_halfvec_idx`) is left out only in the state 039 adopts from and the walk runs around:
  - `match_thoughts`' body orders by the vector column;
  - an HNSW `vector_cosine_ops` index over the column (001's or 007's, with or without its own build parameters) holds the shipped name on the same table;
  - the staging index is of 039's own shape at the column's width.
  Anywhere else it is counted like any other index. 039 would refuse the staging index (another shape, another width, its own `m`), or skip it (the shipped index already 039's), or the body walks the staging index itself (it casts: the walk index remedy's rebuild), or the walk has no vector index to use now (the shipped name missing, INVALID, partial or of another operator class) and the staging index is what 039 puts under the name.
  It also names in `builds` a table 039 would build its own index on, in its transaction, holding writers: the vector index under the shipped name and nothing under the staging one. A staging name taken by another shape is 039's refusal, not a build.
- `memorySizing` takes `stagedBytes`, `stagedTables` and `builds` (none by default) and carries them on `resident`, with `stagedCount`. Neither the fit nor the recommendation counts them.
- `memoryRows` adds a sentence to the ok row and to the warning when one or two indexes were left out. It names them and their size, says that the body still orders by the vector column so searches use the index under the shipped name (named) until 039 swaps the staging one in, and asks for preflight again after 039. In that case the warning's remedy starts by having 039 applied before sizing, `bun db/migrate.ts` where the ledger does not record 039, and where it does, the migrator's `--reapply` with the server and every worker stopped, after which 074, the last definer of match_thoughts, has run again, and both where this role could not read the ledger, as preflight's `ledgerRemedy` says it (`memoryRows(s, { ledgerHas039 })`: true, false or null). The files are templates only the migrator fills in, so the file alone through psql is not offered. A table in `builds` comes first: on a brain past a million rows, build its staging index CONCURRENTLY, as 039's header says. The lead ends by saying to run preflight again after 039 and size only if it still warns, the size below being for the indexes as they stand.
- `db/config.d.mts` follows.
- `server-portable/preflight.ts`:
  - reads each valid HNSW index's name, table, size and `pg_get_indexdef`, and the embedding column's width (`atttypmod`), and passes whether the ledger records 039 (unread: null);
  - takes the body's cast from the catalog read the walk index check uses (unread: nothing left out);
  - hands both to `residentIndexes`;
  - shares the ORDER BY regex with the walk index check, as `WALK_ORDERS_BY_CAST`.
- `server-portable/README.md`'s row description says so.

**Why.** SMD-1499 (#362) counted every valid HNSW index by access method, so 039's swap and any later rename read alike. Its review pass 1 found the one state where that overcounts, on exactly the large brains where the recommendation matters: between an operator's hand-built `CREATE INDEX CONCURRENTLY` and the migration. It was kept out of that PR as a behaviour change.

**Not taken.**
- Counting, across every index, only the one on the operator class the body's cast reaches. An index the walk index check finds mismatched would then read here as no index at all, and an HNSW index a recipe built under its own name would drop out of the count. Only the staging-name pair is decided by the walk.
- Saying what the need will be after 039. Where only one table is staged, 039 may build the other's index itself, so no figure read now is the after-039 one. The clause asks for a fresh run instead.
- A duplicate under the staging name beside an index 039 already swapped in is counted, as before. 039 never adopts it, so no clause about 039 would be true.
- Under a casting body with the vector index back under the shipped name and a staging index beside it, both are counted: the unwalked vector index overstates the need. The walk index row warns in that state, and its remedy, 039 again, adopts the staging index and drops the vector one.
- The body is read from the catalog read's first overload (7 arguments, then 6), as the walk index check reads it. With overloads that disagree, the search signatures row fails the start.
- `builds` sees only valid HNSW indexes. A staging name held by an INVALID index (an interrupted build) is not seen, so the remedy's CONCURRENTLY build fails on the taken name, which says why; a table whose shipped name is missing or INVALID with nothing staged is not named, though 039 builds there too (the walk index row warns in that state).
- 039 is all or nothing: where the other table holds a shape 039 refuses, "039 will adopt" does not happen, and 039's own refusal names the index and the fix.
- The VECTOR and HALF shapes are not shared with the walk index check, whose vector shape reads neither a schema-qualified operator class nor build parameters. Sharing them changes that check, so it is left for the follow-up on its remedy.
- The ledger and `builds` reach only the warning's remedy, which no live test can reach (a pool cannot be lowered for one database). test-schema holds the wording; review pass 2's run-it reviewer ran the warning at `shared_buffers=20MB`.
