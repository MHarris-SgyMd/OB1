## Changelog

One `coordinator` service, part of every stack, runs the core passes `OB1_PASSES` names in `deploy/.env`: `board-sync`, `workers` (extraction and consolidation) and `sleep`. Each pass runs as a user of its own, with only its own settings, so none can read another's environment. `sleep` and `workers` never run together: named together, `sleep` runs and the log says so. It replaces the `sleep`, `extract`, `consolidate` and `board-sync` services and their `sleep`, `workers` and `board-sync` profiles (SMD-3476, the first step of `docs/brain-coordinator.md`).
**Upgrading:** before pulling, write down which of the four services run (`compose ps`). After pulling:
- name those passes in `deploy/.env`, for example `OB1_PASSES=sleep,board-sync`, and drop `sleep`, `workers` and `board-sync` from any `COMPOSE_PROFILES`;
- run `compose up -d --remove-orphans`, which removes the old containers and starts the coordinator. An old `extract` or `consolidate` container left running keeps the scheduler down (exit 2, held), and an old `sleep` container would run a second scheduler beside the coordinator's.

What an operator's commands become:
- `--profile sleep up -d sleep`, `--profile workers up -d` and `--profile board-sync up -d` become `OB1_PASSES` in `deploy/.env` and `up -d coordinator`.
- `logs -f sleep` (or `extract`, `consolidate`, `board-sync`) becomes `logs -f coordinator`, each line marked with its pass, such as `[sleep]`.
- A one-off such as `--profile workers run --rm --no-deps extract bun db/extract-entities.ts --status` becomes `run --rm --no-deps coordinator bun db/extract-entities.ts --status`.
- `cp sleep:/var/lib/ob1/sleep-dumps <dir>` becomes `cp coordinator:/var/lib/ob1/sleep-dumps <dir>`.
- `stop sleep` and the like become `stop coordinator`, which stops every pass it runs.
- To drain a backlog with extraction alone, run `extract-entities.ts` once in the coordinator's container, and name `workers` afterwards.
- `deploy/canary.sh up` takes the canary's passes from its own file's `OB1_PASSES`, never stable's. The first run after the upgrade writes the passes its old containers were running there. board-sync needs both `board-sync` in that line and a Linear key of the canary's own.

## FORK

One coordinator runs the brain's core passes (SMD-3476; the first step of SMD-3215's record)

**What changed.**
- **`db/coordinator.ts`** (new) is the `coordinator` service's command.
  - It reads `OB1_PASSES` (`sleep`, `workers`, `board-sync`; commas or spaces) and runs each pass as a child through `db/supervise.ts`.
  - `workers` is two children, `extract` and `consolidate`. With `sleep` named too they are left out, and the log says so.
  - A name that is no pass is left out and said; the rest run. With none named it runs nothing and waits for its stop.
  - Running as root, it runs each child as its own user: board-sync 1101, extract 1102, consolidate 1103, sleep 1104. Each gets a HOME of its own and only its own settings: the shared environment, minus every setting another child owns and the coordinator's own (`OB1_PASSES`, `PORT`).
  - It hands the dump volume to sleep's user, but only beneath `/var/lib/ob1/`.
  - Each child's output is marked `[<name>] `. A stop goes on to every child.
- **`db/supervise.ts`** is now a library.
  - It takes an argv with no shell (`cmd`), a `uid` and `gid`, and a `label` for its output lines.
  - Its CLI is gone. The compose file's `sh -c` command lines are now `CHILDREN`'s `args` in `db/coordinator.ts`, each a fixed argv built from settings the digits guard has checked.
  - Children start with `--no-env-file`, so the coordinator alone decides their environment.
- **`deploy/compose.yaml`:**
  - The four services and three profiles are replaced by `coordinator`, a default service on `data` and `egress` with the checkout's two read-only mounts and the `sleep-dumps` volume.
  - It runs under an init, `unless-stopped`, with a 120 s grace.
  - It drops every capability except `CHOWN`, `SETUID`, `SETGID` and `KILL`, with `no-new-privileges`.
  - Its environment is the server's anchor, every pass's settings, and `OB1_PASSES`.
- **Advice:** preflight's `workers` and `sleep` rows, `restartCommand` and `startRefusalRemedy` (`db/config.mjs`), and the scheduler's refusal about followers outside it (`db/sleep.ts`) now name the coordinator. "Start it again" is `up -d --force-recreate coordinator` with the pass in `OB1_PASSES`, which works whether the coordinator runs or not. A held pass's fix recreates the coordinator.
- **`deploy/canary.sh`:**
  - Before the change it stops the canary's coordinator, and stops and removes any container of the four retired services.
  - After the smoke it recreates the coordinator with the canary file's `OB1_PASSES` (in `CANARY_DROPPED`, never copied from stable's), leaving out `board-sync` when the canary has no Linear key of its own.
  - `canary_compose` always sets `OB1_PASSES`, so a value exported in the shell never reaches the canary.
  - The first run after the upgrade writes the passes the retired containers ran into the canary's file.
  - `down` names no profile.
- **Check 28** holds the coordinator's mounts, networks and confinement. **Check 32** holds it `unless-stopped`; `supervisorGapsIn` now holds that no service's command names a db/ follower and that the coordinator's command is exactly `bun db/coordinator.ts`, with seven probes.
- **Tests:**
  - **`db/test-coordinator.ts`** (new, no database):
    - what `OB1_PASSES` runs, each child's settings and its command line;
    - that compose's coordinator is handed every setting a child owns, and nothing unaccounted for;
    - as root, a planted pair: one child cannot read another's `/proc/<pid>/environ`, and the same reader gets the secret with the users dropped.
  - **CI:** it runs on the host, and as root in the coordinator's own container. The held-refusal steps run the coordinator with `OB1_PASSES`, add the exclusion case and an unknown name, and check that sleep's user can write the dump volume.
  - **test-live [37b]:** supervise's argv and its label are covered, and the CLI cases are now the coordinator's.

**Verify.**
- On the canary, after a podman machine restart, the coordinator and every pass it should run come back with no one starting them.
- With both `sleep` and `workers` named, it runs `sleep` and says so; nothing is refused (CI covers it too).
- Each child cannot read another's `/proc/<pid>/environ` (`db/test-coordinator.ts --require-root`, in CI).
- The status route, and board-sync's interval as a coordinator trigger, are SMD-3476's later PRs.
