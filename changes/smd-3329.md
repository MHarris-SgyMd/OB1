## Changelog

A vendored server on compat/supabase-sql left running across a migration that adds a column no longer fails each `rpc()`, `.select("*")` or `RETURNING *` over it with "cached plan must not change result type" until it restarts: the shim names the columns it reads, from its catalog (SMD-3329).

## FORK

The compat shim names the columns it reads — a vendored server survives a migration that widens a table or a function (SMD-3329)

**What changed.** `compat/supabase-sql/index.ts` never sends a `*` it can name.
- **A table's `*`** — `.select("*")`, a bare `.select()`, a write's `RETURNING` — is spelled out from the catalog's map, every table's (an array-bearing table's alone since SMD-1602). `pg_class.relnatts` rides beside the rows, as it already did there, so the call after a column is added has it.
- **`.rpc()`** names the columns the function declares: `RETURNS TABLE`, OUT parameters, or the table of `RETURNS SETOF <table>`. A scalar, and overloads that disagree on their shape, are read as before: a scalar's result type is the function's whichever way it is spelled.
- **A 42703 that Postgres places inside the shim's own list** reads the catalog again and runs the call once more, so the caller sees no error. That is a column dropped, or an OUT column renamed; before, a dropped column on a spelled-out star cost one failed call.
  - The place is the error's `position`, the character it points at in the statement, which the shim compares with where it wrote its list. That works whatever language the server's messages are in. A `SQL_ASCII` server counts bytes, so on a statement with a character outside ASCII the shim asks the server's encoding, once per URL.
  - Anywhere else, the 42703 is the caller's, answered once with no re-read, as before: a filter's column, a payload key, an update's `SET`, a column inside an embed, the count query of a page past the end.
  - One raised inside a function body or a trigger carries no `position`, so it is never retried. The statement that raised it may have advanced a sequence.
  - Postgres refuses a column it cannot find before it executes anything, so the call it runs again had done nothing.
- **A changed plan under an `.rpc()` that read `*`** forgets the function and calls once more. A function the catalog read as a scalar, then made again with columns, is then called by name.
  - Only the plan cache's own refusal counts, told by the error's routine (`RevalidateCachedQuery`), which no language changes. A 0A000 that a running body raised, an inlined SQL function's included, is never retried.
  - When the fresh read spells the same statement, the first error is answered without running it again: Bun keeps the failing statement under its text.
  - A named call meeting a changed plan is an OUT column retyped, which no fresh read mends, and is not retried.
- **Names read from the catalog are quoted as Postgres quotes them** (`"my col"`, `"naïve"`, `"q""uote"`), where ident() refuses all but plain ones. A spelled-out star names every column a table has, and before, such a name threw on an array-bearing table's `*`. A caller's own list keeps ident()'s rule. A function with an unnamed OUT parameter (`OUT int`) has no name to project, so it reads `*` as before.
- **An embed's `(*)` stays a star.** Its rows reach the caller as one json column, whose type a new column does not change.
- The shim's README and header, and db/README's 110 paragraph, say so.

**Why.** SMD-3302 named the columns in the brain's own reads and added check 41, which cannot see SQL the shim builds at run time. Bun prepares each statement and keeps it. A migration that widens a table, or drops a function and makes it again with one more OUT column, makes a prepared `*` re-analyse to a different result type, and Postgres refuses the cached plan (0A000) on every call until the process restarts; a named list re-analyses to the one it had. SMD-3302's pass 1 probed this through the shim. Measured again here, on unchanged code: after the migration, `rpc()` of a `RETURNS TABLE` function, `.select("*")`, a bare `.select()` and `RETURNING *` each failed 0A000 on the same client. The embed's `(*)` answered. `integrations/agent-memory-api` and `integrations/smart-ingest` call `rpc("match_thoughts")`. Under `extensions/`, `integrations/` and `recipes/`, 35 calls read `.select("*")` and 26 a bare `.select()`.

**Held.**
- **test-compat [22]**, the ticket's Verify. One client on one connection reads through `rpc()` of a `RETURNS TABLE` function, `rpc()` of a `RETURNS SETOF <table>` one, `.select("*")`, a bare `.select()`, `update().select("*")` and an embed's `(*)`. Each read binds a parameter, since Bun prepares only a statement that has one. Then the function is dropped and made again with one more OUT column, and both tables gain a column. Every read answers again on the same client, and the table's new column arrives on the next call. On main, the `RETURNS TABLE` read, `.select("*")`, the bare `.select()` and `RETURNING *` fail 0A000. The `SETOF` read answers on main too, since its plan holds no reference to the table a migration widens, so it guards against a regression only, as the embed's does.
  - A scalar function made again with columns answers with its rows. A scalar whose type changed, and a named call whose OUT column was retyped, are one statement a call.
  - Then a column is dropped and an OUT column renamed, the first in the list as well as a later one: the next calls answer, with the new name.
  - An insert whose `RETURNING *` names a dropped column answers and writes its row once.
  - Five calls naming a column the table lacks are five 42703s, at most one catalog read and five queries each, for a filter, an insert's key, an update's `SET` and an embed's column. The same holds for a filter after 45 characters outside the BMP in the list's column names, where Postgres counts characters and JavaScript code units.
  - A 42703 from a function body and from a trigger, and a 0A000 from a plpgsql body and from two inlined SQL bodies, each run once: the sequence each advances ends at 5, not 10. The second inlined body is called with an argument its first read lacked, so its statement was never prepared and its fresh read would spell a new one.
  - A count query that fails 42703 on a page past the end leaves the page run once.
  - On a `SQL_ASCII` database, a column dropped after four columns named outside ASCII is recovered on the next call, and a filter on a missing column after them is one query a call.
  - A `*` over columns named with a space, a non-ASCII letter and a quote answers, as do a function with an unnamed OUT parameter and one whose OUT columns have such names.
- [17]'s embed SQL, [18] and [19] now pin the spelled-out star on a table without an array column, and a dropped column answered on the first call.
- **Mutants:** 26, of which test-compat fails 24:
  - the table's star back to `*` and `rpc()`'s projection back to `*`, the Verify's drop-the-mechanism mutants, each fail [22] with 0A000;
  - either retry removed, or the catalog not forgotten before it, or `rpc()`'s changed-plan retry removed;
  - the error's place ignored or never in the list, characters read as code units, the select list's place, a write's list's or `rpc()`'s shifted, `rpc()`'s list left unplaced, the count query left with the page's places;
  - bytes never read, or always, or two to a character;
  - the routine check dropped, named calls retried, the same statement run again;
  - the attribute count left off;
  - catalog names quoted through ident(), or the unnamed-OUT fallback removed.
  - Two are equivalent. Dropping the check that the error is a 42703: the list holds column references, `to_json()` calls and a constant subquery, and no other error Postgres raises points into one (a column privilege's 42501 carries no place, and a type error needs an operator). Dropping the ASCII shortcut before the encoding is asked: it saves one query per URL, whose answer is kept.

**Measured after.** 3,000 `.select("*").eq("id", k)` calls on one connection, over a ten-column table with no array column, alternating the two shims: 740 and 596 ms before, 614 and 603 ms after. That is about 0.2 ms a call either way, with the attribute count's subquery and the longer text no cost that shows. A column retyped under the same client still failed 0A000 on three calls in a row.

**Not taken.**
- **A catalog read per call.** The ticket asked whether to read the shape on every call. The shim re-reads on the evidence instead: a table's attribute count, a column the caller names that the map lacks, and a 42703 on the shim's own column. That costs nothing on the calls where nothing changed.
- **Seeing a function's new OUT column before a restart.** The code that reads a new column ships in a new process. Catching it sooner would mean carrying the function's identity beside every row, for a column no running caller's code was written to read.
- **Retrying a table's 0A000.** It still comes from a column retyped under a running client, or dropped and added again with another type. Bun keeps the failed statement under the same text, so a retry fails the same way. CLAUDE.md lets a migration add a column to `thoughts`, never alter one.
- **Reading the column off the 42703's message.** The first commit did, and review pass 1 found a payload key's message (`column "x" of relation "t" does not exist`) unread, an embed's qualifier dropped, and a function body's column taken for an OUT column. The `position` has none of these problems, and is the same in every language.
- **Working round Bun on a LATIN1 database.** Review pass 2 found Bun 1.4.3 failing a prepared statement that names a column outside ASCII of certain byte lengths (22P05, `0xef 0xbf 0xbd`; 61 bytes fails, 62 answers); the same text unprepared runs, and a UTF8 database is unaffected. Spelling `*` out reaches it where `*` did not. The brain's Postgres is UTF8; SMD-3349 pins the bug down and decides whether a non-UTF8 database is refused.
- **Closing this by SMD-3216's retirement of the shim.** It waits on five tickets, the REST-core ports SMD-2311 and SMD-2690 among them, and 19 vendored files still import the shim.

**Follow-ups.**
- **SMD-3349:** Bun 1.4.3 fails some prepared statements on a non-UTF8 database (22P05 on non-ASCII text of certain byte lengths, literals as well as names), and nothing refuses a non-UTF8 brain.
