## Changelog

The release rehearsal runs with a token that can only read: a pull request or a dispatch runs it as a job of its own, and only a tag push runs the job that can push images and create a release. Both jobs call one copy of the steps, `.github/workflows/release-steps.yml`. The consistency checker now refuses a workflow job that grants a write unless it runs only on a push of a named branch or a tag (SMD-2111).

## FORK

The release rehearsal on a read-only token — only a tag's run can publish (SMD-2111)

**What changed.**
- **`.github/workflows/release.yml` keeps the triggers, the concurrency group and two jobs:**
  - **`rehearsal`** runs when the event isn't a push (a pull request, or a dispatch), with `contents: read` and nothing else.
  - **`release`** runs on a push of a `v` tag, with `contents: write` and `packages: write`, as the one job did.
  - Each calls `.github/workflows/release-steps.yml`, the first with `publish: false`, the second with `publish: true`.
- **`.github/workflows/release-steps.yml` holds the steps once,** moved unchanged from the old job. It triggers on `workflow_call` alone, and declares no `permissions:`, so each call runs with its caller's token.
  - `PUBLISH` is the caller's `publish` input, where it was computed from the event. A `publish: true` from anything but a tag push would be refused by the facts step, since the ref name is then not the last release's `v<X.Y.Z>`.
  - The job is named "Images, stack from them, notes", so the checks read "Rehearsal / …" and "Release / …". No ruleset or check depends on the old name, "Release (images, stack from them, notes)"; check 20's probes keep it as a sample name.
  - The rehearsal also runs, and builds both platforms, when a pull request changes `release-steps.yml`.
- **Check 23 holds the split,** with `workflowPermissionProblems`:
  - a workflow with a `workflow_call` trigger has no other trigger, and declares no `permissions:`, top-level or on a job;
  - any other workflow sets a top-level `permissions:` (a map, `read-all` or `{}`) that grants no write;
  - a job that grants a write (`write-all`, or `write` on any scope) has an `if:` whose top-level `&&` terms include `github.event_name == 'push'` and a ref Dependabot's push can't meet: `github.ref == 'refs/heads/<branch>'` for a branch not Dependabot's (`dependabot/…`, `dependabot-…` or `dependabot_…`, in any case), `github.ref == 'refs/tags/<tag>'`, or `startsWith(github.ref, 'refs/tags/…')`;
  - a condition GitHub would read as an always-true string template refuses: a `${{` anywhere but one `${{ … }}` around all of it, or a `}}` outside a string. So does a top-level `||`;
  - a control runs the rules on the real `release.yml` with its release job cut to the push term alone, and expects the refusal.
- **Comments and docs that named the old shape now name the new one:** FORK.md's paragraph on the pins, deploy/README.md's release lines, two comments in `fork-checks.yml`, and the checker's messages and docblocks that name the file holding the steps.

**Why.** The one job held `contents: write` and `packages: write` on every run, and a rehearsal publishes nothing. It ran on any pull request touching what it builds from. Dependabot's weekly action bumps edit the release workflow's pins, so every such pull request ran the new action, handed the job's token by default (`build-push-action`'s `github-token`, `setup-bun`'s `token`), before anyone had read it. So did any pull request that bumped or added an action there, a maintainer's included.

**Why each rule.**
- **No `permissions:` in a called workflow, and no second trigger.** What a called workflow declares can only narrow its caller's token, never widen it. A `permissions: contents: read` added to `release-steps.yml` would narrow the release job's too, and a tag's run would fail at its first push to GHCR, which no rehearsal reaches. A second trigger would need a top-level `permissions:` for its own runs, which narrows the callers the same way.
- **A ref as well as a push.** Dependabot pushes its own branch, which is a push event. GitHub gives that run a read-only token, but a `permissions:` key raises it. GitHub compares strings case-blind, so the exclusion reads any case. Both write jobs today already pin a ref: the release job a `v` tag, and fork-checks' `publish-test-counts` job `refs/heads/main`.
- **No template.** An `if:` with text beside a `${{ }}` is a string template, and a non-empty string is true. Unwrapped, GitHub reads quotes only inside a `${{ }}`, so a `${{` in a quoted string starts one too. actionlint's `if:` check flags the plain cases as well.

**Held.**
- **The old `release.yml` fails check 23,** as `job release grants contents: write, packages: write, and its if: (none) does not hold it to a push of a named branch or a tag`.
- **The rules' own probes:** 12 workflows they pass and 36 they refuse, each with one problem. For each refused probe, the one defect its label names is what refuses it.
- **36 mutants each fail the checker,** with the tree otherwise unchanged:
  - **31 of the rule:**
    - `holdsToNamedPush` always true;
    - no ref term needed, and no push term needed;
    - any event name accepted;
    - either regex unanchored;
    - a ref by `!=`, or from any context;
    - the Dependabot exclusion dropped, case-sensitive, or reading `/` alone;
    - each template test dropped, reading strings, or skipping them unwrapped;
    - the whole wrap not stripped, or not anchored at its end;
    - no `||` check;
    - strings not skipped, or an unterminated one read as closed;
    - unbalanced parentheses read as balanced;
    - no unwrapping, or unwrapping once;
    - a string `on` not read;
    - each of the six problems off: a second trigger, a called workflow's top-level and job `permissions:`, and a missing, unreadable or writing top-level `permissions:`;
    - `write-all` not read.
  - **5 of the workflows:**
    - the old `release.yml`;
    - the release job's `if:` dropped;
    - its `if:` cut to the push term;
    - `release-steps.yml` with a top-level `permissions: contents: read`;
    - `release-steps.yml` with `workflow_dispatch` beside `workflow_call`.
- **actionlint 1.7.7** passes, and reads the call: a misspelled `publish` input fails it.
- **zizmor 1.32.0**, at its default persona, finds nothing new but two help-level `self-repository` notes (below). Its error on `ci-shift.yml`'s `workflow_run` is on main too.

**Not taken.**
- **zizmor's `$/` self-repository form,** which GitHub now recommends for a reusable workflow in the same repository. With no ref, `$/` and `./` both read the called file from the caller's commit, so the two are the same here. actionlint 1.7.7 and check 23 know only `./`.
- **zizmor's pedantic `excessive-permissions` warning** on `release-steps.yml`, for having no `permissions:`. Not having one is the point: see the first rule.
- **The forms GitHub would also accept:** `'PUSH'` (it compares case-blind), `'push' == github.event_name`, and an `||` group of safe refs such as `main` or a tag. Check 23 refuses them, and its message gives the form to write.
- **Another bot's branch** (renovate's, say), or a bot holding a token that can push main or a tag. Neither exists here: Dependabot is the one bot configured, and it pushes no tags.
