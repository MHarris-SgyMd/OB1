## Changelog

The release rehearsal runs with a token that can only read: a pull request or a dispatch runs it as a job of its own, and only a tag push runs the job that can push images and create a release. Both jobs call one copy of the steps, `.github/workflows/release-steps.yml`. The consistency checker now refuses a workflow job that grants a write and can run on anything but a push (SMD-2111).

## FORK

The release rehearsal reads, and only a tag's run can publish (SMD-2111)

**What changed.**
- **`.github/workflows/release.yml` keeps the triggers, the concurrency group and two jobs:**
  - **`rehearsal`** runs when the event isn't a push (a pull request, or a dispatch), with `contents: read` and nothing else.
  - **`release`** runs on a push of a `v` tag, with `contents: write` and `packages: write`, as the one job did.
  - Each calls `.github/workflows/release-steps.yml`, the first with `publish: false`, the second with `publish: true`.
- **`.github/workflows/release-steps.yml` holds the steps once,** moved unchanged from the old job. It triggers on `workflow_call` alone, and declares no `permissions:`, so each call runs with its caller's token.
  - `PUBLISH` is the caller's `publish` input, where it was computed from the event. A `publish: true` on a ref that isn't a tag is still refused by the facts step, as before.
  - The job is named "Images, stack from them, notes", so the checks read "Rehearsal / …" and "Release / …". No ruleset or script names the old "Release (images, stack from them, notes)".
  - The rehearsal also runs, and builds both platforms, when a pull request changes `release-steps.yml`.
- **Check 23 holds the split,** with `workflowPermissionProblems`:
  - a workflow with any trigger but `workflow_call` sets a top-level `permissions:` that grants no write;
  - a job that grants a write (`write-all`, or `write` on any scope) has an `if:` with `github.event_name == 'push'` as one of its top-level `&&` terms, and no top-level `||`;
  - a workflow whose only trigger is `workflow_call` declares no `permissions:`, top-level or on a job.
- Two comments in `fork-checks.yml`, and check 23's docblock, now name `release-steps.yml` where they name the file holding the release's steps.

**Why.** The one job held `contents: write` and `packages: write` on every run, and a rehearsal publishes nothing. Dependabot's weekly action bumps edit the release workflow's pins, so every such pull request ran the new action, handed the job's token by default (`build-push-action`'s `github-token`, `setup-bun`'s `token`), before anyone had read it. A maintainer's own pull request had the same exposure.

**Why the third rule.** A called workflow's token can only be narrowed by what it declares. A `permissions: contents: read` added to `release-steps.yml` as a tidy-up would narrow the release job's too, and a tag's run would fail at its first push to GHCR. No rehearsal reaches that push, so the first sign would be a failed release.

**Held.**
- **The old `release.yml` fails check 23,** as `job release grants contents: write, packages: write, and its if: (none) does not hold it to a push`. So do the new one with the release job's `if:` dropped, and `release-steps.yml` with a top-level `permissions: contents: read`.
- **The rule's own probes:** 9 workflows it passes and 15 it refuses, each with one problem.
- **Ten mutants of the rule each fail the checker:** `holdsToPush` always true, no `||` check, strings not skipped, unbalanced parentheses read as balanced, no unwrapping of parentheses, the called-alone rule off, the missing-top-level rule off, and the three workflow mutants above. The `||` mutant passed until the probe for `github.event_name == 'push' && a || b` was added.
- **actionlint 1.7.7** passes, and reads the call: a misspelled `publish` input fails it.
- **zizmor 1.32.0** finds nothing new at its default persona but two help-level `self-repository` notes (below). Its error on `ci-shift.yml`'s `workflow_run` is main's too.

**Not taken.**
- **zizmor's `$/` self-repository form,** from GitHub's July 2026 change, for the two `uses: ./.github/workflows/release-steps.yml`. It guards a local action against files changed at run time. A job-level reusable workflow is read from the run's commit before any step runs, so `./` carries no such risk. actionlint 1.7.7 and check 23 know only `./`.
- **zizmor's pedantic `excessive-permissions` warning** on `release-steps.yml`, for having no `permissions:`. Not having one is the point: see the third rule.
