## Changelog

The release rehearsal runs with a token that can only read: a pull request or a dispatch runs it as a job of its own, and only a tag push runs the job that can push images and create a release. Both jobs call one copy of the steps, `.github/workflows/release-steps.yml`. The consistency checker now refuses a workflow job that grants a write unless it runs only on a push of a named branch or a tag (SMD-2111).

## FORK

The release rehearsal reads, and only a tag's run can publish (SMD-2111)

**What changed.**
- **`.github/workflows/release.yml` keeps the triggers, the concurrency group and two jobs:**
  - **`rehearsal`** runs when the event isn't a push (a pull request, or a dispatch), with `contents: read` and nothing else.
  - **`release`** runs on a push of a `v` tag, with `contents: write` and `packages: write`, as the one job did.
  - Each calls `.github/workflows/release-steps.yml`, the first with `publish: false`, the second with `publish: true`.
- **`.github/workflows/release-steps.yml` holds the steps once,** moved unchanged from the old job. It triggers on `workflow_call` alone, and declares no `permissions:`, so each call runs with its caller's token.
  - `PUBLISH` is the caller's `publish` input, where it was computed from the event. A `publish: true` on a ref that isn't a tag would be refused by the facts step, since `--tag <ref_name>` is then not `v<MAJOR.MINOR.PATCH>`.
  - The job is named "Images, stack from them, notes", so the checks read "Rehearsal / …" and "Release / …". No ruleset or check depends on the old name, "Release (images, stack from them, notes)"; check 20's probes keep it as a sample name.
  - The rehearsal also runs, and builds both platforms, when a pull request changes `release-steps.yml`.
- **Check 23 holds the split,** with `workflowPermissionProblems`:
  - a workflow with a `workflow_call` trigger has no other trigger, and declares no `permissions:`, top-level or on a job;
  - any other workflow sets a top-level `permissions:` (a map, `read-all` or `{}`) that grants no write;
  - a job that grants a write (`write-all`, or `write` on any scope) has an `if:` whose top-level `&&` terms include `github.event_name == 'push'` and a ref no bot's push meets: `github.ref == 'refs/heads/<branch>'` for a branch other than `dependabot/…`, `github.ref == 'refs/tags/<tag>'`, or `startsWith(github.ref, 'refs/tags/…')`. A top-level `||`, or a `${{ }}` that wraps only part of the condition, refuses it.
- **Comments and docs that named the old shape now name the new one:** FORK.md's paragraph on the pins, deploy/README.md's release lines, two comments in `fork-checks.yml`, and the checker's messages and docblocks that name the file holding the steps.

**Why.** The one job held `contents: write` and `packages: write` on every run, and a rehearsal publishes nothing. Dependabot's weekly action bumps edit the release workflow's pins, so every such pull request ran the new action, handed the job's token by default (`build-push-action`'s `github-token`, `setup-bun`'s `token`), before anyone had read it. A maintainer's own pull request had the same exposure.

**Why each rule.**
- **No `permissions:` in a called workflow, and no second trigger.** A called workflow's token can only be narrowed by what it declares. A `permissions: contents: read` added to `release-steps.yml` would narrow the release job's too, and a tag's run would fail at its first push to GHCR, which no rehearsal reaches. A second trigger would need a top-level `permissions:` for its own runs, which narrows the callers the same way.
- **A ref as well as a push.** Dependabot pushes its own `dependabot/…` branch, which is a push event. GitHub gives that run a read-only token, but a `permissions:` key raises it. Both write jobs today already pin a ref: the release job a `v` tag, fork-checks' publish job `refs/heads/main`.
- **No partial `${{ }}`.** GitHub reads an `if:` with text outside a `${{ }}` as a string template, which is always true.

**Held.**
- **The old `release.yml` fails check 23,** as `job release grants contents: write, packages: write, and its if: (none) does not hold it to a push of a named branch or a tag`.
- **The rule's own probes:** 9 workflows it passes and 23 it refuses, each with one problem.
- **23 mutants each fail the checker,** with the commit's tree otherwise unchanged:
  - **18 of the rule:** the hold always true; no ref term needed; no push term needed; Dependabot's branch allowed; no partial-wrap check; no whole-wrap strip; strings read for `${{`; no `||` check; strings not skipped; unbalanced parentheses read as balanced; no unwrapping; each of the six problems off (a second trigger, a called workflow's top-level and job `permissions:`, a missing, unreadable or writing top-level `permissions:`); and `write-all` not read.
  - **5 of the workflows:** the old `release.yml`; the release job's `if:` dropped; its `if:` cut to the push term; `release-steps.yml` with a top-level `permissions: contents: read`; and `release-steps.yml` with `workflow_dispatch` beside `workflow_call`.
- **actionlint 1.7.7** passes, and reads the call: a misspelled `publish` input fails it.
- **zizmor 1.32.0**, at its default persona, finds nothing new but two help-level `self-repository` notes (below). Its error on `ci-shift.yml`'s `workflow_run` is on main too.

**Not taken.**
- **zizmor's `$/` self-repository form,** from GitHub's July 2026 change, for the two `uses: ./.github/workflows/release-steps.yml`. It guards a local action against files changed at run time. GitHub reads a reusable workflow named by `./` from the caller's commit, so `./` carries no such risk here. actionlint 1.7.7 and check 23 know only `./`.
- **zizmor's pedantic `excessive-permissions` warning** on `release-steps.yml`, for having no `permissions:`. Not having one is the point: see the first rule.
- **The case-blind forms GitHub would accept,** `'PUSH'` or `'push' == github.event_name`. Check 23 refuses them, and the house form is lower case with the context on the left.
