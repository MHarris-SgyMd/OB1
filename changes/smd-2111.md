## Changelog

The release rehearsal runs with a token that can only read: a pull request or a dispatch runs it as a job of its own, and only a tag push runs the job that can push images and create a release. Both jobs call one copy of the steps, `.github/workflows/release-steps.yml` (SMD-2111).

## FORK

The release rehearsal on a read-only token — only a tag's run can publish (SMD-2111)

**What changed.**
- **`.github/workflows/release.yml` keeps the triggers, the concurrency group and two jobs:**
  - **`rehearsal`** runs when the event isn't a push (a pull request, or a dispatch), with `contents: read` and nothing else.
  - **`release`** runs on a push of a `v` tag, with `contents: write` and `packages: write`, as the one job did.
  - Each calls `.github/workflows/release-steps.yml`, the first with `publish: false`, the second with `publish: true`.
- **`.github/workflows/release-steps.yml` holds the steps once,** moved unchanged from the old job. It triggers on `workflow_call` alone, and declares no `permissions:`, so each call runs with its caller's token. What a called workflow declares can only narrow its caller's token: a `permissions:` there is a ceiling on both callers, and anything short of the release job's two writes fails a tag's first push to GHCR, which no rehearsal reaches. Its header says so.
  - `PUBLISH` is the caller's `publish` input, where it was computed from the event. A `publish: true` on any ref whose name isn't the last release's `v<X.Y.Z>` would be refused by the facts step.
  - The job is named "Images, stack from them, notes", so the checks read "Rehearsal / …" and "Release / …". No ruleset or check depends on the old name, "Release (images, stack from them, notes)"; check 20's probes keep it as a sample name.
  - The rehearsal also runs, and builds both platforms, when a pull request changes `release-steps.yml`.
- **Comments and docs that named the old shape now name the new one:** release.yml's header, FORK.md's paragraph on the pins, deploy/README.md's release lines, two comments in `fork-checks.yml`, and four of the checker's comments and messages that name the file holding the steps.

**Why.** The one job held `contents: write` and `packages: write` on every run, and a rehearsal publishes nothing. It ran on any pull request touching what it builds from. Dependabot's weekly action bumps edit the release workflow's pins, so every such pull request ran the new action, handed the job's token by default (`build-push-action`'s `github-token`, `setup-bun`'s `token`), before anyone had read it. GitHub gives a Dependabot run a read-only token, but the job's `permissions:` raised it. So did any pull request that bumped or added an action there, a maintainer's included.

**Held.** Nothing in CI holds the split yet (SMD-3751, below). What was checked:
- **GitHub's documented behaviour, read by the reviews:**
  - a called workflow's token is its calling job's, and can only be narrowed there;
  - it can read `secrets.GITHUB_TOKEN` without `secrets: inherit`, as the login and `gh release create` do;
  - the `github` context is the caller's, so the event, the ref and the commit the steps read are unchanged;
  - a `./` workflow is read from the caller's commit.
- **The steps are the old job's,** by diff: only the job's name and permissions, `PUBLISH`'s source, and `release-steps.yml` in the both-platforms list differ.
- **actionlint 1.7.7** passes, and reads the call: a misspelled `publish` input fails it.
- **zizmor 1.32.0**, at its default persona, finds nothing new but two help-level `self-repository` notes (below). Its error on `ci-shift.yml`'s `workflow_run` is on main too.

**Review passes.** Four passes found nothing in the split that would break a rehearsal or a tag's publish; each corrected comments and this note. Passes 1–3 also reviewed a rule for check 23 that would hold the split. It went beyond the ticket's Work and was dropped at the maintainer's call.

**Not taken.**
- **zizmor's `$/` self-repository form** (GitHub's July 2026 syntax) for the two `uses: ./.github/workflows/release-steps.yml`. With no ref, `$/` and `./` both read the called file from the caller's commit, so the two are the same here. actionlint 1.7.7 and check 23 know only `./`.
- **zizmor's pedantic `excessive-permissions` warning** on `release-steps.yml`, for having no `permissions:`. Not having one is the point.

**Follow-ups.** SMD-3751: nothing in check-fork-consistency holds the split. A job that grants a write on a pull request's run, a `permissions:` on `release-steps.yml`, or a second trigger on it all pass. The ticket holds the dropped rule's last form (commit bc7f0d1c), what the passes found in it, and an exact-form whitelist to weigh.
