## Changelog

The agenda takes an order (SMD-4192, migration 129). `priority`, the default, ranks as before. `due` lists the items with a due time first, soonest first, so the longest overdue leads, then the undated ones by priority, for a question about deadlines. It is `order` on the MCP `agenda` tool and `GET /v1/agenda`, and the answer says which order was applied.

## Record

The agenda takes the question: a `due` order beside `priority`, chosen by the client, and SMD-3662's what-matters eval measures it as `agenda_question`, the first read to clear its pre-registered bar (SMD-4192)

**Why.** SMD-3662's bar asks a priority read for top-1 on 5 of its 7 prompts. The gold's first item is the Urgent ticket on four of them, and a due or promised item on the other three. A read with one order puts the same item first whatever is asked, so the agenda could never pass; under level first it reached 3 of 7.

**What changed.** The maintainer chose, on 2026-11-10, that the agenda takes the question. The other options were judging it on the "what next" prompts alone, changing the bar for every read, or recording that it can't pass. They also chose that the read lists the agenda's own items, that a keyword rule stands in for the client in the eval, and that the due order puts due time first, then priority. The rule was posted on the ticket before any build or run.
- **Migration 129** replaces 126's agenda with a ten-argument form, its tenth `p_order` (`priority` or `due`; anything else refused 22023), no argument defaulted. The nine-argument agenda becomes a SQL wrapper with 126's defaults that calls it with `priority`. So a nine-argument call, as a server before 129 makes, names one function and gets the priority order, and re-applying 124 or 126 after 129 replaces only the wrapper and that file's comments. Under `due` a stated None counts as undated (the maintainer's amendment, review pass 3). The order is applied before the limit, and the answer carries `order`. `query_log.filter`'s comment names the order an agenda row logs. Every filter and term is 126's.
- **The server** passes `order` through the store, REST and MCP. The priority order is still the nine-argument call, so it reads a brain before 129; `due` on one is refused `ORDER_UNAVAILABLE` (503 over REST), saying the migration. The store checks that the order answered is the one asked. The text says "soonest due first, the undated after" in place of "most pressing first". The logged filter carries the order.
- **The eval** adds `agenda_question`: `DUE_WORDS` picks the order from the query's words, and the read lists the agenda's items as thoughts, each ticket as its head thought and each open item as its origin. A measured read that errors on every prompt now fails the run.

**Measured** once the harness worked, at registration `acb196be7ec50868`: top-1 5 of 7, top-3 6 of 7, mean tau 0.766, so it clears the bar. The ticket predicted the five prompts it wins before the run. A pass shows the design fits these prompts; it doesn't show the keyword rule generalises, since it was written with these queries in view.

Two runs before measured nothing. The first handed the read a closed SQL client; the second bound its keys as a JS array, which Bun sends to `::text[]` as one string. Each scored 0 of 7, with every prompt an error. The rule did not change between the runs. `evals/README.md` records all three.

**Not taken.**
- **A `promised` order or scope.** No order of priority or due time puts the commitment first, and the ticket's decision covers the order alone.
- **Re-sorting the agenda's top items in the server.** The limit would keep the top by priority, and `due` would miss a dated item below it.
- **Logging `order` only when it is not the default** (review pass 2). 124's `include_started` logs its default too, and a row says what was asked.
- **`ob1_ticket_heads_of` and uuid keys in the eval's lookups** (review pass 2), **and one round trip for both** (review pass 3). The read was measured as written; a change to it is a new measurement.
- **Failing a run whose measured read errors on some prompts** (review pass 3). The bar's registered edge case scores such a prompt false, false, 0; the run fails only when nothing was measured.
- **One due key in place of two** (review pass 3). The order would be the same, and the measured function's text would move.
