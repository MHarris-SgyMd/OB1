## FORK

The full-stack job builds the three dashboards in the background while the stack comes up, not in series after it (SMD-2251)

**What changed.** `.github/workflows/fork-checks.yml`'s job `deploy-stack` gains a step right after `setup-bun`, "The three dashboards start building, in the background". It starts one background subshell that installs and builds the three dashboards one after another, in the old step's order (and `bun run check`s the SvelteKit one). It ends at once.
- **Each dashboard** writes its own log and a line of exit code and seconds under `$RUNNER_TEMP/dashboards`, and has its own limit, 240 s (`timeout --kill-after=10s`, which TERMs the build's process group; its KILL follows only while its own child lives, so a process that ignores TERM outlives the limit and dies with the job). The limit is written there too, for the wait step's labels and cap. A hang ends as 124, and the next dashboard still builds; a 137 is a KILL from outside, as by the OOM killer. When all three have run, the subshell writes a done mark.
- **The subshell outlives its step.** Its output goes to files, so the step does not wait on it (with the redirects dropped, a step behind a pipe waited out the build); its stdin is `/dev/null`. The provider stub in "Bring up the compose stack" lives across steps the same way.
- **"The three dashboards build"** stays where it was, just before the SvelteKit smoke, whose `vite preview` needs the build. It now waits: until the done mark, until the subshell dies without one, or a cap a minute past the three limits and their kill-after grace (810 s). It reads the subshell's state from `/proc`, not `kill -0`, which counts a dead shell nothing has reaped yet (a zombie) as alive. It prints how long it waited, then (when the build never finished) which dashboards did, then each dashboard's log (folded when it built, open under a `::error` naming the dashboard when it did not) and a line per dashboard of exit code and seconds. It fails when any dashboard failed or the build never finished. It runs when a stack step failed too (`!cancelled()` and the start step's success), so a stack failure no longer hides whether the dashboards build.
- **The build-time env** (`NEXT_PUBLIC_API_URL`, `SESSION_SECRET`) moves to the start step.

This is SMD-2092's and SMD-2219's shape for work run side by side (a log each, both printed, a limit each), across steps: the wait step cannot `wait` on a process another step's shell started, so it polls for the done mark and the subshell's pid.

**Why.** "Full stack, no Supabase" was the run's critical path at 148–157 s (run 36221013361), and 133–134 s after SMD-2250 (#205). Its steps ran in series, and "The three dashboards build" took 35 s at the end though it needs nothing from the stack: the two Next dashboards are built and never run, and the SvelteKit one's build is needed only by the last step. Most of the stack's time is waiting on health checks, Postgres start-up and stops, not CPU.

**Not taken.**
- **A `.rc` file with no trailing newline** ends the wait step under `-e` with no logs (review pass 1). `echo` always writes one, so only a truncated write reaches it.
- **The Kubernetes image's build in the background too** (7 s). Its stop step uses the image at once, so both would move, and a stack failure would then hide them unless they ran on `!cancelled()` too. With the dashboards off it, the job should end well inside "Schema against real Postgres" (135–136 s), so its 7 s would not shorten the run.
- **Dropping "Tear down".** It asserts nothing, but since SMD-2250 it takes 0–1 s.
- **Building the three dashboards at once.** In series they take 35 s against some 90 s before the smoke needs them, and one at a time competes least with the stack's own image builds.
