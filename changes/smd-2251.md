## Changelog

Fork Checks' "Full stack, no Supabase" job builds the three dashboards in the background from its start, while the compose stack and the canary come up, where it built them in series after the stack. "The three dashboards build" now waits for that build and reports each dashboard, and runs when a stack step failed too (SMD-2251).

## FORK

The full-stack job builds the three dashboards in the background while the stack comes up — their 35 s no longer adds to the job (SMD-2251)

**What changed.** `.github/workflows/fork-checks.yml`'s job `deploy-stack` gains a step right after `setup-bun`, "The three dashboards start building, in the background". It starts one background subshell that installs and builds the three dashboards one after another, the SvelteKit one first (and `bun run check`s it). It ends at once.
- **Each dashboard** writes its own log and a line of exit code and seconds under `$RUNNER_TEMP/dashboards`, and has its own 4-minute limit (`timeout --kill-after=10s`). A hang ends as 124 (137 when TERM is ignored), and the next dashboard still builds. When all three have run, the subshell writes a done mark.
- **The subshell outlives its step.** Its output goes to files and its stdin is `/dev/null`, so the step does not wait on it, and it ignores HUP as `nohup` would. The provider stub in "Bring up the compose stack" lives across steps the same way.
- **"The three dashboards build"** stays where it was, just before the SvelteKit smoke, whose `vite preview` needs the build. It now waits: until the done mark, until the subshell dies without one, or 15 minutes. It prints how long it waited, then each dashboard's log (folded when it built, open under a `::error` naming the dashboard when it did not) and a line per dashboard of exit code and seconds. It fails when any dashboard failed or the build never finished. It runs when a stack step failed too (`!cancelled()` and the start step's success), so a stack failure no longer hides whether the dashboards build.
- **The build-time env** (`NEXT_PUBLIC_API_URL`, `SESSION_SECRET`) moves to the start step.

This is SMD-2092's and SMD-2219's shape for work run side by side (a log each, both printed, a limit each), across steps: the wait step cannot `wait` on a process another step's shell started, so it polls for the done mark and the subshell's pid.

**Why.** "Full stack, no Supabase" was the run's critical path at 148–157 s (run 36221013361), and 133–134 s after SMD-2250 (#205). Its steps ran in series, and "The three dashboards build" took 35 s at the end though it needs nothing from the stack: the two Next dashboards are built and never run, and the SvelteKit one's build is needed only by the last step. Most of the stack's time is waiting on health checks, Postgres start-up and stops, not CPU.

**Held.** The two steps' `run:` blocks, read from the workflow and run in `oven/bun:1.4.0` (GNU `timeout`, four CPUs):

| Case | The wait step |
| --- | --- |
| As committed | the start step ends in 0 s; three built, exit 0 |
| A type error in `open-brain-dashboard-next`'s `app/page.tsx` | fails, `open-brain-dashboard-next failed (exit 1)` with next's `Type error: Type 'string' is not assignable to type 'number'`; the pro dashboard still built |
| `open-brain-dashboard-pro`'s build script is `sleep 600` | fails, `open-brain-dashboard-pro failed (exit 124, over the 4 min limit)` at 240 s, its log ending `$ sleep 600`; the two before it built |
| The background subshell killed (`kill -9`) 3 s in | fails 3 s later, `the background build did not finish`, with the logs so far |
| The 15-minute wait cut to 5 s | fails at 5 s, the same way |

Locally the builds are slow, 75–150 s each, nearly all of it `bun install` fetching packages through the container's network (138.77 s of the SvelteKit dashboard's 145 s); with four such runs at once one install passed the 4-minute limit. On CI the three took 35 s together, installs included.

**Not taken.**
- **The Kubernetes image's build in the background too** (7 s). Its stop step uses the image at once, so both would move, and a stack failure would then hide them unless they ran on `!cancelled()` too. With the dashboards off it, the job should end well inside "Schema against real Postgres" (135–136 s), so its 7 s would not shorten the run.
- **Dropping "Tear down".** It asserts nothing, but since SMD-2250 it takes 0–1 s.
- **Building the three dashboards at once.** In series they take 35 s against the some 90 s before the smoke needs them, and one at a time competes least with the stack's own image builds.
