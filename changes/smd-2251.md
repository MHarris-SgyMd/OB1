## FORK

The full-stack job builds the three dashboards in the background while the stack comes up, not in series after it (SMD-2251)

**What changed.** `.github/workflows/fork-checks.yml`'s job `deploy-stack` gains a step right after `setup-bun`, "The three dashboards start building, in the background". It starts one background subshell that installs and builds the three dashboards one after another in the old step's order, with the SvelteKit one's `bun run check` now right after its build rather than after all three. The step ends at once.
- **Each dashboard** writes its own log and a line of exit code and seconds under `$RUNNER_TEMP/dashboards`, and has a limit, 240 s (`timeout --kill-after=10s`), written there once for the wait step's labels and cap. A hang ends as 124, and the next dashboard still builds. When all three have run, the subshell writes a done mark.
  - timeout TERMs the build's process group, and its KILL follows only while its own child lives. That child is the `sh -c` running the `&&` chain, which dies on TERM: dash does not exec the last command of an `&&` list. So a process that ignores TERM outlives the limit and dies with the job, and a 137 is a KILL from outside, as by the OOM killer. The same process as timeout's direct child gave 137 at the limit plus 10 s (review pass 3).
- **The subshell outlives its step.** Its output goes to files: without the redirects the step waited for the whole build. Its stdin is `/dev/null`. The provider stub in "Bring up the compose stack" lives across steps the same way.
- **"The three dashboards build"** stays where it was, just before the SvelteKit smoke, whose `vite preview` needs the build. It now waits for the done mark, or for the subshell to die without one, or for a cap a minute past the three limits and their kill-after grace (810 s). It reads the subshell's state from `/proc`, not `kill -0`, which counts a dead shell nothing has reaped yet (a zombie) as alive. Then it prints how long it waited, and:
  - **when the build finished:** each dashboard's log, folded when it built and open under a `::error` naming the dashboard when it did not, and a line per dashboard of exit code and seconds. It fails when any dashboard failed.
  - **when it never finished:** a `::error`, which dashboards did finish, and every log as it stands. It fails.

  It runs when a stack step failed too (`!cancelled()` and the start step's success), so a stack failure no longer hides whether the dashboards build.
- **The build-time env** (`NEXT_PUBLIC_API_URL`, `SESSION_SECRET`) moves to the start step.
- **"The Kubernetes image stops on SIGTERM"**, which now runs while the SvelteKit dashboard builds, sends its `docker stop` once the embedding stub logs the server's request, where it waited a fixed 0.5 s. When the stub never logs one (about 5 s of polling), the step fails saying so.

This is SMD-2092's and SMD-2219's shape for work run side by side (a log each, all printed, a limit each), across steps: the wait step cannot `wait` on a process another step's shell started, so it polls for the done mark and the subshell's state.

**Why.** "Full stack, no Supabase" was the run's critical path at 148–157 s (run 36221013361) when this was filed. Since SMD-2250 (#205) it takes 133–134 s, 1–3 s under "Schema against real Postgres" (135–136 s). So this cut is mostly this job's headroom rather than the run's wall time. Its steps ran in series, and "The three dashboards build" took 35 s at the end though it needs nothing from the stack: the two Next dashboards are built and never run, and the SvelteKit one's build is needed only by the last step. Most of the stack's time is waiting on health checks, Postgres start-up and stops, not CPU.

**Not taken.**
- **A `.rc` file with no trailing newline** ends the wait step under `-e` with no logs (review pass 1). `echo` always writes one, so only a truncated write reaches it.
- **A sturdier `/proc/PID/stat` parse** (review passes 2 and 3). The field split assumes a process name with no spaces; the subshell's is `bash`.
- **The Kubernetes image's build in the background too** (7 s). Its stop step uses the image at once, so both would move, and a stack failure would then hide them unless they ran on `!cancelled()` too. The job is already under "Schema against real Postgres", so its 7 s would not shorten the run.
- **Dropping "Tear down".** It asserts nothing, but since SMD-2250 it takes 0–1 s.
- **Building the three dashboards at once.** In series they take 35 s, well before the smoke needs them, and one at a time competes least with the stack's own image builds.
- **"The server stops on SIGTERM" after a failed dashboard build** (review pass 3). A dashboard failure still skips it, as the old step's did; it could run on `!cancelled()` too, but that is outside this ticket.
