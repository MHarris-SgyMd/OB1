## Changelog

`db/tier.ts --compare <a> <b>` composes `brain_info` and the search tools into one "how do these two live brains differ" report over HTTP — identity (version, commit, tier, release range, the tree's latest migration against the ledger's highest, schema version, embedding, Postgres/pgvector, counts), freshness (thought count, newest capture, migration delta), an opt-in retrieval diff (`--replay` replays a supplied query set through each brain's own `search_thoughts`/`search_thoughts_keyword`, the vector arm embedded server-side), and a one-line freshness verdict — reading each brain as a keyed client, writing to neither, printing no key, and exiting non-zero when anything differs (SMD-2109).

## FORK

a cross-brain compare — `tier.ts --compare` answers "do these two brains agree, and if not why" in one HTTP call (SMD-2109)

**What changed.** Running the fork as three brains (stable, canary, working;
SMD-1806) only pays off if you can answer, in one step, whether two of them agree
— on version, migration, corpus freshness and retrieval — and where they diverge.
The pieces existed and nothing composed them: `brain_info` (SMD-2041) reports one
brain; `tier.ts --diff` (slice 2) is the merge-time replay over Postgres, not
"point these two running brains at each other now". A 2026-09-24 grooming session
built the comparison by hand and only then caught a canary frozen a day behind
(407 vs 597 thoughts, a migration behind) still calling two started tickets
Backlog — the friction this closes.

- **`db/brain-compare.ts`** (new) — a read client, reached the way CLAUDE.md says
  a brain is: one HTTP process by URL, with a read key, never Postgres.
  - A brain reference is an `http(s)://` URL (its key from `--a-key`/`--b-key`,
    `OB1_COMPARE_KEY`, or a `?key=` that is lifted off the base into the header)
    or a Claude Code connector name (`open-brain`, `open-brain-canary`), resolved
    through `claude mcp get`, whose URL and `x-brain-key` are read out and the key
    never echoed back.
  - **Identity** is the keyed `GET /health` body — the whole `BrainInfo` record as
    JSON. `version` and `commit` are the server PROCESS's build facts, in no
    database, so identity is an HTTP read by nature. The report names every field
    that differs.
  - **Freshness** is that record's `counts.thoughts` and the ledger-highest delta
    (both machine-readable — the signals the verdict rests on), plus newest capture
    read best-effort from `thought_stats`' prose (null, not a crash, when the format
    moves).
  - **Retrieval** (opt-in, `--replay`) calls `search_thoughts` (hybrid/vector — the
    brain embeds the query server-side, so no local model) and
    `search_thoughts_keyword` against both brains over the same query set and diffs
    the returned ids, parsed from the stable `ID:` lines. Gated behind a supplied
    `--query`/`--queries-file`: `query_log` is not on the read surface, so the
    query set is given, not sourced from stable's log.
  - **Verdict** — one line: "current with each other", or how far the second brain
    trails or leads ("canary is 1 migration behind; 407 vs 597 thoughts").
  - Read-only, no key ever printed (only labels ride the `--json` output), exit 1
    when anything differs.
- **`db/tier.ts`** — a `--compare` verb, parsed and dispatched before the SQL-verb
  parser (it takes brain references and its own flags, not `--from`/`--to`), and
  refusing to combine with `--refresh`/`--diff`/`--promote`. `parseCompareArgs`
  reads the two positional brains, `--a-key`/`--b-key`, a repeatable `--query`, a
  `--queries-file` (one query per line, `#`-comments skipped), and the bare
  `--replay`/`--hybrid`/`--json`.
- **`db/test-brain-compare.ts`** (new) + a CI step in the Retrieval-replay-gate
  job — two fake brains (`Bun.serve`) answer a keyed `/health` and `tools/call`,
  one framing replies as raw JSON and one as SSE, so the identity/freshness/
  retrieval diff, the verdict and the key-safety run with no service container, no
  model and no key.
- **`deploy/README.md`** — a "Compare two live brains" section beside the
  `--diff`/`--replay` docs.

**Why HTTP, not SQL.** `version` and `commit` are the running server's build
facts and live in no database, so a true `brain_info` for a peer can only be
*asked* of it — the ticket's "composes `brain_info`" means calling it. Counts and
the migration ledger — the two signals that catch the motivating incident — come
from that same keyed `/health` body, and the search tools let the retrieval diff
run without the client holding either brain's Postgres credentials.

**Not taken (HTTP-only limits, named in the output).**
- The **exact id-set difference** (which thoughts one holds and the other does
  not). The read tools page prose; they do not enumerate a corpus. The count delta
  stands in for it and catches the stale-canary case; a DB-backed mode adds the
  exact set.
- A **replay sourced from stable's `query_log`**. The log is not on the read
  surface, so `--replay` diffs a supplied query set instead. Same engine shape, a
  supplied source.
- Both are named in the report rather than guessed, and left to a DB-backed
  compare (SMD-2109 follow-up).

**Caveat carried in the output.** Until SMD-2037 lands, a refreshed brain runs at
pgvector's default HNSW scan settings, so a hybrid-arm difference can be
GUC-induced rather than a real corpus delta; the retrieval section says so.
