## Changelog

A plain `migrate.ts` run, and its `--dry-run`, over a database holding `public.thoughts` with no migration ledger or an empty one, is refused: exit 2, nothing written, `--reapply` named, which runs every file in one transaction after checking that the shell agrees with the brain. An empty database still builds (SMD-3425).
**Upgrading:** a stack whose schema was applied without the migrator runs `--reapply` once, with the server and every worker stopped (`docker compose run --rm migrate bun migrate.ts --reapply`); after that its plain runs go on as before.

## FORK

A plain `migrate.ts` run over a schema with no ledger is refused, naming `--reapply` (SMD-3425)

**What changed.**
- `db/migrate.ts`: once public is put first (its own refusals, a role without USAGE on public or another brain on the path, are the more exact and come first), and before the plugins' checks and the ledger's `CREATE TABLE`, a run that is not `--reapply` reads whether `public.thoughts` exists and whether `public.schema_migrations` is missing or records no migration (no row whose name starts with three digits, as `brain_info` counts).
  - With `thoughts` there and nothing recorded, it refuses (exit 2): a plain run and a `--dry-run` alike.
  - The refusal names the case, and that the table may be another application's. It says what a plain run would do, and gives `--reapply` both as `REAPPLY_COMMAND` spells it and in the compose stack's form.
- `db/config.mjs`: `PUBLIC_THOUGHTS_EXISTS`, the pg_class predicate, is shared by the refusal and preflight's ledger row. `plan039`'s text and `apply039`'s docblock no longer offer a plain run over no ledger.
- `server-portable/README.md`: step 4 loses its route for a brain on a Supabase project, whose dashboard-applied schema this refuses. The brain is the compose stack, its own Postgres included (SMD-2288), so the step points at the stack's `migrate` service and §4's `--reapply`. The other Supabase how-to text in the core docs is SMD-3443's.
  - An empty database, a ledger that records anything, `--reapply` and `--grant` are unchanged.
  - The header says so.
- `db/README.md`: §4 says the plain run and its dry run are refused there. The note on 021's backfill no longer offers "just run them" as a way in.
- test-upgrade [22], over the whole schema with no ledger: a plain run and a `--dry-run` are refused, naming `--reapply`, no ledger made. A plain run beside an empty ledger is refused the same way, nothing recorded. Over the schema built through 007, a plain run is refused before `--reapply` applies.

**Why.** SMD-3325 made `--reapply` the remedy for a schema with no ledger, in preflight, the docs and the `--baseline` refusal, but a plain run still went ahead.
- It checked nothing. From a shell of another `OB1_EMBEDDING_MODEL`, 006 re-recorded the brain's model in `ob1_config`, and every reader followed it.
- It gave each file its own transaction, so a run stopped part-way left older definitions committed.

The migrator holds both facts that pick the case, so it enforces the advice instead of leaving it to preflight's text. The maintainer decided on 2026-10-27 to refuse.

**Version contract.** `migrate.ts` is a command the `ob1-migrate` image runs, and the compose stack's `migrate` service runs it on every `up`. A run that went ahead before is now refused there, so this is a major. It rides v2.0.0. A fresh stack is unaffected: its database has no `thoughts` when the service first runs.
