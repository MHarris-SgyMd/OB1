## Changelog

The compose stack's Postgres and Ollama now restart `unless-stopped`, as the servers and the proxy already did, so the stack comes back after a reboot with its database: before, Docker would bring the servers back without Postgres, and the server would loop in preflight. Podman applies restart policies at boot only through `podman-restart.service`, which was disabled on the podman machine where this was found; `deploy/README.md`'s new "After a reboot" says how to enable it and what it will start, that Docker's daemon must itself start at boot, that nothing waits on `depends_on` then, and how to set the policy on a running stack's Postgres without recreating it. A stack brought up before this, a canary's included, keeps its Postgres (and Ollama) at `no` until its next `up -d` or a `docker update`/`podman update --restart unless-stopped` (SMD-2760).

## FORK

The compose stack comes back after a reboot: Postgres and Ollama restart unless-stopped, every policy held, podman's boot unit documented (SMD-2760)

**What changed.**
- `deploy/compose.yaml`: `postgres` and `ollama` gain `restart: unless-stopped`. The servers, REST core and proxy already had it; the migrator and the other one-shot jobs stay `"no"`, and board-sync, the two workers and jev stay `on-failure:3`.
- `deploy/compose.tiers.yaml`: the tier Postgres anchor and Ollama take the same, as check 27 requires (it generates the tier stack from compose.yaml, so it failed until they did).
- `scripts/check-fork-consistency.ts`, check 32: `RESTART_POLICIES` holds every compose.yaml service's `restart` by value. A service added without an entry, a policy changed or a held service gone fails, with probes in memory as check 29 has.
- `.github/workflows/fork-checks.yml`, full stack: a step restarts the Docker daemon and requires Postgres, the server, the REST core and the proxy to come back on `unless-stopped`, each started after the restart and healthy by its own healthcheck within two minutes, and a keyed `thought_stats` answered from the database. It runs before the SIGTERM step, which leaves the server stopped by hand; that step now requires its own stop to add a `SIGTERM: stopped` line, since the daemon's stop leaves one too.
- `deploy/README.md`: a new section, "After a reboot": what each policy brings back, and jev started by hand where the servers name it; Docker's daemon against podman's `podman-restart.service` (rootful machine: `podman machine ssh -- sudo systemctl enable …`; rootless machine: the user unit inside it; rootless podman on Linux: the user unit plus linger; the rootless forms unmeasured); Docker's daemon starting at boot; listing what the unit will start first (`--filter should-start-on-boot=true`); no `depends_on` order at boot, preflight's loop (SMD-2043); an older stack's Postgres (stable's and a canary's) and Ollama set in place; how to check. The canary section's remark points there, and so does its twin in `deploy/canary.sh`'s `published_port` comment. `SETUP.md`'s step 2 points there too.

**Why.** On 2026-10-09 the dogfood Mac's podman machine restarted at about 15:16Z and both brains stayed down until 16:03Z, when they were started by hand; the session hook queued 18 captures meanwhile. Two causes, read on the machine: `open-brain-postgres-1` had policy `no` (compose.yaml's `postgres` never had a `restart:`), and `podman-restart.service` was disabled at both scopes, so even the `unless-stopped` services stayed down. On Docker, which starts `unless-stopped` containers with the daemon, the first alone would bring the servers back without their database.

**Held.**
- Check 32's probes: every policy as held; postgres with none, with `"no"`, with `always`; the migrator restarting; a service the map does not hold, with and without a policy; a held service gone; no services.
- 12 mutants (job runner, each restoring its file byte for byte): dropping postgres's or ollama's restart, postgres at `"no"`, the migrator at `unless-stopped` and the tier anchor's restart dropped are each caught by check 27, and the four compose.yaml ones by check 32 on its own; the policy compare, the not-held branch (caught only by the probe with no policy, added for it), the gone-from-file loop and postgres held at `"no"` by check 32's probes or the tree; the services guard off crashes the run. Not caught: check 32 not called, or not reading the tree — the blind spot checks 29 and 30 share.
- Measured on the dogfood Mac (podman 6.0.2, rootful machine, `podman machine ssh` lands as root): the unit's start filter is `should-start-on-boot=true` ("Always Or Unless-Stopped"); it would start a days-old scratch stack's server and proxy and the buildx container, and not stable's Postgres. On a scratch container, `podman update --restart unless-stopped` kept the same container running and put it on that list at once; a stop by hand took it off.
- actionlint 1.7.12 with shellcheck over fork-checks.yml: clean.
- On a GitHub runner (Fork Checks dispatched on the branch, run 37983066720, all green): the daemon restarted, and Postgres, the server, the REST core and the proxy were each started 1 s after it began, healthy and on `unless-stopped` 8 s in; `thought_stats` answered; the SIGTERM step counted its own line. The same run on a throwaway branch with postgres back on `"no"` (run 37983130587) failed the step after its 2 minutes, Postgres `exited`, the server and REST core looping in preflight, and failed Repo consistency on check 32.

Left for the maintainer as SMD-2834; the section says to start it by hand.
