## Changelog

`deploy/tier.sh` runs `db/tier.ts` (refresh, replay, diff, promote) beside a running stack. It builds `db/tier.Dockerfile`, which is Bun plus `postgresql16-client`, and runs the checkout's `tier.ts` in it on the stack's network. It takes `--from` / `--to` as `HOST[:PORT][/DB]`, builds the URLs from `POSTGRES_PASSWORD`, and reads the env file through compose so the values match the stack's. `tier.ts --refresh` refuses a `--to` that is the `--from` database. It also marks each target it resets on the database itself (`ob1.refresh_target`), and resets only a marked, tier-stamped or empty target, or an Open Brain schema holding no thoughts. So a refresh that failed partway retries, while stable, an untiered brain and another application's database are refused. `--promote` refuses the mirror cases. The deploy-stack CI job seeds a thought and a logged search, then runs a refresh, a replay, a diff, a retry and both refusals on every PR (SMD-2036).

## FORK

`deploy/tier.sh` + `db/tier.Dockerfile` make `tier.ts --refresh` runnable; refresh marks its targets and refuses its source, a brain, or a stranger (SMD-2036)

**What changed.**
- `db/tier.Dockerfile` is `oven/bun:1.4.0-alpine` with `apk add --no-cache postgresql16-client`. The build fails if `pg_dump` or `pg_restore` reports a major other than 16.
- No code is copied in. `deploy/tier.sh` mounts the checkout read-only and runs its `tier.ts`, because a refresh migrates the copy forward with the tree that runs it.
- The wrapper builds the image from stdin. It is cached, and uses `--load` under docker, because on a podman host the buildx builder otherwise keeps the result in its own cache.
- It runs the container with `--init`, so Ctrl-C stops a refresh, and joins `open-brain_default` (`--network` for the tier stack).
- It reads the environment through `compose config --environment`, compose's own parse of the env file under the shell, so quotes, inline comments, `export`, CRLF and a BOM read as they do for the stack.
- It hands on only what `tier.ts` and `migrate.ts` read: `OB1_*`, `POSTGRES_PASSWORD`, `OPENROUTER_API_KEY` and `OLLAMA_BASE`. Access keys and `LINEAR_API_KEY` stay behind.
- The checkout's own `.env` files, mounted with the code, are switched off: `OB1_ENV_FILES=off` (a new opt-out in `db/env.ts`), `bun --no-env-file`, and a working directory outside the checkout.
- It checks `--network` before building, adds `--load` only where docker has buildx, and unsets `CDPATH`.
- It expands `--from` / `--to` into `postgres://postgres:<POSTGRES_PASSWORD, percent-encoded>@HOST:PORT/DB`. The resolved values and URLs go to the container in a mode-600 temporary env file.
- A short-form `--to` gets `OB1_ALLOW_REMOTE_DB=1`. A URL `--to` gets it only from the operator's environment.
- In `db/tier.ts`, `refresh()` looks up the source connection's session (pid and `backend_start`) in the target's `pg_stat_activity`. Only the same cluster lists it, and the database names decide from there.
- Before its reset, `refresh()` marks the target: `ALTER DATABASE … SET ob1.refresh_target = '<tier>'`. The mark is a database-level setting, so the reset does not drop it and pg_restore does not overwrite it.
- `targetRefusal()` allows a target only if it is marked, is stamped `canary`/`working`, has a public schema holding no relations (tables, views, sequences, foreign tables) but what extensions own, or is an Open Brain schema holding no thoughts. An Open Brain schema means `schema_migrations`, `ob1_config` and `thoughts` together; `schema_migrations` alone is Rails', Ecto's and dbmate's name too.
- The mark is read from the database's own row through `config.mjs`'s `DB_LEVEL_SETTINGS_SQL` and `parseSetConfig`, so a role-level, server-level or connection-level value does not count. Only `canary` or `working` is a mark, so a hand-set `stable` does not arm a reset.
- Every other target is refused, and the refusal names no override, because marking the record by hand would disarm the guard for it for good. The refused cases are `tier=stable`, thoughts under no stamp, and another application's tables. Both guards run before the client tools are looked for.
- If the mark cannot be set, refresh stops before the reset. It says the mark needs a superuser, or `GRANT SET ON PARAMETER ob1.refresh_target` on PG15+, and that restoring pgvector needs a superuser in the default install anyway. The mark lasts until `ALTER DATABASE … RESET ob1.refresh_target`, which deploy/README documents and promote's refusal prints.
- `promote()` refuses a `--to` that is the `--from` database, is marked, or is stamped `canary`/`working`.
- A refusal or failed step prints one `tier.ts: error:` line. When compose cannot parse the env file, the wrapper prints compose's own error.

**Why.**
- No image the stack runs, and not this Mac, carries both Bun and a pg16 client. The canary stood up on 2026-09-23 only through a one-off `podman run` with a runtime `apk add`, so the refresh had no reproducible form.
- CI could not run the refresh either: db-live's runner has pg14, which refuses a pg16 server, and test-live [20] drives only the replay engine and the guards.
- The guards came with the wrapper. From a container every database is non-loopback, so the wrapper has to set `OB1_ALLOW_REMOTE_DB`, which switches off the one guard `--refresh` had.
- The two likeliest slips are stable under its other network name (`postgres` against `open-brain-postgres-1`), and `--from` and `--to` swapped. A string compare would let the first through, and the same-database check lets the second through.

**Not taken.**
- Adding the client to the `migrate` image (the ticket's option 2). That image is a release artifact that copies `migrate.ts` alone, and `tier.ts` imports from `db/`, `scripts/`, `evals/` and `server-portable/`.
- A compose service. The canary beside the dogfood is in no compose file (SMD-2038), and a flag picks the network.
- Bun's `--env-file` as the parser. It cuts an unquoted value at `#` even with no space before it, which compose does not.
- `system_identifier` as the identity. A volume or base-backup copy shares it, so a canary made that way would be refused as its own source.
- `ob1_config.tier` as the target's identity (pass 1). pg_restore copies the source's stamp in before the final stamp, and ingest-records and promote write `stable` by default, so the stamp says what the last writer was, not what the database is for.
- Filed as follow-ups rather than folded in, each a mechanism of its own:
  - the passwords off argv inside the container (SMD-2119);
  - hybrid replay from the container on a Linux host (SMD-2120);
  - checking that a short-form `--to` is attached to `--network` before the remote opt-in (SMD-2121).

**Held.**
- test-live [20] (692 assertions) holds the refusals through `refresh()`:
  - the test database into itself, spelled with an extra URL parameter;
  - the canary into stable (stamped `stable` by the section's promote);
  - stable into a canary that holds rows and no tier stamp.
- It reads `targetRefusal`'s cases directly, with no pg_dump needed:
  - a restored `tier=stable` refused unmarked and allowed marked;
  - a `canary` stamp allowed;
  - an Open Brain schema with no thoughts allowed;
  - a new database allowed, and the same one with an `invoices` table refused.
- The same cases also check that:
  - a Rails-shaped database (`schema_migrations` with no thoughts) is refused;
  - a role-in-database `ob1.refresh_target` is not taken as the mark.
- With stand-in `pg_dump`/`pg_restore` on PATH (the restore fails), `refresh()` stops at the restore and leaves its target marked. That shows the mark is set before the restore.
- A hand-set `stable` is not taken as a mark.
- A new database carrying `pg_stat_statements` and `tablefunc` is allowed.
- It checks that `promote` refuses a marked `--to`, and the same database spelled another way.
- Disabling any one of these fails an assert: the mark's allowance, the empty-schema rule (pass 1's "no thoughts table"), the zero-thoughts allowance, or promote's guard. So does disabling either guard outright.
- The deploy-stack step seeds a thought with a vector through `upsert_thought` and logs a keyword search for it through the server. It then refreshes into `ob1_tier_ci` and checks, one test per line:
  - the migrations, thoughts, vectors and `query_log` counts are equal;
  - the probe and its vector arrived;
  - the copy is stamped `working`;
  - `--replay` replayed at least one search, and `--diff` found nothing moved;
  - the copy carries the mark, and a retry over it restamped `stable` (as a refresh that died after its restore leaves it) succeeds;
  - both refusals fire (`open-brain-postgres-1`, and the copy into `postgres`), and the brain still has its thought.
- The CI env file now writes a quoted `POSTGRES_PASSWORD` and `OB1_EMBEDDING_DIM=1024   # …`, as an operator might.
- Replayed against a separate compose project, the step passes. It fails with each of:
  - a schema-only dump;
  - `sameDatabase` disabled;
  - `targetRefusal` disabled;
  - the mark not set;
  - the first cut's wrapper, which read the env file literally (`OB1_EMBEDDING_DIM … NaN`).

**Measured.**
- On this Mac (docker CLI over podman), the image reports `pg_dump (PostgreSQL) 16.15` and Bun 1.4.0 as uid `bun`.
- Against the dogfood, `deploy/tier.sh --refresh --from postgres --to open-brain-canary-postgres/<scratch>` took about 3.7 s with no manual `apk`. That is the ticket's separate-server check, re-run on the tree with every pass's guards (2026-09-24). The copy matched stable (635 thoughts, 2719 audit rows, 382 `query_log` rows, 635 vectors) and was stamped and marked `working`. The scratch database was then dropped, and the live canary database was not touched.
- On throwaway servers with the password `p@ss/w:rd% é#x`, all nine env-file shapes refreshed. The shapes were plain, both quote styles, `export`, CRLF, comment lines, an inline comment, indented, and `OB1_EMBEDDING_DIM=1024   # …`. The first cut failed four of them, and failed the last only after the target was reset.
