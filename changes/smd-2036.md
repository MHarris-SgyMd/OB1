## Changelog

`deploy/tier.sh` runs `db/tier.ts` (refresh, replay, diff, promote) beside a running stack. It builds `db/tier.Dockerfile`, which is Bun plus `postgresql16-client`, and runs the checkout's `tier.ts` in it on the stack's network. It takes `--from` / `--to` as `HOST[:PORT][/DB]` and builds the URLs from `POSTGRES_PASSWORD`. `tier.ts --refresh` now refuses a `--to` that is the `--from` database, compared by the server's identity rather than the URL string. The deploy-stack CI job runs a refresh, a diff and that refusal on every PR (SMD-2036).

## FORK

`deploy/tier.sh` + `db/tier.Dockerfile` make `tier.ts --refresh` runnable, and refresh refuses to reset its own source (SMD-2036)

**What changed.** `db/tier.Dockerfile` is `oven/bun:1.4.0-alpine` with `apk add --no-cache postgresql16-client`. The build fails if `pg_dump` or `pg_restore` reports a major other than 16. No code is copied in: `deploy/tier.sh` mounts the checkout read-only and runs its `tier.ts`, because a refresh migrates the copy forward with the tree that runs it. The wrapper builds the image from stdin (cached; `--load` under docker, whose buildx builder on a podman host otherwise keeps the result in its cache). It passes `--env-file deploy/.env`, sets `OB1_ALLOW_REMOTE_DB=1` and joins `open-brain_default` (`--network` for the tier stack). It expands `--from` / `--to` into `postgres://postgres:<POSTGRES_PASSWORD, percent-encoded>@HOST:PORT/DB` and hands them over as `-e NAME` with no value, so the password is not in the runtime's argument list. In `db/tier.ts`, `refresh()` reads each side's `system_identifier` and `current_database()` (falling back to the server's address when the role may not read `pg_control_system`) and refuses when the two are the same, before it looks for the client tools. The header, the tools-missing message, `db/README.md` and a new `deploy/README.md` section, "Refreshing a tier", name the wrapper.

**Why.** No image the stack runs, and not this Mac, carries both Bun and a pg16 client. The canary stood up on 2026-09-23 only through a one-off `podman run` with a runtime `apk add`. So the refresh had no reproducible form, and CI could not run it: db-live's runner has pg14, which refuses a pg16 server, and test-live [20] drives the replay engine and the guards only. The same-database refusal came in with the wrapper. From a container every database is non-loopback, so the wrapper has to set `OB1_ALLOW_REMOTE_DB`, which switches off the one guard `--refresh` had. And the likeliest typo is stable under the other name it answers to on the network (`postgres` against `open-brain-postgres-1`), which a string compare would let through.

**Not taken.** Adding the client to the `migrate` image (the ticket's option 2). That image is a release artifact that copies `migrate.ts` alone, and `tier.ts` imports from `db/`, `scripts/`, `evals/` and `server-portable/`, which the root `.dockerignore` keeps out. A compose service was not taken either: the canary beside the dogfood is not in any compose file (SMD-2038), and a flag picks the network. A `postgresql17-client`, which would read a 16 server too, was not taken, because its dumps carry a setting a 16 target does not have.

**Held.** test-live [20] (676 assertions): refresh of the test database into itself, spelled with an extra URL parameter, is refused with the same-database message. With the check disabled, the assert fails; the refresh gets past the guard and stops at the missing `pg_dump`. The deploy-stack job refreshes the stack's brain into `ob1_tier_ci` through `deploy/tier.sh`. It asserts that the migration ledger, `thoughts` and `query_log` counts match (the log is non-empty), that the tier is stamped `working`, and that `--diff` finds nothing moved. It also asserts that `--to open-brain-postgres-1` from `postgres` is refused.

**Measured.** On this Mac (docker CLI over podman), the image reports `pg_dump (PostgreSQL) 16.15` and Bun 1.4.0 as uid `bun`. `deploy/tier.sh --refresh --from postgres --to open-brain-canary-postgres/<scratch>` against the dogfood took about 3 s end to end with no manual `apk`. The copy matched stable (602 thoughts, 2481 audit rows, 346 query_log rows, 602 vectors) and was stamped `working`. The same scratch database, named by its container name on one side and its network address on the other, was refused and kept its 602 rows. The live canary database was not touched.
