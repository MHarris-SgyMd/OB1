## Changelog

A work claim now counts its renewals. Each renewal that lands, by `renew_claim` or by `claim_work` with the holder's own token, raises the claim's `renewals` by one; a refused renewal counts nothing, and a claim that takes over a lapsed one starts at 0. `list_claims` carries the count, as does the claim `claim_work`, `renew_claim` and `release_claim` answer with (a refusal's `heldBy` names other claims without it). Claims made before this release read `renewals: null`, uncounted, never 0, and stay so through their later renewals. `db/claim-report.ts` reports how long claims run, from claim to release, by how each ended, by client, by whole ticket or piece and by the merged PR's size, from a `list_claims` dump or `work_claims` itself. **Upgrading:** `bun db/migrate.ts` applies migration 152, a new column on `work_claims` with the claim functions redefined; nothing else changes (SMD-4540).

## Record

A work claim counts its renewals — migration 152 adds work_claims.renewals, so how long a claim ran can be read beside how often its holder renewed it, the counter (PR 1) and a report of how long claims run (PR 2) (SMD-4540)

**What changed.**
- **Migration 152** (`db/migrations/152_claim_renewals.sql`):
  - `work_claims.renewals`, an integer checked `>= 0`. It is added with no default, so the claims standing keep NULL (uncounted), and then defaults to 0 for every claim after.
  - `renew_work_claim` and `claim_work`'s renewal branch (the holder's own token on exactly this work) raise it by one in the `UPDATE` that renews. NULL + 1 is NULL, so an uncounted claim stays uncounted. A refusal writes nothing; a lapsed claim nothing covers, renewed by its holder, counts that renewal; a takeover's new claim is a new row at 0.
  - `ob1_work_claim_json` adds `renewals`, so every function answering with a claim's jsonb built by it carries it (145's `release_holder_claims` names its claims by id, issue and piece alone).
  - Each of the three is carried from its last definer (115's `ob1_work_claim_json` and `renew_work_claim`, 140's `claim_work`), the count its only change, copied by script from the source line ranges with asserted replacements.
- **`list_work_claims` is left as 143 made it.** It returns columns, and a `RETURNS TABLE` cannot gain one under `CREATE OR REPLACE`. Made again in 152 with one more column, 143's own `CREATE OR REPLACE` refused it at a `migrate.ts --reapply`, which runs every file in order: a smoke run before any suite showed it. So `server-portable/store-sql.ts` reads the count beside the listing, a scalar subquery by each claim's id through its row's jsonb (`(SELECT (to_jsonb(w) ->> 'renewals')::int FROM work_claims w WHERE w.id = l.id)`), the listing's order kept by `WITH ORDINALITY`. Through the jsonb, a server newer than its brain (at 151) lists with null rather than failing on a missing column (review pass 1, both lanes); by the id, it reads the primary key, not a hash of every claim's row (pass 2).
- **The server:** `WorkClaim.renewals` (`server-portable/store.ts`), a whole number or null; the `list_claims` tool's description and `server-portable/README.md` name it, a count and not a sign of activity; `rest-client` regenerated.
- **Preflight:** the ticket-claims row's by-hand remedy, where 115's functions are missing, named 115 alone, which would put back 115's `claim_work`, `renew_work_claim` and `ob1_work_claim_json` over 140's and 152's. It now names 115, then 140, 143 and 152 (152 left to the migrator where the ledger reads it not yet applied).
- **Tests:** test-schema **[137]** (the shape, the three last definers, each counting rule, the listing as the server reads it, the check, a re-apply), with `CARRIES` `"152": ["115", "140"]` and [126]'s last-definer row and restore moved to 152; test-upgrade **[20co]** (refused by name without 140's `ob1_work_claim_cap`, then claims standing at the upgrade staying NULL, new ones counting, a re-apply keeping the counts) and its window guard; test-rest-sql [10] (the count through both doors and the listing); test-preflight (the 115 remedy).

**Tidied while the files were open.** Two tidy readers by slice after review pass 3: the migration header's comments rewrapped and made plain, the store's and preflight's comments trimmed of repeats, the changelog's and record's tangled sentences put right, [137]'s and [20co]'s small helpers and stale comments.

**Why.** SMD-4540 reports how long claims run, by how they ended and by the work's size, so SMD-4541 can decide whether a claim should state when its work will be done. A renewal overwrote `renewed_at`, so nothing said how often a holder renewed. The maintainer chose (2026-11-23) the counter first, then the report: the counter collects only once installed, so it goes on the release path first.

**Limits.**
- The count says how often a claim was renewed, not when: active time and gaps stay unrecorded.
- Claims made before 152 are uncounted, and stay so.
- Preflight's by-hand remedy for a ledger read without 152 (naming 115, then 140 and 143) is not asserted; test-preflight's brain has no ledger at that row, so it exercises the text naming 152.
- **The count measures a client's pace, not work.** A Claude Code agent renews at each commit, push and long test run (the claim rule), and its session hook adds renewals at compactions and the session's end, and, where the claims hook is pasted (`--print-hook claude-code --claims`), every quarter of the lease, at most an hour, while tools run or prompts arrive. The agent runner, as built, renews only when it publishes (once at the day lease and once at the week lease, each publish attempt), which no live run does yet; as designed it also renews while its session runs and at each tick while its PR is open. A client with no hook renews as the claim rule says. So counts compare within one kind of client: PR 2's report groups by holder (`holder_kind`, the label's client) before it reads a count beside a duration.

### PR 2: the duration report

**What changed.** `db/claim-report.ts` reads claims from a `list_claims` dump (`--from`, `include_ended`; camelCase or snake_case) or from `work_claims` (`--url`, the count through the row's jsonb, null before 152), and prints how long they ran, claim to release, in four tables: by how each ended, and for merged claims by client, by whole ticket or piece, and by the merged PR's changed lines (`--sizes`, a JSON object of `{ additions, deletions }` by PR number). A claim's ending is read from its release: merged (its holder's reason says "merged", not "not merged"), closed by board-sync (the server's own `closedBySync`), taken over, force-released, released (other: a split, a drop, a test), or lapsed and never released (timed to its lease's end). Its PRs are its reason's first sentence's `OB1 PR N`, with any list after one, their sizes summed. `--from` takes pages walked to the end as one array and refuses a last page that says `truncated`; `--now` dates the report, leaving out later claims and releases. Under the table it says what it cannot see. `--self-check` (21 assertions on fixtures) runs in Brain Checks' new "Claim report rules" step and in `db/ci-parity.sh`; `db/README.md` documents it.

**The recorded read, on the stable brain** (196 claims, 2026-11-23 19:15 UTC, read with one read-only query; stable is before 152, so every count is uncounted; PR sizes from `gh pr list`):

Of the rest: 22 released (other), every one a split into pieces, a Verify or hook test, a hand-over or the agent runner's unpublished run (median 0.1 h); 1 closed by board-sync (SMD-3606 PR 1b: its PR merged about 8 h in, board-sync released it at 68 h); 1 lapsed, never released; 9 live. 195 claims are held by the `claude-code` key and 1 by the agent runner's own key; by label 194 are Claude Code's, 1 Codex's and 1 the agent runner's, and every merged claim is Claude Code's: no other client to compare.

**What it says.** Durations rise with the merged PR's size, a median of about 7 hours under 100 changed lines to 29 at 2,000 or more, but the spreads overlap widely (under 100 lines reaches 17 h at its p75, the 500–1,999 bucket's median). A claim's size is known only once its PR exists, so history by size cannot tell, at claim time, how long a claim should take; by shape alone (known at claim time) it can only say a piece runs longer than a whole ticket (19 h against 6.9 at the median, pieces being the parts of the larger tickets). And every hour here holds the waits for review and for the merge word, not work alone. Whether a stated estimate (SMD-4541) would add anything is the maintainer's decision on these numbers; the renewal counts that would tell a worked claim from a waiting one start once stable carries migration 152.
