## Changelog

A work claim now counts its renewals. Each renewal that lands, by `renew_claim` or by `claim_work` with the holder's own token, raises the claim's `renewals` by one; a refused renewal counts nothing, and a claim that takes over a lapsed one starts at 0. `list_claims` and the claim `claim_work`, `renew_claim` and `release_claim` answer with carry the count (a refusal's `heldBy` names other claims without it). Claims made before this release read `renewals: null`, uncounted, never 0. **Upgrading:** `bun db/migrate.ts` applies migration 152, a new column on `work_claims` with the claim functions redefined; nothing else changes (SMD-4540).

## Record

A work claim counts its renewals — migration 152 adds work_claims.renewals, so how long a claim ran can be read beside how often its holder renewed it, PR 1 of 2 (SMD-4540)

**What changed.**
- **Migration 152** (`db/migrations/152_claim_renewals.sql`):
  - `work_claims.renewals`, an integer checked `>= 0`. It is added with no default, so the claims standing keep NULL (uncounted), and then defaults to 0 for every claim after.
  - `renew_work_claim` and `claim_work`'s renewal branch (the holder's own token on exactly this work) raise it by one in the `UPDATE` that renews. NULL + 1 is NULL, so an uncounted claim stays uncounted. A refusal writes nothing; a lapsed claim nothing covers, renewed by its holder, counts that renewal; a takeover's new claim is a new row at 0.
  - `ob1_work_claim_json` adds `renewals`, so every function answering with a claim's jsonb built by it carries it (145's `release_holder_claims` names its claims by id, issue and piece alone).
  - Each of the three is carried from its last definer (115's `ob1_work_claim_json` and `renew_work_claim`, 140's `claim_work`), the count its only change, copied by script from the source line ranges with asserted replacements.
- **`list_work_claims` is left as 143 made it.** It returns columns, and a `RETURNS TABLE` cannot gain one under `CREATE OR REPLACE`. Made again in 152 with one more column, 143's own `CREATE OR REPLACE` refused it at a `migrate.ts --reapply`, which runs every file in order: a smoke run before any suite showed it. So `server-portable/store-sql.ts` reads the count beside the listing, `LEFT JOIN work_claims` on the listing's ids, its order kept by `WITH ORDINALITY`, through the row's jsonb (`to_jsonb(w) ->> 'renewals'`), so a server newer than its brain (at 151) lists with null rather than failing on a missing column (review pass 1, both lanes).
- **The server:** `WorkClaim.renewals` (`server-portable/store.ts`), a whole number or null; the `list_claims` tool's description names it; `rest-client` regenerated.
- **Preflight:** the ticket-claims row's by-hand remedy, where 115's functions are missing, named 115 alone, which would put back 115's `claim_work` and `renew_work_claim` over 140's and 152's. It now names 115, then 140, 143 and 152 (152 left to the migrator where the ledger reads it not yet applied).
- **Tests:** test-schema **[137]** (the shape, the three last definers, each counting rule, the listing as the server reads it, the check, a re-apply), with `CARRIES` `"152": ["115", "140"]` and [126]'s last-definer row and restore moved to 152; test-upgrade **[20co]** (refused by name without 140's `ob1_work_claim_cap`, then claims standing at the upgrade staying NULL, new ones counting, a re-apply keeping the counts) and its window guard; test-rest-sql [10] (the count through both doors and the listing); test-preflight (the 115 remedy).

**Why.** SMD-4540 reports how long claims run, by how they ended and by the work's size, so SMD-4541 can decide whether a claim should state when its work will be done. A renewal overwrote `renewed_at`, so nothing said how often a holder renewed: a claim renewed at every commit over two days read the same as one left waiting two days. The maintainer chose (2026-11-23) the counter first, then the report: the counter collects only once installed, so it goes on the release path first.

**Limits.**
- The count says how often a claim was renewed, not when: active time and gaps stay unrecorded.
- Claims made before 152 are uncounted, and stay so.
- Preflight's by-hand remedy for a ledger read without 152 (naming 115, then 140 and 143) is not asserted; test-preflight's brain has no ledger at that row, so it exercises the text naming 152.
- A renewal by the session hook's backstop counts as the agent's own does: the count is of renewals that landed, by whoever held the token.
