## Changelog

The claim rule gives an agent a next step for a claim it can't renew or release while the agent registry is away: no push while the claim stays lapsed, a release kept and retried, a release by anyone counted out while it too is refused, and the user told once (SMD-3876).

## Record

The claim rule has a step for a claim that can't be renewed or released while the agent registry is away (SMD-3876)

**What changed.** Steps 2, 4 and 6 of "Claim your work", in CLAUDE.md and AGENTS.md (identical):
- **An operator must act:** tell the user once (again after a compaction or on resume), and don't renew again until they say one has acted. Leave any marker beside the token file in place meanwhile, one naming a claim the user already decided on included, since the hook doesn't renew a claim with one. While the claim is unreleased, this holds over every sentence of the rule that says to renew, retry or delete the marker ("carry on", "After the user's carry on", "retry at each renewal point", "Retry only if …"), each of which would otherwise have the agent delete the marker and renew. Instead of renewing, the agent looks beside the token file and lists the ticket's claims at each renewal point (`list_claims` needs no agent id): its claim shown released (a takeover closes it so) is handled as a release refusal; once it shows lapsed, the agent doesn't push, and another claim on the work claimed or renewed after its claim's `expiresAt`, other than one the user already decided on, is handled as WORK_CLAIMED. Before, every renewal after a carry-on met "tell the user" again. With the registry set up wrong, the hook's marker came back on each due run, about once a minute at checkpoints.
- **The claim had lapsed:** while it stays lapsed, don't push, open a PR or ask for a merge. Retry at each renewal point, and tell the user once if one of those is waiting on it. Before, "renew before each push" and "renew before you ask for the merge" said nothing of a renewal that can't land, though a claim on exactly that work can take the lapsed one over meanwhile.
- **A `release_claim` answering CLAIM_UNATTRIBUTED,** anywhere in the rule (step 2's split, the agent's own older piece, step 6, "drop it"): keep the token file and any marker beside it, and retry the release before the final reply (if an operator must act, once the user says one has acted). If none has landed by then, tell the user the claim's id and that it is dropped, so a later session releases it rather than renewing it: without a marker, the hook renews it there once the registry answers. "Drop it", step 2's split, the own-piece line and step 6 now each delete the files only once the release lands, and say inline to keep them on CLAIM_UNATTRIBUTED; a split refused so works under the whole-ticket claim until its release lands. Before, each deleted the token file and the marker after any release, landed or not: an unreleased claim lost its token, and with it the only way to release it before the lease ran out (a week, with a PR open). The parent bullet's "keep the token" and its "retry at your next renewal point", which a dropped claim doesn't have, said otherwise.
- **"Carry on":** a release, forced or by the claim's holder, can be refused CLAIM_UNATTRIBUTED too (core/claims.ts: a forced one always needs the releaser's agent id, a holder's for a claim made under one), and one saying an operator must act leaves only a lapse. The agent lists the ticket's claims with `include_ended: true` at each renewal point to see whether the claim has ended. Before, the rule offered the user's operator release, which may be refused too.
- **"After the user's carry on":** the markers that are no new stop are those until the agent's renewal lands, with the landing renewal's reply and the marker quoting it ("Renewed your claim …"); once it has landed, any other reply or marker naming the decided claim means tell the user. Before, "a later reply or marker" had no defined start: during an outage every marker naming the decided claim comes before any renewal lands.
- **"Retry shortly"** on a lapsed claim retries only after the check the "had lapsed" bullet gives.

**Why.** Found by SMD-3807's review pass 4, an agent walkthrough of the rule with the registry away or set up wrong, the agent's own claim lapsed, and another key's claim made since. The gaps predate SMD-3807. They follow from `renew_claim` and `release_claim` both answering CLAIM_UNATTRIBUTED with the registry away (SMD-3654, SMD-3705).

**Not taken.**
- A live claim waiting on an operator at step 6's merge: the claim still holds, and step 6 stops only on a refusal saying it was taken over, so the merge goes ahead (walkthrough, Low).
- Step 1's and step 7's operator release, which may be refused CLAIM_UNATTRIBUTED too: the ticket's scope is step 4, and the refusal itself says to retry shortly or that an operator must act (render.ts, cold read, Low).
- A lapse-check marker the hook's detached child writes just after the agent's renewal lands, from a list taken before it, names the decided claim after the landing, so the agent tells the user needlessly: a narrow race, erring toward telling (walkthrough, Low).
- An abandon whose release can't land: nothing on disk records "dropped", so a later session in the worktree, and its hook, renew the claim; the agent writing a `.blocked.json` itself would stop that, a new mechanism beyond the rule's wording (walkthrough, Medium; the user is told the claim's id and that it is dropped).
- A restructure of the operator bullet: with no marker, keep renewing and tell the user once, since a renewal with the registry away still reports a takeover, a closed ticket and a lapse (claims.ts, render.ts). It needs three guards of its own (renew only at renewal points, delete no marker until a renewal lands, and a listing on brains before SMD-3705, whose refusal carries no lapse), so it was not simpler (walkthrough).
- A `decided` list in the token file, which the hook's lapse check would honour, so the user's decision survives a compaction. Declined by the maintainer: once the agent leaves the marker in place, the loop of telling the user is gone without it. After a compaction the agent asks once more, which is what the rule already intends. The list would mean a hook change (tests, mutants, the installed copy updated again), and a file the agent writes would hold a decision the user may never have made.

**Follow-ups.** SMD-4115: a dropped claim whose release can't land is renewed by a later session, since nothing on disk says "dropped".

**Tidied while the files were open.** The operator bullet's closing sentence, which repeated its opening, moved up into it; "a release needs the releaser's agent id" is "can be refused too", true of a holder whose claim was made by name; this record's Fix column names each pass's commit, and its Not taken items are a list.
