## Changelog

The claim rule gives an agent a next step for a claim it can't renew or release while the agent registry is away: no push while the claim stays lapsed, a release kept and retried, an operator's forced release counted out, and the user told once (SMD-3876).

## Record

The claim rule has a step for a claim that can't be renewed or released while the agent registry is away (SMD-3876)

**What changed.** Step 4 of "Claim your work", in CLAUDE.md and AGENTS.md (identical):
- **An operator must act:** tell the user once (again after a compaction or on resume), and don't renew again until they say an operator has acted. Leave any marker beside the token file in place meanwhile, one naming a claim the user already decided on included, since the hook doesn't renew a claim with one. This holds over "carry on", "After the user's carry on" and "retry at each renewal point", each of which would otherwise have the agent delete the marker and renew. Before, every renewal after a carry-on met "tell the user" again. With the registry set up wrong, the hook's marker came back on each due run, about once a minute at checkpoints.
- **The claim had lapsed:** while it stays lapsed, don't push, open a PR or ask for a merge. Retry at each renewal point, and tell the user once if one of those is waiting on it. Before, "renew before each push" and "renew before you ask for the merge" said nothing of a renewal that can't land, though a claim on exactly that work can take the lapsed one over meanwhile.
- **A `release_claim` answering CLAIM_UNATTRIBUTED** (step 6, or "drop it"): keep the token file and any marker beside it, and retry the release at each renewal point (if an operator must act, once the user says one has acted). If the session stops before a release lands, tell the user the claim's id. "Drop it" now deletes the files only once the release lands. Before, the rule said to retry "at your next renewal point", which a dropped claim doesn't have, and it said nothing of the marker. An agent that deleted the marker let the hook revive the dropped claim once the registry answered.
- **"Carry on":** a release needs the agent registry, forced or by the claim's holder (core/claims.ts refuses either without the key's agent id), so while the registry can't answer, for either cause, a claim made under an agent id may end only by lapsing. The agent lists the ticket's claims with `include_ended: true` at each renewal point to see whether the claim has ended. Before, the rule offered the user's operator release, which isn't available then.
- **"After the user's carry on":** "a later reply or marker naming that claim" is now "after that renewal has landed, a later renewal's reply naming that claim, or a marker from one". The landing renewal's own reply names the decided claim, and the claims hook marks it, so the marker alone can't be the signal.
- **"Retry shortly"** on a lapsed claim retries only after the check the "had lapsed" bullet gives. During an outage every marker naming the decided claim comes before any renewal lands, so "later" had no defined start.

**Why.** Found by SMD-3807's review pass 4, an agent walkthrough of the rule with the registry away or set up wrong, the agent's own claim lapsed, and another key's claim made since. The gaps predate SMD-3807. They follow from `renew_claim` and `release_claim` both answering CLAIM_UNATTRIBUTED with the registry away (SMD-3654, SMD-3705).

A `decided` list in the token file, which the hook's lapse check would honour, so the user's decision survives a compaction. Declined by the maintainer: once the agent leaves the marker in place, the loop of telling the user is gone without it. After a compaction the agent asks once more, which is what the rule already intends. The list would mean a hook change (tests, mutants, the installed copy updated again), and a file the agent writes would hold a decision the user may never have made.
