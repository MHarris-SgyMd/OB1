## Changelog

The claim rule gives an agent a next step for a claim it can't renew or release while the agent registry is away: no push while the claim stays lapsed, a release kept and retried, a release by anyone counted out while it too is refused, and the user told once (SMD-3876).

## Record

The claim rule has a step for a claim that can't be renewed or released while the agent registry is away (SMD-3876)

**What changed.** Step 4 of "Claim your work", in CLAUDE.md and AGENTS.md (identical):
- **An operator must act:** tell the user once (again after a compaction or on resume), and don't renew again until they say an operator has acted. Leave any marker beside the token file in place meanwhile, one naming a claim the user already decided on included, since the hook doesn't renew a claim with one. This holds over "carry on", "After the user's carry on" and "retry at each renewal point", each of which would otherwise have the agent delete the marker and renew. Instead of renewing, the agent lists the ticket's claims at each renewal point (`list_claims` needs no agent id): once its claim shows lapsed, it doesn't push, and a claim on the work made or renewed since, other than one the user already decided on, is handled as WORK_CLAIMED. Before, every renewal after a carry-on met "tell the user" again. With the registry set up wrong, the hook's marker came back on each due run, about once a minute at checkpoints.
- **The claim had lapsed:** while it stays lapsed, don't push, open a PR or ask for a merge. Retry at each renewal point, and tell the user once if one of those is waiting on it. Before, "renew before each push" and "renew before you ask for the merge" said nothing of a renewal that can't land, though a claim on exactly that work can take the lapsed one over meanwhile.
- **A `release_claim` answering CLAIM_UNATTRIBUTED** (step 6, or "drop it"): keep the token file and any marker beside it, and retry the release before the session ends (if an operator must act, once the user says one has acted). If none has landed by then, tell the user the claim's id: without a marker, a later session in the worktree has the hook renew the claim once the registry answers. "Drop it" now deletes the files only once the release lands. Before, the rule said to retry "at your next renewal point", which a dropped claim doesn't have, and it said nothing of the marker. An agent that deleted the marker let the hook revive the dropped claim once the registry answered.
- **"Carry on":** a release, forced or by the claim's holder, needs the releaser's agent id from the registry too (core/claims.ts refuses either without it), so one refused CLAIM_UNATTRIBUTED leaves only a lapse. The agent lists the ticket's claims with `include_ended: true` at each renewal point to see whether the claim has ended. Before, the rule offered the user's operator release, which isn't available then.
- **"After the user's carry on":** the markers that are no new stop are those until the agent's renewal lands, with the landing renewal's reply and the marker quoting it ("Renewed your claim …"); once it has landed, any other reply or marker naming the decided claim means tell the user. Before, "a later reply or marker" had no defined start: during an outage every marker naming the decided claim comes before any renewal lands.
- **"Retry shortly"** on a lapsed claim retries only after the check the "had lapsed" bullet gives.

**Why.** Found by SMD-3807's review pass 4, an agent walkthrough of the rule with the registry away or set up wrong, the agent's own claim lapsed, and another key's claim made since. The gaps predate SMD-3807. They follow from `renew_claim` and `release_claim` both answering CLAIM_UNATTRIBUTED with the registry away (SMD-3654, SMD-3705).

**Not taken.** A live claim waiting on an operator at step 6's merge: the claim still holds, and step 6 stops only on a refusal saying it was taken over, so the merge goes ahead (walkthrough, Low). Step 1's and step 7's operator release, which may be refused CLAIM_UNATTRIBUTED too: the ticket's scope is step 4, and the refusal itself says to retry shortly or that an operator must act (render.ts, cold read, Low).

A `decided` list in the token file, which the hook's lapse check would honour, so the user's decision survives a compaction. Declined by the maintainer: once the agent leaves the marker in place, the loop of telling the user is gone without it. After a compaction the agent asks once more, which is what the rule already intends. The list would mean a hook change (tests, mutants, the installed copy updated again), and a file the agent writes would hold a decision the user may never have made.
