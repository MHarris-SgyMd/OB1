## Changelog

Each request to the MCP endpoint now says on its log line which protocol revision it named: a new `rev` field (`2026-07-28`, a 2025-era revision, `unnamed` or `other`), and on its span as `mcp.protocol.version` or `ob1.rev` (SMD-4363). No migration.

## Record

The MCP request's line says which revision it named — `rev`, held to the revisions served, so the log can count the clients on each (SMD-4363)

**Why.** Since SMD-4345 `/mcp` serves the 2026-07-28 revision beside the 2025-era ones, and a request's line read the same for both: the method, the tool, the key's name, how it ended. Nothing said how many requests, or which keys, used either. Whether a client had moved to 2026-07-28 could be read only sideways, from a `server/discover` answered 200 with no `initialize` after it, which is how the canary's upgrade was checked. Three hosted clients went unmeasured in SMD-4344 because measuring them needed a probe at a public address; a brain they already reach shows it, once its line says.

**What changed.**

- `revisionOf` in `server-portable/mcp-edge.ts` reads the revision a request names: what an `initialize` offers (`params.protocolVersion`, which is what the SDK's transport acts on, whatever header came with it); else its envelope's (`params._meta`'s `io.modelcontextprotocol/protocolVersion`, a 2026-07-28 request's word on itself, over a header that disagrees); else its `MCP-Protocol-Version` header's; else `unnamed`. A caller's own `unnamed` is written `other`.
- `mcp-server/app.ts`'s route sets it on the request's record wherever it reads the body: for a request it serves, and for one refused at the key, whose body it reads for the refusal's id.
- `server-portable/telemetry.ts`: `rev` is a field of the line, after `rpc`, held to `MCP_REVISIONS`: 2026-07-28, the five revisions the SDK's 2025-era transport negotiates, and `unnamed`. Any other string is written `other`, as an unknown method is.
- The request's span carries it as `mcp.protocol.version` where it is a revision, and as `ob1.rev` where it is `unnamed` or `other`, the way `ob1.rpc` holds what `mcp.method.name` cannot say.
- `deploy/README.md`'s table of the line's fields and its account of the span, and `mcp-server/README.md`'s "Every request's line", say so.

**Decided.**

- **The client's name is not recorded.** It is the caller's own string (`clientInfo.name`), so writing it needs an allow-list of names kept by hand, and a name on that list is anyone's to send. The key's name is already on the line and is the server's word for who called; where each connector has a key of its own, the key and the revision together say which client speaks what.
- **A request that names no revision is `unnamed`.** The 2025-06-18 and 2025-11-25 revisions have a client send the header on every request after `initialize`, and have a server assume 2025-03-26 without one; 2025-03-26 and earlier have no such header at all. The line says what the request named, not what the server assumed.
- **No label on the duration histogram.** The line counts requests by revision. A label would multiply every series of the histogram by the revisions served, and `scripts/check-consistency.ts` holds that histogram's labels to a measured list.

**What a count of `rev` means.** It counts what requests said, not what the server did.

- A client on 2025-03-26 or earlier is `unnamed` on every request but its `initialize`, so those revisions are counted by their `initialize` lines alone, and `unnamed` holds their other requests with every header-less one.
- A refused request has its `rev`: a 2026-07-28 request the handler refused (400) still says `2026-07-28`. Count with the status.
- An `initialize` offering a revision this server does not serve is `other`, though the transport answers it with one it does.

**Also changed.** CI's `deploy-stack-auth` job counts a `thought_stats` call's line with a pattern anchored at both ends (`STATS_LINE` in `.github/workflows/brain-checks.yml`); the line has `rev` in it now, so the pattern names `"rev":"unnamed"`, its probe naming no revision. The one other workflow pattern on a request's line spans fields with `.*`.

**Not changed.** What any request is answered. The REST core's lines and every other route of the MCP server: no `rev`. The metric's labels.

**Held.**
- `test-mcp.ts` [9b], five rows (233, was 228): eleven requests' `rev` and a batch's (a 2026-07-28 request's, a keyless one's, the envelope's over a header that disagrees, a bare 2025-era request's `unnamed`, a 2025-era header's, an `initialize`'s offer, `other` for a revision not served and for a made-up string, an `initialize` under a header read by its offer, a header that says `unnamed` written `other`, an envelope whose revision is no string, a header-less batch `unnamed`); nothing of a caller's text in any field of any line but the clock's; and `MCP_REVISIONS` equal to what this server serves, read from the installed SDK both ways: its 2025-era list by its export, its 2026-07-28 family by what `server/discover` answers (the SDK keeps that list apart and exports none of it), and `unnamed`. An SDK that serves another revision of either family fails that row.
- `test-server.ts`, three rows (1,667, was 1,664): `requestLine` writes each known value as itself, any other string `other` (a future date, a value with a line break, the empty string), and no `rev` where none was read, with `rev` in the line's order of keys; the real server's span for a request under a `2025-06-18` header carries `mcp.protocol.version` and no `ob1.rev`; a batch's carries `ob1.rev` `unnamed` and no `mcp.protocol.version`.
- Mutants, thirteen, all killed, run on the code as the review left it: the line writing the revision unheld (3 rows in `test-mcp.ts`, 3 in `test-server.ts`); the route never setting it; the header read before the envelope; an `initialize`'s offer not read, and read after the header; a request naming none given no word; a caller's own `unnamed` taken for the route's; a 2025-era revision missing from the list, and 2026-07-28 missing from it; the span carrying neither attribute, carrying `unnamed` under the convention's name, and never carrying `mcp.protocol.version`.

It put about 250 bodies and headers through `revisionOf` and `requestLine` and got only the known words and `other` on the line, and no throw.
