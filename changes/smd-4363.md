## Changelog

A request to the MCP endpoint now says on its log line which protocol revision it named, wherever the server read its body: a new `rev` field (`2026-07-28`, a 2025-era revision, `unnamed` or `other`), and on its span as `mcp.protocol.version` or `ob1.rev` (SMD-4363). No migration.

## Record

The MCP request's line says which revision it named — `rev`, held to the revisions served, so the log can count the clients on each (SMD-4363)

**Why.** Since SMD-4345 `/mcp` serves the 2026-07-28 revision beside the 2025-era ones, and a request's line read the same for both: the method, the tool, the key's name, how it ended. Nothing said how many requests, or which keys, used either. Whether a client had moved to 2026-07-28 could be read only sideways, from a `server/discover` answered 200 with no `initialize` after it, which is how the canary's upgrade was checked. Three hosted clients went unmeasured in SMD-4344 because measuring them needed a probe at a public address; a brain they already reach shows it, once its line says.

**What changed.**

- `revisionOf` in `server-portable/mcp-edge.ts` reads the revision a request names: its envelope's (`params._meta`'s `io.modelcontextprotocol/protocolVersion`, a 2026-07-28 request's word on itself, over a header that disagrees and whatever its method: the SDK takes any request with the envelope for 2026-07-28); else what an `initialize` offers (`params.protocolVersion`, which is what the SDK's 2025-era transport acts on, over a 2025-era header sent with it); else its `MCP-Protocol-Version` header's; else `unnamed`. A caller's own `unnamed` is written `other`.
- `mcp-server/app.ts`'s route sets it on the request's record wherever it reads the body: for a request it serves, and for one refused at the key, whose body it reads for the refusal's id.
- `server-portable/telemetry.ts`: `rev` is a field of the line, after `rpc`, held to `MCP_REVISIONS`: 2026-07-28, the five revisions the SDK's 2025-era transport negotiates, and `unnamed`. Any other string is written `other`, as an unknown method is.
- The request's span carries it as `mcp.protocol.version` where it is a revision, and as `ob1.rev` where it is `unnamed` or `other`, the way `ob1.rpc` holds what `mcp.method.name` cannot say.
- `deploy/README.md`'s table of the line's fields and its account of the span, and `mcp-server/README.md`'s "Every request's line", say so.

**Decided.**

- **The client's name is not recorded.** It is the caller's own string (`clientInfo.name`), so writing it needs an allow-list of names kept by hand, and a name on that list is anyone's to send. The key's name is already on the line and is the server's word for who called; where each connector has a key of its own, the key and the revision together say which client speaks what.
- **A request that names no revision is `unnamed`.** The 2025-06-18 and 2025-11-25 revisions have a client send the header on every request after `initialize`, and have a server assume 2025-03-26 without one; 2025-03-26 and earlier have no such header at all. The line says what the request named, not what the server assumed.
- **No label on the duration histogram.** The line counts requests by revision. A label would multiply every series of the histogram by the revisions served, and `scripts/check-consistency.ts` holds that histogram's labels to a measured list.

**What a count of `rev` means.** It counts what requests said, not what the server did.

- A client on 2025-03-26 or earlier is `unnamed` on every request but its `initialize`, so those revisions are counted by their `initialize` lines alone, and `unnamed` holds their other requests with every header-less one.
- A refused request has its `rev`: a 2026-07-28 request the handler refused (400) still says `2026-07-28`. Count with the status.
- An `initialize` says what it offers, not what it is answered. One offering a revision this server does not serve is `other`, though the transport answers it with one it does; one offering `2026-07-28` with no envelope says `2026-07-28` and is answered as a 2025-era handshake. So the clients on a revision are its lines with `status` 200 and an `rpc` other than `initialize`.
- A request whose body the server never read has no `rev`: one gone before the route ran, or whose key check threw.

**Also changed.** CI's `deploy-stack-auth` job counts a `thought_stats` call's line with a pattern anchored at both ends (`STATS_LINE` in `.github/workflows/brain-checks.yml`); the line has `rev` in it now, so the pattern names `"rev":"unnamed"`, its probe naming no revision. The one other workflow pattern on an MCP request's line spans fields with `.*`; the pattern anchored on the REST core's `/v1/whoami` line is untouched, a REST line having no `rev`.

**Not changed.** What any request is answered. The REST core's lines and every other route of the MCP server: no `rev`. The metric's labels.
