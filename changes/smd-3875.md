## Changelog

The editorial-policy auditor no longer sends the database password to OpenRouter. Its `HTTP-Referer` was `SUPABASE_URL`, which on this stack is the Postgres connection string; it is now a fixed URL. An operator who ran the auditor before this should rotate the database password (SMD-3875).

## Record

The auditor's Referer is fixed — it sent the connection string, password included, to OpenRouter (SMD-3875)

`recipes/editorial-policy/auditor/index.ts` sent `SUPABASE_URL` as the `HTTP-Referer` header of its one OpenRouter call, on every audit. Upstream's value was a public Supabase project URL, so the header was harmless there. Once the recipe moved onto the SQL shim, the same variable carries the Postgres connection string, password included, and OpenRouter may log the header and show it in its analytics. The auditor is opt-in, so the leak reached only an operator who deployed it. Found by the cold reader of SMD-3770 PR 2.

**What changed.**
- **The auditor** sends `OPENROUTER_REFERER`, a fixed URL, the one the other recipes' OpenRouter calls send (`atomizer`, `lint-sweep`, `provenance-chains`).
- **The recipe's README** tells an operator who ran the auditor before this change to rotate the database password.
- **`integrations/test-writes.ts`**, which already drives the auditor against a stubbed OpenRouter, now records every call's headers:
  - the audit's model call must send the fixed Referer;
  - no header of any call, by any writer the suite drives, may carry the connection string, a `postgres://` URL or the password. CI's connection string has one.

  The mutant that puts `SUPABASE_URL` back fails both. Neither failure message prints the connection string.

**The sweep.** Across `recipes/`, `integrations/`, `extensions/` and `plugins/`, no other outbound header, query string or body is built from `SUPABASE_URL`, `DATABASE_URL` or another variable that can hold credentials:
- the other Referers are fixed, or (`entity-wiki`) built from its own app-name setting;
- a credential in a query string appears only in tests;
- the recipes that still build `${SUPABASE_URL}/rest/v1/…` send to that address itself, not to a third party. Given a `postgres://` value they fail rather than leak.

The ticket's own Verify grep used `\s`, which `git grep -E` doesn't support, so it found nothing even with the leak present. `git grep -n -i -E "Referer.{0,6}(SUPABASE_URL|DATABASE_URL|process\.env)" -- recipes integrations extensions plugins` found the line before this change and finds nothing after it.
