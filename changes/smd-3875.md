## Changelog

The editorial-policy auditor no longer sends the database password to OpenRouter. Its `HTTP-Referer` was `SUPABASE_URL`, which on this stack is the Postgres connection string; it is now a fixed URL. An operator who ran the auditor before this should rotate the database password (SMD-3875).

## Record

The auditor's Referer is fixed — it sent the connection string, password included, to OpenRouter (SMD-3875)

`recipes/editorial-policy/auditor/index.ts` sent `SUPABASE_URL` as the `HTTP-Referer` header of its one OpenRouter call, on every audit. Upstream's value was a public Supabase project URL, so the header was harmless there. Once the recipe moved onto the SQL shim, the same variable carries the Postgres connection string, password included. OpenRouter reads that header as the app's site URL for its app attribution and public rankings, so it may have been stored and shown. The auditor is opt-in, so the leak reached only an operator who deployed it. Found by the cold reader of SMD-3770 PR 2.

**What changed.**
- **The auditor** sends `OPENROUTER_REFERER`, a fixed URL, the one `atomizer`, `lint-sweep` and `provenance-chains` send to OpenRouter.
- **The recipe's README** tells an operator who ran the auditor from Daemonic Brain 2.0.0 or earlier to rotate the database password.
- **`integrations/test-writes.ts`**, which already drives the auditor against a stubbed OpenRouter, now records every call's headers:
  - the audit's model call must send the fixed Referer;
  - no header of any call, by any writer the suite drives, may carry the connection string, a `postgres://` URL or the password. CI's connection string has a password of 7 characters. One under 6 is skipped, since the suite's own header values hold words like `stub` and `key`.

  The mutant that puts `SUPABASE_URL` back fails both. Neither failure message prints the connection string.

**The sweep.** Across `recipes/`, `integrations/`, `extensions/` and `plugins/`, no other outbound header, query string or body is built from `SUPABASE_URL`, `DATABASE_URL` or another variable that can hold credentials:
- the other Referers are fixed, or (`entity-wiki`) built from its own app-name setting;
- a key in a query string goes only to the brain's own servers (the auditor's own schedule sends `?key=`), or appears in tests;
- the recipes that still build `${SUPABASE_URL}/rest/v1/…` send to that address itself, not to a third party. Given a `postgres://` value they fail before connecting. The Python importers then print the URL, password included, to the local console: an exposure on the operator's own machine, not this ticket's.

The ticket's own Verify grep used `\s`, which `git grep -E` doesn't support on every platform (macOS's doesn't), so there it found nothing even with the leak present. `git grep -n -i -E "Referer.{0,6}(SUPABASE_URL|DATABASE_URL|process\.env)" -- recipes integrations extensions plugins` found the line before this change and finds nothing after it.

**Review pass 1.** A cold read found no defect in the fix, and confirmed the sweep. Corrected:
- **The password check:** a local DSN with a short password, such as `stub`, would fail the check with no leak present. It now skips a password under 6 characters, and says so.
- **The words:**
  - the README now names the release, 2.0.0 or earlier, rather than the ticket, and says OpenRouter reads the header for its public rankings;
  - this record now says where a key in a query string goes, and that the Python importers print a `postgres://` URL locally;
  - the Verify grep's `\s` is unsupported on macOS, not everywhere.

  (caught: cold-read)
- **The Referer check's message** printed any Referer that wasn't a `postgres://` URL. So a mutant sending the password alone put the password in the log. It now prints only the fixed Referer, and calls any other value withheld. The password-only mutant fails both checks. (caught: mutant)
