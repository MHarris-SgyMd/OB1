## Changelog

The core docs describe the compose stack as the fork's own setup, not as a migration off Supabase. `SETUP.md` and `deploy/README.md` lose "without Supabase" from their titles, the deploy service table says what each service is rather than what of Supabase's it replaces, and provider examples speak of managed Postgres generally; history, the shim's own text and CI's job names keep their mentions (SMD-3443).

## FORK

The core docs stop teaching and framing Supabase (SMD-3443)

**What changed.** The how-to and the framing go; history, the shim's text, CI's job names and one upstream line stay.
- `SETUP.md`:
  - The title is "Setting up Open Brain".
  - The opening names the whole stack, then says the fork began from upstream's Open Brain, whose guide builds on supabase.com, has grown its own tools and schema since, and needs no Supabase account or CLI, and no Deno.
  - The query log's note says "on that host" rather than "a hosted (Supabase) deployment".
  - The prerequisites' "No Supabase account. No Supabase CLI. No Deno." is gone, since the opening says all three.
- `deploy/README.md`:
  - The title is "the compose stack", and the opening names the whole stack rather than "Phase 4 of the migration".
  - The env file's line no longer names `supabase secrets set`.
  - The service table's column is "What it is": each row names the service, not the Supabase piece it replaced. `ollama` is the stack's own model endpoint, where `OB1_LLM_BASE_URL` points unless the env file names another. The old row called OpenRouter the default, and compose's default is `http://ollama:11434/v1`.
  - The preflight note says the server's settings come from the env file by hand, compose building `DATABASE_URL` from its password. The old note said "on Supabase this mattered less".
  - The `vector extension` note names managed providers generally.
  - The caveats:
    - The bullet on upstream's Edge Function failing smoke checks 2 to 4 goes. The fork retired that build in SMD-1800, and FORK.md changes 42 and 75 keep the record.
    - The scheduled-jobs caveat no longer says "off Supabase".
    - The data-migration caveat says "a brain you are moving onto the stack", not "the old database".
    - The auth caveat gives both modes. Without the `auth` profile, a client holds a named, scoped key of its own, which `revoke_agent_key` cuts off within a minute. With the profile, a client holds 600 s tokens, and its grant is revoked on the GUI's page of grants. Upstream's one shared key (issue #216) is what the named keys replaced. The caveat no longer says "moving off Supabase does not improve that".
  - The preflight rationale no longer describes the retired MCP `index.ts` (`initialize`, `tools/list`). Preflight gates the REST core.
  - The preflight note's `--deep` calls the configured model providers, not "OpenRouter".
- `deploy/compose.yaml`'s comments match:
  - the header names the whole stack (forwarder, proxy, REST core, MCP server, GUI, Postgres, migrator), without "Phase 4" or "once Supabase is gone";
  - the four "Replaces:" comments name what each service is, the migrator's with the plugins' migrations it applies after the core's;
  - the `ollama` comment says it is where `OB1_LLM_BASE_URL` points by default.
- `server-portable/preflight.ts`'s header drops "Phase 4 of the migration" and "on Supabase that mattered less". It describes the REST core it gates, not the retired MCP `index.ts`. It says its settings are environment values someone wrote, the compose stack's env file among the sources.
- `deploy/smoke.sh`:
  - Its header points it at the compose stack, on its own machine or behind the TLS proxy or tunnel. It said "a container on EKS", which CLAUDE.md's compose-only rule does not allow.
  - Its comments name upstream's Edge Function build, retired in SMD-1800, where they said "a Supabase Edge Function". Check 2's failure is put down to Supabase's gateway, the others' to the build.
- `server-portable/store-sql.ts`'s header drops "Phase 2 of the migration".
- `.github/workflows/fork-checks.yml`'s four "The Phase 4 exit test, literally" comments say "the stack end to end", since nothing now defines Phase 4.
- `db/README.md`: the opening describes the migrations rather than "Phase 1 of the Supabase migration", and the two pgvector examples speak of managed providers.
- `server-portable/README.md`: the third of "What differs" is what let the SQL store replace the PostgREST one, where it said "Phase 2 of the migration". The opening tells the origin once, "a runtime-neutral build of the MCP server, so the runtime could be chosen last … The runtime chosen was Bun", where it said "no dependency on … Supabase's function host" and "the runtime decision in the Supabase migration".
- `docs/03-faq.md`'s visual-editor answer says the brain has none. The operator GUI at `/dashboard` browses and searches thoughts, but does not edit them. An editor would be a client of the REST core, reachable with `deploy/compose.api-public.yaml`. The old text said "reads from your Supabase tables".
- `docs/agent-memory-portability.md` and `docs/open-brain-assistant-gpt-context.md` call the brain Postgres-backed.

**Kept, and why** (by place, not line, since these files change often).
- `SETUP.md`'s opening sentence on upstream's guide: the one upstream line.
- The shim's own text, which SMD-3216 retires with it:
  - `SETUP.md`'s "Further reading" link to `compat/supabase-sql/README.md`;
  - `db/README.md`'s note that the shim names the columns it can;
  - `CONTRIBUTING.md`'s recipe example run with `SUPABASE_URL='postgres://…'`.
- `db/README.md`'s grants section: what upstream's schema files granted to Supabase's roles (`auth.role()`, `service_role`, default privileges), which explains the grant groups, and that the fork's migrations grant nothing for Supabase.
- CI's job "Full stack, no Supabase", wherever `deploy/README.md`, `compose.yaml` and the workflow cite it.
- `deploy/README.md`'s port guard note: a local Supabase CLI's ports matching the guard's pattern, a collision on an operator's host rather than a deployment.
- `server-portable/README.md`:
  - "What differs from upstream's Edge Function build": history.
  - The `SUPABASE_URL` fallback, and the e2e suite's line that runs "with no Supabase at all" and deletes `SUPABASE_URL`. These are code and its test, which go with the shim; SMD-3216 now names them.
- `README.md`'s note that upstream's AI assistants answer for upstream's Supabase deployment, with how to read their answers here.
- `docs/`: the disposition and the GUI's lineage records, the screenshots' provenance, a connector registry keyword, and the assistant context's own "no Supabase".
- The "off Supabase" comments inside `db/migrations` (004, 008, 010, 017, 025). Applied migrations stay byte-identical: a changed file reads as drifted and stops a plain run.
- `recipes/openclaw-agent-memory`'s README and `metadata.json`, which still say V1 uses Supabase/Postgres where `docs/agent-memory-portability.md` now says Postgres. Recipes are vendored, outside the core docs, and SMD-1795's other children cover them.
- FORK.md's front door ("running Open Brain without Supabase") and its change records. The front door sits nine bytes under its cap, and the ticket's sweep is the core docs.

**Why.** The brain deploys as the compose stack alone, its own Postgres included (SMD-2288), and the fork has no live users. Text written as a migration off Supabase, or for a brain on a Supabase project, told readers about a deployment the fork does not have. SMD-3425's review found the last of the how-to.

**Held.** The consistency checks, 22b and 22c among them, pass. No suite or check pins the changed text, and compose's render is unchanged (comments only).
