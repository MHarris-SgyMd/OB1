## Changelog

Fork Checks' "Full stack, no Supabase" job runs its route-table renders, its Postgres network probes, and the proxy's outside lookup beside the forwarder's self-check side by side rather than one after another. Its proxy-only restarts no longer re-run the migrator (SMD-3472).

## FORK

Full stack's static checks and probes run side by side (SMD-3472)

**What changed** in `.github/workflows/fork-checks.yml`'s `deploy-stack` job:
- **"The proxy loads only the held route tables"** starts each of its 22 `proxy_loads` combinations in the background through a new `loads()`, its output in a file of its own under `$RUNNER_TEMP/proxy-loads/`. A new `settle()` waits for a range of them and prints each one's output, then its exit code if it failed, in call order within the range. Each release mode's five print as that mode ends, and the other twelve print last. A log that can't be read fails the step too.
  - **The release overlay's renders** run one mode at a time, because `compose.release.yaml` is rewritten for each mode. Each release render also checks the file's `cksum` is still its own mode's. The 12 renders that name no release overlay run on beside both modes.
  - **The last `settle` takes every call made above it.**
  - **`rendered`** is now collected in `loads()`, in the step's own shell, since a background call's array never reaches the step.
  - **Bun.YAML reads each file** there once per run, for every render naming it, where each call read it again. It is the same reading, which check 28 holds.
  - **compose.yaml's alone render** goes to a `mktemp` file per call; before, every call shared `.bun-view.alone.json`.
  - **The EXIT trap** settles every call not yet settled. It keeps an exit's own code, and fails the step if any of those calls failed.
    - A failed step waits for its renders and prints every one's output, not just the first failing group's.
    - A failing call a later edit makes anywhere, even after the files check, fails the step.
- **"Postgres answers on the data network alone"** runs its four `docker run` probes side by side, each writing its output and exit code to files under `$RUNNER_TEMP/postgres-probes/`. It reads them in the order they once ran in, with the same messages and the same accepted refusals.
- **"The proxy asks nothing outside the stack, and the forwarder dials it alone"** gives each lookup of `example.com` 2 s (`timeout 2`):
  - **The control runs first,** from `open-brain_edge`, and must resolve within the 2 s in one of three tries. It gets three because musl resends a lost query only after 2.5 s. The proxy's lookup follows the try that resolved. So the resolver upstream of Docker's has just answered for the name, and a proxy that could ask it would have its answer well inside the same bound. The control runs under `--init`. Without it, busybox `timeout` execs getent as PID 1, which ignores the TERM, so nothing is bounded: in traefik's image on podman, `timeout 2 sleep 5` exits 0 only once sleep ends. Docker's init is untested here until CI.
  - **The proxy's lookup** passes only on getent's "not found" (2) or a timeout's code (busybox 143, coreutils 124). A `timeout` that can't run exits 127, or 126 under some engines, and is refused.
  - **The in-container self-check** runs beside both. An early exit waits for it and prints its output under a label.
  - The step reads compose's config once, not twice.
- **Each proxy-only `up`** now passes `--no-deps`: the forwarder step's EXIT trap and the REST core step's two. Without it, each re-ran migrate and waited on every dependency's health. Those dependencies are never stopped in either step, so now only the proxy's health is waited for.

**Why.** Over main's last 20 push runs, this job's median was 196 s. The four steps' medians were 30 s (route tables, 20–37 s), 17 s (forwarder), 9 s (Postgres probes) and 8 s (REST core).
- **The route tables** are static: about 8 compose renders per combination, with no stack running.
- **The forwarder step:** 12 s passed before the self-check printed (run 40996920359), and the self-check takes about 1 s by itself. So most of it is inferred to be the lookup waiting out the resolver of the proxy's internal-only network.
- **The probes:** the two on egress each wait out their 4 s dial.

SMD-3365 (merged) took the job's two hold steps. This takes the next serial sections. It saves runner time in every run, and wall time while this job is the longest.

**Departures from the ticket.**
- **The self-check stays in the container**, run beside the lookup, rather than being replaced by a `cmp` of the mounted `/forwarder.ts`. Run side by side it costs nothing extra. It still proves what a `cmp` wouldn't: the script runs, under the forwarder's own Bun, in its own container. The checker already holds compose's copy byte-equal to the file (`FORWARDER_SCRIPT`).
- **Item 4's trap is the forwarder step's**, not the webhook step's. The webhook step's ups already passed `--no-deps`. The ticket's REST core ups are changed as it says.

**Held.**

  - The first local run found a bug: the counter, then named `base`, overwrote the proxy JSON `base`, and every release call failed. That counter is gone now.
  - **Review pass 1's mutants against the fixed step,** each run against main's step too (which fails each one):
    - ten compose and release-renderer mutants: three run here again (a rehearsal-only key, a tag-only key, a duplicate port);
    - each per-mode or final settle dropped, failed by the checksum or the trap;
    - a new failing combination added before the final settle, after it, after the files check, or after a mode's settle;

- **The probe and forwarder steps' control flow,** under a `docker` stand-in with set exit codes (17 cases; pass 3 ran the forwarder's under bash 5.2 too):
  - each fails as its message says: a data probe that can't connect, an egress probe that connects, docker's 125, an unknown refusal word, a lookup that resolves (0), can't run (127) or is killed (137), and a control that fails or times out in all three tries;
  - a control that fails twice and then resolves passes;
  - a lookup timing out passes, whether busybox's 143 or coreutils' 124;
  - each 1 s set of stand-in calls ends in about 1 s, so the calls run side by side.
- **busybox `timeout` in the proxy's image** (podman, not Docker Engine):
  - under `exec`, time running out exits 143, not found 2, and a missing command 127;
  - as PID 1 (`run`), time running out exits 0; under `run --init`, it exits 143 after 2 s.
- **The checker** passes, and so do **actionlint 1.7.7 and its shellcheck** (checked against a positive control).
- **On Docker Engine,** the lookup's timing and the probes need the PR's own Fork Checks run.
