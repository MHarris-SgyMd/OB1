## Changelog

The read and write tools' logic moves out of the MCP registration into a transport-free `server-portable/core/` (the egress gate, the query log, the store reads and writes, capture's existence-oracle rules), their words into `render.ts`, and every tool's schema into `core/schemas.ts`; every reply now carries its typed answer as `structuredContent` beside unchanged text — the value, a coded refusal, or a typed fault — and the session hook maps capture's new shape codes to the mends it always made (SMD-2283).

## FORK

The read and write tools run on a transport-free core and answer a typed result beside their text — PRs 1 and 2 of 3 (SMD-2283)

**What changed.** `buildServer` held every tool's logic inside its
`server.registerTool` closure, so the REST core SMD-2282 decided on could only
reuse it by copying it — the second gateway SMD-1931 removes. PR 1 (#272) cut
the seam and moved the fourteen read tools; PR 2 moves the three writes.
- `core/schemas.ts` — all twenty tools' titles, descriptions, hints and zod
  schemas, keyed by `tools.ts`'s `ToolName` (`satisfies`, so a manifest name
  without a spec is a compile error), moved by script byte for byte.
- `core/context.ts` — the store and environment readers the composition root
  hands in, the provider settings, the one embedder, the query log's writers,
  and (PR 2) the `door` a write names as its origin (046).
- `core/reads.ts` — the read operations, each `(ctx, principal, input) →
  Outcome<T>`, the search operation with its egress gate among them.
  `core/writes.ts` (PR 2) — `capture`, `updateThought`, `deleteThought`, moved
  whole: the shapes, a capture key's trimmed provenance and owned pointers,
  the gate, the parallel model calls, the write, its retry and its cites.
- `core/refusal.ts` — `Outcome<T>` and the typed refusals. PR 2 adds capture's
  shape codes (`REFUSED_SUPERSEDES_SHAPE`, `REFUSED_DERIVED_FROM_SHAPE`,
  `REFUSED_METADATA_SHAPE`), `EMBEDDING_NOT_ATTACHED`, and the store's edit and
  delete refusals; SMD-1978's codes keep their names and verdicts.
- `render.ts` — every tool's words, moved unchanged and rendered from the value.
- `index.ts` — a registration is `registerOp(name, scope, run, fault)`;
  `GET /health`, `/worker-status` and `/jobs/<id>` call the same core. 3,435
  lines before PR 1, 1,348 after PR 2.

Every reply carries a typed `structuredContent`. Claude Code, VS Code and
Codex hand the model that value alone when it is present (claude-code issue
55677, vscode issue 290063, codex issue 10334), so a value says no more than
its text: a JSON-text tool answers its value; a prose tool `{ ...fields, text }`
with only ids, times, numbers, booleans and enum codes beside the text, each
string held by `render.ts`'s `guard` to its field name's shape; a refusal
`{ code, retryable, text }` (and capture's derived_from `positions`, a reader's
only); a fault `{ code: "FAILED", text }`, capture's `STORE_UNAVAILABLE`. A
value is an object (the v2 wire codec wraps any other), so `worker_status`'s
rows ride under `pools`. Reply text is unchanged on every path that answered
before, but three: a thrown non-Error reads `Error: boom`, not `Error: undefined`;
a fault in the job tools reads `Error: <message>`, not the SDK's default; and
(PR 2's review) a capture-only key whose id is not to hand gets one answer for
every `supersedes` it cannot prove its own — `SUPERSEDES_UNJUDGED`, or with the
registry refusing it one `OWNERSHIP` sentence — where a missing thought was
refused and an attributed one retried, an existence oracle (SMD-1298).

The session hook's `verdictOf` reads a code before prose, so each capture
outcome that took one (PR 2) maps to the verdict its prose gave: the two
pointer shapes mend their pointer, a metadata refusal drops `metadata`, and
`EMBEDDING_NOT_ATTACHED` is retryable with nothing to mend.

**Why.** SMD-2282's first migration step: the REST core (SMD-2284) is blocked
on a middle layer it can call without MCP.

**Held.** Every suite keeps its total except where a section was added:
test-server 365 → 374 (`[16d]` a fault's words; `[16e]` one brain-info read per
store; `[16f]` a sentence planted in `window.syncedAt` is null in the value),
test-e2e-sql 311 → 363 (`[15]` every read tool's value, `[16]` every write
tool's, each refusal's code, and the rule: beside `text`, every string is a
uuid, a time or one token), test-egress 120 → 121, and the hook 648 → 653 (each
new capture code reads as its prose did). Unchanged: test-auth 124,
test-store-sql 196, test-local-provider 170, test-audit 61, test-update-delete
62, test-agents 91, test-store-postgrest 155, test-chunking 35,
test-chunk-context 20, test-embedding-dimensions 10, test-jobs 45, test-writes
389, test-thoughts 286. The Workers dry-run builds (353 KiB gzip).

**Measured.** A differential run of origin/main's server against this one, one
database: 55 read calls and routes identical (PR 1), and 30 write cases — every
capture shape, a capture key's owned and ghost pointers, re-captures, each edit
and delete refusal, `CITED` and its detach — identical after ids are
normalised (PR 2). A one-character render mutant shows as 2 and 7 diffs.

**Mutants.** The egress gate dropped in `core/reads.ts` fails 3 test-egress
assertions through MCP; dropped in `core/writes.ts`'s capture, 5. The hook's
two new pointer mappings removed fail 2 of its parity assertions.

**Follow-ups.** SMD-2461 — one fault classifier for every tool, the agent
resolver and the workers, with the PostgREST store keeping the SQLSTATE.
SMD-2470 — a malformed `derived_from` entry's position, so the hook drops
that entry rather than every source.

**Not taken.** Text-only prose tools — proposed in review pass 4 after passes
2–4 each found a defect in copying prose into the value; the user kept a
typed result on every tool, and in pass 5 chose text plus safe fields. Scope
checks inside the core: the registration still gates a tool by the key's
scope, so a tool a key may not use is absent from its `tools/list`; the REST
core decides its own (SMD-2284), and parses its own input with `SPECS` (noted
there). An `outputSchema` per tool is SMD-1931's contract. A JSON-text tool
answers its value twice, as the MCP spec recommends for a client that reads one.
