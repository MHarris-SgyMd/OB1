## Changelog

The read tools' logic moves out of the MCP registration into a transport-free `server-portable/core/` (the egress gate, the query log, the store reads), their words into `render.ts`, and every tool's schema into `core/schemas.ts`; each read tool's reply now carries its typed answer as `structuredContent` beside unchanged text — the value, a coded refusal, or `FAILED` (SMD-2283).

## FORK

The read tools run on a transport-free core and answer a typed result beside their text — PR 1 of 3 (SMD-2283)

**What changed.** `buildServer` held every tool's logic inside its
`server.registerTool` closure, so the REST core SMD-2282 decided on could only
reuse it by copying it — the second gateway SMD-1931 removes. This pull request
cuts the seam and moves the fourteen read tools across it:
- `core/schemas.ts` — every tool's title, description, hints and zod input
  schema (all twenty, the writes included), keyed by `tools.ts`'s `ToolName`
  with `satisfies Record<ToolName, ToolSpec>`, so a manifest name without a spec
  is a compile error. `Input<K>` is a tool's parsed input. The literals were
  moved by script, byte for byte.
- `core/context.ts` — what an operation runs against: the store and the
  environment through the two lazy readers the composition root hands it, the
  provider settings, the one embedder, and the query log's two best-effort
  writers (moved from `buildServer`'s closures).
- `core/reads.ts` — `search`, `fetch`, `search_thoughts`,
  `search_thoughts_keyword`, `list_thoughts`, `list_supersession_proposals`,
  `thought_stats`, `thought_changes`, `list_thought_ids`,
  `list_logged_searches`, `worker_status`, `brain_info` (its shared read),
  `job_status` and `scan_thoughts`, each `(ctx, principal, input) →
  Outcome<T>`; the one search operation with its egress gate; `parseSince`.
  `core/filter.ts` holds `parseFilter`/`withActorFilter`, now throwing
  `FilterError`, which the search operations return as `REFUSED_FILTER`.
- `core/refusal.ts` — `Outcome<T>` and the typed refusals: `NOT_FOUND`,
  `REFUSED_FILTER`, `REFUSED_EGRESS` (with the rule and the key),
  `REFUSED_SINCE`, `REFUSED_CURSOR`. `FAILED` types a thrown fault, retryable
  only when `isTransient` reads it off the driver's shape: a lost or refused
  connection, a shutdown, a statement or lock timeout, a serialization
  failure, or a provider timeout, 429 or 5xx.
- `render.ts` — the read tools' words, moved from `index.ts` unchanged, now
  rendered from the typed value; `failed()` keeps `Error: <message>` and each
  tool's hint.
- `index.ts` — a read registration is `SPECS.<tool>`, a core call and a render.
  `GET /health`, `GET /worker-status` and `GET /jobs/<id>` call the same core.
  `index.ts` goes from 3,435 lines to 2,101. It re-exports what the suites
  import from it, so no suite's import line moved.

Every read tool's reply now carries its typed answer as `structuredContent`:
the value, the refusal, or `FAILED`. Before, only SMD-1978's coded refusals
and the job handles did. A value is always an object, because the v2 SDK's
wire codec wraps a non-object as `{ result }` on the 2025 protocol era.
`worker_status`'s rows therefore ride under `pools`, while its text stays the
bare array and `GET /worker-status` still answers the array. No text changed.
Claude Code, VS Code and Codex hand the model `structuredContent` alone when it
is present (anthropics/claude-code#55677, microsoft/vscode#290063,
openai/codex#10334). So a prose tool's value carries its rendered text as
`text`, and so does every refusal and fault, and the model there reads today's
words. A tool whose text is its value's JSON adds nothing. A prose value leaves
out the thought bodies its `text` already quotes (hits' and listed thoughts'
`content`, proposals' sides, changes' `head`), so a reply does not carry three
copies of them; the core's value keeps them, for the REST core.
The write tools keep their closures and SMD-1978's codes until PRs 2 (capture,
update, delete, with the session hook's `verdictOf` beside the new codes) and
3 (the worker actions, their POST mirror, and the checker's grep that
`index.ts` holds no SQL, egress or embedding call).

**Why.** SMD-2282's first migration step: the REST core (SMD-2284) is blocked
on a middle layer it can call without MCP.

**Held.** Every suite keeps its total on this tree except where a section was
added: test-server 365 → 373 (`[16d]`, the fault's words, `FAILED`, its hint and
the transient classes; `[16e]`, one brain-info read shared across cores),
test-e2e-sql 311 → 332 (`[15]`, every read tool's value, the text inside it,
the bodies left out, and each refusal's code over MCP), test-egress 120 → 121
(`REFUSED_EGRESS` with its rule). Unchanged:
test-auth 124, test-store-sql 196, test-local-provider 170, test-audit 61,
test-update-delete 62, test-agents 91, test-store-postgrest 155, test-chunking
35, test-chunk-context 20, test-embedding-dimensions 10, test-jobs 45,
test-writes 389, test-thoughts 286, test-preflight 587. The Workers dry-run
builds (349.94 KiB gzip).

**Mutant.** The egress gate dropped in `core/reads.ts`'s `gateQuery` (always
allowed) fails 3 of test-egress's assertions through the MCP path: both search
tools stop refusing, and the code reads `FAILED` where it read
`REFUSED_EGRESS`.

**Not taken.** Scope checks inside the core. The MCP registration still gates
a tool by the key's scope, so a tool a key may not use is absent from its
`tools/list`. The REST core decides where its own authorization sits
(SMD-2284). An `outputSchema` per tool is not declared: that is the contract
SMD-1931 generates. A JSON-text tool still answers its value twice, once as
text and once structured: that is the shape the MCP spec recommends for a
client that reads only one, and `list_thought_ids` at its 10,000-id page is
the one large case.
