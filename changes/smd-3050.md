## Changelog

The `observability` profile's Grafana now loads five alert rules into the Open Brain folder: a server that stopped sending metrics, a server failing over 5% of its requests, the model provider failing calls, the exporter not reaching Postgres, and the collector losing telemetry. No contact point ships, so a rule that fires stays in Grafana's alert list until you add one (`deploy/README.md`, "Alerts"). The servers (and `mcp-server/`) now send a `process.uptime` gauge with their metrics, and `scripts/inline-dashboard.ts` is now `scripts/inline-grafana.ts`, writing the rules into compose.yaml beside the dashboard (SMD-3050).

Upgrading with the profile on: the first `up -d` recreates `lgtm`, whose labels now carry the rules' sha256, so Prometheus, Loki and Tempo restart once (SMD-3050).

## FORK

The observability profile's Grafana alerts on what its dashboard shows — five provisioned rules, no contact point shipped, and an uptime gauge so a stopped server is told from an idle one (SMD-3050)

**What changed.**
- **`deploy/observability/alert-rules.yaml`** (new): Grafana's alerting provisioning file, one group "Open Brain" in the dashboard's folder, evaluated every 30 s; compose.yaml carries it inline as the `grafana-alert-rules` config (each `$` doubled), mounted at lgtm's `provisioning/alerting/open-brain.yaml`, with its sha256 as lgtm's third label. The rules (instant Prometheus queries, each an aggregation at its outermost, a threshold on each):
  - `ob1-server-silent`, **A server stopped sending metrics**: a `service_name` with `process_uptime_seconds` in the last day and none in the last 10 minutes, for 2 minutes (a host waking from sleep catches up inside them; no data is normal).
  - `ob1-server-failures`, **The server failed requests**: `error|stalled|cut` over 5% of a server's requests over 10 minutes, about three or more of them (`increase() > 2.5`: Prometheus estimates a count from its samples), for 5 minutes.
  - `ob1-provider-failures`, **The model provider failed calls**: about three or more of a server's failed calls of one operation and `error_type` over 10 minutes (`> 2.5`; preflight's probes, `ob1_probe`, left out), for 5 minutes.
  - `ob1-postgres-unreached`, **The exporter does not reach Postgres**: the dashboard's `min(up) * (min(pg_up) or on () vector(0))` under 1, either series gone, or no `up` at all (no data alerts), for a minute.
  - `ob1-telemetry-lost`, **The collector is losing telemetry**: the dashboard's twelve loss counters, each summed by itself, rising for 10 minutes.
- **No contact point, policy or template.** Grafana 13's default policy sends to `empty`, which has none (measured), so nothing leaves the machine; `deploy/README.md`'s "Alerts" says what each rule means, how to add a contact point in the UI, and what a notification carries.
- **The uptime gauge** (`server-portable/otel-setup.ts`): the conventions' `process.uptime`, in seconds, read at each metric export (`process_uptime_seconds` in Prometheus, measured), so a running server sends a series from its start; `preflight.ts --deep`, which exports once and exits, sends none (`oneShot`), or its one point would read as a server gone silent for a day.
- **`scripts/inline-grafana.ts`** (was `scripts/inline-dashboard.ts`, SMD-1849) writes every inline Grafana file (`INLINE_FILES`) and lgtm's labels, refusing a character compose.yaml may not hold (check 28) with its file and line; `--check` as before.

**Why.** SMD-1849's profile showed the stack and told no one: a server down, a run of failures, a provider timing out, `pg_up` 0 or Loki refusing every record past 90% disk were seen only by someone looking at the dashboard. The ticket's first rule, "no request series while the container runs", could not be written as asked: the healthcheck's keyless `/health` records nothing by design, so a server no one has called sends no request series (measured), and Grafana cannot see containers. The maintainer chose the uptime gauge over request series (which would fire after every restart not followed by a call within 10 minutes) and over dropping the rule. Three more departures from the ticket: a notification links back to Grafana at its root URL (the stack's origin by default) and a query error's text names Prometheus's address inside `lgtm`, so "no URL" holds for the brain's own endpoints and keys, not for Grafana's links, which only a template would drop and none ships; the delivery check added its webhook through Grafana's API as the UI saves one, not by clicking through the UI; and CI's forced condition is the Postgres rule pending, not firing (a minute more), which the scratch stack measured.

**Held.**
- **Check 38** (new), what a notification may carry and what never fires — what Grafana refuses outright is not copied (it refuses the file and `lgtm` does not start, measured, which CI sees): the inline copy is the file with each `$` doubled; one group of `ALERT_RULE_UIDS` in the folder "Open Brain"; no contact point, policy, template or rule-level routing, a `deleteRules` naming only rules the file no longer holds; no `$` in any key or string Grafana expands (all but an annotation's value and a query's model: measured, Grafana fills them from its environment or a file — lgtm's admin password into every notification); each query `prometheus` or `__expr__`; each Prometheus query's names and labels held as a panel's (`promqlProblems`, shared with check 37), its outermost operation an aggregation by `ALERT_LABELS` or by nothing (`alertGrouping`: exactly the labels a notification carries), comments out, making no label (`label_replace`, `label_join`, `count_values`); a rule's own labels plain words; not paused, no `record`; a uid and a title of its own; an annotation templates only the kept labels and the rule's values; backtick strings read as strings; 58 probes.
- **Check 37:** lgtm's labels include the rules' sha256; `instrumentNamesIn` reads observable gauges (two probes); it runs the generator over both files. **Check 28:** lgtm's `configs` and `BASE_CONFIGS` gain the rules.
- **test-server [22]:** an export carries `process.uptime`, a gauge in `s`, one point with no labels, the process's uptime at the export. **test-preflight [11]:** `--deep` sends no `process.uptime`.
- **CI's observability step:** compose's render of the rules is the file; Grafana holds exactly the file's rules, provisioned from it; on one read, the provider rule pending (the stub's 404s) and the other four normal and healthy; pg-exporter stopped, the Postgres rule pending or firing; each failure says what Prometheus holds.
