## Changelog

`db/tier.ts --replay` and `--diff` reach the two brains over HTTP, each at its own MCP URL or connector name with its own key, and never their databases: stable's logged searches run on both brains and the ids each returns are diffed. `--diff` exits 0 unmoved, 1 when a ranking moved or a step failed, 3 when nothing was compared. A script must change: `deploy/tier.sh --replay`/`--diff` and `tier.ts --diff --from postgres://…` exit 2; the diff is `OB1_COMPARE_KEY=<read key> bun --no-env-file db/tier.ts --diff --from <stable> --to <canary>`, against a stable with `OB1_QUERY_LOG=on`, and tier.sh no longer joins `egress` (SMD-2875).

## FORK

Tier replay and diff over HTTP — no container reaches both brains for them (SMD-2875)

**What changed.**
- `db/tier.ts --replay` / `--diff` take `--from <stable>` and `--to <canary>` as each brain's MCP URL or Claude Code connector name. A key is found as `--compare` finds one: `--from-key`/`--to-key`, else the connector's header or the URL's `?key=`, else `OB1_COMPARE_KEY`, which then goes to both brains. They run `db/brain-compare.ts`'s `runTierReplay`:
  - stable's logged searches (`list_logged_searches`: at most a page of the most recent, after `--since` if given), each on the arm that ran it and each (query, arm) once, run on both brains as a client searches, and the ids the two return are diffed;
  - the report is `--compare`'s (identity, freshness, the id-set difference, retrieval), then the window and the counts, then the verdict;
  - a search both brains fail is skipped; one that one brain fails while the other answers is a failure, shown as `✗ … b failed, a answered` and counted apart from the skips;
  - `--diff` exits 0 unmoved; 1 when a ranking moved, stable's log could not be read (a page whose searches are not a list included), or a search failed on one brain; 3 when nothing was compared (an empty window, every search failed by both, or only rows logged before migration 045, which are counted as such). `--replay` reports, and exits 1 on an unread log or a one-sided failure. `--json` carries the verdict as `gate`. `--compare`'s exit counts a one-sided failure as a delta too;
  - a `postgres://` side is refused (exit 2), as are two verbs, a missing side, a malformed `--since` and a `--refresh` flag. No verb prints the usage.
- The HTTP client follows no redirect (fetch would carry `x-brain-key` to another host), and an invalid URL's refusal never echoes its user or password.
- The Postgres replay engine (`readLoggedSearches`, `replayOne`, `diffResult`, `replayAndDiff`) and the replay's own embedder and egress gate are gone from `tier.ts`; each brain embeds its own query.
- `deploy/tier.sh` refuses `--replay` and `--diff` (exit 2), joins only `<project>_data` by default (nothing it runs embeds), and no longer hands on `OPENROUTER_API_KEY`, which only the replay's embed read.
- `db/test-live.ts` [20] keeps the refresh guards and `--promote`; the replay's cases moved to `db/test-brain-compare.ts`. `db/test-connect.ts` no longer requires `tier.ts` to exit through `closeThenExit`, which only the replay used.
- CI: the tier step holds tier.sh's refusal of `--diff`; the canary step runs `tier.ts --diff` from stable's `/mcp` to the canary's `/canary/mcp` right after the canary's first `up` (exit 0), and over a window after every search (exit 3), with no key in either output.
- `deploy/README.md`, `db/README.md`, `deploy/compose.tiers.yaml`, `docs/operator-surface-tiers.md` and `docs/one-brain-per-stack.md` (row 9, "The tier tools") say how replay and diff run, what they measure, and the key order.

**Why.** `deploy/tier.sh --diff` ran `tier.ts` in one container on both brains' data networks and stable's egress, with a superuser URL for each (SMD-2872's ADR, "The tier tool joins both brains"). SMD-2872 has a brain's data network joined by nothing outside its own project. Replay and diff need no database: the read surface already answers every question they ask.

**What is measured now (the maintainer's choice).** Item 2 of the ticket offered two means: split the Postgres engine across the two projects, measuring the same thing, or move onto HTTP, measuring something else. The maintainer chose HTTP:
- the canary is diffed against stable as it answers now, not against the ids stable logged, so a thought stable gained since the refresh can read as a move; the report's id-set line counts what each holds that the other does not;
- `list_logged_searches` gives the query and arm, so a search replays with the tool's defaults, not its logged `match_count`, threshold, recency weight or filter;
- each brain embeds the query itself, through its own server's egress gate;
- the replays are real searches, which a brain logging searches logs.
