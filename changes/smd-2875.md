## Changelog

`db/tier.ts --replay` and `--diff` reach the two brains over HTTP, each at its own MCP URL or connector name with its own key, and never their databases: stable's logged searches run on both brains and the ids each returns are diffed, so no container joins both brains' networks or holds both superuser passwords for them. `--diff` keeps its exits (0 unmoved, 1 moved or a failed step, 3 nothing compared), and `deploy/tier.sh` refuses the two verbs, pointing at `bun db/tier.ts`. `deploy/tier.sh` runs `--refresh` and `--promote` as two halves, each in a container on one brain's data network with that brain's password alone, the hand-off passed container to container; the dump runs as `pg_read_all_data`, and the image is named for the project, `<project>-tier` (SMD-2875).

## FORK

Tier tools without joining another brain's networks — replay and diff over HTTP, refresh and promote one half per brain (SMD-2875)

**What changed (PR 1).**
- `db/tier.ts --replay` / `--diff` take `--from <stable>` and `--to <canary>` as each brain's MCP URL or Claude Code connector name, with a key found as `--compare` finds one (`--from-key`/`--to-key`, `OB1_COMPARE_KEY`, `?key=`, the connector's header), and run `db/brain-compare.ts`'s `runTierReplay`:
  - stable's logged searches (`list_logged_searches`: the `--since` window, else the most recent page), each on the arm that ran it and each (query, arm) once, run on both brains as a client searches, and the ids the two return are diffed;
  - the report is `--compare`'s (identity, freshness, the id-set difference, retrieval), then the window and the counts, then the verdict: `what moved: nothing — <canary> returns <stable>'s ids on …`, `what moved: N of M …`, or `nothing to compare: …`;
  - `--diff` exits 0 unmoved; 1 when a ranking moved, stable's log could not be read (a page whose searches are not a list included), or one brain failed a search the other answered (named, `failed: <canary> failed N that <stable> answered`); 3 when nothing was compared (an empty window, every search failed by both, or only rows logged before 045, which are counted as such). `--replay` exits 0 unless the log was unread or a search failed on one side; `--json` carries the verdict as `gate`. `--compare`'s exit counts a one-sided failure too;
  - a `postgres://` `--from` or `--to` is refused (exit 2), as are two verbs, a missing side, a malformed `--since` and a `--refresh` flag.
- The Postgres replay engine (`readLoggedSearches`, `replayOne`, `diffResult`, `replayAndDiff`) and the replay's own embedder and egress gate are gone from `tier.ts`; each brain now embeds its own query. `resolveBrain`'s messages name the verb and key flags they were given to.
- `deploy/tier.sh` refuses `--replay` and `--diff` (exit 2), joins only `<project>_data` by default (no `egress`: nothing it runs embeds), and no longer hands on `OPENROUTER_API_KEY`, which only the replay's embed read. Its environment filter is a list of names (pass 1, PR 2), so `OB1_COMPARE_KEY`, which the `--diff` docs have operators export, stays behind.
- `db/test-live.ts` [20] keeps the refresh guards and `--promote`; the replay's cases moved to `db/test-brain-compare.ts` against its fake brains. `db/test-connect.ts` no longer requires `tier.ts` to exit through `closeThenExit`, which only the replay used.
- CI: the tier step drops its Postgres `--replay`/`--diff` runs and holds tier.sh's refusal; the canary step runs `tier.ts --diff` from stable's `/mcp` to the canary's `/canary/mcp` right after the canary's first `up` (exit 0, `what moved: nothing`), and over a window after every search (exit 3), with no key in either output.
- `deploy/README.md`, `db/README.md`, `deploy/compose.tiers.yaml`, `docs/operator-surface-tiers.md` and `docs/one-brain-per-stack.md` (row 9 and "The tier tools") say how replay and diff run now, what they measure, and that tier.sh joins `data` alone.

**What changed (PR 2).**
- `db/tier.ts --refresh` and `--promote` each run as two halves that share a directory, `--handoff <dir>`: `--from … --handoff` is the source half, `--handoff … --to` the target half, and `--from … --to` runs both in one process, the target's guards before anything is dumped.
  - A refresh's source half reads the source's facts (where it is, its major, its database-level settings), checks its tools, dumps (`pg_dump --role=pg_read_all_data` where the login may take that role: it reads every table and sequence and can write nothing), and writes `source.json` (mode 600) beside `stable.dump`.
  - The target half refuses a hand-off that is not one (a setting name no database has, the refresh mark, a major that is not a number, no identity, no dump), runs every guard on `--to` as before, then marks, resets, restores, copies the settings, migrates and stamps.
  - A promote's source half reads the canary's identity and `schema_version` into `promote.json`; its target half refuses stable as its own canary, then stamps it.
- `sameDatabase` compares the identity each server reports (`system_identifier`, the postmaster's start, the database), since neither half reaches the other's database; it looked one connection's session up in the other's `pg_stat_activity`.
- `deploy/tier.sh`:
  - runs the source half in a container on the `--from` side's network alone, with an env file holding `--from`'s URL alone, then passes `/tmp/handoff` to the target half's container with `cp … - | cp -a - …` (no file on the host; `-a` keeps the image user's ownership, which Docker Engine's `cp` drops), then runs the target half on the `--to` side's network alone, with `--to`'s password and the settings a migration reads. A half that fails ends the run with its status;
  - each side is a project: `--to`'s from `--env-file` or `--project`, `--from`'s from `--from-env-file` or `--from-project`, else the `--to` side's network. `--network` and `--from-network` take one network each, and a list is refused. `--project` may now go with `--network`, since it also names the image. A short-form `--from` on another network with no `--from-env-file` is refused (its URL could only take `--to`'s password), as is a shell `COMPOSE_PROJECT_NAME` beside `--from-env-file` unless the projects are named;
  - hands the target half, by name, only what migrate.ts and db/config.mjs read (`OB1_EMBEDDING_MODEL`, `OB1_EMBEDDING_DIM`, `OB1_EMBEDDING_DIMENSIONS`, `OB1_TRGM_INDEX`, `OB1_BACKFILL_LIMIT`, `OB1_CHUNK_CONTEXT`, `OB1_PLUGINS`, `OB1_PLUGIN_DB_PASSWORD`; pass 2 dropped `OB1_METADATA_MODEL` and `OB1_LLM_BASE_URL`, read at import and used by no migration, and named the embedding settings instead of `OB1_EMBEDDING_*`), `OB1_TIER` and `POSTGRES_PASSWORD`; it handed on every `OB1_*`, keys included;
  - hands both halves the arguments it does not read, so a flag tier.ts refuses is refused before the dump, refuses `--handoff`, removes the source half's container (its URL, the dump) as soon as the hand-off is passed, and says when a half's container never ran;
  - builds `db/tier.Dockerfile` as `<project>-tier:latest`, the `--to` side's project, so a second brain's or a scratch run never re-tags `open-brain-tier:latest` (SMD-2537's item);
  - requires exactly one of `--refresh` and `--promote`, refuses a wrapper flag written `--flag=VALUE` (it read as a missing flag), labels each half's container `ob1.tier-half=source|target`, and removes each half's env file as soon as its container is made.
- `deploy/test-tier-sh.ts` (pass 2; CI's repo-consistency job and ci-parity) runs tier.sh against a stub runtime: canary.sh's call gives two containers, one network each; the source half's env file holds `--from`'s URL alone and never the canary's password, the target's the canary's password and the named settings alone; both halves get the arguments; the source container goes before the target starts; a failed source half stops the run; a half that never ran is named; and every refusal is exit 2 before anything is built.
- `tier.ts`'s source halves make the hand-off directory themselves, mode 700, and refuse one that exists (an existing one keeps its own mode).
- `deploy/canary.sh` gives tier.sh `--from-network` (stable's data network, read off its Postgres) and `--network` (the canary's), and `--project <canary>`, so the canary's refreshes build `<canary>-tier`.
- CI:
  - the tier step: a run for project `ob1x` builds `ob1x-tier` and leaves `open-brain-tier:latest`'s id where it was, and `--network` with a list is refused;
  - the tier step's image check points `open-brain-tier:latest` at another image first, since the same Dockerfile builds the same id from cache, and puts it back after;
  - the canary step samples the tier halves' containers every 0.2 s through the first `up`'s refresh (each lives from tier.sh's create to its exit, so a short half is still seen; sampling the networks missed both halves in a local run). No container may be on both, a tier half must be seen on each side, each half's environment must hold its own side's database password, and neither may hold the other's.
- `deploy/README.md`, `db/README.md` and `docs/one-brain-per-stack.md` (row 9, "The tier tools") describe the halves; the cross-project `--network` examples are gone.

**Why.** `deploy/tier.sh --diff` ran `tier.ts` in one container on both brains' data networks and stable's egress, with a superuser URL for each (SMD-2872's ADR, "The tier tool joins both brains"). SMD-2872 has a brain's data network joined by nothing outside its own project. Replay and diff need no database: the read surface already answers every question they ask.

**What is measured now (the maintainer's choice).** Item 2 of the ticket offered two means: split the Postgres engine across the two projects, measuring the same thing, or move onto HTTP, measuring something else. The maintainer chose HTTP:
- the canary is diffed against stable as it answers now, not against the ids stable logged, so a thought stable gained since the refresh can read as a move; the report's id-set line counts what each holds that the other does not;
- `list_logged_searches` gives the query and arm, so a search replays with the tool's defaults, not its logged `match_count`, threshold, recency weight or filter;
- each brain embeds the query itself, through its own server's egress gate;
- the replays are real searches, which a brain logging searches logs.
