## Changelog

`db/tier.ts --replay` and `--diff` reach the two brains over HTTP, each at its own MCP URL or connector name with its own key, and `deploy/tier.sh` runs `--refresh` and `--promote` as two halves, each in a container on one brain's data network with that brain's password alone: no container joins both brains or holds both passwords. A script must change: `tier.sh --replay`/`--diff`, a `--network` list and `tier.ts --diff --from postgres://…` exit 2; the diff is `OB1_COMPARE_KEY=<read key> bun --no-env-file db/tier.ts --diff --from <stable> --to <canary>`, against a stable with `OB1_QUERY_LOG=on`; tier.sh no longer joins `egress`, and runs from a git checkout (SMD-2875).

## FORK

Tier tools without joining another brain's networks — replay and diff over HTTP, refresh and promote one half per brain (SMD-2875)

**What changed: replay and diff over HTTP (PR 1).**
- `db/tier.ts --replay` / `--diff` take `--from <stable>` and `--to <canary>` as each brain's MCP URL or Claude Code connector name. A key is `--from-key`/`--to-key`, else the connector's header or the URL's `?key=`, else `OB1_COMPARE_KEY`, which then goes to both brains. `db/brain-compare.ts`'s `runTierReplay` replays stable's logged searches (`list_logged_searches`: at most a page of the most recent, after `--since` if given), each on the arm that ran it and each (query, arm) once, on both brains, and diffs the ids. The report is `--compare`'s, then the window, the counts and the verdict.
- A search both brains fail is skipped; one that one brain fails while the other answers is a failure, shown as `✗ … b failed, a answered`. `--diff` exits 0 unmoved; 1 when a ranking moved, stable's log could not be read, or a search failed on one brain; 3 when nothing was compared (an empty window, every search failed by both, or only rows logged before 045, counted as such). `--replay` reports, and exits 1 on an unread log or a one-sided failure. `--compare` counts a one-sided failure as a delta.
- A `postgres://` side is refused (exit 2). The HTTP client follows no redirect, and an invalid URL's refusal never echoes its user or password.
- The Postgres replay engine and the replay's own embedder are gone; each brain embeds its own query. tier.sh refuses `--replay`/`--diff`, and no longer hands on `OPENROUTER_API_KEY`.

**What changed: refresh and promote one half per brain (PR 2).**
- `db/tier.ts --refresh` and `--promote` each run as two halves sharing a directory, `--handoff <dir>` (made mode 700; an existing one is refused). Given `--from` and `--to`, both run in one process, the target's guards before anything is dumped.
  - A refresh's source half reads the source's facts (where it is, its major, its database-level settings) and dumps it, as `pg_read_all_data` where that role reads all the login would (no table with row-level security, no large object). It writes `source.json` (mode 600) beside the dump.
  - The target half refuses a hand-off that is not one, runs every guard on `--to` as before, then marks, resets, restores, copies the settings, migrates and stamps.
  - A promote's source half reads the canary's identity and `schema_version`; its target half refuses stable as its own canary, then stamps it.
- `sameDatabase` compares the identity each server reports (`system_identifier`, the postmaster's start, the database name), since neither half reaches the other's database.
- `deploy/tier.sh` runs each half in a container on one side's data network alone, with an env file holding that side's URL alone, removed at create. The hand-off passes container to container with `cp … - | cp -a - …`; the source's container is removed before the target starts. The target half gets, by name, only the settings a migration reads, `OB1_TIER` and its password. Each half is handed, by `cp`, every file git tracks under `db`, `evals`, `scripts`, `server-portable` and `plugins`, and an untracked one only when it is code (SQL only in a migrations directory), never an env file's name nor a directory: the checkout is not mounted, so no env file is in either container.
- Each side is a project: `--to`'s from `--env-file` or `--project`, `--from`'s from `--from-env-file` or `--from-project`. Refused: a list of networks; `--from-project` with `--from-network`; a short-form `--from` on another network without `--from-env-file`; `--from-env-file` with both sides on one network; a shell `COMPOSE_PROJECT_NAME` beside `--from-env-file` unless the projects are named; `--flag=VALUE`; `--handoff`. The image is `<project>-tier:latest`, the `--to` side's project. Compose's words are never relayed; the message names the command that shows them.
- `deploy/canary.sh` gives tier.sh `--project <canary>`, `--network <canary>_data` and `--from-network` (stable's, read off its Postgres).
- CI: the tier step checks the image name (with `open-brain-tier:latest` pointed elsewhere first) and the list refusal; the canary step samples the halves' containers, by label, through the first refresh: none on both brains' networks, each holding its own side's password and not the other's. `deploy/test-tier-sh.ts` (repo-consistency, ci-parity) runs tier.sh against a stub runtime.

**Why.** `deploy/tier.sh` ran `tier.ts` in one container on both brains' data networks (and stable's egress for a `--diff`), with a superuser URL for each (SMD-2872's ADR, "The tier tool joins both brains"). SMD-2872 has a brain's data network joined by nothing outside its own project. Replay and diff need no database; a refresh needs one container per side and a hand-off between them. Each half is still its own brain's superuser, inside its own project.

**What is measured now (the maintainer's choice).** Item 2 of the ticket offered splitting the Postgres engine, measuring the same thing, or moving onto HTTP, measuring something else. The maintainer chose HTTP: the canary is diffed against stable as it answers now, not against the ids stable logged; a search replays with the tool's defaults, not its logged arguments; each brain embeds the query itself; the replays are real searches, which a brain logging searches logs.
