## Changelog

Migration 117 adds open items. A to-do, a commitment or a plugin's task gets an id, a text, an optional owner and due time, and a status: proposed, open, done or dropped. Every change is kept as an event, stamped with the key that made it. An item can come from a thought, where it is noted at the thought's capture time, or stand for a plugin's row. A proposed close names the thought that shows it and waits for a key other than its proposer to accept it. The calls are `open_item`, `update_item`, `set_item_status`, `propose_item_close`, `decide_item_close` and `open_item_history`, with a new **items** grant group. Priority assertions now reach open items (kind `item`), and a capture-only key may state a priority on an item it opened. If your server connects as a `--grant` role, re-run `migrate.ts --grant` after upgrading so the role gets the `items` group and the `priority` group's two new grants (SMD-3665).

## FORK

Open items in the core, PR 1 of 4: a to-do gets an id, a status and a history, and a proposed close waits for another key (SMD-3665)

**What changed.** Migration 117 is SMD-3665's store, the first of four PRs (the maintainer's plan, 2026-11-03).
- **The tables:**
  - `open_item_events`: one row per change (opened, updated or status). Each row carries the item's whole state after it, its maker stamped from the envelope as 116 stamps a priority's, and a reason. The opening alone carries where the item came from (a thought; a plugin row) and `noted_at`, the thought's capture time. A trigger refuses every UPDATE, DELETE and TRUNCATE.
  - `open_items`: the projection, kept current in the write's transaction. It has a drift check with its own copy of the rule, and a rebuild.
  - `open_item_close_proposals`: a close to done or dropped, with its evidence thought, a label and a reason. A row changes only to be decided, once.
- **The rules:**
  - **Statuses:** `proposed` is a start state alone, which is how the extractor's items (PR 3) start. A key confirms one (open) or dismisses it (dropped). Settling an item moots its pending proposals.
  - **A proposal never closes an item alone:** a key other than its proposer accepts it (`PROPOSAL_YOURS` otherwise). The proposer may withdraw it by rejecting it.
  - **The same item again:** opening the same thought and text, or the same plugin row, answers `unchanged` with the item that is there, so the extractor and a backfill re-run open nothing twice. Every write that changes nothing is `unchanged`.
  - **Who may, failing closed as 116:** the envelope must state `write` or `capture`.
    - A capture-only key may open an item, but from a thought only if it captured that thought.
    - It may change only an item it opened, under its envelope's agent id, that no other key has changed since, or one that stands for a row of the plugin its call came through. A plugin hook, `hook:<plugin>`, has no agent id.
    - Both checks are asked before any existence answer.
    - A plugin row's plugin is read from the envelope, never from an argument.
- **116, for the fourth kind:**
  - `ob1_priority_item_exists` answers kind `item` from `open_items`.
  - `assert_priority`'s capture rule admits an open item the key owns.
  - Both functions are replaced whole; every other rule is as 116 wrote it.
  - The server's refusal and the `set_priority` description no longer say open items arrive later.
- **Grants:**
  - The new **items** group: `SELECT, INSERT` on the events, all four privileges on the projection, and `SELECT, INSERT, UPDATE` on the proposals.
  - The **priority** group gains `SELECT` on `open_items` and `open_item_events`.
- **Registered:** `db/README.md`, `db/test-support.ts`'s drop lists, test-upgrade's window, `config.d.mts`, `version.ts`.

**Why.** Outside Linear the brain's open work was `metadata.action_items`, a list of strings with no id, owner, due time or status. Nothing closed one, so every to-do ever captured read as open, and none could carry a priority (docs/priority.md decision 1's fourth kind, which 116 refused until now).
