## Changelog

`db/ingest-records.ts` rebuilds a brain from the records it derives from — FORK.md changes, git commits since the pin, a Linear corpus dump, the memory files — each row source-labelled and written bare for `db/reembed.ts` to embed; a `tier` preflight check and `OB1_TIER` report which pipeline tier a brain is (SMD-1806).

`db/tier.ts` and `deploy/compose.tiers.yaml` add the canary and working tiers: `--refresh` snapshots stable into a tier with `pg_dump`/`pg_restore` and migrates it forward, `--replay`/`--diff` re-run stable's logged searches against the canary and report what moved, `--promote` stamps the soaked version onto stable — three brains on three loopback ports over one shared Ollama (SMD-1806).

## FORK

The stable brain is a derived view over the records, rebuilt by one tool — `db/ingest-records.ts`, with a `tier` the brain reports (SMD-1806)

SMD-1806 wants three brains as a promotion pipeline over one corpus: **stable**
(the record, the only writer) → **main canary** (refreshed and replayed on every
merge) → **working** (per worktree, disposable), so the fork runs its own code on
its own memory and a migration meets real vectors before an operator does. The
canary and working tiers need a `query_log.tier` column (SMD-1490 owns the log's
column set) and the log's hot-path fixes (SMD-1492), and they run SMD-1805's
published images (SMD-1860) — none of which exists yet. This change is the tier
that is unblocked, and the premise the other two stand on: **the brain is a
derived view over the records, never the record itself**, so the stable tier holds
nothing a wipe would lose. Its cost is one re-ingest.

**`db/ingest-records.ts` — the records to rows.** Four sources, each a pure
reader: `fork` (FORK.md's numbered `### N.` change sections, in the tree),
`commit` (git commit messages since the upstream pin — the fork's whole delta, the
span FORK.md documents), `linear` (a corpus dump built by
`evals/build-linear-corpus.ts`, `--linear`), and `memory` (the `*.md` memory files,
`--memory-dir`/`OB1_MEMORY_DIR` — they live outside the repo, so there is no
portable default and the tool reads, never writes, them; `MEMORY.md`, the
truncated index this pipeline exists to beat, is excluded). `--source all` (the
default) ingests every source it has an input for and says on stderr which it
skipped. Each record becomes one thought row with a **deterministic id** (the
`linearThoughtId` construction, generalised over a source-qualified key, so a
Linear ticket lands on the same id whether ingested here or by the eval corpus
loader) and a **`metadata.source` label** — SMD-1806 rule 5, so an agent-written
capture is one source among four and SMD-1724's trust question has an answer from
day one. The upsert is keyed on that id: same id and content is a no-op, an edited
record updates in place, a new record inserts; a different record whose content is
byte-identical to one already stored is skipped on the partial-unique fingerprint
index rather than crashing the run. So a rebuild after a wipe, or after editing a
memory file, writes exactly the rows that moved.

**Bare rows, then reembed.** The ingester writes no vectors and no chunks — that
is the owned embedding path's job. After an ingest, `db/reembed.ts` walks the new
rows through the claim table (015/031) and embeds them exactly as a capture would,
chunking long records through `update_thought`. The rebuild is two commands
(`ingest-records.ts` then `reembed.ts`), and the same claim path a branch that
changes the embedding model would re-embed its copy through.

**The brain says which tier it is.** `OB1_TIER` (`stable`|`canary`|`working`,
default `stable`); the ingester stamps `ob1_config.tier` and `.last_ingest` on
every run — plain KV writes, no migration — and preflight's new `tier` check
reports them beside the schema version, warning when a server's `OB1_TIER`
disagrees with the tier its database was stamped as (a working server pointed at
the stable database), the failure the one-writer rule exists to prevent.

**The canary and working tiers — the engine, the stack.** `db/tier.ts` is the
promotion engine and `deploy/compose.tiers.yaml` the three-brain stack (three
Postgres, one shared Ollama, three servers on loopback ports 8010/8011/8012, built
from the checkout). `--refresh --from <stable> --to <canary>` takes a faithful
whole-database snapshot with `pg_dump | pg_restore` (thoughts, vectors, chunks,
query_log, provenance, agents, audit — so a migration meets *all* the real data),
resets the target and restores, then runs `migrate.ts` forward; it is destructive
to `--to` and refuses a non-loopback target unless `OB1_ALLOW_REMOTE_DB=1`, and
needs a `pg_dump`/`pg_restore` at least as new as the source server (the image
carries them). `--replay`/`--diff` are the live half of the replay gate: for each
search stable logged since the last refresh, re-run the query against the canary
through the shipped retrieval and diff the returned ids against the ids stable
recorded — the per-PR "what moved", measured. The keyword arm replays model-free
(the arm `test-live` [20] drives end to end against a real second database, with
teeth: an identical canary reproduces stable's rankings, a perturbed one is
caught); the hybrid arm re-embeds the query and replays only with a provider
(`OB1_EVAL_EMBED`), as `evals/eval-replay.ts` does. `--promote` stamps the soaked
version onto stable.

**Which numbers each half owns.** The offline replay gate (SMD-1295) is the
keyless, fixture-vector half that runs in CI (`db/test-replay.ts`); the canary's
replay — real vectors, real queries, on merge — is the live half, `db/tier.ts`
above. A PR cites the offline gate's numbers today; it will cite the canary's
measured "what moved" once the canary runs in CI.

**Still deferred to SMD-1805 + SMD-1860.** The *canary CI job on push to `main`*
— which refreshes, replays and diffs against the **published** images through the
merge queue and comments the result on the merged PR — needs SMD-1805's merge
queue and SMD-1860's published images (neither cut yet); `--promote`'s
image-repoint half needs the images too. The engine, the stack and the end-to-end
test do not, and are here now. The `pg_dump` refresh path itself is exercised by
the compose stack, not the fixture CI, which has no client tools that can read the
pg16 server — the same split as the model-backed replay.

**Upstream status:** not sent — upstream ships from `main` with no version, no
tiers and no record to derive a brain from; this is the fork's release pipeline.
