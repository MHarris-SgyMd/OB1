## Record

Re-embed on the claim loop, and no further: its reading of an embedding call's error and its release stay its own, the ticket's PR 3 (SMD-4308)

**The ticket's question.** Work 3 moves reembed.ts onto the driver "with its batch embedding and drain as hooks", and says to drop the PR if the hooks cost more than the copy. Read against what PRs 2a to 2c made (change 531, released in v2.1.0), the answer differs by part.

- **The loop around a thought: moved.** `worker()` in reembed.ts was the same loop as the other two with four differences, each now an option of `claimWorker`. `beforeClaim`: its follower reads the record's embedding model before each claim, and ends when a `--switch-model` run has moved it. `afterGate`: that same move ends a worker that waited at the admit gate. `leaseReturn.refusedLine` and `leaseReturn.saysReturned`: its own words for a return of the leases the database refused, and every return that freed rows said, a follower's too. `leaseReturn.inactiveWhateverTheWriter`: the worker leaves the pass's active set even when the Writer throws on that line, which the other two engines do not do; each keeps what it did.
- **The set-back of an aborted call: moved,** onto `setBackAborted` as it stood. Re-embed has no `--limit`, so it passes a limit of 0.
- **What an embedding call's error means: not moved.** Re-embed has no pauses: a fault to pause for is an outage at once. Its probe is an embedding call that is part of the call in hand, counted in that call's slot wait and aborted with it. A one-shot run halts on a first answer shaped like the configuration's. `thoughtFault` would need a hook for each, and what would be left in common is the two database lines and the suspect's blame.
- **The release of a finished claim: not moved.** Re-embed's says a caveat for a success and for a claim lost, tells the progress line for a deleted thought, and ends its lapse line differently. `releaseFinished` would need three more options for one caller.

`worker()` in reembed.ts goes from 344 lines to 278.

`db/claim-loop.ts` joins the import runner's copy list in `deploy/orchestration/runner.Dockerfile`, which builds reembed.ts; `.dockerignore` has let it in since PR 2a. The image's `bun build` step, rehearsed on a scratch copy of what the Dockerfile copies, resolves with the file and fails on `./claim-loop.ts` without it (caught: run-it).
