## Changelog

The claim workers and the scheduler read their numeric options through one reader in `db/cli.ts` (SMD-4308, PR 1). No behaviour changes: every default, rule and refusal is as it was.

The entity extractor and the consolidation pass run their workers on one claim loop, `db/claim-loop.ts` (SMD-4308, PR 2a). No behaviour changes: each worker claims, beats, stops and returns its leases as it did.

## Record

One reader for the engines' numeric options — `optionReader` in db/cli.ts, in place of the copy each `numbers()` held, the ticket's PR 1 (SMD-4308)

**Problem.** `consolidate.ts`, `extract-entities.ts` and `sleep.ts` each defined the same `read(flag, value, absent, rule)` closure inside `numbers()`, and `reembed.ts` held it as `readOption`: the option given, held to its flag's rule by `numberProblem`, the CLI's default when absent, and a refusal with the script's flag list under it. Four copies of five lines, differing only in whether the rule had a default and whether its type named `fraction`.

**Change.** `db/cli.ts` exports `optionReader(spec, hints)`, which returns that reader bound to a script's flags. The four `numbers()` functions, and reembed's `leaseNumbers()`, call it. The rule defaults to a whole number >= 1, as three of the four copies had it; `sleep.ts` passes a rule at every call, so the default changes nothing there. The flag list is still built only when a rule is broken.

**Verify.** `test-engines.ts` gains two rows on the reader itself: the default for an absent option and the option when its rule holds; and a broken rule refused in `numberProblem`'s words with the flag list under them. The engines' refusals were already pinned through each worker: with the flag list dropped from the reader, 40 of test-engines' rows fail (caught: mutant).

This is the first of the ticket's PRs. The claim loop itself, which the workers still each hold, is PR 2.

### PR 2a — the loop around a thought: db/claim-loop.ts

**Problem.** `worker()` in `consolidate.ts` (420 lines) and in `extract-entities.ts` (483) were one loop written twice around different work. The first 82 lines of each, up to the row a beat found lost, differed in two: the worker id's first word and the columns of the row SELECT. The closing `finally` differed in the extractor's two extra steps. Between them sat each engine's own work on a thought.

**Change.** `db/claim-loop.ts` exports `claimWorker`, one worker of a pass from its first claim to the return of its leases. It holds the worker id and heartbeat, the admit gate before each claim, `--limit`'s count of what is taken and being claimed, the claim, the lost-at-a-beat skip, and the `finally` that returns what is still held. Each engine passes what is its own: `readRows`, its row SELECT, and `row`, its work on one claimed thought with its release, which answers `"stop"` or `"next"` where the loop's body said `return` or `continue`. The extractor passes two more, for the two steps its `finally` had: `finallyFirst` drops the thought in hand, and `beforeReturn` waits for a hard stop's count.

The engines' state is read where the loop needs it, not copied. A flag that changes under a running worker is passed as a function: the stop, the hard stop, the pass's gate, whether the pass is retrying an outage's suspects. `--limit`'s claims in flight became `{ n }`, so the loop and the engine count on one object. The counts the loop reports go through `count`.

Each `row` body is the old loop body moved, not rewritten: two levels of indentation less, `return` now `return "stop"` (18 in consolidate, 21 in extract), a `continue` of the batch loop now `return "next"` (6 in each), and nothing else. The `continue`s of the retry loop inside, and the `return` of `joinHalted`, are as they were. A script made the move and counted them.

`db/claim-loop.ts` joins the server image's copy list and `.dockerignore`'s allow-list, since the coordinator runs both passes from that image; `db/test-coordinator.ts` holds the lists to the passes' import graph and failed until it did (caught: automated). The import runner's image builds neither engine, so its list is as it was.

**Verify.** `./db/ci-parity.sh` passes but for test-live's rest shard, which stops at parity's 600 s limit on the maintainer's Mac under load, with no failed row; run alone it passes, 1,419 of 1,419, as on main. The other four shards keep their counts (sleep 178, long 369, extract 384, sweep 62).

Six mutants of the loop were first run against test-live's rest shard, which holds the sections that drive the workers ([10], [16]). Four died there: `--limit`'s count dropped, the heartbeat's set never told of a claim, the leases not returned, the admit gate skipped. Two lived: the lost-at-a-beat skip dropped, and an isolated pass taking its whole batch. Neither is new: the loop is the code main has, moved. `test-engines.ts` now drives `claimWorker` over a stand-in for the database, 11 rows, no Postgres: the batches claimed and the leases' return, the worker's id, what a one-shot run and a follower say at the return, the lost row skipped and counted by what its row says, an engine's `"stop"`, `--limit`'s room, the isolated pass's one thought a claim and its end, and a claim refused in passing and for good. Against those rows ten of eleven mutants die, the two survivors among them; the eleventh, the admit gate skipped, dies in the rest shard (caught: mutant).

**Not in this PR.** What a thought's processing does with an error — the pauses, the probe, the outage and its suspects — is still in each engine, with about a dozen points where the two differ. So is the release of a finished claim. Those are the ticket's PR 2b.
