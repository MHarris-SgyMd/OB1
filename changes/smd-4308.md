## Changelog

The claim workers and the scheduler read their numeric options through one reader in `db/cli.ts` (SMD-4308, PR 1). No behaviour changes: every default, rule and refusal is as it was.

The entity extractor and the consolidation pass run their workers on one claim loop, `db/claim-loop.ts` (SMD-4308, PRs 2a to 2c): the loop around a thought, what a failed call means (when a failing provider is paused for, probed or waited out, and when the thought is failed), an aborted call set back, and what a finished claim's release finds. No behaviour changes: each worker claims, beats, stops and returns its leases as it did, and every line it prints and every outcome is as it was.

## Record

One reader for the engines' numeric options — `optionReader` in db/cli.ts, in place of the copy each `numbers()` held, the ticket's PR 1 (SMD-4308)

**Problem.** `consolidate.ts`, `extract-entities.ts` and `sleep.ts` each defined the same `read(flag, value, absent, rule)` closure inside `numbers()`, and `reembed.ts` held it as `readOption`: the option given, held to its flag's rule by `numberProblem`, the CLI's default when absent, and a refusal with the script's flag list under it. Four copies of five lines, differing only in whether the rule had a default and whether its type named `fraction`.

**Change.** `db/cli.ts` exports `optionReader(spec, hints)`, which returns that reader bound to a script's flags. The four `numbers()` functions, and reembed's `leaseNumbers()`, call it. The rule defaults to a whole number >= 1, as three of the four copies had it; `sleep.ts` passes a rule at every call, so the default changes nothing there. The flag list is still built only when a rule is broken.

**Verify.** `test-engines.ts` gains two rows on the reader itself: the default for an absent option and the option when its rule holds; and a broken rule refused in `numberProblem`'s words with the flag list under them. The engines' refusals were already pinned through each worker: with the flag list dropped from the reader, 40 of test-engines' rows fail (caught: mutant).

This is the first of the ticket's PRs. The claim loop itself, which the workers still each hold, is PR 2.

### PR 2a — the loop around a thought: db/claim-loop.ts

**Problem.** `worker()` in `consolidate.ts` (420 lines) and in `extract-entities.ts` (483) were one loop written twice around different work. The first 82 lines of each, up to the row a beat found lost, differed in two: the worker id's first word and the columns of the row SELECT. The closing `finally` differed in the extractor's two extra steps. Between them sat each engine's own work on a thought.

**Change.** `db/claim-loop.ts` exports `claimWorker`, one worker of a pass from its first claim to the return of its leases. It holds the worker id and heartbeat, the admit gate before each claim, `--limit`'s count of what is taken and being claimed, the claim, the lost-at-a-beat skip, and the `finally` that returns what is still held. Each engine passes what is its own: `readRows`, its row SELECT, and `row`, its work on one claimed thought with its release, which answers `"stop"` or `"next"` where the loop's body said `return` or `continue`. The extractor passes two more, for the two steps its `finally` had: `finallyFirst` drops the thought in hand, and `beforeReturn` waits for a hard stop's count.

The engines' state is read where the loop needs it, not copied. A flag that changes under a running worker is passed as a function: the stop, the hard stop, the pass's gate, whether the pass is retrying an outage's suspects. `--limit`'s claims in flight became `{ n }`, so the loop and the engine count on one object, and whether the limit is met stays the engine's `limitReached`, passed in: its pass reads the same rule, and the loop holds no second copy of it. The counts the loop reports go through `count`.

Each `row` body is the old loop body moved, not rewritten: two levels of indentation less, `return` now `return "stop"` (18 in consolidate, 21 in extract), a `continue` of the batch loop now `return "next"` (6 in each), and nothing else. The `continue`s of the retry loop inside, and the `return` of `joinHalted`, are as they were. A script made the move and counted them.

`db/claim-loop.ts` joins the server image's copy list and `.dockerignore`'s allow-list, since the coordinator runs both passes from that image; `db/test-coordinator.ts` holds the lists to the passes' import graph and failed until it did (caught: automated). The import runner's image builds neither engine, so its list is as it was.

**Verify.** `./db/ci-parity.sh` passes but for test-live's rest shard, which stops at parity's 600 s limit on the maintainer's Mac under load, with no failed row; run alone it passes, 1,419 of 1,419, as on main. The other four shards keep their counts (sleep 178, long 369, extract 384, sweep 62).

Six mutants of the loop were first run against test-live's rest shard, which holds the sections that drive the workers ([10], [16]). Four died there: `--limit`'s count dropped, the heartbeat's set never told of a claim, the leases not returned, the admit gate skipped. Two lived: the lost-at-a-beat skip dropped, and an isolated pass taking its whole batch. Neither is new: the loop is the code main has, moved. `test-engines.ts` now drives `claimWorker` over a stand-in for the database, 13 rows, no Postgres: the batches claimed and the leases' return, the worker's id, what a one-shot run and a follower say at the return, the lost row skipped and counted by what its row says, an engine's `"stop"`, `--limit`'s room, the isolated pass's one thought a claim and its end, a worker waiting at a closed admit gate and a stop reaching it there, and a claim refused in passing and for good. Against those rows all eleven mutants die, the two survivors among them (caught: mutant).

**Not in this PR.** What a thought's processing does with an error — the pauses, the probe, the outage and its suspects — is still in each engine, with about a dozen points where the two differ. So is the release of a finished claim. Those are later PRs of the ticket: PR 2b takes the first.

### PR 2b — what a failed call means: thoughtFault and recordFailedAndStop

**Problem.** After PR 2a each engine's `row` still held the same 130 to 140 lines in its `catch`, from the database's errors on: the database gone, its end and its moment; the provider's error read through `fault`; the probe; the outage, its suspects and the blame of one retried alone; the request refused; the pauses. Below the retry loop each held the same 36 to 40 lines recording a failure the worker stops after. SMD-3866, SMD-4196, SMD-4166 and SMD-4146 are all bugs in that code, and each names both engines.

**Change.** `db/claim-loop.ts` exports two functions.

- `thoughtFault(host, thought, e)` reads an error a thought's call threw and answers what the worker does next: `stop`, the thought back in the pool; `again`, after a pause; or `failed`, with the error to record and whether the worker stops after it. It throws the database's end, as the code did.
- `recordFailedAndStop(host, …)` records that failure, counts it, and says the two closing lines.

Each engine builds one `FaultHost` as a worker starts. It holds the engine's state where it is read (the stop, the hard stop, the pass's halt, the outage), and the points where the two engines differ, each a function:

| Hook | consolidate.ts | extract-entities.ts |
|---|---|---|
| `read` | `classifyError`, or `fault` with the judge's request rule | `classifyError` with `maxTokensFatal`, or `fault` with the extractor's request rule and the escalation model's absence |
| `probe` | the pair's timeout | the same, on the model the refused call was made to |
| `probedOut` | `ProviderDown`: its own probe already found no answer | none |
| `onProbeRefused` | the tier's refusal noted | none |
| `onOutage` | none | the escalation model gone since the start: the outage probes it |
| `fatal` | what to fix, the tier's refusal, every worker stopped | what to fix, the escalation model's knob, every worker stopped |
| `onPaused` | none | the thought's clock starts again |
| `unrecorded` | the judged count and the ticket calls taken back | none |

One reading changed in form and not in effect: the extractor read a database error as `FOLLOW ? followClassify(e) : null`, consolidation as `FOLLOW && !hardStopped ? …`. The extractor returns on the hard stop earlier in its `catch`, so the second form is true of both, and it is the one kept.

Each engine's own exceptions are still read in its `catch` before `thoughtFault`: the admit gate's, a stop between pairs or windows, a call aborted in hand, a claim gone at the gate. So is the release of a finished claim.

**Verify.** `test-engines.ts` drives both functions over a stand-in engine, 21 rows, no Postgres and no wall clock (the pauses are a millisecond): the database gone, its end thrown, its moment, and neither read apart without `--follow` or past the hard stop; the thought's own error cut to 500 characters; the request refused; the probe answering, refused and unanswered; an outage with and without a suspect; a stopping pass and a standing outage, each unprobed; the pauses, the outage past them, and a one-shot run's failure there; a stop and another worker's outage during a pause; a transient error not paused for on a stopping pass or under a standing outage; a suspect alone blamed four ways, and not probed twice; and the record of a failure five ways. Thirty-seven mutants of the two functions, one edit each, all die in those rows (caught: mutant).

`./db/ci-parity.sh` passes, 115 rows of 115, test-live's shards at their counts (rest 1,425, sleep 179, long 369, extract 384, sweep 62). Four mutants of SMD-2599's table, which named each engine apart, now land in `thoughtFault` once, and each dies in test-live's rest shard as it did: a database cut mid-thought read as the provider's (2 rows fail), a transient error past the pauses no outage (43), a timeout never probed (10), a missing model no outage (8).

The hooks each engine passes were then mutated where they are passed, one per hook and two for `fatal`, against test-live. Five die: consolidation's `fatal` not noting the tier's refusal (rest shard), and in the long shard the extractor's `read` calling a missing escalation model an outage, its `probe` always on the metadata model, its `onOutage` never probing the escalation model, and its `fatal` not naming the escalation model's setting. Four live through the rest, long and sleep shards: consolidation's `probedOut` never true, its `onProbeRefused` not noting the tier's refusal at the first probe, its `unrecorded` not taking the judged count back, and the extractor's `onPaused` not restarting the thought's clock. Each is the line main had, moved, so each is a row main lacks, not a change here; they are not added in this PR, and SMD-4352 asks for them (caught: mutant). The extractor's `onPaused` mutant failed one row in its first long-shard run, "consolidation goes first: no stuck call between the join and the judgement's answer" at 552 ms, and none in a second: that row's timing, which SMD-3862 already records, not the mutant.

### PR 2c — an aborted call set back, and what a release finds: setBackAborted and releaseFinished

**Problem.** Two blocks were still written twice. A call the pass's caller aborted is set back in the queue by the same 13 lines in each engine, differing in one word of one message. The release of a finished claim is 46 lines in consolidate.ts and 72 in extract-entities.ts; the statement differs, and so do two message clauses and the counts of a success, but what the release finds is read the same way: the database gone, the thought deleted, the claim no longer this worker's, the hard stop's release beating this one, a failure, a success.

**Change.** `db/claim-loop.ts` exports two more functions over a `ReleaseHost`, which each engine's one host object also is.

- `setBackAborted(host, thought, call)` sets the thought back and answers `"stop"` when the database refuses, or whether the claim was gone. `call` is the engine's word for the call: "judge call" or "call".
- `releaseFinished(host, thought, f)` runs `f.release`, the engine's own statement, and reads what it found. The engine passes the failure's text or null, its word for what it does to a thought ("judged", "extracted"), the reasons it knows a claim may be gone at release, and its counts of a success.

The extractor's statement, which spends the thought's kept windows with the release and falls back to the release alone when that table is gone, is its old lines inside `f.release`. Each engine reads `outcome` there through a constant, so the callbacks keep its narrowed type.

Still each engine's: its own exceptions before `thoughtFault`, the three short branches for a thought vanished, lost or set back, and the outcome only it has (consolidation's `moved`, the extractor's `superseded`).

**Verify.** `test-engines.ts` drives both functions over a stand-in engine, 7 rows: the set-back with and without `--limit`, a claim gone at the set-back by what its row says, and the set-back refused; a release that went through for a success and for a failure, a claim gone at release with and without a failure, the thought deleted, the hard stop's release first, and the release refused with the database gone, without `--follow`, and for another reason. Twenty-three mutants of the two functions, one edit each, all die in those rows (caught: mutant).


`./db/ci-parity.sh`: 117 rows green; test-live's rest shard stopped at the 600 s limit with no failed row, the Mac under load, and alone passes 1,429 of 1,429. Seven mutants of what each engine passes, against the rest shard: the four that change an outcome die (a failure passed as a success, in each engine; a success uncounted in consolidation; windows left out uncounted in the extractor). The three that change only a message's words live there, and through the long and sleep shards, rows main lacks that SMD-4352 now also asks for: consolidation's "judged" in the deleted-thought line, the extractor's "an edit requeued it" among the lapse reasons, and consolidation's "judge call" in the set-back's refusal (caught: mutant).
