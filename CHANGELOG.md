# Changelog

All notable changes to Daemonic Brain are recorded here, newest first, following
[Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) and
[Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html).

This page is the short companion to the record — one file per change under
[`changes/`](changes/README.md), indexed there, and changes 1–17 in
[`FORK.md`](FORK.md)'s table: why each change was made, what was measured, what
was declined. Changes 1–103 predate the first release; this changelog begins at
the first cut. [`MAINTAINING.md`](MAINTAINING.md)'s "Versioning" and "Cutting a
release" have the scheme and how a release is assembled from
`changes/smd-NNNN.md` fragments.

## [2.0.0] - 2026-11-06

### Added
- `deploy/canary.sh up --no-refresh` brings a standing canary level in place, keeping the rows only it holds: its env file and keys are mended as `up` does, this checkout's `migrate` run on its own database, and the servers, proxy and forwarder recreated on the new build. Every other `up` still refreshes it from stable; `--no-refresh` is refused, changing nothing, on a canary with no database to keep. Either form now stops the canary's servers and a running `sleep` worker before its Postgres is touched and brings the worker back, and refuses a running service of another profile (SMD-3154).
- The MCP server built on the REST core (`mcp-server/`) accepts the authorization server's tokens at `/mcp`, at a scan's job links and at the worker mirrors. It trades each one at the authorization server (RFC 8693) for a token the REST core accepts, and never sends a client's token on. It needs `OB1_AUTH_SECRET_MCP` beside `COMPOSE_PROFILES` naming `auth` and the REST core's `OB1_PUBLIC_ORIGIN`, and warns at the start when they disagree. A refused token is 401 `invalid_token`, or 503 while the authorization server is down, so a client is never sent to a sign-in that cannot finish; scopes that reach no operation are 403 `insufficient_scope`. It serves `/mcp` once its compose service lands; until then the `/mcp` that serves still refuses tokens. **Upgrading:** on a stack with the `auth` profile, a raw access key with dots sent as `Authorization: Bearer` reads as a token here; send it as `x-brain-key` or `?key=` (SMD-2286).
- Preflight has a `thought indexes` row: it warns when an index on `thoughts` that a read is planned around is INVALID or of another shape, or missing on a brain whose ledger records its migration, naming what reads slower and the statements that mend it — or, for an INVALID one while an index operation runs on it or holds `thoughts`, the pid to wait for (SMD-3146). It covers `thoughts_vectorless_idx` (100), `thoughts_trust_rank_idx` (074), the fingerprint's unique index (003) and five others, and names an INVALID index left on `thoughts`: a cancelled `REINDEX CONCURRENTLY`'s copy to drop, anyone else's to rebuild. The `trigram index` row now also says when its index is INVALID, and waits out an index operation holding `thoughts`.
- The `observability` profile's Grafana now loads five alert rules into the Daemonic Brain folder: a server that stopped sending metrics, a server failing over 5% of its requests, the model provider failing calls, the exporter not reaching Postgres, and the collector losing telemetry. No contact point ships, so a rule that fires stays in Grafana's alert list until you add one (`deploy/README.md`, "Alerts"). The servers now send a `process.uptime` gauge with their metrics; `scripts/inline-dashboard.ts` is now `scripts/inline-grafana.ts` (SMD-3050). Upgrading with the profile on: the first `up -d` recreates `lgtm`, whose labels now carry the rules' sha256, so Prometheus, Loki and Tempo restart once (SMD-3050).
- **Breaking:** compose refuses a stack without `OB1_FORWARDER_KEY`. `/mcp`, `/health` and the protected-resource document are served by the MCP server built on the REST core (`mcp-server/`), as compose's new `mcp` service: on the mesh alone, every tool a call on the REST core, an OAuth token traded at the hop. `server`, the MCP server `server-portable/index.ts` was, retires with that file: the REST core (`api`) builds the server image, which is also the image's default command now, and at its start marks lost the jobs `server` left running. **Upgrading:** run the stack's `up` with `--remove-orphans`, or the old `server` container keeps running beside the stack; a raw key holding a character past U+00FF, which `?key=` carried to `index.ts`, reaches no server now: mint its client a new one (deploy/README.md, "Upgrading a stack from before SMD-2287 PR 6b"). `canary.sh up` removes a canary's own. Also, before `up`, mint the MCP server's forward key — `bun server-portable/keygen.ts --name mcp-forwarder --scope forward` from a checkout, or `docker run --rm --entrypoint bun ghcr.io/mharris-sgymd/ob1-server:<X.Y.Z> keygen.ts --name mcp-forwarder --scope forward` on a release install — its hash line in `MCP_ACCESS_KEYS` and the raw key as `OB1_FORWARDER_KEY` in the stack's env file: compose refuses the stack without it (deploy/README.md, "Upgrading a stack from before SMD-2287 PR 5b"). `canary.sh up` mints a canary's own, rewriting its `MCP_ACCESS_KEYS` once (comments in it dropped; one written across lines refused until it is on one line) (SMD-2287).
- `db/rebuild.ts`, the operator's door to `rebuild_derived`, is now an importable engine: `run(opts)` runs it in-process and `sweepOrphans(sql, opts)` runs its orphan sweep on a caller's client. The CLI is unchanged (SMD-2679, the first of its PRs). The sleep scheduler's passes now run under session limits (SMD-2679, its second PR). Each pass's connections open with `statement_timeout` 300 s, `work_mem` 4 MB and `maintenance_work_mem` 64 MB (`--statement-timeout`, `--work-mem`, `--maintenance-work-mem`, and their `OB1_SLEEP_*` settings). A statement past its timeout no longer ends the scheduler (what it does now is under Changed, with the work periods). The same PR gave each sleep a 60-minute clock (`--budget`, `OB1_SLEEP_BUDGET`); the work periods replaced it before any release shipped it, so no release ran a sleep to a clock. Each sleep now begins with a re-derive pass (SMD-2679, its third PR): `rebuild_derived`'s orphan sweep deletes the lineage rows whose artifact is gone — up to 500 thoughts a sleep, no model — before extraction claims. The log says how many it swept. Re-embed's hard stop now aborts the embedding call in hand, so `db/reembed.ts`'s in-process `run()` — the sleep scheduler's, once re-embed joins sleep — returns at once rather than when that call does, up to `OB1_LLM_TIMEOUT` later; the CLI already exited on the release (SMD-2679, PR 4a-1). `db/reembed.ts --follow [SECONDS]` polls after its pass, pooling again at each poll, as the claim workers' followers do; a follower never switches the model — a configured model other than the one the brain records is refused as `model-switch` (SMD-2679, PR 4a-2a). A follower waits a database or provider outage out, and ends, refused `provider`, when the provider refuses the request itself (SMD-2679, PR 4a-2b). The sleep scheduler now re-embeds before it extracts, when the brain has vectors not at the configured embedding model; a brain with none starts no re-embed pass and calls no embedding endpoint. Whatever refuses re-embed sets it down for that sleep, and a brain recording another embedding model than the stack's sets it aside, each said in the log and on `heartbeat:sleep`, while extraction and consolidation run on (SMD-2679, PR 4b-1). **Behaviour changes:** a brain from before migration 021 has its unlabelled vectors re-embedded and labelled by its first sleeps, one embedding call a row, before extraction (`bun db/reembed.ts --dry-run` says how many), and so is a thought saved with no vector; `heartbeat:sleep` reads failed while re-embed is set aside or down for a cause the operator mends, and preflight says "its last pass failed"; a `reembed.ts --follow` run by hand keeps the scheduler from starting (2); a one-shot `sleep.ts` whose re-embed was set down or aside exits 1.
- A migration that changes which ticket status types the brain knows can now rebuild only the rows that change: `ob1_rebuild_source_gate_for_types(text[])`, added by migration 108, reconciles the dependency gate's rows for the status types given. Both it and the full `ob1_rebuild_source_gate()` hold every write to thoughts and their source rows until the migration commits; the full one runs for as long as it takes to reconcile every source row, the keyed one only for the rows of the types given. `ob1_refresh_set_readers()`, also new, makes the brain's own functions use the changed set at once in every open session rather than the one they had cached; a server's own cached statements take it when the server restarts (SMD-3160, migration 108).
- The stack serves an operator GUI at `/dashboard`: `dashboard/`, a SvelteKit server and a client of the REST core, run as compose's `app` service from the server image. Sign in with a read or write access key to see the brain's counts and newest thoughts, browse every thought a page at a time with filters, search by meaning or exact text, read what changed, the supersession proposals, the worker queue and the query log, see its status and any thought, and use the pages of the plugins `OB1_PLUGINS` turns on (the example plugin's Notes, where a write key pins a note to a thought); the key stays on the server (SMD-2280).
- `evals/eval-mediated-pairs.ts` measures whether the consolidation pass can ask the subject-anchored ADR's mediated-pair test: the typed-decision tier and the pass's chat model, against two blind raters' labels of 100 canary pairs. Neither meets its bar. The chat model's first step finds mediated pairs (κ 0.64), but no model's state step meets its bar, and the ADR's test is now version 2. So decide mode caps a mediated pair (decide version 4). The judge's model is asked the test's link step about a pair the decider calls outdates at the pass's floor, or evolves the pass would store. A pair linked only through a third subject, or by one thought naming the other's subject in passing, is stored as related at most, with no supersession proposed. The pass key moves to `@p4d4`, so a brain running decide mode judges its pool again (SMD-3203). The sleep scheduler can write each consolidation pass's verdicts, pair by pair: `OB1_SLEEP_DUMP_DIR` (or `db/sleep.ts --dump-dir`) names a directory (in compose, where the `sleep` service mounts its `sleep-dumps` volume), and each pass appends every verdict there, decide mode's link step included, to one file per pass key.
- `list_thoughts` pages: `sort` newest (the default) or oldest first, and `after`, the cursor the previous page ended with, so a GUI list or an agent can walk every thought there when it began once (newest first, one captured meanwhile is not among them; oldest first, it comes at the end). A cursor of the other sort, or no cursor of this tool's, is refused (SMD-2995).
- A supersession proposal's review can take one consolidation pass at a time. `list_supersession_proposals` (and `GET /v1/proposals`) takes `judge_key`, the pass key each proposal names — its model, or under decide mode the decider and the writer, with the prompt and decide versions — selected before the 200-row cap, and each proposal's value now carries `judgeKey`. `consolidate.ts --status` counts the pending proposals by pass; `--list <status> --key <judge key>` lists one pass's proposals, and `--list relations --key` its relations. A server or CLI from before this release reads a brain at 109 as missing migration 070: upgrade it, do not re-apply 070 (SMD-3248, migration 109).
- The consistency checker holds deploy/README.md's path table to the proxy's route tables (check 28b). A path a router routes with no row fails, as does a row answering a path no router routes with anything but a 404. A row that doesn't name its router's backend (or 404 for a router to noop@internal) fails too, and so does an overlay's row that doesn't name its overlay file (SMD-2296).
- Two maintainer scripts for CI-efficiency work. `scripts/ci-step-times.ts` prints a CI job's time and its steps' over a window of runs, with each one's median, p90, min and max. `scripts/suite-sections.ts` runs a suite and prints its sections by wall time, slowest first (SMD-3305).
- The supersession proposal listing pages. `list_supersession_proposals` (and `GET /v1/proposals`) takes `after` — the `cursor` the page before ended with — and answers `cursor` (null once no more follow) and `remaining` (how many follow), so any status or pass of more than 200 proposals can be walked page by page; `consolidate.ts --list <status> --after <cursor>` does the same, a capped page printing the line for the next. A cursor carries the filters it was made under and is refused with others. A server or CLI from before this release reads a brain at 110 as missing an earlier listing migration (070 from v1.9.0): upgrade it, and do not run the `--reapply` its preflight prints. A server left running across the migration fails its listings ("cached plan must not change result type") until it is restarted (SMD-3249, migration 110).
- `evals/eval-mediated-pairs.ts` measures five other ways of asking the mediated-pair test's link step, the step decide version 4 caps a pair on, the last two under a version 3 of the test. It records that version 4's cap missed its precision bar on the canary (0.686 against 0.7). None of the five qualifies, so decide mode is unchanged and version 4 stays (SMD-3299).
- Migration 111 records a thought's own subject: a `subject` facet, one standing per thought, keyed `ticket:`, `pr:`, `version:` or `phrase:`, with its lineage at the text's fingerprint. `record_thought_subject` writes it, refusing a text that moved since it was read. The thoughts about one subject can then be read as one work thread, in capture order (SMD-3306). The extraction pass now records each thought's own subject when a rule finds it: the ticket the thought is filed under, else a session summary's header ticket when the header lists that one alone and one of the session's prompts names it. `extract-entities.ts --subjects` finds the rest: it asks the judge model, with a question of the subject's own, about a thought no rule keys, and takes up the thoughts extracted before migration 111, edited since, or keyed under an older rule or question; `--subjects rules` asks no model. The judge model reasons before it answers unless `OB1_SUBJECT_REASONING` is off. Migration 113 gives the sweep a pool: new and edited thoughts join it, a run takes only what it holds, a thought the model named nothing for is not asked again until its text or its ticket changes, `--retry-failed` asks again those that failed, and a run under another pool's key, `--subjects rules` among them, needs `--switch-key` (SMD-3306, its second to fifth PRs). `--subjects` stops, exit 3, once more than a fifth of the judge model's last 48 answers, kept across runs, gave no subject, not JSON or naming nothing, and puts the thoughts it was answered nothing for back in its pool; `--judge-checked` runs it with that alarm off, for a judge checked and found right (SMD-3306 PR 5b). A trip holds a scheduler's following runs of each judge model whose answers gave no subject until a `--judge-checked` run of that model lifts the hold; one that a trip naming its model lands under, after it began and before its lift, ends, exit 3, nothing claimed, and a provider's transient error puts the thought back in the pool, asked again after the pause (SMD-3306 PR 6a). A scheduler's run of `--subjects` reports its start and each refusal by its kind, its check reading the pool's name as the run would; its start waits out a database not answering, up to its first claim, and probes its judge model, waiting for one not answering; past its pauses, or hung, it waits out the provider's outage as a claim pass does; a provider's transient error puts its thought back first in the pool now, a hand run's too, so a thought the provider errs on again right after answering a probe is failed as its own, for `--retry-failed`, and one whose own error makes no suspect, or that hung, goes behind the rest, dated 30 days ahead, so the thoughts pooled since come first, a hung one marked so on its claim, its next hang in any following run its own; it says those waits through its row, and runs its pooling exempt from its `statement_timeout` while watched; `--retry-failed`, and `retry_failed` on the subject pool, put a failed claim dated past now at the pool's head and clear the pool's standing hang marks (SMD-3306 PR 6b-1). The sleep scheduler runs the sweep as its fourth pass, once a period, beside consolidation once extraction has drained, its claims bounded by the period's start plus 30 days: its first period names the pool and pools the backlog, asking the judge model (`OB1_JUDGE_MODEL`, else the metadata model) one call at a time, at most about 1,200 a day for the 27B with its reasoning on; what that first period asks is settled before the scheduler runs on this release, with `sleep` out of `OB1_PASSES` meanwhile, from 1.9.0, from the `workers` pass and at a first start too: a brain whose judge model is not yet measured on the question names the rules' pool, `--subjects rules` by hand in the stack, which the scheduler then follows, asking no model (deploy/README.md's sleep pass gives the order); while the sweep's run asks the judge model, consolidation's judge calls get one of its calls in their limit too (1,020 s with the reasoning on, 420 s off), read as each call starts, since on a model server of one slot they wait it out, and a thought that hangs the provider is still failed as its own beside it; another pool named, or a garbage-judge alarm's trip, holds it until a run by hand, the scheduler never switching a pool; a refusal sets it down for the period alone, the other passes running on; a thought it set back behind the rest begins no period, and is asked once in the next period other work begins; and a paused period aborts at most three of its calls an hour (SMD-3306 PR 6b-2). Migration 120 links each work thread: the thoughts holding one subject key, in `created_at` order, each an `evolves` of the one before it, origin `thread`, kept by the database as subjects land and close and as thoughts go (a delete by a role without the structure group, a least-privilege server's, leaves its neighbours to `db/threads.ts --key` or the key's next re-link), beside the judge's relations, which their readers still count alone; `db/threads.ts` links an existing brain's threads once after the upgrade (SMD-3306 PR 7a-1). **Upgrading:** after migration 120, run `cd db && bun threads.ts --url <the owner's URL>` once, from a checkout (on the compose stack, reaching its Postgres through deploy/README's host-ports file), to link the threads a brain already holds (`--status` counts them and names the keys that differ, `--dry-run` writes nothing); until then a thread is linked only where a subject lands or leaves. A subject is written under READ COMMITTED alone: under a REPEATABLE READ or SERIALIZABLE default every subject write is refused at its commit, which preflight's isolation check names. A role that calls `close_thought_subject` needs the subject door's writes since (INSERT on `thought_facets`; INSERT, UPDATE and SELECT on `derivations`), as the subject sweep's already has. A thought deleted by a role without the structure group leaves its neighbours unlinked until `threads.ts --key` (`--status` names the key). Applying 120 remakes 084's index, holding `thought_facets` until it commits.
- The session-capture hook delivers each summary to every brain its config lists (`"brains": [{"name", "url", "key"|"key_file"}, …]`), each with its own capture key, its own queue and its own supersedes chain. A brain that does not answer waits in its own queue and delays no other. The one-brain config works as before. **Upgrading:** nothing for one brain. To add a canary, mint a capture key on it, then move the config to a `brains` list with the current brain first, so it keeps its state (SMD-3313).
- On a stack configured with the authorization server (`COMPOSE_PROFILES` naming `auth`), the operator GUI at `/dashboard` signs the operator in through it, by code with PKCE, as its `gui` client: the password and the consent at the AS, then every page under a token the GUI holds and renews itself, never in the browser. Sign-out revokes it. Key sign-in stays off on the public origin; on the brain's machine, the break-glass port `http://127.0.0.1:8001/dashboard/` (`BREAKGLASS_PORT`, published on loopback alone and only under the `auth` profile) takes an access key whatever the authorization server's state. The GUI's page of grants (`/dashboard/grants`) lists every client signed in as the operator, MCP clients and the GUI's own sign-ins, and revokes any of them: its refresh tokens are refused at once, and the access token it holds lapses within ten minutes. **Upgrading** a configured stack: `compose up -d --build --wait` from the stack's checkout, `auth` in `COMPOSE_PROFILES` — it rebuilds the server image `app` runs (a plain `up` recreates `app` on the old one, whose GUI signs no one in) and the authorization server, whose `gui` client now takes refresh tokens, and starts the break-glass port (where 8001 is taken, or another stack on the machine is configured too, set `BREAKGLASS_PORT` first); it signs everyone out of the GUI (SMD-3307).
- `capture_thought` takes a `client_key`: a UUID, by convention the thought's id on the brain where the write was first made, when a client copies the write to another brain. The copy keeps it, one thought per key (migration 112), and `update_thought`, `delete_thought` and the `supersedes` and `derived_from` of either accept it wherever they take an id: the thought with that id, else the one keeping that key. A key that names a thought already returns it and writes nothing. Only a key that can read may send one. `metadata.client_key` is the server's now: a caller's `metadata` or `metadata_patch` naming it is refused. **Upgrading:** migration 112 refuses, by name, rows that already share a `metadata.client_key` value (a caller's metadata could set the key until now); keep one per value and re-run (SMD-3314). The session-capture hook copies your writes to another brain: with a `connector` on the brain your Claude Code connector writes to and a `write_key` on each brain that should receive copies, an async `PostToolUse` hook (`--print-hook claude-code --fan-out`) repeats each capture, edit and delete that landed through that connector, in order, through each brain's own write key and queue, a capture under the first brain's id as its `client_key`. A write through any other connector (the canary's own) is not copied. **Upgrading:** nothing unless you want copies; the receiving brain needs migration 112 (`--check` says) (SMD-3314, its second PR).
- `OB1_LISTEN_HOST` names the one IP address the REST core and the MCP server listen on, for a server run outside the stack; unset, they listen on every address, as before, and compose never forwards it. A value that is no IP address, a link-local IPv6 one, or one the host does not have, stops either server at start with exit 2, in words, without printing the value. Every test suite's and smoke script's servers and children now listen on 127.0.0.1 alone and are dialled there, save a few deliberate exceptions: on every address, or dialled as `localhost`, another app on macOS could answer in their place. The vendored servers (the extensions, the integrations and the editorial-policy auditor) read `OB1_LISTEN_HOST` too; a value that is no IP address, or a link-local one, stops one at start, in words, and an address the host does not have stops it with Bun's own error (SMD-3323).
- The operator GUI edits, deletes and captures a thought, and acts on a worker pool: a thought's page links to an edit page, which saves through `update_thought` and refuses an edit from a stale read rather than overwriting the change, and to a delete page, which confirms first and asks again before deleting a thought other thoughts cite; a capture page saves a new thought through `capture_thought`, labelled with the GUI's own source, `dashboard`; the workers page retries a pool's failed rows and releases its stale leases; the proposals page accepts and rejects a supersession proposal, offering "Accept anyway" where the brain's checks refuse an accept, and shows who decided each one. Each calls the REST core under the signed-in visitor's credential, and a read session is offered none of them (SMD-3322).
- `scripts/ci-step-times.ts --shift` names each Fork Checks job or step on main whose last 3 runs all went over its line, the median of the 10 before them plus max(30 s, 20%), with the pull requests merged where it landed. A new workflow, `.github/workflows/ci-shift.yml`, runs it after each Fork Checks run on main and shows each one made at that run as a warning and a table in its summary; it blocks nothing (SMD-3467).
- A supersession proposal records who decided it, for a reject as for an accept. Before, a reject left no trace of the key that ran it unless it cleared a pointer. `consolidate.ts --list accepted|rejected` prints `decided by:` on each row (the key's name and the kind it had when it decided, or "no agent id recorded" for a run without `OB1_WORKER_KEY`), and `--accept`/`--reject` print it after deciding. Classify your keys first (`set_agent_kind`) to tell your decisions from the workers'. The `list_supersession_proposals` tool, `GET /v1/proposals` and the GUI don't show it yet. Rows decided before the upgrade get their reviewer from the audit where the decision wrote or cleared a pointer; the rest say none was recorded (SMD-2608, migration 114).
- Every brain can now record who is working on what. An agent claims a ticket, or one piece of it (`PR 1b-2`), under a lease, and gets back a token that proves the claim. Another agent's claim on the same work, even under the same key, is refused with an answer naming the holder's key and since when. A whole ticket and any of its pieces count as the same work; two different pieces don't. A claim lapses unless renewed with its token, and an operator key can release a stuck one with a reason. This release adds the database side: the `work_claims` table and the `claim_work`, `renew_work_claim`, `release_work_claim` and `list_work_claims` functions, with a new `claims` grant group. No client calls them yet: the REST and MCP operations and the label on search results come in later releases. If your server connects as a `--grant` role, re-run `migrate.ts --grant` after upgrading so the role gets the `claims` group (SMD-3597, migration 115).
- A supersession proposal can now be decided over the REST core and MCP, not only with `consolidate.ts --accept`/`--reject`. The new `review_supersession_proposal` tool (`POST /v1/proposals/{id}/review`) takes `decision: "accept"|"reject"`, an optional `direction` and `note`, and `force`. It is open to any write key, an agent's included, and the proposal records who decided. It makes the CLI's checks and refuses each by name: a text edited since judged (a stale proposal's), a lineage pair, a WRITER flag. `force: true` waives those three on an accept, as `--force` does. The `list_supersession_proposals` tool and `GET /v1/proposals` now name who decided each accepted or rejected proposal, as `consolidate.ts --list` does. **Upgrading:** the compose stack's servers connect as the database owner and need nothing. A self-hosted server role made with `migrate.ts --grant` needs it run again, for the server group's new `UPDATE` on `supersession_proposals`. Until then a decision is refused (over MCP the reply names the grant; over REST it is a `FAILED` 500 with Postgres's "permission denied"); nothing else changes (SMD-3338).
- Agents can now claim work through the brain, over REST or MCP: `claim_work` claims a ticket, or one piece of it, and returns a token once; `renew_claim` and `release_claim` act on your own claim with that token, and an operator key may force-release a stuck claim with a reason; `list_claims` shows who holds what. A claim another agent holds is refused with an answer naming the holder and when its lease ends (HTTP 409 over REST). Keep the token private: anyone holding it under your key acts as the holder, and the session-capture hook now blanks one before a summary leaves. Preflight's `work claims` row is now called `worker claims`, beside a new `ticket claims` row that checks the claim functions, the `claims` grant and whether statement logging would print a token (SMD-3598, SMD-3615).
- Fork Checks publishes every suite's assertion total to the repository wiki's Test-counts page on each push to main, with the commit and the run it came from and every job that did not succeed. The READMEs no longer quote counts, so a PR that adds an assertion edits no doc, and a consistency check keeps counts out of them (SMD-3614).
- AGENTS.md and CLAUDE.md now tell every coding agent how to claim its ticket on the stable brain: check `list_claims` before recommending or starting work, claim for a day before creating the branch, keep the token in a git-ignored `.work-claims/` file, renew at commits, pushes and resumes with the file's lease, hold the claim for a week once the PR is open, and release at merge or abandon. The session-capture hook, given the agent's own key as its claim key, renews those claims at each compaction and session end, and with its new `--claims` hook at most hourly while a Claude Code session works. It never claims or releases (SMD-3602).
- `evals/eval-priority.ts` measures whether a read puts what matters first: a seeded personal brain and board, seven prompts with a gold order each, scored by top-1, top-3 and Kendall's tau through the server's own search, keyless and in CI, with a pre-registered bar a priority read must clear and a dogfood set of "what next" sessions recorded by hand. Today's search gets top-1 on 1 of 7 prompts (SMD-3662).
- Migration 116 adds priority assertions: a key states how much an item (a thought, a ticket or an entity) matters, on one scale from 0 none to 5 critical, optionally by a due time and with a reason, and every statement is kept. The maker and its tier come from the key, never the call, and the operator's statement outranks a declared source's, an agent's and an inferred one. `assert_priority`, `clear_priority`, `priority_of` and `priority_history` are the calls, with a new **priority** grant group. ### Security
- A capture-only key's `supersedes` no longer tells it anything about the thought it names. - A capture-only key can no longer alter another key's thought by re-capturing its text. Before, the re-capture merged the key's metadata and `source` into the existing row, appended an update event in its name and moved `updated_at`, so a key that could guess a thought's text could relabel it. Migration 080 adds `p_payload.recapture` to all three `upsert_thought` forms, and the server sends `"keep"` for a capture-only key: a capture that lands on an existing row writes nothing to it, except a vector onto a row that has none (one update event, the metadata untouched, and the windows such a row may hold dropped unless its label is the vector's). The fix needs the server and the migration both, in either order: until both are in, a capture key's re-capture still merges (SMD-2539).
- A capture-only key can no longer set how another key's thoughts read through a ticket's status. - The import runner's emitters get no network. - Check 21 holds every `.sql` git tracks, `db/migrations/` included, to the SQL-safety guard rail read as statements: no `DROP TABLE`, `DROP DATABASE`/`DROP SCHEMA`/`DROP OWNED`, `TRUNCATE` with a table after it, or `DELETE FROM` whose statement has no `WHERE` of its own — comments excepted, string literals read, a refusing `BEFORE TRUNCATE ON` trigger the rule applied; the rules are `db/config.mjs`'s `DESTRUCTIVE_SQL_RULES`, and CLAUDE.md and CONTRIBUTING.md name the check (SMD-1936).
- A PR that changes `db/migrations/`, `server-portable/` or `evals/` beyond tests and docs must ship a `changes/smd-NNNN.md` fragment, or the `Repo consistency` job refuses it by file name; the ruleset record and check 20 are ready for GitHub's merge queue, which the API refuses on this user-owned repository (SMD-1857).
- `db/sync-linear.ts` keeps a brain in lockstep with the Linear board — every issue of an initiative's projects as one thought, captured when new and updated in place when it moves, through the server's own store and embedder as the actor `board-sync` — and `deploy/compose.yaml`'s opt-in `board-sync` profile runs it on a schedule (SMD-1954).
- A release job: on a `v<X.Y.Z>` tag, `.github/workflows/release.yml` publishes `ob1-server` and `ob1-migrate` to GHCR, brings the stack up from the pulled images under the full-stack job's checks plus preflight's schema-version row, and creates the GitHub release with a compose overlay pinning both images and Ollama by digest, the cut's change files and the review yield; the migrator is an image (`db/Dockerfile`), Ollama is pinned by tag in `deploy/compose.yaml`, and a release cut is two commits the assembler now orders (SMD-1860).

### Changed
- FORK.md is a 60 KB front door with a generated index; every numbered change (18–103) is one file under `changes/`, release fragments sit beside them until they are numbered, and check 15 holds the sizes, the numbering and every citation of a change number (SMD-1917).
- The search tools take a metadata `filter` and log it: `search_thoughts` and `search_thoughts_keyword` gain an optional shallow-object filter (`metadata @> filter`), the three search tools now share one search operation, and migration 045 populates `query_log.filter` and adds `arm` (hybrid|keyword) and `tier` (the writer's `OB1_TIER`), so the log records the filter, the arm and the tier of every query — keyword searches among them (SMD-1490, migration 045).
- `scripts/` is TypeScript and type-checked in CI: the thirteen `.mjs` scripts are `.ts`, with a `tsconfig.json` mirroring the server's and the type pins check 18 holds across five directories, a `Typecheck the scripts` step in the job that runs the checker, and every reference outside `changes/` following; the "node runs it too" claim goes (SMD-1870).
- `prune_query_log`'s retention delete can now seek: migration 047 adds a plain btree on `query_log.logged_at`, so the time-range `DELETE` range-scans instead of sequentially scanning the whole log. The awaited log write on the request hot path is kept deliberately — a dropped row is a lost replay for the canary — and both costs are now measured by `db/bench-querylog.ts` (SMD-1492, migration 047).
- `main`'s ruleset now requires every job in `fork-checks.yml` (twelve, was nine of twelve), on a head up to date with `main`, each check pinned to the Actions app, and admits changes only through a pull request; the ruleset is a file, `.github/rulesets/main.json`, and `check-fork-consistency` check 20 holds it to the workflow's job list (SMD-1856).
- The capture's tag extraction is `server-portable/metadata.ts` (`extractMetadata`, `metadataRefused`, and `tagsOverExisting` — what an answer writes over an existing row's tags), the `.env` reader is `db/env.ts` (`evals/env.ts` re-exports it) and the Linear GraphQL client is `db/linear-api.ts`, shared with `evals/build-linear-corpus.ts` — pure moves, so a tool that writes thoughts beside the server carries no second copy of the prompt, the search path or the access rule (SMD-1985).
